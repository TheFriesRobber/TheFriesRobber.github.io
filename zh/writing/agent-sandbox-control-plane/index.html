Agent Sandbox 二：Runtime Provider 为什么不够

从一次“Runtime 已创建但响应丢失”的故障出发，划清 Agent Control Plane 与底层 Runtime Provider 的责任。

2026/07/14 阅读 次
AgentSandboxDistributed Systems

问题

Agent 系统请求 Runtime Provider——Kubernetes 或云平台这类负责创建和停止 workload 的底层平台——创建一个 Runtime。Provider 已经创建了 workload，但响应在返回途中丢失，调用方只看到 timeout。

如果调用方立刻重试 createRuntime()，可能创建第二个 workload；如果把 timeout 当作失败，又可能遗留一个仍在运行、持续计费并持有网络权限的孤儿资源。即使 Provider 支持按 request token 去重，它也只能回答“这次资源创建有没有重复”，仍不知道：

  • 这个 Runtime 属于哪个 Agent Session，又应该挂载哪个 Workspace；
  • 当前这一代 Runtime 是否仍有执行权，环境是否已经可以执行 Tool；
  • 用户已结束 Session 时是否应该回收它。

底层平台会创建资源，不等于它拥有 Agent 的业务状态。因此，Agent 系统仍需要自己的 Sandbox Scheduler；本文把它作为业务 Control Plane 来讨论。

Provider 管物理资源，Control Plane 管业务意图

下表中的 generation 是同一个逻辑 Sandbox 下某一代 Runtime；Lease 是授予当前 generation 的有期限执行权；Ready Contract 则是 Runtime、Workspace、Lease 与执行环境共同满足后，Sandbox 才能对外可用的条件。

两层的边界可以先写成一张表：

问题Runtime ProviderSandbox Control Plane
创建、查询、停止 workloadowner发出期望并记录结果
provider resource ID、region、templateowner保存引用
Session / user / tenant identity不得推断owner
Runtime profile 与 policy执行映射后的参数owner
Workspace binding实际挂载决定应挂载什么
Lease 与 generation可承载或回传owner
Agent Ready Contract提供底层探针定义并判定
timeout 后的 orphan reconciliation提供查询与删除原语决定认领、重试或清理

Provider API 是 mechanism：它提供创建、检查和删除资源的能力。Control Plane 是 policy 与 intent owner：它记录某个 Session 期望什么 Sandbox，并把多个 Provider 的不同资源语义收敛成稳定的业务契约。

这并不意味着 Control Plane 要重新实现 Kubernetes 或云平台调度。节点选择、镜像拉取、容器重启等物理机制仍由 Provider 负责；Control Plane 只保留 Provider 无法替 Agent 应用决定的状态。

Session Identity 必须独立于 Provider Resource

一个 Session 可以经历多个 Runtime：

session_12
  desired sandbox profile: code-agent.v4
  workspace: workspace_7
  current generation: 42

generation 41 → provider resource workload_a → expired
generation 42 → provider resource workload_b → ready

如果把 workload_a 的 ID 当作 Sandbox identity，Runtime 替换后就只能创建“新 Sandbox”，上层很难表达同一个 Session 的连续性。反过来，Session ID 也不应传给 Provider 充当唯一物理资源 ID：一次 replacement、蓝绿升级或 orphan recovery 可能需要同时观察多个 workload。

Control Plane 需要同时保存逻辑 identity 与物理 binding，并明确哪个 generation 当前有效。Provider resource 是 observed state 的一部分，不是业务 owner。

Desired State 与 Observed State 不能合成一个 Status

Control Plane 的核心记录不是“容器现在是什么状态”，而是期望与观察之间的差异：

{
  "sandbox_id": "sandbox_session_12",
  "spec": {
    "desired_state": "active",
    "runtime_profile": "code-agent.v4",
    "workspace_id": "workspace_7"
  },
  "status": {
    "phase": "provisioning",
    "generation": 42,
    "provider_ref": "workload_b",
    "conditions": {
      "runtime_reachable": true,
      "filesystem_writable": false,
      "lease_fresh": true
    }
  }
}

spec.desired_state=active 表达业务意图，status.phase=provisioning 表达当前观察。两者短时间不同是正常情况；Controller 应继续 Reconcile。若用户此时请求停止，desired state 可以立即改为 stopped，即使 Provider 还没有完成删除。

只保留一个 status=running 会丢失方向：系统不知道应该继续修复它、等待它、还是终止它。

Create Timeout 之后先进入 Unknown，再 Reconcile

回到开场故障。Control Plane 应在调用 Provider 前先持久化逻辑 Sandbox identity 和稳定的 operation identity。下面的 operation_key 表示这次逻辑创建动作；同一动作发生物理 retry 时，它保持不变，单次 Provider 调用才称为 Attempt。

sandbox=sandbox_session_12
generation=42
provider_operation=create
operation_key=sandbox_session_12:42
state=dispatched

Provider 返回 timeout 时，Control Plane 不能断言“没有创建”。它把这次物理操作标记为 unknown，然后通过 Provider 能力恢复：

  1. 按 operation_key 或 labels 查询既有 resource。
  2. 找到唯一、参数匹配的 workload 时，认领并保存 provider_ref。
  3. 找到多个候选时，保留一个符合 policy 的资源，隔离并清理其余资源。
  4. 明确确认不存在，且去重窗口仍有效时，才用同一 operation identity 重试。
  5. 无法安全判断时，保持 reconciliation / manual repair，而不是生成新 identity。

Provider 最好提供幂等创建、按外部 key 查询和条件删除；这些能力让恢复更可靠。但由谁认领资源、是否仍符合当前 Session desired state，仍由 Control Plane 决定。

Ready 是 Control Plane 的提交条件

Provider 的 Running 或 created 不能直接映射为 Agent Ready。Control Plane 需要组合：

  • Provider resource 已绑定且仍属于当前 generation；
  • Workspace 挂载身份正确；
  • Runtime Contract 的初始化条件成立；
  • Lease 尚有足够 headroom；
  • build、policy 与 network contract 没有漂移。

只有这些条件在发布时仍共同成立，Acquire 才能返回 Runtime endpoint。Ready 之后也不是永久事实：Lease 会到期，Runtime build 会变化，探针会失败。Control Plane 要刷新 Ready Contract，或把 Sandbox 移出可分配集合。

Acquire、Refresh、Release 与 Expire 是业务动作

底层平台通常只有 create、get、delete；Agent 需要更高层的生命周期：

动作Control Plane 的语义
Acquire找到或创建满足 Session Contract 的 Runtime，并返回当前 generation
Refresh续约 Lease、重新验证 Ready Contract，不改变逻辑 Session
Release调用方不再占用当前执行权；按 policy 保温、回池或停止
ExpireLease 或 Ready Contract 超时，禁止继续分配并触发收敛

Release 不必等于立刻删除 workload。高频 Agent 可以把 Runtime 保持一段时间以降低下次延迟；但保温资源不应继续携带已经失效的执行权。业务 Lease、Workspace 访问与物理资源生命周期要分别处理。

Reconciliation 需要稳定查询和条件写入

一个可靠 Controller 会反复执行：

load desired + last observed state
        ↓
query provider / storage / lease facts
        ↓
compute one safe next action
        ↓
commit with expected generation/version

最后一步必须带条件。若 Controller 在查询后，用户已经把 desired state 改为 stopped，旧 reconciliation 不能再把 Runtime 发布为 Ready。generation、resource version 或 compare-and-swap 用来阻止迟到结果覆盖新意图。

Kubernetes controller 同样以 desired state、current state 和控制循环为基本模型。Agent Control Plane 借用的是这套收敛方式，不是要求每个系统都实现 Kubernetes CRD。

Provider Adapter 要归一化能力，不掩盖差异

多 Provider 系统常把接口压缩成：

create()
get()
delete()

这会掩盖恢复真正依赖的差异：是否支持 idempotency key、能否按 label 查询、创建结果是否最终一致、停止是否同步、Volume 何时可挂载、Runtime readiness 如何探测。

更安全的 adapter contract 会显式声明这些 capability，并把 Provider 原始状态翻译成 Control Plane 可解释的 observation。缺少某项能力时，Control Plane 应选择更保守的流程，而不是假装所有 Provider 都有相同保证。

回到问题

Runtime 创建请求 timeout 后，底层平台只拥有 workload 的物理事实；它不知道这个资源是否仍符合 Agent Session 的当前意图。

Sandbox Control Plane 先持久化 Session identity、desired state、generation 和 operation identity，再调用 Provider。结果未知时，它查询、认领或清理物理资源；条件满足后才发布 Ready；用户停止或 Lease 过期后，再驱动 Release 与回收。

Provider 负责把资源创建出来，Control Plane 负责证明“这一个资源，现在可以代表这一个 Session”。两层都不可少，但它们不能共同拥有同一个语义决定。

后续问题

  • Acquire 跨越 Volume binding、Runtime creation 和初始化时，具体状态机怎样设计。
  • Runtime 替换时，Workspace 怎样保持逻辑连续性。
  • Warm Pool、Volume Pool 与 Runtime Profile 应怎样进入调度决策。
