Agent 每轮应该暴露哪些能力

区分 instruction resource、Tool surface、Connector 与 MCP，决定模型本轮真正可见的能力。

2026/07/24 阅读 次
Agent CoreAgentToolsSkills

问题

一个宿主接入了搜索、文件、数据库、工单、邮件和几十个业务 Tool，还加载了若干 Skill 与 MCP server。最简单的做法是把所有描述都放进每次模型请求，让模型“自己选择”。

结果往往相反：相似 Tool 互相干扰，高权限动作在无关任务中出现，Context 被大量 schema 占用，动态发现的新能力又绕过了原来的 policy。接入能力与暴露能力不是同一件事。

先把四种“能力”分开

Tool、Skill、Connector 和 MCP 常被统称为 capability，但它们回答不同问题：

抽象主要责任
Tool模型可以提出什么结构化动作
Skill可复用的工作方法和指令资源
Connector外部身份、credential 与系统访问边界
MCP能力发现和调用的协议接口

一条调用链可以同时使用四者：Skill 告诉 Agent 如何处理工单，MCP 暴露可发现 Tool，Connector 解析用户 credential，最终 Tool definition 进入模型请求。把它们压成一个 registry，会让 instruction、执行权和凭证 owner 混在一起。

Surface 是本轮解析出的视图

Registry 表示宿主知道哪些能力；当前 Model Turn 的 surface 则是经过任务、身份和 policy 解析后的结果。

normalized capability inputs
          ↓ discovery
task + identity + policy
          ↓ resolve
turn-scoped capability surface

Tool definition 在进入这条链之前，就应该按用户意图、权限和副作用划分好。本文不重新决定一个 endpoint 应拆成几个 Tool，只消费已经规范化的定义。

最终 surface 需要回答：

  • 当前模型看见哪些 Tool；
  • 哪些 Skill 内容已进入 prompt，哪些只能显式调用；
  • discovery 结果是否仍需授权；
  • 能力来自哪个版本和 source；
  • 下一 Turn 重新解析时，哪些变化才生效。

Eager、deferred 和 disabled 是不同状态

少量高频、低风险且容易区分的 Tool 可以 eager 暴露。大量相似、低频或昂贵的能力更适合 deferred discovery。被 policy 禁止的能力则是 disabled，不能因为搜索命中而解锁。

Tool Search 返回的是 candidate，不是执行权。一个完整的 deferred 路径应当是：

search query
→ candidate definitions
→ identity/policy filter
→ schema/version check
→ next-turn surface

若搜索结果直接进入当前正在生成的模型请求，模型输入就失去稳定 snapshot；若搜索绕过 policy，discovery 就变成权限提升通道。

Pi 的 Skill 与 resource 边界

Pi 当前把 Skill 表示为带 name、description、content、filePath 等信息的指令资源。需要区分三件事：

  • package utility 负责发现、加载和格式化 Skill；
  • host 决定哪些 concrete resources 与 prompt 进入 Harness；
  • Harness 提供显式 skill() invocation 等运行边界。

这不等于 Harness 自动拥有完整 Skill registry 或 package governance。Version、pin、dependency、rollback，以及 Skill 需要哪些 Tool、文件或环境，是宿主可以增加的 provenance contract，不是 Pi 当前字段已经保证的能力。

相关实现可参考 Pi 的 skills.ts 和 agent-harness.ts。

用两个任务检查最终 Surface

任务一是“搜索并总结公开文档”。它需要搜索和读取 Tool，也许需要相关 Skill；不需要邮件发送、工单修改或用户私有 credential。

任务二是“根据批准的内容更新工单”。它可能需要工单 Connector、当前用户授权和写入 Tool，但仍不应自动获得邮件或数据库管理能力。

两次解析可以使用同一个 registry，却得到不同 surface：

read task  → search, read
write task → search, read, update_ticket

如果动态 discovery 找到 delete_ticket，policy 仍可把它留在 disabled set。能力是否“存在”、是否“被发现”、是否“对本轮可见”和是否“获准执行”必须是四个不同判断。

回到问题

接入很多 Tool、Skill、Connector 和 MCP server 后，正确做法不是把它们全部塞给模型，而是：

  1. 先让各能力保持自己的责任边界；
  2. 消费已规范化、带 provenance 的 capability inputs；
  3. 用任务、身份和 policy 过滤 discovery 结果；
  4. 把最终集合固定进下一次 turn snapshot；
  5. 执行时仍由 Tool 和 backend 重新验证授权。

能力表面是一份 turn-scoped view，不是全局 registry 的复制。它越小、越可解释，模型越容易选对动作，安全边界也越不依赖模型“自觉忽略”不相关能力。
