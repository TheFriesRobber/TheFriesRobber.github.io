Capability Integration 五：文件不能只是 Message Attachment

沿一份 PDF 的上传、派生、编辑与下载过程，区分 Blob、Artifact、Workspace Path 和 Message Reference 的身份与生命周期。

2026/07/15 阅读 次
AgentFilesInfrastructure

问题

用户在手机上上传 requirements.pdf，让 Agent 整理成项目计划。Agent 抽取文本，在 Workspace 里多次修改 plan.md，最后生成 plan.pdf。第二天，用户在电脑上继续修改；一周后，他删除了最初那条上传消息。

如果系统只保存消息上的 Attachment 记录和下载 URL，删除消息后就会出现一连串无法由 Attachment 回答的问题：

  • 原 PDF、抽取文本、编辑稿与最终报告分别由谁保留？
  • 电脑端应打开 Workspace 中的最新草稿，还是消息里曾经展示的版本？
  • 下载链接过期或用户删除源文件时，哪些内容才算真正删除？

这些不是“把 URL 存久一点”就能解决的问题。Message Attachment 只能说明当前消息怎样指向文件；如果它同时承担内容、业务身份、工作路径和访问入口，当 Message 生命周期结束，其他对象便失去了各自的 owner。

一条文件链上其实有五种对象

以这次任务为例，可以先把对象拆开：

Upload upload_17
  └─ Blob sha256:ab...              原始 PDF 字节
       └─ Artifact artifact_source_17  requirements.pdf v1
            ├─ Artifact artifact_text_18  extracted.txt v1
            └─ Workspace Path /project/plan.md
                 └─ Artifact artifact_report_25  plan.pdf v3

Message message_8 ──references──> artifact_source_17
Message message_21 ─references──> artifact_report_25

这五种对象回答不同问题：

对象稳定身份代表什么典型 owner生命周期依据
Upload一次接收文件的动作Upload service接收完成、失败或过期
Blob一组不可变字节Object storage / blob service引用、保留策略与合规要求
Artifact系统可解释的一份输入或产物Artifact service业务 owner、版本、provenance、retention
Workspace Path当前工作目录中的可变名称Workspace ownerSession / Task 的工作生命周期
Message Reference某条消息怎样展示或引用 ArtifactConversation ownerMessage 生命周期

一个实现可以把其中几类数据存进同一张表，但不能因此合并语义。message_8 被删除，只能直接删除它对 artifact_source_17 的引用；是否删除 Artifact、Blob 和派生产物，必须继续按照各自的 owner 与 retention 判断。

Blob 保存字节，Artifact 保存业务身份

Blob 最适合表示不可变内容。用内容摘要作为 key，可以让相同字节去重，也能在复制后验证内容是否变化：

{
  "blob_id": "sha256:ab12...",
  "size": 284193,
  "media_type": "application/pdf"
}

但相同字节不等于同一个业务对象。Alice 和 Bob 可以分别上传完全相同的模板；一次上传可能是合同原件，另一次只是示例。它们可以安全地指向同一份物理 Blob，却必须拥有不同的 Artifact identity、authorization 和 retention。

{
  "artifact_id": "artifact_source_17",
  "owner": {"type": "user", "id": "user_7"},
  "kind": "source_document",
  "version": 1,
  "blob_ref": "sha256:ab12...",
  "created_from": {"upload_id": "upload_17"}
}

因此，content-addressed identity 适合证明“内容是否相同”，不能独自证明“这是谁的文件、为什么存在、谁能读取”。Artifact 才是 policy 与业务生命周期应绑定的对象。

Workspace Path 是可变工作名，不是版本身份

/project/plan.md 对 Agent 很重要，因为 Tool 需要通过一个稳定路径反复读取和写入。但路径表达“当前这个名字指向什么”，并不天然保存历史版本。

第一次写入可以建立：

/project/plan.md → workspace_file_9 revision 1 → blob sha256:c1...

修改后，同一路径可能变成：

/project/plan.md → workspace_file_9 revision 2 → blob sha256:d8...

如果用户要求“把昨天的版本导出为 PDF”，只保存路径就无法回答“昨天的版本”是哪一组字节。Workspace owner 至少需要 revision、内容引用和并发写入条件；需要交付、审计或跨 Session 使用时，再把某个 revision 提升为独立 Artifact。

并非每次按键都要创建 Artifact。Workspace 可以高频保存内部 revision；当文件成为输入、检查点、审批对象或最终交付物时，再创建稳定的 Artifact identity。这样既不会把工作目录变成不可控的版本仓库，也不会让重要产物只剩一个随时会变化的路径。

派生关系必须记录输入版本和生成方

extracted.txt 和 plan.pdf 都不是凭空出现的。它们需要记录由什么输入、什么处理过程和哪个版本生成：

{
  "artifact_id": "artifact_report_25",
  "kind": "report",
  "version": 3,
  "blob_ref": "sha256:f4...",
  "derived_from": [
    {"artifact_id": "artifact_source_17", "version": 1},
    {"workspace_file_id": "workspace_file_9", "revision": 7}
  ],
  "generated_by": {
    "type": "program",
    "name": "pdf_renderer",
    "execution_id": "job_pdf_25"
  }
}

这里的 generated_by 必须明确生成方。文本可能由模型生成，PDF 字节则可能由确定性的渲染程序生成；如果只写“AI 生成”，读者和系统都无法判断该重跑模型、重跑渲染器，还是直接复用已有 Blob。

Provenance 不要求复制完整执行日志，但至少要能定位输入 identity 与 version、转换类型、生成方及对应 execution。W3C PROV 也把 derivation 建模为实体之间由活动建立的生成关系，而不是仅靠相似文件名猜测来源。

下载链接是访问能力，不是 Artifact 身份

跨设备下载通常需要一个短期 URL。这个 URL 应被看成授予某个 Artifact version 的访问能力：

download capability
  subject=user_7
  artifact=artifact_report_25@v3
  expires_at=2026-07-22T10:00:00Z
  disposition=attachment

链接过期只表示访问能力失效，不表示 Artifact 或 Blob 已删除。反过来，Artifact 被撤销或失去授权时，即使 URL 尚未到期，下载层也应拒绝访问。AWS S3 的 presigned URL 同样把有效期与签名凭证作为访问约束；它不是对象的长期业务 identity。

Message 中最好保存 Artifact reference，由读取时的授权服务签发新链接，而不是把某次签出的 URL 当作永久附件字段。这样用户换设备、链接过期或权限变化时，系统仍能对同一个 Artifact 重新做 policy 判断。

Retention 与删除要沿引用关系收敛

删除不能只从对象存储执行一个 DELETE。它至少包含三层决策：

  1. Conversation owner 删除 Message Reference。
  2. Artifact owner 判断 Artifact 是否仍被 Task、Workspace、交付记录或合规策略保留。
  3. Blob owner 在没有有效引用且 retention 已满足后，才回收物理内容。

派生关系也不意味着级联删除。删除原 PDF 后，最终报告可能因为已交付而需要继续保留；但它的 provenance 应记录源文件已删除或不可访问。若 policy 要求“删除源文件及所有可逆派生物”，则 Artifact service 应沿 lineage 生成一组可审计的删除计划，而不是让对象存储根据路径前缀猜测。

版本化对象存储还会带来一个容易忽略的边界：删除当前 key 可能只创建 delete marker，旧 version 仍存在。业务层的 artifact.deleted、下载授权撤销与物理擦除完成应是可以区分的状态。

因此，清理通常是异步收敛：

Artifact marked deleted
  → revoke capabilities
  → detach references
  → evaluate descendants and retention
  → delete eligible blob versions
  → record erasure outcome

只有最后一步成功，系统才可以声称对应物理版本已被擦除；中间失败应保持可重试状态，而不是把数据库中的 deleted=true 当作全部完成。

最小 Artifact Contract

一份会跨 Message、Session 或设备使用的文件，至少需要这些字段：

  • 稳定的 artifact_id、owner 与 kind；
  • 指向不可变内容的 blob_ref、media type、size 与 integrity digest；
  • Artifact version 或所引用的 Workspace revision；
  • provenance：输入版本、转换类型、生成方和 execution identity；
  • authorization 与可撤销的访问入口；
  • retention、删除状态及物理擦除结果；
  • 引用它的 Message、Task、Workspace 或交付记录。

这并不要求所有文件都永久保存。它要求每个删除和保留决定有明确 owner，并且 URL、路径与 Message 不再冒充文件本身。

回到问题

删除最初的上传消息，只应先删除 message_8 → artifact_source_17 这条引用。原 PDF 是否保留，由 Artifact owner 根据 Task、retention 与用户删除意图决定；Workspace 中的 plan.md 继续由 Workspace 生命周期管理；最终 plan.pdf@v3 仍可作为已交付 Artifact 在电脑端重新授权下载。

文件一旦进入 Agent 的长期任务，就不再只是 Message 上的一个 Attachment。Blob 保存字节，Artifact 保存业务身份与来源，Workspace Path 提供可变工作名，Message Reference 负责展示，下载 URL 只提供有期限的访问能力。把这些身份拆开，系统才有可能对版本、跨设备访问、删除和审计给出一致答案。

后续问题

  • Runtime 更换后，Workspace Path 怎样继续指向同一份持久文件。
  • Artifact 与 Workspace 之间怎样安全地导入、导出和冻结版本。
  • 大文件进入 Model Context 时，怎样做解析、分块与引用而不复制全部内容。
