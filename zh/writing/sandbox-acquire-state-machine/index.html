Agent Sandbox 三：Runtime 创建成功为什么还不等于 Ready

把 Volume binding、Runtime creation、挂载、初始化和 Ready 发布拆成可恢复的提交边界。

2026/07/14 阅读 次
AgentSandboxDistributed Systems

问题

createRuntime() 已经返回成功，Agent 的第一个命令却偶尔报：

ENOENT: /workspace/project

这发生在 Acquire——系统从接受请求，到准备 Runtime 与 Workspace，再返回一个可执行 Sandbox 的完整过程——过早结束时。重试几秒后命令又能成功。另一次故障中，Runtime 已经存在，但 Scheduler 在收到 Provider 响应前重启；恢复后的 Scheduler 再创建一个 Runtime，留下两个 workload。还有一次，Volume 已经挂载，初始化脚本失败，系统却仍把 Sandbox 标成 Ready。

这些表面上是三个 bug，根因却相同：Acquire 被实现成一个同步函数，createRuntime() 的返回被当作“可执行 Sandbox 已获得”。实际上，Volume、Runtime、mount、filesystem initialization 和 readiness 分别由不同系统完成，也有不同的结果未知边界。

本文中，Provider 负责创建、查询、挂载和停止物理资源；Sandbox Scheduler 是业务 Control Plane，持有 Session intent、generation、Lease 与 Ready 发布权。后文所有状态转换都沿用这个分工。

Acquire 返回的是已提交契约，不是创建响应

Acquire 的目标不是“拿到一个 Runtime ID”，而是发布一份同时满足以下条件的 Ready record。这里，generation 表示同一逻辑 Sandbox 下单调递增的 Runtime 代次，每次替换 Runtime 都要递增；Lease 记录当前 generation 的有期限执行权；Ready record 则是 Control Plane 确认这些事实共同成立后才允许返回的持久记录：

runtime bound to current generation
∧ intended workspace mounted
∧ filesystem initialized and writable
∧ runtime contract verified
∧ lease still fresh

每个条件都有独立 owner，所以中途状态必须持久化。否则 Scheduler 重启后只能从头再做一遍，既不知道哪些副作用已经发生，也无法判断哪些动作可以安全重试。

用 Phase 表达阶段，用 Condition 表达事实

一个可恢复的 Acquire 可以采用这些主要 Phase：

Requested
  → Binding
  → Starting
  → Mounting
  → Initializing
  → Ready

错误和恢复不应覆盖主线 Phase。保留最后一个已提交的业务 Phase，再用 active_operation、稳定 operation identity 与 operation_status=unknown|reconciling 表示哪个外部动作结果不确定、Controller 正在查询什么。Operation identity 在同一外部动作的 retry 与 recovery 之间保持不变，因此重启后仍可查询原结果；一次实际发给 Provider 的物理调用则称为 Attempt，同一个 operation 可以经历多个 Attempt。Failed 表示当前 generation 已经到达不可自动恢复的终态；若要重建 Runtime，必须创建新 generation。

同时，用 Conditions 保存可组合的观察事实：

{
  "phase": "Mounting",
  "active_operation": {
    "kind": "mount_workspace",
    "operation_id": "mount:sandbox_12:42",
    "status": "reconciling"
  },
  "conditions": {
    "volume_bound": true,
    "runtime_created": true,
    "workspace_mounted": false,
    "filesystem_initialized": false,
    "runtime_contract_ready": false
  }
}

Phase 告诉调用方当前主要等待什么，Conditions 告诉 Controller 哪些事实已经成立。仅靠十几个线性 status 会快速陷入状态组合爆炸。

每个阶段都要定义提交事实

Phase进入前已提交的事实成功后提交什么主要 owner
RequestedAcquire identity、Session、desired profile、generation当前请求可开始分配Control Plane
BindingWorkspace identity 已解析Volume / claim 与 Session bindingWorkspace owner
Startingbinding 与 operation identity 已由 Control Plane 保存Provider 创建物理资源；Control Plane 保存 provider binding recordProvider 拥有物理资源事实；Control Plane 拥有绑定记录与状态转换
MountingRuntime 与 Volume identity 已知Runtime 内观察到正确 mount identityProvider + runtime init
Initializingmount 已验证目录、权限、基础文件与依赖初始化完成runtime init
Ready所有必要 Conditions 成立带版本与有效期的 Ready recordControl Plane

“成功后提交什么”是 crash recovery 的起点。比如 Provider resource ref 只存在于进程内存中，Scheduler 在 Starting 之后崩溃，就无法删除或认领已创建的 Runtime。

因此，在调用 Provider 前，Control Plane 要先保存 operation identity；Provider 拥有物理资源及其状态，Control Plane 在创建或发现资源后尽早保存 provider binding record，再等待耗时 readiness。持久化顺序比函数调用顺序更重要。

Desired State 可以在任意阶段改变

用户可能在 Mounting 时取消任务。此时不能强迫状态机先走到 Ready 再 Release。Control Plane 应把：

desired_state: active → stopped

作为独立事实提交。Controller 观察到它后，停止继续初始化，转入清理路径：

Binding / Starting / Mounting / Initializing
        └─ desired=stopped → Releasing → Terminated

当前 Phase 表示已观察到的进度，desired state 表示要收敛到哪里。把二者分开，取消和超时才能从任意中间态安全发生。

三种 Timeout 需要三种处理

Binding timeout：未必可以换一块 Volume

如果 Workspace owner 明确确认没有创建 binding，可以重试同一 binding identity。若请求 timeout、结果未知，则必须先查询 Session 是否已经绑定 Volume；直接分配另一块 Volume 可能让同一 Workspace 出现两个内容分支。

Starting timeout：先查询 Provider

Provider 已经创建 Runtime 但响应丢失时，当前 operation 进入 Unknown。Controller 按 operation key、label 或 generation 查询：

0 个匹配资源 → 在幂等边界内重试
1 个匹配资源 → 认领并保存 provider_ref
多个匹配资源 → 选定一个，隔离其余资源
无法判断       → 保持 Reconciling / 人工修复

timeout 不是“创建失败”的证据。

Ready timeout：资源存在但契约未成立

Runtime 可以一直 Running，但 Workspace mount 或初始化条件没有满足。此时 retry createRuntime() 通常无效；Controller 应检查 Condition，决定修复初始化、创建新的 generation 来替换当前 Runtime，或把当前 generation 标记为 Failed。

这三类 timeout 使用相同的错误字符串，会让自动恢复采取错误动作。错误需要携带阶段、operation identity、结果是否确定以及可重试条件。

Ready 发布必须防止迟到结果

假设 generation 41 的初始化探针很慢。用户重试后，generation 42 已经获得 Lease 并完成 Ready；这时 41 的探针才返回成功。

Ready 写入必须原子比较它声称共同成立的全部 binding。下面的 SQL 只展示这些条件，不代表所有字段必须位于同一张表：

UPDATE sandbox
SET phase = 'Ready', ready_contract = ...
WHERE sandbox_id = ?
  AND generation = 41
  AND desired_state = 'active'
  AND provider_ref = ?
  AND workspace_binding_version = ?
  AND lease_generation = ?
  AND lease_expires_at > now()
  AND contract_version = ?
  AND resource_version = ?;

若 generation 已是 42，或同一 generation 下任一 provider、Workspace、Lease 与 Contract binding 已变化，更新影响 0 行，迟到结果进入 reconciliation。仅在应用内检查一次、再无条件写数据库，仍存在检查与写入之间的竞态。任何 Runtime replacement 都应递增 generation；若实现另有 attempt identity，凡提交该 Attempt 结果的条件写入也必须比较它。

Ready record 还应绑定 runtime_id、workspace_binding_version、lease_generation 与 contract_version。否则，它可能由不同时间的几个“成功”拼成一个实际上从未成立过的状态。

Scheduler 重启后从持久事实继续

恢复流程不是重新调用整个 acquire()。Controller 读取当前 Phase、Conditions 与外部 identity：

phase=Starting
operation_key=sandbox_12:42
provider_ref=null

它知道 Provider 调用可能已经发生，于是先 query；若状态是：

phase=Initializing
provider_ref=workload_b
workspace_binding=volume_31@v9

则先探测 workload 与 mount，再继续初始化或清理。每个阶段都必须能回答：

  • 哪些副作用可能已经发生？
  • 用什么 identity 查询？
  • 哪个动作可安全重试？
  • 当前 desired state 是否仍要求继续？

不能回答这些问题的中间态，不是可恢复状态机，只是日志里的进度文字。

可观测性要按阶段定位等待

只监控总 acquire_latency，无法区分 Provider 启动慢、Volume binding 堵塞还是初始化失败。至少应记录：

  • 每个 Phase 的进入时间、停留时间与退出原因；
  • 当前最老的非终态 Acquire；
  • unknown / reconciling 数量及年龄；
  • 各 Condition 失败原因；
  • Ready timeout 发生在哪个阶段；
  • orphan Runtime 与重复 Volume binding 的清理结果。

高分位延迟还要按 cold create、warm reuse 和 recovery 分开。Warm hit 与首次创建混在一起，平均值既不能代表用户等待，也无法验证优化落在哪一段。

状态机不必等于一张巨大的表

状态可以存成当前 Snapshot、追加事件或两者结合。关键不是表结构，而是：

  • 每次外部动作前后都有稳定 identity 与提交边界；
  • 状态转换由明确 owner 条件写入；
  • Controller 能根据持久事实重复执行；
  • 结果未知不会被伪装成明确失败；
  • terminal state 不会被迟到响应重新打开。

实现可以让 Workspace service、Provider 和 Control Plane 各存自己拥有的事实，再由 Control Plane 投影当前 Acquire 状态。不要为了“一个状态机”强迫所有系统共享一个 status 字段。

回到问题

createRuntime() 成功只证明 Provider 创建了计算资源。/workspace/project 是否存在，还取决于正确 Volume 已绑定、Runtime 实际观察到 mount、初始化完成并且当前 Lease 仍有效。

把 Acquire 拆成 Requested、Binding、Starting、Mounting、Initializing 与 Ready，并为 Unknown、Reconciling 和清理路径保留明确语义，Scheduler 才能在 timeout、重启和取消后从持久事实继续。Ready 是这些事实同时成立后的一次条件提交，不是某个 Provider API 的成功回包。
