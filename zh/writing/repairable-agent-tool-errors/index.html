Agent Tools 五：让 Tool Error 帮助模型修复

从一次无法修复的参数错误出发，设计能告诉模型下一步该改什么、能否重试的 Tool Error contract。

2026/07/14 阅读 次
AgentToolsAPI Design

问题

用户让 Agent 把一个任务分配给“Alex”。模型调用 assign_task：

{
  "task_id": "task_17",
  "assignee": "Alex"
}

后端发现同名用户不止一个，返回：

400 invalid body

模型知道调用失败了，却不知道错在字段格式、权限、资源状态，还是 Alex 无法唯一匹配。下一轮只能猜：把名字改成小写、重复原调用，或者换一个根本不存在的字段。即使多试几次，修复成功也主要来自运气。

对人类开发者来说，异常字符串可以作为排查入口；对处在控制回路里的模型来说，Tool Error 还要回答另一个问题：下一步允许改变什么，改变以后是否值得再次调用。

错误如果只描述异常，就没有修复方向

一次 Tool Call 可能在不同边界失败：请求没有进入 handler、参数无法解析、业务对象不满足条件、调用者无权执行，或者外部副作用的结果无法确认。

如果这些情况最后都变成 invalid request，Runtime 会丢掉三类关键信息：

  • 哪个边界拒绝了调用。
  • 模型能否通过修改参数解决。
  • 再次执行会不会重复已经发生的副作用。

所以，面向模型的错误不能只是内部 exception 的字符串版本。它需要是一份稳定 contract，把实现细节转换成模型可以采取的有限动作。

JSON-RPC 2.0 的 Error Object 已经区分 code、message 和实现定义的 data；RFC 9457 也为 HTTP API 定义了机器可读的 problem detail。它们说明错误响应应该有稳定结构，但不会替 Agent Runtime 决定哪些字段可以安全地交给模型，也不会定义怎样修复一次 Tool Call。

先区分失败边界，再判断谁能修复

最小分类不需要覆盖所有异常类型，但必须保留责任边界：

Failure class发生位置模型通常能否修复例子
transport请求发送、连接或协议层不一定connection reset、响应无法解析
validation参数结构和字段约束通常可以缺少 task_id、日期格式错误
domain当前业务状态取决于错误同名对象、任务已关闭
policyauthorization 或安全策略通常不应靠改写参数绕过当前 actor 无分配权限

这里的分类不是让模型理解后端架构，而是限制错误后的动作。

validation 可以指出应修正的字段；domain 可以提供受限候选或建议先读取最新状态；policy 应明确拒绝，不能暗示模型换一种参数就能绕过；transport 则需要结合幂等和副作用状态判断是否可以 retry。

分类以后，开场中的错误不再是宽泛的 400，而是一个可操作的 domain failure：名字存在，但不能唯一定位目标。

Error envelope 要表达下一步允许做什么

一种概念性 envelope 可以写成：

{
  "status": "failed",
  "error": {
    "code": "assignee_ambiguous",
    "class": "domain",
    "message": "More than one assignee matches 'Alex'.",
    "field": "assignee",
    "same_request_retryable": false,
    "repairable": true,
    "requires_user_input": true,
    "next_action": {
      "type": "ask_user_to_choose",
      "field": "assignee",
      "max_resubmissions": 1
    },
    "hint": "Ask the user to choose one candidate before resubmitting.",
    "candidates": [
      {"id": "user_12", "label": "Alex Chen · Payments"},
      {"id": "user_29", "label": "Alex Li · Risk"}
    ]
  }
}

这些字段承担不同职责：

  • code 是低基数、可版本化的机器判断，不应直接使用 exception class name。
  • class 表明失败边界，帮助 Runtime 选择 repair、retry、拒绝或人工确认。
  • field 把问题定位到模型能修改的输入。
  • hint 为人类和模型补充简短说明，机器决策不能只靠解析这段文字。
  • candidates 提供后端已经确认存在的选择，避免模型继续编造 ID。
  • same_request_retryable 只回答“原参数不变时是否值得重试”，不证明上一次没有产生副作用。
  • repairable 表示执行可以继续恢复，不等于模型已经拥有消解歧义所需的事实。
  • requires_user_input 和结构化 next_action 表达必须先向谁取得信息、允许修改什么，以及最多重新提交几次。

Agent 根据这份响应向用户展示两个有权查看的候选；用户确认 Alex Chen · Payments 后，模型才把 assignee 从模糊名字换成 user_12。Runtime 仍会重新做 schema validation、authorization 和 backend state check；错误提示和用户选择共同形成新提案，不是绕过可信校验的凭证。

如果后端能够用用户原始条件确定唯一结果，next_action 可以允许模型自主改写；只要仍有多个合法候选，repairable 就应该把流程引向澄清，而不是授权模型从展示标签中猜一个。

Candidate 和 Hint 必须有界

把所有搜索结果、数据库字段或 stack trace 返回给模型，看似能提高修复率，实际会扩大数据暴露和 prompt injection 面。

Candidate 应满足三个条件：

  1. 只包含当前 subject 有权看到的对象。
  2. 数量有上限，并提供稳定 ID 与最小区分信息。
  3. 内容按外部数据处理，不能因为出现在 error 中就成为可信 instruction。

如果匹配结果太多，正确响应不是把几百个用户塞进 Context，而是要求模型补充过滤条件，或者先调用受控 search Tool。

Hint 也不应泄漏内部表名、SQL、路径和 exception message。task row lock failed in shard_3 适合内部日志；task_state_changed 和“重新读取任务后再决定”才是面向模型的动作边界。

重试标记不能掩盖未知副作用

参数错误发生在执行前，可以明确返回 failed。但如果 Tool 已向外部服务发出写请求，随后等待响应 timeout，Runtime 观察到的只能是 unknown：动作可能失败，也可能已经成功。

{
  "status": "unknown",
  "error": {
    "code": "result_not_confirmed",
    "class": "transport",
    "same_request_retryable": false,
    "hint": "Query the operation by idempotency key before retrying."
  },
  "effect": {
    "tool_execution_id": "tool_exec_42",
    "idempotency_key": "idem_8f1c..."
  }
}

这里把 same_request_retryable 设为 false，不是说系统永远不能恢复，而是禁止模型立刻生成一个新的写动作。tool_execution_id 和 idempotency key 应在第一次 Attempt 前分配，并由同一逻辑动作的后续 Attempt 复用，不能仅由业务参数拼接；否则两个参数相同、意图不同的合法动作可能被误判成一次 retry。Runtime 应先用这份稳定 operation identity 查询结果；只有下游明确支持幂等重放时，才可以复用同一个 identity 再次尝试。

这与 Agent Tools 四：Tool 调用需要完整生命周期 的边界一致：exception 只是一条观测，不能自动证明外部事实没有发生。

修复能力要用完整轨迹评估

评测 Tool Error 不能只看 handler 是否返回了预期 code。真正的问题是：错误进入下一个 Model Turn 后，系统能否用有限步骤恢复，同时不制造额外副作用。

开场案例可以形成两条对照轨迹：

模糊错误
assign_task("Alex")
→ 400 invalid body
→ assign_task("alex")
→ 400 invalid body
→ 任务未完成

结构化错误
assign_task("Alex")
→ assignee_ambiguous + 2 candidates
→ Agent asks the user to choose
→ user selects user_12
→ assign_task("user_12")
→ succeeded

至少应分别记录：

  • repair success：收到可修复错误后，Task 最终是否完成。
  • repair attempts：成功前又产生了多少次 Tool Call。
  • repeated identical call rate：模型是否原样重复失败参数。
  • unsafe retry count：结果未知时是否发起了新的副作用。
  • candidate precision：返回的候选是否都可见、有效且与当前字段相关。

每个 rate 都要写明分母。例如 repair success 的分母应是“实际收到可修复错误的 case”，而不是所有 Tool Call。

回到问题

400 invalid body 只告诉模型调用没有得到成功响应，没有告诉它应该修改哪个字段，也没有告诉 Runtime 能否安全重试。

把错误建模为稳定的 Tool Error contract 后，开场中的同名用户问题会成为 assignee_ambiguous：后端提供当前用户可见的有限候选，并用 requires_user_input 要求 Agent 先取得用户选择；模型只能把确认后的稳定 ID 组成新提案，可信边界再重新校验。若失败发生在副作用之后，响应则保留 unknown，先查询原 operation，而不是鼓励盲目 retry。

Tool Error 的价值不在于写出更友好的报错，而在于让失败后的下一步仍然处在受控执行协议里。
