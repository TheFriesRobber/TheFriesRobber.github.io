Agent Tools 三：按任务装配 Tool Surface

从完整 Tool registry 中按权限和任务选择 eager、deferred 与 disabled 能力，并评估 token、延迟和漏召回的取舍。

2026/07/14 阅读 次
AgentToolsAPI Design

问题

一个 Agent 刚上线时可能只有五个 Tool：搜索网页、读取文件、写入文件、查询日历和发送消息。随着 connector（连接外部系统的适配器）、设备能力、业务操作和管理动作不断加入，registry 很快会增长到几十甚至上百个定义。

把所有 Tool 的 name、description 和 parameter schema（参数规则）在每个 Model Turn 都交给模型，至少会产生三个问题：

  • Tool definition 本身占用输入 token。Token 是模型计量输入文本的基本单位，schema 越复杂，这部分输入通常越长。
  • 相似能力同时出现，模型需要在更大的选择空间中路由。
  • 当前任务不需要、甚至当前用户无权调用的能力，也可能进入模型上下文。

但简单地把低频 Tool 全部隐藏也不成立。模型看不见一项能力，就无法主动选择它；如果 discovery 失败，系统会把“能力存在”变成“实际不可达”。

Tool surface 的核心问题不是怎样装下更多 Tool，而是：针对当前 Run，哪些能力应该立即可调用，哪些可以按需发现，哪些根本不应出现。

可以把 registry 想成仓库里的全部工具，把 Tool surface 想成这次任务摆在模型桌面上的工具。仓库可以很大，但桌面上只应放当前任务允许且可能用到的那一小部分。

这里的 Run 指一次 Agent Loop：从收到用户输入或恢复动作开始，到给出最终结果、明确暂停为可恢复状态，或者失败、取消时结束。

Registry、Allowed set、Initial surface 与 Unlocked set 是四个不同集合

先区分四个集合：

集合含义典型决定者
Registry系统已安装、能够构造的全部 Tool代码、插件、connector catalog
Allowed set当前用户、场景和资源范围内被允许的 Tool身份认证、权限策略、功能开关、依赖可用性
Initial surface当前 Run 开始时模型可以直接调用的完整定义Surface policy
Unlocked set运行中通过 discovery 新加载的 Tool搜索结果与再次授权

这四个集合不能合并成一个 allTools 数组。Registry 回答“系统有什么”，allowed set 回答“当前 Run 能用什么”，surface 回答“模型现在看见什么”。

最重要的顺序是：先做权限和场景过滤，再把允许集合分成 eager（立即加载）和 deferred（按需加载）。 Discovery 只能帮助模型找到能力，不能成为授权机制。

如果先对完整 registry 建 search index，再在调用时鉴权，模型仍可能从搜索结果中看到未授权 Tool 的名字和描述。这既泄露能力信息，也会诱导模型规划一条注定失败的路径。

Eager、deferred 和 disabled 是三种不同状态

一个 Tool 在某个 Run 中可以处于三种状态：

状态模型最初看到什么适合的能力主要代价
eager完整 name、description 和 schema，可立即调用高频、当前任务明确需要、召回失败代价高持续占用上下文，扩大直接选择空间
deferred一个可搜索的摘要、namespace 或索引条目；完整定义按需加载低频、大 schema、垂直 connector 能力增加 discovery 步骤，可能漏召回
disabled什么都看不到，也不能通过 discovery 获得未授权、依赖缺失、场景不允许或已停用能力在当前 Run 完全不可达

disabled 不是“更深一层的 deferred”。如果当前用户不能发送外部消息，这项能力就不应进入可搜索集合；不能指望模型搜到后自己克制。

同一个 Tool 也不需要永久属于某一类。search_web 在研究任务中可能 eager，在纯本地格式转换中可以 disabled；export_spreadsheet 在通用对话中可以 deferred，在明确的数据导出任务中则应 eager。

因此，分类取决于“这个 Tool 在这一次 Run 中是否合适”，不是 Tool class 上永远不变的属性。

怎样决定一个 Tool 是否 eager

“高频 eager、低频 deferred”只是起点。实际分类至少要看五个维度。

从任务类型就能预判的需要

如果任务场景已经知道目标，应该优先用这个信息收窄 surface。文件编辑任务通常需要读取和写入文件；研究任务通常需要搜索与抓取。不要让模型先额外搜索一次，才能发现最基本的执行能力。

漏召回的代价

有些 Tool 调用频率不高，却是关键控制能力。例如 request_user_confirmation 或 report_blocker 可能很少触发，但缺失时模型会猜测或在错误路径上继续。这类 Tool 往往应该 eager。

Tool 定义占用多少上下文

一个只有两个参数的查询 Tool，与包含几十个字段和多个动作的复杂企业系统连接器，初始加载成本不同。应该测量序列化后实际占用的 tool-definition token，而不是只数 Tool 数量。

Discovery 是否容易表达

模型需要根据当前上下文生成搜索语句。如果用户说“把这份结果同步到我的知识库”，knowledge_base namespace（把一组相关 Tool 放在一起的命名空间）很容易被发现；如果能力名称与用户语言差异很大，或必须先知道内部术语才能搜索，deferred 会显著提高漏召回风险。

额外 round trip 是否可接受

按需发现通常会增加一次搜索、加载，或者一个 Model Turn，也就是多一次系统与模型之间的往返（round trip）。对于交互式短任务，这段延迟可能比节省的 token 更重要；对于长任务，减少后续 Model Turn 重复携带的大 schema 可能更有价值。

可以把分类写成一个显式 review 表，而不是靠感觉：

问题倾向 eager倾向 deferred
当前任务是否大概率需要？是否
漏召回是否会让任务走错或无法恢复？高低
完整 schema 是否很大？小大
用户意图是否容易映射到 namespace/摘要？难易
是否能接受按需发现带来的额外延迟？否是

这张表没有给出固定阈值。分类应由 eval 和 trace 校准，而不是把所有“大 Tool”机械地设为 deferred。

按需 discovery 的完整生命周期

一个不依赖某家 provider 的流程可以这样设计：

1. Resolve Run context
   user identity + scenario + policy + available dependencies

2. Build allowed set
   registry -> authorization -> scenario policy -> dependency checks

3. Build initial surface
   eager tools: full definitions
   deferred tools: searchable summaries or namespaces

4. Discover
   model emits a capability query or selects a namespace

5. Re-authorize and load
   validate result is still allowed -> load full definitions -> deduplicate names

6. Call
   model invokes the unlocked Tool -> handler and backend validate again

这里有几个不能省略的关键检查点。

首先，搜索结果不是执行许可。Tool 在解锁前要再次检查当前身份、功能开关和依赖，因为长 Run 中这些条件可能已经变化。

其次，要明确“解锁后何时可调用”。有的 runtime 可以在同一次模型响应中完成搜索、注入定义并继续调用；有的实现要等到下一个 Model Turn 才把搜索结果加入上下文。应用必须记录这个过程，不能假设所有模型平台都有相同的 Model Turn 行为。

第三，Tool name 在最终 surface 中必须唯一。Registry 中不同 connector 可能都提供 search 或 list_items；加载后如果名称冲突，模型和 gateway 都无法可靠路由。Namespace、稳定前缀或显式 transform 应在把定义交给模型前解决冲突。

OpenAI 当前的 Tool search 同时提供 hosted（平台代为搜索）和 client-executed（应用自己搜索）两种路径：前者适合请求开始时已经知道候选集合，后者允许应用根据自己的状态执行 discovery。本文更新时，官方文档把这项能力限定在 GPT-5.4 及以后模型；应用仍应在使用前核对当前支持范围。这个产品接口会演进，但它揭示的系统边界是通用的：搜索可以由模型平台或应用执行，候选能力和授权责任仍需要应用明确管理。

Discovery index 应该保存什么

Deferred 不代表完全不可见。模型至少需要足够信息判断“值得搜索哪一类能力”。

一个 namespace 或 index entry 可以包含：

{
  "name": "calendar",
  "summary": "Read availability and create calendar events.",
  "capabilities": ["availability", "scheduling"],
  "side_effects": ["create_event"]
}

它不需要包含每个函数的完整 parameters，但应满足三个条件：

  1. 使用用户任务中的语言，而不是只写内部 service 名。
  2. 区分读取与写入，避免模型为了查数据加载高风险 mutation surface。
  3. 不包含当前用户无权知道的能力元数据。

Index entry 太短会导致漏召回；太长则只是把完整 schema 的 token 成本换了一个位置。更稳妥的结构通常是少量清晰 namespace，每个 namespace 下包含语义相近的 Tool，而不是一个包含所有能力的巨大“misc”目录。

搜索结果也不宜无限返回。一次加载过多 Tool 会让 surface 在运行中重新膨胀，并削弱 discovery 的意义。通常只返回得分最高的前 k 个结果（Top-k），但具体数量需要根据 Tool 相似度、任务复杂度和 eval 结果决定，不能照搬一个通用常数。

失败和 fallback（降级路径）必须显式设计

Discovery 可能因为搜索无结果、索引陈旧、provider 不支持、网络失败或模型没有发起搜索而失败。

常见但危险的 fallback 是：Tool search 不可用时，把所有 deferred Tool 全部展开。这样可能提高召回，但也可能突然增加 token、破坏 prompt cache，并把原本经过容量控制的 surface 变成另一套行为。

更明确的 fallback 可以是：

  • 保留一组经过预算评估的 core eager Tool。
  • 对高价值 namespace 提供有限的静态 fallback。
  • Search 无结果时返回可修复提示，让模型改写 query 或说明缺少的能力。
  • 当前 provider 不支持 dynamic loading 时，在 Run 开始前由 application router（按任务选择 Tool surface 的应用路由层）选择一个较小的静态 surface。
  • 无论采用哪种 fallback，都继续应用同一份 allowed set，绝不因为 discovery 故障放宽权限。

还需要定义解锁后的有效期。通常可以选择：

  • Model-Turn-scoped（单轮有效）：下一个 Model Turn 重新计算，最严格，但重复 discovery 较多。
  • Run-scoped（单次执行有效）：当前 Agent Run 内持续可见，适合多步任务。
  • Session-scoped（会话内有效）：跨多个 Run 缓存，延迟更低，但更容易遇到权限、版本和依赖漂移。

生命周期越长，越需要记录 Tool definition version、当时生效的 policy snapshot（策略快照）和失效条件。不能因为模型在十分钟前解锁过某项能力，就假设它现在仍然允许调用。

Surface 不是安全边界的全部

从模型上下文中移除 Tool，可以减少误调用和能力泄露，但不能代替 handler 与 backend authorization。

原因很直接：

  • 内部代码可能绕过模型直接调用 handler。
  • Tool definition 可能因 cache 或 adapter bug 被错误注入。
  • Run 开始后，资源权限可能变化。
  • 合法 Tool 仍可能携带越权资源 ID。

因此，完整路径仍然需要分层检查：

registry policy
  -> allowed-set filtering
  -> model-visible surface
  -> handler validation
  -> backend authorization
  -> storage consistency and audit

Surface 遵循最小能力暴露：只让模型看到完成任务所需的能力。Backend 执行最终的最小权限原则：调用者只能访问获准资源。前者减少模型的无效选择，后者保证即使 surface 出错也不能越过资源边界。

怎样评估 eager 与 deferred 的取舍

只报告“节省了多少 tool-definition token”会鼓励把越来越多 Tool 设为 deferred，却看不到任务完成率和延迟的损失。至少应该同时测量：

指标回答的问题
Initial tool-definition tokens初始 surface 实际减少了多少输入
Discovery recall需要某项 deferred 能力时，是否成功找到
Tool selection accuracy加载后是否选对 Tool，而不是相似能力
Extra Model Turnsdiscovery 增加了多少个模型轮次
Time to first useful Tool Call从用户请求到第一次有效 Tool Call 的延迟
Task success ratetoken 优化是否损害最终任务完成
Unauthorized exposure rate未授权名称或 schema 是否进入搜索结果或 surface
Fallback rate正常 discovery 多久失败一次，失败后走了哪条路径

比较实验应固定模型、任务集、Tool 版本和权限上下文，至少包含四类案例：

  1. 只需要 core eager Tool。
  2. 明确需要一个 deferred Tool。
  3. 用户表达与 Tool 名称不一致，需要语义 discovery。
  4. 用户请求一项存在于 registry、但当前无权使用的能力。

第四类尤其重要：正确结果不是“成功搜到再被 backend 拒绝”，而是能力从候选集合开始就不可见，同时系统能给用户一个不泄露内部细节的边界说明。

最终优化目标不是 token 最小，而是在质量、延迟、成本和权限之间取得可验证的平衡：

useful surface
  = enough capability to finish the task
  - irrelevant choice and schema cost
  - unauthorized exposure

这个式子不是可直接计算的单一分数。它提醒我们，减少 surface 和保持能力可达是两个方向相反的约束，必须用一组指标共同判断。

Deferred loading 不是所有 Tool surface 的默认答案

  • 小型 Agent 只有少量、边界清晰的 Tool 时，全部 eager 往往最简单，也最可靠。
  • Deferred loading 优化的是定义暴露与选择空间，不会自动缩短 Tool result、conversation history 或其他上下文。
  • Namespace 能改善发现，但不能修复单个 Tool 内部含糊的 name、description 和 schema。
  • 高风险 Tool 不应仅因为“很少使用”而 deferred；未授权时必须 disabled，需要确认时还要有独立 confirmation/policy。
  • Dynamic loading 的具体 API、当前或后续 Model Turn 的生效方式、缓存行为都可能因 provider 而异，应用应在自己的 surface contract（对工具可见性和加载时机的约定）中封装这些差异。

回到问题

Tool 数量增长后，不能只在“全部给模型”和“全部藏起来”之间二选一。

更稳妥的设计顺序是：

  1. Registry 保存系统能够构造的完整能力。
  2. 根据当前身份、场景、依赖和 policy 得到 allowed set。
  3. 在 allowed set 内，把核心且召回敏感的能力设为 eager。
  4. 把低频、大 schema、易于发现的能力组织成 deferred namespace 或 index。
  5. 把未授权或当前无效的能力设为 disabled，确保 discovery 也看不到。
  6. 用 token、recall、额外 Model Turn、延迟、Task 成功率和权限暴露共同评估。

按需 discovery 的价值，不是让一个 Agent 在理论上连接无限多个 Tool，而是让它在每个具体任务中只看到足够完成工作的那一小部分。
