Agent Tools 一：Tool Schema 是面向模型的 API

Tool schema 不是 backend DTO 的复制，而是帮助模型选择能力、生成参数并从错误中恢复的接口。

2026/07/12 更新于 2026/07/14 阅读 次
AgentToolsAPI Design

问题

假设后端已经有一个创建日历事件的接口。它接收十几个字段：用户 ID、组织 ID、标题、开始时间、结束时间、参与者、通知策略、审计来源、请求 ID 和重试配置。

最直接的做法，是把这份 request DTO（Data Transfer Object，服务之间传递参数的数据结构）转成 JSON Schema（描述 JSON 数据形状与约束的规则），再注册成 Agent Tool。类型能对上，执行函数也可以复用，似乎没有必要再设计一层接口。

但模型不是一个按固定代码调用 API 的客户端。它必须先从自然语言中判断要不要调用，再判断调用哪个 Tool，最后生成一组满足规则的参数。DTO 中每多一个名字含糊的字段、每少一个必要约束，都会让模型多做一次不必要的猜测。

因此，Tool schema 不应是 backend DTO 的复制品。它是一个 model-facing API：Tool name 和 description 帮助模型路由能力，input schema 约束可表达的意图，handler 则把这份不可信输入转换为经过鉴权的确定性操作。

可以把 Tool schema 理解成模型面前的一张操作表单：name 和 description 是表单标题与用途说明，input schema 决定模型能填写哪些字段，handler 负责检查并真正提交。Backend DTO 更像系统内部工单，里面可以包含模型不该填写的身份和执行信息。

本文会反复使用下面几个词：

术语本文中的含义
model-facing API面向模型设计的接口；目标是让模型容易选对、填对和改对
runtime包围模型的一层运行框架，负责传入 Tool、校验调用并执行 handler
handler收到 Tool 参数后真正执行业务逻辑的函数
backendhandler 调用的确定性服务、数据库或外部 API
trusted context由登录态和系统生成的可信信息，例如用户身份、权限、请求 ID
trace / evaltrace 是一次真实调用的过程记录；eval 是用固定案例重复评测系统的方法

一个 Tool 同时参与两次决策

Function calling 常被描述成“模型生成 JSON，应用执行函数”。这个描述略过了更早的一步：模型首先需要从可见 Tool 中选择一个能力。

一次调用至少包含两个不同问题：

决策主要输入常见失败
是否调用、调用哪个 Toolname、description、当前任务误选相似 Tool、该调用时没有调用、把读操作当成写操作
参数怎样生成property name、type、required、enum、字段 description漏字段、类型错误、自创字段、混淆空值语义

这也是为什么只检查“JSON 能否通过 schema”不够。一个调用可以结构完全合法，却选择了错误能力；也可以选对 Tool，却因为接口暴露了无关字段而在参数阶段失败。

Tool 的完整边界还包括 runtime 注入的身份、权限和审计信息。模型只负责表达用户任务中可以推导出的业务参数，不应该生成这些可信上下文。

先从 backend DTO 的反例开始

下面是一份适合服务间调用、却不适合直接暴露给模型的输入：

{
  "user_id": "u_123",
  "tenant_id": "t_456",
  "title": "Project sync",
  "starts_at": "2026-07-16T10:00:00+08:00",
  "ends_at": "2026-07-16T10:30:00+08:00",
  "notification_policy": "default",
  "actor_type": "assistant",
  "request_id": "req_789",
  "retry_mode": "safe"
}

这些字段混合了三类信息：

  1. 用户明确表达的业务意图，例如标题、时间和参与者。
  2. 应用根据当前 session 推导的上下文，例如用户、时区和作用域。
  3. 基础设施内部需要的控制字段，例如 request ID、actor 和 retry policy。

后两类字段一旦进入 schema，模型就不得不为它们做决定。更严重的是，user_id 或 actor_type 看起来只是字符串，实际上却属于权限和审计边界。即使模型大多数时候能填对，也不能把授权建立在“模型通常不会伪造”之上。

更窄的 model-facing Tool 可以只接收完成任务所需的信息。为了展示范围约束，下面假设这个示例产品只接受 5 到 480 分钟的事件、最多 50 名参与者；这些数字是示例策略，不是通用日历限制：

{
  "type": "object",
  "properties": {
    "title": {
      "type": "string",
      "minLength": 1,
      "description": "Event title visible to attendees."
    },
    "starts_at": {
      "type": "string",
      "description": "Start time with an explicit UTC offset."
    },
    "duration_minutes": {
      "type": "integer",
      "minimum": 5,
      "maximum": 480,
      "description": "Event duration in minutes."
    },
    "attendee_emails": {
      "type": "array",
      "items": { "type": "string" },
      "minItems": 1,
      "maxItems": 50,
      "description": "Confirmed attendee email addresses. Omit when there are no attendees."
    }
  },
  "required": ["title", "starts_at", "duration_minutes"],
  "additionalProperties": false
}

Runtime 再补上可信上下文：

async function executeScheduleEvent(args: ScheduleEventArgs, ctx: ToolContext) {
  const input = validateBusinessRules(args, ctx.timezone)

  return calendarClient.createEvent({
    ...input,
    userId: ctx.authenticatedUserId,
    permissionScope: ctx.permissionScope,
    actor: ctx.actor,
    requestId: ctx.requestId,
  })
}

这不是为了让 Tool 看起来更简单，而是在明确责任：模型表达任务，runtime 提供可信上下文，backend 执行最终授权和一致性检查。

Name 和 description 是路由接口

Tool name 首先应该表达一个稳定动作，而不是内部 service 或 class 名称。

calendar_api_v2_execute       # 暴露实现，意图不清
manage_calendar              # 范围太宽
schedule_calendar_event      # 动作和资源都明确

Description 则需要回答几个路由问题：

  • 这个 Tool 完成什么结果？
  • 什么情况下应该调用？
  • 什么情况下不该调用？
  • 它是读取数据，还是会产生持久副作用？
  • 最关键的前置条件是什么？

例如：

Create one calendar event for the current user. Use only after the title,
start time, and duration are known. This tool writes to the calendar; it
does not search for availability or resolve ambiguous time zones.

这段 description 没有解释后端怎样存储 event，也没有重复每个字段的类型。它提供的是选择 Tool 所需的判别信息。

Description 也不是越长越好。把权限手册、字段文档、重试规则和产品背景全部塞进去，会稀释真正影响选择的信号。可以按职责分层：

信息更合适的位置
何时调用、是否有副作用Tool description
单个参数怎样填写Property description
当前任务的行为原则System/developer instruction
用户身份、资源作用域Trusted runtime context
最终授权和业务约束Handler 与 backend

少量重复是合理的，例如写操作可以同时在 Tool description 和确认 UI 中标明副作用。但不能因为 prompt 已经说过“不要越权”，就省掉真正的 backend authorization。

Schema 应表达最小充分输入

所谓“最小”，不是尽量少写约束；所谓“充分”，也不是把所有内部选项都交给模型。目标是让模型只需做完成用户任务所必需的决定。

每个字段都应该能回答：

  • 它对应哪个用户意图？
  • 没有它时，handler 能否安全、确定地推导？
  • 缺失、空字符串、空数组和 null 是否有不同含义？
  • 合法范围能否由 schema 直接表达？
  • 它是否其实属于身份、权限、审计或基础设施配置？

JSON Schema 中，写在 properties 里的字段默认并不是必填；必须显式放进 required。同样，未声明的字段默认可以出现，只有使用 additionalProperties: false 才会拒绝模型自创的近义字段。

需要特别区分三种状态：

{}

表示字段缺失；

{ "note": "" }

表示调用方明确传入空字符串；

{ "note": null }

表示显式 null，而且只有 schema 允许 null 时才合法。

如果 handler 用 value ?? "" 把三者合并，schema 再精确也保不住语义。对于“空字符串表示删除内容”之类的接口，字段可以允许为空，但字段本身仍应是 required。

Schema validation 不能代替 handler validation

严格 schema 能减少语法层面的无效输入，却不能证明调用已经被授权，也不能覆盖所有业务条件。

仍然需要 handler 检查：

  • starts_at 是否能解析，是否包含明确时区。
  • 参与者是否在当前用户允许邀请的范围内。
  • 写操作是否已经获得当前场景要求的确认。
  • 当前 runtime 实际支持的 JSON Schema keyword 是否与定义一致。

最后一点经常被忽略。不同模型平台、网关和 runtime 可能只实现 JSON Schema 的一部分。某个 keyword（例如 minItems）出现在类型定义里，不代表每条执行路径都会执行它。可靠的做法是：为 model-facing schema 建 contract test（验证各条执行路径是否遵守同一份 schema），同时在 handler 保留关键业务校验；不要把正确性押在某个适配器恰好支持的行为上。

可以把验证边界拆成三层：

层适合检查什么
Schema/runtime validator类型、required、enum、范围、额外字段
Handler跨字段关系、当前状态、确认条件、可修复业务错误
Backend/storage身份授权、资源所有权、事务、版本和幂等（重复提交仍产生同一个业务结果）

三层可以有意重复关键检查。重复的目的不是互不信任，而是每一层都拒绝自己有能力识别的非法状态。

错误也是 model-facing API 的一部分

如果 application/runtime 把 Tool error 返回给模型，它就会成为下一步决策的输入。对工程师来说，400 invalid body 也许足以开始查日志；对模型来说，它几乎没有提供下一步动作。

一个可修复错误至少应包含稳定错误码、问题字段和修复提示。可以把它组织成一个固定格式的 error envelope：

{
  "ok": false,
  "error": "ambiguous_time_zone",
  "field": "starts_at",
  "message": "The start time does not include a UTC offset.",
  "hint": "Ask the user for a time zone, then retry with an explicit offset.",
  "recoverable": true,
  "requires_user_input": true,
  "retryable": false
}

错误包需要控制边界：

  • error 使用低基数、稳定的机器码，便于 trace 和 eval 聚合。
  • message 解释当前失败，不透传 stack trace 或内部服务响应。
  • hint 给出合法的下一步，不替模型虚构缺失事实。
  • recoverable 表示是否存在合法修复路径；requires_user_input 说明当前信息不足，需要先询问用户。
  • retryable 只表示相同条件下重试是否可能成功。缺少时区属于可修复但不可直接重试，短暂网络失败才可能同时是 recoverable 和 retryable。
  • 候选值只返回经过权限过滤且数量受限的集合。

这样，失败后的修复能力也成为接口设计的一部分，而不是依赖模型猜测。

用 trace 和 eval 改 schema

一份 schema 在代码审查中看起来合理，不代表模型真的能稳定使用。至少应该在固定任务集上分别观察：

指标它暴露的问题
Tool selection accuracyname/description 是否让模型选对能力
First-call valid rateschema 和字段说明是否足够清楚
Repair success rate错误是否支持下一步修复
Redundant call rateTool 是否诱导重复读取或重复写入
Task success rate合法调用是否真的完成用户目标
Permission violation attempts可见 Tool、prompt 或参数是否在诱导越权尝试

诊断时不要只看最终 task success。两个版本都可能完成任务，但一个版本第一次调用就成功，另一个版本需要三次无效参数重试；它们在延迟、成本和脆弱性上完全不同。

迭代也应一次只改变有限变量。例如，先保持 schema 不变，只修改 Tool name 和 description，观察选择率；再收紧字段与错误提示，观察首次合法率和修复率。否则结果改善后，很难知道真正起作用的是哪一层。

Schema 只能约束模型可见的输入形状

Tool schema 不是所有问题的答案：

  • Tool 太多导致模型选择空间过大，需要单独设计 Tool registry（完整工具目录）、权限过滤和按需发现；这属于 Tool surface（模型当前实际可见的工具集合），而不是单个 schema。
  • 一个带多个 command 的 Tool 如果参数差异过大，可能需要拆成多个 Tool；但应先用失败分布证明问题来自拆分粒度。
  • 长时间、可恢复、多阶段的工作应由 workflow 或 task 状态机承载，Tool 只作为其中的原子能力。
  • 高风险副作用通常还需要用户确认、policy hook 或审批流程，不能靠 description 中的一句话代替。
  • Schema 保证的是输入形状，不保证事实真实、调用合理或执行成功。

回到问题

Agent Tool 与 backend API 可以复用同一个业务能力，却不应该默认复用同一份接口形状。

Backend DTO 面向受控程序调用者，往往包含完整执行上下文；Tool schema 面向一个需要先理解自然语言、再选择能力并生成参数的模型。一个可靠的 model-facing API 应该做到：

  1. 用明确的 name 和 description 缩小能力选择的歧义。
  2. 只暴露模型完成用户任务所需的最小充分输入。
  3. 由可信 runtime 注入身份、权限、审计和基础设施上下文。
  4. 用 schema、handler 和 backend 分层验证，而不是把正确性押在单一 validator 上。
  5. 把错误修复和真实调用评测纳入接口生命周期。

代码是 Tool 的执行实现，schema 则是模型看到的产品界面。两者服务同一个动作，但承担不同责任。
