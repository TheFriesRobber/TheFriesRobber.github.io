Agent Memory 六：Hot、Cold 与 Pinned 分层

Memory 不应全量进入 prompt；先按可见性分层，再在当前预算内组装。

2026/07/14 阅读 次
AgentMemoryData Governance

问题

用户让 Agent 修改一份正在编写的欧洲市场周报。Memory 中同时有三类记录：用户明确要求“所有周报都要列出风险”，近期确认且仍有效的欧洲市场报告口径，以及半年前一次会议的完整笔记。

最省事的实现，是把三类内容全部塞进 prompt。这样确实不容易漏掉事实，却会让无关旧记录持续占用 token，也扩大敏感内容的暴露面。另一个极端是只做一次相似度检索，但“周报”和半年前的会议笔记可能比那条简短的长期偏好更相似。检索召回了很多内容，模型仍可能漏掉真正不能缺席的规则。

问题不在于 Memory 存得太多，而在于“能够被读取”和“本轮应该进入 Context”被当成了同一件事。

Memory Budget 不是把总预算再平均分配

全局 Context Budget 先在 history、Memory、文件和 Tool Result 之间分配；Memory 拿到其中一部分后，内部仍要决定哪些记录必须稳定可见，哪些可以按近期工作集进入，哪些只在命中当前任务时读取。Context Engineering 二 讨论的是前一层的全局竞争，本文处理后一层的 Memory 内部分层。

Pinned、Hot 与 Cold 描述的是这三种可见性策略，不是三套互不相通的存储系统：

层级进入 Context 的条件预算不足时典型内容
Pinned当前版本、仍获授权，并且对一类任务是必需条件先压缩表达；仍放不下时缩小任务或失败，不静默删除明确的长期偏好、身份与硬约束
Hot与当前 Task 相关，且处于近期工作集摘要、降低数量或退回 Cold近期确认的项目口径、最近更正的长期偏好
Cold经过 Retrieval 命中并通过有效性与权限过滤只保留引用或不注入长尾事实、历史材料、低频证据

Pinned 并不等于“永远无条件放进 prompt”。一条偏好被撤销、过期或在当前资源范围内没有权限时，即使曾被 pinned，也不能继续可见。Pinned 表示通过有效性检查以后，它在预算竞争中不能被普通相关性分数挤掉。

Hot 也不只是“最近写入”。最近的无关记录没有理由进入本轮 Context；较早但仍属于当前任务工作集的记录也可能保持 Hot。Cold 更不是删除，它仍可由 Retrieval 按需读取。

这里的分层只消费已经通过 Writer Gate 的 current Memory record，不负责把当前 Task state 或实时 Tool data 持久化。后两类信息仍由各自 owner 管理，再由 Context Assembly 按本轮需要加入 Context。

Pinned、Hot 与 Cold 先决定可见性再竞争预算

假设全局 Assembly planner 给 Memory 留出 900 tokens。Memory view builder 随后对已授权的 current records 按 task scope 与 policy revision 分类，并记录每条记录入选或省略的原因；final assembler 在注入前再次检查授权。Pinned、Hot 与 Cold 因而是每个 Model Turn 的派生 view，不是记录的永久属性。

本轮候选记录如下：

mem_pref_v3   pinned  周报必须列出风险                 45 tokens
mem_eu_v8     hot     当前欧洲市场报告口径摘要         520 tokens
mem_notes_v2  cold    半年前会议笔记                  3,400 tokens

系统先放入 mem_pref_v3。它不是因为与“修改周报”最相似才入选，而是因为它是这类任务当前有效的硬约束。随后，mem_eu_v8 以 Hot 记录进入，剩余预算只够补充少量检索证据。mem_notes_v2 即使包含“周报”一词，也不会整份常驻；只有本轮确实询问那次会议时，Retrieval 才从中选出相关片段。

最终交给 Assembly 的不是一堆未经解释的文本，而是一份可审计的 Memory view：

memory_view:
  pinned: [mem_pref_v3]
  hot: [mem_eu_v8]
  cold_refs: []
  omitted:
    - memory_id: mem_notes_v2
      reason: not_relevant_within_budget
  watermark: memory_revision_41

这份 view 只代表当前 Model Turn 的选择。Memory Store 里的记录没有因为本轮未被选中而消失；下一次 Task 可以得到不同的 Hot 集合和 Cold 命中。

更新偏好时，旧 Pinned 不能留在缓存里

现在用户把要求改成“只有管理层周报才列出风险”。Memory Writer 不应原地覆盖 mem_pref_v3，而是写入新版本 mem_pref_v4，并让旧版本不再属于 current view。

如果 Context Assembly 只按 memory_id 缓存 pinned 文本，它可能在下一轮继续注入旧要求。Principal 与 tenant identity 必须由物理分区或 cache key 承载；无论采用哪种隔离，view identity 都仍要绑定资源与任务 scope、current version set，以及影响可见性的 revision，例如：

partition: (subject_id, tenant_id)
key: (resource_scope, task_scope,
      current_version_set_digest, memory_revision,
      authorization_input_fingerprint, budget_policy_revision)

任意一项变化，旧 Memory view 都只能作废并重新组装；真正注入前还要按当前 authorization state 再检查一次，不能把 cache hit 当成授权证明。下一份普通团队周报会发现 mem_pref_v4 不适用于当前 scope，因此不注入风险要求；管理层周报则会把新版本作为 Pinned 放入。这个过程改变的是当前可见版本和 view，不需要删除历史版本。

这里尤其不能用“缓存稍后自然过期”代替失效。Pinned 内容通常正是会改变模型行为的约束；短暂地继续使用旧版本，也可能让本轮输出违背用户刚刚完成的更正。

分层也需要明确的失败语义

Memory 分层的价值不只是省 token，还在于让预算不足时的行为可预测：

  • Pinned 互相冲突时，先解决版本与 scope，不能把冲突文本一起交给模型碰运气。
  • 有效 Pinned 本身超过预算时，压缩只能缩短表达，不能改变约束；仍无法容纳就应缩小 Task 或返回 context_budget_exceeded。
  • Hot 可以按任务阶段摘要或退回 Cold，但要保留来源引用，避免摘要变成不可追溯的新事实。
  • Cold 未命中时保持不注入，不用为了填满预算而补齐无关内容。

因此，评估分层策略不能只看 prompt 变短了多少。至少还要检查必需约束的覆盖率、无关记录的暴露率、更新后旧版本进入 view 或 prompt 的比例，以及在同一预算下 Task 是否仍能完成。旧版本被延迟索引召回为 candidate 可以单独作为 freshness 诊断，只要它在 current-version resolution 后没有继续暴露给模型，就不应算成分层失败。完整的 Memory Eval 会在后续文章继续展开。

回到问题

全量注入把“存过”误当成“本轮该看”；纯相似度检索又可能让必要约束和普通候选一起竞争。Pinned、Hot、Cold 分层把这两个判断拆开：先确认记录当前是否有效，再决定它在本轮的可见性和降级方式。

于是，周报要求以 Pinned 稳定进入，近期确认的报告口径占用 Hot 预算，半年前的材料留在 Cold 等待明确查询。用户更新偏好后，版本与 revision 让旧 view 立即失效。Memory 仍然完整保留，但 prompt 只得到当前任务真正需要且有权使用的部分。
