Tool 是面向模型的执行契约

从 model-facing Schema 到可信执行、外部副作用、结果归一化和可修复错误，建立完整 Tool contract。

2026/07/24 阅读 次
Agent CoreAgentToolsAPI Design

问题

模型调用 create_note，参数通过 JSON Schema 校验。handler 向远端发出写入请求，随后 timeout。Runtime 只把异常文本 "request timed out" 放回 Context。

下一轮模型看到的是一个错误字符串。它不知道参数是否需要修改，不知道动作能否 retry，更不知道 note 是否已经创建。Schema 是合法的，handler 也确实被调用了，但这仍不是一个完整的 Tool contract。

Schema 服务的是模型决策

Backend API 往往按数据库字段、历史兼容和传输效率设计；Tool schema 则同时参与模型的两个决策：

  1. 现在应该选择哪个 Tool；
  2. 选择后应该提供哪些参数。

因此直接暴露 backend DTO 经常会产生两个问题：模型要在大量无关字段中猜意图，或者一个高权限 endpoint 被包装成看似普通的多用途 Tool。

Tool definition 应提供最小充分信息：

  • name 和 description 能区分用户意图；
  • schema 表达模型必须决定的输入；
  • 不由模型决定的 tenant、actor、credential 和 operation ID 由可信 Runtime 注入；
  • 不同副作用或权限边界优先拆成不同 Tool。

Schema 约束的是模型可见输入形状，不是整个执行安全边界。

Tool Call 是不可信 proposal

即使 arguments 符合 schema，它们仍来自模型输出。完整调用路径至少包括：

definition
→ model proposal
→ provider binding transform
→ canonical validation
→ authorization
→ handler invocation
→ external effect
→ normalized result

Provider SDK 的 validation 只能说明它接受了某种请求格式。Runtime 仍要在 canonical schema 上校验；handler 还要检查资源是否存在、版本是否匹配、值是否满足业务 invariant。Authorization 更不能从模型参数中读取可信身份。

这种分层不是重复劳动。每层拥有不同事实：schema 知道结构，Runtime 知道当前执行身份，backend 知道资源的最新状态。

Handler 返回值不是外部事实的全部

纯函数 Tool 可以把函数返回近似视为执行结果；有副作用的 Tool 不行。网络 timeout、进程退出或 cancellation 都可能发生在外部提交之后。

首篇已经用 operation、Tool Execution 与 Attempt 解释了 unknown effect 的恢复状态机。这里不再展开那条控制流，只把 unknown 作为结果契约中的一种类别，重点说明 envelope 如何约束模型的下一步。

因此 model-visible result 至少需要区分：

字段说明
outcomesucceeded、failed 或 unknown
retryable当前证据是否允许新 Attempt
errorClassvalidation、authorization、dependency、timeout 等
effectRef可用于查询或 reconcile 的外部引用
repair模型可以安全修改哪些输入

这是一种目标 envelope，而不是 Pi 当前 AgentToolResult 的既有字段。Pi 当前会把 Tool Result 放回 Context，并以独立 isError 表示错误，但没有标准化 unknown outcome、retryability 或 effect reference。当前类型可参考 types.ts。

可修复错误必须约束下一步

模型能修复的通常是 selection 或 arguments，例如缺少必填字段、枚举值无效、资源名有多个候选。错误可以返回有限 candidate 或明确 hint。

模型不能修复的包括：

  • 当前身份没有权限；
  • 外部动作结果未知；
  • backend invariant 要求人工或另一状态 owner 决定；
  • policy 明确禁止该动作。

把这些错误都写成“请重试”会让模型越过真正的 owner。尤其是 unknown effect，下一步应该是 query/reconcile，而不是重新生成一组看起来更好的参数。

同一 Envelope 必须区分三种下一步

同一个错误字符串会诱导模型一律重试；结构化 envelope 则应把决定权交给正确的 owner：

Envelope允许的下一步
errorClass: validation，带有限候选或字段 hint模型可以 repair arguments，提出新 proposal
errorClass: authorization，retryable: false停止调用；由用户或授权 owner 改变权限
outcome: unknown，带 effectRefRuntime 或查询能力 reconcile；模型不得重新生成写入

回到 create_note：Runtime validation 通过后注入 subject 与 operation key；backend 接受请求但响应丢失，handler 返回 outcome: unknown 与 effectRef: op-17。这条结果不需要在本文重走完整 retry 流程，只需要证明模型看见了唯一安全的下一步：查询或请求 reconcile。

Contract test 因此不能只测试 schema parser。它至少要验证 provider binding 没有删约束、canonical validator 与 handler 对样例解释一致、三类 envelope 不会互相转换，尤其不能把 unknown effect 变成可 repair 的普通失败。

Pi 当前的 validation、Tool execution event 和结果写回路径位于 agent-loop.ts。更丰富的 effect/error envelope 是本文提出的宿主演进方向。

回到问题

一个 JSON Schema 加一个 handler，只覆盖了 Tool contract 的两段。完整契约还要回答：

  • 模型为什么能选对这个 Tool；
  • arguments 在哪个可信边界被重新校验；
  • 谁根据当前身份授权；
  • 外部 effect 由谁拥有；
  • timeout 后是 failed 还是 unknown；
  • 哪些错误能由模型 repair，哪些必须交回 Runtime 或 backend。

当 create_note timeout 时，模型应该看到的是受约束的下一步，而不是一条没有语义的异常文本。做到这一点，Tool 才真正成为面向模型、同时守住执行事实的 API。
