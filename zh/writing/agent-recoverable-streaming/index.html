实时输出为什么不是执行记录

区分 durable execution event、lossy transport signal 与客户端 cursor，让断线恢复不改写执行事实。

2026/07/24 阅读 次
Agent CoreAgentStreamingRecovery

问题

Agent 已经完成一个 Tool，服务端也发出了 tool_execution_end。客户端却在收到这个事件前断线。重连后，它只看见后续 token，于是界面一直显示 Tool “执行中”。

如果重新运行 Agent 来补界面，可能重复副作用；如果只重连 SSE/WebSocket，又无法拿回断线期间丢失的事件。实时连接传得快，不代表它保存了执行事实。

进程内 event 不是 durable event

Pi 的 AgentEvent 描述模型、Tool 和 Agent 生命周期信号，subscriber 也可以被等待。这有助于在当前进程内传播和收敛事件，但 event 本身没有自动获得 stable durable ID、持久存储或跨重启 replay 能力。

要承诺断线恢复，host 需要把两层分开：

层责任
Durable execution event记录已经确认的执行事实，支持按 ID 查询
Delivery signal通过 SSE/WebSocket 等尽快通知客户端，允许丢失和重连

网络连接可以消失，durable event 仍然存在。反过来，发出一条 signal 也不能证明对应事实已经提交。

Cursor 让客户端重建视图

每条可恢复事件需要稳定 ID，并属于明确 stream 或 Run：

run_id: run-9
event_id: 1042
type: tool_execution_completed
tool_call_id: call-3
outcome: succeeded

客户端保存最后确认的 cursor。重连时先请求 after=1041 的历史，再订阅新事件。UI 是这些事件的 projection，可以重复构建，而不是一次连接留下的不可恢复内存状态。

这不要求所有 token 都进入永久日志。Tool outcome、状态转换、用户确认和最终 message 通常具有恢复价值；模型 token delta 更像可丢失的展示信号。需要恢复文本时，可以保存完成后的 message 或分段 checkpoint，而不是把每个 token 都当业务事实。

补历史与订阅之间也有 race

一个常见错误流程是：

  1. 查询 cursor 之后的历史；
  2. 历史返回；
  3. 再建立实时订阅。

事件可能恰好发生在步骤 1 和 3 之间。安全实现需要一个明确边界，例如先建立带缓冲的订阅，再补历史并按 event ID 去重；或者由服务端提供“从 cursor 开始订阅”的原子接口。

无论采用哪种实现，都要允许 at-least-once delivery，并让 projection 依据 event ID 幂等应用。试图依靠连接层提供“永不重复、永不丢失”通常会把 transport guarantee 写得过强。

慢消费者不能拖住执行事实

实时 subscriber 如果无限阻塞执行主链，一个慢浏览器就可能拖慢 Tool settlement；如果完全不等待，又可能造成无界内存增长。

比较稳妥的边界是：

  • durable event 提交不依赖单个客户端在线；
  • delivery 使用有界 buffer；
  • 超过上限时断开或降级 token signal；
  • 客户端重连后从 durable cursor 补关键事件；
  • cancellation 通过独立控制协议进入 Runtime，不依赖关闭 socket。

Pi 当前 awaited subscriber 的 settlement 语义可以作为进程内协作机制，但不能直接推广成跨进程 durability。当前 event 类型可参考 types.ts。

回到问题

客户端错过 tool_execution_end 后，不应该重新运行 Agent，也不能指望重新连接拿回空气中已经消失的 signal。正确路径是：

  1. Tool completion 先成为带 stable ID 的 durable execution event；
  2. SSE/WebSocket 只负责发送可丢失通知；
  3. 客户端用 cursor 查询遗漏事件；
  4. projection 按 event ID 幂等重建；
  5. token delta 可以降级，已确认的执行 outcome 不能丢。

实时输出解决“现在尽快看见”，执行记录解决“以后仍能证明”。把这两个问题分开，断线恢复才不会变成重复执行。
