Agent Runtime 六：按失败边界选择恢复动作

2026/07/15
AgentRuntimeReliability

问题

一个 Agent 正在生成市场报告。它先调用模型整理数据，再调用 create_document 创建文档，最后让模型补写摘要。

主模型请求 timeout 后，HTTP client 最多执行三次请求（含首次）；Provider Adapter 则在包含主 route 的最多三个 route attempt 中选择；最外层 Run 仍未得到结果，于是把整段流程最多执行三次。每层都是三次 Attempt，嵌套后，一次逻辑 Model Turn 最坏会放大成 27 个物理请求。

更危险的是 create_document：如果外部服务已经创建文档、只是响应丢失，最外层 Run 重跑会创建多份文档。统一的“失败就重试”没有恢复系统，只有不断扩大的 Attempt 数量。

问题不在于三次这个数字，而在于三个层级都把自己看到的错误当成了自己的恢复权。

先确定失败属于哪个 owner

恢复动作应留在拥有该状态的对象内。Transport timeout、Model Turn、Tool Execution、Plan 和 Task 不是同一个 retry unit：

失败位置稳定 identity首先要回答的问题
Transport / providerModel Turn请求是否被接受，是否已有完整 response item
Tool validationTool Call / Tool Execution输入能否由模型修复，是否已经产生副作用
外部 Tool effectTool Execution结果是 failed，还是仍然 unknown
Plan premisePlan revision / item哪些后续 item 依赖了失效前提
Task outcomeTask用户目标是否仍可完成，还是需要终止或人工处理

同一条异常文本不足以完成分类。timeout 只说明 caller 在期限内没有得到确认；它不能证明 provider 没生成结果，也不能证明 Tool 没产生外部效果。Runtime 还需要知道当前 owner、逻辑 identity、已经提交的事实，以及调用是否可能产生副作用。

这里把同一模型推理边界下的 transport retry 和 route fallback 都记为同一个 Model Turn 的不同 Attempt。只有模型输入或预期推理边界发生变化，Runtime 才开始新的 Model Turn；切换 provider 本身不会偷偷改变度量 grain。

因此，错误应先归一化成稳定 failure class，例如 transport_timeout、provider_rate_limited、tool_invalid_argument、effect_result_unknown、plan_premise_invalid。原始异常仍可进入受控日志，但恢复 policy 不应依赖随 SDK 或 provider 改变的错误字符串。

恢复动作不是 retry 的同义词

分类完成后，Runtime 才能选择动作：

动作适用条件不应做什么
Retry同一逻辑操作可安全再尝试，且仍有 budget生成新 identity 掩盖重复执行
Fallback原 route 失败，备用 route 仍满足原契约拼接两个 Attempt 的 partial output
Repair模型可根据结构化错误修改 Tool 参数原样重复无效参数
Replan前提或依赖失效，旧计划已不能完成目标只把失败 item 重新标成 pending
Reconcile外部效果可能已发生但结果未知在确认前再次执行不可逆动作
Escalate / stoppolicy、授权或安全边界不允许自动恢复用更多 retry 绕过硬限制

Backoff 和 jitter 只能控制 retry 的时间分布，不能证明 retry 安全。对于有副作用的调用，Runtime 仍需稳定 idempotency key、可查询的业务 reference 或显式 reconciliation；这些条件都不存在时，应保持 unknown 并停止自动重放。

把报告例子走一遍

现在让所有恢复动作由一个 Runtime policy 协调：

1. 主模型请求 timeout
   → Routing Decision 已确认当前 route 的 provider_side_effects=none
   → 没有完整 response item 被接受，丢弃未完成输出
   → 在同一 Model Turn 下创建新的 Attempt，并消耗一次 fallback budget

2. 备用模型返回完整 create_document Tool Call
   → Runtime 校验并创建稳定 Tool Execution

3. create_document 响应 timeout
   → effect intent 已提交，但没有 terminal result
   → 标记 effect_result_unknown，先按 idempotency key / document reference 查询

4. 查询得到 doc_42
   → Tool Execution 收敛为 succeeded，不再次创建文档

5. 后续发现报告依赖的数据口径已经失效
   → 将 plan_premise_invalid 交给 Plan owner，生成新 revision
   → 只取消或替换受影响的后续 item，不重跑已确认的 doc_42 创建事实

如果第 3 步得到的是明确 validation error，动作会变成 repair；如果授权已经撤销，则直接 stop。恢复动作来自 failure class 和 effect 状态，而不是来自“再试一次也许会好”。

Retry budget 必须跨层共享

即使每层 retry 都单独合理，叠加后仍可能耗尽 deadline、token 和下游容量。因此 RunSpec 或 Runtime policy 应为一次逻辑目标分配共享 budget，并让每个动作记录消耗：

recovery_budget
  transport_attempts: 2
  model_fallbacks: 1
  tool_repairs: 2
  replans: 1
  deadline: 45s

这些不是通用默认值，只是说明 budget 需要按动作区分。一次便宜的 transport retry 与一次重新规划的成本和风险不同；它们可以有各自上限，但还要受总 deadline、成本和副作用 policy 约束。

Runtime 还应识别没有进展的循环。若连续两个 Plan revision 仍引用同一个失效前提，或者 Tool repair 反复产生相同参数 digest 和 error code，继续消耗 budget 不会带来新信息。此时应终止、要求用户确认或进入人工恢复，而不是把循环包装成“仍在运行”。

怎样验证恢复策略

只看最终成功率会奖励无限重试。一次恢复至少应保留：逻辑 operation、所有 Attempt、failure class、选择的恢复动作、budget 消耗、最终副作用和 artifact reference。

这样才能检查：是否在错误层重跑了整个 Run，fallback 是否违反原能力约束，Tool 是否产生重复副作用，以及 replan 是否真正改变了失效依赖。线上 failure 可以再转成固定 fixture，验证相同分类是否仍产生相同边界内的动作。

回到问题

统一 retry 把不同 owner 的失败压成同一件事，因此既会放大请求，也会让结果未知的外部动作被重复执行。

分层恢复先确定失败属于哪个 identity，再结合结果确定性和副作用 contract 选择 retry、fallback、repair、replan、reconcile 或 stop。共享 budget 限制整个恢复链，Attempt lineage 则证明系统到底试过什么。这样，恢复是在正确边界内推动状态收敛，而不是从最外层重新开始。
