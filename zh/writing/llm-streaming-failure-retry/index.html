LLM Infra 14：一次流式推理失败后，什么时候可以重试

区分 logical request、attempt、execution、partial delivery 与 cancellation，建立流式推理的 retry、restart 和 fail-explicitly 边界。

2026/07/29 阅读 次
LLM InfraInferenceStreamingReliability

问题

一个请求已经向客户端流出一段文本，连接随后断开。Gateway 自动把同一 Prompt 发到另一个 Replica；新输出从头生成并发生分叉，客户端收到重复或互相矛盾的内容，两个 Replica 还都产生了 usage。

普通 HTTP retry 常把“没有拿到完整响应”理解成“再发一次”。对自回归 streaming，这个模型不成立：请求可能已经执行，部分 Token 也可能已经成为用户可见结果。

Timeout 只描述观察方

gRPC 的 deadline 文档明确指出，client 超时后会停止等待，但 server application 仍需要停止它已经启动的工作。Client 与 server 还可能对同一次调用得到不同本地结论：server 已完成，client 却观察到 deadline exceeded。

因此：

gateway timeout
≠ placement 未到达
≠ execution 未开始
≠ cancellation 已生效
≠ 没有产生 usage

同样，client disconnect 只说明 transport 断开。取消请求从 gateway 传播到 scheduler、Replica 和并行 ranks，需要时间，也可能失败。

四个对象决定恢复边界

attempt_state:
  logical_request_id: req_123
  attempt_id: att_2
  release_digest: release_91a
  execution:
    started: true
    stopped: unknown
  cancel:
    requested_at: ...
    engine_observed_at: null
  delivery:
    chunks_emitted: 6
    emitted_token_cursor: 47
    ack_protocol: none
    acknowledged_cursor: null
    terminal_transport_status: unavailable
  usage:
    generated_tokens: 91
  • Logical request 表示调用方想完成的一次工作。
  • Attempt 表示一次物理发送，retry 必须产生新 attempt_id。
  • Execution 表示 Runtime 是否接纳并实际计算。
  • Gateway emitted cursor 表示 Gateway 已尝试发出多少输出。
  • Acknowledged cursor 只有在 API 定义显式 application ACK 时，才表示调用方确认到哪里。

普通 SSE/HTTP stream 通常没有通用的 application-consumption ACK，也没有可移植的 Token resume protocol。一次成功 write 最多形成 Gateway 本地的 emitted evidence，不能证明 Client 已收到、解析或提交给应用。没有 ACK 时，Client-visible outcome 保持 unknown；除非 API 和 Runtime 明确支持，任何 cursor 都不是“从第 48 个 Token 继续”的能力。

首输出前重试也不是零成本安全

如果 client 没收到任何 chunk，新 attempt 不会制造重复可见 Token，但旧 attempt 仍可能：

  • 已经完成 Prefill；
  • 正在 Decode；
  • 产生计费或 GPU usage；
  • 在取消传播前继续执行；
  • 最终与新 attempt 同时完成。

所以更准确的说法是：首 chunk 前可以在调用方协议允许时启动新的 attempt，但仍要接受重复计算与 unknown execution outcome。

平台可以先请求取消旧 attempt，并等待 execution_stopped evidence，再决定是否重试。若只能得到 cancel_observed_by_engine，旧 execution 是否停止仍是 unknown，必须按可能并行执行处理；如果 deadline 不允许等待，就把这项风险记录到 outcome 和 usage，而不是称为 exactly-once。

部分交付后，默认不能拼接

自回归输出取决于前缀、sampling、model/runtime revision 和执行路径。即使 seed 相同，版本、Batching 和数值差异也可能改变输出。新 Replica 从同一 Prompt 重新生成，不保证前 47 个 Token 后的 continuation 与旧 attempt 一致。

部分交付后的选择应明确：

已知状态默认动作原因
Gateway 确认未发出 chunk，旧执行确认停止启动新 attempt无重复可见输出，仍是新计算
Gateway 确认未发出 chunk，旧执行未知可按策略启动新 attempt接受重复执行与 usage 风险
Gateway 已发出 chunk，Client ACK 缺失或只确认部分fail explicitly 或经调用方同意从头重启按可能已部分可见保守处理，默认不能拼接
Runtime 有显式 resume contract按该协议恢复必须绑定 state、release 与 cursor
已完成但 acknowledgement 未知返回 unknown / 查询结果（若支持）自动重试可能重复完整结果

Fallback 到另一个 deployment 还必须通过第 15 篇的完整 compatibility contract，包括 protocol、capability、quality/safety、数据政策和 SLO envelope；资源不足不是静默更换模型的授权。

Cancellation 需要三个不同事实

不要用一个布尔值 cancelled=true。至少要记录：

cancel_requested
→ cancel_observed_by_engine
→ execution_stopped

第一步是调用方意图，第二步证明 Runtime 看到了请求，第三步才说明 GPU 不再继续该 execution。多 rank 或 P/D 分离拓扑中，还要确认哪些阶段已经停止。

Usage 也要按 attempt 记录：

  • input tokens accepted；
  • Runtime 生成的 Token；
  • Gateway 发出的 chunk/Token cursor；
  • 显式 Client ACK（若协议存在）；
  • cancellation 后仍计算的 Token；
  • terminal outcome。

这些事实必须保留 producer/provenance，不能由 Runtime 签出 client-delivered Token。Logical request 的账单或配额如何合并 attempts 是上层 policy；Infra 只提供不丢失且不越过 owner 的 usage evidence。

处理开篇断流

原流程是：

gateway emitted through token cursor 47
→ disconnect
→ gateway retries from prompt
→ second output diverges

修正后：

  1. Gateway 记录 attempt att_1 已发出至 cursor 47；没有 ACK 时，把 Client 是否已消费标为 unknown，并按可能 partial delivery 保守处理。
  2. 向 Runtime 发 cancel，并分别记录 requested、observed 与 stopped。
  3. 默认返回明确失败，不自动拼接。
  4. 如果调用方选择“从头重新生成”，创建 att_2，并明确它是新输出。
  5. 两个 attempts 的 usage 都关联同一个 logical request，但各自保留 outcome。

回到问题

开篇的 Gateway 已经发出部分 Token；即使无法证明 Client 消费到哪里，也无权把“连接失败”解释成“模型没有执行”，更不能把第二次完整生成拼到第一次输出后面。

流式恢复必须由 attempt、execution、Gateway emitted evidence、显式 Client ACK（若有）和 cancellation facts 共同决定。首 chunk 前的新 attempt 仍可能重复计算；可能部分可见时默认显式失败；只有 API 与 Runtime 提供明确 resume contract 时，才可以从已确认 state 恢复。
