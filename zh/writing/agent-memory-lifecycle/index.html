Agent 17：Memory 的写入、版本与当前视图

把 write gate、Writer 信任域、版本链和 current view 串成长期 Memory 的完整生命周期。

2026/07/24 更新于 2026/07/27 阅读 次
Agent StateAgentMemoryData Modeling

问题

用户第一次告诉 Agent：“以后尽量在上午联系我。”系统把它保存成长期偏好。几周后，用户明确更正：“以后改成下午。”后台归纳任务却根据旧记录再次生成“上午”，下一次 Session 仍在错误时间联系用户。

历史消息没有丢，检索也确实找到了相关内容。问题发生在更早的位置：系统把每次提取结果都当成新的长期事实，却没有定义谁能写、哪一版当前有效，以及更正、撤销和删除分别意味着什么。

长期 Memory 需要一条完整生命周期：候选信息先经过 write gate，由受限 Writer 提交带来源的版本；读取方默认只消费 current view，更正、撤销、删除和 undo 则按不同语义改变后续可见性。

被提取出来不等于值得长期保存

模型或规则从对话中提取出的内容只能成为 memory_candidate。可信 Runtime 负责附加 subject、source reference 和 actor，模型不能自行声明这些身份：

candidate:
  claim: preferred_contact_time = morning
  observed_scope: future
trusted_envelope:
  subject: user_42
  source_ref: message_61
  actor: in_loop_agent

Write gate 再判断：

Gate要回答的问题
Durable当前 Task 结束后是否仍可能成立
User-specific是否描述当前 subject，而不是第三方
Future-useful后续是否有明确用途
Source-grounded来源是否支持 claim 及其适用范围
Permission-safe当前 actor 是否允许保存这种数据

这些不是加权分。信息再有用，也不能抵消来源不足或没有保存权限。临时地点、一次性格式要求和实时变化的外部状态通常应停在当前 Task，或带明确 expiry，而不是被升级成永久用户属性。

Writer 权限要落实到每次 Mutation

对话内 Agent、后台归纳、批量导入和用户编辑拥有不同的证据与权限：

Writer合理动作不应拥有的权限
In-loop Agent提交当前授权 Context 支持的 candidate修改其他 subject
Background consolidation追加 observation、提出 change proposal覆盖用户显式声明
Import job写入映射过的 namespace越过映射写入其他目录
User edit更正、撤销或删除可管理记录绕过 retention 与第三方数据规则

Memory service 应从可信执行环境获得 actor，而不是接受 Tool arguments 中的 writer: user。每次 mutation 至少校验 subject、namespace、action、evidence class、source refs 和 expected revision。

因此，后台任务可以记录“最近三次联系发生在上午”，却不能据此覆盖用户明确声明的“下午偏好”。发生的事件与用户意愿可以同时为真，不应先压成同一字符串再比较相似度。

Version Chain 让更正改变 Current View

首次写入形成版本 1：

memory_id: contact_time
version: 1
value: morning
status: current
source_ref: message_61

用户更正时，合法 Writer 以 expected_current_version: 1 提交版本 2：

memory_id: contact_time
version: 2
value: afternoon
status: current
source_ref: message_82
supersedes: 1

同一提交边界把 v1 标成 superseded，并推进 current pointer。若另一个 Writer 仍基于 v1 并发写入，expected revision 不匹配，应返回 conflict，让上层重新读取和判断，而不是 last-write-wins。

重复投递同一逻辑 mutation 时，应复用稳定 operation ID，返回已经形成的版本；不同意图不能因为内容相似而共享幂等键。

Supersede、Revoke、Delete 与 Undo 不是同义词

操作后续读取历史内容
Supersede使用新版本依 retention policy 保留旧版本
Revoke当前值不再生效可保留撤销事实与获准历史
Delete/erasure内容退出普通读取与派生路径无强制 retention 时仅保留不含原值的 tombstone
Undo创建新版本恢复先前业务值版本链继续向前

Undo 不能把 current pointer 静默倒回 v1，否则审计会看不见“曾改成下午、后来又恢复上午”的事实。它应创建 v3，并把恢复原因指向 v1。

删除也不能实现成 hidden=true 后继续把原文留在 index、cache、summary 和普通备份读取路径中。原内容应退出业务读取和派生路径；若适用 policy 强制法定或安全 retention，保留副本必须隔离、限制用途与访问，并记录删除已经覆盖的范围、例外期限和最终清除时间。若 policy 禁止保留历史，superseded value 也应被清除，只留下不含内容的版本元数据。

Current View 是读取 Contract

Current view 不是另一份独立事实，而是 Memory service 根据版本、expiry 和 revoke/delete 状态产生的 canonical projection。普通 retrieval 从它开始，再由读取路径根据当前 subject/actor 执行独立 authorization filter；不能从全部历史中搜索后让相似度决定哪版有效。

审计或修复方只有在 retention 与授权允许时才读取历史；它们看到历史，不代表历史可以重新进入新的 Model Turn。Index、cache 和摘要都应携带 Memory revision，current view 推进后使旧派生结果失效。

把开场偏好走完

开场生命周期可以表示为：

message_61 “上午” → write gate pass → v1 current
message_82 “下午” → authorized supersede(v1) → v2 current
background observation “最近上午联系” → append observation
                                      → cannot supersede v2

若用户随后撤销联系时间偏好，系统创建 revoke event，current view 不再返回该项；若用户要求删除，内容从允许的读取与派生路径中清除。以后用户又选择上午，则这是新的 v3，而不是让被删除或 superseded 的旧值自行复活。

回到问题

旧“上午”偏好覆盖“下午”，不是 retrieval 排序问题，而是 Memory 缺少受控 mutation 和 current view。

让候选先通过 write gate，按 Writer 的 subject、namespace、action 与 evidence 授权，再用 expected revision 提交 version chain，读取方就只会得到 v2。后台归纳仍可保存有来源的 observation，却不能改变用户明确偏好。

Memory 的长期价值不在于保存更多文本，而在于每条当前状态都能回答：谁依据什么写入、它是否仍有效，以及怎样被更正、撤销和删除。
