Capability Integration 一：Tool、Skill、Connector 与 MCP 怎样分工

从一次外部能力升级失败出发，用模型可见性、版本、凭证和执行 owner 区分 Tool、Skill、Connector 与 MCP。

2026/07/17 阅读 次

问题

假设要给 Agent 增加“发送周报邮件”的能力。系统里很快出现四种说法：

  • 给模型注册一个 send_email Tool。
  • 安装一个“周报发送” Skill。
  • 接入邮件 Connector。
  • 配置一个提供邮件能力的 MCP server。

第一版可以工作。后来邮件服务要求新增 workspace_id，只有部分 Runtime 升级了 Tool Schema；Skill 仍按旧步骤生成参数；Connector 保存着用户 OAuth credential；MCP server 已经暴露新版 Tool。调用开始失败时，团队却无法回答：应该升级哪一层，谁负责兼容，谁有权使用 credential？

问题不是名字太多，而是四个名字被当成同一种“模型能力”。它们可以出现在同一条调用链里，但回答的是不同问题。

先用责任问题拆开“能力”

判断一个对象属于哪种抽象，不要先看产品叫法，而要问四个问题：

  1. 模型具体可以提出什么动作？
  2. 哪些可复用说明、脚本和依赖需要一起加载？
  3. 谁持有用户授权并访问外部系统？
  4. Client 与 Server 用什么协议发现和调用能力？

这四个问题分别接近 Tool、Skill、Connector 和 MCP。它们不是一条固定的上下层级：一个 Skill 可以只组织本地文件操作，不经过 Connector；一个 Connector 可以通过应用私有 API 暴露 Tool，而不使用 MCP；MCP server 也可以提供不需要用户 credential 的只读资源。

因此，下面的定义是一份工程责任地图，不是要求所有框架采用同一套类型系统。

Tool 定义模型可以提出的动作

Tool 是 model-facing action contract。它用名称、description、输入 Schema 和结果语义回答：模型在当前 Model Turn 可以选择什么动作，以及参数应该怎样生成。

在邮件例子中，Tool 可以是：

{
  "name": "send_email",
  "description": "Send a prepared report to approved recipients.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "recipient": {"type": "string"},
      "subject": {"type": "string"},
      "body": {"type": "string"}
    },
    "required": ["recipient", "subject", "body"]
  }
}

它不应该让模型填写 OAuth token、tenant identity 或已授予的 scope。这些不是任务参数，而是可信执行 context。

Tool 的 owner 负责模型能否区分这个动作、Schema 怎样演进、错误怎样进入下一轮，以及当前 surface 是否应该暴露它。Tool 不必拥有外部 credential，也不必决定整个能力包如何安装。

Skill 封装可复用的工作方法

对于需要发现、加载、升级和回滚的 Skill，本文把它视为一组可版本化的 instructions、references、scripts、assets 和依赖声明。它回答的是“Agent 怎样完成一类工作”，不只是“调用哪个函数”。

例如“发送周报” Skill 可以描述：让模型读取本周 Artifact 并按模板生成摘要，运行确定性校验脚本检查收件人范围，最后由模型提出 send_email Tool Call，再由 Runtime 校验并执行。Skill 只封装这些步骤和依赖，不亲自生成摘要、执行校验或发送邮件；其中只有最后一步是 Tool action，前面的说明、模板和脚本属于可加载的工作方法。

公开的 SKILL.md 格式是这种设计的一种实例：Skill 目录至少包含带 metadata 的 SKILL.md，还可以带 scripts/、references/ 和 assets/。但具体格式不是本文结论。更重要的 contract 是：

  • Skill 有稳定 identity 和可 pin 的版本。
  • 加载前可以检查依赖与 Runtime compatibility。
  • Skill 声明需要哪些 Tool 或 Connector，但不能凭声明扩大权限。
  • 执行仍继承当前 Run 的 identity、budget、observability 和 sandbox policy。

Skill 能教 Agent 怎样使用能力，却不能因为说明文件里写了“允许发送”，就替 backend 完成 authorization。

Connector 是 Credential 与外部系统的可信边界

Connector 负责代表用户或 tenant 访问外部系统。它通常管理 OAuth authorization、token storage、refresh、scope、provider account mapping 和 API normalization。

RFC 6749 把 access token 定义为访问 protected resource 的 credential，并要求 token 在传输和存储中保持机密。对 Agent 系统来说，直接后果是：模型、普通 Skill 文本和不可信 Sandbox 都不应看到原始 token。

邮件 Connector 可以暴露一个可信执行接口：

send_email(args, trusted_context)
  → 根据 trusted_context 找到授权记录
  → 为目标 provider 获取或刷新短期 credential
  → 检查 scope、recipient policy 与 account binding
  → 调用外部邮件 API
  → 返回归一化结果

Connector 的 owner 负责 credential lifecycle 和 provider-specific failure。Tool Schema 改名不应迫使 Skill 保存 token；MCP transport 改变也不应改变 OAuth credential 的 owner。

MCP 规定怎样发现和调用，不自动承担全部治理

Model Context Protocol 使用 client-host-server 架构，并通过 JSON-RPC、初始化和 capability negotiation 暴露 Tools、Resources 与 Prompts。它回答的是：Host 与 Server 怎样建立连接、声明支持的协议能力、发现 primitive 并发起调用。

这使 MCP 可以承载邮件 Tool 的发现与调用，但“使用 MCP”不自动解决下面的问题：

  • 哪个 tenant 可以看见这个 server。
  • Runtime 应该路由到 v1 还是 v2。
  • OAuth credential 存在哪里。
  • Tool Schema 变化怎样灰度和回滚。
  • Server 健康但业务依赖失效时是否仍可路由。

这些决定属于应用或 MCP Hub 的 control plane。协议提供 negotiation 事实，Hub 才根据版本、健康、授权和 rollout policy 形成 route decision。把静态 server endpoint 列表称为“治理层”，会把协议连通性误当成运行安全性。

同一条调用链可以同时包含四种抽象

回到发送周报的例子，一条完整路径可以是：

Skill: weekly-report@3
  模型读取 Artifact 并生成摘要；校验脚本检查发送步骤
          ↓ requires
Tool: send_email schema v2
  模型只生成 recipient、subject、body
          ↓ discovered and called through
MCP connection: mail-server route v2
  协商 protocol capability，传输 Tool Call 与 Result
          ↓ invokes trusted integration
Connector: mail-account-7
  持有 OAuth grant，注入 workspace 与 provider account
          ↓ calls
Mail provider API

当外部 API 新增 workspace_id 时，先判断它属于哪种事实：

  • 如果模型必须根据任务选择 workspace，它可能进入 Tool Schema。
  • 如果 workspace 来自已认证 tenant，它应由 Connector 或 Runtime context 注入，不能交给模型。
  • Skill 只有在工作步骤或依赖发生变化时才需要升级。
  • MCP server 可以发布新版实现，但 route 是否切换由 control plane 决定。

这样，版本升级不再是“所有能力一起升级”，而是沿 owner 判断哪份 contract 真正改变。

回到问题

“发送周报邮件”可以同时使用 Tool、Skill、Connector 和 MCP，因为四者描述的是同一能力的不同维度。

Tool 让模型提出明确动作；Skill 封装可版本化的工作方法；Connector 在可信边界管理用户授权和外部 API；MCP 规定 Host 与 Server 怎样发现和调用 primitive。版本、凭证或调用失败时，先按这四类责任定位 owner，才能知道应该修改哪份 contract。

把它们都叫作“模型能力”并没有错；错误是因此假设它们共享同一个版本、权限和故障边界。
