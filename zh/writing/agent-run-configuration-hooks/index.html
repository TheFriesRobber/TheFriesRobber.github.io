Run 配置如何在每轮稳定下来

区分长期 policy 与每轮 snapshot，并限定控制型 Hook 和只读 Observer 对 snapshot 的影响边界。

2026/07/24 阅读 次
Agent CoreAgentRuntimeHooks

问题

一个 Agent 正在请求模型，当前 Tool surface 中包含 write_file。管理员此时禁用了这个 Tool。模型请求返回后仍提出 write_file，Runtime 应该执行还是拒绝？

如果 Runtime 在一次 Model Turn 中随时读取“最新配置”，模型看到的是旧 Tool schema，执行器使用的却是新 allowed set；如果一直固定 Run 启动时的配置，紧急禁用又可能迟迟不生效。问题不在于配置能否变化，而在于变化从哪一个明确边界开始可见。

Policy 不是一次 Turn 使用的配置

长期 policy 表达宿主希望系统遵守什么，例如允许哪些模型、Tool 和资源上限。它可以在 Run 期间变化，也可以依赖当前用户、租户和环境。

Model Turn 真正需要的是已经解析完成的具体值：

policy + identity + session state + runtime resources
                      ↓ compile
                turn snapshot

snapshot 至少要固定 messages、model、thinking 参数、Tool definitions、resource references 和 policy revision。这样，模型输入、Tool binding 和后续验证才能解释自己基于哪一版决策。

这里的“固定”不是要求复制整个对象图，而是要求本轮可观察语义不被原地修改。内部对象可以通过不可变数据、版本化引用或受控读取实现，关键是不能让同一 Turn 悄悄消费两个 revision。

Pi 当前生成的是 per-turn object

Pi Harness 的 createTurnState() 会构造一个本轮随后复用的对象，这是比每次临时读取字段更清晰的边界。但当前构造过程包含多个异步步骤：Session context、resources、metadata、tool context 和 system prompt 可能依次被解析；与此同时，Harness 的 setter 仍允许修改 model、tools 等配置。

因此它可能读到旧 resources 和新 model。top-level spread 也只提供浅层复制，不能保证内部引用不被修改。把这个对象称为“原子 snapshot”会高估当前实现。

若宿主要提供同 revision 保证，可以选择两种常见做法：

  1. 构造前捕获 configurationRevision，异步解析完成后重新校验；revision 已变化就丢弃并重建；
  2. 在 snapshot 构造期间串行化配置写入，让读写共享同一临界边界。

这两种都是宿主层的目标 contract，不是 Pi 当前自动提供的行为。Pi 当前代码边界可见于 agent-harness.ts。

配置变化需要声明可见性

有了 revision，禁用 write_file 的决定可以变得明确：

时刻可见配置处理方式
已发出的模型请求revision 12保持本轮输入语义
Tool 执行前revision 12 + 当前安全授权Tool 仍需重新授权
下一 Model Turnrevision 13不再向模型暴露 write_file
进程恢复后host 重新编译校验 revision 和依赖后再继续

snapshot 不是绕过实时安全检查的通行证。模型看见某个 Tool，只说明它在提议阶段可见；执行前的 backend authorization 仍然使用当前事实。若紧急禁用必须阻断所有新副作用，宿主可以在执行边界拒绝旧 proposal，同时把拒绝原因作为可解释结果返回。

Hook 只能在声明的边界影响 revision

Hook 容易再次把稳定性打破。一个 beforeModel Hook 若能修改 Tool surface，就必须说明结果属于当前 revision 还是下一 revision；Observer 若名义上只用于观测，就不应通过共享引用修改 snapshot。

Pi 当前有几层不同机制：

  • low-level 的 before/after Tool callback；
  • Harness typed on() 事件及其现有结果组合语义；
  • subscribe() 这类订阅接口。

这些能力不能被统一描述成一个已经完备的 Hook framework。本文只关心它们与 snapshot 的交点：控制型返回值什么时候生效，只读观察者能看到什么。Hook container、cleanup、通用 reducer 和 replay 属于另一条 API 设计问题。

一个简单规则是：

  • 改变后续 model、Tool surface 或 resource 等 snapshot 配置的 Hook 结果，必须进入可命名的 configuration revision；无法归入当前 revision，就从下一 Turn 生效；
  • 只决定当前 Tool Call 的 allow/deny、result patch 或 short-circuit，则记录为绑定当前 snapshot revision 的 execution decision/outcome，不创建新的配置 revision。

回到问题

运行中禁用 write_file 时，不需要在“永远使用旧配置”和“立刻混入新配置”之间二选一：

  • 已发出的模型请求继续以 revision 12 解释；
  • Tool Call 仍只是 proposal，执行边界可以依据当前安全 policy 拒绝；
  • 下一 Turn 使用 revision 13，模型不再看到该 Tool；
  • 进入明确 revision 的 Hook/config update 才能改变后续 snapshot；call-local execution decision 绑定当前 snapshot revision，不创建新的配置 revision。

Pi 当前提供了可复用的 per-turn object 和若干 callback/event 边界，但没有自动给出跨异步字段的原子 revision。将这点写清楚，宿主才能在需要时补上真正的 snapshot contract，而不是依赖一个听起来正确的名字。
