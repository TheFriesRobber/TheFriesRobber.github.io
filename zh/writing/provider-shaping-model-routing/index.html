Context Engineering 五：用 Adapter 隔离 Provider 差异

用 canonical contract 和 provider adapter 隔离 prompt、Tool Schema、消息与 streaming event 的格式差异。

2026/07/15 阅读 次
AgentContext EngineeringModel Routing

问题

假设 Runtime 已经选好模型，并准备执行一次文档搜索。内部记录的是同一个逻辑交互：

user request
→ assistant tool call: search_documents(call_17)
→ tool result: call_17
→ assistant final answer

不同 provider 对这段交互的表达可能不同：有的把 Tool Call 和 Tool Result 表示成独立 item，有的把它们放进 assistant 与 user message 的 content block；Tool name、Schema 子集、streaming event 和结束原因也可能采用不同约束。

如果业务代码只统一成一个 generate() 方法，却在调用前后散落这些分支：

if provider == "a":
    # 改 role、拼 tool result
elif provider == "b":
    # 改 content block、转换 schema

那么 provider 差异并没有被抽象，只是从 HTTP client 泄漏到了 Context Assembly、Agent Loop 和 Tool Runtime。

真正需要统一的不是函数名，而是 Runtime 依赖的语义：一次请求包含哪些 instruction、message 和 Tool；返回了哪些完整 item；Tool Call 与 Tool Result 怎样关联。

Canonical contract 不是所有 Provider 的最小交集

Runtime 可以先定义自己的 canonical contract，例如：

{
  "operation_id": "model_op_17",
  "continuation_ref": "conversation_9@item_24",
  "instructions": [{"kind": "runtime_policy", "content_ref": "policy_8"}],
  "input_items": [
    {"type": "user_message", "content": "查找设计文档中的重试策略"},
    {
      "type": "assistant_tool_call",
      "call_id": "call_16",
      "name": "search_documents",
      "arguments_ref": "args_16"
    },
    {
      "type": "tool_result",
      "call_id": "call_16",
      "status": "succeeded",
      "content_ref": "artifact_42"
    }
  ],
  "tools": [{"definition_ref": "search_documents@revision_5"}],
  "required_features": ["tool_call_identity", "streaming"],
  "required_provider_guarantees": ["preserve_required_fields"]
}

Canonical 不应照抄某家 API，也不必退化成所有 provider 都能表达的最小字段集。它应表达 Runtime 真正需要的能力；某个 route 无法表达时，Adapter 返回明确的不兼容，而不是静默丢字段。

这样，上游只处理 canonical user_message、assistant_tool_call、tool_result 和稳定的 call_id。Provider 把它们放在哪种 role 或 content block 中，属于 Adapter 的责任。

Adapter 先声明能力，再做转换

Adapter 不应该拿到请求后边转换边猜。它可以先根据 route 的 capability profile 做 preflight：

canonical request
→ capability check
→ schema and message transform
→ provider request
→ provider response / stream
→ canonical items and events

Preflight 的结果至少区分三种情况：

结果含义上游动作
supported所需语义可以表达继续渲染请求
lossy可以发送，但某些语义会减弱仅在 policy 明确允许时继续
unsupported必需语义无法表达交回 Router 选择其他 route

Adapter 不负责根据字段名称猜测业务风险。Canonical request 或上游 policy 应明确哪些 provider-side generation guarantees 是必需的，例如 preserve_required_fields；Adapter 只报告对应约束能否表达。必需保证无法表达时返回 unsupported，非必需约束丢失时返回 lossy。Adapter 不能为了让 HTTP 请求成功而自行降低契约，也不能自行决定某个 Schema keyword 对业务是否重要。

Tool Call identity 不能在转换中丢失

继续使用 search_documents。Runtime 需要稳定知道 Tool Result 属于哪个 Tool Call：

canonical call_id: call_17
provider call identity: provider_call_xyz

Adapter 可以保存映射，但返回 Runtime 时必须恢复 canonical call_id。如果只按 Tool name 匹配，在并行调用两次 search_documents 时就无法判断哪个结果对应哪组参数。

这份映射不能只是进程内的二元 Map。一次 provider continuation 可能跨进程恢复，同一个 logical model operation 也可能在 fallback 后产生新的 attempt。映射至少要带上：

canonical call_id
route and provider
model attempt_id
provider response / conversation identity
provider-native call identity

它应随 canonical event 或 provider continuation state 持久化。继续同一个 provider conversation 时，Tool round trip 通常保持 route-sticky，并回传原生 call identity。Fallback 到另一个 provider 时，只有目标 Adapter 能完整表达所有必需且可迁移的 continuation state，才能根据 canonical Tool Call 与 Tool Result 重新渲染配对；不能把上一家的 native ID 直接带过去。

Canonical call_id 只解决业务关联，不保证整个 continuation 都可移植。Provider-native reasoning item、opaque compaction item 或强制消息顺序可能仍属于原 route；目标协议无法表达时，Adapter 应返回 incompatible_continuation，让 Runtime 从已经确认的稳定事实边界建立新的 model operation，而不是伪装成同一段 conversation 的无损续接。

请求侧的转换可能是：

canonical tool_result(call_17)
→ provider-specific message role / content block
→ provider_call_xyz

响应侧则反向归一化：

provider tool-use item(provider_call_xyz)
→ canonical tool_call(call_17, name, arguments)

这个映射是执行协议的一部分，不是日志里的辅助字段。丢失它会直接破坏 Tool Call、重试和结果消费。

Prompt shaping 不能改变权限与事实边界

Provider 可能要求不同的 system instruction 位置、message role 或 Tool description 格式。Adapter 可以改变表达方式，但不能重新决定内容的权限与角色。

例如，Context Assembly 已经把文件片段标为不可信 data。Adapter 可以把它渲染成 text block，却不能因为某个 provider 只有一种方便的 message role，就把文件内容提升为 system instruction。Tool Surface 也应在进入 Adapter 前由 policy 确定；Adapter 只转换已允许的 definitions。

可以把分工写得很清楚：

层负责什么不负责什么
Context Assembly选择内容、处理权限与冲突Provider role 格式
Router选择满足约束的 route消息和 Schema 转换
Adapter表达 canonical contract、报告损失改写业务 policy
Runtime消费 canonical item 与 event解析每家原始响应

Streaming 只能统一事件语义，不能统一 chunk 形状

不同 provider 可能按 token、content block、Tool argument delta 或完整 item 推送事件。强行把每个原始 chunk 一一映射成相同结构，会让 Runtime 依赖某家的切分方式。

更稳妥的做法是统一 Runtime 真正关心的事件：

response.started
text.delta
tool_call.delta
item.assembled
tool_call.validated / tool_call.invalid_arguments
response.completed
response.failed

delta 适合实时展示，不一定能独立重放；item.assembled 只表示 provider 已结束这个 item 的传输，Adapter 已把 chunks 组装起来。它不保证 Tool arguments 能解析，更不保证通过 Schema。Runtime 解析并执行 canonical validation 后，才产生 tool_call.validated 或 tool_call.invalid_arguments；只有前者可以进入 handler。

统一事件也不意味着两个 provider 会产生相同 token 边界、时间顺序或 finish reason。Adapter 应保留原始 reason 供诊断，同时映射出 Runtime 使用的有限分类；无法准确映射时标记 unknown，不要编造一个看似统一的值。

Adapter 转换后仍要保留 identity 与约束

文档搜索请求经过 Adapter 的过程可以是：

1. Router 选择 route_b，固定 Adapter profile revision 9。
2. Adapter 检查 Tool Call identity、streaming 和 Schema 能力。
3. 将 canonical messages 与 Tool definition 渲染为 provider request。
4. Stream 中首次出现 Tool Call identity 时，分配或恢复 canonical `call_id`，并按 route、attempt 和 provider response 保存映射。
5. 把后续原始 stream 转成 text.delta 与 tool_call.delta。
6. Tool arguments 传输结束后，输出 item.assembled(tool_call call_17)。
7. Runtime 解析参数并用 canonical Schema 校验，输出 tool_call.validated 后才执行 Tool。
8. 下一个 Model Turn 将 tool_result(call_17) 再由同一个 Adapter 渲染回 provider protocol。

Agent Loop 从头到尾不需要判断 route_b 使用哪种 role；Tool Runtime 也不需要解析 provider 的 content block。若第 2 步发现 Schema 必需约束无法表达，流程在发送请求前就返回 unsupported，由 Router 决定是否存在其他合格 route。

Contract test 要检查语义往返

只测试“请求返回 200”无法发现 Tool Call identity 丢失、Schema 约束被删除或 finish reason 映射错误。Adapter 的 contract tests 至少应覆盖：

  • Canonical request 能否渲染成 provider 接受的结构。
  • Tool Call、Tool Result 和并行调用能否在重启、continuation 与 model attempt 边界上保持稳定关联。
  • 带 provider-native reasoning 或 opaque continuation item 的请求，能否在同 route 正确续接，并在跨 provider 无法表达时明确返回 incompatible_continuation。
  • 必需 Schema 约束被保留、明确降级或明确拒绝。
  • Streaming chunks 能否收敛为完整 canonical item。
  • Provider error 能否映射为有限但不失真的 failure class。
  • Canonical → provider → canonical 的 round trip 是否保留 Runtime 依赖的语义。

这些测试应绑定 provider API version、Adapter revision 与 capability profile revision。Provider 行为变化后，系统才能知道应该更新转换规则，而不是让业务代码再增加一个临时分支。

回到问题

一个统一的 generate() 方法只能隐藏调用入口，不能自动隐藏协议差异。

Runtime 需要先定义自己依赖的 canonical contract，再让 Provider Adapter 负责 capability preflight、message 与 Schema shaping、Tool Call identity 映射，以及 response 和 streaming event 的归一化。任何无法无损表达的部分都应显式报告。

这样，Router 决定选谁，Context Assembly 决定给模型看什么，Adapter 只负责怎样表达；provider 差异才真正停在边界之后。

后续问题

  • 同一 Tool Schema 经不同 Adapter 转换后，怎样发现 validation drift。
  • Provider、prompt、Tool Surface 变化后，Eval manifest 应怎样固定执行配置。
  • Adapter 的 capability profile 怎样随 provider 变化持续校准。
