Agent Tools 二：一个 Tool，还是多个？

Tool 应按用户可区分的意图、权限和副作用拆分，而不是照搬 backend endpoint。

2026/07/14 阅读 次
AgentToolsAPI Design

问题

一个文件服务只有一个 backend endpoint。先用概念性的 request shape 表示它接受的字段：

{
  "command": "read | write | delete",
  "path": "...",
  "content": "...",
  "recursive": false,
  "force": false
}

真实 schema 可以用 oneOf 或条件分支，让每个 command 只接受相关字段；上面不是完整 JSON Schema。即便解决了字段合法性，把它原样暴露成 manage_file Tool 仍有语义问题：当用户只说“看看配置文件”时，读取、覆盖和删除都留在同一个模型可见入口。Runtime 可以派生并版本化一个删去未授权分支的受限 schema，也可以在把 command 与资源规范化后做精确授权；代价是 surface 过滤、政策映射、缓存和 contract test 都要理解这层分支。

于是，schema 在 JSON 层面完全合法，Tool call 仍可能在语义上选错动作。

反过来，把每个 backend endpoint、每个 flag 组合都做成独立 Tool 也不会自动更好。十几个名称相近的 Tool 会让模型先在更大的候选集中猜一次，重复参数和模糊描述还可能制造新的误选。问题不是“一个还是多个”本身，而是模型需要做的决策应放在哪一层。

拆分改变的是两次选择

Agent Tools 一 把 Tool Schema 看成面向模型的 API。Tool 拆分进一步决定模型如何完成两次选择：

  1. Tool selection：这次用户意图属于哪个动作；
  2. argument generation：选定动作后，需要填写哪些参数。

这里的“两次选择”是分析 Tool call 错误的两个维度，不表示 provider 能观测到模型先完成名称、再顺序生成参数；协议通常只返回最终的名称与 arguments，同一次响应还可能没有调用或包含多个调用。把差异很大的动作合在一起，会把名称选择隐藏进 command 参数；拆得太碎，则让模型在名称候选中处理本来只是普通参数的差异。合适边界应该让“选 Tool”对应用户能够理解的一类动作，让参数只描述这类动作内部的变化。

可以按五个问题判断两个动作是否应该留在一起：

判断差异越大时越应该拆分
用户意图用户是否会用不同动词、目标或成功标准描述它们？
必需参数一个动作的参数对另一个是否大量无意义？
权限与确认是否需要不同 capability、审批或确认？
副作用与重试一个只读，另一个会写入、删除或产生外部效果？
结果与错误恢复调用后的结果形状和修复路径是否不同？

这是一组设计信号，不是“满足三项就必须拆”的公式。最终仍要用真实 Task 分布和模型 Eval 验证。

不同副作用应该拆成不同 Tool

对开头的接口，更清晰的模型侧 Tool 可以是：

read_file(path, line_range?)
write_file(path, content, overwrite=false)
delete_file(path, expected_file_version)
delete_directory(path, expected_tree_version)

read_file 是只读动作，只需要读取权限，失败后通常可以修正路径再试。write_file 会改变内容，需要写权限；覆盖已有文件时可以要求额外确认或前置版本。两类删除都绑定目标版本，并按风险决定是否确认；递归目录删除还要绑定树范围与版本，通常需要更严格的 capability 和确认。资源范围与恢复成本不同，所以示例把它们拆开。

现在用户说“看看 config.yaml”。从两个分析维度看，这个调用只需给出 read_file 与 path；content、force 和删除确认不再进入这一轮决策。Runtime 验证并规范化 Tool 名与参数后，对 canonical file.read action 和目标资源检查 actor 已有的 capability，不会因为模型选择了名称就授予权限。

如果用户说“把 timeout 改成 30 秒”，模型会选择 write_file 或更窄的编辑 Tool。是否值得再拆出 edit_file，要看产品的真实合同：如果 edit 接受 patch、要求原内容版本并在冲突时重试，而 write 接受完整内容并可创建文件，两者有不同参数与恢复路径，拆分有帮助；如果它们最终都要求完整新内容、权限和失败语义也相同，两个近义 Tool 只会增加选择歧义。

不要把普通参数误拆成 Tool

假设读取接口还支持 encoding=utf-8|base64。这通常只是同一读取意图的表示方式，没有新的权限、副作用或成功标准。拆成 read_utf8_file 和 read_base64_file，会迫使模型在不了解文件内容前先猜编码。

同样，list_files(path, recursive=false) 可以保持一个 Tool，只要普通与递归 listing 共享相同的权限边界、受限成本和结果 contract。如果递归扫描会跨越不同资源边界、产生显著成本或需要单独确认，那时才有理由把它拆成另一个受限动作。

因此，backend endpoint 既不是合并依据，也不是拆分依据。一个 endpoint 可以对应多个模型 Tool；多个 endpoint 也可以在模型侧组成一个稳定意图，只要 Runtime 在背后处理差异而不让模型猜内部拓扑。

权限边界通常比命名偏好更可靠

当两个动作在安全属性上不同，拆分往往最有价值。考虑 get_invoice 与 refund_invoice：它们共享 invoice_id，但前者只读，后者会产生资金副作用、需要更高权限和明确确认。合成 invoice(command=get|refund) 后，Runtime 仍可把经过 schema 校验的 command 规范化为 canonical action，再据此做授权、日志和确认；如果还要在模型调用前隐藏 refund，就必须派生并版本化受限 schema。拆分只是让这种过滤和政策映射更直接。

拆分后，Runtime 可以在模型看到 Tool 之前就按 actor capability 隐藏 refund_invoice；即使可见，执行前也要验证并规范化 Tool 名与参数，再根据可信 Context 和 backend 当前状态，对 canonical action 与资源重新授权，并要求绑定 invoice_id 与金额的确认。Tool 名称同样由模型生成，不是安全边界；拆分的价值是让 surface 过滤、政策映射和审计更直接。

用 Eval 决定，而不是看 schema 是否整齐

至少准备四类测试：只读请求、写入请求、高风险删除请求，以及意图不完整、应该先澄清的请求。每个 case 先标注允许的结果集合，例如：

case_id: inspect_config
expected: call(read_file) | clarify
forbidden_effects: [write, delete, network_egress]

对合并和拆分方案使用相同模型 snapshot、prompt、Tool 可见性策略与 Task 集，并为每个 case 重复固定数量的 trial。在 sandbox、dry-run 或 spy backend 中记录：

  • 结果是否落在标注的 call / clarify / refuse 集合内，包括零调用和多调用；
  • 参数是否有效且只包含当前动作需要的字段；
  • 模型是否提出了超出用户意图的副作用；
  • 失败后需要多少次修复调用；
  • schema 与 Tool definitions 占用的 token。

“policy 与 confirmation 能否精确绑定动作”不需要靠模型抽样判断，应另做确定性的 contract test。详细指标体系属于后续 Tool Eval；这里的最小实验只用于比较这次合并或拆分是否降低误选。

OpenAI 的 function tools 与 Anthropic 的 client tool definitions 都以名称、描述和 JSON Schema 向模型表达可调用动作；OpenAI 也另有不使用 JSON Schema 参数的 custom tools，因此这里不把结论泛化到所有 Tool 类型。严格 schema 能约束参数形状，却不会替系统判断 Tool 的语义边界。一个 command=delete 可以完全符合 enum，仍然不是用户要的“看看文件”。所以 Eval 必须检查 intent 与 side effect，不只检查 JSON 是否通过验证。

回到问题

万能 Tool 把读取、写入和删除的差异藏进一个参数，让模型更难区分副作用；若要按动作收窄 surface，Runtime 还得派生受限 schema，并在 policy 中先规范化 discriminator。机械拆分则会把编码、flag 或 backend 拓扑变成不必要的 Tool selection。

更稳定的做法，是按用户可区分的意图、必需参数、权限、外部效果与错误恢复划边界，再用 Eval 检查模型是否真的更少误选。对文件例子，读取、写入、单文件删除和递归目录删除值得拆开；编码方式通常只应留作参数。Tool surface 的形状服务于模型决策，而不是复刻后端目录。
