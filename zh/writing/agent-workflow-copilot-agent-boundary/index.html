Agent 44：怎样在 Workflow、Copilot 与 Agent 之间选择

用路径可预编排性、动态证据、行动责任和结果验证区分 Workflow、Copilot 与 Agent，并组合三者而不是争夺统一标签。

问题

某团队计划使用 Agent 自动分配退款审批人。规则已经写在政策中：

  • 金额不超过 1000，由一线客服提交；
  • 超过 1000 且不超过 5000，需要主管审批；
  • 超过 5000，需要财务审批；
  • 特殊商品额外增加合规审批。

输入结构明确，所有分支可以提前列出。模型当然可以读取金额和商品类型，再输出审批人，但它没有解决任何未知问题，只是在重新推断一套确定规则。

与此同时，另一项任务要求系统根据客户描述、订单、支付和物流状态动态调查问题，并决定接下来查询哪个系统。团队也把它叫做 Workflow。

当 Workflow、Copilot 和 Agent 只被当成产品标签时，设计讨论会围绕名称进行；真正需要判断的是：路径由谁决定、动作由谁负责、结果由谁验证。

Workflow 拥有预先确定的控制流

Workflow 适合控制流可以提前表达的任务。

它不要求每个任务只有一条路径。条件分支、循环、超时和人工审批都可以属于 Workflow，只要分支条件与后续动作能够在执行前定义。

退款审批路由可以表示为：

amount <= 1000
  → 一线处理

1000 < amount <= 5000
  → 主管审批

amount > 5000
  → 财务审批

special_item = true
  → 追加合规审批

这里需要的是规则版本、确定性执行和审计，而不是模型在每次请求中重新解释政策。

Workflow 的核心并非“没有 AI”，而是控制流 owner 在执行前已经知道合法路径。即使某一步使用模型提取商品类别，审批路由仍然可以由 Workflow 拥有。

Copilot 改善人的决策，但不接管任务

有些任务无法完全用确定规则表达，但最终判断仍应由人负责。

例如，客服面对一段复杂诉求，需要理解客户关心的问题、汇总历史沟通，并拟定处理方案。模型可以：

  • 总结客户诉求；
  • 找出可能相关的政策条款；
  • 提示缺失材料；
  • 生成回复草稿；
  • 比较不同处理选项。

如果客服审查后决定下一步，并由客服触发所有外部动作，这更接近 Copilot。

Copilot 的价值不在于“只能聊天”，而在于它没有独立的任务完成责任。它优化人的信息处理和判断，却不代表用户持续推进外部状态。

因此，Copilot 的成功指标通常包含建议采纳、人工修改和决策时间，而不能直接把外部任务完成归因给模型。

Agent 处理不能预先穷举的运行时路径

中间观察会改变下一步，并不足以证明任务需要 Agent。Workflow 的条件分支同样在运行时读取结果；只要合法状态、判断条件和后续转移能够预先定义，控制流仍然可以由 Workflow 拥有。

Agent 的价值出现在更窄的条件中：系统需要解释开放输入，根据当前目标判断还缺什么证据，并在一组有界能力中选择下一步，而这些合法路径无法在当前任务范围内被穷举成稳定规则。

退款调查可能是：

读取客户诉求
→ 查询订单
→ 根据订单状态决定是否查询物流
→ 发现支付冲突后查询支付流水
→ 请求用户补充材料
→ 重新评估当前状态
→ 创建退款草稿或升级人工

如果订单、支付和物流只有一组固定状态及转移，这条路径仍然应该编码为 Workflow。只有当客户描述和外部证据是开放的、所需调查步骤不能被稳定枚举时，Agent 才负责维护任务目标、解释证据缺口，并在多个合法能力之间选择下一步。

但“动态选择路径”仍不自动意味着“完全自主”。Agent 只应在 Task Contract 允许的范围内推进状态；高风险动作可以继续由 Workflow 插入审批，政策规则仍由确定性组件执行。

Agent 的核心差异不是“运行时才知道分支”，而是在有界权限内处理无法预编排的 path selection 和 task progression。所有可预定义的政策判断和状态转移仍应留在确定性边界。

四个问题比功能列表更适合做选择

可以用四个问题选择主要执行机制。

路径能否提前编排

如果分支和循环都能在执行前定义，优先使用 Workflow。分支数量多不等于需要 Agent。

合法路径能否被稳定穷举

动态证据是所有条件执行都会遇到的现象。真正的分界是：证据的解释、缺口和下一步能力是否可以提前写成稳定 predicate 与 transition。可以穷举时仍然优先 Workflow；无法穷举但能力和权限可约束时，才考虑 Agent。

谁拥有外部动作

如果人审查并触发所有动作，Copilot 可能已经足够；如果系统需要在边界内持续推进外部状态，则需要 Agent 或 Workflow 承担执行责任。

完成是否能够被外部验证

无论使用哪种机制，结果都必须可验证。不能观察动作结果的任务，不适合直接提高自主程度。

把四个问题组合起来，可以形成一个简化决策：

任务特征主要机制
路径和规则确定，动作可预编排Workflow
判断开放，但由人选择和执行Copilot
证据和路径无法稳定穷举，系统需要在有界能力内持续推进Agent
结果不可观察或风险无法约束暂不自动执行

这张表给出的是主要责任边界，不要求整个产品只能属于一列。

真实系统通常组合三者

退款处理可以同时使用三种机制：

Agent
  解释开放诉求和未预见的证据缺口
  在有界能力内选择下一项调查或 Clarification

Workflow
  执行金额阈值、审批路由和超时升级

Copilot
  向客服解释证据、提供方案并生成沟通草稿

这种组合保留了各自最强的语义：

  • 确定规则由确定性系统执行；
  • 开放判断由模型辅助；
  • 不能预编排、但能力可约束的任务由 Agent 推进；
  • 风险决定由明确 owner 承担。

如果强行让 Agent 拥有全部逻辑，政策规则会变得难以审计；如果强行用 Workflow 表达全部调查路径，流程会不断增加脆弱分支；如果只做 Copilot，用户可能仍要手工完成所有跨系统协调。

选择机制不是比较“智能程度”，而是分配控制流和责任。

自主程度应独立于机制命名

即使确认需要 Agent，还要单独确定它的自主程度：

只读分析
→ 提议动作
→ 确认后执行
→ 有界自动执行
→ 自动执行并抽样复核

同一个 Agent 可以对不同动作处于不同等级。例如，它可以自动查询订单，确认后创建退款草稿，但永远不能直接执行超过阈值的退款。

将自主程度独立建模，可以避免“既然叫 Agent，就应该端到端自动化”的错误推论。Agent 描述动态任务能力，权限仍由动作风险和验证能力决定。

回到问题

退款审批路由具有明确输入和固定规则，因此应该由 Workflow 执行。让模型每次重新判断审批人，只会增加不确定性。

退款调查若只有固定状态和分支，仍然应由 Workflow 推进；只有当开放诉求和证据缺口让合法调查路径无法稳定穷举时，才适合由 Agent 在有限能力范围内推进。客服解释和沟通草稿则可以保留为 Copilot。

Workflow、Copilot 与 Agent 不是三个互斥产品，也不是从低级到高级的成熟度阶梯。它们分别拥有预编排控制流、人的决策辅助和运行时任务推进。

需求调研的目标不是为 Agent 找更多工作，而是把每段工作交给能够承担其事实、控制流和风险责任的机制。
