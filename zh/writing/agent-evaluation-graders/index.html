Grader 应该验证哪一层结果

把确定性断言、规则 Grader、LLM Judge 与 Tool、Context 领域结果放进同一证据层级。

2026/07/24 阅读 次
Agent VerificationAgentEvaluationLLM Judge

问题

下面用一个构造的 Eval case。它要求 Agent 完成两件事：

  1. 把客户地址更新到指定 revision；
  2. 写一封解释地址变更影响的邮件。

最终文本读起来很自然，于是一个 LLM Judge 给出高分。但后端仍停留在旧 revision，邮件还把客户所在区域对应的配送规则写错了。

如果让同一个 Judge 同时判断“数据库是否真的更新”“领域规则是否满足”和“文字是否清楚”，三个证据强度完全不同的问题就被压成了一个分数。Judge 既可能相信 Agent 的自述，也无法访问真正的 backend state。

Grader 设计的核心不是寻找一个万能评分器，而是先问：这个命题离确定事实有多远，最强的可用证据是什么。

先把成功标准拆成可观察命题

“成功更新地址并写好邮件”可以拆为：

命题最强证据特征
地址 revision 已从 7 变成 8后端读取或 committed event确定执行事实
只修改了目标客户地址mutation diff确定执行事实
新地址属于区域 North版本化区域规则可编码领域判断
邮件使用 North 对应的配送说明邮件结构 + 规则映射多数可编码
邮件解释清楚、语气得体文本与 rubric开放语义判断

拆分后，每个 grader 只回答它有能力证明的问题。Task success 是这些条件按产品规则组合后的结论，不应反过来替代底层证据。

确定性断言优先验证已经存在的事实

只要命题能从 trace、Artifact、数据库或明确 contract 中直接观察，就应优先使用代码断言。例如：

must:
  customer_42.address_revision == 8
  mutation_diff.changed_records == ["customer_42"]

forbid:
  unauthorized_tool_call
  mutation_to_other_customer

must-before:
  committed_revision_event < agent_success_claim

这里的 must、forbid 和时序约束分别验证存在、禁止和先后关系。它们的失败通常可直接定位到具体事实，不需要模型重新解释一次。

确定性不等于只比较字符串。JSON Schema、集合差异、Artifact hash、数据库 revision、Tool effect reference 和状态机 transition 都可以成为断言输入。边界是这些证据必须来自可信 owner，不能拿 Agent 自己生成的“已更新”文本去证明更新发生。

这类 grader 的主要风险是 contract 写错或 fixture 不完整，因此它们同样需要版本、测试与审阅；“是代码”不自动等于“是正确标准”。

Rule-based Grader 负责可编码的领域约束

有些判断不是原始事实，却能由明确规则稳定推导。地址对应区域就是一例：

输入：normalized_address + region_rule@12
输出：region = North

接着可以验证邮件是否包含 North 对应的必要说明，是否错误引用 South 的规则。只要领域 owner 能给出稳定 contract，就没有必要让 LLM Judge 每次重新推断。

规则 grader 应保存：

  • 输入字段与 source revision；
  • rule 或 policy version；
  • 命中的具体规则；
  • verdict 与可解释 reason；
  • 对未知值的处理。

遇到规则表没有覆盖的新地址时，结果应是 unknown 或需要人工审阅，而不是用默认分支悄悄判通过。

LLM Judge 只处理难以稳定编码的语义

邮件是否清楚、是否完整解释影响、语气是否符合受众，可能难以被有限规则覆盖。这时 LLM Judge 有价值，但它提供的是有条件的语义判断，不是确定事实。

Judge input 应只包含完成 rubric 所需的信息：

task: explain_address_change
candidate_email: ...
grounding_facts:
  region: North
  delivery_rule: ...
rubric_version: email_clarity@4

Rubric 要把维度分开，例如事实一致性、完整性、清晰度和语气。若“是否使用正确区域规则”已经能确定性验证，就把 verdict 作为 grounding fact 传入或直接设为 hard gate，不要让 Judge 再投一次票。

Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena 展示了 model-based judge 与人工偏好的比较，也讨论了 position、verbosity 和 self-enhancement 等偏差。对工程系统而言，这意味着 Judge 需要校准和版本治理，不能因为输出带理由就把它当作客观真值。

Judge 本身也是被评测系统

一个可维护的 Judge contract 至少包括：

  • Judge model 的可解析版本或响应 metadata；
  • rubric、system prompt 与输入规范化版本；
  • 人工标注 calibration set；
  • 重复 trial 的 verdict distribution；
  • pass、fail、uncertain 与调用失败的处理；
  • cache key、usage、latency 和成本事实；
  • 与被测 configuration 分开的 identity。

不要只记录最终平均分。对同一 calibration item 重复调用时，应保存：

case_id × judge_configuration × judge_trial → verdict

然后按明确分母报告与人工标签的一致、false positive、false negative 和 uncertain 数量。本文不提供一组通用阈值，因为可接受误差取决于 rubric、风险和人工复核成本。

若 Judge version 或 rubric 改变，旧分数与新分数不能直接混用。可以在同一 calibration set 上运行重叠实验，查看分歧样本，再决定是否重评历史结果。

Cache 和成本不能隐藏 Judge 变化

Judge cache key 至少应包含：

normalized input fingerprint
+ judge model/configuration identity
+ rubric version
+ grading prompt version

缺少任一项都可能把旧 rubric 的 verdict 错误复用给新实验。Cache hit 应与真实 Judge call 分开计数；token、latency 和 billed cost 只对实际调用归因，allocated infrastructure cost 则使用明确的分摊规则。

评测报告若写“Judge 平均成本”，还必须说明分母是 scheduled grading items、实际 Judge calls，还是包含 retry 的 Judge Attempts。本文不填任何 provider 价格，因为这些值会变化，也不是 grader 选择原则的一部分。

Hard Failure、Soft Score 与 Unknown 要分别保留

回到地址案例，可以得到一条分层评分记录：

deterministic:
  address_revision_updated: fail
  mutation_scope_exact: pass
rule_based:
  region_mapping: North
  delivery_rule_consistent: fail
llm_judge:
  clarity: pass
  tone: pass
  judge_configuration: judge_config_sha256:...
task_outcome: fail

这里即使语义分数很好，地址没有提交仍是 hard failure。相反，如果所有事实和规则都通过，而 Judge 返回 uncertain，系统可以进入人工审阅，而不是擅自把 uncertain 当成 fail 或 pass。

加权总分适合排序或趋势分析，但不能覆盖 hard invariant。发布 gate 应先处理禁止项和确定性失败，再解释 soft score 的聚合方法与分母。

更复杂的领域指标仍由各自评测拥有

Tool Eval 会进一步验证 selection、argument、repair、execution 和 mutation precision；Context Eval 会验证 required information、provenance、pollution、conflict 和 permission。这些指标的定义应留在对应领域，而不是塞进一个通用 Judge。

通用 grader 层只提供选择原则：

可信事实可直接观察
  → deterministic assertion

明确领域规则可稳定编码
  → rule-based grader

开放语义无法稳定编码
  → calibrated LLM Judge 或人工评审

当一个开放判断后来形成稳定 contract，应把它下沉为规则或确定性断言。证据层级应随着系统成熟向更强的可验证性移动。

回到问题

地址更新是否发生，应由 backend revision 和 mutation diff 证明；区域规则是否正确，应由版本化领域规则验证；只有邮件是否清楚得体，才值得交给经过校准的 LLM Judge。

把三个层级混成一个 Judge 分数，会让自然语言的说服力覆盖真实副作用。更可靠的设计是先使用最强可得证据，保留 hard failure、soft score 和 unknown，再把它们按产品 contract 组合成 Task outcome。

LLM Judge 不是最后的真相层，而是确定事实和可编码规则都无法完整回答时，一个需要被版本化、校准、重复评测和计费的评测组件。
