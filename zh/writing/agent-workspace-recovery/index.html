Agent 25：Workspace 如何跨 Runtime 恢复

用 Workspace identity、Runtime profile compatibility 和 lease 判断有状态执行环境应复用、迁移还是隔离。

2026/07/24 更新于 2026/07/27 阅读 次
Agent ProductionAgentSandboxRecovery

问题

一个 Python Agent 的 Runtime 崩溃了。系统启动新 Runtime，把旧 Workspace 重新挂载到相同路径，然后从上一次 Session 继续。

第一个 Tool Call 却破坏了 Workspace：旧环境里的 native extension 是为另一版 Python 构建的，cache 与新工具链不兼容，而上一次写入还停留在未确认状态。文件确实“还在”，但这不等于新 Runtime 可以安全接管。

恢复需要回答两个不同问题：

  1. 当前 Session 是否有权接管这个 Workspace？
  2. 新 Runtime 是否与 Workspace 中需要保留的状态兼容？

前者由 lease 和 fencing 解决，后者需要显式的 Runtime profile compatibility。两者都成立，才允许复用；否则只能迁移、重建派生状态或隔离。

Workspace identity 必须独立于 Runtime

把 Workspace 等同于某个容器目录，会让 Runtime 生命周期决定文件生命周期。更稳妥的模型是：

对象用途典型生命周期
Workspace identity表示一个可继续工作的文件空间跨 Runtime
Runtime提供进程、工具链和隔离环境可替换
Workspace lease决定当前写 owner有期、可接管
Artifact reference指向可发布或下载的稳定产物跨 Workspace
temporary pathRuntime 内可丢弃的中间文件随 Runtime 消失

相同的 /workspace/report.md 只说明进程内路径相同，不证明底层 Workspace identity、文件 revision 或 lineage 相同。恢复记录应保存稳定 reference，再由新 Runtime materialize 到本地路径。

先把 Workspace 内容按兼容责任分类

Workspace 内的状态并不具有相同的兼容承诺：

  • 用户和任务产物：源代码、文档、数据文件，通常要求保留。
  • 可重建派生状态：package cache、索引、编译输出，可以在 profile 变化时删除并重建。
  • Runtime-owned metadata：虚拟环境、socket、PID、lock、绝对路径索引，通常不能跨 Runtime 直接继承。
  • 外部 Artifact reference：只保存引用和 revision，不应因挂载路径改变而失去身份。

这项分类决定迁移策略。如果把所有目录都当成“持久文件”，新的 Runtime 会误用旧 binary 和 lock；如果把整个 Workspace 都视为 cache，恢复又会丢掉用户真正需要的结果。

一个最小 manifest 可以记录：

{
  "workspace_id": "ws_7",
  "revision": 18,
  "created_by_profile": "python-3.12@sha256:old",
  "layout_revision": 3,
  "data_schema_revision": 5,
  "mount_policy_revision": 8,
  "zones": {
    "/project": "durable",
    "/cache": "rebuildable",
    "/runtime": "runtime_owned"
  }
}

这是设计示例，不是通用 provider schema。关键不在字段名字，而在于恢复决策有可比较的输入。

Runtime profile 是兼容承诺，不只是镜像标签

latest 或一个可变镜像名不足以判断兼容性。Runtime profile 至少应固定会改变 Workspace 解释方式的部分：

  • image digest 与 OS/architecture；
  • 语言 Runtime 和关键 toolchain revision；
  • Workspace layout 与 mount policy；
  • Runtime-owned metadata schema；
  • Sandbox security policy 中会影响可见路径或权限的部分。

不是每次差异都要求完整迁移。可以把比较结果分成四类：

结果条件动作
compatibledurable 区解释不变，派生状态仍兼容直接挂载并验证
rebuildabledurable 区兼容，cache/runtime-owned 区不兼容隔离旧派生状态后重建
migration_requiredlayout 或数据 schema 需要转换在独占 lease 下执行版本化迁移
incompatible无安全迁移路径或策略不允许隔离并停止自动恢复

“同一主版本大概兼容”不是可靠判断。Profile compatibility 应由显式规则和 fixture 测试支持；无法确认时选择隔离，比让新 Runtime 直接写更安全。

接管要同时验证 lease 与 revision

假设 Runtime A 在 Workspace revision 18 时失联。Control Plane 为 Runtime B 获取 generation 6 的 lease。B 不能只凭 mount 成功就写入，它还应确认：

workspace_id = ws_7
expected_revision = 18
lease_generation = 6
profile_decision = rebuildable

Workspace backend 或可信写入层在提交时检查 generation 与 revision。若 A 恢复后带着 generation 5 提交，应被拒绝；若发现 revision 已经变成 19，B 也不能继续沿用基于 revision 18 生成的迁移计划。

迁移本身需要状态，例如 planned → running → verified → committed。失败时保留旧 revision 或隔离中间结果，避免把“脚本启动过”误当成迁移完成。对于不可逆转换，先创建新 revision 或快照通常更容易恢复，但具体原子性取决于底层存储，不能由 Workspace 抽象自行承诺。

Fencing 必须落在实际文件写入路径

Lease record 或 Workspace revision 字段本身不会阻止旧 Runtime 修改一个已经挂载的普通共享 Volume。若 A 仍能直接执行 POSIX write，它可能在任何 revision commit 之前覆盖 bytes；事后发现 generation 过期只能暴露冲突，不能撤回写入。

接管协议因此必须选择一种真实可强制的边界：

  • 存储服务接受带 generation 的 write token，并拒绝旧 token；
  • 基础设施先强制 detach 旧挂载，再证明新的 single-writer attach 已成立；
  • 新 Runtime 先以只读方式挂载，直到旧 writer 的失权证据成立；
  • Runtime 只写隔离 overlay 或不可变 Blob，再由 Workspace owner 原子比较 lease generation 与 expected base revision，发布新的可见 revision。

不同存储系统提供的能力不同。若系统无法证明 A 已失去写能力，B 的状态应是 takeover_pending 或 read-only，而不是为了可用性开放双写。ReadWriteOnce 之类的调度或挂载标签也不能代替实际产品对已挂载 writer 的强制保证。

开场还提到上一次写入停留在未确认状态。Workspace recovery 只能根据可见 revision 判断文件状态，不能替 Run 或 Tool effect owner 宣告那次逻辑操作成功或失败。恢复前应按原 operation/effect reference 查询或 reconciliation；如果那项 unknown effect 可能继续修改同一组文件，新 Runtime 只能隔离相关路径或等待 owner 收敛，不能把取得新 lease 解释成旧操作从未发生。

把开场 Workspace 走一遍

开场中的新 Runtime 使用 Python 3.13，而 manifest 表明旧 profile 是 Python 3.12：

  1. Control Plane 先确认旧 lease 已失效，并为新 Session 获取 generation 6。
  2. Compatibility rule 判定 /project 中的源文件可保留，/cache 与 /runtime/venv 必须重建。
  3. 系统将旧派生目录隔离为只读诊断数据，不让新工具链直接加载。
  4. Run owner 查询上一次未确认写入；确认没有仍会修改 /project 的旧 effect 后，Workspace owner 才开放 generation 6 的写边界。
  5. 新 Runtime 从 lockfile 重建环境，运行最小验证，再把 Workspace revision 推进到 19。
  6. 只有 revision 19、generation 6 和目标 profile 全部匹配后，Sandbox 才进入 ready。

如果 lockfile 或数据 schema 没有受支持的迁移路径，结果应是 incompatible，由用户选择旧 profile、导出 Artifact 或人工迁移，而不是静默尝试。

Volume pool 不能改变恢复语义

预创建 volume 可以把 provisioning 延迟移出用户关键路径，但 pool 中的 volume 在绑定前不应拥有某个 Workspace 的逻辑身份。领取过程仍需原子绑定 workspace_id，并执行相同的清理、初始化、profile 和 lease 检查。

因此，Volume pool 是延迟与成本优化。它不能让系统跳过 compatibility，也不能把“某块盘可用”升级成“某个 Workspace 可恢复”。如果没有真实 latency 与 idle cost 数据支持，先按需创建通常更简单。

回到问题

开场中的旧 Workspace 不应被直接交给 Python 3.13 Runtime。正确恢复路径是：先让新 Session 获得新的 lease generation，再证明旧 Runtime 已无法写入，交给原 effect owner 收敛未确认操作，随后依据 manifest 将 durable 文件与可重建状态分开，清理不兼容环境，重建工具链并验证新的 Workspace revision。

如果 profile 规则无法证明兼容，系统应隔离 Workspace，而不是把“挂载成功”当作恢复成功。

Workspace 的持久身份让文件跨 Runtime 延续；lease 防止多个 Runtime 同时拥有它；profile compatibility 决定新 Runtime 怎样解释它。三者合在一起，恢复才从“重新挂盘”变成可验证的接管协议。
