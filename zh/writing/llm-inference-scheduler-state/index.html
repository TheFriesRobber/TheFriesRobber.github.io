LLM Infra 10：推理调度器必须拥有哪些状态

说明跨 Replica 调度为何不能只看 Queue length，并建立 Request、Endpoint observation、placement decision、affinity 与 admission outcome 的状态边界。

2026/07/29 阅读 次
LLM InfraInferenceSchedulingControl Plane

问题

两个 Replica 的 queue length 都接近零。一个已经加载目标 Adapter，并持有可复用前缀；另一个需要冷加载，KV pool 也接近上限。Least-queue 把请求发给后者，随后 gateway timeout；重试又去了另一个 deployment generation。

Queue length 没有错，它只是没有描述请求能否执行、要做多少 Token work，以及 Endpoint observation 是否仍然新鲜。

跨 Replica inference scheduling 不是一次无状态负载均衡。它需要把请求约束、Endpoint observation、placement decision 与 execution admission 分开。

Request count 不是 service demand

“队列里有 3 个请求”可能意味着：

  • 3 个短 Decode；
  • 1 个超长 Prefill 加 2 个短请求；
  • 3 个等待尚未加载 Adapter 的请求；
  • 3 个已经失去 deadline、即将被取消的请求。

Cluster scheduler 至少需要消费：

request_spec:
  request_id: req_123
  required_model_revision: release_91a
  adapter: adapter_sql_v4
  token_envelope:
    prompt_tokens: 2400
    max_output_tokens: 300
  deadline: 2026-07-29T12:00:02Z
  affinity:
    prefix_key: optional
    session_key: optional

这些字段来自请求与受信任 control plane。业务“需要什么能力”已经在 Agent/model boundary 解决；Infra scheduler 只处理已经 resolved 的兼容 deployment 需求。

Endpoint state 是带时间的观测

llm-d 与 Gateway API Inference Extension 的公开调度设计会观察 queue、running requests、KV utilization、LoRA affinity 或 prefix/session affinity，再进行 filter、score 和 pick。它们证明这些信号可用于 inference-aware routing，也同时暴露了一个事实：scheduler 看到的是 observation，不是设备内的即时真相。

一份 observation 应带来源和时效：

endpoint_observation:
  observation_id: obs_b_91
  endpoint_uid: replica_b
  deployment_revision: release_91a
  endpoint_generation: 42
  collected_at: 2026-07-29T12:00:00.100Z
  signals:
    queue:
      source: runtime-metrics
      observed_at: 2026-07-29T12:00:00.080Z
      ttl_ms: 250
      running: 2
      waiting: 0
    kv:
      source: runtime-kv-events
      watermark: 18442
      observed_at: 2026-07-29T12:00:00.020Z
      ttl_ms: 150
      utilization: 0.91
    adapters:
      source: residency-controller
      observed_at: 2026-07-29T11:59:59.900Z
      ttl_ms: 500
      active: [adapter_chat_v2]
    health:
      source: endpoint-health-controller
      observed_at: 2026-07-29T12:00:00.090Z
      ttl_ms: 200
      state: ready

ttl_ms、字段组合和 generation fence 是本文的设计建议，不是某个项目的统一协议。不同来源保留自己的时间与 watermark，避免一次较新的聚合掩盖已经过期的 KV 或 residency 信号。过期或缺失的硬约束信号应让 Endpoint 被过滤；优化信号缺失时则采用保守分数，不把未知当成命中。Placement 必须记录实际消费的 observation_id。原则是：没有 observation age，就无法判断“空闲”是否仍然成立。

Filter、Score 与 Pick 应留下决策证据

调度可以分三步：

  1. Filter：排除 model revision、Context、adapter、拓扑或健康状态不兼容的 Endpoint。
  2. Score：按 pending Token、KV capacity、adapter/prefix affinity、queue age 和 deadline 计算候选代价。
  3. Pick：选择一个 Endpoint，并保留所依据的 observation references。
placement_decision:
  placement_id: place_456
  request_id: req_123
  observation_refs: [obs_a_77, obs_b_91]
  candidates:
    - endpoint: replica_a
      score: 0.82
      reasons: [adapter_ready, prefix_affinity]
    - endpoint: replica_b
      score: 0.21
      reasons: [adapter_missing, kv_pressure]
  selected_endpoint: replica_a
  policy_version: placement-v5

这是一条可审计决策记录，不保证同样输入能在未来重放出同样结果。Observation、热度和 Runtime state 都会变化。

Placement 成功不等于 Execution 已接纳

即使 scheduler 选中了 Replica，状态也可能在网络传输期间改变。Replica 还需要基于本地最新 KV、Token budget 和 generation 进行 admission。

本文建议把结果表达为：

admission_receipt:
  placement_id: place_456
  attempt_id: attempt_07
  admission_id: admit_802
  endpoint_uid: replica_a
  outcome: accepted # accepted | queued | rejected
  execution_id: exec_991
  reason: kv_capacity_available
  returned_at: 2026-07-29T12:00:00.220Z

AdmissionReceipt 同样不是行业标准。它解决的是状态边界：cluster scheduler 拥有 placement decision，Replica scheduler 只返回自己已经做出的本地 execution admission。

Gateway 另外拥有对这次调用的观测：

receipt_observation:
  attempt_id: attempt_07
  state: unknown # received | unknown
  reason: upstream_timeout_before_receipt

unknown 不是 Replica 的 admission 决定，而是 gateway 没有收到 receipt 时对 attempt 的判断。缺失 receipt 既不证明请求没有被接纳，也不证明 execution 没有开始。

如果 gateway timeout：

  • 不能推出 placement 未到达；
  • 不能推出 execution 未开始；
  • 不能推出取消已经生效；
  • 更不能承诺业务 exactly-once。

后续重试必须使用新的 attempt identity，并在第 14 篇定义 partial delivery 与 unknown outcome。

Affinity 只能优化兼容候选

Prefix、session 与 Adapter affinity 可以避免重复 Prefill 或冷加载，但不能覆盖硬约束。

正确顺序是：

compatibility and health filter
→ capacity / deadline feasibility
→ affinity score

如果一个 Endpoint 持有 Prefix Cache，却无法满足当前 scheduling step 与本地 admission policy 所需的 KV/Token budget，Cache hit 不能让它变成可行候选。Paged KV Runtime 可以逐步分配 block；只有平台明确采用 full-envelope reservation 时，才需要按完整请求上限做保守判断。同样，adapter ready 不能覆盖 deployment revision 或 tenant isolation 不兼容。

llm-d 的 precise prefix-aware routing 依赖 Runtime KV events；近似方式则维护推断的内存 LRU。二者的 freshness 和准确度不同，必须进入 observation source，而不能统一叫“Cache aware”。

重新调度开篇请求

Least-queue 只看到：

replica_a.queue = 0
replica_b.queue = 0

Inference-aware decision 还看到：

replica_a: adapter ready, prefix affinity, KV sufficient
replica_b: adapter missing, KV pressure, observation older

于是 Filter/Score/Pick 选择 A；A 的本地 scheduler 再返回 accepted。若 gateway 没有收到 A 的 receipt，这次 attempt 的 gateway observation 才是 unknown；它不应假装请求尚未执行，而要进入第 14 篇的流式失败协议。

回到问题

开篇请求不应该被发给 queue 同样短、却需要冷加载且 KV 紧张的 Replica。调度器需要的不是更多零散指标，而是四个明确对象：RequestSpec、带时间的 EndpointObservation、可审计 PlacementDecision，以及 Replica 本地返回的 Admission outcome。

它们分开之后，stale state、affinity、timeout 和 retry 才不会被压缩成一次“负载均衡成功”。
