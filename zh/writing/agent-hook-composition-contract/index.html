Agent 03：Hook 的组合顺序必须成为执行契约

从一次被重新加入请求的禁用 Tool 出发，定义 Hook 的 phase、修改权、短路、清理、失败与 replay 契约。

问题

一次 Model Turn 开始前，Runtime 依次运行三个 Hook：

  • capability policy 删除当前用户无权使用的 delete_file；
  • provider transformer 把内部请求转换成供应商 payload；
  • trace observer 记录模型最终看到的 Tool surface。

如果它们只是按注册顺序共享并修改同一个对象，transformer 可能从原始 registry 再次读出 delete_file；observer 也可能记录 policy 执行前的候选，而不是实际请求。三个 Hook 单独看都正确，组合后却改变了授权结果和可观测事实。

beforeModel 只说明调用发生在模型之前，没有说明谁先执行、谁能修改什么，以及某个 Hook 失败后是否应重做已经发生的动作。Hook 要成为稳定 extension point，组合语义必须进入 Runtime contract。

Pi 当前提供 Hook 插口，不提供这套组合协议

在本轮核对的 Pi 源码快照中，Tool 路径只有单个 beforeToolCall 与 afterToolCall 插口。beforeToolCall 在参数 validation 之后、handler 之前执行；afterToolCall 在 handler 返回后执行。当前实现没有多 Hook phase/priority、scope unwind 或稳定 hook_event_id。更重要的是，afterToolCall 抛错会进入当前 Tool 执行的 catch 路径，把已经成功的 handler result 表现为 error，而不是自动隔离成 observer delivery failure。

这不是说 Pi 的行为错误；单 callback contract 不需要假装已经拥有 plugin composition semantics。本文其余部分定义的是宿主或更高层 Runtime 在一个插口内组合多个扩展时需要补上的目标协议，不能写成 Pi 已经提供的保证。当前边界可参考固定版本的 agent-loop.ts。

注册顺序不能承担权限顺序

Hook 数组的注册位置常由模块初始化时机决定，不应顺便决定 policy 优先级。更可靠的方式是先定义 phase，再在 phase 内使用明确的 dependency 或 priority：

trusted inputs
→ policy decision
→ request transformation
→ observation scope
→ model or Tool execution
→ result normalization
→ output policy
→ observation close

这条顺序表达三项约束：

  1. policy 先依据可信 identity 和 current authorization 收窄能力；
  2. transformation 只能转换已批准输入，不能恢复被移除的能力；
  3. observer 读取最终请求和归一化结果，不能把中间对象当成执行事实。

不同 Runtime 可以使用不同 phase 名称，但需要把“谁拥有决定、谁只转换、谁只观察”固定下来。否则新增一个 plugin 就可能改变安全边界。

每类 Hook 只能拥有必要的修改权

Phase 还不够；同一 phase 内的 Hook 也不应默认拿到可变的完整 Context。

Hook 类型可以做什么不能做什么
Policyallow、deny、要求确认、收窄 surface增加超出 Run envelope 的能力
Transformation从已批准输入产生新的 typed value修改 subject、authorization 或 effect identity
Control选择一个声明过的控制分支用任意字符串伪装正常结果
Observation记录 event、metric、trace改写请求、结果或触发业务 effect

Transformation 返回新值比共享可变对象更容易审查。Observer 则应接收只读 view；即使它与执行代码位于同一进程，也不能依赖“约定不要修改”来保护事实。

回到开场：policy 以三个候选和可信授权为输入，输出只含 read_file、write_file 的 allowed request。Transformer 只接收这份结果；trace observer 在 provider payload 完成后记录最终 Tool identity 或稳定 fingerprint。delete_file 没有路径重新进入请求。

Short-circuit 必须产生可观察的 typed outcome

Policy 拒绝、缓存命中、预算耗尽和等待用户确认都可能跳过正常调用。用 null 或提前 return 表示这些分支，会让调用方无法区分拒绝、缓存、等待和 Hook bug。

控制型 Hook 应返回有限、可枚举的 outcome：

continue(transformed_input)
deny(reason, policy_ref)
require_confirmation(action_ref)
use_cached(result_ref)
fail(error_class, retryable)

每种 outcome 都要说明从哪里继续。deny 和 require_confirmation 不调用 handler；use_cached 虽然跳过实际请求，结果仍要经过与实时结果相同的 normalization 和 output policy；所有分支都写入执行事件。

这样 short-circuit 改变的是显式控制流，不是隐藏在 callback 内部的一次提前返回。

Before 与 After 应按 scope 收敛

Tracing span、临时 credential 和资源 lease 通常成对出现。它们更像嵌套 scope，而不是两个互不相关的列表：

before A
  before B
    execute
  after B
after A

如果 after 仍按注册顺序运行，A 可能先释放 B 仍在使用的资源。Runtime 应声明 reverse unwind，并让 cancellation 走同一条清理路径：已经进入的 scope 依次退出，cleanup error 单独记录，不能覆盖原始 cancellation 或执行结果。

尚未进入的 scope 不需要 cleanup；已经提交的外部 effect 也不会因为 unwind 被回滚。Hook cleanup 负责释放 Runtime 资源，不负责改写外部世界。

Observer 失败不能重做业务动作

假设 write_file 已经成功，随后 trace observer 向 collector 写入事件时 timeout。若整个 Hook chain 被标记为 failed，外层 retry 可能再次执行 write_file。

正确记录应保留两个 owner：

Tool Execution: succeeded, artifact=report.md@v3
Trace delivery: unknown or failed, event_id=trace-19

Policy 无法判断时，高风险动作通常应 fail closed；纯 transformation 在调用发生前失败，可以安全终止当前阶段；observer 失败则通常降级或单独恢复。强合规系统可以要求审计通道就绪后才允许动作，但这个 gate 必须发生在 effect 之前，不能事后把已发生的写入改成失败。

Replay 复用稳定 Hook event identity

恢复或 retry 可能再次进入同一个 Hook。纯 validation 可以重算；带外部 effect 的 Hook 必须声明 delivery contract。

例如 after-hook 发送通知，通知已经到达但 checkpoint 尚未更新时进程退出。恢复若生成新的 message ID，用户会收到两次。安全选择是：

  • 把通知提升为显式 Tool Execution，使用 logical operation 与 Attempt；
  • 或把它保留为基础设施 Hook，但复用稳定 hook_event_id，由下游按该 identity 去重或幂等 upsert。

稳定 ID 本身不会阻止重复 effect。它只让接收方有机会识别同一次逻辑交付；是否允许 at-least-once、是否具备幂等写入，必须由 Hook contract 明确。

组合契约需要用反例验证

Hook 能注册成功不能证明组合安全。最小 contract suite 应覆盖：

  • policy 永远先于 transformation，已移除的 Tool 不能从 registry 被重新加入；
  • deny 与 require_confirmation 不进入 handler；
  • cached result 虽跳过 handler，仍经过 output policy；
  • before scope 按进入顺序建立，并在异常与 cancellation 下 reverse unwind；
  • observer delivery failure 不改写已经确定的业务结果；
  • replay 复用同一 hook_event_id，重复 delivery 由声明的下游契约收敛。

Tool System Eval 可以继续衡量最终 selection 和 mutation，但这些确定性组合不变量应先由 Runtime contract test 直接断言。

回到问题

开场中的 delete_file 不应该因为 transformer 重新读取 registry 而回来，trace 也不应记录一个模型从未看见的 surface。做到这一点需要：

  1. policy、transformation、control 与 observation 进入声明过的 phase；
  2. 每类 Hook 只获得必要的修改权；
  3. short-circuit 返回 typed outcome 并成为执行事实；
  4. before/after scope 在成功、异常和 cancellation 下都按相反顺序收敛；
  5. observer failure 与业务结果分开恢复；
  6. replay 复用稳定 Hook event identity 和已声明的 delivery contract。

Hook 的价值不是让任意代码插入任意位置，而是在不破坏原执行契约的前提下扩展 Runtime。组合顺序被固定后，新增 Hook 才不会变成隐藏的授权分支或重复副作用入口。
