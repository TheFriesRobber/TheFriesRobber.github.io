Agent Runtime 三：用 RunSpec 隔离业务策略

用执行前编译的 RunSpec 分开 Profile policy 与 Runtime mechanism，避免业务分支不断侵入 Agent Loop。

2026/07/17 阅读 次
AgentRuntimeArchitecture

问题

假设同一套 Agent Runtime 同时支持两种入口：

  • 对话入口使用响应快、成本低的模型，只开放搜索和读取 Tool，最多运行 8 个 Model Turn。
  • 后台研究入口允许更长时间运行，开放文件写入和 SubAgent，预算也更高。

最直接的实现，是在 Agent Loop 里判断入口类型：

if request.mode == "chat":
    model = "fast-model"
    tools = read_only_tools
    max_model_turns = 8
elif request.mode == "research":
    model = "reasoning-model"
    tools = read_write_tools + subagent_tools
    max_model_turns = 40

接下来又会出现付费等级、地区限制、实验分组、用户授权和模型降级。每种条件看起来都只增加一个 if，最终却让 Loop 同时决定“这次执行允许什么”和“Tool Call 应该怎样运行”。

这时最危险的问题不是代码太长，而是同一个请求在执行中途可能改变含义：恢复时重新读取了新配置，Eval 使用了另一套默认值，或者某个分支忘记同步 Tool 权限。

Policy 与 mechanism 为什么要分开

这里的 policy 是“本次执行选择什么”，例如模型、Tool Surface、预算和权限范围；mechanism 是“已经选定后怎样执行”，例如调用模型、校验 Tool Call、传播取消和记录事件。

Agent Loop 应该能够执行不同 policy，但不应该知道为什么某个用户得到了某组 Tool。否则，每增加一种产品规则，都要改动最核心的执行控制流。

可以把边界压缩成三个对象：

对象回答的问题生命周期
Profile某类场景通常采用什么 policy可以持续修改
RunSpec这一次 Run 最终采用什么执行契约Run 创建时固定
Runtime state这一次 Run 已执行到哪里随执行变化

Profile 可以叫 scenario、preset 或 agent definition，名字并不重要。重要的是它仍是一份可变策略；真正交给 Runtime 的应该是已经解析完默认值、权限和实验条件的 RunSpec。

RunSpec 固定什么

继续使用前面的后台研究入口。编译后的 RunSpec 可以是一个概念性结构：

{
  "spec_version": 3,
  "profile": {"id": "research", "revision": 12},
  "model_route": {
    "primary": "reasoning-model",
    "fallback_policy": "same-capability-only"
  },
  "tool_surface": {
    "revision": 27,
    "allowed": ["search", "read_file", "write_file", "spawn_agent"]
  },
  "limits": {
    "max_model_turns": 40,
    "deadline_seconds": 1800,
    "max_subagents": 3
  },
  "authority": {
    "subject_ref": "subject_8",
    "grant_ref": "grant_31",
    "grant_revision": 5,
    "max_audience": ["search-service", "workspace-service"],
    "max_scopes": ["web:search", "workspace:read", "workspace:write"]
  }
}

它固定的是选择结果，不是把整个运行现场都塞进配置。

  • Model response、当前 Model Turn、剩余预算和 Tool Result 属于 Runtime state。
  • 用户刚上传的新文件、执行期间的 steering 输入属于新的运行事实。
  • OAuth token、API key 等 secret 不应复制进 RunSpec。grant_ref + revision 指向不可变的最大授权 envelope，RunSpec 同时固定 audience、scope 和 resource boundary；执行时可以因撤销或当前条件进一步收窄，不能在 fingerprint 不变时扩大权限。
  • 每轮真正送给模型的 Context 仍要结合最新 history、Memory、文件和 Tool Result 组装，不应在 Run 创建时冻结成一长段字符串。

这个区分让 RunSpec 保持可序列化和可解释，同时避免它变成“所有东西的 JSON”。

把开场例子走一遍

后台研究请求到达后，流程不再让 Loop 判断 mode：

1. Compiler 读取 research Profile revision 12。
2. 根据当前授权，把 Tool Surface 收窄为四个 Tool。
3. 解析模型和预算，生成 RunSpec version 3。
4. 持久化不可变 RunSpec 和 fingerprint，再追加引用它们的 `run.created(run_id, runspec_ref, fingerprint)` 事实。
5. Runtime 按 RunSpec 启动 Loop，并记录实际发生的 model/tool event。

如果用户没有文件写权限，第 2 步就会排除 write_file。Runtime 不需要在每次 Tool Call 时重新理解“research 用户能否写文件”；可信的 Tool handler 仍会做后端鉴权，也可以因授权撤销进一步拒绝动作，但不能让同一 RunSpec 获得编译时上限之外的新能力。

RunSpec 与 Event Log 位于同一数据库时，RunSpec 持久化和 run.created append 可以共享 transaction。跨存储时，应先保存不可变 RunSpec，再 append 引用；append 最终失败留下的 orphan RunSpec 由 retention / reconciliation 清理。RunSpec 是被执行事实引用的契约，不是 Run snapshot 的 projection。

如果 Profile 在 Run 执行到一半时升级到 revision 13，当前 Run 仍使用 revision 12。新策略只影响之后创建的 Run。这样一次恢复不会因为重新读取 Profile 而突然换模型或增加 Tool。

为什么需要 version 与 fingerprint

只保存 profile_id=research 仍不够，因为这个 Profile 会变化。RunSpec 至少需要保留自身 schema version、依赖对象的 revision，以及基于规范化内容计算的 fingerprint。

它们分别解决不同问题：

  • spec_version 告诉恢复代码怎样读取这份结构。
  • Profile、Tool Surface、prompt 等 revision 说明输入来自哪个版本。
  • Fingerprint 用于判断两次执行是否真的使用了同一份契约，而不是只碰巧使用了同一个名字。

Fingerprint 可以理解为 RunSpec 内容的“短指纹”。但 SHA-256 只接收 bytes，并不知道 JSON 里的 object key、空白或数字应该怎样表示；因此系统必须先定义 canonicalization，也就是“同一份逻辑内容怎样稳定变成同一串 bytes”。

例如，可以先按业务语义排除 created_at 等运行时字段、把没有顺序语义的 Tool 集合排序，再使用 RFC 8785 JSON Canonicalization Scheme 生成 UTF-8 bytes。下面是两条完整 test vector；hash 输入就是代码块中每行 JSON 的 UTF-8 bytes，不包含换行：

{"canonicalization":"jcs-v1","model":"reasoning-model","profile":{"id":"research","revision":12},"tool_surface":{"allowed":["read_file","search"],"revision":27}}
sha256 = 374c31f96298b5fe5522161fb193f902efb1cee09fcf76dd2a45c11ac97de0b1
{"canonicalization":"jcs-v1","model":"reasoning-model","profile":{"id":"research","revision":12},"tool_surface":{"allowed":["read_file","search","write_file"],"revision":28}}
sha256 = eb98321387bd356c133bbb08dfe58262608b8e304a2a5604a7e22f795a23fb44

两个 Run 都叫 research，但第二条多了 write_file，因此 fingerprint 不同。Trace 或 Eval 看到差异后，就知道这两次执行不能只按同一个 Profile 名称直接比较。反过来，如果规范化内容相同，fingerprint 也应相同，不必逐字段比较整份 RunSpec。

canonicalization 本身也是契约的一部分：实现必须固定字段包含规则、业务集合的排序方式和 JCS 版本，并保存相应 test vector。只写一句“先把 JSON 排序”仍可能让不同语言产生不同 bytes。

Fingerprint 不等于安全签名，因为任何能修改 RunSpec 的人都可以重新计算一个匹配的新 hash。它适合发现配置漂移和快速比较内容，不能单独证明是谁生成了这份 RunSpec。

即使 fingerprint 相同，也不能证明外部 Provider 行为完全相同。它只能让 Trace、恢复和 Eval 回答：“这两次执行的本地契约是否一致？”

Runtime 仍然需要执行时判断

把 policy 编译到 RunSpec，不代表 Runtime 里不能有任何分支。与执行事实有关的判断仍属于 mechanism：

  • Tool Call 是否符合 schema。
  • Deadline 是否已经到达。
  • 取消是否已经被请求。
  • 本次失败是否满足 RunSpec 允许的 retry 条件。
  • 当前授权引用是否已被撤销，后端是否仍允许产生副作用。

区别在于 Runtime 根据显式契约和当前事实做判断，不再自行推导产品身份、套餐或入口类型。Policy compiler 决定 retry budget 是多少；Runtime 负责正确消耗它。

回到问题

Agent Loop 不应该随着入口、用户等级和实验策略一起膨胀。更稳定的分工是：Profile 表达可变 policy，compiler 在执行前把选择结果固化为 RunSpec，Runtime 只解释这份契约并记录执行事实。

这样，新增一种场景通常意味着新增或修改 Profile 与 compiler rule，而不是在模型和 Tool 循环里再加一条业务分支。更重要的是，一次 Run 从创建、恢复到 Eval 都能指向同一份执行契约。

后续问题

  • RunSpec 创建后，Runtime 产生的消息、状态和事件应以什么作为事实源。
  • 每个 Model Turn 如何从 history、Memory、files 与 Tool results 组装最新 Context。
  • Profile、compiler 与 Runtime 是否需要拆成不同服务，应由哪些故障和所有权边界决定。
  • RunSpec 跨越信任域时，怎样使用 HMAC 或数字签名证明来源与完整性。
