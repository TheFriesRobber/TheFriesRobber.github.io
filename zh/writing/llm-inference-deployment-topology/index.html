LLM Infra 09：推理部署拓扑怎样由瓶颈反推

将模型放不下、单请求延迟、聚合吞吐和 Prefill/Decode 资源不对称分开，再选择 Replica、Tensor/Pipeline Parallel、Context Parallel 或 P/D 分离。

问题

同样是“给一个模型分配多张 GPU”，可以得到完全不同的结果：

  • Tensor Parallel 让模型装下了，总吞吐却没有按 GPU 数增长；
  • 多 Replica 提高了聚合吞吐，却仍处理不了单请求的超长 Context；
  • Prefill/Decode 分离缓解了阶段干扰，又新增了 KV 传输和跨池调度。

这些结果没有互相矛盾。Replica、模型切分和阶段分离解决的是不同约束。部署拓扑必须从瓶颈反推，不能从“现在有几张卡”正向拼装。

先把约束分成四类

Model fit

权重、KV、Activation 和 Runtime headroom 无法放进单 GPU。问题是单个可执行副本放不下，复制更多副本没有帮助。

Single-request latency

模型能放下，但单个请求的 TTFT 或 TPOT 不达标。增加并行 degree 可能缩短部分计算，也会引入 collective 和更小 Kernel，结果必须实测。

Aggregate goodput

单 Replica 已满足请求 SLO，但总到达率超过它的 service curve。此时复制独立 Replica 通常是最直接的候选。

Phase asymmetry

Prefill 与 Decode 的资源偏好、SLO 或到达形态明显不对称。把它们绑在同一个 Replica 可能无法独立配比，但分离会引入 KV transfer 与两个调度阶段。

只有先定位约束，才知道应该比较哪些候选拓扑。

Replica 复制解决 fleet throughput

对 dense model 的常见 Data Parallel serving，系统会复制完整 model weights，每个 Replica 处理独立请求并拥有自己的 KV Cache。vLLM 的 Data Parallel deployment 也支持这种结构，并允许 DP 与 TP 组合。MoE 是重要例外：DP 与 Expert/Tensor Parallel 的组合可能要求 rank 对齐 forward 并在 expert layer 同步，因此 failure group 和执行边界可能跨多个 rank。

Replica 的优势是故障与调度边界较直观：

request
→ choose one compatible Replica
→ that Replica owns the sequence execution

但它有前提：

  • 单个 Replica 已能装下模型和目标 Context；
  • 每个副本有足够独立 batching opportunity；
  • Router、gateway 与共享存储不会成为新瓶颈；
  • workload 能在副本之间合理分配，不被 adapter 或 KV affinity 固定。

所以 fleet capacity 不能默认等于 Replica 数 × 单 Replica 峰值。需要用真实路由和 workload 再测 fleet service curve。

TP、PP 与 Context 方向切分解决不同的 fit

**Tensor Parallel（TP）**在单层内部切分矩阵或 Tensor。典型 Transformer partition 会在 block 内产生 collective communication；具体次数和位置由实现决定。TP 可以降低每卡权重占用，并可能缩短部分算子，但通信和 Kernel 变小会造成收益递减。

**Pipeline Parallel（PP）**按 layer/stage 切分模型。单个 autoregressive sequence 仍要按 stage 依赖向前推进；只有足够的并发或 microbatch 填充 pipeline，bubble 才能被摊薄。因此 PP 首先是 model placement 手段，不是默认的单请求低延迟方案。

Context/sequence 方向切分把长 sequence 的状态或 attention 计算分散到多个 rank。它是否可用、KV 怎样分片，取决于模型架构与 Runtime，不能从“长 Context”直接推导出某个固定方案。

一个规则 dense deployment 常被概念化为：

fleet GPUs ≈ DP × TP × PP

这只适用于规则拓扑。Context Parallel、Expert Parallel、异构设备或共享 worker 都会改变关系。

Prefill/Decode 分离解决阶段配比

DistServe 和 Splitwise 都把 Prefill 与 Decode 放到不同资源池，使两阶段可以独立选择并行与扩容策略。vLLM 也提供 experimental 的 disaggregated prefill；当前官方文档将其用途限定为分别调节 TTFT 与 ITL、控制 tail ITL，并明确说明该实现不提升 throughput。其他系统也必须按各自版本与 workload 实测，不能把论文结果迁移成 Runtime 保证。

P/D 分离不是“再加一层 Router”。它新增了：

request
→ Prefill placement and execution
→ KV state transfer
→ Decode placement and streaming

因此决策必须包含：

  • KV transfer 的格式、带宽与失败语义；
  • Prefill 与 Decode deployment revision 是否兼容；
  • 两个队列怎样共同满足 TTFT/TPOT；
  • 一个阶段成功、另一个阶段失败时谁拥有 outcome；
  • 跨节点 placement 是否让传输抵消独立扩容收益。

只有当阶段不对称带来的收益大于传输与控制面成本，P/D 分离才是合理候选。论文里的性能数字只对其测试模型、硬件和网络成立，不能成为通用阈值。

回到问题

TP 没让总吞吐按卡数增长，是因为它首先解决单副本 fit，并在关键路径增加通信；Replica 处理不了超长 Context，是因为复制没有改变单副本状态上限；P/D 分离新增 KV transfer，则是阶段独立扩展必须支付的成本。

部署拓扑的正确顺序是：先确定 model fit、single-request latency、aggregate goodput 或 phase asymmetry 哪个约束生效，再为该约束建立候选，最后用同一 workload 与 SLO 测量 service curve。
