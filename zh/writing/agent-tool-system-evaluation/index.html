Agent 37：Tool System 评测要诊断哪一层失败

分层评测 Tool selection、参数、repair、mutation precision 与 task success，避免最终回答掩盖执行错误。

2026/07/24 更新于 2026/07/27 阅读 次
Agent VerificationAgentEvaluationTools

问题

下面用一个构造 case。它要求 Agent 把客户 customer_42 的地址改为新值。最终回答是“地址已更新”，文本看起来完全正确；但 trace 显示：

模型选择：bulk_update_customers
参数：filter = "status:active"
第一次调用：schema validation failed
修复后调用：执行成功
外部结果：customer_42 与另外两条记录都被修改

如果 Eval 只检查最终回答里是否出现新地址，这个 case 会通过。Handler 单测也可能全绿，因为它确实按参数执行了批量更新。真正失败的是 Tool selection、mutation scope 和成功声明的证据。

Tool System Eval 必须沿 lifecycle 记录每一层结果；否则一个最终 task score 会把模型、schema、Runtime 和外部副作用的故障混在一起。

先固定被评测的 Tool Lifecycle

一条 Tool 执行可以拆成：

eligible case
  → candidate Tool surface
  → model proposal
  → trusted argument validation
  → optional repair episode
  → authorized Tool Execution
  → provider Attempt
  → normalized Tool Result
  → external effect evidence
  → Task outcome

每层都有不同 owner：

  • Tool surface 决定模型当时能看到哪些能力；
  • 模型提出 Tool 和 arguments；
  • Runtime 负责可信 validation、authorization 和 repair policy；
  • handler/provider 执行物理 Attempt；
  • 外部资源 owner 决定副作用是否真正提交；
  • Task owner 根据 evidence 判断用户目标是否完成。

Eval 记录需要保留 case、operation、Tool Execution 与 Attempt 的 identity。validation error 后的参数修复发生在授权执行之前，因此记为 repair episode/round，不叫 Attempt；最终获准 proposal 才创建 Tool Execution，物理重试则必须创建新的 Attempt。

Selection 指标必须先定义 Eligible Population

“Tool selection accuracy”至少包含两个不同问题。

Selection recall 关心需要调用某 Tool 的 case 是否真的选到了它：

正确选择目标 Tool 的 eligible cases
/ contract 明确要求该 Tool 的 eligible cases

Selection precision 关心提出的 Tool 调用是否必要且正确：

必要且 Tool 正确的 model proposals
/ 全部 model Tool proposals

一个纯问答 case 不需要 Tool，就不该进入目标 Tool 的 recall denominator；但 Agent 若在这个 case 无故调用写入 Tool，该 proposal 应进入 precision 或 restraint 指标。

多种 Tool 都能合法完成目标时，case contract 应声明允许集合或行为约束，而不是把唯一参考轨迹当成唯一正确路径。例如 update_customer 和带严格单条 filter 的 bulk_update_customers 都可能合法；真正必须守住的是授权和 mutation scope。

Argument Validity 与 Repair 是两个结果

模型提出的 arguments 需要分层判断：

层级示例证据
Schema validity字段类型、必填项、枚举trusted validator
Semantic validity日期范围、revision、资源关系domain rule
Authorization validity是否允许修改目标资源policy decision
Execution validityprovider 是否接受并执行normalized result

Parameter validity 的分母应是模型提出的 Tool proposals，而不是只统计最终进入 handler 的调用。否则所有 validation failure 都被过滤掉，指标会虚高。

Repair success 则只在“错误可修复、Runtime 实际给了修复机会”的 proposal 上计算：

修复后通过目标 validation 的 repair episodes
/ 全部 eligible repair episodes

还要保留 repair episode 数、错误类型和最终是否改变原意。把错误参数改成合法参数不等于任务成功；模型可能为了通过 schema，扩大 filter 或选择了错误资源。

Execution Outcome 不能替代 Effect Evidence

Handler 返回 ok，只能证明 handler 对这次调用给出了成功结果。对于外部写入，Task success 还需要来自 effect owner 的证据，例如：

  • committed revision；
  • immutable event；
  • provider operation ID 与查询结果；
  • mutation diff；
  • Artifact identity 和 checksum。

timeout 也不能自动记成外部失败。若请求可能已经提交，应记录 outcome=unknown，凭 operation key 查询后再决定是否 retry。盲目重试非幂等写入，可能把一次不确定结果扩大成重复副作用。

因此，Tool Eval 至少要区分：

Attempt outcome
Logical Tool Execution outcome
External effect outcome
Task outcome

这四层可以在同一个 case 中给出不同答案。

Mutation Precision 直接验证“只改了应该改的”

对有副作用 Tool，最终文本不能证明 mutation scope。Case 应定义允许变化集合：

before:
  customer_42.address_revision: 7
allowed_mutations:
  - customer_42 # 一次结构化 address + revision 更新，按 record 计
forbidden_mutations:
  - other_customer.*

这里选择 record-level grain：一次对同一 customer 的结构化 address + revision 更新算一条 mutation。一个可解释的记录可以同时报告：

expected mutations observed / expected mutations
allowed actual mutations / all actual mutations
forbidden mutations count

如果实际有三条记录被修改，其中只有 customer_42 在允许范围内，那么“允许 mutation / 全部 actual mutation”的构造结果是 1/3；但这不应被平均分稀释，forbidden mutations count=2 可以直接触发 hard failure。

没有实际 mutation 的 read-only case 不进入 mutation precision denominator。它应改测读取范围、来源正确性和是否产生任何禁止副作用。

Case 集合要覆盖不同 Effect 语义

只测 happy path 无法证明 Tool System 在恢复路径上安全。至少要区分：

Case 类型主要验证
Read-only是否选对来源、参数范围和返回证据
Idempotent writeoperation key、重复 Attempt 与最终 revision
Non-idempotent writetimeout 后禁止盲重试、unknown outcome
Repairable arguments错误 envelope 能否驱动正确修复
Concurrent mutationexpected revision、conflict 与禁止覆盖
Unauthorized actionselection restraint、authorization hard failure

这些 case 不要求每种 Tool 使用同一指标。重点是让 Tool contract 声明的副作用和恢复语义都获得对应证据。

从一条 Trace 生成分层评分记录

回到开场构造例子，可以生成：

case_id: update_single_customer
selection:
  eligible_target_tools: [update_customer]
  proposed_tool: bulk_update_customers
  verdict: fail
arguments:
  proposals: 2
  schema_valid: 1
  semantic_scope_valid: 0
repair:
  eligible_episodes: 1
  schema_repaired: 1
  intent_preserved: 0
execution:
  tool_executions: 1
  final_outcome: succeeded
effects:
  expected_mutations: 1
  actual_mutations: 3
  allowed_actual_mutations: 1
  forbidden_mutations: 2
task_outcome: fail

这份记录没有给出一个装饰性的总分。它说明 handler 完成了调用，schema repair 也成功了，但模型选错能力、修复扩大了作用域，最终产生两个禁止 mutation，所以 Task 必须失败。

若产品还需要总体 dashboard，可以按层聚合，但每个 rate 都要保留 eligible population：

指标分母
Selection recallcontract 要求目标 Tool 的 cases
Selection precision全部 model Tool proposals
Parameter validity全部提出的 Tool proposals
Repair success全部 eligible repair episodes
Tool Execution success全部 terminal Tool Executions
Attempt success全部 terminal provider Attempts
Mutation precision全部实际 mutations
Task success全部有效 cases

不同分母的值不能相加成一个“Tool accuracy”。

Contract Test、Model Eval 与线上证据各守一层

Schema contract test 可以发现字段和 adapter drift；handler test 可以覆盖 success、error、cancel 和 effect contract；surface integration test 可以确认 discovery、binding 与 hook；model eval 才能观察 selection 和 repair；生产 observability 则暴露真实分布和未知副作用。

这不是五套重复测试。每层控制的变量和能定位的 failure 不同。Tool rename 可能不影响 handler 单测，却改变模型 routing；模型选对 Tool，也可能被 adapter 错误转换参数；所有离线测试通过，生产 provider 仍可能产生 timeout 和 unknown outcome。

因此，发布判断需要组合这些证据，而不是要求某一层替其他层证明它看不到的事实。

回到问题

开场中的 Agent 最终文本正确、handler 也成功返回，却仍然是失败案例：它选择了错误 Tool，修复后的参数扩大了作用域，并修改了两个不应变化的资源。

把 lifecycle 拆成 selection、arguments、repair、execution、effect 和 Task outcome，再为每层声明 case、logical operation、Tool Execution、Attempt 或 mutation denominator，才能定位故障。对于真实副作用，最终声明必须由 effect evidence 或 backend assertion 支持。

Tool System Eval 的目标不是产出一个更漂亮的总分，而是让“模型选错、参数错误、恢复错误、执行未知、越界 mutation”不再被同一句“任务已完成”掩盖。
