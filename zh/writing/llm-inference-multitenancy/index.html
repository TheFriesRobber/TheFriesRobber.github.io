LLM Infra 16：Tenant identity 怎样贯穿推理资源链

让受信任 Tenant identity 贯穿 Queue、Model/Adapter、Prefix Cache、execution、log 与 usage fact，并明确逻辑隔离和硬件隔离的边界。

2026/07/29 阅读 次
LLM InfraInferenceMulti-TenancySecurityCost

问题

Tenant A 的长请求占用大量 KV blocks，Tenant B 的低延迟请求持续排队；两者使用相同文本前缀，Cache 层又只按 Token hash 复用；usage 最后只按 gateway request 数归属。

公平性、Cache 隔离和资源归属看似是三个问题，真正缺失的是同一条受信任 Tenant identity。它在入口鉴权后没有继续进入 queue、adapter、Cache、execution 与 usage。

Tenant identity 不能由客户端自报

平台需要从已认证 subject 和服务端 policy 解析 isolation context：

isolation_context:
  subject_id: subject_123
  tenant_id: tenant_a
  trust_domain: tenant_a-prod
  cache_salt_id: salt_91
  quota_class: interactive-standard
  adapter_scope: tenant_a
  log_scope: tenant_a
  issued_by: trusted-gateway
  immutable: true

请求 header 可以携带 context reference，但不能允许客户端覆盖 tenant_id、salt 或 quota class。每个 retry attempt 都必须携带受信任、仍有效且不可篡改的 principal context，并重新经过 admission；跨越认证边界，或 authorization grant 已过期、撤销时，必须重新认证或授权，不能信任客户端自报字段，也不能继承已经失效的扣减结果。

Tenant identity 与用户 subject 也不能混用：subject 表示调用者，tenant 表示资源与隔离归属，一个 tenant 可以有多个 subjects。

Identity 必须进入每一个共享边界

trusted gateway
→ admission / queue
→ model and adapter resolution
→ Prefix Cache namespace
→ Replica execution
→ logs / traces / artifacts
→ usage facts

每个边界使用 identity 的目的不同：

边界Identity 参与的决策
Queuequota、priority、weighted fairness
Model/Adapter可见范围、允许的 revision
Prefix Cachetrust domain 与 cache salt
Executionattribution、cancellation、isolation placement
Logs/Trace查询与内容访问范围
Usageattempt 与资源事实归属

第 07 篇说明 cache_salt 可以隔离 Prefix Cache sharing domain。它只是降低跨域 Cache reuse 与 timing exposure 的一个机制，不是完整授权，也不能替代进程、网络、日志和硬件隔离。

Fairness 与 Quota 必须使用同一 Work unit

按 request count 限流会让一个超长 Context 请求与一个短请求成本相同。更合理的 admission 可以同时使用：

  • requested prompt / max output Token；
  • active sequence 与 KV reservation；
  • deadline / priority；
  • tenant burst allowance；
  • 已接纳但未完成的 work。

这仍然是估算，实际 usage 要等 Runtime 执行后记录。Fairness policy 与 usage fact 分开：

  • Policy 决定现在允许多少工作进入。
  • Runtime fact 记录实际产生多少 Token、execution time 与 outcome。

如果二者使用不同 tenant identity，系统会出现入口扣 A、Runtime 记 B、最终账单再平均分摊的断链。

隔离强度是一条谱系

Kubernetes 官方多租户文档把 namespace、RBAC、NetworkPolicy 和 quota 视为逻辑与 control-plane 隔离手段；它们不自动提供物理 GPU 隔离。

NVIDIA MIG 把部分 GPU compute、cache 和 memory path 切成独立实例，提供更强的资源与故障隔离。MPS 或 time-slicing 则仍共享更多底层资源。即使使用 MIG，也不能据此宣称消除了所有 side channel、Runtime bug 或应用层数据泄漏。

因此，placement policy 必须按数据与风险选择：

隔离需求可能方案仍需处理
同 trust domain 的效率共享同进程/同 GPU Cache sharingquota、日志、Cache salt
隔离应用与 Runtime state独立进程或逻辑专用 Replica若仍共享 GPU，不承诺 SM、L2 或显存带宽 QoS
划分单卡资源与 QoS受支持硬件/profile 上的 MIGhost、network、control plane、应用缺陷
强硬件/组织隔离专用 GPU/节点/集群身份传播、日志与供应链仍存在

“共享 GPU”不是单一安全等级，namespace 也不是硬件隔离证明。

Usage fact 不是 Billing decision

usage_evidence:
  usage_id: usage_771
  logical_request_id: req_123
  attempt_id: att_2
  tenant_id: tenant_a
  release_digest: release_91a
  execution_fact:
    producer: runtime-signed-event
    input_tokens: 2400
    output_tokens_generated: 91
    cache_read_tokens: 512
    execution_started_at: ...
    execution_ended_at: ...
    replica_uid: replica_a
    outcome: cancelled_after_start
  delivery_fact:
    producer: gateway-signed-event
    chunks_emitted: 6
    emitted_token_cursor: 47
    client_ack_protocol: none
    acknowledged_cursor: null

这个 bundle 把 Runtime execution 与 Gateway delivery evidence 按 producer 分开；没有显式 application ACK 时，它不声称 Client 已收到或消费 Token。它也不决定价格。GPU 时间如何在 Batch 内分摊、Cache hit 是否计价、失败是否退款，属于 Billing policy；Policy 可以演进，但不能改写原始 usage evidence。

Gateway Token count 也不等于 GPU 占用。Prefix Cache、quantization、Batching、preemption 和并行拓扑都会改变资源成本。成本归属模型可以消费这些 facts，但必须披露假设。

用负向测试验证身份没有中途丢失

至少应验证：

  1. 客户端伪造 tenant_id header 不会覆盖 trusted context。
  2. 不同 cache salt 的相同前缀不会互相命中。
  3. Tenant A 的 Adapter 对 B 不可路由。
  4. Queue policy 对长 Token work 执行 quota，而非只数 request。
  5. 日志与 trace 查询受 tenant scope 约束。
  6. Retry 产生新 attempt，并重新 admission 与记录 usage。
  7. Billing adjustment 不修改任何原始 usage evidence；调整以独立 ledger/event 追加。

这些测试比“所有组件都有 tenant 字段”更强，因为它们检查了跨边界的实际 enforcement。

回到问题

Tenant A 挤压 B、跨租户 Prefix Cache 命中、usage 归属错误，并不需要一个同时负责安全、调度和计价的超级组件。它们需要同一条不可伪造的 Tenant identity 贯穿每个 owner。

Queue 用它实施 fairness，Cache 用它划分 trust domain，Adapter 与日志用它限制可见性，Runtime 用它产生 usage facts。隔离强度则由共享进程、MIG、专用设备或集群等 placement 明确表达，不能由一个 namespace 名称推断。
