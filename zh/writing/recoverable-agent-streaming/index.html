Agent Runtime 七：实时输出不是执行记录

2026/07/15 阅读 次
AgentRuntimeStreaming

问题

用户让 Agent 生成一份报告。浏览器先后看到模型输出和 Tool 进度，就在文件写入完成后断网了。连接恢复时，页面仍停在“正在生成”：

Runtime     file.created(seq=27) → run.completed(seq=28)
Browser     最后看到 seq=26，然后断线

这里的“实时输出”不只是模型逐字生成的 token，还包括 Tool 调用进度、Run 状态变化和最终结果如何持续到达客户端。

SSE 通常会自动重连，WebSocket 也可以由应用重新建立连接。为什么这两件事仍不能保证用户看到 27 和 28？

因为“连接重新建立”只说明现在又能接收数据，不说明断线期间的数据被保存过。Streaming transport 解决实时传输，执行恢复需要另一个事实来源。

重连不等于重放

SSE 的 Last-Event-ID 允许浏览器在重新连接时把 EventSource 最近 dispatch 的 event ID 交给服务器。但它是 transport cursor，不证明应用已经把事件成功写入 UI 或本地状态。协议也不会替服务器保存历史，更不会规定服务端必须从哪里重放缺失事件。

WebSocket 提供双向连接，同样没有内建的持久 event log。若服务端只是把内存中的 token 和状态变化直接写入 socket，连接关闭后，那段数据就没有第二个读取入口。

Redis Pub/Sub 也不改变这个结论。Redis 官方把 Pub/Sub 描述为 at-most-once：订阅者断线或处理失败时，已经发布的消息不会再次发送。它适合低延迟 fanout，不适合独自承担恢复。

所以需要先把两类数据分开：

类型作用丢失后怎么办
Durable Event证明执行中已经提交了什么事实从稳定 cursor 继续读取
Lossy Signal提醒在线消费者“有新事实可读”可以丢；消费者重新查事实源

一个 signal 可以携带完整 event 以减少一次读取，但接收者仍不能因为收到它，就假设该 transport 是事实源。

一条可靠的读取路径

Runtime 提交事件时，顺序应该是：

1. append durable event，获得稳定 seq
2. commit
3. publish signal(session_id, high_watermark=seq)

这里的 high_watermark 是同一 Event Log 中当前已经提交的最大 Session sequence，不是 gateway 最后观察到的 signal，也不是某条连接的本地进度。只有来自事实源的 watermark，才能告诉客户端最多可以补到哪里。

不要先发 signal 再写 event。否则客户端被唤醒时还读不到对应事实，随后若 signal 丢失，也不知道要再次查询。

客户端首次打开页面或重新连接时，应使用一个明确的 application cursor。它只在事件按序、幂等应用成功后推进；若 cursor 无法与本地状态原子保存，客户端宁可从更早位置重放，也不能因为事件已经 dispatch 就跳过它。

GET /sessions/session_17/events?after=26
→ seq 27 file.created
→ seq 28 run.completed
→ next_cursor=28

追赶到当前 high watermark 后，客户端继续接收实时 signal。每次收到 signal，都从自己的 applied cursor 之后读取，而不是盲目信任 signal payload。重复 signal 可能触发冗余空读取，但不会改变已经应用的状态；需要减少读取时，gateway 或客户端可以合并相同或更小的 watermark。漏掉 signal 则可以通过重连、周期 reconciliation 或之后更大的 watermark 补齐。

补历史与订阅之间也有 race

一个容易遗漏的窗口是：客户端先查到 seq 28，尚未开始订阅时，seq 29 已经产生；如果 seq 29 的 signal 也发生在订阅前，客户端仍会漏掉它。

有几种可行解法：

  • 先建立订阅，再读取一次 durable log，之后用 cursor 去重。
  • 建立订阅时由服务端在订阅已经生效的同一 handshake 中返回 watermark，再读取到该 watermark。
  • 把 signal 只当唤醒提示，并保留低频 reconciliation。

它们的共同点不是某个固定 API，而是：正确性来自按 cursor 读取事实源，订阅只缩短发现新事件的时间。

回到开场例子，浏览器即使错过 seq 27 和 28 的全部实时通知，也能在重连后从 cursor 26 补齐。页面是否恢复，不再依赖断线发生在哪一毫秒。

这项补齐保证只在 Event Log 的 retention window 内成立。如果客户端的 cursor 早于最旧保留 sequence，服务端应明确返回 cursor_expired 或 gap，而不是悄悄从一个更晚位置继续。客户端随后从 current snapshot 或完整 Message projection 重建页面；这份响应必须携带自身对应的 as_of_seq，客户端再从 seq > as_of_seq 追赶。不能在读取 snapshot 之后另取一个更晚的 high watermark 作为新 cursor，否则两次读取之间产生的事件会被永久跳过。

Token streaming 与执行事件不是同一种粒度

模型 token 的数量可能很大，而且许多中间 token 不值得长期保存。可以把它们视为 lossy delta，同时定期提交较粗粒度的 durable event：

assistant.output.started
assistant.output.delta      # 可丢的实时片段
assistant.message.completed # 持久化的最终消息

如果产品要求断线后逐字恢复，就需要把 delta 分块持久化，并承担更高的存储与重放成本。否则，更常见的边界是恢复到最后一条完整消息或 Tool event，而不是重建每一个曾显示过的 token。

这是一项产品语义选择，不能由“我们用了 SSE”自动决定。

慢消费者需要有界缓冲

Durable log 解决丢失，不代表实时链路可以无限堆积。假设模型快速产生 delta，而移动端网络只能慢速读取；无界 Queue 会把背压转化成不断增长的内存。

实时层需要明确：

  • 每个连接最多缓存多少条或多少字节。
  • 哪些 delta 可以合并或丢弃。
  • 落后到什么程度后主动断开，让客户端走 cursor 恢复。
  • Terminal、approval request 等关键事件是否必须先落 durable log。

有界 Queue 满时，不应阻塞整个 Agent Runtime 等一个慢浏览器。如果事件已经持久化，可以断开这个订阅者；如果只是可丢 delta，可以合并或丢弃并明确 UI 降级。

Cancellation 也不能只依赖连接

浏览器关闭 WebSocket，不一定表示用户取消 Run；它也可能只是网络切换。反过来，用户点击 Stop 后 socket 恰好断开，也不能让取消意图消失。

因此取消应该经过独立、可确认的 control path，写入 durable state，再通知执行者。Transport disconnect 最多触发资源清理或短暂 grace period，不能直接被解释成业务取消。

同样，Runtime 向 Provider 传播取消，也只能说明本地已请求停止。Provider 或 Tool 是否已经产生输出或副作用，仍要依据各自协议确认。

回到问题

SSE、WebSocket 和 Redis Pub/Sub 都能让在线用户更快看到变化，但连接重建不等于历史重放。

Agent Streaming 的恢复模型应该是：Runtime 先提交带稳定 sequence 的 Durable Event，再发送允许丢失的实时 signal；客户端维护 applied cursor，在 retention window 内增量补齐，cursor 过期时从完整视图重建。这样实时链路可以追求低延迟，事实链路可以独立承担恢复，两者不再互相假装。
