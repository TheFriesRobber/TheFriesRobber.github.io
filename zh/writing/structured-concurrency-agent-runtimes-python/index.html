Agent Runtime 十三：用 Structured Concurrency 收拢并发任务

2026/07/15
AgentRuntimePythonAsyncio

问题

Python Agent Runtime 已经完成三个 Tool Call 的 admission，并创建了三个可以并行推进的 Tool Execution。最直接的写法是：

async def start_tools(executions):
    for execution in executions:
        asyncio.create_task(execute_tool_execution(execution))

    return "started"

这段代码确实让三个 coroutine 同时运行，却在创建 Task 后立刻返回。接下来几个问题没有 owner：

  • 父 Run 什么时候可以进入完成状态？
  • 一个 Tool Execution 失败后，谁读取它的异常？
  • 用户取消 Run 时，谁负责停止剩余 Tool Execution？
  • 进程 shutdown 前，哪些工作必须等待？

Structured Concurrency 解决的不是“怎样更快创建 Task”，而是 ownership：一组并发工作必须属于一个明确的生命周期；父级负责等待子级结束，并接收它们的失败。

本文基于 Python 3.11 及以上版本提供的 asyncio.TaskGroup。除非明确写作应用层 Task，本文后续的 Task 都专指 Python asyncio.Task；移交 Queue 或 workflow 的请求外工作则称为 Job。

create_task() 没有错，丢掉 Task 才是问题

asyncio.create_task() 返回一个 Task。调用方如果保存它，就可以等待结果、读取异常或请求取消；如果直接丢弃 reference，代码也同时丢掉了管理这项工作的入口。

Python 官方文档明确建议保存 create_task() 返回的 reference。Event loop 只持有 Task 的 weak reference，没有其他强引用的 Task 甚至可能在执行完成前被垃圾回收。

即使 Task 正常存活，上一段代码仍然存在更根本的问题：start_tools() 的函数生命周期与它启动的工作脱离了。函数已经返回，Tool Execution 却可能仍在修改外部状态。

这会产生两个互相冲突的事实：父 Run 认为这个阶段结束了，子 Task 仍认为自己可以继续执行。

TaskGroup 把并发工作放回父级 Scope

asyncio.TaskGroup 是一个 async context manager。离开 async with 之前，它会等待组内 Task 全部结束：

import asyncio


async def execute_tools(executions):
    tasks = {}

    async with asyncio.TaskGroup() as group:
        for execution in executions:
            tasks[execution.id] = group.create_task(
                execute_tool_execution(execution),
                name=f"tool:{execution.id}",
            )

    return {
        execution_id: task.result()
        for execution_id, task in tasks.items()
    }

现在 execute_tools() 只有两种清晰结果：要么所有子 Task 已经收敛，可以返回结果；要么组内出现未处理失败，异常向父级传播。它不会在子 Task 仍运行时假装阶段已经完成。

默认情况下，一个子 Task 抛出 CancelledError 之外的未处理异常后，TaskGroup 会请求取消其余 Task，并等待它们结束。普通失败会按类型合并成 ExceptionGroup 或 BaseExceptionGroup；KeyboardInterrupt 和 SystemExit 则会在其他 Task 收敛后重新抛出。

这不代表所有 Tool Execution failure 都应该让整组 fail-fast。参数无效、资源不存在等预期业务失败，可以在 execute_tool_execution() 内转换为 typed result，让其他独立 Tool Execution 继续执行；Runtime bug 或未分类异常则继续抛出，让父级知道当前阶段没有可靠完成。

Structured Concurrency 提供清楚的失败传播，但是否允许部分成功仍然是业务 policy。

Cancellation 需要子级配合收敛

TaskGroup 的失败处理依赖 cancellation。Python 中调用 task.cancel() 是发出取消请求，CancelledError 会在 coroutine 下一次获得执行机会时抛出；它不是强制立即终止。

子任务需要在 finally 中释放资源，并在捕获 CancelledError 做完必要清理后继续传播：

async def write_artifact(stream, sink):
    try:
        async for chunk in stream:
            await sink.write(chunk)
    except asyncio.CancelledError:
        await sink.mark_interrupted()
        raise
    finally:
        await stream.aclose()

如果代码吞掉 CancelledError，父 TaskGroup 可能一直等不到子级按预期收敛。反过来，即使本地 Task 已经取消，也不能直接推断远端副作用已经撤销：HTTP 请求可能已经提交写入，subprocess 也可能已经修改文件。

所以 Structured Concurrency 能保证本地 Task lifecycle 有 owner，却不能代替 Tool Runtime 对外部结果进行确认。

真正的后台 Job 不能只靠裸 Task

有些 Job 本来就需要在请求返回后继续，例如一个可能运行几分钟的报告生成 Job。这不意味着 fire-and-forget 的内存 Task 就变得安全。

请求结束后仍需执行的工作，应该先获得 durable Job identity 和可恢复状态，再交给 Queue 或 Workflow worker。这样，新 owner 是后台 worker，而不是已经消失的 HTTP request scope。

请求内并发：TaskGroup 拥有并等待子 Task
请求外 Job：Queue / Workflow 拥有 durable Job
无 owner Task：生命周期没有明确归属

区分标准不是工作运行多久，而是谁负责在进程重启、取消和失败后继续解释它的状态。

TaskGroup 不解决资源上限

TaskGroup 回答“谁拥有这些 Task”，不回答“一次可以运行多少 Task”。如果同时向下游发出一万个请求，它们即使都在同一个 group 中，也可能压垮 connection pool 或 provider limit。

Semaphore、bounded Queue 和 admission control 负责限制并发与传递 backpressure；deadline 负责限制整个阶段能够消耗的时间。它们与 ownership 互补，但不是 Structured Concurrency 本身。

同样，两个 Tool Execution 并行修改同一资源仍需 OCC、transaction 或按 key serialization。TaskGroup 只管理 Python Task 的生命周期，不保证业务状态一致性。

问题不在 create_task()，而在 ownership

create_task() 本身不是反模式。如果调用方：

  • 保存 Task reference。
  • 明确谁等待结果或处理异常。
  • 在父级取消和 shutdown 时收敛 Task。
  • 不在子 Task 尚未结束时把父阶段标成完成。

那么它仍然是合适的底层 API。TaskGroup 的价值，是让一组共同完成某个阶段的 Task 默认拥有同一个结构化 scope，减少遗漏这些责任的机会。

回到问题

并发 Tool Execution 的首要问题不是怎样把循环改成 create_task()，而是创建之后谁对这些 asyncio.Task 负责。

TaskGroup 让父级等待子级，统一传播未处理失败，并通过 cancellation 让整组工作收敛。需要脱离父级生命周期的工作，则应把 ownership 明确移交给 Queue 或 Workflow，而不是留下一项无人负责的内存工作。

当每个 Task 都能回答“我属于哪个 scope，谁等待我，失败交给谁”，Python async 才从同时运行很多 coroutine 变成一个可解释的执行结构。
