Agent Memory 四：用版本链管理更正与撤销

用版本链、current view 和条件写入，让长期 Memory 可以解释、纠正并处理并发修改。

2026/07/14 阅读 次
AgentMemoryData Governance

问题

用户原来要求“会议尽量安排在上午”，后来明确改成“以后只安排下午”。系统直接把同一行的 value 从“上午”覆盖成“下午”。

当前结果看似正确，却留下两个问题。系统无法解释上周为什么按上午安排；另一个早已读取“上午”的 writer 也可能稍后提交修改，把新偏好再次覆盖。直接 update 只保留最后一个字符串，没有保留变化语义，也没有发现 stale writer。

Memory 需要允许事实变化，但“可修改”不等于“原地覆盖唯一版本”。

版本历史、current view 和 audit 解决不同问题

一条可治理的 Memory 可以分成三层：

  • version history 保留 claim 在不同时间的版本、来源和关系；
  • current view 只暴露此刻有效且允许读取的版本；
  • audit event 记录谁请求了什么 mutation，以及 policy 如何决定。
memory_id: schedule_preference_17
version: 3
value: meetings_only_in_afternoon
status: current
supersedes: version_2
source_ref: message_88
expected_version: 2

Retrieval 通常查询 current view，不必把整条历史放入模型 Context。需要解释或恢复时，系统再沿版本关系和 audit event 找到变化来源。

Supersede、revoke、delete 和 undo 不是同一个动作

这些操作都会让旧值不再出现在 current view，但含义不同：

动作表达的事实结果
Supersede有一个新的当前值替代旧值新建版本并指向被替代版本
Revoke旧记录不再被认可，但没有新值将其从 current view 撤下并记录原因
Delete内容必须按用户请求或 retention policy 变得不可用删除或擦除受保护内容；只在 policy 允许时保留最小 tombstone
Undo恢复到先前的业务值新建一个恢复版本，不让历史“倒流”

“撤销错误推断”和“用户现在改了偏好”不能都叫 update。前者不应暗示相反事实成立，后者则有新来源支持新值。Delete 更不是把敏感内容永久保留在所谓 append-only log 中；物理保留必须服从 privacy 和 retention 要求。

把上午改下午的例子走一遍

旧 current record 是 version_2 = mornings_preferred。用户更正后，writer 提交 version_3，携带原始 message source，并声明 expected_version: 2。Memory service 以条件写入完成切换：

version_2: superseded by version_3
version_3: current, afternoons_only
current view: version_3

这样，上周基于 version 2 的安排仍然可以解释；下一次 Retrieval 只看到 version 3。如果用户说“撤回刚才的修改，还是上午”，系统不会删除 version 3 再复活 version 2，而会创建 version_4，其值恢复为上午，并记录它是一次 undo。Current view 前进到 version 4，历史顺序保持不变。

条件写入阻止 stale writer 覆盖新事实

假设 in-loop Agent 和后台归纳都读到 version 2。Agent 先根据用户原话写入 version 3。归纳任务稍后仍以 expected_version: 2 提交自己的候选。

Memory service 应拒绝第二次切换，因为 current version 已经不是 2。这与 HTTP If-Match 防止 lost update 的思路相同：writer 必须证明自己修改的是刚刚读取的版本。失败后，它只能重新读取 version 3，再判断 observation 是否仍冲突、可以合并，还是应放弃。

不要用“最后写入者获胜”掩盖冲突。两个 writer 都有权限，也可能对不同字段做了可合并修改；是否 merge 取决于 record type 和 claim scope，而不是提交时间。

来源失效时，current view 也要变化

版本 status 不能只由业务更正驱动。Source 被撤权、超过 retention 期限或证据完整性失效时，依赖它的 current record 需要重新验证。默认动作是把记录标为 unavailable、请求确认或触发重建，不能自动复活一个已被 supersede 的旧 claim。只有 record type 明确定义了恢复规则，而且另有独立、当前有效的证据支持旧值时，系统才能选择一个替代 current record。无论如何，都不能继续从搜索索引返回已经无权使用的版本。

这也是 current view 独立存在的原因。Version history 说明发生过什么，current view 回答现在能用什么。两者如果混成一张“最新更新时间”表，授权变化和 supersede 很容易被当成普通排序问题。

应该测试什么

测试不仅要覆盖 v2 → v3 的正常路径，还要覆盖两个 writer 同时基于 v2 写入、revoke 后没有替代值、delete 后内容不可恢复、undo 生成新版本，以及 source 撤权后 current view 不再泄漏旧值。

核心检查包括：版本链无环、每个 claim scope 最多一个 current 版本、supersedes 指向存在的版本、条件写入拒绝 stale revision，以及 search index 即使延迟也不能绕过 current-view 验证。

回到问题

把“上午”原地改成“下午”只能得到一个最新字符串，无法说明变化，也挡不住基于旧值的并发覆盖。

让每次 supersede、revoke、delete 或 undo 都拥有明确语义；用 append-style 版本关系保存允许保留的历史，用 current view 提供现在可用的事实，再用 expected_version 保护切换。Memory 才能在允许用户纠正的同时，保持可解释性和并发安全。

后续问题

  • 搜索索引仍返回 superseded 版本时，Retrieval 怎样在使用前过滤。
  • 多种 candidate generation 方法怎样兼顾 recall 和 current validity。
  • 版本历史与长期 Context Budget 应怎样隔离。
