Agent Evaluation 一：非确定性系统不能只看 Pass Rate

从相同总体通过率背后的不同失败分布出发，用 case、configuration 与 trial 解释 Agent 能力是否稳定。

2026/07/12 阅读 次
AgentEvaluationReliability

问题

考虑一个简化的构造例子：两个 Agent 版本都在 25 次测试中通过 20 次，dashboard 因而显示同样的 80% pass rate。

把结果按 case 展开以后，却是两种完全不同的系统：

                  case 1  case 2  case 3  case 4  case 5
系统 A（各跑 5 次）   4/5     4/5     4/5     4/5     4/5
系统 B（各跑 5 次）   5/5     5/5     5/5     5/5     0/5

系统 A 在每个 case 上都有一次波动；系统 B 在这 5 次观测中对四个 case 全部通过，却有一个 case 全部失败。把 25 次结果加总以后，两种失败结构都变成 80%。

如果产品允许自动 retry，A 可能有机会恢复；如果失败 case 对应高风险动作，B 的盲区可能直接阻止发布。评价非确定性 Agent 的第一步，因此不是选择一个更复杂的总分，而是保留 case × configuration × trial 这三个维度。

总体 Pass Rate 会抹掉 Case 分布

单个 pass/fail 只是一条 trial 的结果。把不同 case、模型配置和随机采样混在一个分母里，会同时丢掉两个问题：

  • 失败集中在哪些 case。
  • 同一个 case 是在重复观测中持续失败，还是偶尔失败。

开场中系统 B 的总体平均值并不低，但 case 5 的成功概率在这组观测里是 0/5。若只按总体 pass rate 做 release gate，增加更多简单 case 甚至可以稀释这个盲区，让数字看起来更好。

所以 dashboard 至少要能从总体指标下钻到 per-case trial matrix。总体数适合观察趋势，不能代替对最差 case 和 failure distribution 的判断。

最小记录是一条 Trial，而不是 Case 的最终状态

每次 trial 都应保存独立结果和完整 configuration identity：

{
  "case_id": "case_5",
  "dataset_version": "regression@18",
  "configuration": {
    "model": "model_alias_a",
    "prompt_version": "prompt@7",
    "tool_surface_version": "tools@12",
    "grader_version": "grader@4"
  },
  "trial_id": "trial_5_3",
  "seed": 103,
  "outcome": "task_failed",
  "failure_class": "task_failure",
  "failure_reason": "wrong_tool_selection"
}

case_id 表示要验证的输入与目标；configuration 固定本轮比较的系统版本；trial_id 表示在这组条件下的一次执行。随机 seed、provider metadata、timeout 和并发等条件也应记录，但它们不能替代这三个核心 grain。

如果只在 case 行上覆盖最终状态，fail → pass 会看起来像问题消失，无法知道系统是否先失败四次才偶然成功。如果把每次运行都当成新 case，又无法判断它们是在重复验证同一个能力。

Single-trial、Pass@k 与 All-trials-pass 回答不同问题

同一组 trial 可以派生多个指标，但它们不是同一个指标换了名称。

Single-trial success

micro-averaged valid-trial success
= 通过的有效 trials / 全部有效 trials

它回答从所有有效 trial 中随机选一次执行时，系统成功的频率。开场中 A 与 B 都是 20/25。这个 micro average 会让 valid trials 更多的 case 获得更高权重；当 infrastructure invalid 导致各 case 的有效样本数不同时，还应报告每个 case 的 valid/invalid support，并同时给出 per-case success 的 macro average，或先补齐相同的有效 trial 数再比较。

Pass@k

Pass@k 回答在固定 configuration 下，从同一个 case 独立生成的候选样本中取 k 个时，至少一个成功的概率。HumanEval 论文在每个问题采样 n 个候选、其中 c 个正确且 n ≥ k 时，使用下面的无偏估计形式：

pass@k = 1 - C(n - c, k) / C(n, k)

当 n - c < k 时，估计值为 1。这个值要先按 case 计算，再对 cases 求平均；不能把不同 case 的 n 和 c 合并后只算一次。

这个指标适合衡量“固定 configuration 下生成多个候选，并能识别成功结果”的能力。只有当这些候选满足评测所假设的采样条件，产品允许安全生成 k 个候选，并且具有与评测 grader 对齐的可靠 verifier/selector 时，Pass@k 才能近似产品体验。若产品只能用启发式排序，就应另外评测真实 selector 之后的 Task success。会改变 prompt、state 或 Tool 结果的自适应 repair/retry，应直接评测完整 retry policy 的 Task outcome；文件写入、付款或发送消息也不能因为 Pass@3 很高，就默认可以盲目执行三次。

All-trials-pass

所有 trials 都通过的 cases / 被评测的 cases

它强调有限观测中的一致性。开场中 A 没有 case 达到 5/5，B 有四个 case 达到 5/5。这个指标会对较小波动很敏感，因此必须同时报告每个 case 的 trial 数量，不能把跑 2 次和跑 50 次的结果直接比较。

Single-trial success、Pass@k 和 all-trials-pass 分别回答单次可靠性、候选采样的覆盖能力，以及有限 trials 是否全部通过。选择哪个作为 gate，取决于产品到底允许怎样执行。

Infrastructure Invalid 需要单独的分母

标记 infrastructure_invalid 以前，必须先声明 system under test（SUT）的边界和 failure owner。只有当 trial 因评测侧 fixture 无法启动、测试数据损坏或 grader/harness 崩溃，因而没有对声明的 SUT 产生有效观察时，才属于 infrastructure invalid。若 provider、Runtime 或 network 本来就是产品执行路径的一部分，请求未到达或网络中断就是有效的 timeout/system failure，必须留在 valid denominator 中。把评测侧故障直接记为 model failure 会混淆被测系统和测试基础设施；把产品路径故障从分母静默删除，又会虚高成功率。

更完整的报告同时保留：

scheduled trials        100
valid trials             92
infrastructure invalid    8
task successes           74 / 92 valid trials

这样可以分别得到 valid-trial success 和 infrastructure-invalid rate。前者描述在有效执行中的任务表现，后者描述这次 experiment 是否足以支持结论。

若某个 configuration 的 invalid rate 明显升高，不能只在剩余有效样本上宣布模型质量提升。需要先判断 invalid 是否与该 configuration 有因果关系，例如新版 Tool Surface 触发了 harness 不兼容；failure owner 尚未确定时，应单独报告这些 trials，并把比较标记为不可比，而不是先把它们移出分母或自动归罪于模型。

Failure Distribution 才能区分盲区与波动

Pass/fail 说明结果是否达标，failure taxonomy 才说明下一步该修什么。这里把稳定、低基数的 failure_class 与更具体的 failure_reason 分开；入口文章先定义 coarse class：

Failure class例子主要检查方向
task_failure最终答案错误、Artifact 缺失model、prompt、Tool behavior
policy_violation调用了禁止的 Toolsurface、authorization、grader
timeout在 deadline 前未完成latency、retry、budget、下游依赖
infrastructure_invalidfixture 未启动、harness 崩溃Eval infrastructure

然后回到 per-case matrix：

  • 某个 case 在所有 configuration 下都失败，可能是 dataset 或 grader 定义有问题。
  • 只有一个 configuration 在同一 case 的全部观测 trial 中失败，更像固定能力回归。
  • 多个 case 随机出现不同 timeout，更像全局 flakiness 或 provider/runtime 问题。
  • 同一 case 的 failure_class 从 task_failure 变成 timeout，或 failure_reason 从 wrong_answer 变成 deadline_exceeded，总体 pass 仍下降，但修复方向已经改变。

Failure taxonomy 不需要在入口文章中覆盖所有领域错误。关键是保留原始 trial、稳定的 failure class 和可演进的细分 reason，使后续能够按 Tool、grader、provider 或 Runtime owner 下钻，而不是只剩一个布尔值。

Release Gate 要来自产品的重试与错误成本

没有一个统一指标适合所有 Agent 产品。

如果产品只给一次答案，single-trial reliability 和最差 case 更重要；如果产品可以在无副作用的代码候选中采样三次，Pass@3 可能有直接意义；如果动作高风险且不允许自动 retry，任何 policy violation 都可能成为 hard failure，即使总体 pass rate 很高。

因此，定义 gate 时至少需要写清：

  • 每个 case 跑多少次，为什么这个数量足以支持当前判断。
  • 产品真实允许多少次 retry 或候选采样。
  • 哪些 failure 可以恢复，哪些必须一次不发生。
  • 指标按 trial、case 还是 Task outcome 聚合。
  • infrastructure invalid 达到什么条件时 experiment 不可比较。

增加 trial 能降低偶然采样对判断的影响，却不会自动修复 dataset coverage。五个 case 各跑一百次，仍然只能说明这五个 case 的分布。

回到问题

系统 A 和系统 B 都得到 80%，只是因为总体统计把 case 和 trial 压成了一个分母。

保留 case × configuration × trial 后，A 表现为覆盖面较广但每个 case 都有波动；B 在这 5 次观测中表现为四个 case 全部通过、一个 case 全部失败。再结合产品是否允许 retry、失败是否有副作用，以及 infrastructure-invalid rate，团队才能决定是治理 flakiness、修复固定盲区，还是拒绝这次 experiment 的结论。

非确定性评测不是追求更多指标，而是让每个指标仍然回答一个明确的产品问题。
