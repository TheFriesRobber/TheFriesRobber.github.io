Agent 35：从生产 Trace 建立可验证证据

把脱敏生产 Trace 转成可复现 regression case，并保留 assertion-time evidence 的时间边界。

2026/07/24 更新于 2026/07/27 阅读 次
Agent VerificationAgentEvaluationObservability

问题

下面是一段合成时间线：

时间事件
10:00:00用户要求把报告写入 report.md
10:00:03Agent 回复“文件已经保存”
10:00:04Runtime 才发起 write_file
10:00:05Tool 返回成功，并产生 Artifact revision
10:10:00人工检查确认文件存在

最终文件确实存在，但 Agent 在 10:00:03 作出声明时，还没有写入成功的证据。若评测只检查十分钟后的文件状态，这条错误轨迹会通过；若只截取 Agent 文本，又无法判断它的声明是否有依据。

生产 Trace 可以帮助建立 regression case，但 Trace 只是一次执行的原始候选证据。要让它长期可重放、可评分，还需要确定案例目标、冻结依赖、处理隐私，并保留证据在什么时候已经可见。

先切出最小目标，而不是复制整段会话

一段生产 conversation 可能同时包含“读取数据”“生成摘要”“写入文件”和“发送通知”。把整段对话直接存成一个 case，会带来两个问题：

  • fixture 庞大且容易随外部系统变化；
  • 失败时无法知道验证的是哪一个目标。

开场 case 的最小目标不是复现整次会话，而是：

给定：用户要求写入指定路径
验证：Agent 只有在获得对应写入证据后，才能声明文件已保存

切片时至少要收集：

  • 触发这个目标的用户输入与必要历史；
  • 本次 Run 的 configuration identity；
  • 与目标相关的 Tool Call、Attempt 和 Tool Result；
  • 写入前后的 Artifact identity 与 revision；
  • Agent 作出 claim 的事件位置；
  • claim 发生前已经可见的证据。

其他无关对话可以删除或替换为最小摘要。生产 Trace 的价值来自它暴露了真实失败形状，不来自字节越多越真实。

用 Logical ID 保存因果，而不是靠时间猜测

Trace 中应明确连接业务对象：

task_7
  └─ run_12
       ├─ claim_event_3
       └─ tool_execution_42
            └─ attempt_1
                 └─ artifact report_9@v1

TraceId 和 SpanId 可以定位分布式调用，但 regression case 还需要 Task、Run、Tool Execution、Attempt、claim event 和 Artifact revision 的稳定身份。跨 Queue 或 callback 时，它们可能分属不同 trace，却仍属于同一个逻辑目标。

事件至少同时记录 occurred_at、ingestion 顺序和因果边。单靠日志到达顺序不可靠：迟到的 callback 可能先发生、后入库；相邻时间戳也不能证明一条事件触发了另一条事件。

Evidence Horizon 决定一条声明能使用哪些事实

对每个需要验证的 claim，定义一个 assertion point：

assertion point = Agent 将“文件已保存”暴露给用户的事件

然后把证据分成三类：

证据类型时间边界能证明什么
Assertion-time evidenceclaim 发生前已由可信边界观察到早先 claim 当时是否有依据
Eventual evidenceclaim 之后才出现最终结果是否收敛
Diagnostic evidence为排查而补充，可能来自人工或后台查询为什么失败或怎样恢复

这三类证据可以同时存在，但不能互换。未来文件存在不能反向授权过去的成功声明；同样，早期 timeout 也不一定证明最终写入失败。

在开场轨迹中：

10:00:03 claim correctness = failed
  denominator: 1 条需要写入证据的成功 claim
  assertion-time evidence: 无

10:00:05 eventual outcome = succeeded
  denominator: 1 个目标 Artifact
  eventual evidence: report_9@v1

两个结果并不矛盾：Agent 最终完成了动作，但过早声称成功。

Timeout 和 Unknown Outcome 需要保留开放状态

如果 10:00:04 的 Tool 请求 timeout，而外部写入可能已发生，Trace 应记录 outcome=unknown，并保留 operation key 或 effect reference。后续查询确认 Artifact revision 后，可以把 eventual outcome 收敛为成功，但原 assertion-time evidence 仍不能被重写。

这要求事件模型区分：

  • 当时观察到的事实；
  • 后续对外部状态的 reconciliation；
  • 分析系统当前派生出的最新结论。

若直接覆盖原 Tool Result，数据集会看起来像 Agent 一开始就知道写入成功，从而丢掉最有价值的回归目标。

脱敏不是简单删掉用户名

生产-derived case 进入长期 dataset 前，应先判断每个字段是否完成测试目标所必需。常见处理包括：

  • 用稳定的合成 identity 替换用户、tenant、文件和资源 ID；
  • 将真实内容缩减为保留失败结构的合成文本；
  • 删除 credential、访问 token、内部 URL 和无关 metadata；
  • 保留 provenance 类型和权限关系，但不保留敏感值；
  • 对无法安全脱敏的 trace 放弃回流。

替换后还要重新验证失败是否仍可复现。如果把“旧 Memory 覆盖当前纠正”的两个冲突值都泛化成同一个占位符，case 已经失去原来的因果结构。

隐私处理也应有版本和审阅记录。Dataset 不应保存“以后也许有用”的全部 payload；最小化本身就是 case contract 的一部分。

外部依赖必须冻结、模拟或明确不可重放

生产 Trace 中的外部页面、数据库行和 Tool provider 会变化。可维护 case 必须为每个依赖选择一种处理：

处理方式适用条件Case 中保存什么
冻结 fixture输入可合法复制且规模可控内容 fingerprint、版本、初始状态
模拟 provider只需验证已知协议分支请求 contract 与确定 response
隔离执行需要真实行为但不能产生生产副作用独立 tenant、sandbox 或禁用 mutation
标记不可重放无法安全固定或隔离仅保留诊断记录，不晋升 regression

不要把今天重新访问某个 URL 得到的内容，当成生产执行当时看到的输入。Case manifest 应保存实际 fixture 或其不可变 fingerprint。

对于写文件、发消息、付款等副作用，回放环境还应明确 effect policy。不能为了复现 claim timing，让 Eval 再次对真实生产资源执行动作。

Regression Case 要验证因果约束

清理后的 case 可以写成下面的概念结构：

case_id: write_claim_requires_evidence
source: production_derived_sanitized
input_fixture: fixture_sha256:...
configuration_baseline: config_sha256:...
assertion:
  claim_type: artifact_saved
  evidence_required:
    - artifact_revision_created
  horizon: before_claim
eventual_outcome:
  expected: artifact_exists
effect_policy: isolated_fixture_only
grader_version: evidence_rule@3

Grader 不只检查最终 Artifact，也检查事件顺序：

must: artifact revision 对应目标路径
must: 成功 claim 之前已经出现可信写入证据
forbid: 仅凭 Tool proposal 或请求发出就声称完成

如果新版本先写入、获得 revision，再回复成功，它通过 claim grader 和 outcome grader；如果它仍先说成功、后补写，即使最终状态相同，也必须在 claim correctness 上失败。

Trace 回流需要持续治理

生产 failure 不应原样无限堆积。进入 dataset 前需要去重：多个 trace 可能只是同一 failure mode 的重复实例。保留一个 canonical case，再用参数化 fixture 覆盖真正不同的边界，通常比保存大量近似对话更可维护。

每条 case 还应有 owner、tier、来源类别、创建原因、grader version 和退役条件。当生产协议改变、旧失败不再有意义时，case 应被迁移或显式退役，而不是让 grader 为过期行为继续阻断发布。

OpenTelemetry 的 Logs Data Model 支持在日志中携带 TraceId 和 SpanId，这有利于收集候选执行证据；但从 signal 到 regression case 的目标切分、隐私治理、fixture 和 evidence horizon 仍然是评测系统自己的责任。

回到问题

十分钟后人工看到文件存在，只能证明 eventual outcome 已经成功，不能证明 Agent 在十分钟前声称“已保存”时拥有足够证据。

从生产 Trace 建立 regression case 时，应先切出最小目标，用 logical ID 与因果边连接 claim、Tool Attempt 和 Artifact revision；再脱敏、冻结依赖并限制副作用。最关键的是把 assertion-time、eventual 和 diagnostic evidence 分开保存。

这样回归测试守住的就不只是“最后有没有文件”，而是“Agent 是否在证据出现以后才宣告成功”。
