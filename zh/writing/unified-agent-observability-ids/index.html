Agent Observability 二：用 Logical ID 与 Taxonomy 关联 Log、Metric 与 Trace

从一次 Tool retry 的三套观测记录出发，区分业务身份、物理尝试与 Trace context，并建立可关联的错误语义。

2026/07/15 阅读 次
AgentObservabilityTracing

问题

一次 Agent Run 调用 read_file。第一次请求 timeout，Queue retry 后由另一个 worker 成功完成。三个观测系统都收到了数据：

Log
  run_id=run_12 tool=read_file message="request timeout"

Trace
  trace_id=4bf9... span_id=00f0... status=ERROR
  retry worker 创建了另一个 trace_id=91aa...

Metric
  agent_tool_requests_total{tool="read_file", status="error"} += 1
  agent_tool_requests_total{tool="read_file", status="ok"} += 1

现在要回答“这次用户任务为什么慢，但最后仍然成功”，工程师必须手工猜测：两条 metric 是否属于同一个 Run，第二条 trace 是否是第一次 timeout 的 retry，日志里的 run_12 又对应哪个 span。

问题不是缺少 trace。问题是 Log、Metric 和 Trace 只共享了技术组件名，没有共享 Agent 执行中的 logical identity、Attempt 边界和 failure taxonomy。

Trace ID 只说明一条传播链，不等于业务身份

W3C Trace Context 定义了跨进程传播的 trace context；OpenTelemetry 的 TraceId 和 SpanId 用它关联一条分布式调用路径中的 span。它很适合回答“这个请求经过了哪些服务”。

但 Agent 执行还有更长寿的对象：Task 可以跨多个 Run，Run 可以等待 Queue，Tool Execution 可以有多次 Attempt，Artifact 可以在原 Run 结束后才完成。它们的生命周期不一定与一条 trace 相同。

如果 retry worker 没有接上原 trace context，第二次 Attempt 会产生新 trace；即使正确传播了 context，trace backend 的保留、采样和 span 结构也不应该决定业务对象 identity。

所以需要明确两类关系：

业务关系
task_7 → run_12 → tool_execution_42 → attempt_1 / attempt_2

观测关系
attempt_1 → trace_4bf9 / span_00f0
attempt_2 → trace_91aa / span_18c2

Trace ID 可以变化，tool_execution_42 仍表示同一个获准执行的逻辑动作。反过来，同一条 trace 中也可能包含多个 Tool Execution，不能拿 trace ID 充当 Tool identity。

Logical ID 与 Attempt ID 要同时保留

开场中的 retry 至少需要下面这些字段：

字段Grain作用
task_id用户目标连接跨 Run 的最终结果
run_id一次 Agent Loop连接当前输入与 terminal Run
tool_execution_id获准执行的逻辑动作多次 retry 仍保持稳定
attempt_id一次物理尝试记录 timeout、latency 与 provider response
trace_id / span_id观测传播路径在 tracing backend 中定位请求

这延续了 Agent Observability 一：建模前先明确 Grain 的结论：Tool Execution 成功率和 Attempt 成功率可以不同。O2 进一步要求这些 grain 在不同 signal 中仍使用相同语义和字段名。

稳定不等于所有字段都由客户端生成。真正的 owner 应在对象首次提交时分配 identity，并在 Queue message、retry request 和 callback 中传播。收到重复消息时，consumer 复用原 tool_execution_id，但为新的物理调用创建新 attempt_id。

Log 和 Span 可以携带高基数关联字段

OpenTelemetry Log Data Model 为 LogRecord 定义了可选的 TraceId 和 SpanId，因此日志可以直接跳到对应 span。Agent 系统还应把 logical identity 作为结构化字段记录，而不是只拼进 message：

{
  "event": "tool.attempt.finished",
  "task_id": "task_7",
  "run_id": "run_12",
  "tool_execution_id": "tool_execution_42",
  "attempt_id": "attempt_1",
  "trace_id": "4bf9...",
  "span_id": "00f0...",
  "outcome": "unknown",
  "error.type": "deadline_exceeded"
}

对应 span 也可以包含这些 attributes。这样，从 trace 可以跳到同一 Tool Execution 的其他 Attempt；从业务日志也可以回到实际网络路径。

这类 ID 基数很高，但 Log 和 Trace 本来就保存单条事件或 span。仍需做访问控制和保留期治理，不能因为便于关联就把用户输入、credential 或敏感资源名复制进所有 signal。

Metric 共享 Taxonomy，不应复制全部高基数 ID

“三类 signal 建立共享关联语义”不意味着把 run_id、task_id 或 tool_execution_id 作为普通 metric label。

Metrics 会按 attribute 组合形成 time series。OpenTelemetry Metrics SDK 也明确存在 cardinality limit；若每个 Run 都创建一组新 series，成本和内存会随请求量增长，最终可能触发 overflow aggregation，反而失去可观测性。

Metric 应共享的是字段语义和低基数 taxonomy：

agent_tool_attempts_total{
  tool="read_file",
  outcome="unknown",
  error.type="deadline_exceeded"
}

若后端支持 exemplar，可以让少量 metric data point 关联代表性的 trace context；也可以在告警触发后按相同时间窗、tool 和 error type 查询 Log/Trace。重点是三类 signal 对 outcome 和 error.type 的含义一致，而不是每条 metric 都携带所有业务 ID。

一个实用边界是：

  • Log/Trace 保存高基数 identity，用于定位单次执行。
  • Metric 使用有界维度，用于聚合趋势和告警。
  • Exemplar 或查询链接连接聚合与单次样本。

要驱动恢复，Error Taxonomy 还需记录 Failure Owner

如果 Log 记录 timeout、Trace 使用 DEADLINE_EXCEEDED，Metric 却只写 error=true，关联以后仍然不知道问题属于 model、Tool、Runtime 还是 provider。

OpenTelemetry Semantic Conventions 已定义 error.type，并建议同一失败在对应 Span 与 Metric 中使用相同值；成功操作不应携带该属性。Agent Runtime 可以在内部维护 canonical error class，但导出到 OpenTelemetry 时应映射到 error.type。outcome、failure_owner 与 retry_disposition 则是本文建议的应用层字段：

{
  "outcome": "unknown",
  "error.type": "deadline_exceeded",
  "failure_owner": "tool_provider",
  "retry_disposition": "query_before_retry"
}
  • outcome 表示当前能确认的结果，例如 succeeded、failed、cancelled、unknown。
  • error.type 是跨 Span、Metric 与 Log 对齐的稳定、低基数失败类型。
  • failure_owner 指向最先拥有修复动作的边界，而不是简单复制抛异常的服务名。
  • retry_disposition 描述 Runtime 下一步允许怎样处理。

同一个 HTTP 504 可能代表 provider deadline，也可能是本地 gateway timeout；taxonomy 应由最接近事实的边界规范化，并保留原始 status 作为诊断字段。不能为了统一而抹掉 source evidence，也不能在成功 signal 上残留上一次失败的 error.type。

一次 Retry 怎样落进三类 Signal

把开场中的两个 Attempt 重新记录：

tool_execution_42
  attempt_1
    log:   outcome=unknown error.type=deadline_exceeded
    span:  trace_4bf9 span_00f0 status=ERROR
    metric: tool_attempts{tool=read_file,outcome=unknown,error.type=deadline_exceeded} +1

  attempt_2
    log:   outcome=succeeded
    span:  trace_91aa span_18c2 status=OK
    metric: tool_attempts{tool=read_file,outcome=succeeded,...} +1

terminal logical result
  log/event: tool_execution_42 outcome=succeeded attempts=2
  metric: tool_executions{tool=read_file,outcome=succeeded} +1

现在可以同时回答三个问题：

  • 两个 provider Attempts 中，一个确认成功、一个结果未知；如果指标明确以“确认成功 / 全部 terminal Attempts”为分母，才可以记为 1/2。
  • 逻辑 Tool 动作是否完成：1/1 Tool Execution 最终成功。
  • 为什么用户感到慢：Attempt 1 消耗了 deadline，Attempt 2 才确认结果。

即使两个 Attempt 属于不同 trace，tool_execution_id 仍把它们连接起来；即使 Metric 不保存这个 ID，统一的 tool、outcome 和 error.type taxonomy 仍可与详细 signal 对齐。

Queue 和 SubAgent 需要显式传播，而不是事后猜测

跨 Queue 时，producer 应把业务 identity 与 trace context 作为不同字段写入 message envelope：

{
  "task_id": "task_7",
  "run_id": "run_12",
  "tool_execution_id": "tool_execution_42",
  "attempt_no": 2,
  "trace_context": {
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
    "tracestate": "vendor=value"
  }
}

Receive span、批处理 Process span 默认用 Span Link 关联 message creation context；只有处理单条消息的 Process span，才可以按 tracing policy 把该 context 作为 parent。如果因为安全边界或采样策略开启新 trace，仍应保留 Span Link。traceparent 与存在时的 tracestate 一起构成传播 context，但无论怎样组织 trace topology，都不能丢掉 logical identity。SubAgent、callback 和后台 Job 同理：Span parent/link 服务观测，业务 parent/child relation 服务执行语义。

如果历史系统已经产生多套 ID，不应靠时间接近永久 join。可以在可信入口建立 correlation mapping，并让新事件逐步携带 canonical identity；无法证明关系的旧记录要标记为 unresolved，不能为了完整率硬连。

回到问题

开场中 Log、Metric 和 Trace 都有数据，却无法解释一次 retry，是因为它们只记录了各自方便的技术标识。

保留 task_id → run_id → tool_execution_id → attempt_id 的业务关系，再把每次 Attempt 关联到 trace/span，两个 worker 的请求就仍属于同一个逻辑动作。Log 和 Trace 保存高基数 identity；Metric 使用同一 outcome/error taxonomy 和有界维度，必要时通过 exemplar 或查询跳回具体 trace。

共享语义不是把所有字段复制到所有 signal，而是让三个系统对“记录的是哪个 grain、结果是什么、失败由谁处理”给出同一个答案。
