Agent Discovery

先定义业务结果，再决定是否需要 Agent

从“我们想做一个 Agent”退回任务结果、当前损失、责任边界和完成证据，把解决方案偏好改写成可验证的业务问题。

问题

一个客服团队提出要做退款 Agent。最初的功能列表很快成形：读取客户消息、查询订单、判断退款条件、生成回复，最好还能直接创建退款。

这份需求看起来具体，却没有回答一个更基本的问题：团队究竟想改善什么结果？

如果客服真正的瓶颈是支付状态同步延迟，生成回复不会缩短处理周期；如果大量时间花在等待主管确认，让 Agent 更快地产生建议也不会减少等待；如果退款错误来自政策版本不一致，再强的模型也只会更快地使用错误规则。

“我们想做一个 Agent”已经预设了解法，却没有定义问题。需求调研的第一步，是把 Agent 从句子中暂时拿掉，重新描述任务结果、当前损失和责任边界。

功能请求隐藏了三种不同的问题

用户表达的“需求”通常混合了三个层次：

解决方案偏好：我们想做退款 Agent
能力请求：它应该查询订单、判断政策并回复客户
业务问题：退款处理慢，而且相同情况会得到不同结果

前两个层次可以帮助理解用户想象中的产品，但只有第三个层次能够支持投资判断。它说明现状哪里不好，却还没有假定一定由 Agent 解决。

同一个能力请求也可能对应不同业务问题。“自动查询订单”可能为了减少人工操作，也可能为了避免漏查已取消订单；“自动回复”可能为了缩短首次响应，也可能只是希望统一措辞。这些目标需要不同的完成条件和 Eval。

因此，调研不能停在“希望系统做什么”。还要继续问：

  • 这项任务最终交付给谁；
  • 当前结果为什么不理想；
  • 损失发生在时间、成本、质量、风险还是能力覆盖；
  • 哪个变化对业务真正有用；
  • 谁能够确认变化已经发生。

这些问题不是在拒绝用户提出的 Agent，而是在为它寻找可以被证伪的理由。

业务结果必须落到外部状态

退款场景中，团队可能依次提出三个目标：

  1. 更快生成客服回复；
  2. 更快完成退款处理；
  3. 减少客户从申请到到账的时间。

三个目标看起来相近，实际边界完全不同。

生成回复只要求产生文本；完成退款处理要求支付系统接受动作并返回退款标识；缩短到账时间还涉及支付渠道后续状态。Agent 对哪个结果负责，决定它需要访问哪些数据、拥有哪些 Tool，以及何时可以声明完成。

可以用一条最小结果链检查需求：

模型输出
→ 用户或系统采取动作
→ 外部状态发生变化
→ 结果被重新观察和确认

链条在哪一步结束，任务责任就应写到哪一步。若 Agent 只负责建议，就不能用“退款完成率”评价它；若 Agent 被要求完成退款，就不能把“生成了正确话术”当作成功。

这也是为什么业务结果必须带证据。客服说“已经处理”、Tool 返回 HTTP 200、支付系统出现退款记录，分别代表不同强度的事实。需求阶段不必设计完整运行时协议，但必须知道最终由什么外部状态证明任务完成。

当前损失决定机会是否真实

明确结果后，还要确认现状是否真的值得改变。一个任务看起来繁琐，不代表自动化后会产生净收益。

可以从最近的真实案例追问：

  • 任务从触发到完成经历了多长时间；
  • 其中多少是操作，多少是等待；
  • 哪些步骤最常返工；
  • 错误多久以后才会被发现；
  • 哪些角色为错误补救；
  • 如果维持现状，损失会继续发生在哪里。

这里不需要急着估算一个漂亮的 ROI。需求调研首先要找到损失的机制。

假设客服填写退款草稿只需要两分钟，但主管平均两小时后才审批，那么把填写时间压缩到十秒不会显著改变端到端周期。相反，如果客服花大量时间跨系统收集信息，且 Agent 能可靠完成这部分，即使最终审批仍由人工执行，也可能产生真实收益。

判断依据应来自真实案例、工单或操作记录，而不是访谈中的印象数字。没有测量时可以先记录为待验证假设，不能把“用户觉得很频繁”直接写成收益事实。

责任边界必须和结果一起定义

业务结果还隐含另一组问题：谁拥有任务，谁承担错误？

退款任务可能涉及客户、客服、主管、财务和支付系统。提出需求的人、实际使用的人、批准高风险动作的人和承担损失的人，往往不是同一个角色。

因此，业务问题陈述至少要区分：

角色在需求中的责任
任务发起者提供请求和必要材料
一线执行者处理常规情况并维护客户沟通
决策 owner判断政策无法直接覆盖的例外
风险 owner批准高金额或不可逆动作
结果确认者根据外部证据判断任务完成

如果这些角色没有分开，需求很容易把“帮助客服”扩展成“代替主管授权”，或把“创建退款草稿”误写成“完成退款”。

Agent 自主程度可以后续再决定，但责任 owner 必须在需求阶段可识别。否则团队无法定义权限，也无法解释失败后应该交给谁。

一份业务问题陈述已经足以筛选方向

完成上述澄清后，退款需求可以改写为：

一线客服处理符合标准政策的退款时，需要跨订单、支付和物流系统收集证据，导致常规工单处理时间长，并因漏查状态产生返工。目标是在不扩大退款授权的前提下，减少常规案例的信息收集与草稿准备时间；金额超限、状态冲突和政策未覆盖的案例仍由对应 owner 决定。结果通过端到端处理时间、人工修改率、错误退款和升级质量验证。

这段陈述没有承诺一定建设 Agent，却已经提供了四个可以继续调研的对象：

  • 真实工作中的信息收集路径；
  • 常规与例外案例的分界；
  • 可以委托的动作范围；
  • 验证业务变化所需的指标。

如果后续发现规则完全固定，最终解法可能是 Workflow；如果主要价值来自辅助判断，可能是 Copilot；只有当任务需要动态收集证据、选择路径并推进外部状态时，Agent 才成为合理候选。

回到问题

客服团队最初要求一个能够查询订单、判断政策和生成回复的退款 Agent。那是一张功能清单，不是可验证的需求。

把 Agent 暂时拿掉后，真实问题变成：常规退款的证据收集和草稿准备消耗时间，状态遗漏造成返工，而高风险例外仍需要明确 owner。

现在团队还没有决定最终产品形态，但已经知道要改善的结果、不能越过的责任边界，以及用什么外部证据判断变化。这比一开始确认模型和 Tool 更重要。

需求挖掘不是证明用户提出的 Agent 值得做，而是先证明存在一个值得改变的业务结果。
