Agent Runtime 十：子任务应该交给谁执行

2026/07/17 阅读 次
AgentRuntimeWorkflow

问题

用户让 Agent 比较三个技术方案。主 Agent 在 Plan 中拆出三个研究方向，或者在推理过程中临时发现它们：

subproblem A  研究方案 A
subproblem B  研究方案 B
subproblem C  研究方案 C

这里先固定三个概念：SubAgent 是父 Agent 在当前 Run 内动态发起并继续拥有的 Child Run；Child Job 是由持久调度系统拥有、可以由其他 worker 接管的工作单元；Workflow Fanout 则由 workflow controller 按已知依赖启动多个节点并负责汇合。具体框架可能使用不同名字，本文比较的是它们各自的状态 owner。

这些记录只说明“还有三个子问题需要完成”，尚未创建任何 SubAgent 或后台任务。Plan item 不拥有执行生命周期，模型提出的 delegation 也只是请求。Runtime 或业务 controller 仍要决定：由当前父 Run 等待 child、由 durable job system 接管，还是由 workflow controller 管理分支和汇合。

三种实现都可能画成并行箭头，但父进程退出、用户取消或只完成两个分支时，系统应做什么完全不同。

因此，“能并行”不是选择执行原语的充分理由。真正需要分开问的是：谁负责收敛子工作的状态，谁消费结果并完成最终交付，内容又保存在哪里？

子问题的来源不决定执行原语

子问题可以来自三个位置：

  • Agent Loop 在当前推理中动态发现需要补充研究。
  • 可修订 Plan 新增一个待完成 item。
  • 确定性的业务流程预先声明一组分支。

来源只能解释“为什么出现这项工作”，不能决定“谁负责让它完成”。比较执行原语前，可以先把请求压缩成几个与 owner 有关的条件：

goal                 要交付什么
needed_within_parent 父 Run 是否要在进入终态前消费结果
survive_restart      是否要求跨 worker / process 恢复
independent_lifecycle 是否允许父 Run 先结束，或单独取消、重试和交付
known_dependencies   分支和汇合是否预先确定
delivery_owner       谁消费结果并向用户完成最终交付

这里的 delegation proposal 仍是与执行原语无关的子工作请求。只有系统已经选择 SubAgent 后，模型或父 Runtime 才会生成 SubAgent-specific 的 spawn_agent request。可信 Runtime 还要校验 Tool Surface、预算和授权，再创建真正的 Child Run；这个过程由下一篇《Agent Runtime 十一：Spawn Request 如何变成受控 Child Run》展开。本文先解决 proposal 应交给哪种状态 owner。

三种委派的核心差异

前面的三个名字只是语义分类；其中 Workflow Fanout 只有在 history/state 持久化时才提供跨进程恢复。判断可以落在下面几个维度：

维度SubAgentChild JobWorkflow Fanout
工作状态 owner父 RunJob systemWorkflow execution / controller
跨进程恢复不一定是主要目标取决于是否持久化 workflow history/state
分支从哪里来模型动态决定应用或父执行提交通常来自显式 workflow 逻辑
结果消费与最终交付父 Agent 汇总并交付Job caller 或后续 Run 消费Workflow caller 或产品层交付
结果保存位置父 Run result 或 artifactJob result 或 artifact store节点输出、业务库或 artifact store

这不是产品功能对比，而是语义分类。Artifact store 只负责保存和 retention，不负责判断工作是否完成，也不一定向用户交付结果。一个 SubAgent framework 也可以把 Child Run 持久化；这会增加恢复责任，但只有显式把状态 owner 交给持久调度系统，才会成为本文所说的 Child Job。

什么时候选择 SubAgent

如果主 Agent 在推理中发现需要一个临时专家，父 Run 会在进入终态前消费结果，并且仍负责收敛 child 状态，SubAgent 通常最自然：

父 Agent：我需要先比较数据库方案
→ 启动 database-research SubAgent
→ 等待结构化结论与证据
→ 父 Agent 验证并继续回答

这类工作的特点是：目标由模型动态产生，子结果服务于当前 Run，父 Agent 仍对最终答案负责。父 Run 取消时，child 通常也应取消；父 Run 已经结束后，孤立 child 的结果往往没有消费者。父 Tool Execution 可以同步等待，也可以先保存 handle、稍后收集；sync / async 只是结果收集方式，不改变状态 owner。

如果 child 只是进程内 async task，worker 崩溃后它会一起消失。这不是错误，只要 API 从未承诺恢复。Durable Runtime 也可以持久化父 Run、Child Run 和 handle，在新 worker 中恢复二者，同时继续由父 Run 拥有 child。是否跨进程恢复决定持久化责任，不自动决定生命周期 owner。

什么时候升级为 Child Job

假设其中一个分支需要爬取大量公开文档、生成 PDF，并允许父 Run 先进入终态、用户之后单独查看。这项工作已经拥有独立生命周期：

  • 父 Run 可以先返回“任务已创建”。
  • 父 Run 结束后仍要继续。
  • 任务需要自己的 retry budget、状态和 artifact。
  • 用户可能单独取消或重试它。
  • 结果可以由后续 Run 或产品页面独立消费。

这时更合适的是 durable Child Job。父 Run 保存 job_id，但不持有它的全部运行状态。Job system 负责 claim、lease、恢复和终态；结果通过稳定 artifact 或 completion event 返回。

Child Job 不等于“放到 Queue 就完成了”。Queue 可能重复投递，外部副作用仍需幂等，父子之间也要明确取消和结果保留策略。

什么时候使用 durable Workflow Fanout

如果三个分支在运行前已经由业务流程确定，而且只有全部完成后才能进入固定汇总步骤，workflow fanout 更合适：

prepare input
├─ analyze A
├─ analyze B
└─ analyze C
   ↓
compare results
   ↓
publish report

这里的核心不是让三个 Agent 自由协商，而是 controller 需要知道依赖、重试、部分完成和 join 条件。如果 controller 把 workflow history/state 持久化，并定义 replay/recovery contract，这些记录可以成为可恢复的控制流事实；单纯写出 fanout + join 结构并不会自动获得 durability。分支结果仍可以保存在业务数据库或 artifact store。

模型仍可以参与某个节点，但不应该让模型临时改写已承诺的 workflow 终态语义。例如“允许两个分支成功就继续”应是显式 join policy，而不是汇总 Agent 临场猜测。

同一个例子如何选择

回到“三个技术方案”的请求，可以按下面的顺序判断：

  1. 谁拥有子工作的状态、retry 和终态？ 父 Runtime 为当前 Run 收敛 Child Run，才是本文所说的 SubAgent；Job system 独立 claim、retry 并提交终态，就是 Child Job，即使父 Run 会等待它完成。
  2. 父 Run 是否必须消费结果后才能结束？ 这决定父级是否等待以及谁完成最终交付，不单独决定工作状态 owner。
  3. 父 Run 结束后，工作是否还要继续、单独取消或独立交付？ 这是选择 Child Job 或 durable workflow node 的强信号，但不是 Child Job 的必要条件。
  4. 分支和依赖是否由确定性业务流程预先定义？ 是，则优先 Workflow Fanout。
  5. 谁消费分支结果并完成最终交付？ 这个对象必须明确 join、取消和失败策略；它不一定是保存 artifact 的组件，也不一定拥有子工作的执行状态。

假设只是一次交互式回答，三个研究分支都可在几十秒内完成，而且用户取消后无需保留结果：使用三个受父 Run 管理的 SubAgent 即可。

假设其中一个分支要把 report.md 转为 PDF，父 Run 会等待结果，但 Queue、worker claim、retry 和 Job 终态都由持久调度系统管理：它仍然是 Child Job。父 Run 是结果消费者，不是工作状态 owner。

假设每个分支会产生独立报告，父 Run 可以先结束，之后由后续 Run 或产品页面分别消费：创建三个 Child Job，并让后续汇总任务等待 artifact。运行时间长本身不是升级条件；关键是生命周期和交付责任已经独立。

假设这是每天固定运行的分析管道，分支集合和汇总规则提前已知：使用 workflow fanout，不必让主 Agent 重新“发明”调度结构。

失败和取消最能暴露边界

场景SubAgentChild JobWorkflow Fanout
父 Run 取消通常传播取消按显式 policy 取消或继续由 parent-close/cancellation policy 决定
Worker 崩溃进程内 child 可能丢失新 worker 接管持久 workflow 可从 history/state 恢复；非持久实现不能保证
一个分支失败父 Agent 决定是否降级Job 独立 retry 或终态Join policy 决定 fail-fast、部分成功或补偿
父级已结束结果通常失去消费者结果按 retention 保留Parent-close policy 决定 child 行为

不要把“取消请求已发送”写成“子工作已经停止”。无论使用哪种原语，都要区分 request、acknowledgement 和最终收敛。

Temporal 等 workflow 系统甚至显式提供 Parent Close Policy，让 child 在 parent 结束时 terminate、request cancel 或继续。这恰好说明父子生命周期不是由“嵌套调用”自动决定的。

组合通常比统一更合理

复杂系统不必三选一。一个 durable workflow node 可以启动 Agent Run，Agent 在某个 Model Turn 内再使用 SubAgent；SubAgent 发现长任务后，也可以通过受控 Tool 创建 Child Job。

组合时要避免身份丢失：

workflow_execution_id
→ job_id
→ run_id
→ child_run_id

这些 ID 表达不同 grain，不能全部压成一个 parent_id。Trace 可以把它们连起来，但 retry、状态和成本仍归各自 owner。

回到问题

Plan 或 Agent Loop 产生三个子问题，并不等于已经生成三个 SubAgent。它只让系统看见了三项待完成工作。

SubAgent 适合由父 Run 收敛状态的动态协作；Child Job 适合把 claim、retry 和终态交给持久调度系统的工作；durable Workflow Fanout 适合依赖和汇合规则明确、由持久 controller 管理的 control flow。先分别确定工作状态由谁收敛、结果由谁消费和交付、内容保存在哪里，再选择原语，系统才不会在父进程退出后才发现自己从未定义谁负责收尾。
