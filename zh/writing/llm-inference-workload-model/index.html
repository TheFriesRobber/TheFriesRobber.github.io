LLM Infra 01：先把推理负载描述清楚

用输入与输出 Token、Prefill/Decode、arrival shape、并发和 deadline 建立可供 SLO、Benchmark、容量与调度共同消费的 workload envelope。

问题

两个模型入口都稳定在 100 requests/s。入口 A 大多是短 Prompt、短输出；入口 B 的平均请求数相同，却混入了长 Context 和长生成。监控只看 QPS 时，两者像是承受了同样的压力，B 却更早出现排队，Time to First Token（TTFT）也持续变长。

问题不在于 QPS 算错了，而在于它只数了请求，没有描述请求要求模型完成多少工作、占用状态多久，以及何时完成才算有用。

这篇文章要建立的不是一套更大的指标列表，而是一个可以被 SLO、Benchmark、容量规划和调度器共同消费的 workload envelope。

Request count 隐藏了 Token work

先看一组合成请求。它们只用于说明描述方法，不代表任何模型或 GPU 的实测性能。

入口请求速率输入 Token 分布输出 Token 分布流量形态
A100 req/sP50 120，P95 240P50 32，P95 64均匀到达
B100 req/sP50 120，P95 8,000P50 32，P95 1,000每分钟一次突发

请求数相同，并不意味着输入 Token、输出 Token或同时驻留的 sequence 数相同。更重要的是，输入与输出 Token 也不能直接合并成一个总数，因为它们进入的是不同执行阶段。

主流推理工具本身也保留了这些区别。vLLM 的 per-request metrics 分开记录 prompt_tokens、completion_tokens、queue time、生成时间和 inter-token latency；NVIDIA AIPerf 则把 Input Sequence Length、Output Sequence Length、TTFT 和 Inter Token Latency 分开定义。这些字段的存在不是统计偏好，而是执行模型不同造成的结果。

因此，requests/s 只能作为 arrival rate 的一个投影。它不能单独成为容量单位。

Prefill 与 Decode 施加的是两种压力

生成式推理通常可以分成两个阶段：

  • Prefill 处理已有 Prompt，为每一层计算表示并建立后续生成需要的 KV state。
  • Decode 自回归地产生新 Token，每一步读取已有状态，再把新 Token 的状态追加进去。

长 Prompt 会直接增加 Prefill 工作；长输出会让 sequence 在 Decode scheduler 和 KV Cache 中停留更久。两个请求即使总 Token 数接近，也可能因为输入/输出比例不同而产生完全不同的 TTFT、Token 间隔和显存驻留时间。

DistServe 的论文把 TTFT 与 Prefill、Time Per Output Token（TPOT）与 Decode 分开建模，并指出两阶段的计算与资源特征不同。这里不需要接受某一种具体部署架构，也能得到一个基本结论：workload model 必须保留阶段，不能只保留总 Token 数。

于是入口 B 的异常不再神秘。长 Context 拉长了部分请求的 Prefill；长生成又提高了 active sequence 的驻留时间。二者共同改变了队列与显存压力，而 QPS 对这些变化完全失明。

平均长度仍然会丢掉尾部风险

把 QPS 换成“平均输入 400 Token、平均输出 100 Token”仍然不够。

假设 99 个请求输入 100 Token，另一个请求输入 30,000 Token。平均值能反映总量，却不能告诉 scheduler 那个长请求会不会阻塞短请求，也不能告诉容量规划它是否会触碰 Context 或 KV 上限。

可用的 workload 描述至少要保留下列分布，而不是只保存均值：

维度为什么要保留
输入 Token 分布决定 Prefill 工作，并影响第一段 KV 占用
输出 Token 分布或上限决定 Decode 驻留时间和最终 KV 占用
输入/输出相关性长输入是否通常也伴随长输出
arrival shape均匀、Poisson、周期性突发或集中提交会形成不同队列
观测并发与连接生命周期open-loop 下并发是 arrival 与 service time 共同产生的结果；streaming 请求还可能被客户端提前取消
deadline / priority同样的工作量，在不同完成期限下不是同一种服务
model / adapter / feature决定请求可以在哪个兼容 deployment 上执行

这些字段不要求平台永久保存原始 Prompt。Token count、bucket、时间窗口和经批准的 workload label 已经能支持大部分容量讨论，也能减少不必要的内容留存。

Workload envelope 把观测与预测分开

下面是一份概念性 schema。它不是某个 Runtime 的 API，重点是把“已观测事实”和“未来假设”分开：

workload_envelope:
  identity:
    model_requirement: chat-compatible-v3
    workload_class: interactive
  observed_window:
    start: 2026-07-28T10:00:00Z
    duration: 15m
    request_count: 90000
    input_tokens: {p50: 180, p95: 2200, p99: 7800}
    output_tokens: {p50: 64, p95: 420, p99: 900}
    requested_max_output_tokens: {p50: 256, p95: 1024}
    input_output_joint_buckets_ref: artifact://wl_7fd2/joint-token-buckets
    replayable_arrival_trace_ref: artifact://wl_7fd2/arrival-trace
    arrival:
      mean_rps: 100
      peak_10s_rps: 175
    observed:
      active_requests: {p50: 38, p95: 92}
      streaming_connections: {p50: 35, p95: 86}
    cancellations:
      before_first_token: 0.012
      after_first_token: 0.006
  forecast:
    horizon: 30m
    arrival_multiplier: [0.8, 1.0, 1.4]
  contract:
    ttft_deadline_ms: 1500
    tpot_deadline_ms: 80
    priority: normal

其中 Token 分布、相关性、到达窗口、观测并发和取消结果是观测；arrival_multiplier 是预测；deadline 是服务契约。三者如果混在一起，后续就无法区分“流量变了”“预测错了”和“SLO 改了”。这里的 marginal percentiles 方便阅读，真正重建 workload 仍要消费 joint buckets 或 arrival trace。

合成例子里，入口 B 不应被压缩成“100 req/s”。它应该被描述为：在给定时间窗口内，存在怎样的输入/输出长度分布、怎样的 burst、多少并发，以及哪些请求必须在什么期限内得到首 Token 和后续 Token。

同一份 envelope 必须贯穿后续决策

workload model 的价值，最终取决于它是否真的被下游消费：

  • SLO 设计用它区分交互、异步与 Batch 请求，避免共享一个 P95。
  • Benchmark 用它生成长度、arrival、并发和 deadline 分布，而不是只跑固定长度。
  • 容量规划用它选择与生产负载相同的 service curve。
  • 单 Replica scheduler 用它估计 Prefill、Decode 和 KV 需求。
  • Autoscaling 与 admission 用它比较 pending work 和 deadline slack。

如果每个环节重新定义“一个请求”，指标口径就会漂移。Benchmark 可能证明了短 Prompt 的吞吐，容量规划却拿它承诺长 Context；gateway 统计逻辑请求，Runtime 又把 retry attempt 重复算成新需求。

Workload envelope 不是 Source of Truth 的唯一记录，但它必须有稳定版本和 fingerprint，使每一条性能结论都能回答：结论对应的是哪一种负载？

回到问题

入口 A 与入口 B 都是 100 requests/s，但它们不是同一种 workload。B 的长 Context 增加 Prefill 压力，长输出延长 Decode 与 KV 驻留，突发到达又在短窗口内制造队列。

正确的修复不是再给 QPS 加一个平均 Token 数，而是建立带分布、阶段、arrival shape、并发和 deadline 的 workload envelope。这样，下一篇讨论 TTFT、TPOT、吞吐与成本时，才能针对同一个工作对象定义“什么叫交付成功”。
