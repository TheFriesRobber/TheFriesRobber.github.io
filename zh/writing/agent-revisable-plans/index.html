Agent 14：Plan 怎样在前提变化后安全修订

把 Plan 建模为带 revision、依赖、前提和 evidence lineage 的可修订 Artifact，而不是执行状态机。

2026/07/24 更新于 2026/07/27 阅读 次
Agent CoreAgentPlanningArtifacts

问题

Agent 的计划假设目标 API 支持批量写入，于是生成三个步骤：准备批量 payload、调用批量接口、验证结果。执行中读到新文档，发现该 API 只支持单条写入，但三个步骤仍都显示 ready。

如果只让模型“重新想一个计划”，旧计划项、已经取得的证据和正在执行的工作会失去关联；如果继续原计划，又会在失效前提上重复失败。Plan 需要被修订，但不能冒充 Runtime 的执行状态。

Plan 描述承诺，不拥有执行事实

Plan item 表达“为了目标，准备完成什么”。它可以关联 Child Run、Job 或 Tool operation，但这些执行原语各自拥有 started、attempt、outcome 和 cancellation。

把 Plan item 直接标成 running/succeeded，容易让两层事实混在一起：

  • Plan revision 说明当前承诺是否仍有效；
  • execution owner 说明某次工作实际上发生了什么。

执行结果可以成为 Plan evidence，Plan 却不能覆盖 Tool 或 Job 的历史。这样，replan 才不会把已经发生的副作用从记录中删掉。

最小 Plan Artifact 需要 revision

一份可修订 Plan 至少包含：

plan_id
revision
goal
items
dependencies
assumptions
evidence references
supersedes

每个 item 还应能表达 ready、blocked、stale 或 done 这类承诺状态。这里的 done 表示“目标所需的证据已满足”，不是某个 handler promise 返回。

Revision 让读取方明确自己看到哪一版。原地修改 item 文本会让正在执行的 Child Run 无法判断自己对应哪个 proposal，也让审计无法解释计划为什么变化。

模型只能生成 revision proposal。可信 Plan owner 还要校验 evidence、policy 和 expected_revision，再通过 compare-and-swap（CAS）原子切换 active revision。若用户修改和后台 replan 都基于 revision 1，只有一个 proposal 能提交；另一个必须读取新的 active revision 后重新计算。执行对象与结果消费方始终绑定 plan_id + revision + item_id。

前提失效要沿依赖传播

开场计划可以表示为：

assumption A: bulk API is supported
item 1: build bulk payload      depends on A
item 2: call bulk API           depends on item 1
item 3: verify all writes       depends on item 2

新文档使 A 失效后，不是所有 evidence 都必须丢弃。已经收集的记录列表仍然有效；bulk payload 的组织形式可能失效；验证目标仍有效，但其输入依赖需要重建。

Plan owner 校验 expected_revision=1 后提交 revision 2：

  • A 标为 invalid，并引用新文档；
  • item 1、2 标为 stale；
  • 新增“逐条写入并使用 operation key”；
  • item 3 改为依赖所有单条写入的 terminal evidence；
  • 可复用的输入 evidence 保持原引用。

这比完全生成一份无关新计划更安全，因为变更原因和仍有效证据都可追踪。

Replan 要说明什么改变了

一次可审查的 replan 至少回答：

  1. 哪条新 evidence 推翻了哪个 assumption；
  2. 哪些 item 因依赖关系变成 stale 或 blocked；
  3. 哪些 evidence 仍然有效；
  4. 哪些已启动执行需要取消、等待或继续；
  5. 新 revision 何时成为 active plan。

Plan revision 不能自动取消外部工作。若旧 item 已经创建 Child Run，真正的执行 owner 仍要处理 cancellation 和 effect reconciliation。Plan 只改变“这个工作是否仍服务于当前承诺”。

Plan 可以产生 Delegation proposal

一个 ready item 可以成为 delegation proposal，但它不决定应该使用 SubAgent、后台 Job 还是 durable Workflow。执行原语取决于完成状态 owner、生命周期、隔离和恢复要求。

这也说明没有显式 Plan 的简单任务仍然可以 delegation；有 Plan 的任务也不必把每个 item 都变成 Child Run。Plan 负责依赖与承诺，Delegation 负责选择执行 owner。

回到问题

发现批量 API 不受支持后，安全修订不是清空旧计划，也不是让旧步骤继续 retry。Plan owner 应：

  1. 用新证据使旧 assumption 失效；
  2. 沿依赖标记 stale/blocked item；
  3. 保留仍成立的输入和验证 evidence；
  4. 生成新的 Plan revision；
  5. 让各 execution owner 独立处理已启动工作的取消或收敛。

Plan 因而是一份可版本化、可修订的 Artifact。它告诉读者和系统“当前承诺为什么是这一版”，但不篡改已经发生的执行事实。
