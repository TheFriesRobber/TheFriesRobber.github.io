Spark 数据倾斜：如何识别、定位和治理

数据倾斜不是简单的“任务慢”，而是数据在 partition 间分布失衡。本文从 Spark UI、key 分布和执行计划出发，梳理 join 与聚合倾斜的处理方法。

2020/04/16 阅读 次
SparkBigdataPerformanceShuffle

问题

一个 Spark job 大部分 task 很快结束，最后几个 task 却运行很久；某个 executor 持续 spill、GC，甚至 OOM。增加 executor 数量、调大 memory 或提高 shuffle partition 数以后，问题仍然存在。

这通常不是“集群资源不够”，而是数据倾斜：需要处理的数据没有均匀分布到各个 partition，少数 task 承担了远高于平均值的工作量。

数据倾斜常见于：

  • join、groupBy、reduceByKey 等按 key 重新分区的操作。
  • 大量 null、空字符串、默认值或异常 key 被归到同一个 partition。
  • 少数热门用户、商品或租户贡献了大部分数据。
  • join 关系不是预期的一对一，而是局部多对多，产生数据膨胀。

先区分几个相似问题

不是所有 task 长尾都是数据倾斜。

Partition 数量不足

如果所有 task 都很大、运行时间接近，只是并行度不够，更像 partition 数量不足。增加合理的并行度可能有效。

输入文件不均匀

如果倾斜发生在读取阶段，可能是少数文件特别大、文件不可切分，或数据源本身的 partition 不均匀。这与 shuffle 之后按 key 聚合产生的倾斜不同。

Executor 或节点异常

如果相似大小的 task 只在特定节点上变慢，应先检查节点、磁盘、网络和 executor 状态。数据倾斜通常表现为某些 task 的输入记录数或 shuffle read 明显更高，而不只是运行位置不同。

数据倾斜

如果同一 stage 中大多数 task 很快完成，少数 task 的 input、shuffle read、spill 或 records 数量高出一个数量级，才应该优先怀疑数据倾斜。

如何定位

1. 从 Spark UI 找到倾斜的 stage

先看 stage 的 task 指标分布，而不是只看平均值。重点关注：

  • Duration 的中位数、最大值和长尾。
  • Input Size / Records。
  • Shuffle Read Size / Records。
  • Shuffle Write Size / Records。
  • Memory Bytes Spilled 和 Disk Bytes Spilled。
  • GC Time、Peak Execution Memory 和失败重试次数。

如果最大值远高于中位数，继续查看最慢 task 的 partition id、executor 和输入规模。倾斜的核心证据是工作量不均匀，而不只是 task 时间不同。

2. 找到产生 shuffle 的算子

在 SQL/DataFrame 作业中，可以查看执行计划：

df.explain("formatted")

重点看 Exchange 前后的 join、aggregation、distinct、window 等节点。对于 RDD，可以通过 toDebugString 查看依赖关系，并关注 join、groupByKey、reduceByKey、repartition 等会产生 shuffle 的 transformation。

3. 检查 key 分布

对可疑 key 做频次统计，并查看头部 key 占总量的比例：

import org.apache.spark.sql.functions._

df.groupBy($"key")
  .count()
  .orderBy(desc("count"))
  .limit(20)
  .show(false)

这段诊断本身也会触发 shuffle，大表上可以先采样或限制输入范围。除了 top key，还要单独检查：

  • null、空字符串和默认值。
  • 不符合业务约束的 key。
  • join 两侧同一 key 的记录数。
  • hot key 是否随日期、租户或流量事件变化。

如果 join 两侧某个 key 分别有 m 和 n 条记录，结果可能产生 m × n 条。很多所谓“join 倾斜”其实首先是 join grain 或数据唯一性出了问题。

治理顺序

1. 先修复数据语义

不要一开始就加盐。先回答：这个 hot key 是否应该存在？

  • null 或默认值不需要参与 join 时，提前过滤。
  • 不同业务含义被压成同一个默认 key 时，恢复正确的数据模型。
  • 维表 key 本应唯一时，先去重或修复上游约束。
  • join 前只保留必要的列和行，降低 shuffle 数据量。

这类修复同时改善正确性和性能，通常比参数调优更根本。

2. 小表使用 broadcast join

如果 join 的一侧足够小，可以把它广播到 executor，避免大表按 join key shuffle：

import org.apache.spark.sql.functions.broadcast

val result = facts.join(broadcast(dim), Seq("key"), "left")

Broadcast 的前提是小表能安全放入每个 executor 的内存。不要因为统计信息错误而强制广播一个实际很大的数据集。

3. Join 前先聚合或裁剪

如果下游只需要某个 key 的汇总结果，应在 join 前完成可下推的过滤和聚合。把十亿条明细先 join，再聚合成一百万行，通常不如先聚合再 join。

这一步需要确认语义等价，特别是去重、非等值 join 和多对多关系。

4. 单独处理 hot key

当只有少数已知 key 倾斜时，可以把它们拆成单独分支：

val hotKeys = Seq("unknown", "anonymous")

val isHot = coalesce($"key".isin(hotKeys: _*), lit(false))
val hot = df.filter(isHot)
val normal = df.filter(not(isHot))

普通数据继续走原计划，hot key 根据业务语义选择过滤、单独聚合、广播或专门的 join 方案。相比给全量数据加盐，这种方式影响范围更小，也更容易验证。

5. 对 skewed join 加盐

当大表中的 hot key 必须参与 join，且另一侧不能直接整体 broadcast 时，可以把一个 hot key 拆到多个 salt bucket。大表按稳定字段分配 salt，小表对应记录复制到所有 bucket。下面的 hotFacts 和 hotDim 分别表示事实表与维表中已经筛出的热点 key 分支：

import org.apache.spark.sql.functions._

val buckets = 16

val saltedFacts = hotFacts.withColumn(
  "salt",
  pmod(xxhash64($"event_id"), lit(buckets)).cast("int")
)

val expandedDim = hotDim.withColumn(
  "salt",
  explode(sequence(lit(0), lit(buckets - 1)))
)

val result = saltedFacts.join(expandedDim, Seq("key", "salt"))

Salt bucket 不是越多越好。它会复制另一侧数据、增加记录数和调度开销。应根据 hot key 的数据量、目标 partition 大小和 executor 并行度选择，并只对确实倾斜的 key 使用。

6. 对聚合做两阶段聚合

对于满足结合律和交换律的聚合，可以先按 (key, salt) 局部聚合，再去掉 salt 做第二次聚合：

val partial = input
  .withColumn("salt", pmod(xxhash64($"event_id"), lit(16)))
  .groupBy($"key", $"salt")
  .agg(sum($"amount").as("partial_amount"))

val result = partial
  .groupBy($"key")
  .agg(sum($"partial_amount").as("amount"))

sum、count、min、max 比较容易拆分。avg 需要分别保存 sum 和 count；精确 distinct、分位数和顺序相关计算不能简单套用同样方法。

7. 使用 AQE 处理运行时 skew join

在支持 Adaptive Query Execution 的 Spark SQL/DataFrame 作业中，可以让 Spark 根据运行时 shuffle 统计识别并拆分 skewed partition：

spark.sql.adaptive.enabled=true
spark.sql.adaptive.skewJoin.enabled=true
spark.sql.adaptive.skewJoin.skewedPartitionFactor
spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes

不同版本的默认值和适用 join 策略可能变化，应以当前部署版本为准。AQE 能缓解运行时 partition 倾斜，但不能修复错误的 join grain、异常 key 或数据膨胀。更完整的说明见 Spark Adaptive Query Execution 简记。

为什么只增加 partition 往往没用

在典型的按 key 进行 hash shuffle 的场景里，同一个 key 的记录会进入同一个 partition。即使把 partition 数从 200 调到 2000，一个占据 30% 数据量的 hot key 仍然只能落入其中一个 partition。

增加 partition 可以减小普通 partition，却不会拆开单个 hot key。它可能让中位数 task 更快，但最慢 task 几乎不变，反而增加调度和小文件开销。

如何验证治理有效

不要只比较 job 总耗时。至少检查：

  1. 同一 stage 的 task duration、shuffle read 和 spill 的最大值与中位数差距是否缩小。
  2. 最慢 task 是否不再长期拖住整个 stage。
  3. 加盐或拆分后是否引入额外数据膨胀。
  4. 结果行数、聚合值和 join 语义是否与基线一致。
  5. 方案在不同日期、租户和流量峰值下是否仍然稳定。

性能优化不能以结果正确性为代价。特别是加盐、预聚合和 hot key 分支，都应该用可重复的数据集做结果对账。

回到问题

处理 Spark 数据倾斜的关键不是先调参数，而是先找出哪个 stage、哪个 shuffle 边界、哪些 key造成了不均匀。

一个比较稳妥的顺序是：

  1. 用 Spark UI 证明存在 partition 级别的工作量差异。
  2. 通过执行计划找到产生倾斜的 join 或 aggregation。
  3. 检查 key 分布和业务 grain，优先修复数据问题。
  4. 再选择 broadcast、预聚合、hot key 分流、加盐或 AQE。
  5. 同时验证性能和结果正确性。

数据倾斜本质上是数据分布和计算边界共同造成的问题。只有理解数据为什么集中到少数 partition，才能选择不会把复杂度转移到别处的方案。
