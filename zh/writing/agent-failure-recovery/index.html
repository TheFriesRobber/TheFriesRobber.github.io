谁拥有失败状态，谁决定恢复动作

按 Model、Tool、Plan 与 Service 的失败所有者选择 retry、fallback、repair、reconcile 或 replan。

问题

同一次 Agent Run 先遇到模型限流，随后 write_note timeout，最后发现计划依赖的 API 已经不支持批量写入。三个错误都进入统一 retry middleware，每个最多重试三次。

结果是：模型限流继续消耗同一路由的 retry budget 和时间，并可能加剧限流；结果未知的写入被重复执行；已经失效的计划仍按原前提继续。统一 retry 看起来简单，却把三个不同 owner 的失败压成了函数异常。

先问谁能判断结果

恢复动作应由能够判断结果、并拥有修复状态的边界决定：

失败事实 owner可能动作
模型请求限流model boundary / host routerwait、fallback、stop
Tool 参数无效Tool contractrepair arguments
Tool effect 结果未知external systemquery、reconcile
计划前提失效Plan Artifactreplan
下游服务暂时不可用service/runtime boundaryretry、defer、degrade

这里的 Plan owner 管理带 revision、assumption 和 dependency 的可信计划状态，不是模型临时生成的一段文本。

Runtime 可以协调这些动作，却不应假装自己拥有所有事实。尤其是外部副作用，promise reject 只说明本地没有拿到正常响应，不能证明业务动作失败。

Retry 只是恢复动作之一

恢复动作的语义并不相同：

  • retry：在相同 contract 下创建新的 Attempt；
  • fallback：换到另一个仍兼容的实现或模型；
  • repair：修改模型可控的输入，再提出新 proposal；
  • query/reconcile：读取外部事实，让 unknown outcome 收敛；
  • replan：前提变化后修订 Plan；
  • stop：证据不足或风险过高时，保留失败并退出。

选择 retry 前至少要满足：失败发生在可重试边界、当前动作允许产生新 Attempt、预算仍允许、重试不会掩盖未知副作用。

对 write_note timeout，正确动作首先是 query/reconcile；对 schema validation error，模型可以 repair；对 API 能力变化，再多次调用旧方案也不会成功，只能 replan。

Fallback 不能越过失败边界

模型限流可能允许 fallback，但仍要重新检查备用模型的能力、policy 和 Context compatibility。Tool 已经执行后，切换模型不能把 effect 状态重置。

同样，服务降级也不能悄悄降低安全 contract。例如主写入接口不可用时，不能退化成“先写本地文件、以后再说”，除非本地文件本来就是被授权的 durable owner，并且后续交付责任明确。

Fallback 的判断标准不是“有没有另一个实现”，而是“另一个实现是否能保持当前 operation 的语义和责任”。

Retry budget 要跨层共享

如果模型层、Tool 层、HTTP client 和 Queue 各自重试三次，一次用户请求可能产生远多于三次的物理 Attempt。

更合理的 budget 需要沿调用链传播：

run recovery budget
├── model attempts
├── tool attempts
└── service attempts

每次恢复动作记录消耗原因、failure owner 和 operation ID。这样，系统可以在“继续尝试”与“保留剩余预算给更有价值的 fallback”之间做决定。

Budget 不是固定次数的代名词。高风险写入可能一次 unknown 就停止；可重复的只读查询可以允许更多 Attempt；计划前提失效则不应消耗 retry budget，而应进入 replan。

用同一 Run 走完恢复决策

回到开场：

  1. 模型限流发生在生成前，Router 判断备用模型满足能力和 policy，于是 fallback；
  2. write_note timeout，Runtime 记录 outcome: unknown，通过 effect reference 查询；
  3. 外部系统确认 note 已创建，原 operation 收敛为 succeeded，不产生重复 Attempt；
  4. 后续步骤发现批量 API 不再支持，Plan owner 标记相关前提失效并生成新 revision；
  5. Run 继续执行仍有效的计划项，而不是重试旧调用。

Pi 当前有 model/tool error 与 host-injected model boundary，但没有提供完整的跨层 recovery policy。其 Agent Loop 可参考 agent-loop.ts。本文的 failure owner、budget 和动作选择是宿主设计。

回到问题

模型限流、Tool timeout 和计划前提失效不能共享一种 retry，因为它们的结果判断与修复状态分别属于不同 owner。

一个可用的恢复决策顺序是：

  1. 定位 failure owner；
  2. 判断已知 outcome，保留 unknown；
  3. 选择 retry、fallback、repair、reconcile、replan 或 stop；
  4. 检查 operation identity、side-effect boundary 和剩余 budget；
  5. 记录新 Attempt 或新 Plan revision，而不是覆盖历史。

恢复系统的目标不是“最终尽量成功”，而是在不篡改事实、不重复副作用的前提下选择下一步。成功率只有和正确的 failure grain 放在一起，才有意义。
