Agent Memory 一：RAG 为什么替代不了 Memory

2026/07/12 阅读 次
AgentMemoryData Governance

问题

6 月 1 日，用户告诉 Agent：“以后尽量把评审安排在上午。”系统把这句话做成 embedding。7 月 10 日，用户又明确更正：“以后都改到下午。”

下一次安排评审时，vector search 同时找回两条高度相关的历史消息：

0.93  以后尽量把评审安排在上午
0.91  以后都改到下午

提高 top_k 只会更稳定地返回矛盾。提高相似度阈值还可能删掉较新的正确表达。Retrieval 能回答“哪些历史文本与查询相似”，却没有回答“哪条用户偏好当前有效”。

这就是 RAG 与长期 Memory 的分界：RAG 负责找证据，Memory 还要维护会被更正、撤销和过期的状态。

历史证据不等于当前事实

两条消息都真实发生过，因此都应留在 conversation history。可当前 Task 不能同时采用“上午”和“下午”。如果系统把历史文本直接当作 Memory record，就会混淆三个问题：

问题需要的对象
用户曾经说过什么Source event / raw history
哪条信息值得跨 Session 保留Memory write decision
当前应该采用哪个版本Versioned record 的 current view

Current view 不是删除历史，而是一个派生结果：在当前授权、时间和版本规则下，哪些 record 仍然生效。需要解释或重新判断时，系统仍能沿 source reference 回到原始表达。

最小 Memory pipeline

一个可治理的流程至少需要下面几步：

source event
  → memory candidate
  → write gate
  → versioned memory record
  → current view
  → retrieval candidate
  → Context Assembly

模型或规则可以从对话中提出 candidate，但 candidate 还不是长期事实。Write gate 判断它是否足够持久、与当前用户有关、未来有用、来源明确且允许保存。通过后才生成带 owner、source 和 version 的 Memory record。

Retrieval 也不是最后的决策者。它从 current view 中找回候选，Context Assembly 再结合当前 Task 的指令、权限和其他来源决定是否采用。这样，Memory 不会因为“被搜到”就自动升级成当前 instruction。

把上午改成下午

第一次写入可以形成：

memory_id: meeting_time_preference
version: 1
value: morning
source_ref: message_61
status: superseded

7 月 10 日的明确更正形成新版本：

memory_id: meeting_time_preference
version: 2
value: afternoon
source_ref: message_82
status: current
supersedes: 1

下一次查询时，raw history 仍包含两条消息，但 current view 只暴露 v2。若用户问“我以前是不是偏好上午”，系统可以读取 history；若当前任务是安排下周评审，retrieval 应从 v2 开始。

如果用户说的是“这两周先改到下午”，它可能是一条有有效期的例外，而不是永久 supersede。适用范围不清楚时，系统应先确认，不能让 Memory writer 把临时 Context 决定改成长久事实。

Memory 类型不能共享一个 owner

“Memory”常被用来统称不同对象：用户长期偏好、当前 Task 状态、一次 Run 的 working state、Agent 的固定 persona。它们可以使用相似存储技术，却不应共享更新规则。

用户偏好由用户表达和受控 writer 更新；Task state 由应用 owner 收敛；Run working state 属于 Runtime；persona 则来自版本化配置。把它们都写进一个 vector index，会让一次相似度查询同时决定用户事实、执行状态和系统行为。

本文只建立长期用户 Memory 的最小边界。具体什么值得写、不同 writer 能改什么、版本怎样并发更新，以及怎样 ranking，分别需要后续决策。

存储形态不是语义契约

Memory 可以落在文件、关系数据库、文档库或搜索索引中。Anthropic 的 Memory Tool 也明确由应用执行 client-side 文件操作，实际数据仍存储在应用控制的基础设施里。这个接口说明“模型可以请求读写”，并不替应用定义版本、授权和 current view。

同样，向量数据库可以成为 candidate index，却不应成为唯一事实源。Embedding model 或索引变更后，candidate 可以重建；source、version 和撤销关系不能只存在于向量 metadata 中。

回到问题

开场中的旧偏好不是检索失败：系统确实找到了相关历史。错误在于把相关历史直接当成当前事实。

Agent Memory 需要在 source event 之上增加 write gate、versioned record 和 current view，再把当前有效内容交给 retrieval 与 Context Assembly。这样，“上午”仍是可追溯历史，“下午”才是当前偏好；系统既没有抹掉来源，也不会让更相似的旧句子重新生效。

后续问题

  • 什么信息值得跨 Session 写入长期 Memory。
  • 不同 Memory writer 应拥有怎样的 mutation 权限。
  • 用户更正、撤销与并发编辑怎样形成新版本。
  • Current view 之后怎样做 keyword、vector、hybrid retrieval 与 reranking。
