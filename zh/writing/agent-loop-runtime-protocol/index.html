为什么 while 循环还不是 Agent Runtime

2026/07/15
AgentRuntimeSystems Design

问题

最小的 Agent Loop 通常是这样写的：

while True:
    response = model.generate(messages, tools)
    if response.tool_calls:
        messages.extend(execute(response.tool_calls))
    else:
        return response.text

模型提出 Tool Call，Runtime 执行，再把结果交回模型。模型不再调用 Tool 时，循环结束。

在 Demo 里，这段代码完全够用。假设用户说：“查一下北京明天的天气，并写进我的笔记。”模型先调用 get_weather，再调用 write_note，最后告诉用户已经完成。每一步都成功时，整个过程确实像一个 while 循环。

真正的问题不是它不能运行，而是它只描述了 happy path。只要一次 Tool 调用的结果不再明确，这个循环就不知道任务实际上进行到了哪里。

一次 Timeout 就会破坏这个模型

继续使用写笔记的例子。

write_note 已经把内容保存成功，但返回响应时网络中断了。Runtime 最终只收到一个 timeout：

try:
    result = await write_note(content)
except TimeoutError:
    # 接下来应该做什么？
    ...

站在 Runtime 的角度，至少有三种可能：

  1. 请求根本没有到达笔记服务。
  2. 请求到达了，但写入失败。
  3. 写入已经成功，只是响应丢失。

同一个 timeout 观察可能对应三种不同结果。此时简单循环只能做几个都不可靠的选择。

如果把 timeout 当成失败并让模型重试，用户可能得到两份相同笔记；如果假装成功，可能告诉用户一个并不存在的结果；如果直接结束，当前执行路径就没有确认任务是否完成。没有结果查询或对账机制时，用户和 Runtime 都无法得知最终结果。

问题的根源不是缺少一次 try/except，而是这段 Loop 把两件不同的事混在了一起：

  • 当前函数有没有拿到返回值。
  • 外部世界有没有产生副作用。

函数返回失败，不等于外部操作失败。对只读查询，这个区别可能只是多一次请求；对写文件、发邮件或创建订单，它会直接改变用户能看到的结果。

为什么一条 Tool error 不够

要理解简单 Loop 为什么无法处理这个 timeout，需要先分清三层事实：

模型：提出调用 write_note
Runtime：发出了调用，但没有收到确定响应
笔记服务：可能已经创建 note_42

模型只能提出下一步，Runtime 只能确认自己是否拿到了响应，真正的写入结果由笔记服务掌握。正常返回时，这三层可以合并成一条 Tool Result；发生 timeout 后，它们却不再一致。

如果 Runtime 只向 messages 追加一条错误：

Tool error: request timed out

下一轮模型看到的只是“调用报错”，很自然会再次调用 write_note。但这条消息漏掉了最重要的事实：第一次写入不是已经失败，而是结果未知。

结果未知是一种需要继续处理的执行状态，不是一句自然语言错误。Runtime 至少需要记住这是哪一次写入、是否拿到过 note_id，以及下一步应该确认原来的结果还是重新执行。否则，进程一旦重启，只恢复 messages，这些信息就会全部丢失。

这也是问题从 timeout 走向 retry 的地方：在不知道第一次是否成功时，“再调用一次”到底意味着什么？

Retry 之前，先分清“再试一次”和“再做一次”

用户只要求创建一份笔记。第一次调用 timeout 后，Runtime 想要 retry，看起来很自然。但它必须先回答一个问题：这次 retry 是继续完成第一次写入，还是发起第二次写入？

假设第一次调用其实已经创建了 note_42，只是响应在返回途中丢失。如果 Runtime 把 retry 当成一个全新的创建请求，结果会是：

用户意图：创建一份笔记

第一次调用 → 已创建 note_42，但 Runtime 只看到 timeout
第二次调用 → 又创建 note_43，并返回成功

第二次调用本身成功了，用户却得到了两份笔记。问题不在于 retry 失败，而在于系统把同一个用户意图执行了两次。

要避免这种情况，笔记服务需要能够认出：“这两次请求是在尝试完成同一个写入。”常见做法是给这个逻辑动作分配一个稳定的 idempotency key，也就是同一动作多次尝试时始终不变的标识：

第一次尝试（operation_7）→ 创建 note_42，响应丢失
第二次尝试（operation_7）→ 识别为同一动作，返回已有的 note_42

这要求下游服务支持幂等处理，也要求 Runtime 在 timeout 后仍然记得 operation_7。如果进程重启后只恢复聊天记录，Runtime 就可能生成一个新的标识，把 retry 再次变成新的写入。

所以 retry 不是简单地“失败后再调用一次”。它依赖两个前提：系统能识别哪些尝试属于同一个逻辑动作，并且能在结果未知或进程重启后保留这个身份。否则，retry 只会把一次不确定的执行变成多次可能重复的执行。

Runtime 最少需要补上什么

到这里不需要立刻设计一套庞大的 Schema。这个例子只要求 Runtime 不再把一个逻辑动作、一次调用和最终结果当成同一件事。

对于“创建一份笔记”这个目标，Runtime 需要保留三层关系：

逻辑动作：创建一份笔记（operation_7）
执行尝试：attempt 1 timeout，attempt 2 返回成功
确认结果：note_42 已创建

一个逻辑动作可以有多次执行尝试，但只能收敛到一个确认结果。这样，timeout 后的 retry 才是在继续 operation_7，而不是悄悄创建一个新动作。

这些信息最终可以保存在状态表、event log 或 workflow engine 中，具体形式取决于系统规模。关键不是先选哪种基础设施，而是让结果未知时的状态能够跨过当前函数调用，必要时也能跨过进程重启。

因此，while 循环仍然可以负责控制流；Runtime 补上的是循环之外的执行事实。

回到问题

while 循环没有错。它准确表达了 Agent 的控制流：模型决定下一步，Runtime 执行，再回到模型。

它缺少的是失败后的事实边界。

当一次 Tool timeout 可能同时意味着“没有执行”“执行失败”或“执行成功但响应丢失”时，Runtime 不能再用一条错误消息代替真实状态，也不能让模型猜测外部世界发生了什么。

从这一刻开始，Agent Loop 才不再只是一个 while 循环。它需要由 Runtime 明确区分逻辑动作、执行尝试、已确认事实和未决结果。
