Agent 38：Context Assembly 评测不能只看 Recall

用 required information、citation、pollution、conflict 与 budget efficiency 验证一次 Context 投影。

2026/07/24 更新于 2026/07/27 阅读 次
Agent VerificationAgentEvaluationContext Engineering

问题

下面用一个构造例子。用户刚刚纠正：“以后把周报发到项目频道，不再发私信。”Context pipeline 成功检索到这条消息，retrieval recall 因而是满的；但旧 Memory 仍写着“周报发私信”，并且被排在纠正消息之后。预算不足时，当前纠正还被 compression 裁掉了。

模型最终选择私信。检索系统确实“找到了相关内容”，最终 Context 却是错的。

Retrieval 只产生候选集合。一次真正交给模型的 Context 还经过 selection、冲突处理、ordering、compression、permission 和 provider shaping。Context Eval 的对象应是这次带 provenance 的投影，而不是“向量检索返回过什么”。

把 Pipeline 的可观察对象分开

一次 Context Assembly 可以表达为：

source records
  → retrieval candidates
  → assembly decisions
  → AgentMessage projection
  → provider-shaped messages
  → model response

每层回答不同问题：

层级可观察对象典型失败
SourceHistory、Memory、Tool Result、文件及版本源事实已经过期或无权限
Retrieval候选项与 scorerequired item 未召回
Assemblyinclude/drop/override/compress 决策冲突处理错误
Projection带 provenance 的模型输入预算污染、关键约束缺失
Provider shaping实际发送的 messagesadapter 丢字段或改变顺序
Response模型输出有正确 Context 仍推理失败

只检查最终回答会把模型行为归罪给 Context；只检查 retrieval candidates 又会漏掉 assembly 之后发生的错误。因此，每个 Eval case 应固定要验证的层级。

Case 先声明 Required、Distractor、Conflict 与 Unsafe

开场 case 可以把输入 fixture 分类：

required:
  - id: user_correction_v2
    fact: delivery_channel = project_channel
    source: current_user_message
distractor:
  - id: unrelated_meeting_note
conflicting:
  - id: preference_v1
    fact: delivery_channel = direct_message
    source: memory
    superseded_by: user_correction_v2
unsafe:
  - id: other_tenant_preference

这些标签不是模型可见的答案，而是 grader contract。它们让系统能够分别判断：

  • required information 是否进入最终投影；
  • distractor 是否不必要地消耗预算；
  • conflicting item 是否被正确标记、降权或排除；
  • unsafe item 是否在权限边界前被拒绝。

同一 source item 在不同 case 中可能角色不同。旧历史如果仍是当前事实，就不是 distractor；分类必须由 case 目标、时间和 policy 共同决定。

Coverage 要测最终投影，不只测候选集合

Retrieval recall 可以定义为：

被召回的 required items / 全部 required items

但 Context coverage 应针对真正交给模型的投影：

在 provider-shaped Context 中仍可用的 required facts
/ 全部 required facts

“仍可用”不仅是字符串存在。若压缩把“不要发私信”改成“讨论周报发送方式”，关键否定语义已经丢失；若 source 被拼接进不可见 metadata，也不能算模型获得了事实。

因此，coverage grader 可以组合：

  • 确定性检查 item identity 或 provenance；
  • 规则检查结构化 constraint 是否保留；
  • 对无法稳定编码的摘要等价性使用经过校准的语义 grader。

选择 grader 的原则不改变 Context 指标本身。

Provenance 与 Citation 要验证“事实来自哪里”

模型得到正确答案，不代表来源正确。它可能碰巧依赖参数记忆，或引用了已过期的 Memory。

一次 projection 应保留 source identity、revision、时间、权限域和 transformation lineage：

context_item_9
  ← user_message_22
  ← transformed_by compression@5
  ← included_by assembly_policy@8

如果产品要求输出 citation，可以分别评测：

citation coverage
= 有所需 citation 的 claims / 全部必须引用的 claims

citation correctness
= 指向支持该 claim 的 citations / 全部实际 citations

分母必须说明是 claim 还是 citation。一个 claim 带了 citation，却指向不支持它的 source，coverage 可能通过，correctness 仍应失败。

Pollution 关注错误加入，而不只是遗漏

Context failure 至少有三类：

missing: required item 没有进入
pollution: 无关或有害 item 被加入
override: 较弱或过期事实覆盖了权威事实

Pollution rate 可以按投影项计算：

被判定为 distractor 的 included items
/ 全部 included items

也可以按 token 计算污染预算，但必须使用实际 tokenizer 或明确估算方法，并写出分母是最终 Context token。项数和 token 比例回答不同问题：一个很长的 distractor 可能只占一项，却吞掉大部分预算。

Unsafe 或越权内容不应被一个较低 pollution percentage 稀释。它通常是独立 hard failure：

包含至少一个 unauthorized item 的 projections
/ 全部 evaluated projections

权限检查应发生在内容进入模型之前；不能因为最终回答没有复述秘密，就把越权投影判为安全。

冲突处理需要明确优先关系

面对 preference_v1=direct_message 与 user_correction_v2=project_channel，pipeline 不能只按 similarity score 或最新插入时间排序。Case 应提供可验证的 precedence：

当前用户明确纠正
  supersedes
同一主体的旧偏好 Memory

Grader 可以检查：

  • 冲突是否被识别；
  • authoritative item 是否进入；
  • superseded item 是否被删除或显式标记；
  • projection 中是否仍存在未解决的双重指令；
  • budget 降级是否错误保护了旧值。

当 policy 无法决定哪个 source 更权威时，正确结果可能是保留冲突并要求澄清，而不是强行选一个值。unknown 是合法结论。

Budget Efficiency 必须与价值一起定义

“Context 越短越好”不是完整指标。删除所有信息当然节省 token，却无法完成任务。

可以先记录：

required facts preserved / final Context tokens
distractor tokens / final Context tokens
final Context tokens / configured Context budget

这些比例适合诊断，但不能单独作为 Task gate。更有意义的比较是在相同 case、相同 model configuration 下，观察两个 assembly configuration 是否都守住 required information、权限和 conflict contract，再比较预算使用。

所有 token 数都要说明 tokenizer 或计数方法。本文不提供任何“最佳比例”；不同任务的最小充分 Context 不同。

预算不足时，降级顺序本身也应成为测试对象。例如：

先保护：当前任务约束、未解决 Tool Result、权威纠正
再压缩：已被后续消息覆盖的历史
最后丢弃：无关候选

如果 pipeline 反过来先删当前纠正，即使总 token 没超限，Context contract 仍然失败。

五类 Regression Case 覆盖不同决策

一个可维护的 Context suite 可以包含：

Case注入条件预期证据
Required missing关键事实接近 retrieval 边界最终投影仍包含该事实
Distractor pollution高相似但无关片段无关项被 drop 或不挤占关键预算
Stale conflict旧 Memory 与当前纠正冲突当前纠正胜出或触发澄清
Permission violation其他 tenant 的高相关内容进入模型前被拒绝
Budget degradation输入超过配置预算按结构化顺序压缩并保留约束

每个 case 都应保存 source fixture、assembly configuration、provider-shaped Context fingerprint 和 grader version。否则 pipeline 更新后无法判断是 retrieval、assembly 还是 adapter 发生了变化。

满分 Recall 仍可能得到失败 Context

对开场构造例子，可以得到：

retrieval:
  required_items_found: 1/1
projection:
  required_facts_preserved: 0/1
  stale_conflicts_included: 1
  authoritative_conflict_winner: fail
  unauthorized_items: 0
budget:
  within_limit: true
  degradation_order: fail
context_outcome: fail

Retrieval recall 是 1/1，Context outcome 仍失败，因为 required fact 在最终投影中丢失，旧 Memory 还错误赢得冲突。模型选择私信可能受这份 Context 影响，但最终 response failure 仍需单独评测，不能仅凭相关性把全部责任归给 assembly。

回到问题

检索系统找到所有相关片段，只能证明 candidate retrieval 没漏掉 required item，不能证明模型最终看到的 Context 正确。

Context Eval 要沿 source、retrieval、assembly、projection 和 provider shaping 固定可观察对象，再分别验证 required coverage、provenance、citation、pollution、conflict、permission 与 budget degradation。遗漏、错误加入和错误覆盖是三种不同 failure。

开场中高 recall 仍失败，正是因为评测对象不该停在“找到了什么”，而应落到“这一轮在什么来源、权限、冲突和预算决策下，真正把什么交给了模型”。
