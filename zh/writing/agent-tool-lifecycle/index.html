Tool Lifecycle 不只是函数调用

2026/07/15
AgentToolsRuntime

问题

Agent Tool 经常被描述成“一个带 JSON Schema 的函数”：模型生成参数，Runtime 调用函数，再把返回值交回模型。

Tool definition → Model arguments → Handler → Tool Result

这个模型很适合演示 function calling。假设用户说“把报告保存到项目目录”，模型调用：

{
  "name": "write_file",
  "arguments": {
    "path": "/project/report.md",
    "content": "..."
  }
}

即使 handler 本身没有 bug，这次调用仍可能在其他位置出错：当前用户其实不能写这个目录；模型看到的是旧版 Tool definition；文件已经写入，但 Runtime 只收到 timeout；handler 返回了完整文件对象，下一个 Model Turn 却看不出写入是否成功。

这些问题无法只在函数体里解决，因为它们分别发生在模型看到 Tool 之前、执行动作之前、外部副作用发生时和结果回到模型之后。

所以 Tool Lifecycle 的意义不是罗列更多阶段，而是让同一个逻辑动作穿过这些边界时，身份、权限和结果不会断开。

Tool 已注册，不代表模型现在应该看见它

Registry 回答“系统里有哪些能力”，当前 Tool surface 回答“这个 Model Turn 可以使用哪些能力”。两者不是同一个集合。

write_file 已注册，仍可能因为当前用户只有读取权限、项目 workspace 尚未挂载，或当前 Model Turn 只允许分析而不能修改，而不应进入模型输入。

registered tools
      ↓  identity、permission、environment
allowed tools
      ↓  eager、deferred、on-demand
current model surface

这里必须先算 allowed set，再考虑哪些 Tool 常驻、延迟加载或按需发现。否则，一个未授权 Tool 即使最终没有执行，它的名称、description 和资源类型也可能已经暴露给模型。

Tool surface 的选择策略已在 Agent Tool Surface：Eager、Deferred 与按需加载 中单独讨论。对 Lifecycle 来说，关键只是保留这次调用使用了哪个 definition，以及它为什么出现在当前 surface。

Model arguments 只是执行提案

模型生成的 path 和 content 表达它想怎样完成任务，但不能同时决定这次动作代表哪个用户、属于哪个 tenant，或者是否已经得到写权限。

一次可信执行包含三类来源不同的信息：

信息来源例子
Model arguments模型根据任务生成path、content
Runtime context认证与 policy 层注入subject、actor、tenant、deadline
Backend state资源 owner 维护文件版本、目录权限、当前 lease

只有第一类应该由模型填写。把 tenant_id 或 authorization scope 放进 Tool Schema，相当于让不可信输入声明自己的权限。

因此，handler 的概念接口更接近：

type ToolHandler<Args, Result> = (
  args: Args,
  context: TrustedToolContext,
  signal: AbortSignal,
) => Promise<Result>

args 表达模型提案，context 提供可信身份与执行边界，signal 传递 deadline 或 cancellation。它们在函数入口汇合，但不能因此失去各自来源。

Schema 合法，不代表这个动作可以执行

JSON Schema 可以确认 path 是字符串、content 没有超过长度限制，却无法证明当前用户有权修改 /project/report.md，也无法知道文件版本是否在模型读取后已经变化。

执行前仍需由可信边界完成两类判断：

  • Runtime 使用认证得到的 subject、actor 和 tenant 做 authorization。
  • Backend 使用最新资源状态检查 owner、版本、业务约束和 transaction boundary。

这是同一个动作在不同时间点面对的不同事实，并不是重复校验。Schema 拒绝结构上不合法的参数；authorization 拒绝调用者无权进行的动作；backend 拒绝当前状态下无法成立的修改。

Tool Schema 为什么是 model-facing API，可参考 Agent Tool Schema 是面向模型的 API。

Handler 返回异常，不等于外部动作失败

如果文件服务已经保存 report.md，但响应在返回途中丢失，Runtime 最终只看到 timeout。此时再次调用可能覆盖文件、产生新版本或重复触发后续流程。

因此，一次获准执行的写操作需要稳定的 Tool Execution identity。多次 Attempt 可以属于同一个 Tool Execution，但不能因为 retry 就悄悄变成新的用户动作：

tool_execution_write_7
  ├─ attempt 1：timeout，结果未知
  └─ attempt 2：确认 file_version_12 已存在

这要求 Runtime 保留 Tool Execution identity，也要求下游在可能时提供幂等或结果查询能力。Lifecycle 在这里记录的是 succeeded、明确 failed 或 unknown，而不是把所有 exception 都解释成“没有发生”。

成功响应也不能原样塞回 Context

外部文件 API 可能返回权限列表、内部存储字段、历史版本和几 MB 内容。handler 调用成功，不代表这些数据都适合成为下一个 Model Turn 的输入。

Runtime 应把 backend response 转换成有界、可解释的 Tool Result，例如：

{
  "status": "succeeded",
  "file": {
    "path": "/project/report.md",
    "version": 12
  },
  "content_included": false
}

结果需要明确是否完整、是否截断、事实来自哪里，以及大内容应到哪个 Artifact 读取。否则模型可能把局部结果当作完整结果，或让外部数据中的文字变成新的 instruction。

Lifecycle 连接的是同一个动作

到这里，一次 write_file 已经经过了几个不同 owner：Registry 提供 definition，policy 决定是否可见，模型生成参数，Runtime 注入可信 context，backend 确认副作用，result normalizer 再决定模型看到什么。

Lifecycle 不要求把所有实现放进一个服务。它只要求这些决定仍能关联到同一个 Tool Call 和获准执行后创建的 Tool Execution：模型看到了哪个 definition、谁授权了什么动作、发生了哪些 Attempt，以及最后确认了哪个结果。

如果这些关系断开，系统只能看到“函数调用过”和“某处报错”，无法判断问题发生在 Tool 选择、参数生成、authorization、执行还是结果消费。

回到问题

Tool handler 被调用成功，只能说明执行入口走通了一次。

一个可解释的 Tool Runtime 还要保证：模型看到的是当前允许的 definition；模型参数不会伪造可信身份；Schema、authorization 与 backend state 各自检查自己掌握的事实；结果未知时不会盲目生成新动作；成功结果经过归一化后再进入下一个 Model Turn。

把这些边界连接起来，Tool 才不只是一个函数，而是一项能够被安全执行并确认结果的 Agent 能力。

后续问题

  • Tool Error 怎样向模型表达可修复原因，而不是只返回异常字符串。
  • Timeout 与 Cancellation 怎样沿调用链传播并最终收敛。
  • 并发 Tool Call 修改同一资源时怎样保证一致性。
  • Tool 安全应怎样分布在 prompt、surface、handler 与 backend。
  • 怎样分别评测 Tool 选择、参数、执行可靠性和结果消费。
