Agent Sandbox 四：Runtime 更换后怎样继续使用同一个 Workspace

拆开 Session、Runtime、Volume 与 Lease，并用统一路径契约说明 Agent 怎样在 Runtime 替换后继续工作。

2026/07/14 阅读 次
AgentSandboxDistributed Systems

问题

Agent 已经在 /workspace/project/report.md 写了半小时。执行它的 Runtime A 突然崩溃；Control Plane 启动 Runtime B 后，文件却不见了。

/workspace 原本被当作 Workspace，也就是需要跨 Runtime 保留的可编辑文件区。系统恢复了同一个 Session Context；Context 保存对话和执行上下文，却不替文件保存字节。模型知道下一步该做什么，B 也能执行命令，但 /workspace 只是 A 的容器本地文件系统：Session 被持久化了，工作文件却仍随 Runtime 一起消失。

把整个容器磁盘做成永久盘似乎可以解决问题，却会引入新的混乱：缓存和临时凭证也被长期保留；旧 Runtime 与新 Runtime 可能同时写盘；最终交付文件没有独立版本；系统甚至无法解释某个路径属于 Session、Task 还是一台机器。

持久 Workspace 的关键不是“让容器磁盘活久一点”，而是把逻辑工作区、可替换计算、物理存储与当前执行权拆开。

四种身份不能共用一个 Sandbox ID

对象它代表什么生命周期
Session一段可继续的用户交互与资源范围可跨多次 Run 和 Runtime
Runtime当前执行命令的计算进程可失败、升级和替换
Volume持久保存 Workspace 字节的存储资源可跨 Runtime
Lease某一代 Runtime 当前是否有权使用 Workspace有期限，可续约和替换

它们的关系可以写成：

Session session_12
  └─ Workspace workspace_7
       └─ Volume volume_31

Runtime A ── lease generation 41 ──> workspace_7  (expired)
Runtime B ── lease generation 42 ──> workspace_7  (current)

Session 提供逻辑连续性，Volume 提供字节连续性，Runtime 提供计算，Lease 提供当前 owner。Kubernetes 的 PersistentVolume 同样拥有独立于单个 Pod 的生命周期；Pod 替换会产生新的 UID，而不是让旧 Pod“搬到”另一台机器继续存在。

Workspace Identity 应先于 Volume Identity

应用关心的是 workspace_7，不是某个云盘或 PVC 名称。Workspace record 可以包含：

{
  "workspace_id": "workspace_7",
  "session_id": "session_12",
  "storage_binding": {
    "provider": "pvc",
    "volume_id": "volume_31",
    "binding_version": 9
  },
  "path_contract_version": 2,
  "status": "bound"
}

Volume 是当前物理实现。迁移存储、从 snapshot 恢复或复制到另一个 region 时，volume_id 可以变化，而 Workspace identity 与内部路径仍保持稳定。

反过来，不应从某个 Runtime 上出现 /workspace 目录就推断 Workspace 已绑定。Control Plane 和 Runtime 初始化探针都要验证 workspace_id、Session 及 binding version，防止空目录或错误 Volume 冒充工作区。

路径契约要区分持久、临时与交付

Agent Tool 需要稳定的文件路径，但不同路径不应共享 retention：

/workspace/                 持久工作区，跨 Runtime
  project/                  用户与 Agent 的可编辑文件
  .agent/                   可恢复的工作元数据

/tmp/agent/                 当前 Runtime 的临时空间
  downloads/
  caches/

/artifacts/                 Artifact 的只读或受控导入视图
  input/
  output/

这是虚拟文件系统（VFS）的路径契约，不要求底层一定是同一个文件系统。实现可以把 /workspace 挂载为持久 Volume，把 /tmp/agent 放在本地 ephemeral disk，再通过 Artifact gateway 将对象存储内容暴露到 /artifacts。

下面的 fencing 指在存储或写入边界强制拒绝过期 generation 的写入；它不是 Lease 字段本身自动提供的能力。

三类路径的规则应明确：

路径类型Runtime 替换后允许直接修改典型用途
persistent保留是，受 Lease / fencing 约束草稿、代码、任务中间结果
temporary丢弃是解压目录、缓存、可重建下载
artifact按 Artifact 生命周期保留通常只读；修改后导出新版本输入文件、最终交付物

如果所有文件都放进持久盘，临时秘密和无限缓存会变成 retention 风险；如果所有输出都留在 Workspace，最终交付物又缺少稳定 identity、version 与下载授权。

首次绑定必须先建立逻辑关系

新 Session 第一次需要 Workspace 时，可以按以下顺序：

1. 创建或读取 workspace_7
2. 为 workspace_7 分配 volume_31
3. 条件写入 storage binding version 9
4. 为 Runtime generation 41 取得 Lease
5. 挂载 volume_31，并在 Runtime 内验证 workspace marker
6. 初始化路径契约
7. 发布 Ready

workspace marker 可以保存 Workspace identity 与 path contract version，但它不是唯一 Source of Truth；磁盘内容可能来自旧 snapshot，marker 也可能陈旧。Runtime observation 必须与 Control Plane 当前 binding 和 Lease 一致。

如果 Volume 分配成功而 binding 写入失败，Controller 根据 allocation identity 查询并认领或回收；不能默默再分配一块盘。否则同一个 Workspace 会产生两个都看似合法的内容分支。

Runtime 替换是重挂载，不是复制 Session

A 崩溃后，恢复路径应是：

1. generation 41 的 Lease 到期或被撤销
2. generation 42 获得新的 Lease
3. Runtime B 挂载 workspace_7 当前绑定的 volume_31
4. 验证 filesystem 与 path contract
5. B 发布 Sandbox Ready
6. Run owner 再从 Checkpoint / Event Log 恢复执行状态，并继续读取 report.md

Workspace 恢复与 Agent 执行恢复是两件事。Volume 恢复文件，Sandbox owner 在挂载、路径契约和 Lease / fencing 成立后发布 Sandbox Ready；Checkpoint / Event Log 则由 Run owner 用来恢复 Run 进行到哪里、哪些外部副作用仍需 reconciliation。后者可能收敛到 resumed、继续 waiting 或 manual_recovery，不能反过来成为 Sandbox Ready 的前置条件。把模型消息记录写进 Workspace，并不能替代执行状态；把 Checkpoint 放进数据库，也不能恢复未持久化的文件字节。

旧 Runtime 失联时需要安全接管

Lease 到期只能说明 Control Plane 不再授权 A，不能证明 A 已停止。若存储允许 A 与 B 同时挂载，A 可能在网络恢复后继续写入。

安全接管需要至少一种可强制执行的 fencing：

  • 存储层支持按 generation 的写入 token；
  • 切换前由基础设施强制 detach 旧挂载；
  • 只允许单 writer attach，并确认旧 attachment 已释放；
  • 所有写入先落到隔离的 overlay 或 Blob，再由 Workspace owner 在一次原子操作中校验当前 Lease generation 与 expected base revision（这些修改所基于的 Workspace 逻辑提交版本）；只有它仍等于当前可见 revision，才推进新的可见 revision。

Kubernetes PersistentVolume 的 access mode 描述调度和挂载方式，但官方文档也提醒，它们不一定在挂载后强制写保护。不能仅从 ReadWriteOnce 这个名字推断业务上的旧 writer 已被 fence。

如果系统无法证明 A 已失去写能力，B 可以先以只读方式恢复，或进入 takeover_pending，而不是为了可用性直接开放双写。这里的选择取决于数据丢失容忍度，但必须显式。

Workspace Revision 让写入可解释

普通文件系统提供路径和字节，不自动提供 Agent 需要的逻辑提交。重要修改可以由 Workspace owner 建立 revision：

{
  "workspace_id": "workspace_7",
  "revision": 18,
  "base_revision": 17,
  "lease_generation": 42,
  "changes": [
    {"path": "project/report.md", "blob_ref": "sha256:..."}
  ]
}

若 Runtime 直接修改共享 Volume，这份 revision 只能用于追踪和发现冲突，不能充当 fencing：旧 Runtime 可能在 revision 提交前就覆盖字节。此时必须在开放 B 的读写挂载前完成存储级 fence、可靠 detach 或有强制保证的单 writer attach。

如果系统改为让 Runtime 只写隔离 overlay 或不可变 Blob，则可以在 Tool 完成、Checkpoint 或 Artifact 导出时建立一致的 revision boundary。Workspace owner 通过一次条件提交同时检查 current Lease generation 与 expected base_revision，再推进可见 revision；lease_generation 是 owner 的校验输入，不会凭字段本身证明调用方仍是当前 owner。

对于代码仓库，Git commit 可以承担一部分 revision identity；对于一般文件，Workspace service 仍要定义最小的快照或 manifest 机制。

Workspace、Memory 与控制状态不能互相替代

三类持久状态常被一起叫作“Agent memory”，但 owner 与恢复方式不同：

状态内容恢复时怎样使用
Workspace文件、代码、可编辑中间结果重挂载并验证 revision
Memory用户偏好、长期事实、检索内容按 scope 与 policy 重新读取
Control stateRun、Tool Execution、Lease、Checkpoint按状态机与 Event Log 恢复

把 run_status.json 写入 Workspace 并不能自动获得原子状态转换；让数据库保存 report.md 的路径，也不等于文件仍存在。每类状态都应保留自己的 Source of Truth，再用 identity 关联。

删除与回收也要分层

结束 Runtime 只释放计算，不一定删除 Workspace；结束 Session 也不必立刻物理擦除 Volume。回收策略可以是：

Runtime stopped
  → revoke Lease
  → detach Volume
  → Workspace enters retained
  → retention expires
  → snapshot / Artifact references checked
  → Volume deleted

若最终报告已导出为 Artifact，它可以按交付策略继续存在，而 Workspace 草稿随后被删除。反过来，删除 Artifact 下载入口也不应清空整个 Workspace。

清理失败要有持久状态与重试 owner。数据库中删除 Workspace row、却留下无人认领的 Volume，不是删除成功；它只是失去了可追踪 identity。

回到问题

Runtime A 崩溃后，Runtime B 之所以找不到 report.md，不是 Session 恢复失败，而是文件从未离开 A 的临时文件系统。

正确模型让 Session 指向稳定 Workspace，让 Workspace 绑定可替换的 Volume，让 Runtime 只承担计算，再由 Lease 与 fencing 决定当前哪一代 Runtime 可以写。B 获得新 generation 后重挂同一 Volume，验证路径契约，再结合 Checkpoint 恢复执行；A 即使恢复连接，也不能提交旧 generation 的修改。

持久化 Workspace 不是持久化整台机器。它是把应该跨 Runtime 的文件身份与不应跨 Runtime 的计算、缓存和执行权分开。

后续问题

  • Volume Pool 怎样降低首次绑定延迟，同时避免把旧内容交给新 Session。
  • Workspace 的 snapshot、clone 与跨 region 恢复应怎样建模。
  • Artifact 怎样从 Workspace revision 导出，并保留稳定 lineage。
