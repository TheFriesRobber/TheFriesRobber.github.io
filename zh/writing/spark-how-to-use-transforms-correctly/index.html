如何正确使用 Spark Transformation

Spark transformation 是延迟执行、可重算的分布式计算描述。正确使用它，需要理解 action、closure、副作用、shuffle、partition 和 cache 的边界。

SparkBigdataRDDPerformance

问题

下面这些现象在刚开始使用 Spark 时很常见：

  • 调用了 map，日志却没有立即输出。
  • 同一个 transformation 看起来执行了两次。
  • 在 map 里修改 driver 变量，action 完成后变量仍然没变。
  • 在 transformation 中写数据库或调用外部 API，偶尔出现重复写入。
  • 连续几个很简单的算子，运行时却产生了大量 shuffle 和 spill。

这些问题并不是 map 或 filter 的 API 难以理解，而是 Spark 的 transformation 不是普通的本地集合操作。它描述的是一段延迟执行、分区并行、失败后可以重算的计算。

Transformation 和 Action

RDD 操作可以分成两类：

  • Transformation：从一个 RDD 生成新的 RDD，例如 map、filter、flatMap、reduceByKey 和 join。
  • Action：真正请求结果或输出，例如 count、collect、reduce、saveAsTextFile 和 foreach。

Transformation 默认是 lazy 的：调用时只记录依赖关系，不立即处理数据。直到 action 需要结果，Spark 才根据 lineage 构建 job 和 stage。

val cleaned = input
  .filter(_.nonEmpty)
  .map(_.trim)

// 到这里通常还没有执行集群计算
val count = cleaned.count()

Lazy evaluation 让 Spark 可以把多个步骤组合起来，并且避免生成不必要的中间结果。但它也带来一个重要结论：transformation 中的代码可能不执行、执行一次，也可能因为多个 action、失败恢复或推测执行而重复执行。

Transformation 中的函数应该尽量纯净

理想的 transformation 函数应该满足：

  • 相同输入得到相同输出。
  • 不依赖可变的外部状态。
  • 不修改 driver 中的普通变量。
  • 不把外部副作用当作 exactly-once 操作。

Driver 变量不会按本地代码的方式更新

下面的写法看起来像是在统计记录数：

var records = 0L

val normalized = input.map { value =>
  records += 1
  value.trim
}

normalized.count()
println(records)

运行在 executor 上的是 closure 的序列化副本。每个 task 修改的是自己的副本，不是 driver 中的 records。local mode 下偶尔表现得“可以工作”，也不能说明 cluster mode 下语义正确。

需要计数时，优先使用 action 或明确的 aggregation。Accumulator 适合监控和诊断，但也要理解 task 重试与 lazy evaluation 对更新时机的影响，不应把它作为业务结果的唯一来源。

外部写入可能发生多次

val result = input.map { record =>
  externalClient.write(record)
  transform(record)
}

这段代码可能因为以下原因重复调用 write：

  • 同一 lineage 被多个 action 重新计算。
  • task 失败后重试。
  • executor 丢失缓存 partition 后重算。
  • 集群启用 speculative execution，同时运行同一个 task 的多个 attempt。

如果必须产生外部副作用，需要在输出系统中设计幂等 key、去重或事务边界，并根据 task attempt 语义处理重试。更常见的做法是让 transformation 只生成待写数据，再交给具有明确交付语义的输出阶段。

多个 Action 可能造成重复计算

同一个未持久化 RDD 被多个 action 使用时，Spark 可以沿 lineage 重新计算它：

val normalized = input.map(expensiveNormalize)

val count = normalized.count()
normalized.saveAsTextFile(outputPath)

expensiveNormalize 可能执行两遍。如果中间结果计算昂贵、会被重复使用，并且适合当前内存与磁盘条件，可以显式持久化：

import org.apache.spark.storage.StorageLevel

val normalized = input
  .map(expensiveNormalize)
  .persist(StorageLevel.MEMORY_AND_DISK)

val count = normalized.count() // 同时物化 cache
normalized.saveAsTextFile(outputPath)
normalized.unpersist()

不要机械地对所有中间结果调用 cache()：

  • 只使用一次的数据没有复用收益。
  • 缓存会占用 executor memory，并可能挤压 execution memory。
  • 缓存块可能被淘汰、落盘或在之后重新计算，收益可能低于重算成本。
  • 持久化级别应根据对象大小、序列化开销和重算成本选择。

Closure 会被发送到 Executor

Spark 会把 transformation 使用的函数和它捕获的变量序列化并发送给 executor。常见问题包括：

  • 无意中捕获整个外部对象 this。
  • 捕获不能序列化的连接、线程池或 client。
  • 把很大的 lookup map 随每个 task 重复发送。
  • closure 依赖只存在于 driver 本地的文件或环境。

把需要的字段复制到局部变量，可以缩小 closure。较大的只读 lookup 数据适合 broadcast：

val lookupBroadcast = sc.broadcast(lookup)

val enriched = input.map { record =>
  val lookup = lookupBroadcast.value
  enrich(record, lookup)
}

Broadcast 变量应视为只读数据。更新 driver 上的原始对象不会自动更新已经分发的 broadcast；不再使用时可以显式销毁。

窄依赖和宽依赖

Transformation 不只是数据处理函数，它还决定数据是否需要跨 partition 移动。

窄依赖

一个输出 partition 只依赖少量确定的父 partition，通常可以在同一个 stage 中 pipeline：

  • map
  • filter
  • flatMap
  • mapPartitions
  • 不触发 shuffle 的 coalesce

宽依赖

一个输出 partition 依赖多个父 partition，通常需要 shuffle，并形成 stage 边界：

  • groupByKey
  • reduceByKey
  • join
  • distinct
  • repartition
  • sortByKey

Shuffle 需要网络传输、序列化、排序和磁盘文件。正确使用 transformation，不是完全避免宽依赖，而是知道它为什么存在，并减少不必要的数据移动。

例如，对 key 做聚合时，通常优先考虑 reduceByKey 或 aggregateByKey，而不是先把所有 value 通过 groupByKey 拉到同一个 reducer 再求和：

val totals = pairs.reduceByKey(_ + _)

这类算子可以在 shuffle 前做局部 combine，降低网络数据量。但选择聚合函数时必须满足相应的结合律和类型语义。

和 Partition 相关的几个选择

map 和 mapPartitions

map 对每条记录调用一次函数；mapPartitions 对每个 partition 调用一次函数并接收 iterator。

当初始化解析器或只读辅助对象的成本很高时，可以在 mapPartitions 中每个 partition 初始化一次：

val parsed = input.mapPartitions { rows =>
  val parser = new ExpensiveParser()
  rows.map(parser.parse)
}

它可以减少初始化开销，但也会扩大单次函数的责任范围。不要借此在 executor 中长期保存不可控的全局状态；涉及连接和外部写入时，还需要明确资源关闭、重试和幂等语义。

保留已有 partitioner

对 pair RDD 只转换 value 时，mapValues 可以保留 partitioner；普通 map 通常不能保证这一点。保留正确的 partitioner 有机会避免后续不必要的 shuffle。

不过，“保留 partitioner”必须与 key 未变化这个前提一致。如果 transformation 改变了 key，就应该让 Spark 重新建立正确的 partition 分布。

coalesce 和 repartition

  • coalesce(n) 常用于减少 partition；默认不 shuffle，可能造成 partition 大小不均。
  • repartition(n) 会 shuffle，成本更高，但能重新平衡数据，也可以增加 partition。

选择它们时要看目标：减少小 task、重新平衡数据和控制输出文件数是不同问题。

如何选择 Transformation

  • 一条输入对应一条输出：map。
  • 一条输入对应零到多条输出：flatMap。
  • 只保留部分输入：filter。
  • 按 key 聚合：优先考虑带 combine 能力的 aggregation。
  • 只修改 pair RDD 的 value：考虑 mapValues。
  • 每个 partition 共享昂贵初始化：考虑 mapPartitions。

在 DataFrame/Dataset 场景中，优先使用 Spark 能理解的内置表达式。过早把逻辑封装进普通 UDF，可能让 Catalyst 无法进行 predicate pushdown、常量折叠或其他计划优化。

Lineage、Persist 和 Checkpoint

RDD 通过 lineage 重算丢失的 partition，这是 transformation 可以安全重试的重要原因。长 lineage 会增加调度复杂度和重算成本。

persist 解决的是复用与重算成本；checkpoint 解决的是截断 lineage，两者目的不同。使用 checkpoint 时需要配置可靠存储，并通过 action 触发实际计算。不要把 checkpoint 当成普通 cache，也不要认为 cache 能提供永久存储。

如何验证 transformation 用得是否正确

看执行结构

  • RDD 使用 toDebugString 查看 lineage 和 shuffle dependency。
  • DataFrame/Dataset 使用 explain("formatted") 查看逻辑与物理计划。
  • Spark UI 查看 job、stage、task、shuffle、spill 和重复计算情况。

测试 action，而不只是定义 transformation

因为 transformation 是 lazy 的，只构造 RDD 并不能证明函数真的可序列化或能在 executor 上运行。测试至少要触发一个 action：

val result = transform(sc.parallelize(input, 2)).collect().toSeq

local[2] 比 local[1] 更容易暴露并发和 partition 假设，但本地测试仍不能完整模拟 executor 丢失、task 重试和生产数据分布。对于外部副作用，还应单独验证幂等与重试行为。

检查这些信号

  • 同一段昂贵 lineage 是否因多个 action 重复执行。
  • 是否存在意外 shuffle 或 partition 数量突变。
  • task closure 是否过大或无法序列化。
  • transformation 是否依赖 driver 可变状态。
  • cache 是否真正复用，还是不断 eviction 和重算。
  • 输出系统是否能承受 task retry 带来的重复尝试。

回到问题

正确使用 Spark transformation，核心不是记住更多 API，而是接受它的执行模型：

  1. Transformation 只描述计算，action 才触发执行。
  2. Transformation 可能被重算，所以函数应尽量纯净、确定。
  3. Closure 会被序列化到 executor，不应无意捕获大对象或本地资源。
  4. 宽依赖会产生 shuffle，需要理解数据如何跨 partition 移动。
  5. Cache、partitioner 和 checkpoint 都有明确用途，不是通用优化开关。
  6. 任何依赖 exactly-once 的外部副作用，都不能只靠 transformation 本身保证。

把 transformation 看成分布式执行计划的一部分，而不是 Scala collection 的远程版本，很多“本地能跑、集群出错”的问题就会更容易解释。
