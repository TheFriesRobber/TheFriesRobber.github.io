Agent Tools 八：为什么 Tool Validation 会漂移

2026/07/14 阅读 次
AgentToolsAPI Design

问题

假设 Agent 有一个批量归档笔记的 Tool：

{
  "name": "archive_notes",
  "parameters": {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "properties": {
      "note_ids": {
        "type": "array",
        "items": {"type": "string"},
        "minItems": 1,
        "uniqueItems": true
      }
    },
    "required": ["note_ids"],
    "additionalProperties": false
  }
}

它表达的意图很简单：至少归档一条笔记，不接受未知字段，同一次 Tool Call 的 note_ids 数组也不能包含重复 ID。

Runtime A 将这份 Schema 原样交给支持相应约束的 binding；Runtime B 的 Adapter 保留 type、properties、required 与 additionalProperties，删除了不支持的 array 约束。模型在 Runtime B 返回：

{"note_ids": []}

同一份 canonical Tool definition，在一条路径上会被拒绝，在另一条路径上却可能进入 handler。如果 handler 恰好把空列表理解成“归档全部”，一次看似普通的兼容性差异就可能变成高风险副作用。

这就是 validation drift：Tool 参数在不同转换与执行路径上，实际遵循的约束不再相同。

“符合 Schema”可能指三件不同的事

Tool Call 经常被笼统描述成“已经过 Schema 校验”，但这句话可能混合了三个阶段：

  1. Provider 是否接受这份 Tool definition。
  2. 模型生成的参数是否符合 provider 实际执行的约束。
  3. Runtime 在调用 handler 前是否按 canonical contract 再次校验。

Provider 接受 Schema，不一定表示支持其中每个 keyword；非 strict 模式下，模型输出看起来像 JSON，也不表示满足 required、range 或 array 约束。部分 provider 的 strict tool mode 会对自己支持的 Schema 子集提供 conformance 保证，但这个保证仍受 mode、model 与支持子集限制。Runtime 本地校验通过，也不表示调用者有权限修改当前资源。

因此，Schema validity、authorization 和业务状态校验需要分开。本文只讨论第一到第三步之间的结构校验，不把它扩展成完整的 Tool 安全模型。

Drift 出现在一条转换链上

同一 Tool definition 通常会经过：

canonical schema
→ provider adapter
→ provider tool binding
→ model arguments
→ parser / coercion
→ runtime validator
→ handler

每一段都可能改变语义：

  • Provider 只支持 JSON Schema 的一个子集。
  • Adapter 为兼容 provider 删除、展开或重写 keyword。
  • Parser 把字符串 "3" 自动转成数字 3。
  • Validator 使用不同 draft，或把 format 只当 annotation。
  • Bridge 自动填充默认值，而另一条路径保持字段缺失。
  • Handler 使用单独维护的 DTO，已经与 Tool definition 不一致。

其中一些转换可以接受，但必须是显式契约。例如，Runtime 可以决定所有入口都允许安全的字符串到枚举规范化；它不能让这种 coercion 只在某个 provider 路径中偶然发生。

Canonical Schema 先要固定 Dialect

只保存一份没有 dialect 的 Schema，还不能成为跨 Runtime 契约。不同 JSON Schema draft 和 vocabulary 对 keyword 的解释可能不同；format 是只做 annotation，还是也执行 assertion，也需要明确。

因此 canonical binding contract 至少要固定：

schema dialect: https://json-schema.org/draft/2020-12/schema
required vocabularies: as declared by the dialect
format policy: annotation only
coercion policy: disabled
default application: runtime-defined, disabled by default

根 Schema 中的 $schema 让实现知道应该采用哪个 dialect，contract 还要固定 $schema 无法单独表达的 parser、format、coercion 与 default 规则。本文示例至少依赖 Core、Applicator 与 Validation vocabulary：properties、items 和 additionalProperties 属于 Applicator，而 type、required、minItems 与 uniqueItems 属于 Validation。某个 Runtime 不支持这份 dialect 声明的 required vocabulary 时，应在加载 Tool definition 时失败，而不是换成自己的默认 draft 继续执行。

Canonical Validator 才是统一结构校验边界

Provider-facing Schema 的作用，是约束模型生成 Tool Call。Strict mode 可以在 provider 支持的子集内给出更强的 Schema conformance；非 strict 模式或 lossy transform 则更接近生成提示。两种情况下，它都不适合作为多 provider 可信执行边界的唯一 validator，因为 Runtime 还要统一 dialect、转换和 handler 入口。

Runtime 应保留原始 canonical Schema，并在 arguments 完整后、handler 执行前按同一套规则校验：

provider says complete tool call
→ parse without hidden coercion
→ canonical validation
→ repairable error or structurally validated handler input

回到空数组例子。即使 Runtime B 的 Provider Adapter 删除了 minItems，本地 canonical validator 仍会拒绝：

{
  "status": "invalid_arguments",
  "tool": "archive_notes",
  "path": "/note_ids",
  "constraint": "minItems",
  "message": "至少需要一个 note_id"
}

这个错误可以作为下一个 Model Turn 的修复输入，但 handler 不会被调用。Provider 约束减少可能降低模型生成的 arguments 一次通过 canonical validation 的概率，却不会悄悄扩大结构校验边界。

Adapter 必须报告自己改了什么

如果转换后只保存最终 Provider Schema，系统很难判断某次失败来自模型，还是 Adapter 已经删除了约束。每次编译 Tool Surface 时，可以产出 transform report：

{
  "tool": "archive_notes",
  "canonical_revision": 7,
  "canonical_dialect": "https://json-schema.org/draft/2020-12/schema",
  "adapter_revision": 12,
  "provider_profile_revision": 4,
  "preserved": ["type", "properties", "required", "additionalProperties"],
  "dropped": ["minItems", "uniqueItems"],
  "classification": "lossy"
}

不是所有 dropped keyword 都要求拒绝 route。关键在于它是否改变可接受参数集合，以及 Runtime 是否仍在执行前可靠地实施该约束。对于影响副作用范围、数据类型或必填字段的差异，policy 可以要求 Adapter 直接返回 unsupported；对于只影响模型生成质量的提示性信息，可以允许 lossy transform，但必须可观察。

Contract test 应从样例集合开始

只比较两份 Schema 文本无法证明行为相同。更直接的方法是为每个 Tool contract 保存一组 provider-neutral cases：

[
  {"name": "one id", "args": {"note_ids": ["n1"]}, "valid": true},
  {"name": "empty", "args": {"note_ids": []}, "valid": false},
  {"name": "duplicate", "args": {"note_ids": ["n1", "n1"]}, "valid": false},
  {"name": "unknown field", "args": {"note_ids": ["n1"], "all": true}, "valid": false},
  {"name": "wrong type", "args": {"note_ids": "n1"}, "valid": false}
]

测试分成两层：

  1. Canonical validator test：所有 Runtime 必须加载同一 dialect 与 validator policy，并对这些 cases 得到相同结果；不支持该 dialect 的实现直接失败。
  2. Binding contract test：每个 Adapter 说明当前 mode 与 provider 子集提供什么保证、哪些约束被保留、拒绝或降级，并验证转换不会意外改名或漏掉 required field。

如果要调用真实模型做测试，还要把它当作生成行为 Eval，而不是确定性的 validator test。模型可能在相同 Schema 下生成不同参数；测试应统计 case × configuration × trial 的结果，不能用一次成功证明约束永远有效。

不要把默认值与 Coercion 藏在 Adapter 里

JSON Schema 把 default 定义为 annotation；它本身不要求 validator 把缺失字段补出来。某些 SDK 或 DTO layer 会额外填充默认值，另一些不会；类似地，自动把字符串转成数字也会扩大可接受输入。这些行为必须由上面的 canonical validator policy 固定。

如果产品确实需要这些行为，应在 canonical binding contract 中明确：

missing optional field → runtime applies declared default
string "3" for integer → rejected
unknown property → rejected

这样所有 provider 都先回到同一规则，再进入 handler。否则，切换 SDK、validator 或语言实现就可能改变 Tool 的真实输入边界。

Handler 仍然要做防御性校验

Canonical Schema 只能验证当前 arguments 的结构，不能掌握最新资源状态。即使 note_ids 是非空、唯一的字符串数组，handler 和 backend 仍要检查：

  • 这些 note 是否存在且属于当前 tenant。
  • 当前 subject 是否有归档权限。
  • note revision 是否已经变化。
  • 一次最多允许归档多少条。
  • 当前重试的 Attempt 是否仍属于同一个稳定 identity 的 Tool Execution，以及 idempotency key、结果查询或对账机制能否阻止重复副作用。

这些不是对 JSON Schema 的重复实现，而是由不同 owner 掌握的事实。Provider binding 帮助模型生成；Runtime validator 固定结构契约；handler/backend 保护权限、业务状态和副作用。

版本必须进入 Trace 与 Eval

当 validation drift 只在某条 route 出现时，Trace 至少要关联：

tool definition revision
tool surface revision
adapter revision
provider capability profile revision
canonical schema dialect and validator policy revision
canonical validator version
handler version

不需要把每份 Schema 全文复制到每条 log，但必须能从稳定引用重建当时的转换链。否则 Provider 更新、Adapter 修改或 handler 发布后，旧失败会与新失败混在一起，回归测试也无法复现。

回到问题

同一 Tool Schema 在不同 Runtime 中表现不同，通常不是 Schema 文件突然变了，而是它经过的 provider subset、Adapter transform、parser、validator 和 DTO 各自改变了可接受输入。

解决方法不是否认 provider strict mode 的保证，也不是只相信某一层已经“严格校验”，而是把 dialect、vocabulary 与 validator policy 一起固定为 canonical contract：Adapter 显式报告当前 mode 的保证、降级或不支持；所有完整 Tool arguments 在进入 handler 前经过同一 validator；contract test 用正反样例验证行为，而不是只比较 Schema 文本。

这样，provider binding 可以在支持范围内提供严格生成保证，却不会成为决定 Tool 是否安全执行的唯一边界。

后续问题

  • Tool Error 怎样以可修复形式返回模型。
  • Selection、parameter validity、repair 与 mutation precision 怎样组成端到端 Tool Eval。
  • Provider capability profile 怎样通过持续 contract test 更新。
