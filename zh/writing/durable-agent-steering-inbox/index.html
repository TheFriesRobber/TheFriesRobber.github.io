Agent Runtime 八：用持久 Inbox 接收 Steering

从执行期间的新输入和结束阶段的竞态出发，解释 Agent Runtime 为什么需要持久、可确认消费的 steering inbox。

2026/07/17 阅读 次

问题

Agent 正在调用一个需要两分钟的 Tool。用户看到中间结果后补充：“只保留最近一个月的数据。”服务端立即回复“已收到”，并把消息放进当前负责执行 Run 的后台进程（下文简称 worker）的内存 Queue。

几秒后 Tool 返回，worker 恰好重启。新的 worker 根据已有消息继续执行，却找不到刚才那条补充要求。对用户来说，系统明确说过已经接收；对 Runtime 来说，这条输入从未成为可恢复事实。

把消息直接追加到当前 messages 也有问题：模型调用可能已经开始，当前 Model Turn 到底有没有看到它变得不可判断；如果同时修改正在迭代的 Context，还会产生依赖时序的结果。

“收到输入”其实包含三个承诺

执行期间的新输入通常被称为 steering，但这个词容易把几个阶段混在一起：

  1. accepted：系统已经持久接纳，重启后仍然存在。
  2. consumed：输入已经绑定到某个明确 Model Turn 的 canonical input；它不证明 Provider 已接收请求或模型已经“读到”。
  3. applied：模型或 Tool 是否真的按它改变了行为。

前两项可以由 Runtime 记录，第三项往往需要从后续执行事实或结果验证。API 在只完成内存 enqueue 时就返回 accepted，相当于做出了自己无法兑现的承诺。

所以 steering 需要一个持久 Inbox。它不是另一份聊天记录，而是“已被系统接纳、尚未进入某个 Model Turn 的输入”这一状态的 owner。这里的 accepted 还隐含一个重要条件：输入正文和 Inbox 记录都已经持久化。只写下一条指向不存在正文的 payload_ref，仍然无法在恢复后兑现承诺。

最小 Inbox 模型

一条输入可以保留以下逻辑字段：

input_id
tenant_id
subject_ref
session_id
target_run_id
inbox_seq
payload_ref
payload_digest
payload_canonicalization
state              pending | consumed | rejected_terminal
accepted_at
consumed_by_model_turn_id
consumed_at

input_id 让客户端 retry 不会产生两条相同输入，但它需要数据库约束配合，例如以 (tenant_id, subject_ref, input_id) 建立唯一键。input_id 在提交主体的命名空间内标识一次操作；不同主体可以独立使用相同 ID。发生冲突时，系统还要比较 target_run_id、payload_canonicalization 和 payload_digest：目标和内容都相同，才返回原来的接纳结果；同一主体用同一个 ID 携带不同目标或内容时，应明确返回 conflict。

写入之前，可信的接入层还要从登录态中取得 tenant_id 和 subject_ref，确认这个主体有权 steering 目标 Run。它们不能直接相信请求正文，否则攻击者只要猜到 run_id 就可能向别人的执行注入输入。

inbox_seq 是同一 Run 内单调递增的接纳顺序。它比只按 accepted_at 排序更稳定：两条输入可能拥有相同时间戳，也可能由不同服务实例同时写入。consumed_by_model_turn_id 则说明输入被绑定到哪个 Model Turn 的 canonical input，而不是只写一个模糊的 processed=true。

如果 payload 和 Inbox 在同一个数据库，可以在同一事务里保存不可变正文并插入 Inbox。若正文位于对象存储，更稳妥的方式是先按内容地址写入不可变对象，再提交 Inbox。两种“结果未知”要分开处理：对象写入的结果未知，就按内容地址查询对象并校验 digest；Inbox 提交的结果未知，就按上面的幂等键查询接纳记录。只有对象、没有 Inbox 的孤立 payload 由 retention 清理，不能仅凭对象存在就声称输入已经 accepted。Runtime 在消费前仍要校验 digest，避免把损坏或被替换的正文送入模型。

客户端收到 accepted 后，只能确信输入已进入 Inbox。若界面要展示更精确状态，可以在它被绑定到某个 Model Turn 后显示“已分配给 Model Turn”；模型请求已发送和模型响应应由后续 Model Turn event 表达。

为什么只能在 Model Turn boundary 消费

Model Turn boundary 是模型请求尚未组装或上一轮已经结束的位置。Runtime 在这里可以：

1. 按 inbox_seq 读取 pending input
2. 按稳定顺序生成输入消息
3. 创建 next Model Turn
4. 把这些 input 标记为 consumed_by_model_turn

这里的“创建 Model Turn”不只生成一个 model_turn_id，还要持久化这次模型请求使用的不可变 canonical input（或稳定内容引用），以及本次纳入的 Inbox input_id 列表。它与标记 consumed_by_model_turn_id 应共享原子边界。否则，worker 可能只创建 Model Turn identity 就崩溃，留下“已消费”却无法重建输入；也可能恢复时把同一条 steering 注入第二个 Model Turn。

如果模型请求已经发出，新输入默认留给下一个 Model Turn。系统也可以选择中断当前模型调用后重开一轮，但那是显式的 interruption policy，不能通过修改正在使用的数组偷偷实现。

回到开场例子：补充要求先变成 pending。旧 worker 在 Tool 返回后崩溃，新 worker 仍能看到它，并在创建下一 Model Turn 时将其绑定。输入没有因为进程生命周期结束而消失。

结束阶段最容易出现竞态

更隐蔽的情况发生在 Run 即将完成时。这里先假设 Run owner 已经验证：这次 Agent Loop 已有 final output、所有由 Run 拥有的 child work 已经收敛，而且当前状态允许进入终态。Inbox 为空并不证明上层 Task 已完成；下面的协议只负责让这个既有 Run 终态决定与最后一刻到达的 steering 不互相穿透。

T1 Runtime 检查 Inbox：为空
T2 用户发送新输入
T3 Runtime 把 Run 标记为 completed
T4 新输入已 accepted，但没有执行者再来消费

解决它不能只靠“结束前再查一次”，因为检查和接纳仍然可以交错。需要一个 terminal admission boundary，而且接纳事务和结束事务必须争用同一个串行化点。

这里不应该把可随事件重建的 Run 页面快照当成协调者。更适合承担这个职责的是一个很小的 command-side run_control 记录：

run_id
admission_epoch
admission_state       open | closing | closed
owner_fencing_token
next_inbox_seq

它只负责接纳窗口和当前执行 owner，不负责保存完整的 Run 展示状态。steering.accepted、steering.consumed、run.continued 或 run.completed 等决定仍写入 Event Log；面向查询的 Run snapshot 再从这些事实构建。

例如，输入接纳路径先验证主体权限，再按完整幂等键查询既有记录。若记录已经存在，就核对主体、目标、canonicalization 和 digest，并直接返回最初的接纳结果——即使当前窗口后来已经关闭。首次查询只是一条快速路径：两个相同 retry 可能都暂时看不到对方未提交的记录，因此取得 run_control 锁后必须再次查询幂等键。只有二次查询仍确认是新键时，才检查当前 epoch、分配 inbox_seq、持久化 payload 和 Inbox，并追加接纳事件：

BEGIN;
-- 授权后先查询已有幂等记录；存在且内容一致时返回原 accepted 结果。
SELECT admission_epoch, admission_state
FROM run_control
WHERE run_id = :run_id
FOR UPDATE;

-- 在锁内重新查询幂等键；存在时核对内容并返回原结果。
-- 也可用 INSERT ... ON CONFLICT DO NOTHING 后读取、核对已有记录。
-- 验证 tenant、subject 和 steering 权限。
-- 只有当前 epoch 仍为 open，才分配 inbox_seq 并插入 pending input。
INSERT INTO steering_inbox(...);
-- 追加 steering.accepted。
COMMIT;

结束路径也取得同一个锁。它先把当前 epoch 改成 closing，阻止新输入悄悄落到即将结束的这一轮，然后读取 pending input：

BEGIN;
SELECT admission_epoch, admission_state, owner_fencing_token
FROM run_control
WHERE run_id = :run_id
FOR UPDATE;

UPDATE run_control
SET admission_state = 'closing'
WHERE run_id = :run_id
  AND admission_state = 'open'
  AND owner_fencing_token = :owner_token;

SELECT input_id
FROM steering_inbox
WHERE target_run_id = :run_id
  AND state = 'pending'
FOR UPDATE;

-- 有 pending input：创建并绑定 next Model Turn，标记 consumed，
--                  推进 admission_epoch，再把窗口重新设为 open。
-- 没有 pending input：追加 run.completed，并把窗口设为 closed。
COMMIT;

这里的 SQL 是概念模型；创建 Model Turn、标记 Inbox 已消费和追加决定事件也必须位于同一个提交协议中。应用还要检查每条语句的实际结果。也可以使用带整体 retry 的 serializable transaction，或者用版本号实现等价的 CAS 协议。关键不是选择哪种数据库语法，而是两条路径不能各自在普通 snapshot 中读一次 admission_state 后独立提交。

这样竞态只有两种确定结果：

  • 输入先提交：finalizer 能看到 pending input，原子创建下一 Model Turn，并为后续接纳推进 epoch、重新打开窗口。
  • finalizer 先提交终态：窗口成为 closed，后来的输入不会被错误标成属于当前 Run，可以明确拒绝，或根据产品规则创建 follow-up Run。

不能出现“当前 Run 已接受，但没人负责”的第三种结果。

如果 Run control、Inbox 与 Event Log 位于不同存储，就不能直接声称这些步骤原子完成；需要把 admission decision 收敛到一个 Source of Truth，再通过 outbox 或 reconciliation 驱动另一侧。

这个协议还假设同一时刻只有一个持有效 lease 的 Run owner 能消费 Inbox 和提交终态。owner_fencing_token 用来拒绝旧 worker 的迟到写入。lease 如何续期与接管属于执行所有权问题，但这里必须明确它是前提，否则两个 worker 仍可能同时创建 next Model Turn。

唤醒信号仍然有用

持久 Inbox 不等于每个 worker 都要高频轮询。写入成功后，可以通过进程内 Queue、Redis Pub/Sub 或其他 notification 唤醒当前 owner。

但 signal 只意味着“可能有新输入”，worker 被唤醒后仍以 Inbox 查询为准。为了保证 signal 丢失后最终仍有人处理，系统还需要一种明确的 re-drive：例如写 Inbox 的事务同时写 outbox，由 durable queue 重试投递；或者由 heartbeat/定时扫描在约定的最大间隔内重新发现 pending input。signal 重复时，Inbox 状态和 inbox_seq 也不会让同一输入被重复绑定。

这和输出 Streaming 的边界相似：通知负责延迟，durable record 负责正确性。不过两者的数据 owner 不同——输出事件证明 Runtime 已经做了什么，Inbox 证明用户输入是否已被接纳和消费。

Stop、Steer 与 Follow-up 不应混成一个动作

它们都可能从同一个输入框进入，但语义不同：

输入类型目标常见处理
steer活跃 Run 的下一次推理进入 Inbox，在 Model Turn boundary 消费
stop当前执行控制状态持久化 cancel request，并唤醒执行者
follow-up已结束目标上的新意图创建新 Run，引用之前的 Session 事实

把 stop 当成自然语言消息，模型可能在下一个 Model Turn 才看到；把 follow-up 强塞进已经 terminal 的 Run，又会破坏终态。统一接入层可以共享 identity 和 idempotency，但状态转移必须不同。

回到问题

执行期间的新输入不能只存在于当前 worker，也不能在模型请求进行中随意改写 messages。

更清晰的协议是：先在可信接入层完成授权，把正文和输入幂等写入持久 Inbox，再在明确 Model Turn boundary 创建消费记录；signal 只负责降低唤醒延迟，durable re-drive 负责最终发现。Run 结束前关闭当前 admission epoch，并让竞态收敛为“原子创建下一 Model Turn 后重新开放”或“提交终态并明确进入后续路径”。

这样，accepted、consumed 和“是否真正执行”不再被一句含糊的“已收到”掩盖。

后续问题

  • Run owner 的 lease、fencing token 和接管协议应怎样设计。
  • 输入已消费后，Checkpoint 应怎样保存 Model Turn 与 Inbox cursor。
  • 高风险 steering 是否需要重新确认授权或用户批准。
