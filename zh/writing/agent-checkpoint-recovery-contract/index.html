Agent Runtime 五：Checkpoint 不是对象快照

2026/07/15 阅读 次
AgentRuntimeRecovery

问题

一个 Agent 正在生成报告。它已经调用 create_document，外部服务返回了 doc_42，接下来准备让模型撰写摘要。此时，负责执行这个 Run 的后台进程（下文简称 worker）崩溃。

如果系统每隔一分钟序列化一次 Runtime 对象，最近快照可能仍停在 Tool 调用之前：

内存快照：准备调用 create_document
外部事实：doc_42 已经创建

恢复后直接从快照继续，会再次创建文档；恢复后把整个函数标成完成，又会漏掉摘要。问题不在于序列化格式，而在于内存对象从来没有完整拥有外部世界的状态。

四种容易混淆的持久化对象

Checkpoint 只有和其他持久化对象分工后才有意义：

对象回答的问题典型内容
Event Log已经提交过哪些执行事实Tool intent、result、Model Turn completed
Snapshot当前派生状态是什么Run state、当前 Model Turn、预算余额
Checkpoint从哪里、按什么条件恢复snapshot reference、event cursor、waiting condition、version
Artifact执行产生了什么交付物文件、报告、代码、引用

Event Log 偏历史，snapshot 偏快速读取，artifact 是用户可见结果。Checkpoint 则是一份恢复协议：它不仅指向一个位置，还要说明恢复代码需要验证哪些外部条件。

把 ORM connection、async task、socket 或 framework 内部对象序列化进去，看起来更完整，却通常无法跨进程、版本或机器恢复。这些临时对象应在恢复时重新创建。

对于外部副作用，Runtime 还需要在调用前持久化 effect intent：稳定 effect_key、参数摘要、目标系统和初始状态。只有 intent 提交成功后才能发起调用。这样，worker 若在调用后硬崩溃，恢复时至少知道“这个逻辑动作可能已经发生”，而不会生成一个新身份重新执行。

Checkpoint 最少保存什么

对开场中的 Run，一份概念性 Checkpoint 可以是：

{
  "checkpoint_version": 4,
  "run_id": "run_8",
  "run_spec_fingerprint": "sha256:...",
  "resume_contract_revision": "report-agent.v3",
  "snapshot_ref": "snapshot_73",
  "event_cursor": {"stream_ref": "session:session_17", "seq": 73},
  "resume_at": "reconcile_create_document",
  "waiting": null,
  "pending_effects": [
    {
      "effect_key": "run_8:create_document:v1",
      "provider": "document-service",
      "idempotency_scope": "tenant:tenant_9",
      "idempotency_expires_at": "2026-07-18T09:00:00Z",
      "status": "in_progress",
      "external_ref": null
    }
  ],
  "artifact_refs": [],
  "budget": {"model_turns_used": 6},
  "created_at": "2026-07-17T09:00:00Z"
}

这里的 snapshot_ref 指向截至 Session stream session:session_17 中 seq=73 的完整可恢复派生状态；恢复器可以验证 Snapshot、stream 与 sequence 的绑定关系，再从 73 之后补事件。裸数字 73 在另一条 Session stream 中没有意义。恢复当前 Run 时仍按顺序读取这个 Session stream，再只把与当前 Run 有因果关系的事件应用到恢复状态。如果不保存 Snapshot，也可以从 Event Log 起点完整重放，但不能既没有基础状态，又从中间 cursor 开始。

RunSpec 说明这次执行采用什么契约，resume_contract_revision 说明当前 resume_at 依赖哪一版恢复语义。Effect contract 还要说明下游 provider、幂等作用域和 key 的有效期；只有 effect_key 本身不足以证明几天后重试仍会去重。

resume_at 也不应该是任意代码行号。它应指向代码能够长期理解的逻辑边界，例如某个 Tool Execution 已提交、正在等待 approval，或者需要 reconciliation 的 effect。

恢复不是反序列化，而是 reconciliation

恢复 run_8 时，可以按以下顺序处理：

1. 读取 Checkpoint version 4、对应 RunSpec 和 `snapshot_73`，验证 Snapshot 恰好覆盖到指定 Session stream 的 cursor 73。
2. 从同一 stream 读取 event seq > 73，吸收 Checkpoint 之后已经提交、且与当前 Run 有关的事实。
3. 对所有已有 intent、但没有 terminal result 的 effect，先按稳定业务引用查询；只有 idempotency key 仍在 provider 的去重窗口内时才可按原 key 重试。这包括 `in_progress`、`dispatched` 和显式 `unknown`。
4. 重新验证授权、artifact 与 waiting condition 是否仍然有效。
5. 构造新的 Runtime state，从下一个合法边界继续。

假设 worker 在外部服务返回 doc_42 后，已经追加 seq 74 effect.succeeded(effect_key, doc_42)，却来不及生成新 Checkpoint。上面的旧 Checkpoint 仍停在 in_progress，但第 2 步会吸收 seq 74，把 doc_42 纳入新状态，恢复代码就不会重复创建文档。

如果外部调用成功，但连 success event 也没写入，持久层可能仍停在 intent 或 in_progress，不会自动变成 unknown。恢复器应把所有“已提交 intent、无终态结果”的 effect 视为结果不确定。Key 仍在下游去重窗口内时，可以复用原 key 重试；窗口已过时，只有能按稳定业务引用查询原结果才可继续。既无法查询、又无法确认下游仍会去重时，应进入 reconciliation 或 manual_recovery，不能把“复用相同 key”当成安全保证。

反过来，如果 effect intent 根本不存在，Runtime 就不应已经发起过外部调用；这是“先持久化 intent，再调用”的顺序所提供的边界。若实现允许先调用后补 intent，Checkpoint 再完整也无法可靠识别那次孤立副作用。

因此 Checkpoint 不能替代幂等和 reconciliation。它只让恢复过程知道要核对什么。

Pause 与 crash 使用同一份恢复契约

人工审批、等待用户输入和定时暂停，都可以被建模为显式 waiting condition：

{
  "kind": "approval",
  "request_id": "approval_9",
  "resource_version": 17,
  "expires_at": "2026-07-18T09:00:00Z"
}

进入 pause 前，Runtime 先提交 waiting event 和 Checkpoint，再释放 worker。Resume 时不能只检查“有人点了同意”，还要确认 approval 是否绑定同一个 action、参数和 resource version，是否已过期，以及当前授权是否仍成立。

Crash 与主动 pause 的区别在于触发方式，不在于恢复协议。两者都应从最后一个已提交边界重建，而不是依赖原进程仍保留调用栈。

Replay 为什么通常不是完全确定的

有些 durable workflow 系统通过 event history 重放确定性 workflow code，并把外部调用结果作为 history event 保存。这是一种强约束的执行模型。

普通 Agent Runtime 往往更松散：

  • 相同 prompt 再次调用模型，输出可能不同。
  • Tool 背后的数据会变化。
  • 当前授权、时间和文件版本可能已经改变。
  • Provider 可能升级模型行为。

所以“从 Checkpoint replay”应该优先理解为重放已记录事实以重建状态，而不是重新调用所有外部依赖并期待得到相同结果。

若确实需要可重复 Eval，应固定 RunSpec、prompt、Tool fixture、model version 和 grader，并把外部调用替换成记录结果；那是另一套可复现性契约，不能由生产 Checkpoint 单独保证。

Schema 与代码升级怎么办

长时间 Run 可能跨过一次部署。checkpoint_version 版本化存储 schema，resume_contract_revision 则版本化 resume_at、状态转移和恢复动作的语义。两者都要进入 worker 的兼容矩阵：schema 没变但恢复逻辑变了，也必须生成新的 resume contract revision。然后为兼容性选择一种策略：

  • 新代码保持对仍受支持旧 Checkpoint schema 的向后兼容读取。
  • 在部署前把旧 Checkpoint 迁移到新版本。
  • 把旧 Run 路由给兼容 worker，直到它们结束。
  • 无法安全恢复时进入明确的 manual_recovery，而不是静默从头重跑。

兼容测试应使用保存下来的旧 Checkpoint fixture，并覆盖其 resume contract revision，验证新代码能否读取、重放和继续。仅测试最新 schema 的 round trip，发现不了真实升级问题。

Checkpoint 的生成频率

每个 token 都写 Checkpoint 成本过高，只在 Run 结束时写又失去恢复价值。比较自然的边界包括：

  • 一个有副作用的 Tool Execution 收敛后。
  • 一个 Model Turn 完成后。
  • 进入人工等待或长 timer 前。
  • 已产生重要 artifact 后。
  • Event Log 累积到需要缩短重建时间时。

频率取决于允许重做多少纯计算、写入成本和恢复目标。Checkpoint 可以滞后于 Event Log，只要恢复过程会读取 cursor 之后的事实。

回到问题

运行时对象快照只记录某个进程曾经看见什么，不能证明外部世界已经发生什么。

有用的 Checkpoint 应保存逻辑恢复位置、与 event cursor 绑定的 Snapshot reference、RunSpec identity、等待条件，以及 pending、unknown 或已确认 effect 的稳定身份；恢复时再加载基础状态、重放后续事件、核对结果不确定的副作用并重建临时对象。它不承诺外部世界可完全确定性重放，而是让每一次继续执行都有可解释、可验证的起点。
