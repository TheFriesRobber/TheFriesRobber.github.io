Agent Runtime 二：一次执行该怎样分层

用一份 PDF 报告按完成责任和 retry boundary 区分 Task、Run、Model Turn、Tool Execution 与 Job，并映射 OpenAI、Anthropic 和 pi 的常见叫法。

问题

用户让 Agent：“读取这份文件，生成报告，并导出成 PDF。”

读取文件、生成 Markdown 和提交转换请求可以在当前 Agent Loop 内完成，但 PDF 转换可能持续几分钟，还要由独立 worker 执行。当前请求返回“正在转换”之后，用户可能继续追问进度，进程也可能重启；这些后续活动仍然服务于同一个目标，却不一定属于同一次 Agent Loop。

一次执行可能是：

Task：生成并交付 PDF 报告
  Run 1：处理用户最初的请求
    Model Turn 1：模型提出 read_file
    Tool Execution 1：read_file 成功
    Model Turn 2：模型生成正文并提出 save_report
    Tool Execution 2：save_report 成功
    Tool Execution 3：enqueue_pdf_conversion 成功
    Model Turn 3：模型回复“报告正在转换”
  Job：worker 将 report.md 转成 report.pdf
  Run 2：用户稍后询问进度

如果系统只保存一条记录：

{
  "id": "run_18",
  "status": "running"
}

这个 running 几乎无法回答任何具体问题。模型还在生成吗？文件已经保存了吗？后台转换是否已经进入 Queue？当前 Agent Loop 已经结束，还是被明确暂停、以后要从原处恢复？用户取消的是这次交互，还是整个报告目标？

问题不只是缺少几个 status。系统把用户目标、一次 Agent Loop、模型轮次、Tool 副作用和后台调度压成了同一个对象。

Run、Turn 与 Step 没有跨框架统一定义

OpenAI、Anthropic 和 pi 都实现了“调用模型、执行 Tool、把结果交回模型”的循环，但它们对 run、turn、step 的命名并不完全相同：

生态公开资料中的主要叫法需要注意的边界
OpenAI Agents SDK一次 SDK run 是一个 application-level turn；Runner 会在其中反复调用模型和执行 ToolOpenAI 把整次应用交互称为 turn，不适合再用裸 Turn 指内部模型轮次
Anthropic Agent SDK / Messages APIquery() 发起一次 Agent 工作；文档也用 assistant turn 描述一次 Claude 响应，并以 tool_use / tool_result 延续循环Session 可以跨多次 interaction；max_turns 统计的是循环中的模型轮次，不是持久用户目标
piagent_start / agent_end 界定一次 low-level agent run；agent_settled 表示 pi 不会再因自动 retry、compaction 后 retry 或 queued follow-up 继续；每个 turn_start / turn_end 表示一次 LLM 响应及其 Tool callslow-level run 与最终 settled 边界不同；turn 明确是 Loop 内部粒度

因此，本文不会声称存在一套行业标准对象树，而是采用一套能显式映射三家语义的本系列词汇：

本系列术语它回答的问题常见 owner
Session哪些交互共享持久对话、Context 与资源？application / session service
Task用户的持久目标是否已经完成？application / orchestrator
Run由一次新输入或恢复动作启动的 Agent Loop 是否已经停止、暂停或失败？Agent Runtime
Model Turn一次模型响应及其 Tool 调用处理是否到达下一次模型请求前的边界？Agent runner
Tool Execution某个获准执行的 Tool 动作是否得到确定结果？Tool Runtime
Job已移交调度系统的后台工作是否收敛？Queue、worker 或 workflow engine

Model Turn 特意带上 Model，用于避开 OpenAI 把整个 Run 称为 application-level turn 的歧义。Step 则不再作为本系列的固定运行时对象：有的框架用 step 表示一次循环，有的产品把任意进度都叫 step。需要谈模型决定时写 Model Turn，谈 Tool 时写 Tool Call 或 Tool Execution，谈物理重试时写 Attempt。

这些对象通过 causality 和 parent identity 关联，但不共享完成条件。

Task 追踪用户目标，Session 保存跨 Run 的上下文

这个例子中的 Task 是“生成并交付 PDF 报告”。用户第一次发出要求时创建 task_report_7；系统回复“正在转换”后，这个目标还没有完成，所以 Task 仍是 waiting。

task_report_7：waiting
已完成证据：report.md@v3 已保存
等待条件：job_pdf_9 产生并发布 report.pdf

用户稍后询问“转换好了吗”，这是同一个 Session 中的新输入，也会启动新的 Run。新 Run 可以读取 task_report_7 和 job_pdf_9 的状态后回答，但不必假装最初的 Agent Loop 一直占着执行权。

Session 与 Task 也不能合并。Session 是对话和 Context 的持久容器，可以先后承载“生成报告”和“把报告发给我”两个 Task；一个 Task 也可能因为通知或审批跨越多个交互。是否复用 Task，取决于应用认定用户目标是否仍是同一个，不取决于消息是否在同一个 Session。

Task 在这里是应用层术语，不等同于 Python 的 asyncio.Task，也不等同于 Queue 中的一条 Job。框架没有替应用自动定义“用户目标何时算完成”；这项判断必须由产品或 orchestrator 持有。

Run 是一次 Agent Loop，不是用户目标的永久外壳

run_18 从用户最初的输入开始，Runner 在其中多次调用模型、执行 Tool，直到模型给出“报告正在转换”的最终回复。这时本次 application-level turn 已经结束，Run 可以进入 succeeded，而 task_report_7 继续等待后台 Job。

run_18：succeeded
final output：报告正在转换
task_report_7：waiting for job_pdf_9

这一区分修正了一个常见误用：不能为了表示用户目标尚未完成，就让 Run 在 HTTP 请求返回后无限保持 running。running 应当有实际 owner、lease 或 heartbeat 支持；否则它只是一条无法验证的陈旧状态。

有一种情况可以保留同一个 Run identity：Runtime 明确把它暂停为可恢复执行，例如等待审批，或持久保存了继续 Agent Loop 所需的状态。恢复动作是在继续同一个未完成的 application-level turn，而不是仅仅因为同一个 Task 还有后续工作。若最初的 Run 已经向用户给出 final output，之后的新消息通常启动新 Run。

因此，Run 的 terminal state 只说明这次 Agent Loop 如何停止。它可以成功地产生“转换已受理”的回复，却不能据此推断 PDF Task 已完成。

Model Turn 是 Loop 内的一次模型轮次

在 run_18 中，第一次 Model Turn 让模型看到用户要求和文件 Tool，模型返回 read_file 调用；Tool Runtime 执行后，把结果加入下一次模型可见输入。第二次 Model Turn 再根据文件内容生成报告并提出保存动作。

每个 Model Turn 可以独立记录：

  • 实际使用的 model/provider；
  • context revision 与 Tool surface；
  • 模型响应、token、latency 和 finish reason；
  • 它提出的 Tool Call，以及随后形成的 Tool Execution identity。

只有当 Tool 结果已经处理完毕、Runner 准备发起下一次模型请求时，这个 Model Turn 才到达边界。这样既能对应 pi 的 turn 事件，也能解释 Anthropic 文档中的 assistant turn。对 OpenAI 而言，它是 SDK Run 内部的一次模型/Tool 循环，不要把它误称为另一个 application-level turn。

如果 provider 在接受请求前发生 transport error，并且可以安全重试，第二次物理请求仍可记作同一个 Model Turn 的 transport Attempt。只有模型获得新的可见输入，例如 read_file 的结果已经加入 Context，才开始新的 Model Turn。否则，指标会把基础设施 retry 误算成 Agent 多思考了一轮。

Tool Call 是提议，Tool Execution 才拥有执行状态

模型返回 save_report(path, content) 时，产生的是 Tool Call：一份结构化的动作提议。Runtime 完成参数校验、权限判断和 policy 检查后，才创建 Tool Execution 并产生外部效果。

假设 save_report 已经写入 report.md，但响应丢失。Runtime 看到 timeout 时，不能把 Tool Execution 直接标记为 failed；外部效果可能已经发生，只是当前没有确认结果。

tool_execution_save_4
  logical identity：保存 report.md@v3
  status：unknown
  attempt 1：timeout

后续 retry 如果仍在确认或完成同一次保存，应保留 tool_execution_save_4，只新增 Attempt。若用户要求“另存一份”，那才是新的 Tool Execution。

这也是不再使用泛化 Step 的原因。Tool Call 回答“模型提出了什么”，Tool Execution 回答“Runtime 实际授权并执行了什么”，Attempt 回答“物理上试了几次”。把三者都叫 Step，会再次丢失重试和外部副作用的 identity。

生命周期移交调度系统后，叫 Job

PDF 转换进入 Queue 后，当前 Agent Loop 可以结束，worker 也可能重启。它由调度系统独立排队、租约、重试和收敛，因此本文称它为 Job：

job_pdf_9：convert report.md@v3 to PDF
  attempt 1：worker lost
  attempt 2：running

Job 的 retry unit 是同一项后台工作，不是重新创建 Run，也不是让模型重新生成报告。只要输入仍是 report.md@v3，而且转换可以安全重放或按 job_pdf_9 去重，worker retry 就可以继续属于同一个 Job。若报告正文更新到 version 4，应明确取消旧 Job 或创建新 Job，不能让两个版本竞争同一个输出路径。

Job 成功产生 report.pdf 后，应用再根据正确版本、原子发布和完整性验证等证据，把 task_report_7 收敛为 succeeded。这里不是把 Job 状态自动复制给 Task，而是 Task owner 重新判断用户目标是否满足。

如果转换只是当前 Tool 函数中的一次同步调用，例如 await convert_to_pdf(report)，则无需创建 Job；它仍属于当前 Tool Execution。区分 Tool Execution 与 Job 的标准不是动作名称或耗时长短，而是生命周期和 owner 是否已经移交给独立调度系统。

Retry 必须停留在正确的 identity 上

现在假设 PDF worker 第一次崩溃、第二次成功。正确的恢复路径是：

task_report_7 保持 waiting
run_18、model_turn_1..3 保持 succeeded
tool_execution_read、tool_execution_save、tool_execution_enqueue 保持 succeeded
job_pdf_9 新增 attempt 2

如果系统只能 retry 整个 Run，模型会重新读取文件、生成正文并保存。即使最后 PDF 正确，系统也无法解释多出来的 token、文件版本和外部写入。

反过来，模型输出解析失败时，也不应 retry PDF Job。失败发生在哪个 owner，就先在那个 identity 内判断能否恢复：

  • transport retry 留在同一个 Model Turn；
  • Tool retry 留在同一个 Tool Execution；
  • worker retry 留在同一个 Job；
  • 恢复明确暂停的 Agent Loop，可以保留同一个 Run；
  • 用户发出新的交互输入，通常创建新 Run；
  • 是否新建 Task，由应用判断它是不是同一个用户目标实例；目标改变、用户明确要求重新执行，或旧 Task 已终态而开始新的交付，通常都创建新 Task。

Cancellation 传播意图，不覆盖历史事实

用户在 PDF 转换期间说“不要这份报告了”，应用先把 task_report_7 置为 cancelling，并向 job_pdf_9 发出 cancellation request。已经结束的 run_18、Model Turn 和 Tool Execution 不能改写为 cancelled：报告正文确实生成并保存过，这是历史事实。

Job 也不能在收到请求时立刻宣称 cancelled。worker 可能正在写文件，远端转换服务也可能已经产生结果。只有 owner 确认工作停止并处理残留 Artifact 后，Job 才进入相应 terminal state；确认前可以保持 cancelling。

如果用户只说“停止当前回答”，应用也不能默认取消整个 Task。取消请求必须带上目标 identity：是当前 Run、某个 Tool Execution、后台 Job，还是用户目标本身。父级传播的是意图，每个 owner 仍根据自己观察到的事实收敛。

分开以后，查询才有明确答案

同一时刻可以保存：

Session session_3               → active
Task task_report_7              → waiting for job_pdf_9
Run run_18                      → succeeded
Model Turn model_turn_1..3      → succeeded
Tool Execution tool_exec_save_4 → succeeded, report.md@v3
Job job_pdf_9                   → running, attempt 2

产品界面查询 Task，知道用户目标仍在处理中；交互历史查询 Run；模型成本查询 Model Turn；Tool 可靠性查询 Tool Execution 与 Attempt；Queue 运维查询 Job。它们通过 parent、causality 和 Artifact version 关联，但不再争用同一个 status 字段。

Checkpoint 需要保存哪些状态、event log 怎样派生 current snapshot，是后续的持久化问题。分析仓库怎样按 grain 计算指标，则可参考 Agent Observability 一：建模前先明确 Grain。本文先固定本系列的 Runtime 语义：谁拥有状态，谁判断完成，失败应在哪个 identity 上恢复。

回到问题

业界一致的是 Agent Runtime 需要反复调用模型和 Tool，不一致的是每一层究竟叫 run、turn 还是 step。直接搬用其中一家的裸词，会让同一个 Turn 在不同文章里一会儿表示整次应用交互，一会儿表示一次模型响应。

本系列因此使用显式名称：Session 保存跨 Run 的上下文，Task 表示用户目标，Run 表示一次 Agent Loop，Model Turn 表示 Loop 内模型轮次，Tool Execution 表示获准执行的动作，Job 表示移交调度系统的后台工作。Step 只作为普通流程词，不再承担固定状态机语义。

名称对齐之后，更重要的边界也随之清楚：模型响应不证明 Tool 已执行，Run 成功不证明 Task 已完成，Job 重试也不应让 Agent 从头再跑一遍。

后续问题

  • Checkpoint 应保存 event、snapshot 还是可重建状态，进程重启后怎样恢复。
  • Event log 与 current snapshot 怎样处理并发更新和乱序事件。
  • Deadline 与 cancellation 怎样跨 Task、Run、Tool Execution 和 Job 传播。
  • 这些对象的指标怎样进入统一 Trace，又不混淆 grain。
