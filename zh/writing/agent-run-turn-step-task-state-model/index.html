Run、Turn、Step 与 Task 是不同的状态机

2026/07/15
AgentRuntimeState Machine

问题

用户让 Agent：“读取这份文件，生成报告，并导出成 PDF。”

假设读取和保存都能在当前请求内完成，但 PDF 转换可能持续几分钟，还要使用独立的转换环境。为了避免 HTTP 请求一直占着连接，Runtime 在保存 Markdown 后把转换工作提交给 Queue，由另一个 worker 执行。当前请求可以先结束，进程也可能重启，但这个 Run 仍要等到 PDF 真正产生后才能完成。

在这个前提下，一次执行可能经过下面几步：

Turn 1：模型决定读取文件
Step 1：read_file 成功
Turn 2：模型生成报告正文
Step 2：保存 report.md 成功
Task 1：后台将 report.md 转成 report.pdf

这里的 Task 不是每个 Agent 都必需的一层。它表示一项已经脱离当前调用、需要被独立排队、执行和恢复的工作。如果 PDF 转换只是当前函数内的一次同步调用，例如 await convert_to_pdf(report)，它仍然只是 Run 中的一个 Step，不需要单独引入 Task。

如果系统只保存一条执行记录：

{
  "id": "run_18",
  "status": "running"
}

这个 running 几乎无法回答任何具体问题。模型还在生成内容吗？文件已经保存了吗？PDF 转换是否进入 Queue？用户取消时应该停止哪一项工作？进程重启后应该重做整份报告，还是只恢复 PDF 转换？

它们都发生在同一次用户请求里，却不共享同一个完成条件。问题不是还缺几个 status，而是系统把不同粒度的执行对象压成了一条状态。

先问每个状态在回答什么

Run、Turn、Step、Task 并不是各个框架统一使用的标准术语。有的实现会把一次 Agent Loop 迭代也叫 step，有的会把后台工作直接叫 job。名字可以不同，但四类问题不能混在一起：

对象它回答的问题谁判断它完成
Run这次用户目标最终完成了吗？Agent Runtime 或 orchestrator
Turn这一次模型请求与响应结束了吗？model adapter
Step这个逻辑动作得到确定结果了吗？执行该动作的 Runtime
Task这项脱离当前调用、可独立调度的工作是否已经收敛？Queue、worker 或 workflow engine

这里的关键不是形成一棵整齐的对象树，而是让每种状态只描述自己真正掌握的事实。

同一个 Run 中，不同对象可以同时处于不同状态；父级状态不能覆盖子级已经发生的事实。

Run 追踪的是用户目标

在这个例子里，Run 的目标不是“模型成功返回一次”，而是“可用的 PDF 报告已经产生”。因此，Turn 2 返回报告正文后，Run 仍不能标记为 succeeded；它还在等待 PDF Task。

此时更准确的状态是：

run_18：waiting
等待原因：task_9 尚未完成
已完成证据：report.md version 3
缺少证据：report.pdf artifact

waiting 与 running 的区别对用户界面和恢复逻辑都有意义。前者表示当前没有模型或 Tool 正在占用执行权，系统正在等待一个外部条件；后者只有在有效 lease 或 heartbeat 支持时，才表示某个 owner 正在推进工作。进程崩溃后留下的旧 running 不能继续当作实时事实，lease 失效后需要进入 reconciliation 或 recovery。

Run 的 terminal state 也必须回到目标判断。PDF Task 最终失败时，Run 可以是 failed；用户明确接受 Markdown 报告作为降级结果时，同一个 Run 也可能以 succeeded 结束，但需要记录交付的是哪种 Artifact。不能只因为最后一次函数调用没有异常，就推断用户目标完成。

Turn 只描述一次模型往返

Turn 1 的输入包括用户要求和文件 Tool，输出是模型提出的 read_file 调用。Turn 2 的输入增加了文件内容，输出是报告正文。

每个 Turn 可以独立记录：

  • 实际发送给哪个 model/provider；
  • 使用了哪个 context revision 和 Tool surface；
  • 响应是否完整、被取消或解析失败；
  • token、latency 和 finish reason。

Turn succeeded 只证明 model adapter 得到了可用响应，不证明响应提出的 Tool 已执行，也不证明整个 Run 已完成。

如果在 provider 接受请求前发生 transport error，并且已知可以安全重试，Runtime 可能仍把第二次尝试视为同一个 Turn 的另一次 transport Attempt。只有当模型获得了新的可见输入，例如读文件结果已经加入 context，才开始新的 Turn。否则，指标会把基础设施 retry 误算成 Agent 多思考了一轮。

Step 追踪一个逻辑动作

Step 表示 Runtime 需要观察和推进的一个逻辑动作。在当前例子中，读取文件和保存 Markdown 是两个 Step。

假设 save_report 已经写入 report.md，但响应丢失。Runtime 看到 timeout 时，Step 不应直接进入 failed，而应进入 unknown：外部效果可能已经发生，只是当前没有确认结果。

step_save_report
  logical identity：保存这份报告
  status：unknown
  attempt 1：timeout

后续 retry 如果仍是在确认或完成同一次保存，应保留 step_save_report，只新增 Attempt。若用户点击“另存为一份新报告”，那才是新的 Step。

这正是 Step 与物理请求不能共用 identity 的原因。Step 回答“这个动作最终完成了吗”，Attempt 回答“Runtime 实际试了几次”。Attempt 是执行证据，不是这里要增加的第五种业务状态机。

生命周期脱离当前调用后，才需要 Task

PDF 转换进入 Queue 后，当前 HTTP 请求可以结束，worker 也可能重启。它已经不再属于当前函数栈，而由调度系统接管，因此需要一个能跨请求和进程存在的 identity 与状态。这就是本文所说的 Task。

task_9：convert report.md@v3 to PDF
  attempt 1：worker lost
  attempt 2：running

Task 的 retry unit 是同一项可调度工作，不是重新创建 Run，也不是让模型重新生成报告。只要输入仍然是 report.md@v3，而且转换动作可以安全重放或由下游按 task_9 去重，worker retry 就可以继续属于同一个 Task；如果报告正文更新到 version 4，则应由 Runtime 明确取消旧 Task 或创建新 Task，不能让两个版本竞争同一个输出路径。

Task succeeded 后产生 report.pdf，Runtime 才可能获得让 run_18 收敛所需的证据。这里不是 Task 状态自动向上复制成 Run 状态，而是 Run 根据自己的目标条件重新判断：正确输入版本生成的 Artifact 已原子发布，并通过最低限度的完整性或格式验证。仅仅看到输出路径存在，不能排除 worker 崩溃或取消留下的部分文件。

如果转换很快，而且父级会在返回前等待它结束，设计可以更简单：把 convert_to_pdf 作为一个 Step 执行即可。区分 Step 与 Task 的标准不是动作名称，也不只是耗时长短，而是生命周期和 owner 是否已经分离：仍由当前 Runtime 调用负责等待与收敛的是 Step；移交给 Queue、worker 或 workflow engine 独立负责的是 Task。

Retry 为什么必须停留在正确的层

现在假设 PDF worker 第一次执行崩溃，第二次成功。正确的恢复路径是：

run_18 保持 waiting
turn_1、turn_2 保持 succeeded
step_read、step_save_report 保持 succeeded
task_9 新增 attempt 2

如果系统只能 retry 整个 Run，模型会重新读取文件、重新生成正文并再次保存。即使最后 PDF 正确，系统也无法解释多出来的 token、文件版本和外部写入。

反过来，模型输出解析失败时，也不应 retry PDF Task。失败发生在哪个对象，就先在那个对象的边界内判断能否恢复；只有原有目标已经无法继续，才向上终止 Run 或创建新的 Run。

这个规则并不意味着每层都必须自动 retry。它只要求 retry 不能悄悄改变逻辑身份：

  • transport retry 仍属于同一个 Turn；
  • Tool retry 仍属于同一个 Step；
  • worker retry 仍属于同一个 Task；
  • 用户重新执行目标通常创建新的 Run。

Cancellation 也不是把所有状态改成 cancelled

用户在 PDF 转换期间取消 Run，Runtime 先把 Run 置为 cancelling，并向 task_9 发出 cancellation request，但不能把已经完成的 Turn 和 Step 改写为 cancelled。报告正文确实生成并保存过，这是历史事实。

Task 也不应在收到请求时立刻宣称 cancelled。worker 可能正在写文件，远端转换服务也可能已经产生结果。只有 owner 确认工作停止并处理残留 Artifact 后，Task 才进入相应 terminal state；确认前可以保持 cancelling 或其他明确的过渡状态。

Run 要等自己拥有的未完成工作完成 reconciliation 后，再按产品 policy 进入 terminal state。若 PDF 在取消请求之后才完成，policy 可以选择保留为未交付 Artifact、交付并将 Run 标记为 succeeded，或清理后将 Run 标记为 cancelled；无论选择哪一种，都不能改写已经完成的子对象历史。

因此，取消传播的是意图，不是对所有子对象的状态覆盖。每个 owner 仍要根据自己观察到的事实收敛。

分开以后，查询才有明确答案

同一时刻可以保存如下状态：

Run run_18       → waiting for task_9
Turn turn_1      → succeeded
Step step_read   → succeeded
Turn turn_2      → succeeded
Step step_save   → succeeded, artifact report.md@v3
Task task_9      → running, attempt 2

产品界面查询 Run，知道用户目标还在处理中；模型成本查询 Turn；Tool 可靠性查询 Step 与 Attempt；Queue 运维查询 Task。它们通过 parent、causality 和 Artifact version 关联，但不再争用同一个 status 字段。

Checkpoint 需要保存哪些状态、event log 怎样派生 current snapshot，是后续的持久化问题。分析仓库怎样按 grain 计算指标，则可参考 Agent Activity 建模先明确 Grain。本文先解决 Runtime 语义：谁拥有状态，谁判断完成，失败应在哪一层恢复。

什么时候一个状态已经够用

如果请求只有一次模型调用，不执行 Tool、不产生后台工作，失败后整次重来没有额外副作用，那么 Run 与 Turn 可能是一对一的。实现上可以只保存一条记录，不必为了概念完整创建四张表。

分层的触发条件是生命周期真的开始分离：一个用户目标包含多次模型往返，逻辑动作可能 retry，或工作需要脱离当前请求继续执行。此时继续共用状态，才会让恢复和指标变得含糊。

回到问题

Run、Turn、Step 与 Task 的区别，不在于名字或层级，而在于它们有不同的完成证据和 retry unit。

模型返回，不代表 Tool 已执行；Tool 完成，不代表后台工作已收敛；Task succeeded，也只有在交付了 Run 所需的正确 Artifact 时，才能帮助用户目标完成。

把状态留给真正拥有它的对象后，Runtime 才能在失败时只恢复必要的一层，也能解释当前究竟是在调用模型、确认动作、等待 worker，还是已经完成用户目标。

后续问题

  • Checkpoint 应保存 event、snapshot 还是可重建状态，进程重启后怎样恢复。
  • Event log 与 current snapshot 怎样处理并发更新和乱序事件。
  • Deadline 与 cancellation 怎样跨 Run、Step 和 Task 传播。
  • Run、Turn、Step、Task 的指标怎样进入统一 Trace，又不混淆 grain。
