Agent Memory 三：按 Writer 隔离写入权限

2026/07/14 阅读 次
AgentMemoryData Governance

问题

用户曾明确说：“以后会议尽量安排在下午。”几周后，后台归纳任务发现最近三次会议都在上午，于是把长期偏好改成“上午开会”。

归纳任务没有伪造数据，但它把观察到的行为当成了用户授权的偏好。如果对话内 Agent、后台归纳、批量导入和用户编辑都调用同一个 write_memory，并且都能修改任意记录，那么写入质量只能依赖 prompt 中一句“请谨慎”。只要某个 writer 判断错了，污染就会进入所有后续 Session。

问题不只是“谁登录了系统”，而是这次 mutation 代表谁、依据什么证据、可以改哪类 Memory。

Writer identity 不能由模型自己声明

Memory service 应从受信任的执行环境获得 actor identity，而不是接受模型参数里的 writer: user。一次 mutation 至少要绑定：

actor: background_consolidation
subject: user_42
namespace: preferences.schedule
action: propose_observation
evidence_class: behavioral_observation
source_refs: [calendar_event_7, calendar_event_9, calendar_event_12]

这组信息形成一次受限 capability：某个 actor 只能对指定 subject 和 namespace 执行指定动作，并提交允许的 evidence class。模型可以生成候选内容，不能自行扩大 capability。

四类 writer 不应共享 write-all surface

Writer可以使用的证据合理动作不应拥有的权限
In-loop Agent当前授权 Context 中的用户原话和 Tool Result提交 candidate；在 policy 允许时写入显式事实修改无关 subject 或任意历史版本
Background consolidation已授权历史中的重复观察写入低权重 observation；提出合并或 supersede 建议覆盖用户显式声明
Import job已映射的数据集和字段写入指定 namespace，并保留 dataset provenance越过映射写入其他目录
User edit用户在 Memory UI 中确认的输入更正、撤销或删除自己可管理的记录绕过隐私、retention 或第三方数据规则

这不是给每类 writer 排一个全局优先级。权限必须收窄到 subject、namespace、action 和 evidence；否则“用户编辑最高”也可能被误用来修改别人的记录。

把上午会议的例子走一遍

后台归纳可以提交“最近三次会议发生在上午”这条 observation，因为来源支持它。但当它试图 supersede “用户偏好下午”时，Memory service 会比较 mutation 与 capability：

requested_action: supersede_explicit_preference
actor: background_consolidation
allowed_actions: [append_observation, propose_change]
decision: reject
reason: writer_cannot_override_explicit_user_statement

系统可以保留上午会议 observation，供日程冲突分析使用，也可以生成一条待用户确认的 change proposal；current preference 仍是“下午”。如果用户随后在 Memory UI 中改成“最近改为上午”，受信任的 user-edit actor 才能提交新的显式版本，旧偏好被 supersede 而不是被后台任务静默覆盖。

因此，冲突判断同时看 claim scope 和 provenance。三次上午会议与“长期偏好下午”甚至可能同时为真：前者描述发生过的事件，后者描述安排意愿。系统不应先把两者压成同一种字符串，再靠 writer 排名决定胜负。

最小权限要落实到 mutation

只把不同 writer 分到不同 API key 仍然不够。一把可以写整个 Memory store 的“后台 key”，只是换了凭证名称。真正的最小权限需要在每次 mutation 上验证：

  • actor 是否能代表这个 subject；
  • namespace 是否属于它的职责；
  • action 是 append、propose、supersede、revoke 还是 delete；
  • evidence class 能否支持目标 record type；
  • source refs 是否仍被授权和保留。

检查应由 Memory service 执行，拒绝结果使用稳定 reason code。这样审计才能回答“是谁依据哪些来源试图改什么”，Eval 也能验证越权 mutation 一定失败。

Agent delegation 也不能绕过这层边界。父 Agent 把归纳工作交给子 Agent 时，传递的是缩小后的 capability；子 Agent 不应继承父级所有 Memory 权限，更不能通过自然语言声称自己代表用户。

怎样验证隔离真的有效

除了测试正常写入，还要覆盖反例：后台归纳覆盖显式偏好、import 写错 namespace、in-loop Agent 修改另一个 subject、用户编辑携带未授权第三方数据，以及模型伪造 actor 字段。

关键指标不是 writer 的成功率，而是 unauthorized mutation acceptance rate、provenance completeness 和冲突升级是否正确。一个安全的 writer 可以经常提出候选，但越过 capability 的写入必须稳定失败。

回到问题

上午会议的 observation 并不等于用户撤回了下午偏好。错误之所以发生，是因为后台归纳和用户编辑共享了同一套 mutation authority，系统无法区分“观察到”与“用户授权修改”。

把 actor identity 放在受信任边界内，再按 subject、namespace、action 和 evidence class 发放 capability，后台任务仍能发现变化，却只能追加 observation 或提出建议。真正改变 current Memory 的动作，由拥有相应证据与权限的 writer 完成。

后续问题

  • 同一条 Memory 被更正、撤销或删除时，版本链应该怎样表示。
  • 两个合法 writer 基于旧版本并发修改时，怎样避免 lost update。
  • Retrieval 怎样确保只使用当前有效且允许读取的版本。
