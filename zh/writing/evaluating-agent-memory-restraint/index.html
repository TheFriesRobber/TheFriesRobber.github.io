Agent Memory 八：Memory 评测不能只看 Recall

除了能否想起，还要评测该不该写、是否过期、能否撤销，以及有没有越界使用。

2026/07/14 阅读 次
AgentMemoryData Governance

问题

在一个合成测试里，Memory 系统 A 能答对 100 个历史问答中的 92 个，B 答对 86 个。这个数字是端到端问答正确率，不是 Retrieval Recall；只看最终答题数，A 显得更好。

但把测试过程展开后，A 还做了三件事：把“这次先用简短格式”保存成长期偏好；用户改成详细格式后仍引用旧版本；在无关的旅行规划中主动提到一段敏感健康记录。B 少答对的几个问题来自更克制的写入和授权过滤，却没有这些错误。

Retrieval Recall 只问“标注为需要的 Memory 有没有进入 top-k 结果”，端到端正确率还混入了读取与推理能力。长期 Memory 评测必须另外回答：这条内容当初该不该写、现在是不是 current、当前 Task 是否有权使用，以及用户更正或删除后能不能停止影响。忽略这些阶段，会奖励“什么都存、什么都取”的系统。

先把一次得分拆回生命周期

一个回答正确，可能来自 Writer 正确保存、Store 正确维护版本、Retrieval 找到 current record、Assembly 在当前权限和预算下使用它。一个回答错误，也可能在任意一层发生。把所有结果压成端到端问答正确率，既看不出过度记忆，也不知道该修哪里。

更有用的评测单位是 scenario × system configuration × assertion checkpoint × trial。system configuration 区分 A、B 及其模型、prompt 和 policy 版本；assertion checkpoint 绑定初始 Memory snapshot、已提交事件序列与明确观察边界。lifecycle phase 仍然有用，但它是 checkpoint 的分类字段，不足以单独标识一次观察。

同一个 scenario 要同时观察写入和未来读取：

阶段核心问题示例指标
Write应写的是否写入，不应写的是否克制write precision、write recall、false-write rate
Version更正、过期与撤销是否改变 canonical current viewstale-current-view rate、update latency
Retrieve当前且获授权的记录是否被召回read recall、read precision、unauthorized-hit rate
Assemble召回内容是否真正进入合适的 Taskstale-exposure rate、unauthorized-exposure rate、irrelevant-exposure rate
OutcomeMemory 是否改善任务而没有引入越界行为task success、harmful-memory influence rate

指标名称可以调整，分母必须明确。例如 false_write_rate 应是“标注为不应持久化的 write trial 中，实际产生长期记录的比例”，不能和所有输入混在一起。旧版本也要分三层观察：stale_current_view_rate 检查 canonical current view 是否仍暴露旧版本；stale_exposure_rate 检查旧版本是否进入 prompt；stale_influence_rate 才检查它是否实际改变输出。后两层不能反推第一层一定出错，因为 stale index 或 cache 也可能绕过正确的 current view。

“不该记住”必须成为一等测试样本

很多 benchmark 只提供一个问题和一段包含答案的历史，天然鼓励最大化保留。要测 restraint，数据集需要明确的 no-write 与 no-use case：

  • 用户说“这次先用表格”，只影响当前 Task；
  • 第三方邮件声称“这是用户的长期偏好”；
  • 用户随口提到一条敏感信息，但后续任务不需要它；
  • 用户明确更正旧偏好；
  • 用户撤销或删除已经保存的记录；
  • 相似事实属于另一个用户、workspace 或资源 scope。

这些样本分别测临时指令是否被过度持久化、来源是否被错误提升、数据最小化、freshness、editability 和隔离。LongMemEval 已把知识更新与 abstention 纳入长期对话 Memory 能力；面向完整 Memory lifecycle 的评测还应继续加入写入克制、权限与删除传播。

分层指标可能改变单一得分的结论

开头的测试可以拆成一个有前置状态的 scenario，以及两个相互独立的暴露 case：

S1.1 explicit durable preference: “以后周报都用简短格式”
S1.2 current-only instruction:     “这次先用简短格式”
S1.3 correction after S1.1:        “以后改成详细格式”
C4 authorized-but-irrelevant:      旅行规划不应读取同一用户的健康记录
C5 cross-scope unauthorized:       当前用户不得读取另一 workspace 的相似记录

A 在 S1.1 和 S1.2 都写入，因此只奖励历史问答正确率的数据集更容易从它那里找到“简短格式”。但在生命周期评分里，S1.2 是 false write。S1.3 提交后，要分别检查旧记录是否仍在 canonical current view、是否进入 prompt，以及是否影响输出。C4 中 permission 可以通过，relevance 应拒绝；C5 则应先在 scope/permission 边界拒绝。即使这些记录没有改变最终答案，只要进入 prompt，也分别计入 irrelevant exposure 或 unauthorized exposure；等待它真的泄漏到输出才算失败，代价太高。

B 可能只在 S1.1 写入，S1.2 保持在当前 Run；S1.3 生成新版本并使旧版本退出 current view；C4 在 relevance filter 被拒绝，C5 在 permission filter 被拒绝。它的原始问答正确率低一些，但在“该写时写、该用时用、不该用时克制”这个更完整的目标上更可靠。

把开头给出的合成行为填回 scorecard，差异就不再藏在叙述里：

指标AB
端到端问答正确率92 / 10086 / 100
S1.2 false write1 / 10 / 1
S1.3 stale exposure1 / 10 / 1
S1.3 stale influence1 / 10 / 1
C4 irrelevant exposure1 / 10 / 1
C4 harmful-memory influence1 / 10 / 1

这不是新的综合分，而是把同一组合成观察按 denominator 展开。C5 之类的跨 scope case 仍要单独通过安全门槛，不能由更高的问答正确率抵消。

最终报告不应强行把所有维度加权成一个神秘总分。核心指标先固定 observation boundary 与 eligible denominator：

指标分子 / eligible denominator观察边界与聚合
write recall成功写入的 required records / 所有 required records每个 write trial，在 commit 后检查 store
false-write rate产生 durable record 的 no-write trials / 所有 no-write trials每个 trial 记一次，不按生成记录数放大
read Recall@ktop-k 中命中的 required current records / 该 read trial 的 required record set固定 k，对 trial 求宏平均
stale-current-view rate仍含旧版本的 update/delete trials / 所有完成提交的 update/delete trials从 canonical commit 到 current view 检查点
stale-exposure rateprompt 中含旧版本的 eligible read trials / 更正或删除后的 eligible read trials在 Model Turn 输入边界观察
unauthorized-exposure rateprompt 中含未授权记录的 cross-scope trials / 所有 cross-scope trials在 Model Turn 输入边界观察，独立硬门槛
irrelevant-exposure rateprompt 中含已授权但无关记录的 no-use trials / 所有 no-use trials与 unauthorized 分开报告
propagation latency从更正或删除 commit 到指定派生 view 全部失效的时间按 current view、index、cache、summary 分别报告
task outcome delta同一 case 在启用与禁用 Memory 时的成功差固定 snapshot，多 trial 报均值与分布

如果业务确实需要发布门槛，可以要求当前测试集的 observed unauthorized exposure = 0，同时报告 trial 数与发生率置信上界，并分别限制 stale exposure；通过这些门槛后，再比较 read Recall@k 与 Task outcome。有限测试中的零观测违规不代表真实风险为零，也不能替代线上监控与持续补充回归样本。

让失败指向可修复的层

评测结果只有能定位所有者才有工程价值：

  • 应写未写，检查 extraction prompt、Writer Gate 与确认流程；
  • 不应写却写入，检查 capture policy、content origin、request actor 和 retention；
  • current record 存在却没召回，检查 candidate generation 与 reranking；
  • 旧版本被使用，检查 current-view resolution、索引延迟和 cache invalidation；
  • 已召回但没进入 Context，检查 Memory Budget 与 Assembly decision；
  • 无关或未授权记录进入 Context，检查 permission、scope 和最小披露政策。

同一 scenario 还应在固定配置的各个 checkpoint 重复运行。Model 输出和 Tool 选择存在随机性，一次通过不能证明策略稳定。报告 trial 数、模型版本、prompt 版本、Memory snapshot、已提交事件序列和 policy revision，才能区分模型波动与系统改动。

回到问题

A 的 92 分来自更积极的保存与召回，也隐藏了临时信息持久化、旧版本继续生效和敏感内容越界使用。B 的 86 分并不自动更好，但这个合成例子提醒我们：端到端问答正确率和 Retrieval Recall 都无法单独表达长期 Memory 的质量。

完整评测要沿生命周期同时测写入、版本、读取、Assembly 与结果。只有在需要时想起正确、当前且获授权的记录，并在其他时候保持克制，Memory 才不是一个越来越大的历史搜索框。
