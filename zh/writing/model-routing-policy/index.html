Context Engineering 四：Model Routing 怎样安全 Fallback

将模型选择建模为可解释 policy，并明确 fallback 后哪些执行状态仍然可以复用。

2026/07/17 阅读 次

问题

假设一个 Agent 要读取截图，整理其中的问题，再调用 create_ticket。这里的 create_ticket 是由本地 Runtime 执行的 client Tool：provider request 只生成 Tool proposal，本身不能执行 provider-side Tool 或产生票据副作用。这次执行要求模型同时具备：

  • 图片输入能力。
  • 当前 Tool Schema 所需的结构化输出能力。
  • 足够容纳截图说明、最近对话和 Tool definitions 的 Context window。
  • 符合当前数据区域和成本预算。

Runtime 先调用主模型，但请求 timeout。最直接的 fallback 是把请求中的 model name 换成备用模型，然后原样重发。

这条路径可能再次失败：备用模型不接受图片，支持的 Schema 子集不同，Context window 更小，或者不满足这次任务的数据政策。即使请求成功，Runtime 也未必知道主模型在 timeout 前是否已经产生了完整 Tool Call，能否继续使用已经收到的 partial output。

所以 Model Routing 不只是从一个字符串切换到另一个字符串。它需要先回答两件事：哪个模型满足本次执行契约，以及当前失败是否允许换模型继续。

先过滤不合格模型，再比较成本和延迟

如果先按单价或平均延迟给所有模型排序，Router 可能选出一个便宜但无法完成任务的候选。更稳妥的顺序是先从 RunSpec 或当前任务中提取硬约束：

required modalities
required tool / structured-output features
estimated input and reserved output budget
required context capacity and maximum output
data policy and region
allowed provider set
provider-side effect policy

模型目录则为每个候选维护 capability profile。它描述已知能力、限制和当前健康状态，但不是永远正确的静态表；模型版本、provider 行为和组织配置发生变化时，profile 也要更新并带 revision。

Router 先排除不满足硬约束的候选，再在剩余集合中根据延迟目标、成本预算、质量等级和实时可用性做选择：

all candidates
→ capability and policy eligibility
→ latency / cost / quality ranking
→ selected route with fallback set

这让“不可用”和“不优先”成为不同结果。一个不支持图片的模型不是得分较低，而是对当前请求不合格。

Routing Decision 要能解释为什么选它

回到截图任务。Router 可以生成一条概念性的 decision record：

{
  "operation_id": "model_op_17",
  "requirements": {
    "modalities": ["text", "image"],
    "tool_contract": "ticket_tools@revision_8",
    "estimated_input_tokens": 18000,
    "reserved_output_tokens": 4000,
    "required_context_capacity_tokens": 22000,
    "minimum_max_output_tokens": 4000,
    "provider_side_effects": "none",
    "data_policy": "region_a"
  },
  "selected": "model_route_primary",
  "eligible_fallbacks": ["model_route_secondary"],
  "excluded": [
    {"route": "model_route_fast", "reason": "image_input_unsupported"},
    {"route": "model_route_large", "reason": "cost_budget_exceeded"}
  ],
  "policy_revision": 6
}

estimated_input_tokens 是当前 Assembly 结果的估算，不是模型容量；Router 用它加上 reserved_output_tokens 得到所需 Context capacity，同时单独检查候选的 max output 是否至少满足 minimum_max_output_tokens。把这几个值压成一个 min_input_tokens，会让“请求有多大”和“模型能容纳多少”重新混在一起。

这里记录的是 route，而不一定是一个裸 model name。Route 还可以固定 provider、模型版本、Adapter profile、区域和参数上限。这样 Trace 能区分“Router 做了错误选择”和“选中的模型调用失败”，Eval 也能按同一份 routing policy 比较结果。

Fallback 取决于失败发生在哪里

并不是所有 model failure 都适合换模型重试：

观察到的失败Router 可以怎样处理不能直接推断什么
请求前发现 capability 不匹配改选另一个合格候选原候选只是“质量稍差”
Provider 明确返回 rate limit 或 unavailable在预算内切换合格 route第一次调用产生了可用结果
Timeout，未收到完整响应无 provider-side effect 时建立新 attempt；否则先查询或对账Provider 一定没有完成生成或外部动作
已收到 partial text 或 partial Tool Call丢弃不完整 item，再从稳定边界重试partial JSON 可以安全续写
输出完整但质量检查失败repair、补充 Context 或重新规划多换几个模型必然会变好
数据政策或权限不允许终止或缩小任务可以用更便宜模型绕过 policy

这里的 timeout 只是 Runtime 的观察：它说明在 deadline 内没有拿到可确认结果，不证明 provider 端从未完成计算。对于本文只生成 client Tool proposal 的 route，model request 本身没有外部副作用；Runtime 仍要先确定哪些 item 已完整落入 Event Log，才能决定 fallback 从哪里继续。

只有 route capability 明确保证 provider_side_effects=none 时，安全默认才是让新 route 在同一个 logical model operation 下建立新 attempt：只复用已经确认的输入事实，不拼接两个 attempt 的不完整输出。如果 route 允许由 provider 执行的 server Tool 或 remote MCP Tool，request timeout 还可能留下状态未知的外部动作；Runtime 必须根据 provider response identity 或 Tool Execution identity 查询和对账，或者依赖明确的幂等恢复。这里的分类依据是执行 owner 与副作用 contract，而不是 Tool 是否采用 MCP 协议。无法确认时保持 unknown，不能直接 fallback 再执行一次。跨 Tool 执行的总体 retry budget 和 failure recovery 仍由 Runtime 的分层恢复策略管理。

切换模型后，输入也需要重新检查

两个模型都被标记为“支持图片和 Tool”，不代表同一份最终请求可以原样发送。Fallback 前至少要重新验证：

  • 新 route 的 Context 上限是否容纳当前 Assembly 结果。
  • Tool Surface 经对应 Adapter 转换后是否仍保留必需约束。
  • System instruction、message role 和 structured output 是否可以无损表达。
  • 已完成的 Tool Result 是否能在新协议中保持 call identity 和内容边界。
  • 输出预算、采样参数和停止条件是否仍然有效。

如果 Context 过大，系统可以回到结构化降级；如果必需 Tool Schema 无法表达，应该返回 incompatible_route，而不是静默删除约束后继续。

这一步解释了为什么 Router 与 Provider Adapter 必须分开：Router 决定“选哪个候选”，Adapter 负责回答“如何把 canonical request 表达成该 provider 的协议”。Adapter 报告不兼容后，Router 可以改选；Adapter 本身不应因为转换失败就私自换模型。

把开场例子走一遍

截图任务的完整选择与 fallback 可以是：

1. 从 RunSpec 读取图片、Tool contract、Context、数据政策与 provider-side effect 要求。
2. 排除不支持图片、不满足区域政策或会在 provider 内执行 Tool 的 route。
3. 在合格候选中选择 `provider_side_effects=none` 的主 route，并保存 Routing Decision。
4. 主 attempt timeout，且没有完整 response item 被接受；该 route 本身不会执行外部动作。
5. 将失败分类为 transport_timeout，消耗一次 fallback budget。
6. 选择仍满足全部硬约束的 secondary route。
7. 用 secondary Adapter 重新渲染同一份 canonical request。
8. 新 attempt 返回完整 Tool Call，Runtime 才进入 Tool Lifecycle。

如果第 4 步已经收到完整、通过校验的 create_ticket Tool Call，就不应仅因最终文字流中断而让另一模型再生成一个新的票据提案。是否执行原 Tool Call，应由 Runtime 根据已持久化 item 和当前任务状态决定，而不是由 Router 猜测。若换成允许 provider-side Tool 的 route，这条示例路径不再成立：timeout 后必须先查询或对账已有执行。

怎样验证 Router 没有把问题藏起来

Model Routing 的 Eval 不应只统计“最终有没有回答”。至少要按 failure class 观察：

  • 硬约束过滤是否漏掉不兼容 route。
  • 每次选择和排除是否能由 decision record 解释。
  • Fallback 是否仍满足原始 capability 与 policy。
  • Timeout、rate limit、unsupported feature 和质量失败是否触发了不同动作。
  • Fallback 次数、额外延迟和成本是否在预算内。
  • 两个 attempt 的 partial output 是否被错误拼接或重复消费。

否则，较高的最终成功率可能只是来自无限 fallback，同时隐藏了成本失控和偶发重复 Tool Call。

回到问题

安全的 Model Routing 需要把任务要求编译成硬约束，先过滤不合格候选，再按成本、延迟和质量排序。发生失败后，它还要根据 failure class 判断是否允许 fallback，并重新验证新 route 与原执行契约是否兼容。

换一个 model name 只改变了请求目标；Routing Decision、兼容性检查和 attempt 边界，才让这次切换仍然属于同一个可解释的 Agent Run。

后续问题

  • Canonical request 应怎样通过 Provider Adapter 转换为不同消息与 Tool 协议。
  • Tool Schema 经不同 Adapter 转换后，怎样检测 validation drift。
  • Service、model、Tool 与 plan failure 怎样共享总体 retry budget。
