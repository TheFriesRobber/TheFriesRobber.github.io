Agent 23：Artifact 的引用、保留与删除必须分层

区分 Message reference、既有下载能力、Artifact 逻辑删除、lineage retention 与限定 target set 的 provider 对象版本删除。

2026/07/27 更新于 2026/07/27 阅读 次
Agent ProductionAgentArtifactsData Governance

问题

用户把一份合同上传到 Agent，让它生成摘要和最终报告。一周后，用户删除了最初的上传消息，并要求删除原文件。

Conversation service 删除了 Message 上的附件引用，Artifact service 把原文件标成 deleted，但此前签发的下载 URL 仍能访问；对象存储启用了版本化，删除当前 key 只写入了 delete marker；最终报告又因为已交付而仍需保留。

如果系统把这些动作都叫“删除文件”，它就无法回答用户最重要的问题：现在只是聊天里看不见了、新访问已被阻止、旧访问能力也已失效，还是目标对象版本已经按 provider contract 永久删除？

删除需要沿不同 owner 的状态逐步收敛：先移除引用并阻止新访问，再单独收敛已签发的访问能力；Artifact owner 根据 lineage 与 retention 定义删除 target set，最后由 Blob owner 记录每个目标对象版本及受治理副本的 provider deletion outcome。

Reference 删除只改变谁还在引用 Artifact

同一个 Artifact revision 可以被多个对象引用：

Message message_8 ───────┐
Task task_12 ────────────┼─> artifact_source_17@1
Workspace ws_9 ──────────┘

删除 message_8 时，Conversation owner 只能权威地移除这一条 reference。它不能据此推断 Task 已结束、Workspace 不再使用该输入，或 Artifact 已满足保留期。

因此，reference 应有独立 identity 和状态：

reference_id: msgref_31
owner: message_8
artifact: artifact_source_17@1
state: detached
detached_at: ...

Artifact service 随后重新计算有效引用和 policy，但不能让调用方通过文件名、旧 path 或 Blob hash 绕过这项判断。相同 bytes 可能属于不同 tenant 或不同 Artifact；content identity 不等于业务 owner。

访问撤销与字节回收是两个提交边界

Artifact 进入删除流程后，首先要阻止新的正常读取。一个概念性状态机可以是：

active
  → delete_requested
  → new_access_blocked
  → existing_capabilities_revoked | pending_expiry | unknown
  → retention_blocked | erase_eligible
  → erasing
  → provider_deleted | deletion_failed

new_access_blocked 是第一个业务可见边界：新的 resolve、download 和 materialize 请求被拒绝，依赖该 Artifact 的 capability surface 也不再暴露它。它不证明已经签发的 bearer capability 失效，也不等于 provider 已删除对象版本。

下载 URL 同样只是访问能力，不是 Artifact identity。更容易撤销的设计是让客户端持有短期、绑定 subject、Artifact revision 和 audience 的 capability，并在兑换或下载边界重新检查 Artifact 状态。若直接签发对象存储的 presigned URL，是否能立即撤销取决于签名 credential、bucket policy、对象状态和缓存路径；系统不能只把数据库改成 deleted 就宣称所有既有 URL 已失效。

Artifact owner 因而要追踪已签 capability 的最大有效期、credential/policy 撤销结果和无法枚举的暴露窗口。只有旧能力已被强制撤销，或全部经过可证明的 expiry，状态才是 existing_capabilities_revoked。否则保持 pending_expiry 或 unknown，并把最晚 expiry 或无法确定的原因返回调用方。

因此，删除 API 的响应应区分：

{
  "artifact": "artifact_source_17@1",
  "logical_state": "new_access_blocked",
  "existing_capabilities": "pending_expiry",
  "provider_deletion": "pending"
}

用户可以立即得到“不会再签发新访问”的结论，同时看见旧 URL 的剩余暴露窗口和 provider 删除仍在进行。只有 existing_capabilities_revoked 成立，系统才可以报告访问已完全撤销。

Lineage 与 retention 决定擦除集合

原合同可能已经产生两个派生 Artifact：

artifact_source_17@1
  ├─ extracted_text_18@1
  └─ final_report_25@3

Lineage 证明派生关系，却不自动定义级联删除。最终报告可能已经交付并受独立 retention policy 约束；抽取文本可能是可逆中间数据，需要随源文件删除；审计记录可能只能保留不含原始内容的 tombstone。

Artifact owner 应把删除请求编译成带理由的计划：

对象决策原因
artifact_source_17@1revoke + erase when eligible用户请求删除原文件
extracted_text_18@1revoke + erasepolicy 认定为可逆派生物
final_report_25@3retain已交付，拥有独立业务 owner
lineage edgeretain as tombstone证明报告来源，但不保留源 bytes

如果存在 legal hold、最低保留期、仍活跃的 Workspace reference 或另一个合法 owner，Artifact 进入 retention_blocked。阻塞原因、policy revision 和重新评估时间必须持久化，不能靠一次失败的删除 Job 留在日志里。

Blob 删除需要逐版本、逐副本 evidence

Artifact 获准删除后，Blob owner 才回收不可变内容。它必须先确认没有其他合法 Artifact reference 指向同一 Blob；内容去重不应让一个 tenant 的删除请求移除另一个 tenant 仍在使用的对象。

删除计划还要先固定 target set：primary object 的哪些 version、由系统管理的 replica、备份与导出副本是否在本次承诺内，以及各自的 owner 和 retention。未纳入 target set 的备份不能被一句“Blob 已删除”掩盖；无法由当前系统控制的副本要作为明确 limitation 返回。

版本化对象存储还需要逐个处理物理版本。以 Amazon S3 为例，对启用版本控制的对象执行不带 version ID 的简单删除，通常会插入 delete marker，而不是永久删除已有版本。业务层因而要分别记录：

blob_ref: sha256:ab12...
target_versions:
  - version_id: v7
    outcome: provider_deleted
  - version_id: v5
    outcome: retention_blocked
delete_marker:
  observed: true
provider_deletion_state: partial

not found 也只能作为某个查询边界上的 observation。系统结合明确的 version ID、provider 的永久删除响应和后续不可寻址检查，才能把它提升为该 provider contract 下的 provider_deleted evidence。删除 timeout 则保持 unknown 或 erasing，由同一个 deletion operation identity 继续查询，不能创建新 Artifact identity 掩盖结果。

provider_deleted 只表示 target set 中的对象版本已按 provider 服务语义永久删除、不能再通过该对象身份恢复或寻址。它不证明底层介质发生逐字节擦写。只有 provider contract、独立审计或适用合规证明覆盖介质与所有受治理副本时，产品才应使用更强的“物理擦除完成”表述。

Provider 删除完成后，可以保留最小 tombstone：Artifact identity、删除请求 actor、target set、policy revision、完成时间和不含敏感内容的 deletion evidence。它用于证明发生过哪项治理动作，不应继续提供内容访问路径。

同一删除计划必须按 owner 逐层提交

开场中的删除按 owner 推进：

  1. Conversation owner 删除 message_8 → artifact_source_17@1，但不声称 Artifact 已删除。
  2. Artifact owner 接受用户请求，把源文件和可逆抽取物推进到 new_access_blocked，新的 resolve 与 download 被拒绝；旧 URL 保持 pending_expiry，直到 credential/policy 撤销或 expiry evidence 成立。
  3. 已交付报告因为独立 retention 继续存在；其 lineage 改为只保留 tombstone。
  4. 删除计划把 primary object versions 和系统管理的 replica 纳入 target set，并把不受当前系统控制的备份列为 limitation。
  5. Blob owner 逐版本删除并验证；若某一版本受 retention 阻塞，整体状态保持 partial。只有 target set 全部获得 evidence 后，Artifact 才报告 provider_deletion=complete。

这条链允许不同状态短时间不一致，但每个差异都有 owner、原因和下一步 reconciliation。它也避免为了立即返回“删除成功”，把逻辑不可见误写成物理擦除。

回到问题

用户删除上传消息时，系统首先失去的是一条 Message reference。删除原文件的请求随后阻止新访问，并单独追踪旧 URL 是否已撤销或到期；再依据 lineage、有效引用和 retention 计算 target set。最终报告可以按自己的 owner 继续保留，原文件与可逆派生物则由 Blob owner 逐版本清理。

如果对象存储只写入 delete marker、旧 capability 仍有效，或仍有版本受 retention 阻塞，系统只能分别报告 new_access_blocked、pending_expiry 和 provider deletion pending/partial。只有 target set 中的对象版本与受治理副本都有可验证的永久删除结果，才能报告 scoped provider deletion complete；这仍不是底层介质擦写证明。

Artifact 删除因此不是一次 DELETE 调用，而是一条从 reference、capability、业务 identity 到 scoped provider deletion evidence 的可恢复收敛协议。
