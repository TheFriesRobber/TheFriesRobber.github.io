Agent 的最小内核：Loop、Turn 与执行状态

从一次结果未知的 Tool 写入出发，用最小状态模型解释 Agent Loop、Model Turn、Tool Execution 与 Attempt 的边界。

2026/07/24 阅读 次
Agent CoreAgentRuntimeState Machine

问题

设想一个最小 Agent：

while (true) {
  const response = await model(messages);
  if (!response.toolCalls.length) return response;

  for (const call of response.toolCalls) {
    messages.push(await tools[call.name](call.arguments));
  }
}

它已经能调用 Tool，也能把结果交回模型。但如果 write_note 已经把内容写进外部系统，响应却在返回前超时，这个循环只看到一个 rejected promise。它无法回答最关键的问题：这次写入是失败了，还是结果未知？

如果把两者都当成失败并直接 retry，第二次调用可能重复写入；如果把 timeout 当成成功，又可能向用户报告一个从未发生的动作。Agent Runtime 的最小内核因此不是 while，而是一套能区分“模型提议、执行尝试和外部事实”的协议。

Tool Call 只是模型提出的动作

模型输出的 Tool Call 表达的是“我建议调用 write_note，参数如下”。它不是授权，也不是外部动作已经发生的证据。

从提议到事实至少跨过三个 owner：

边界拥有什么能证明什么
ModelTool Call proposal模型希望执行某个动作
Runtimevalidation、authorization 和执行 Attempt某次尝试被接纳、启动或返回
External systemnote、payment、file 等业务状态副作用是否真正发生

Pi 的当前 Loop 已经把模型轮次、Tool Call、Tool Result 和 turn-boundary 控制流分开；agent-loop.ts 也会发出 Tool execution event。不过它没有独立的 logical operation、Tool Execution 或 Attempt 状态对象。下面的状态模型是建立在 Pi 控制流之上的设计建议，不是当前 API 的描述。

后文统一使用下面的层级：

Task
└─ Run：Agent Loop 的一次执行实例
   ├─ Model Turn：一次模型请求及其响应
   └─ Tool Execution：一个已授权 proposal 的逻辑执行
      └─ Attempt：一次已经开始的物理 dispatch

logical operation：跨 Turn 或 Tool Execution 关联同一业务意图的稳定身份

Task 表达用户目标，Run 从一次输入开始，跨越若干 Model Turn 与 Tool Execution，直到本次 Loop 收敛。每次 retry 都在同一个 Tool Execution 下创建新 Attempt；logical operation 则是跨层关联键，不应被误画成 Attempt 的直接父对象。这些对象不必都成为公开类，但日志、评测和恢复必须知道自己正在统计哪一层。

一次 Tool 执行需要三种身份

处理 timeout 和 retry 时，最容易混淆的是三种 identity：

  • logical operation：用户或业务真正要求完成的稳定意图，例如“把这段内容写入 note-42”；
  • Tool Execution：Runtime 对一个已授权 Tool proposal 的逻辑执行；
  • Attempt：Tool Execution 为完成动作实际开始的一次物理 dispatch。

第一次 write_note timeout 后，logical operation 与 Tool Execution 仍是同一个，但 Attempt 已经结束。若幂等契约与当前 evidence 允许再次调用，应产生新的 Attempt ID，而不是把历史覆盖掉。

operation op-17
└── tool execution tool_exec-1
    ├── attempt a1 → timeout → observed outcome unknown
    └── attempt a2 → 只有在确认安全后才允许创建

这个区分让两个看似矛盾的指标同时成立：Attempt timeout/unknown rate 可以增加，而 Tool Execution 与 logical operation 最终仍可能成功。后续的可观测性、评测和成本归因也必须沿用同一 grain。

跨过外部 Effect 边界后，Timeout 默认只能推出结果未知

函数返回值描述的是 Runtime 观察到什么，不一定描述外部世界发生了什么。若 timeout 发生在 dispatch 前、validation 阶段，或能证明 handler 尚未启动，则可以确认没有产生副作用；只有已经跨入不可确认的外部 effect 边界后，timeout 才默认意味着 unknown。

对于纯查询，timeout 后重新查询通常不会改变业务状态；对于幂等写入，Runtime 可以用稳定 operation key 重试；对于没有幂等或查询接口的写入，安全状态只能是 unknown。

proposal 在 preflight 阶段先经过 proposed → rejected | authorized。authorized proposal 先创建 Tool Execution；Runtime 真正开始物理 dispatch 时才创建 Attempt。单个 Attempt 的概念状态从这里开始：

dispatching
  → observed_succeeded
  → observed_failed
  → observed_unknown

这里的 observed_failed 必须有证据证明动作没有生效，或证明失败发生在副作用之前。observed_unknown 则明确表示：Attempt 没有给出可用结论，不能自动把它变成 failed。Attempt 的原始观察不可覆盖；Tool Execution 在汇总 Attempt 与后续 effect evidence、完成必要的 query/reconcile 后，才更新自己的 current verdict。

回到 write_note：如果外部系统支持用 operation key 查询，Runtime 先查询 op-17。查到 note 已存在，Attempt a1 仍保留“当时观察为 unknown”，但 effect evidence 与 tool_exec-1 的 verdict 收敛为 succeeded；查到明确未执行，才允许创建新 Attempt；无法查询时，保持 unknown，并把不确定性暴露给上层。

Cancellation 不会改写已经发生的事实

对已经启动并跨过外部 effect 边界的 Attempt，取消和 timeout 有相同限制。Abort signal 可以请求 handler 尽快停止，却不能回滚已经提交的 HTTP 请求、数据库事务或远端任务。尚未开始 dispatch 的 Tool Execution 则可以明确停止，此时根本不创建 Attempt。

因此 cancellation 是独立的控制状态，不是与 succeeded、failed、unknown 并列的 effect outcome。它至少包含两件事：

  1. Runtime 不再启动新的工作；
  2. 已启动的 Attempt 协作收敛，外部 effect 继续按 succeeded、failed 或 unknown 记录。

只有尚未 dispatch 时，才可以把 Tool Execution 结算为 cancelled_before_dispatch，并且它没有 Attempt。一旦创建 Attempt 并越过 effect boundary，就只能记录 cancellation_requested，同时保留 Attempt 的独立 observed outcome 和 Tool Execution 的 current verdict。若 dispatch 已开始但能证明 effect 没有发生，Attempt 可以 observed failed；把 cancelled 当成所有子动作的最终业务结果，会丢失真实历史。

Loop 什么时候可以停止

“模型没有继续调用 Tool”只是一个停止候选，不是唯一条件。Runtime 还要确认：

  • 没有必须处理的 steering 或 follow-up；
  • 没有仍由当前 Run 拥有的子任务；
  • 没有必须在返回前暴露的 unknown effect；
  • 当前结果满足宿主定义的终止策略。

Pi 当前 Loop 会在 turn boundary 检查 steering，并在本来准备结束时检查 follow-up；这说明停止本身就是协议的一部分，而不是简单的 break。具体的耐久恢复、分布式 Job 和客户端重连属于后续文章，但它们都应该消费这里的 logical operation、Tool Execution、Attempt 和 outcome，而不是另造一套身份。

实现依据可参考 Pi 的 agent-loop.ts 与 types.ts。

回到问题

一个能调用 Tool 的 while 循环只描述了控制流，没有描述执行事实。遇到 write_note timeout 时，正确的问题不是“要不要再跑一次函数”，而是：

  1. 这是哪个 logical operation、Tool Execution 和 Attempt？
  2. timeout 发生在副作用之前、之后，还是无法判断？
  3. 哪个 owner 能查询或修复外部事实？
  4. 当前证据允许 retry、reconcile，还是只能保持 unknown？

当 Runtime 能回答这四个问题，retry、取消、终止和后续恢复才有共同语义。Loop 仍然可以很小，但它不再把函数返回误认为整个世界的状态。
