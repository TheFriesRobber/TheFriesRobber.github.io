Agent Runtime 十二：为 Middleware Hook 定义执行契约

2026/07/15 阅读 次
AgentRuntimeMiddleware

问题

一个 Agent Runtime 在调用模型前注册了三个 Hook：

  • capability policy 根据当前权限移除不可用 Tool；
  • request transformer 把内部请求渲染成 provider payload；
  • tracing 记录模型实际看到了哪些 instructions 和 Tool 的结构化信息，而不是默认保存完整敏感内容。

初始 Tool 候选是：

read_file、write_file、delete_file

当前用户只有读取和写入权限，delete_file 不得进入模型输入。如果 Hook 只按注册顺序依次执行，就会出现几个不同结果：

transform → policy
provider payload 已经包含 delete_file，之后修改内部列表也来不及

trace → policy → transform
trace 记录了一个模型实际没有看到的 Tool surface

policy → transform → trace
policy 先收窄能力，trace 记录最终请求

三个 Hook 单独看都合理，交换顺序后，安全性和可观测事实却一起改变。beforeModel 这个名字只说明回调发生在模型之前，没有说明谁可以修改什么、谁能阻断调用，以及 tracing 应观察修改前还是修改后的请求。

所以 Hook 能否成为稳定 extension point，取决于 composition contract，而不是 Runtime 暴露了多少个回调名称。

注册顺序不能代表执行语义

把 Hook 存进数组，再按顺序调用，是最容易实现的机制：

for hook in before_model_hooks:
    request = await hook(request)

问题在于，这段代码让“谁先注册”同时决定了 policy 优先级、数据修改权和观察口径。新增一个 plugin，甚至只是调整初始化顺序，都可能改变最终 Tool surface。

更稳妥的做法是先定义 phase，再允许同一 phase 内使用明确的 priority 或 dependency：

trusted context
  → policy decision
  → request transformation
  → observation scope opens on the final request
  → model call
  → result normalization
  → output policy
  → observation scope closes with the final result

这不是要求所有 Runtime 都采用同一套阶段名。它表达的是一个更基本的约束：应在渲染或发送请求前，依据可信权限收窄能力；transformation 不能重新扩大 policy 已经决定的能力；observer 只能在最终请求形成后打开 span，并在结果归一化后关闭，从而明确自己观察的是哪个版本。

Hook 的 phase 表达权限与事实边界；数组中的注册位置不应该悄悄改变这些边界。

先区分 Hook 能做什么

Hook 容易失控，通常不是数量太多，而是每个回调默认拿到了同样大的权力。可以先按行为分成几类：

类型可以做什么不应该做什么
Policyallow、deny、要求确认或收窄能力静默增加 Tool 或伪造 trusted context
Transformation从已批准输入产生新的 typed value修改身份、权限与审计主体
Controlshort-circuit、fallback 或选择明确分支返回一个无法区分于正常结果的任意字符串
Observation记录 event、metric 和 trace改写业务结果或偷偷触发新的业务动作

这里不是要建立抽象分类学，而是限制修改权。Tracing 如果只需要读取最终请求，就不应拿到可变 request；request transformer 如果只负责 provider shaping，就不应能够替换 Runtime 注入的 subject 或 credential。

一种简单做法，是让 transformation 返回新值，而不是共享可变对象：

import asyncio


decision = policy.evaluate(context, request)
if decision.denied:
    return denied_result(decision.reason)

provider_request = transform(decision.allowed_request)
with trace.model_span(provider_request) as span:
    try:
        response = await model.generate(provider_request)
    except asyncio.CancelledError:
        span.record_cancelled()
        raise
    except BaseException as error:
        span.record_error(error)
        raise
    else:
        span.record_result(response)

这里的 model_span 是概念接口，不对应某个 SDK 的具体 API。例子假设 record_* 和 scope cleanup 是 no-throw 或先写入本地 buffer：observation 失败会被单独记录和重试，不能覆盖已经得到的模型结果、原始异常或 cancellation。它要表达的是：observation 在最终 provider request 形成后开始，无论模型成功、抛出异常还是被取消，同一个 observation scope 都能正确关闭。

回到开头的例子，policy 先得到三个候选 Tool 和可信权限，输出只包含 read_file、write_file 的 allowed request；transformer 只能渲染这个集合；trace 记录最终 provider request 的 Tool 名称或稳定 hash。delete_file 不会因为 transformer 重新读取原始 registry 而回来。

Short-circuit 必须是可见结果

Policy 拒绝高风险 Tool、缓存命中跳过 model call、或预算耗尽直接结束当前阶段，都可能需要 short-circuit。

如果 Hook 只返回 None 表示“不要继续”，调用方很难区分拒绝、缓存命中和 Hook bug。更清楚的 contract 是返回 typed outcome：

continue(transformed_request)
deny(reason, policy_id)
require_approval(action_id)
use_cached(response_id)
fail(error_class, retryable)

这样，后续 observer 可以记录这次模型为什么没有被调用，Run 也能决定是等待用户确认、采用缓存结果还是进入失败状态。每种 outcome 还要明确从哪个 phase 继续：deny、require_approval 和 fail 不调用 model/tool handler；use_cached 虽然跳过 model call，缓存结果仍要经过与实时结果相同的 normalization 和 output policy；所有分支都产生可观察的执行 event。否则，缓存就可能成为绕过结果策略的隐藏路径。

Short-circuit 改变了控制流，因此必须进入执行事实，不能只是某个回调提前 return。

Before 与 After 的顺序通常不是对称列表

有些 Hook 会成对管理资源。例如 tracing span 在调用前打开，在调用后关闭；temporary credential 在进入 Tool 前注入，在离开后撤销。

这类 Hook 更接近嵌套 scope：

before A
  before B
    execute
  after B
after A

如果 after 仍按注册顺序执行，A 可能先关闭 B 仍在使用的资源。是否采用反向顺序，应由 Runtime contract 明确，而不是让每个 Hook 作者猜测。

Cancellation 也必须遵循同一套 unwind contract：已经进入的 scope 按反向顺序清理，temporary credential 等资源不能因为取消而遗留；cleanup error 应单独记录，不能覆盖原始 cancellation。带外部副作用的 after hook 是否允许 replay，则继续遵循后文定义的 delivery contract。

并非所有 after hook 都属于同一个 nesting。记录 metric 的 observer 可以消费已经完成的 event；结果 policy 则必须在内容交给用户或进入下一个 Model Turn 的 context 前运行。把它们都放进一个 afterModel 数组，只会再次把不同语义交给注册顺序。

Hook 失败不能改写已经发生的 Tool 结果

顺序问题在 happy path 已经可见，retry 会让失败契约更加重要。

假设 write_file 已经成功保存报告，随后一个 afterTool Hook 要把 tracing event 写入远端 collector，但 collector timeout。如果 middleware 把整个 chain 都当成 failed，外层 retry 可能再次执行 write_file：

attempt 1：write_file succeeded → trace delivery timeout
attempt 2：write_file succeeded again

第二次写入不是 tracing 的 retry，而是业务副作用被重复执行。Runtime 必须保留两个独立事实：

Tool Execution：succeeded，artifact = report.md@v3
Trace delivery：failed，等待单独重试或降级

因此，每类 Hook 都需要预先决定失败策略：

  • Policy 无法完成判断时，通常不能继续高风险动作，应 fail closed 或要求确认。
  • Transformation 失败时，当前 model/tool call 尚未发生，可以终止这一阶段；只有 transformation 本身是纯函数时，retry 才容易安全。
  • Observation 失败时，通常不应重做已经完成的业务动作，可以写入本地 buffer、单独 retry 或标记 observability degraded。
  • 强合规审计可能要求 observation 失败时阻止后续动作，但这个约束必须发生在动作之前，不能事后假装已经发生的副作用不存在。

“通常”很重要：不同产品可以选择不同 policy。Contract 的目标不是规定唯一答案，而是让失败到底阻断、降级还是单独恢复不再由异常碰巧冒泡到哪里决定。

Retry 与 Replay 要使用稳定身份

Runtime retry 一次 model call 时，纯 validation 和 transformation 可以重新执行。Metric observer 只有在指标有意统计物理 Attempt、允许重复，或能够按稳定 event identity 去重时，才可以安全重放。只要 Hook 有外部副作用，重放就可能重复产生结果。

例如 Hook 在 Tool 完成后发送通知。进程在通知成功后、记录 checkpoint 前崩溃，恢复时会再次进入 afterTool。如果通知使用新的 message ID，用户会收到两条消息。

这类动作不应隐藏在“顺便执行”的 callback 中。更稳妥的选择有两个：

  1. 把通知提升为显式 Tool Execution，由 Runtime 保存 logical identity、Attempt 和结果。
  2. 如果它确实属于基础设施 Hook，就使用稳定 event_id，让下游去重，并记录 delivery 状态。

这样，replay 的单位是同一个 Hook event，而不是一次全新的业务意图。Metric、tracing、billing 和 audit 等 observer 也都需要明确自己接受 at-least-once delivery、幂等 upsert，还是必须由 durable outbox 交付。稳定 event_id 本身不能阻止重复副作用；只有下游执行去重或幂等 upsert 时，重复交付才会收敛为一个结果。

Contract Test 应验证组合，而不只是单个 Hook

单测每个 callback 能否返回正确值还不够。真正容易出错的是组合语义。最小的一组 contract test 可以覆盖：

  • capability policy 发生在 provider payload 生成之前；
  • transformer 不能增加 policy 已移除的 Tool；
  • deny 或 require-approval 后，model/tool handler 没有被调用；
  • cached response 仍经过 normalization 和 output policy；
  • 成对 scope 的 after 以反向顺序收敛；
  • cancellation 触发已进入 scope 的反向清理，cleanup error 不改写原始取消结果；
  • observer 失败不会把已成功的 Tool Execution 改成 failed；
  • replay 符合声明的 delivery contract：at-least-once 复用同一个 event_id 并允许重复投递，只有声明幂等或去重时才验证不会产生重复副作用；
  • trace 能区分原始候选、policy decision 与最终请求。

这些测试不需要真实模型。用一个记录调用顺序的 fake handler，就能验证 Runtime 的 extension contract 是否稳定。真实模型评测解决的是 Hook policy 是否有效，contract test 先保证 policy 按预期位置执行。

Trace 内容本身也需要边界。默认记录结构 metadata、稳定 ID、phase、状态和经过脱敏的摘要通常已经足够；完整 instructions 或 provider payload 只有在明确需要时才启用，并受 redaction、访问控制和 retention policy 约束。Credential、secret 与不必要的用户原文不应进入 trace。

回到问题

beforeModel、afterModel、beforeTool、afterTool 只提供了时间位置，没有定义执行语义。

一个稳定的 Hook 系统还要回答：policy、transformation、control 与 observation 谁先执行；每类 Hook 能修改哪些字段；short-circuit 怎样成为可观察结果；异常是阻断、降级还是单独恢复；retry 与 replay 是否会重复副作用。

当这些 contract 明确后，Hook 才能让 Runtime 被安全扩展。否则，每增加一个 callback，系统就多一个隐藏的控制流分支，而真正的执行顺序只能靠读初始化代码猜测。

后续问题

  • Policy decision 怎样与用户确认和高风险 Tool approval 连接。
  • Hook event、Runtime event 与 Trace span 应怎样共享 identity。
  • Plugin 或 Skill 版本变化后，旧 Checkpoint 应使用哪一版 Hook contract 恢复。
  • Provider adapter 的 request shaping 应暴露哪些稳定 extension point。
