Agent 40：平台边界由状态所有权和反转条件决定

用 Source of Truth、failure domain、资源曲线、采用成本和反转条件决定 Agent 能力是否拆成平台服务。

2026/07/24 更新于 2026/07/27 阅读 次
Agent ArchitectureAgentPlatform EngineeringArchitecture

问题

下面用一个构造架构。一个 Agent 系统把 Loop、Context 和 Tool 按名词拆成三个服务。某次 Tool 写入已经成功，Tool Service 也发出了结果；Loop Service 在更新 Run state 前崩溃；Context Service 则从旧 projection 恢复，重新把同一 Tool Call 交给模型。

重启后三个服务分别给出：

Loop Service: Run 仍在 executing
Tool Service: Tool Execution 已 succeeded
Context Service: 最新 Context 未包含 Tool Result

服务更多并没有带来更清楚的责任。一次本应局部完成的状态变化，变成跨网络、跨版本和跨恢复协议的状态机。

平台边界不能从领域名词直接推导。要先确定哪个组件拥有事实、哪些 invariant 必须成立，再判断独立部署是否真的带来故障、资源或演进收益。

Source of Truth 是语义决定权

“Source of Truth” 不等于整个系统只保存一份数据。Run state、event、Context snapshot、search index 和 warehouse fact 可以同时存在；真正需要唯一的是同一个业务判断由谁提交。

定位 owner 时，可以问：

  1. 哪个组件有权执行合法 state transition？
  2. 这个决定依据哪些当时可见的事实和 policy？
  3. 哪些副本只是 projection、cache 或索引？
  4. 如果派生数据全部丢失，哪份记录足以重建？

在开场案例中，可以有两种合法设计。

设计 A：Core 原子提交已观察的 effect evidence 与下一状态。

external backend:
  owns actual effect

core transaction:
  commit(effect reference/evidence,
         Tool Execution state,
         next Run state,
         Context revision)

外部 effect 无法被 Core 的本地 transaction 吸收。Backend 始终拥有实际写入；Core 只能在获得可验证的 effect reference 后，原子保存“观察到了什么”以及下一逻辑状态。若进程在外部写入后、本地提交前崩溃，恢复必须用稳定 operation ID 查询或 reconcile，在确认前不能把同一 Tool Call 重新交给模型。

设计 B：Event Log 是 Core 观察事实的权威来源。

atomic append:
  tool_effect_observed {
    operation_id,
    tool_execution_id,
    source_attempt_id,
    effect_ref,
    observed_outcome
  }
derived:
  Run state projection
  Context projection

此时只需原子追加 Core 已确认的观察 event，两个 projection 可以异步收敛，并通过 cursor、version 和幂等 rebuild 恢复。tool_execution_id 指明哪次逻辑执行需要收敛；证据若来自某次物理调用，source_attempt_id 保留当时观察。若 outcome 仍是 unknown，event 也必须保留 unknown；后续 reconciliation 追加新 event，而不是覆盖原观察或把本地 append 当成外部写入本身。重点不是哪种存储形式普遍更好，而是先选择 invariant，再让服务边界服从它。

Derived View 发生错误时，要修对位置

如果已确认 effect evidence 的权威 event 已经存在，Context projection 漏消费了它，repair location 在 projection：重新处理 event、校验 cursor 并幂等收敛。

如果 event 本身把 unknown outcome 错写成 succeeded，修复应回到拥有 Tool result normalization 的边界。不能在 Context Service 里增加一条补丁，把所有 timeout 又解释成 unknown；那会产生第二套业务语义。

因此，每个独立边界至少要声明：

  • authoritative state；
  • accepted commands；
  • emitted facts；
  • derived views；
  • idempotency 和 version；
  • recovery、rebuild 与 reconciliation 路径。

没有这些内容，拆分只改变网络拓扑，没有建立平台 contract。

可重建 View 还需要版本化的语义 Fact

“有 Event Log”仍不足以保证 projection 可重建。Event 必须保存 owner 已经决定的语义，而不是只暴露一组让每个 consumer 自己解释的原始 status。开场中的 effect observation 可以写成：

{
  "event_id": "event_51",
  "schema_version": 2,
  "operation_id": "op_17",
  "tool_execution_id": "tool_exec_42",
  "effect.outcome": "unknown",
  "normalization_policy_version": 4,
  "effect_ref": "provider_op_9",
  "supersedes_event_id": null
}

如果 v2 新增 unknown，旧 consumer 不能用“不是 succeeded 就算 failed”的 catch-all 继续处理。它必须按兼容 contract 保留 unknown、拒绝处理或显式降级，并暴露自己尚未消费的 schema/version。否则 Source of Truth 已经保留不确定性，Derived View 却会重新发明一个确定失败。

修复历史时还要区分三种动作：

  • 权威 fact 正确、projection rule 有 bug：固定 source range 与 rule version，幂等 rebuild；
  • 当时的 observation 正确、后续 reconciliation 获得新证据：追加指向原 event 的新 fact，不覆盖原 observation；
  • owner contract 新增语义：先发布 versioned schema 与 consumer 兼容策略，只有历史证据足够时才 backfill，不能从缺失字段推测答案。

因此，“确定性 rebuild”至少要求目标时间范围内的权威 history、稳定 identity/sequence、消费过的 schema version、projection rule version 和 cursor。Reconciliation 用这些信息修复局部 drift；rebuild 则从可信起点重新生成较大范围。两者都不能绕过 semantic owner。

先把代码边界与部署边界分开

Loop、Context、Tool 和 Memory 应拥有清楚的 module contract，不代表它们必须是独立服务。常见选择至少有三层：

边界主要收益新增成本
Module / package封装语义、测试依赖方向同进程故障与发布仍共享
Library / shared process复用实现、保持本地调用版本兼容和宿主升级
Independent service独立容量、故障隔离、发布与 ownership网络失败、latency、schema negotiation、运维和恢复

默认从最小可用边界开始，可以让 contract 先稳定。若一个 Context policy 仍在频繁改变，过早做成远程平台 API，会把尚未稳定的内部假设固化成跨团队版本负担。

相反，如果某能力已经有稳定 owner 和独立资源曲线，继续嵌在所有宿主里也可能阻止统一治理。决策需要证据，而不是统一偏好。

独立 Service 需要至少一个真实拆分信号

可以从四类信号检查候选边界。

故障需要独立隔离

Sandbox provider 可能运行不可信代码，具有与 Agent Core 不同的安全和故障域。让它独立部署，能够限制进程、凭证和资源影响范围。

但“某模块会失败”不是充分理由；所有代码都会失败。需要说明同进程故障会扩大什么 blast radius，以及远程调用新增的 partial failure 能否被协议处理。

资源曲线独立变化

Sandbox 调度可能受 CPU、内存与启动队列限制，Evaluation pipeline 可能消耗批量模型调用，而 Agent Core 主要持有低延迟 Run state。资源类型和扩缩信号长期不同，是拆分的有力候选。

没有实测 profile 时，只能把它写成待验证假设，不能用“未来可能很大”作为既成事实。

Change Cadence 与兼容责任长期独立

若 Tool contract 必须同时支持多个宿主版本，独立 service 需要明确 schema evolution、兼容窗口和 deprecation。仅仅因为两个团队想分别发布，不代表系统语义已经能分开。

团队 ownership 可以先分离，部署仍保持一起；组织图不是 Runtime 拓扑。

多个采用者共享稳定 Contract

平台能力应来自多个场景重复出现、且已经稳定的语义。例如三个 Agent 产品都需要相同的 Tool authorization 和 normalized result contract，才可能提炼出共享 runtime。

“第二个调用方出现”仍不自动证明要建服务。共享 module、library 或模板可能已经足够；平台化还需要计算 migration、support、compatibility 和退出成本。

平台收益必须使用可观察分母

“提高可靠性、降低成本、加速采用”都是需要测量的判断。上线前可以定义指标，不能提前填写改善结果。

维度需要声明的 Grain 与分母
Adoption在目标时间窗内实际使用该 contract 的 eligible workloads / 全部 eligible workloads
Reliability按 logical operation 或 request 定义的成功与 failure
Latency在相同 workload class 下的端到端或边界调用分布
Costobserved/allocated cost / Task、operation 或资源单位
Migration burden已迁移调用方、剩余调用方和实际工程工作

这些指标要有 baseline、采样窗口和 configuration identity。若只迁移最简单的调用方，不能用它推断所有 workload 的 adoption 成本；若服务化把本地调用变成网络调用，latency 与 failure denominator 也要包含 retry 和 timeout。

平台服务还应承担 support 和 incident ownership。一个中央 API 如果把恢复责任留给每个调用方，组织上集中、语义上却仍然分散。

对开场系统选择最少必要边界

对这个构造系统，一种有条件的收敛方案是：

Agent Core deployment
  owns:
    Run transition
    per-turn Context projection
    Tool Execution logical state
    observed effect evidence
  modules:
    loop
    context
    tool contract
    memory read/write policy

Sandbox control plane（候选独立服务）
  owns:
    sandbox admission
    lease
    runtime provider reconciliation

把强相关的 Run、Context、Tool logical state 和已观察 effect evidence 留在同一 owner 内，减少开场的跨服务恢复；外部 backend 继续拥有实际 effect。代码仍按 module 隔离。Sandbox 因不可信执行、独立容量和 reconciliation 需求成为候选远程边界。

这不是普遍答案。如果 Event Log 已经是权威事实源，Context projection 也能从 event 独立重建，那么它可以拥有不同部署节奏；如果 Tool provider 本身是外部服务，Agent Core 仍应保留 logical Tool Execution 与 unknown outcome，而不是把结果 ownership 全推给网络响应。

Evaluation pipeline 也可能独立部署，因为它有批量 workload 和不同的运行节奏；但生产与 Eval 仍应复用同一 Spec compiler 和执行 contract，不能因部署分离再造一套 Runtime。

ADR 要记录判断和反转条件

只写“决定拆出 Context Service”无法指导未来。一个有用的 architecture decision record 应包含：

decision: keep Context projection in Agent Core
status: accepted
reversibility_class: staged_commitment
context:
  invariant: observed effect evidence, Run transition and visible Tool Result must share one revision
assumptions:
  - Context workload does not require independent capacity
  - all current consumers release with Agent Core
alternatives:
  - independent Context Service
evidence_needed:
  - latency profile
  - failure ownership
  - eligible adopters
consequences:
  - shared deployment
  - simpler local atomicity
irreversible_commitments:
  - after the first external adopter, support the published API through its declared compatibility window
validation:
  metrics:
    - projection latency by workload class
    - rebuild parity from the same event cursor
  observation_window: ...
reversal_conditions:
  - measured workload requires independent capacity
  - stable event contract permits deterministic rebuild
  - multiple consumers require an independently versioned API
migration_or_rollback:
  - build the candidate projection from the same versioned facts
  - compare current state at an explicit cursor
  - move one eligible consumer while retaining the Core path
  - route that consumer back if parity or recovery invariants fail
deprecation:
  old_path_sunset_when:
    - every declared consumer uses the versioned API
    - the rollback window has ended
review_owner: ...
review_date: ...

这是决策结构示例，不声称这些条件已经在某个真实系统中发生。Michael Nygard 对 ADR 的原始说明 强调记录驱动决策的 forces，并在后续反转时保留旧记录、标记为 superseded。反转不应删除历史理由，而应创建新决定并说明哪些上下文已经变化。

reversibility_class 说明这是低成本试验、渐进承诺还是高成本决定；irreversible_commitments 列出一旦外部采用就不能立即撤回的 API、数据或支持责任。Migration 先证明同一 versioned fact 与 cursor 能产生等价 projection，再移动 consumer；deprecation 只有在采用者、rollback window 和 support owner 都满足退出条件后才发生。这样“可反转”才是执行 contract，不只是 ADR 里的一个提醒日期。

反转条件也不能只写“规模变大”。它要连接到可观察证据和具体动作。例如：

如果相同 workload class 下，Context 计算长期成为独立容量瓶颈，
且 event contract 已能确定性 rebuild projection，
则重新评估独立部署。

即使条件触发，也只是重开决策，不是自动拆服务；还要重新计算 migration、partial failure 和兼容成本。

简单设计仍然有明确适用范围

同一部署单元不等于无架构。只要 module contract、state owner、event identity 和恢复路径清楚，它可以是刻意选择的 modular deployment。

当系统只有一个宿主、负载曲线接近、变化必须同步，并且关键 invariant 需要低延迟或原子提交时，本地边界往往已经足够。只有在独立故障、资源、演进或采用收益长期超过远程调用和治理成本后，独立 service 才更合理。

回到问题

把 Loop、Context 和 Tool 按名词拆成服务后，一次 Run 更难保持一致，是因为拆分发生在 state owner 和 invariant 之前。每个服务都保存了一部分状态，却没有一个边界拥有完整的提交与恢复语义。

先让外部 backend 继续拥有实际 effect，再决定 Core 对 effect evidence、logical state 和 Context 使用原子 current state，还是可追加 event；恢复必须凭 operation/effect reference query 或 reconcile。随后再区分 Source of Truth 与可重建 projection。代码可以先按 module 隔离，只有故障隔离、资源曲线、change cadence 或多调用方采用提供了足够证据，才升级为独立部署。

平台边界不是一次永久命名。把假设、分母、迁移成本和反转条件写入 ADR，系统才能在证据变化时收缩或拆分，而不是继续维护一张已经失效的服务名词表。
