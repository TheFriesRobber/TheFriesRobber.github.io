Agent 13：执行中的新输入怎样进入下一轮

区分 steering、follow-up、取消和 durable admission，明确运行中新输入的接纳与消费边界。

2026/07/24 更新于 2026/07/27 阅读 次
Agent CoreAgentRuntimeSteering

问题

Agent 正在执行写入 Tool，用户发来：“不要写了，先只读检查。”这条消息应该立刻打断 handler，还是等下一轮再交给模型？

如果把它当成普通 chat message 追加到末尾，当前 Run 可能已经结束；如果把它当成强制取消，已经发生的写入也不会自动回滚。Steering 是新的控制输入，不是时间倒流。

Steering 只在稳定边界进入 Context

模型请求和 Tool batch 执行期间，Context 应保持稳定。把新消息插入一个已经发出的模型请求没有意义；在一批 Tool Result 尚未收敛时修改消息序列，也会破坏 Call/Result 对应关系。

因此 Pi 会在 turn boundary 轮询 steering message：当前 Tool 工作先收敛，新输入再进入下一次模型调用。它可以改变后续计划，却不能改写已启动 Attempt 的事实。

对开场消息应拆成两条语义：

  • “不要再启动写入”是后续控制意图；
  • “已经启动的写入怎样处理”由 cancellation 与 effect reconciliation 决定。

只有把二者分开，Runtime 才不会把 steering 错当成回滚协议。

Follow-up 解决的是结束竞态

Follow-up 与 steering 的消费时机不同。Steering 用于 Run 正在工作时影响下一 Turn；follow-up 则在 Agent 本来准备停止、没有更多 Tool Call 和 steering 时被消费。

Pi 当前 Loop 的顺序体现了这个区别：steering 在 turn boundary 检查，follow-up 在 otherwise-stop 后检查。这个顺序能减少普通结束路径中的遗漏，但不能原子关闭 terminal race：最后一次 drain 返回空以后、Run settlement 以前，仍可能有新输入入队而不被当前 Run 消费。

两类输入都可以有 queue mode，例如 one-at-a-time 或批量 drain。但 queue mode 只决定当前进程如何取消息，不提供跨重启保证。

“已接收”要声明承诺等级

一个 API 返回 202 Accepted 时，调用方可能理解为消息已经可靠保存。实际系统需要区分：

received   服务收到了请求
admitted   policy 接受了这条输入
durable    重启后仍能恢复
consumed   已进入某个明确 Turn

Pi 当前 Agent 与 Harness 使用内存队列。steer() 或 followUp() 返回，只表示消息进入当前进程的队列，不能写成 restart-safe admission。

只有当产品明确承诺“accepted 后即使进程退出也会继续处理”，host 才需要 durable inbox：

  • stable input ID 和 target Run/Session；
  • accepted/admitted/consumed 状态；
  • 幂等提交与重复检测；
  • 未消费输入的唤醒机制；
  • terminal Run 到达时的拒绝或新 Run 规则。

相关当前实现可参考 Pi 的 agent.ts 与 agent-loop.ts。

Terminal race 需要一个 owner

最棘手的情况是：Agent 正准备返回最终答案，新的 follow-up 同时到达。若终止判断与入队没有共同边界，可能出现消息已返回 accepted，却永远无人消费。

要彻底关闭这个 gap，宿主增强需要让同一个 owner 串行处理“接纳输入、检查队列和进入 terminal”；Pi 当前并不提供这项原子保证。耐久实现则可以使用条件更新：

if run is accepting_input:
  append inbox item
else:
  reject or create a new run

这里没有通用答案。对话产品可以把 terminal 后输入创建为新 Run；严格工作流可能直接拒绝。重要的是 acceptance 与 terminal transition 由同一个事实源裁决。

Stop、Steer 与 Follow-up 不是同一个动作

三者分别表达：

  • stop/abort：请求当前工作停止并等待收敛；
  • steer：改变当前 Run 下一 Turn 的方向；
  • follow-up：在原任务本来结束时追加下一轮输入。

把它们合成一个自由文本队列，会让取消、顺序和 durability 都无法解释。API 可以共用传输通道，但 durable state 和消费条件应保持不同。

回到问题

用户说“不要写了，先只读检查”时：

  1. Runtime 可以发出 cancellation request，阻止新的写入并等待已启动 handler 收敛；
  2. 已发生或未知的写入进入 query/reconcile，不被 steering 覆盖；
  3. 消息在下一个 turn boundary 进入 Context；
  4. 如果当前 Run 已进入 terminal，则按产品规则拒绝或创建新 Run；
  5. 只有承诺跨重启处理时，才把消息写入 durable inbox。

Pi 当前提供了清晰的内存队列和消费顺序。宿主应诚实描述它的承诺：内存 queue 是运行期控制机制，durable admission 是另一层产品协议。
