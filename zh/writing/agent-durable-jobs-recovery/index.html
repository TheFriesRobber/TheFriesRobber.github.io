Agent 32：耐久任务怎样跨过 Queue 与 Workflow 恢复

区分 Queue 重投、事件发布和跨状态部分成功，为每条失败边界选择正确的恢复机制。

问题

Agent 把一个文件转换任务写入 Queue。worker 完成转换并把 Artifact revision 4 提交到存储，随后在删除或 ack 消息前崩溃。Visibility timeout 到期后，同一消息被另一个 worker 再次领取。

如果第二个 worker 把这次 delivery 当成新任务，会重复调用外部服务，甚至发布 revision 5；如果它因为“消息处理过”直接丢弃，又可能漏掉第一次没有完成的后续事件发布。

Queue、业务数据库和 Workflow history 各自拥有不同事实。恢复协议必须先区分 logical operation 与 delivery Attempt，再针对提交边界选择机制：

  • 重复 delivery 用稳定 operation identity、幂等和事实查询处理；
  • 本地业务事务与事件发布之间用 transactional outbox 衔接；
  • Workflow state 与外部 business state 的部分成功，用 retry、reconciliation 或领域 compensation 收敛。

它们不能被一个“开启 retry”开关替代。

一条消息可能产生多个 Attempt

先固定 identity：

概念示例是否因重投改变
Logical operationconvert:file_12:source_rev_3否
Jobjob_42通常否
Delivery Attemptattempt_1、attempt_2是
Business resultartifact_19@rev4不应因重投自动重建

Amazon SQS Standard queue 明确采用 at-least-once delivery，并提示应用按重复处理设计；visibility timeout 也不保证期间绝不重复投递。其他 Queue 的保证不同，所以系统应以所选产品的官方 contract 为准，而不是笼统宣称 exactly-once。

Visibility timeout 只暂时隐藏消息。延长 timeout 可以减少长任务中的重投，却不能证明 worker 活着，也不能替代业务 lease、幂等键或结果查询。

重投先查询业务事实

开场时间线是：

t0 attempt_1 receives job_42
t1 artifact rev4 committed for operation convert:file_12:source_rev_3
t2 worker crashes before ack
t3 visibility timeout expires
t4 attempt_2 receives job_42

attempt_2 首先按 operation key 查询业务 store：

operation record exists, outcome = committed
artifact_ref = artifact_19@rev4
source_revision = 3

如果记录与结果完整，它复用 rev4，补齐允许重复执行的 control-plane 步骤，再 ack 消息。它不重新转换。

为了让查询可靠，operation record 与业务结果应在同一业务提交边界中关联。仅在 worker 内存里保存“做过了”或只依赖 Queue message ID，无法覆盖进程崩溃、生产者重发和不同 Queue 的 identity 变化。

若查询结果是：

  • not started：当前 Attempt 可以在获得必要 lease 后执行；
  • committed：复用结果并继续收敛；
  • in progress with live owner：延后或等待，不并发重做；
  • unknown 或本地记录不完整：查询外部 effect，或进入 reconciliation/manual review。

Timeout 不能自动归类为 not started。

幂等不是简单的去重表

一张 processed_message_ids 表只能说明某个 ID 被记录过，无法说明业务 effect 是否成功、结果是什么、输入 revision 是否一致。

更有用的 operation record 需要绑定：

{
  "operation_id": "convert:file_12:source_rev_3",
  "input_revision": 3,
  "status": "committed",
  "result_ref": "artifact_19@rev4",
  "effect_ref": "provider_request_81"
}

如果相同 key 带来不同参数，系统应报 conflict，而不是返回旧结果。幂等键代表“同一个意图的 retry”，不能被用来合并两个不同业务动作。

对于不支持幂等键或状态查询的外部系统，只能缩小自动 retry，并保留 unknown。应用无法在自己的数据库里证明远端绝未执行。

Outbox 只跨过本地事务与事件发布

假设 Artifact rev4 与 operation record 已在数据库提交，随后系统需要发布 artifact.ready。如果先提交数据库、再直接发 Queue，进程可能在两步之间崩溃；如果先发消息再提交，消费者可能看到尚不存在的业务状态。

Transactional outbox 的作用是把业务更新和待发布事件写入同一个本地事务：

DB transaction:
  commit artifact rev4
  commit operation outcome
  insert outbox event artifact.ready

dispatcher:
  read unpublished outbox rows
  publish event
  mark published

Dispatcher 仍可能在 publish 成功、mark published 前崩溃，所以事件仍可能重复；consumer 仍需幂等。Outbox 解决的是“不丢失本地提交对应的发布意图”，不是端到端 exactly-once，也不能把两个独立数据库变成一个原子事务。

Workflow state 不是 Business state

Durable Workflow 可以保存控制流 history、timer、retry 和 activity completion，但 Artifact、付款、工单或文件仍由各自 backend 拥有。可能出现：

Workflow activity recorded timeout
Business backend actually committed

或者：

Workflow step completed
Outbox dispatcher has not published downstream event

恢复时应按 failure owner 选择：

  • Retry：操作可安全重试，或远端用同一 operation key 保证语义。
  • Reconciliation：系统能查询 Source of Truth，把 control state 与 business state 对齐。
  • Compensation：已经确认的业务动作需要另一个有领域意义的动作抵消，例如创建退款或恢复上一 revision。

Compensation 不是数据库 rollback。它本身也可能失败、被重试或需要授权；只有业务能够定义“怎样抵消”时才成立。若外部 effect 结果未知，先 reconciliation，不能在不确定是否发生时盲目补偿。

DLQ 是隔离区，不是业务终态

消息超过重试策略进入 DLQ，只说明 Queue 不再按原策略自动投递。它不证明业务失败，也不会自动撤销已完成 effect。

DLQ 处理需要携带 operation identity、最后一次 error、Attempt history 和业务查询入口。重新驱动消息前先查事实；永久 schema 错误、权限撤销和结果未知应走不同处置，而不是全部“一键重放”。

Backpressure、worker 扩容和 Queue 选型是资源治理问题，不属于这篇恢复协议。

回到问题

开场的 attempt_2 收到重复消息后，用 convert:file_12:source_rev_3 查询到 Artifact rev4 已提交，于是不再调用转换服务。它确认 outbox 中已有 artifact.ready 发布意图，让 dispatcher 继续投递，最后安全 ack 当前消息。

如果 rev4 只在远端出现、本地 operation outcome 仍未知，worker 应按 effect reference reconciliation；无法查询时保持 unknown，而不是重做或假装失败。

Queue retry 产生新的 Attempt，不产生新的业务意图。Outbox 保住本地提交后的发布意图，Workflow 保存控制流，business backend 保存领域事实。明确这些 owner，耐久任务才能在重复、崩溃和部分成功之间恢复，而不依赖不存在的端到端 exactly-once。
