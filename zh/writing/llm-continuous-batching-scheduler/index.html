LLM Infra 06：Continuous Batching 怎样改变请求调度

从长度不一且持续到达的 sequence 出发，解释 iteration-level scheduling、Token/KV budget、公平性、chunked prefill 与 preemption。

2026/07/29 阅读 次

问题

三个请求一起进入模型：A 输出很长，B 和 C 很快结束。Request-level batching 如果必须保持原组合，B、C 完成后的执行位置会闲置；允许每轮补入新请求后，吞吐可能提高，A 却也可能因为新请求或 KV 压力被反复推迟。

Continuous Batching 解决的不是“Batch size 太小”，而是把重新组合执行集合的边界移动到模型 iteration。这个改变提高了复用机会，也把 Token budget、KV capacity、顺序和 preemption 变成 scheduler 的显式责任。

Request batch 与 iteration batch 不是同一个对象

Orca 将传统 request-level scheduling 与 iteration-level scheduling 区分开：后者每次执行模型的一轮，再根据请求是否完成和新请求是否到达重新组成下一轮 batch。

概念 trace 如下，不代表真实 GPU 时间：

Iteration 1: active = {A, B, C}
Iteration 2: B finished; active = {A, C, D}
Iteration 3: C finished; active = {A, D, E}

这里必须区分三种顺序：

request arrival order
≠ per-iteration execution grouping
≠ request completion order

并非所有非 continuous 实现都会机械等待整批结束；实现也可以缩小 active batch。真正的差别是 scheduler 是否能在 iteration boundary 重新 admission，并把变化后的 state 安全映射到下一次模型执行。

Scheduler 每轮分配的是 Token 与状态预算

对每个 runnable request，scheduler 至少需要知道：

  • 已计算到哪个 Token；
  • 当前属于 Prefill 还是 Decode；
  • 本轮最多可以推进多少 Token；
  • 已持有和新增需要多少 KV blocks；
  • 是否达到 max tokens、stop condition 或 cancellation；
  • priority、arrival time，以及平台自定义的 deadline policy。

当前 vLLM 的 SchedulerConfig 就包含单 iteration 的 max_num_batched_tokens、max_num_seqs、chunked prefill 和 FCFS/priority policy。其 V1 scheduler 在 token budget 内处理 running requests、分配 KV slots；无法分配时可以根据策略 preempt。

这些是一个具体 Runtime 的实现证据，不是所有 serving engine 的统一状态机。Deadline-aware scheduling、pause/resume 名称和 preemption 代价仍然由各实现与平台策略定义。

Chunked Prefill 让两阶段共享 iteration

一个长 Prefill 如果整段进入某次 execution，可能让已有 Decode sequence 等待更久。Chunked Prefill 把长 Prompt 切成多个 token chunks，使 scheduler 能在 token budget 内混合安排 Prefill 与 Decode。

它引入了新的取舍：

  • chunk 太大，Decode 仍可能出现长间隔；
  • chunk 太小，调度和 Kernel 效率可能变差；
  • 优先 Decode 可以保护 TPOT，却延长长 Prompt 的 TTFT；
  • 优先 Prefill 可以快速建立新 sequence，又可能影响正在 streaming 的请求。

所以 max_num_batched_tokens 不是单纯的吞吐参数。它与 Prefill chunk policy 一起决定 TTFT、TPOT、Batch opportunity 和公平性。

KV 不足时，Preemption 不是免费暂停

上一节的显存账本说明，active sequence 会持续占用 KV blocks。当新请求需要更多 blocks 而 pool 不足时，scheduler 有几种选择：

  • 不 admission 新请求；
  • 推迟低优先级 request；
  • preempt 已运行 request，并在恢复时 recompute 或 swap state；
  • 拒绝请求并返回稳定 reason code。

无论选择哪一种，preemption 都不是“把任务放回队列”这么简单。它会改变：

  • 已计算 Token 是否仍保留；
  • KV state 是否需要重建；
  • 之前消耗的计算是否变成重复工作；
  • request 的 deadline 是否还可满足；
  • usage 与 outcome 应怎样记录。

因此，Runtime 暴露的 preemption count 和 KV usage 是重要证据。频繁 preempt 可能表示 Token/KV budget 与 workload 不匹配，而不是“GPU 还不够忙”。

吞吐、公平与延迟是不同策略

Continuous Batching 本身不会必然造成 starvation，也不会自动提供公平。结果取决于 policy。

Policy 倾向可能收益主要风险
最大化本轮 Token 数聚合吞吐长 Prefill 或大请求占用预算
Decode 优先稳定 streaming TPOT新长 Prompt TTFT 变长
Shortest-job-like短请求更快完成长请求长期等待
FCFS顺序容易解释head-of-line blocking
Priority / deadline保护重要请求低优先级 starvation，需要 aging

平台应该把 policy 当作 SLO 决策，而不是隐藏在一个 batch-size default 中。若 Runtime 只提供 FCFS/priority，deadline 与 tenant fairness 可能需要在上层 admission 完成；但上层不能假装自己拥有 iteration 内部的 KV state。

把开篇请求走一遍

假设 A、B、C 同时开始，D、E 随后到达：

I1: A/B/C Prefill
I2: A/B/C Decode
I3: B finish; admit D; A/C/D active
I4: C finish; E arrives, but KV budget insufficient

在 I4，正确记录不是“E 排队”，而是：

scheduling_decision:
  iteration: 4
  runnable: [A, D]
  waiting: [E]
  token_budget_remaining: 32
  kv_blocks_free: 1
  kv_blocks_required_for_E_this_iteration: 2
  decision: defer_E
  reason: insufficient_kv_budget
  policy: fcfs_with_decode_priority

如果 A 随后被 preempt，记录还要说明其 KV state 和 recompute outcome。这样，吞吐改善和长请求受损都能从同一条 trace 解释。

回到问题

Continuous Batching 让 B、C 完成后可以立即补入 D、E，因此减少 request-level 固定组合带来的空闲。但它也迫使 scheduler 在每个 iteration 重新分配 Token 和 KV budget，并明确处理 Prefill/Decode、顺序、公平和 preemption。

所以优化目标不能写成“把 Batch 做大”。应该写成：在指定 workload 与 SLO 下，用什么 iteration policy 形成更高 goodput，同时不让长请求、低优先级请求或已开始的 streaming request 失去可解释的进展。
