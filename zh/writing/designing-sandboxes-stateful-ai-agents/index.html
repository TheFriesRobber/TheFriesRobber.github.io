Agent Sandbox 一：容器健康不等于 Sandbox 可用

从“旧 Runtime 仍健康但已失去 Workspace 所有权”出发，建立有状态 Sandbox 的最小可用契约。

2026/07/12 阅读 次
AgentSandboxDistributed Systems

问题

10:00，执行 Agent 的可替换进程 runtime_a 因网络分区停止续约。Lease 是 Control Plane 发出的有期限执行权；它的进程没有退出，health check 仍然成功，但 Lease 到期后，它已经不再拥有当前执行权。

10:02，用户发来新消息。系统启动 runtime_b，把同一个持久 Workspace——需要跨进程保留的工作目录——挂载给它，并签发新的 Lease。

10:05，网络恢复。runtime_a 携带旧 Session 和旧 Workspace Path 请求继续执行：

runtime_a: process healthy, lease epoch 41
runtime_b: process healthy, lease epoch 42
workspace: bound to epoch 42

如果获取 Sandbox 的流程只检查容器是否健康，就会同时把 A 和 B 当作可用 Sandbox。两个 Runtime 可能覆盖同一文件、重复执行 Tool，或者分别向用户报告互相矛盾的结果。后文把这套获取流程称为 Acquire。

容器健康只回答“这个进程还能响应吗”。有状态 Agent 真正需要回答的是：“这个 Runtime 现在是否有权代表该 Session，使用这一个 Workspace 继续执行？”

Sandbox 不是容器，而是一份可验证的绑定

本文把可交付给 Agent 的 Sandbox 定义成三项同时成立的关系：

Sandbox usable
  = Runtime ready
  ∧ Workspace bound to the intended Session
  ∧ Lease held by this Runtime generation

三项事实的 owner 不同：

事实它证明什么典型 owner
Runtime readiness进程和执行环境满足当前 Runtime Contractruntime provider + readiness checker
Workspace binding指定 Volume / Workspace 属于哪个 Sessionworkspace / storage control plane
Lease ownership当前哪一代 Runtime 可以执行有副作用的动作sandbox control plane

容器 ID、Session ID、Workspace ID 和 Lease generation 不能互相代替。一个 Runtime 可以健康但 Lease 已过期；一个 Volume 可以挂载成功但挂给了错误 Session；一个 Lease 可以有效但 Runtime 初始化尚未完成。任何一项不成立，都不应返回“Sandbox ready”。

Runtime Ready 必须验证执行契约

running 常常只表示容器主进程已经启动。Agent 执行 Tool 还可能依赖：

  • 工作目录已挂载且可写；
  • 基础命令和 Runtime 版本正确；
  • 环境变量、凭证代理或 egress policy 已就绪；
  • Skills、Tool bridge 或初始化文件可读取；
  • 当前 Runtime build 满足 Session 要求。

因此，readiness 应验证这份 Runtime Contract，而不是只探测一个 HTTP 端口。Kubernetes 也明确区分容器正在运行与 Pod Ready：readiness probe 用来判断容器是否已经能接受流量，startup probe 则避免初始化期间被过早判死。

对 Agent 来说，“接受流量”还不够。一个能返回 200 OK、却没有正确 Workspace 的 Runtime，依然不能执行用户任务。

Workspace Binding 证明挂载对象没有串 Session

Workspace 是 Session 的持久工作区，而 Runtime 是可以替换的计算进程。Acquire 不能只检查 /workspace 目录存在，因为空目录、旧缓存或挂错 Volume 都可能满足这个条件。

一次可验证的绑定至少包含：

{
  "workspace_id": "workspace_7",
  "session_id": "session_12",
  "volume_id": "volume_31",
  "mount_path": "/workspace",
  "binding_version": 9
}

Runtime 内的初始化探针应读到同一份 Workspace identity；Control Plane 则验证这份 binding 当前仍指向目标 Session。首次绑定、重新挂载和切换 Runtime 都需要新的 observed fact，不能从“上次曾挂载成功”推断现在仍正确。

Kubernetes PersistentVolume 的生命周期独立于单个 Pod，这正是持久 Workspace 可以跨 Runtime 的基础；但“Volume 仍存在”不等于“当前 Runtime 已安全获得它的业务所有权”。后者仍需要上层绑定与 Lease。

Lease 传播当前执行权

Lease 是有期限的执行权，不是永久 owner 字段。一个概念性 Lease 可以写成：

{
  "lease_id": "lease_session_12",
  "holder_runtime_id": "runtime_b",
  "generation": 42,
  "expires_at": "2026-07-23T10:07:00Z"
}

Runtime 每次执行有副作用的 Tool、提交 Workspace revision 或发布结果时，都应携带当前 generation，资源 owner 再检查它是否仍然有效。这一步称为 fencing：即使旧 Runtime 在网络恢复后仍能发出请求，generation=41 也会被拒绝。

只有“定期续约 + 超时后换 owner”，但下游写入不检查 generation，不能阻止旧 owner。Lease 决定当前意图，fencing 把这个决定落实到副作用边界。

Acquire 要在三个事实汇合后才发布

最小 Acquire 流程可以是：

1. 解析或创建 Session 对应的 Workspace binding
2. 为本次 Runtime generation 取得 Lease
3. 创建或复用 Runtime
4. 挂载并初始化 Workspace
5. 验证 Runtime Contract 与 Workspace identity
6. 原子发布：该 Runtime generation 对该 Session ready

这里的“原子发布”不是要求 provider、数据库和存储共享一笔分布式事务。它要求 Control Plane 只在已观察到的 Runtime、Workspace 和 Lease 仍匹配时，提交一个可被 Acquire 返回的 Ready record：

{
  "session_id": "session_12",
  "runtime_id": "runtime_b",
  "workspace_id": "workspace_7",
  "lease_generation": 42,
  "ready_contract_version": 3
}

如果在发布前 Lease 已被替换，或 Workspace binding 版本变化，当前尝试必须重新校验，不能把旧观察结果拼成一个从未同时成立过的状态。

Reconnect 也是一次 Acquire

进程崩溃、客户端断线或 Scheduler 重启后，系统很容易沿旧 runtime_id 直接 reconnect。但 reconnect 不能恢复过去的权利，只能重新证明现在的绑定。

runtime_a 在 10:05 回来时，即使：

  • 它仍持有旧 Session ID；
  • 本地 /workspace 还能读取文件；
  • health check 与 Runtime Contract 都通过；

它的 Lease generation 仍是 41，而当前 binding 已发布 generation 42。Control Plane 必须拒绝它继续执行，并安排停止或隔离旧 Runtime。

同理，如果当前 Lease 仍属于 A，但 Workspace 实际挂载失败，系统也不能仅凭 Lease 返回 A。三项条件必须在同一个 Acquire 结果中共同成立。

失败需要由 Reconciliation 收敛

Acquire 横跨数据库、Runtime provider 和存储，局部失败不可避免：

  • Lease 已签发，Runtime 创建失败；
  • Provider 已创建 Runtime，但响应丢失；
  • Volume 已挂载，初始化探针一直失败；
  • 新 Runtime 已 Ready，旧 Runtime 未能停止；
  • Scheduler 在发布 Ready 前重启。

请求处理函数只能返回当前已知结果，不能保证所有资源已在同一时刻回滚。Control Plane 需要持续比较 desired state 与 observed state：

desired: session_12 owned by generation 42, one ready runtime
observed: runtime_b ready, runtime_a still reachable
action: keep b, fence and terminate a

Kubernetes controller 采用同样的基本模式：观察当前状态，再通过控制循环使它接近期望状态。对 Sandbox 来说，Reconciliation 的目标不只是“有一个容器”，而是“只把仍持有正确 Workspace 与 Lease 的 Runtime 暴露为可用”。

最小返回契约

调用方不应只拿到一个 endpoint。Acquire result 至少要能绑定：

  • Session 与 Sandbox identity；
  • Runtime identity 和 generation；
  • Workspace identity / binding version；
  • Lease expiry 或续约边界；
  • Ready Contract version 与验证时间。

后续 Tool Runtime 可以用这些字段验证请求是否仍属于当前 generation。调用方不必了解底层 provider 的全部资源细节，但必须能区分“同一个逻辑 Session 的新 Runtime”与“旧 Runtime 的迟到响应”。

回到问题

10:05 的 runtime_a 仍然健康，却已经无权继续使用 Workspace。它只满足 Runtime readiness；Workspace 与 Lease 已经绑定给 generation 42 的 runtime_b。

有状态 Sandbox 的可用性不是单个进程属性，而是 Runtime readiness、Workspace binding 与 Lease ownership 在同一时刻成立的关系。Acquire 负责验证并发布这份关系，fencing 拒绝旧 owner 的副作用，Reconciliation 再清理局部失败留下的孤儿资源。

把 Sandbox 看成这份可验证的 Session Contract，容器才会回到它应有的位置：一种可替换的 Runtime 载体，而不是用户状态与所有权的唯一身份。

后续问题

  • Provider 与业务 Control Plane 应怎样分工，才能恢复结果未知的创建请求。
  • Acquire 横跨 Volume、Runtime 和初始化时，哪些阶段必须成为持久状态。
  • Runtime 更换后，持久 Workspace 怎样安全地重新挂载。
