Agent Memory 二：什么信息值得长期保存

2026/07/14 阅读 次
AgentMemoryData Governance

问题

用户在出差途中说：“我这周住在柏林，帮我找附近的会议室。”Agent 完成任务后，后台归纳把“用户住在柏林”写进长期 Memory。

两个月后，用户在上海安排活动，Agent 仍优先推荐柏林地点。原句没有写错，embedding 也没有失效；错误发生在写入时：一个有明确时间范围的任务事实，被升级成了没有期限的用户属性。

如果规则只是“以后可能有用就保存”，Memory 会不断吸收地址、临时目标、第三方信息和模型猜测。Recall 可能变高，current Context 却越来越不可信。

Candidate 还不是可写入事实

从 conversation 提取出的内容应先成为 memory_candidate。Candidate 保留原始表达、source、subject、适用范围和提取方式，但不会自动进入长期 current view。

candidate: user lives in Berlin
source_ref: message_41
observed_scope: this week
extraction: model_inference

这条 candidate 的问题已经可见：source 只支持“本周在柏林”，而不是“长期居住在柏林”。Write gate 的任务不是润色句子，而是判断现有证据能否支持一种可持续、可治理的长期记录。

五个 write gate

一条候选信息通常需要同时通过五个判断：

Gate要回答的问题失败时怎样处理
Durable它是否会在当前 Turn / Task 之后继续成立？留在当前 Context，或加明确 expiry
User-specific它是否描述当前 subject，而不是第三方或一般事实？不进入用户 Memory
Future-useful将来是否有清晰任务会使用它？不因“也许有用”默认保存
Source-groundedSource 是否支持要写入的 claim 和 scope？缩小 claim、要求确认或拒写
Permission-safe当前 writer 是否允许保存这类内容和敏感度？拒写或转入需要确认的受控流程

五个 gate 不是加权评分。某条信息很有用，也不能弥补它属于第三方或没有保存权限。产品可以为不同 Memory 类型设置不同 threshold，但硬授权边界不能由 relevance 覆盖。

把柏林例子走一遍

这条候选可以生成一份可解释的决定：

decision: do_not_write_long_term
reasons:
  durable: false
  user_specific: true
  future_useful: limited
  source_grounded: false_for_permanent_residence
  permission_safe: true
alternative:
  keep_in_task_context_until: 2026-07-21

如果用户说“我已经搬到柏林，以后优先推荐这里”，durable、future-useful 与 source-grounded 才同时成立；系统仍要根据位置数据 policy 决定直接写入还是先确认。相同地点，不同表达范围，会得到不同 write decision。

用户明说与模型推断不是同等证据

“我以后都安排下午”可以直接支持一条显式偏好；一次下午开会只能支持一条观察，不能自动推出长期偏好。重复行为也可能来自时区、日程冲突或临时项目。

因此 record 需要区分 evidence class：

explicit_user_statement
confirmed_user_edit
repeated_corroborated_observation
single_observation
model_inference_without_direct_evidence

这些是来源类别，不是从上到下的固定优先级。用户在 UI 中确认一个新值，本身也是显式用户证据；发生冲突时，要先比较 claim scope、发生时间与 mutation authority，再判断 provenance 能否支持当前值。用户编辑也不能把别人的数据写入自己的 Memory，重复观察也不一定需要持久化。

对推断性 candidate，更安全的动作通常是等待更多 evidence、以较短 TTL 保存为低置信观察，或向用户确认。不要把模型生成的自然语言置信度当作授权。

必须拒写的内容

有几类信息即使与任务相关，也不应默认进入长期用户 Memory：

  • 一次性验证码、access token、secret 和完整 credential。
  • 只描述第三方、且没有适当授权的数据。
  • 外部文档中的指令或未经确认的主张。
  • 高频变化、下一次使用前必须实时查询的事实。
  • 当前 writer 无权写入的敏感目录。

拒写不等于忘记当前任务。必要内容可以在当前 Run 或 Task 的受控 Context 中使用，随后按 retention policy 失效。长期 Memory 是更强的跨 Session 权限，不应成为所有 Context 的默认归宿。

Write decision 也需要测试

Write gate 应输出稳定 reason code，例如 temporary_scope、third_party_subject、insufficient_evidence、realtime_fact、sensitive_not_allowed。这样 Eval 才能用正反例测试“该写时写”和“不该写时克制”。

只测未来能否 recall，会奖励保存所有内容。还要测 write precision、scope preservation、拒写原因，以及用户确认后 decision 是否正确改变。

回到问题

“本周住在柏林”被误用，不是检索阶段才发生的错误。Write path 已经把临时事实改写成永久属性，后续 retrieval 只能反复放大污染。

让 candidate 依次通过 durable、user-specific、future-useful、source-grounded 和 permission-safe gate，系统才能决定长期写入、带期限保存、请求确认或拒写。Memory 的第一项质量指标不是记住多少，而是是否只保存自己有证据、有权限、未来确实应该继续使用的内容。

后续问题

  • 对话内写入、后台归纳、数据导入和用户编辑应拥有怎样不同的权限。
  • 已经写入的事实怎样被 supersede、revoke、delete 或恢复。
  • 怎样评测 Memory 的 restraint、freshness 和 leakage。
