Session Tree 如何支撑恢复

区分分支化 Session 历史、Context 投影、恢复边界和未来的 durable execution journal。

2026/07/24 阅读 次
Agent CoreAgentSessionRecovery

问题

Agent 调用 write_note，远端已经完成写入，但进程在 Tool Result 保存前退出。重启后，Session 中只有此前的 messages。系统应该继续、查询，还是重新调用？

同一分支此前还做过 Context compaction；重启后的宿主既无法从可见 messages 判断写入事实，也不能假定 compaction 之前选择的 model、active tools 和运行依赖仍可从当前路径完整派生。

如果恢复等同于“把 messages 重新发给模型”，模型会再次提出写入；如果直接假定已成功，又没有证据支撑。Session history 能恢复对话，却不自动恢复执行事实与运行配置。本文把两者放进同一次恢复：Session 负责可追溯历史，独立证据分别支撑 effect reconciliation 与 host configuration rehydration。

Session Tree 保存的是可追溯历史

Pi Harness 的 Session 使用 append-only、带 parentId 的 entry 形成分支树。选择不同 leaf 可以得到不同 branch，compaction entry 又能把较早消息压缩成新的 Context 起点。

这种结构比原地修改 message array 更适合：

  • 保留用户编辑或重试前的历史；
  • 从旧节点创建新分支；
  • 记录 model、thinking、active tools 等配置变化 entry；
  • 让 Context 从当前 leaf 投影出来。

但“记录过 entry”不等于“恢复时一定能看到完整配置”。Pi 的 buildContext() 使用 getPathToRootOrCompaction()。遇到带 retained tail 的 compaction 时，路径会在 compaction 边界停止，而 compaction entry 本身不保存所有配置。因此 compaction 之前最后一次 model、thinking 或 active-tools 变化可能不再参与当前 SessionContext 派生。

这意味着当前 Session 能在 context-visible path 内派生配置，而不是完整的 branch-scoped restore source。

Context projection 不是执行 journal

Session Tree 主要回答“当前分支的模型上下文是什么”。外部副作用则需要回答“哪个 operation 的哪个 Attempt 发生了什么”。两者的事实粒度不同。

开场写入至少需要以下 durable evidence：

operation id
attempt id
tool proposal
authorization/config revision
started marker
effect reference
terminal outcome or unknown

把这些全部塞进自然语言 message，会丢失状态边界；只保存最终 Tool Result，又无法覆盖“effect 已发生、result 未保存”的窗口。更强恢复需要独立的 turn/tool journal，Session message 只消费已经确定的结果。

当前 Harness 不会自动恢复完整运行配置

Pi 当前 createTurnState() 会消费从 Session 派生的 context.messages，但 model、thinking、active tools 和运行时函数依赖仍由 host 配置。Session 即使能派生这些值，Harness 也没有自动把它们重建成可执行配置。

恢复还涉及无法序列化或不应盲目反序列化的对象：

  • provider client 和进行中的 stream；
  • Tool handler、credential provider 和网络连接；
  • 当前 policy、secret 和 runtime resource；
  • 已升级的 schema 或代码版本。

因此 restore 不是反序列化整个对象图，而是 host rehydration：读取 durable state，按当前环境重新解析依赖，再校验是否兼容。

Pi 的 Session 与 Harness 当前边界可参考 session.ts 和 agent-harness.ts。

Compaction 与恢复配置要各自有契约

Context compaction 可以丢弃模型不再需要的细节；恢复配置不能因此丢失当前执行所依赖的 revision。

宿主有两种安全选择：

  1. 配置恢复独立遍历完整 parent ancestry，不复用被 Context compaction 截断的路径；
  2. compaction 同时保存可验证的 configuration checkpoint，并让后续 entry 明确引用它。

无论选择哪种，都要把 Context 摘要与 restore checkpoint 分成不同对象。前者为模型节省 budget，后者为 Runtime 恢复依赖。

用证据决定恢复动作

回到 write_note，最小恢复表可以是：

Durable evidence恢复动作
有 terminal effect record重建 Tool Result，不重复执行
只有 intent/start 和 effect referencequery/reconcile 外部系统
有 operation key，外部明确未执行创建新 Attempt
没有 durable intent 或无法查询保持 unknown，停止自动 retry

这张表故意不把“Session 中没有 Tool Result”解释成“Tool 没执行”。缺少记录只说明本地没有证据。

恢复完成后，host 再生成新的 turn snapshot，把已确认结果投影回 Context。Provider stream 不从中间续接；若需要客户端重连，应消费独立的 durable event 和 cursor。

回到问题

只恢复 messages，既无法判断 write_note 是否已在外部生效，也无法保证 compaction 之前的运行配置仍可重建。Session Tree 能提供分支化、可追溯的 Context 历史，但它有三个明确边界：

  • 配置只在 context-visible path 内派生，compaction 可能截断更早 entry；
  • 当前 Harness 只自动消费派生 messages，运行依赖由 host 重建；
  • 外部 Tool effect 需要独立的 operation/Attempt journal。

因此同一次恢复应按以下顺序进行：

  1. 用 operation journal 查询 write_note 的 terminal、effect reference 或 unknown evidence，必要时向外部系统 reconcile；
  2. 独立读取完整 ancestry 或 configuration checkpoint，再结合当前 host policy 重建 model、tools、credential provider 等依赖；
  3. 校验旧状态与当前代码、schema 和权限是否兼容，不兼容就停止或迁移；
  4. 最后才生成新的 turn snapshot，把已确认的 Tool 结果和当前配置投影为 Context。

Session Tree 是这次恢复的历史基础，但 effect evidence 和 restore configuration 都不能从可见 messages 猜出来；它本身不是完整恢复协议。
