Agent 04：Context 是受约束的投影

把来源、权限、冲突和预算决策放在 provider shaping 之前，让每次模型输入都可解释、可降级。

2026/07/24 更新于 2026/07/27 阅读 次
Agent CoreAgentContext EngineeringPolicy

问题

用户刚说：“以后请在下午联系我。”长期 Memory 里仍保存着旧偏好“上午联系”，一个查询 Tool 又返回“客户时区当前是夜间”。如果把 history、Memory 和 Tool Result 依次拼进 prompt，模型会看到三个都像事实、却互相冲突的片段。

再假设输入已经接近模型窗口上限，最简单的尾部截断还可能恰好删掉用户刚刚的更正。Context Assembly 因而不是消息拼接问题，而是一次带约束的投影决策。

Context 不是任何状态源的副本

History、Memory、文件和 Tool Result 都有自己的事实 owner。Context 只是为某个 Model Turn 生成的读取视图，它不应该反过来成为长期事实源。

至少要区分四层：

层作用
Source of Truth保存原始事实、版本与权限
Candidate可能与当前任务相关的内容
AgentMessage projectionRuntime 选择、冲突处理和压缩后的语义输入
Provider payloadAdapter 转成特定模型协议的最终请求

Pi 在模型调用边界提供 transformContext 和 convertToLlm，这体现了 AgentMessage 与 provider payload 之间的分层。它没有替宿主决定所有来源冲突和预算政策，这部分仍是 Context Assembly 的责任。

先排除不能进入的内容

排序不是第一步。没有权限、已撤销、超出当前 tenant、来源无法解释的候选，即使向量相似度很高，也不应该进入本轮。

一个候选至少要能回答：

来自哪个 source 和 revision？
在什么时间与对象范围内有效？
当前 subject / tenant 是否获准读取？
它是什么语义类型，预计占用多少 budget？

这些信息不是为了把 Context 变成数据库 schema，而是为了回答三个执行问题：这段内容来自哪里、现在是否仍有效、当前模型是否获准看到。

回到联系时间案例：旧 Memory 已被用户的新输入 supersede，它可以保留在审计历史中，却应在 candidate filtering 阶段被排除；夜间时区是 Tool 的当前观测，只影响“现在是否发送”，不能覆盖用户的长期偏好。

冲突需要按权威和时间显式处理

两个候选都合法时，Runtime 还要决定它们是互补还是冲突。常见信号包括：

  • 用户当前明确指令通常高于旧的推断偏好；
  • 同一事实源的新 revision 高于被 supersede 的旧 revision；
  • Tool observation 只在它声明的时间和对象范围内有效；
  • 系统政策可以限制动作，却不应该伪造用户事实。

决策结果最好可枚举，而不是只留下最终字符串：

include
exclude_stale
exclude_unauthorized
shadowed_by_newer_revision
compress
truncate_payload

这样，当模型做出意外回答时，工程师可以先检查 assembly decision，而不是只猜模型为什么“忽略”某句话。

Budget 应作用于语义单元

完成合法性和冲突判断后，才进入预算分配。直接按字符或 token 从尾部裁切，会破坏 Tool Result、JSON、引用关系和对话因果。

更稳妥的降级顺序是：

  1. 保留当前用户意图、必要系统约束和未解决的 Tool Call/Result 配对；
  2. 对较早 history 做带边界的摘要；
  3. 截短可重新获取的 Tool payload，同时保留 effect reference 和关键字段；
  4. 移除低相关、低权威的可选候选；
  5. 仍然超预算时明确失败或换用更大上下文，而不是静默删除关键约束。

这里没有通用的“每类来源固定占多少 token”。Source quota 是上限和保护边界，不是保证某一来源一定占满的座位。

投影结果需要可解释

对开场案例，一份最小 decision record 可以是：

user correction: include
old memory: exclude_stale
timezone observation: include, valid for current scheduling decision
older history: compress

最终 Context 可以明确告诉模型：用户偏好是下午；当前当地时间不适合立即联系；如果需要安排下一次动作，应选择下一个合适的下午时段。它没有把三条原始文本粗暴拼接，也没有让 Tool observation 改写长期 Memory。

Pi 当前转换边界可参考 agent-loop.ts。本文的 provenance、冲突和预算决策是宿主层设计建议。

回到问题

History、Memory 和 Tool Result 冲突时，Context Assembly 的正确顺序是：

  1. 从事实源生成带 provenance 的候选；
  2. 排除无权限、已撤销和不在有效范围内的内容；
  3. 按 authority、revision、时间和当前任务解决冲突；
  4. 对剩余语义单元做结构化预算降级；
  5. 记录每个 include、exclude 和 compress 决定；
  6. 最后才由 Adapter 转成 provider payload。

因此 Context 不是“所有已知内容”的集合，而是某一 Model Turn 在当前权限、证据和预算下可解释的投影。这个区别让后续 Memory、Provider Adapter 和 Context Eval 可以共享同一条证据链。
