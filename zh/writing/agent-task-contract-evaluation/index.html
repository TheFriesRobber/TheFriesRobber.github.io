Agent 46：用 Task Contract 把需求变成可验证契约

用输入、能力、禁止动作、完成证据和升级条件连接业务需求、Tool、权限、Human-in-the-Loop、Eval 与 Pilot。

问题

退款 Agent 的 PRD 写道：

Agent 应准确处理退款申请，在不确定时寻求人工帮助。

模型团队把“处理”理解为给出退款建议，产品团队认为它应创建退款草稿，业务团队则期待它完成低金额退款。对于“不确定”，有人指模型置信度低，有人指信息缺失，还有人指金额超过权限。

同一句需求产生了三种实现，也无法形成一致的 Eval。即使最终回答看起来正确，也没有人知道 Agent 是否完成了同一个任务。

自然语言需求只有进一步约束输入、能力、权限、完成证据和升级 owner，才能成为可执行的 Agent Task Contract。

Task Contract 连接业务目标与执行边界

Task Contract 不是 Prompt，也不是 Backend API Schema。它描述一次任务在业务与执行层共同成立的约束：

谁发起什么任务
→ Agent 可以观察什么
→ 可以使用哪些能力
→ 哪些动作被允许或禁止
→ 什么外部证据代表完成
→ 哪些状态必须交给其他 owner

一个概念性的退款契约可以写成：

task: prepare_standard_refund
actor: support_agent
trigger: refund_request_submitted

inputs:
  - customer_request
  - order_record
  - payment_status
  - shipment_status
  - active_refund_policy

capabilities:
  - query_order
  - query_payment
  - query_shipment
  - create_refund_draft

allowed_actions:
  - collect_task_evidence
  - classify_standard_policy_path
  - create_refund_draft

prohibited_actions:
  - submit_refund
  - modify_policy
  - access_unrelated_customer_data

completion:
  - policy_path_is_supported
  - evidence_bundle_is_complete
  - draft_order_amount_and_reason_match_authoritative_evidence
  - draft_policy_revision_matches_active_policy
  - refund_draft_reference_is_queryable

escalation:
  - condition: required_evidence_missing
    mode: clarification
    owner: requestor
    resume: re_evaluate_with_new_evidence
  - condition: trusted_sources_conflict
    mode: exception_handling
    owner: source_system_owner
    resume: continue_from_recorded_task_state
  - condition: policy_has_no_matching_path
    mode: takeover
    owner: policy_owner
    resume: human_owns_remaining_task
  - condition: amount_exceeds_authority
    mode: approval
    owner: refund_supervisor
    resume: execute_only_scoped_approved_action
  - condition: tool_effect_is_unknown
    mode: reconciliation
    owner: runtime_reconciliation_owner
    resume: continue_only_after_outcome_is_confirmed

这份示例没有规定具体实现格式。真正重要的是每个字段都改变执行或验证：删除任何一项，团队都会重新产生边界歧义。其中 runtime_reconciliation_owner 只负责发起查询并收敛本地 observed outcome；实际退款副作用仍以外部 Backend 的业务记录为权威事实。

输入要表达可用证据，而不只是字段

order_record 出现在输入列表中，不代表它天然可信或足以支持决策。

Task Contract 需要进一步约束：

  • 证据从哪个系统获得；
  • 当前执行身份能否访问；
  • 允许使用多旧的数据；
  • 哪个来源拥有哪个事实；
  • 缺失或冲突时能否继续；
  • 是否允许使用用户自行提供的内容授权动作。

例如，客户消息可以表达退款诉求，却不能证明支付状态；订单系统可以提供订单信息，却未必拥有最终支付事实。把所有内容放进同一个 Context 后交给模型总结，会丢失证据的权限和来源差异。

因此，Contract 不需要包含完整数据治理设计，但必须声明哪些 Evidence 足以支持哪些 Decision。后续 Tool 和 Runtime 才能保留这些边界。

能力列表同时定义 Agent 不能做什么

Tool surface 经常被写成系统可以提供的所有 API。Task Contract 则从当前任务出发，只暴露完成所需的最小能力。

退款草稿任务需要查询订单、支付和物流，并创建草稿；它不需要修改客户信息，也不需要直接提交退款。

最小能力范围带来两个结果：

  1. 模型更容易在相关能力之间选择；
  2. 即使 Prompt 被误解，执行边界仍然不提供无关副作用。

但没有暴露 Tool 不等于完成了禁止动作定义。某些动作可能通过多用途 Tool 间接实现，或者未来版本新增能力。因此，Contract 仍要显式声明 prohibited actions，并由 authorization 与 backend invariant enforcement，而不能只依赖模型遵守文字说明。

Clarification、Approval 与 Escalation 不是同一种人工介入

“需要人工时询问用户”把不同 owner 混在一起。

Human-in-the-Loop 至少有四种语义：

类型人工提供什么任务之后怎样继续
Clarification缺失或歧义的信息Agent 基于新输入重新判断
Approval对一个具体动作授权只执行被确认的动作
Exception handling处理规则未覆盖的业务状态由业务 owner 给出决定
Takeover接管后续任务责任Agent 停止自主推进并完整交接

退款金额超过阈值不是向客户 Clarification；政策例外也不能由任意用户点击“确认”解决；Tool 写入结果未知时，人工可能需要 reconcile，而不是再次批准相同动作。

Task Contract 应为每个条件指定交互类型和 owner。这样 Human-in-the-Loop 才是执行协议的一部分，而不是 Agent 失败后的统一出口。

完成条件必须能够独立于模型验证

如果 Contract 写着“生成正确退款草稿”，Eval 仍然需要知道正确是什么意思。

更可验证的完成条件包括：

  • 使用了任务要求的政策版本；
  • 所需证据均存在且来源获准；
  • 草稿中的金额、订单和原因与证据一致；
  • Backend 返回可再次查询的草稿引用；
  • Agent 没有调用禁止能力；
  • 需要审批时没有宣称任务已经完成。

这些条件应尽量由确定性检查或外部状态验证。只有语义质量无法直接编码时，才使用规则 Grader 或 LLM Judge，并明确它验证的是哪一层结果。

“Agent 回答退款已创建”不能证明退款草稿存在。Task completion 应由外部查询确认；自然语言回答只负责向用户表达已经确认的事实。

Contract 可以直接生成 Eval Case

每条 Contract 约束都应在 Dataset 中找到对应案例。

正常案例验证标准路径；边界案例验证金额和日期阈值；异常案例验证缺失证据、来源冲突和 Tool failure；权限案例验证 prohibited actions；对抗案例验证用户是否能诱导 Agent 越权。

一个 Case 至少包含：

initial_state:
  order_status: paid
  shipment_status: not_shipped
  refund_amount: 600

available_evidence:
  - order_record
  - payment_record
  - active_policy

expected:
  outcome: draft_created
  required_evidence: [order_record, payment_record, active_policy]
  draft_assertions:
    order_id: equals_order_record
    amount: equals_approved_refund_amount
    reason: matches_policy_path
    policy_revision: equals_active_policy_revision
  prohibited_effects: [refund_submitted]
  completion_evidence: refund_draft_reference

另一个冲突 Case 则要求：

initial_state:
  order_system_shipment: shipped
  logistics_system_shipment: not_collected

expected:
  outcome: escalated
  escalation_mode: exception_handling
  escalation_owner: logistics_owner
  resume: continue_from_recorded_task_state
  prohibited_effects: [refund_draft_created, refund_submitted]

Eval 不应强制 Agent 采用唯一自然语言或唯一推理路径，但必须验证结果状态、权限边界和必要证据。

Pilot 验证的是 Contract 假设

离线 Eval 说明 Agent 在选定 Case 和配置下能否遵守 Contract；Pilot 还要验证 Contract 是否覆盖真实工作。

需要观察：

  • 真实请求有多少落在 Contract 范围内；
  • escalation 是否遗漏了新的异常类型；
  • 人工能否使用 Agent 提交的 Evidence 接管；
  • Completion 条件是否真的对应业务完成；
  • 用户是否在 Contract 外创造新的绕行；
  • Tool 和政策变化是否导致范围漂移。

如果大量案例因为物流数据不可用而升级，问题可能不在模型，而在 Tool Coverage；如果人工总要修改退款原因，可能是 Contract 的输入或质量标准不足；如果用户频繁要求直接提交退款，可能是产品承诺与权限边界不一致。

这些发现应回流到 Contract 和 Dataset，而不是只调整 Prompt。

Contract 必须版本化

政策、Tool、权限和完成标准都会变化。一次执行只有记录所使用的 Contract revision，失败才可复现。

至少应能关联：

  • Task Contract revision；
  • Policy revision；
  • Tool definition 和权限配置；
  • Agent configuration；
  • Eval Dataset revision。

版本化并不意味着把所有内容塞进一个文件，而是让一次 Run 能够说明当时依据哪组边界执行。

当政策更新后，旧 Trace 仍可按旧 Contract 解释；新 Eval 则可以验证迁移是否改变了允许动作和完成条件。

回到问题

“准确处理退款，在不确定时找人工”无法决定 Agent 是给建议、建草稿还是直接退款，也无法区分 Clarification、Approval、Exception handling 和 Takeover。

Task Contract 把任务限定为准备标准退款草稿，声明所需证据和可用能力，禁止直接提交退款，并为状态冲突、权限超限和 unknown effect 指定升级条件。相同约束随后生成正常、边界、异常、权限和对抗 Eval。

需求因此不再是一句依赖各团队解释的期待，而成为可以实现、测试、审计和在 Pilot 中证伪的执行契约。

Agent 需求调研的终点不是功能列表，而是一项具有明确输入、能力、责任、完成证据和退出条件的 Task。
