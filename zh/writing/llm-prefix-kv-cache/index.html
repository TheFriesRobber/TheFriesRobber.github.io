LLM Infra 07：Prefix Cache 复用为什么不能只看相同前缀

把 Prefix/KV Cache 复用拆成 deployment namespace、Token block identity 与 isolation policy，避免把文本相同误当成状态兼容。

2026/07/29 阅读 次
LLM InfraInferenceKV CacheCaching

问题

一个平台直接对 Prompt 文本做 hash，作为 Prefix Cache key。模型升级或切换 LoRA 后，相同文本仍命中旧条目；另一个租户发送相同系统 Prompt，也进入了同一个共享域。

文本相同只说明输入字符串相同。KV Cache 是一次特定模型执行产生的派生状态，复用前还要回答两个问题：

  1. 这份状态在执行上是否兼容？
  2. 即使兼容，策略是否允许它们共享？

KV 不是文本，而是模型派生状态

Transformer 在处理 Token 时，为 attention 计算并保存 Key/Value state。后续 Token 可以读取已有 KV，避免重新计算整个前缀。

因此，复用的直接输入不是原始字符串，而是 Token IDs 与它们所在的前缀位置。Chat template 和 tokenizer 会影响字符串怎样变成 Token；如果两个请求最终得到完全相同的 Token IDs，它们本身不会继续改变 KV。反过来，相同文本经过不同 template 或 tokenizer 得到不同 Token IDs，自然不能命中同一 block identity。

更根本的变化来自模型执行：

  • model weights 或 revision；
  • LoRA / adapter；
  • attention 与 position 语义；
  • KV dtype、layout 与 format version；
  • 影响模型输入的多模态内容。

这些条件在一个单模型 Runtime 内可能由进程配置固定，并不一定逐项出现在 per-block hash 中。跨进程或远程 Cache 服务则需要一个外层 namespace，防止不同 deployment 的 blocks 意外相遇。

把 Cache identity 分成三层

一份可审计的设计可以分成：

cache_namespace:
  model_artifact_digest: sha256:...
  model_config_digest: sha256:...
  adapter_artifact_digest: sha256:... # base deployment 也使用稳定 sentinel
  kv_format: fp16-layout-v3
  attention_mode: causal-rope-v2
  block_hash_algorithm: sha256
  serialization_format: canonical-cbor
  serialization_version: 1

block_identity:
  parent_block_hash: ...
  token_ids_hash: ...
  runtime_extra_hashes:
    multimodal_input: null
    lora_id: null

isolation_policy:
  trust_domain: tenant-group-a
  cache_salt: ...
  retention_class: short-lived

这是设计建议，不是 vLLM 现有对象的复制。

  • cache_namespace 证明物理状态格式与 deployment 兼容。Adapter 字段必须由不可变 artifact digest 派生；Runtime-local LoRA ID 只能在固定 engine namespace 内使用。跨进程或远程 Cache 还要固定 hash algorithm 与 canonical serialization version，不能假设不同 Python/Runtime 版本产生可复现的 bytes。
  • block_identity 证明这是同一条 Token prefix chain 上的同一 block。
  • isolation_policy 证明请求被允许进入同一个共享域。

把三层压成一个 prompt hash，会同时丢失执行兼容性与授权边界。

具体 Runtime 的 Block hash 只覆盖它拥有的边界

vLLM 当前 Automatic Prefix Caching 的 block hash 由 parent block hash、当前 block Token IDs 和 extra hashes 构成。官方设计给出的 extra hash 例子包括 LoRA ID、多模态输入 hash 与用于多租户隔离的 cache salt。

它还只缓存完整 blocks。Parent chain 使相同 Token block 位于不同前缀时不会被错误视为同一状态；LoRA 与多模态信息则补充仅凭 Token IDs 无法表达的执行差异。

为什么 model revision 没有总是逐 block hash？因为单 engine 的 base model 通常已经固定。它属于 engine/namespace 的前置条件。若平台把 blocks 移到跨 deployment 的远程 Cache，namespace 就必须显式带上这些兼容维度。

这里的规则应该是：Cache key 只需要包含该层可能变化、且会改变派生状态的字段；更上层固定的条件必须由 namespace 隔离。

数学兼容不等于允许共享

两个租户可能使用同一 model revision、相同 Token IDs 和相同 adapter，计算出的 KV 在数学上兼容。平台仍可能禁止共享，因为 Cache hit 本身可能泄露某个前缀是否出现过，条目也可能受不同 retention 或数据区域策略约束。

vLLM 的 cache_salt 会参与第一个 block 的 hash，并通过 parent chain 影响后续 blocks，从而限制前缀 Cache 的共享域。官方文档把它用于共享环境下的 Cache isolation。

这不是完整的租户安全方案。Cache salt 不能代替入口鉴权、日志隔离、进程/设备隔离和 retention enforcement。它只解决 Cache reuse 这一条路径。

Isolation decision 应由受信任边界注入，不能接受客户端随意声明：

authenticated tenant
→ policy resolves trust_domain and salt
→ request enters Cache namespace
→ block lookup

Eviction 也必须保留身份与状态

Prefix Cache 仍占用 KV blocks，因此会与 active sequence 争夺显存。Runtime 需要决定哪些条目可被驱逐、哪些被当前请求引用、哪些受 retention policy 限制。

常见状态可以概念化为：

candidate → resident → referenced → evictable → evicted

Eviction policy 可以考虑最近使用、block 成本和显存压力，但不能越过 namespace 与 isolation boundary 合并统计。一个租户的高命中率不应自动授权另一个租户共享。

缓存命中还必须进入可观测记录：

cache_decision:
  namespace_digest: ...
  matched_tokens: 512
  block_count: 32
  isolation_domain: tenant-group-a
  outcome: hit
  reused_prefill_tokens: 512

这样，Benchmark 才能区分 cold 与 warm state，容量分析也能知道多少 Prefill work 被真实跳过。

回到问题

开篇的 prompt hash 只绑定了原始文本，既没有证明 KV 来自兼容 deployment，也没有表达 tenant sharing policy。

安全的复用要经过三层判断：deployment namespace 是否兼容，Token block 与 parent chain 是否相同，isolation policy 是否允许共享。Tokenizer 和 template 作为 provenance 决定 Token IDs，但在 Token IDs 已经相同时，不应被机械重复加入 key。

Cache 命中率只能在这三层边界之内优化。越过正确性或隔离边界得到的“命中”，不是性能收益，而是状态污染。

Cache identity 决定哪些 KV 状态可以复用；下一篇的 quantization 会改变这些状态的物理表示，因此必须进入 namespace，并重新验证 memory、quality 和 service curve。
