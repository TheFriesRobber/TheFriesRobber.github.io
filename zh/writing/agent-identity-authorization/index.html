Agent 20：身份与授权必须贯穿执行链

区分 subject、actor、execution identity、credential 与 authorization，让权限跨 Queue、Tool 和 Child Run 传播。

2026/07/24 更新于 2026/07/27 阅读 次
Agent ProductionAgentSecurityAuthorization

问题

用户让 Agent 修改一份报告。API 入口已经认证用户，也确认他此刻可以编辑文件。系统随后把任务放进 Queue，由后台 worker 创建 Child Run，最后调用文件 Tool。

真正写入时，backend 看到的是 worker 的 service credential。审计只能回答“某个 worker 调用了接口”，却无法证明它在代表哪个用户、委派经过了哪些 Agent，也无法判断原来的权限是否已经被撤销。

一种看似直接的修补是把用户 access token 放进 Job，让它沿 Queue、Child Run 和 Sandbox 一路传下去。这又扩大了 bearer credential 的暴露面，而且 token 在等待期间可能过期。

真正需要贯穿执行链的不是同一枚 token，而是可验证的关系：谁的目标正在被执行，当前谁在行动，哪个工作负载发起请求，以及当前 action 对当前 resource 是否仍被允许。

五个概念回答不同问题

概念回答的问题文件修改示例
Subject目标与权限代表谁发起请求的用户
Actor谁正在代表 subject 行动Agent、Child Run 或 worker
Execution identity哪个工作负载访问基础设施worker workload identity
Credential调用方怎样向某个服务证明身份audience-bound 短期 token
Authorization当前动作是否允许file.update on file_12

它们不能互相替代。trace_id 可以关联调用路径，却不是身份；user_id 是一个声明，单独放进 Queue 并不能证明是谁写入；service credential 能证明 worker，却不会自动表达它代表哪个 subject。

RFC 8693 的 OAuth Token Exchange 明确区分 subject token 与 actor token，并区分 delegation 和 impersonation。Agent 系统不一定采用这套协议，但应保留相同的语义区别：delegation 不应把 actor 伪装成 subject。

Queue 保存委派引用，不保存无限权限

入口完成认证后，可以创建一条受约束的 delegation record：

{
  "delegation_id": "del_81",
  "subject_ref": "user_7",
  "actor_ref": "agent_run_19",
  "tenant_id": "tenant_3",
  "actions": ["file.update"],
  "resources": ["file_12"],
  "audience": ["file-service"],
  "expires_at": "...",
  "parent_delegation": null,
  "status": "active"
}

Job 只携带 delegation_id 和完成工作所需的稳定 identity。worker 用自己的 workload identity 领取 Job，再向可信授权服务解析 delegation，并获得面向 file service 的短期 credential。长期用户 token 不进入 prompt、Queue payload 或 Workspace。

这种设计没有冻结入口时刻的权限。worker 执行前仍需检查 delegation 是否过期或被撤销、subject 是否仍能访问资源、action 和 audience 是否匹配。

Child Run 只能收窄委派

父 Agent 能修改整个项目，不代表负责摘要的 Child Run 也需要写权限。创建 child 时，应让可信 Runtime 计算子权限是否为父权限的子集：

parent: files.read + files.write on /project/**
child:  files.read on /project/docs/**

收窄可以发生在 action、resource、tenant、audience、有效期和 delegation depth 上。Child Run 返回的自然语言不能自行扩大这些边界；它的 execution identity 也不能仅凭 run_id 推导，必须由可信运行环境绑定和认证。

如果后续确实需要扩大权限，应回到拥有授权权力的主体重新决策，而不是让模型在 Tool arguments 中填一个更大的 scope。

RBAC、ABAC 与 capability 是互补层

这三种模型常被当作互斥选项，其实分别适合不同稳定性：

  • RBAC 表达稳定职责，例如“编辑者”可以提出文件更新。
  • ABAC 在决策时消费 tenant、resource owner、classification、时间等属性。
  • capability 或 delegation grant 表达针对具体 action/resource 的临时、可传递但受约束的能力。

一个实际决策可以先用 RBAC 确认 subject 具备编辑职责，再用 ABAC 检查文件所属 tenant 和当前状态，最后签发只对 file_12、file.update 和 file service 有效的短期 grant。

这是设计组合，不是某项标准要求的固定流水线。系统简单、请求不跨边界时，backend 直接基于认证用户执行 RBAC/ABAC 已经足够；只有发生异步执行或 delegation，才需要稳定的委派引用。

模型提出参数，Backend 执行授权

模型可以提出：

{"tool": "update_file", "fileId": "file_12", "expectedRevision": 7, "patch": "..."}

模型可见的 fileId 必须来自 Runtime 已解析并授权暴露的 canonical resource reference；如果用户最初提供的是 path，可信边界要先把它解析为绑定 revision 的 resource identity，再进入 proposal。模型不能权威地提供 subject_id、tenant_id、授权结论或 credential。Runtime 从可信 Session 和 delegation 中注入这些字段，Tool handler 做参数、revision 与 policy 检查，最终由拥有资源事实的 backend 再次授权：

// 概念示例
await fileService.update(
  {fileId: args.fileId, expectedRevision: args.expectedRevision, patch: args.patch},
  {
    subject: trusted.subject,
    actor: trusted.actor,
    executionIdentity: trusted.executionIdentity,
    delegation: trusted.delegationRef,
    tenant: trusted.tenant
  }
);

最终 enforcement 必须靠近资源，因为只有 backend 知道文件当前 owner、revision、classification 和策略。Tool description、system prompt 和模型“认为已经授权”都不是可信授权事实。

把身份链写进审计，而不是只写调用者

一次有用的 audit record 至少关联：

subject → actor chain → execution identity
        → delegation revision
        → tenant + action + resource
        → authorization decision + effect outcome

这不等于记录所有 token 或 prompt。Credential 通常只记录 issuer、audience、key/token reference 和过期信息；secret 本体不应进入日志。审计也要区分 authorization decision 与最终 effect，避免把“允许调用”误写成“修改已经成功”。

回到问题

开场中的 worker 不应仅靠共享 service token 修改报告。它领取 Job 后，用 workload identity 解析仍有效的 delegation，获得面向 file service 的短期 credential；file service 再根据当前 subject、actor、tenant、action 和 file_12 的资源状态执行授权。

这样，用户权限被撤销时 backend 可以拒绝；Child Run 只能使用被收窄的 grant；审计也能同时说明谁的目标、哪个 actor 和哪个工作负载参与了动作。

身份连续不意味着 credential 一路传到底。连续的是可验证的 delegation chain，授权则在真正拥有资源事实的边界重新执行。
