LLM Infra 15：模型升级、灰度与 Fallback 怎样保持部署契约一致

将 Model、Tokenizer、Template、Adapter、Engine image、Runtime 配置与 capability claims 固定为 release manifest，并以同一 workload 推进灰度和回滚。

2026/07/29 阅读 次
LLM InfraInferenceRelease EngineeringFallback

问题

一次“模型小版本升级”只替换了 model name，沿用旧 tokenizer、template 与 generation defaults。接口仍返回 200，但实际 Token 序列、结构化输出、latency distribution 和显存行为都改变了。只回滚权重，也没有恢复旧行为。

推理部署的可发布对象不是裸模型权重。它是一组共同决定输入、执行与输出契约的 artifact 和配置。

Model name 不是 Release identity

Hugging Face Hub 允许用 commit revision 固定 snapshot；Transformers 的 tokenizer revision 和 chat template 决定消息如何变成模型实际看到的 Token。vLLM 也分别暴露 model revision、code revision、tokenizer revision、quantization 和 generation config。

一份 release manifest 可以是：

inference_release:
  release_id: chat-v3-20260729.1
  base_model:
    repository: example/chat-model
    commit: 8f3...
    digest: sha256:...
  tokenizer:
    repository: example/chat-model
    commit: 8f3...
    digest: sha256:...
  chat_template_digest: sha256:...
  adapter:
    repository: example/tool-adapter
    commit: 91a...
    digest: sha256:...
  generation_config_digest: sha256:...
  weight_dtype: bf16
  quantization_method: null
  engine_image_digest: sha256:...
  engine_args_digest: sha256:...
  parallelism: {tp: 2, pp: 1}
  hardware_class: gpu-pool-a
  protocol_schema_version: response-v4
  capability_claims: [streaming, structured-output-v2]
  benchmark_evidence_refs: [curve_aa12, quality_87c]

这是本文的设计建议。重点是所有可变项都被解析为不可变引用，而不是依赖 main、latest image 或隐式 defaults。

Compatibility 至少有四个维度

维度要回答的问题
Protocolrequest/response schema、streaming 与 finish reason 是否兼容
CapabilityContext、structured output、adapter、reasoning 等是否支持
Quality同一 evaluation suite 是否通过
Resourcememory、TTFT/TPOT、service curve 是否仍在 envelope 内

Fallback 只能进入预先审核的 allowlist，并满足完整 compatibility contract：protocol、当前请求必要 capabilities、quality/safety gate、数据政策，以及该 workload 所需的 SLO envelope。实际 routing 时还要确认资源可用，但“有空闲容量”不能绕过质量、语义或数据约束。Infra 不负责把不兼容 provider response 塑形成业务想要的语义；那属于 Agent/provider boundary。Infra 要么选择满足完整合同的 deployment，要么返回显式 unsupported/rejected outcome。

“语义等价”也不能只写在配置里。它需要 evaluation、contract tests 和 workload-specific Benchmark 支持。

Shadow、Canary 与 Staged rollout 证明的事情不同

Shadow 可以把生产输入复制到候选 release，观察离线输出、latency 和资源，但不能证明真实 client delivery，也可能因额外流量影响容量。涉及 Prompt 内容时还要满足数据政策。

Canary 让少量真实请求由候选处理，可以观察端到端结果；流量必须按 workload segment 分层，否则只覆盖短请求会掩盖长 Context 风险。

Staged rollout 逐步扩大兼容流量，同时设置 promote、hold 与 rollback 条件。

每个阶段都要同时记录：

requested model/capability
resolved release digest
workload fingerprint
quality result
TTFT/TPOT/goodput
failure and fallback outcome

只比较 5xx 不够。返回 200 的协议漂移、输出缩短或质量回归同样可能违反契约。

Rollback unit 必须是完整 Manifest

如果新 release 同时改变：

  • model weights；
  • tokenizer / template；
  • Runtime image；
  • scheduler defaults；
  • quantization / parallelism；

只回滚其中一个对象会产生未验证组合。Rollback 应把 routing 重新指向一个已经验证、仍可加载的完整 manifest。

这也不能保证逐 Token 重现旧输出。Sampling、driver/hardware、外部 policy 和 Cache state 都可能影响行为。Rollback 的合理承诺是恢复到经过验证的 deployment contract 与证据范围，而不是 bitwise determinism。

平台还要保留：

  • 旧 artifact 与 image 的可用性；
  • 对应 hardware class；
  • migration 前后的 Cache namespace；
  • in-flight requests 的 draining policy；
  • 何时禁止从新 release fallback 到旧 capability。

用开篇升级走一遍

原升级把新 weights 与旧 tokenizer/template 混在一起。按 release manifest 流程：

  1. 构建候选 manifest，固定所有 artifact 和 defaults。
  2. 运行 protocol/quality contract tests。
  3. 用第 03 篇的相同 workload 测新 service curve。
  4. Shadow 只收集允许的数据与差异。
  5. Canary 按 workload segment 接收真实流量。
  6. 任一硬约束失败，Router 将新请求切回旧完整 manifest；候选进入 draining。

这样，rollback 恢复的是已知组合，而不是临时拼出的“旧权重 + 新 Runtime”。

回到问题

开篇升级仍返回 200，却改变 Token、协议、延迟和显存，因为 model name 没有固定完整 deployment identity。只回滚权重，自然不能恢复经过验证的组合。

模型发布应以完整 release manifest 为原子单位，用同一 workload 与完整 compatibility contract 推进 Shadow、Canary 和 staged rollout。Fallback 只能选择同时通过 protocol、capability、quality/safety、数据政策与 SLO envelope 的 allowlisted release；Rollback 回到完整 manifest，但不夸大为逐 Token 确定性重现。
