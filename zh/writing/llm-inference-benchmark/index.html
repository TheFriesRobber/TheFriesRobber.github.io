LLM Infra 03：一次推理 Benchmark 怎样产生可比较的 Service Curve

固定 workload distribution、arrival control、warm state、deployment manifest 与质量约束，测出可供容量规划消费的 service curve。

2026/07/29 阅读 次
LLM InfraInferenceBenchmarkReproducibility

问题

方案 B 的报告显示 tokens/s 高于方案 A。进一步查看才发现，B 使用了更短的输出、已经 warm 的 Prefix Cache，并且只统计成功请求；超时请求从延迟分布中消失了。

两个结果都叫“100 QPS Benchmark”，却不是在测同一件事。QPS 没有说明 arrival pattern、并发上限、输入/输出长度、warm state 和质量条件；成功请求平均值还会把最慢的一批请求直接删掉。

Benchmark 的目标不是产出一个更大的数字，而是回答一个具体决策：在固定约束下，哪个 deployment configuration 能交付多少 workload。

先写决策，再启动压测

不同问题需要不同实验：

  • 比较 Runtime，需要固定模型、量化、并行和 workload。
  • 比较并行策略，需要固定总硬件、模型、Runtime 与 SLO。
  • 验证容量，需要改变 arrival rate，观察 SLO attainment 何时下降。
  • 验证 cold start，需要明确每次 trial 是否重新加载模型和 Cache。

如果实验问题只是“谁更快”，研究者很容易在看到结果后改变解释。更稳妥的方式是在运行前写出：

decision: choose_serving_configuration
hypothesis:
  candidate_b_increases_goodput_without_changing_quality
fixed:
  workload_fingerprint: wl_7fd2
  model_release: model-manifest-sha256:...
  hardware_pool: gpu-topology-a
  quality_gate: chat-contract-v3
changed:
  serving_engine_config: [candidate_a, candidate_b]
primary_metric:
  name: application_goodput_rps
feasibility_gate:
  good_request_fraction_gte: 0.95

这是一份概念性 experiment contract。它强迫实验在开始前说明固定了什么、改变了什么，以及什么结果可以推翻假设。

Workload identity 不能只写 QPS

上一篇的 workload envelope 应直接进入 Benchmark，而不是重新生成一组方便的请求。至少需要固定：

  • 输入与输出 Token 分布以及两者相关性；
  • model、adapter、template 与 feature 分布；
  • arrival process、burstiness 和并发上限；
  • streaming、deadline、priority 与取消行为；
  • warm/cold Cache 状态；
  • 请求数量、持续时间和随机种子。

vLLM 的 Benchmark CLI 把 request-rate、burstiness 与 max-concurrency 分成独立参数；NVIDIA AIPerf 也能把 Poisson request rate 与最大并发组合。这说明 request rate 和 concurrency 不是同一个旋钮。

两种常见负载模式回答不同问题：

  • Open-loop 以外部到达过程发送请求。服务变慢时，新请求仍继续到达，可以观察排队和过载。
  • Closed-loop 保持固定并发，一个请求完成后才发下一个。服务变慢时，发送速率也随之降低，更适合观察给定并发下的响应。

用 closed-loop 结果承诺 open-loop 容量，会让负载生成器替服务完成 backpressure；用无限 request rate 测出的 maximum throughput，也不能直接代表生产 arrival 下的 tail latency。

Deployment manifest 决定结果属于谁

推理性能不是裸模型权重的属性。一次可复现 trial 至少要记录：

deployment_manifest:
  model:
    repository: example/model
    revision: immutable-commit
    tokenizer_revision: immutable-commit
    chat_template_digest: sha256:...
  runtime:
    engine: example-engine
    version: x.y.z
    quantization: bf16
    scheduler_config_digest: sha256:...
  placement:
    replicas: 1
    tensor_parallel: 2
    pipeline_parallel: 1
  hardware:
    gpu_model: example-gpu
    gpu_count: 2
    interconnect: local-high-bandwidth
  state:
    model_warm: true
    prefix_cache: cold

同一 model name 可能解析到不同 revision；Tokenizer、chat template 和 generation defaults 也会改变实际 Token 序列。Runtime 版本、Kernel、driver、并行拓扑和 scheduler 配置则会改变执行路径。

如果 manifest 不完整，结果只能被标记为一次观测，不能成为下一轮容量规划的稳定输入。

Service curve 不是单点峰值

容量规划真正需要的不是“最大 tokens/s”，而是 service curve：在固定 workload 与 deployment manifest 下，随着 offered load 或 concurrency 变化，系统能交付怎样的 latency、goodput 和 failure outcome。

每个 request 先同时检查 TTFT ≤ 1,500 ms、TPOT ≤ 80 ms、completion 与 quality，再计算 application goodput 和 good-request fraction。如果契约要求 good-request fraction ≥ 95%，这条合成曲线能支持的结论是：满足条件的区域到 1.5 req/s 附近为止。表中的 P95 只帮助诊断分布，不能单独证明联合达标。这个例子也不能证明任何真实硬件有对应容量。

Service curve 必须保留完整分布与所有 attempted outcome。若只保留成功请求平均值，过载区反而可能看起来更快，因为最慢请求已经 timeout、被拒绝或取消。

Warm state、输出长度与质量不能成为暗门

三类常见偏差会制造虚假收益。

第一，Cache 状态不同。Prefix Cache warmup 可以减少重复 Prefill，但它只对匹配前缀生效。A warm、B cold 或反过来，都不是公平比较。应分别报告 cold、steady-state warm 和 Cache hit distribution。

第二，输出长度不同。如果一个候选因为 EOS、截断或 generation defaults 变化而生成更短文本，E2E latency 和 tokens/s 都会改变。实验要记录 requested 与 actual output length，并解释为什么输出仍满足同一质量约束。

第三，失败样本被过滤。每个 request 应保留 arrival、first token、completion/cancellation、Token count 和 reason code。Aggregate 表只能由完整 raw results 导出，不能成为唯一证据。

对于 stochastic decoding，还需要固定或记录 sampling config、随机种子和 trial repetition。质量 gate 应先于性能结论：输出协议或能力已经改变时，不能把更快称为等价优化。

从 Benchmark 交付可消费的证据

一次可用于容量规划的 Benchmark 至少交付四类 artifact：

  1. experiment-contract.yaml：问题、假设、固定项和变更项。
  2. workload-envelope.yaml：长度、arrival、deadline 与随机种子。
  3. deployment-manifest.yaml：模型、Runtime、配置、硬件和 warm state。
  4. raw-results.* 与派生脚本：每个 request 的时间戳、Token、outcome 和 trial identity。

还需要记录 warmup、trial 数量和环境噪声。没有重复实验和 uncertainty 时，可以报告一次观测，但不应把小差异解释成稳定收益。

回到问题

方案 B 的 tokens/s 更高，原报告仍不能支持“B 更好”。它改变了输出长度与 Cache 状态，还删掉了超时请求，等于同时改变 workload、state 和结果分母。

正确的重测方式是固定 experiment contract、workload envelope、deployment manifest 和 quality gate，使用相同 arrival control，并保留全部 raw outcomes。最终交付的不是单点峰值，而是 goodput、TTFT、TPOT 与 failure 随 offered load 变化的 service curve。

下一篇容量规划可以消费这条曲线；如果 workload 或 manifest 改变，曲线也必须失效并重新测量。
