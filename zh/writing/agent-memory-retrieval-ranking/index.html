Agent Memory 五：Retrieval 不能只看相似度

从当前有效事实出发，组合 keyword、vector、hybrid search 与 reranking，而不是只优化相似度。

2026/07/17 阅读 次
AgentMemoryRetrieval

问题

用户问：“帮我安排下周的项目评审。”Memory 中有两条记录：旧版本写着“上午有空，适合评审”，新版本则是“工作日只剩下午有空”。Query 里出现“评审”，所以包含同一个词、描述也更完整的旧版本获得更高相似度。

Vector search 没有出错。它完成的是“找语义相近文本”，而系统需要回答的是“当前任务可以使用哪些仍有效的事实”。如果检索只按相似度排序，过期、被 supersede 或无权读取的内容仍可能赢得第一名。

Candidate generation 不等于最终 Memory

Memory Retrieval 可以拆成一条有边界的 pipeline：

Task query
  → permission / subject filter
  → keyword + vector candidate generation
  → current-version resolution
  → task-aware reranking
  → Context Assembly

Keyword、vector 和 hybrid search 都只负责扩大 candidate recall。Candidate 进入 Context 前，还必须解析到 source of truth 中的 current version，并经过 permission、有效期与 task relevance 检查。相似度是信号，不是授权，也不是事实状态。

Keyword、vector 和 hybrid 各自解决什么

方法擅长找回容易漏掉或误排
Keyword人名、产品名、错误码、原句和稀有 token同义改写、自然语言表达变化
Vector语义相近但措辞不同的记录精确标识符；也可能把相似的旧版本排得很高
Hybrid合并 lexical 与 semantic candidate仍不理解版本、权限和业务有效性

Hybrid search 可以用加权分数或 reciprocal rank fusion 合并两路结果。它通常比押注单一路径更稳健，但融合只改变候选顺序，不会自动过滤 revoked record。Subject、tenant 与 read permission 必须在读取 candidate payload 和参与 ranking 之前执行；version 与 expiry 可以在 source-of-truth resolution 时验证，但仍须在 Context Assembly 前完成，并在注入模型前再次校验 authorization。

把评审安排的例子走一遍

候选层可能返回：

1. v1  上午有空，适合安排项目评审   keyword/vector: high
2. v2  工作日只剩下午有空          vector: medium
3. v5  偏好用 30 分钟完成评审       keyword: medium

Version resolver 根据稳定的 memory_id 查询 current view，发现 v1 已被 v2 supersede，于是 v1 不能进入 reranking。接下来，reranker 结合当前 Task“安排评审”判断：v2 决定可用时段，v5 决定会议长度，两条都相关。最终交给 Context Assembly 的不是 top-1 文本，而是一组仍有效、允许读取且作用不同的事实：

availability: weekday afternoons only (current v2)
meeting preference: 30-minute reviews (current v5)

如果搜索索引同步较慢、仍把 v1 排在第一，source-of-truth resolution 也会将它淘汰。不能把“稍后重建索引”当作正确性保证；索引可以提供 candidate，不能决定 current truth。

Reranking 需要哪些信号

通过硬过滤后，reranking 才适合综合软信号：

  • 与当前 Task 和阶段的相关性；
  • memory type，例如可用时段、偏好或已完成事实；
  • freshness 与显式 expiry；
  • source authority 和 evidence strength；
  • 是否需要与其他 current record 一起使用。

可以把它们实现成可学习模型、规则或两阶段组合，但不要用一个不透明总分覆盖 permission、revocation 或 current-version 状态。硬约束先过滤，软信号再排序，失败时才能解释某条 Memory 为什么没有进入 Context。

Query 也不必只复制用户最后一句话。Runtime 可以根据 Task 类型构造结构化 retrieval request，例如 subject、目标 memory type、时间窗口和所处阶段。这样“安排评审”能主动寻找 availability 与 meeting preference，而不是等待两条记录偶然拥有相似措辞。

评估不能只看相似度

离线数据集至少要标注：应该召回的 current record、应该拒绝的 stale 或 unauthorized record，以及 Task 最终需要的 record set。由此可以同时测：

  • recall：需要的当前事实是否进入候选和最终结果；
  • precision：返回内容是否确实帮助当前 Task；
  • stale-hit rate：superseded、expired 或 revoked 内容是否被使用；
  • unsupported-use rate：缺少来源或权限的内容是否进入 Context。

还要故意让搜索索引落后于 version store，验证 current-view resolution 仍能阻止旧版本。只在干净索引上测 top-k 相似度，会错过 Retrieval 最危险的失败路径。

回到问题

旧记录因为包含“项目评审”而更相似，却已经不是当前可用事实。把它排在第一是 candidate generation 的合理结果，把它交给模型才是 Retrieval pipeline 的错误。

先用 keyword 与 vector 提高 recall，再以 source of truth 解析 current version，执行 permission 和有效性硬过滤，最后按 Task relevance、type、freshness 与 authority rerank。Memory Retrieval 的产物才会从“相似文本”变成“当前任务可以信任的一组事实”。

后续问题

  • 检索出的多类 Memory 应各占多少 Context Budget。
  • Memory 中的外部文本怎样避免通过 Retrieval 注入指令。
  • 怎样联动评估 write restraint、retrieval recall 和下游 Task outcome。
