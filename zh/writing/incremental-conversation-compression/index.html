Context Engineering 三：用增量压缩管理长对话

用 checkpoint summary、增量压缩与来源回链管理长 conversation。

2026/07/15 阅读 次
AgentContext EngineeringMemory

问题

假设用户与 Agent 通过 100 次用户交互完成一份报告：前 30 次确定范围，中间 40 次搜索资料，最后 30 次修改结论。

到第 70 次用户交互时，完整 history 已经放不进 Context。最直接的处理有两种：

  1. 每次重新总结前面所有消息。
  2. 维护一份 summary，每次空间不足就用新 summary 覆盖旧 summary。

第一种做法会反复读取和总结同一批内容，成本随对话增长；第二种做法虽然便宜，却容易让 summary 在多次改写中逐渐偏离原文。更麻烦的是，用户可能在第 82 次交互时说：“报告范围不是所有地区，只保留欧洲。”系统需要知道旧 summary 中哪些结论依赖了被更正的范围。

如果 summary 只是一段没有来源的文字，系统既不知道它覆盖了哪些消息，也不知道应该局部修正、整体重建，还是让最近一句话临时覆盖它。

所以长对话压缩的核心不是“写一段更短的摘要”，而是：把 summary 当成可重建的派生视图，并明确它覆盖的原始区间。

先把原始历史与模型输入分开

压缩流程本身不应该改写或删除 conversation 的事实记录；独立的数据保留与授权策略仍可能让来源被删除或变得不可读。可以先把两个概念分开：

  • Raw history：在保留期限与当前授权允许范围内可读的用户消息、模型回复、Tool Call 与 Tool Result 原始记录。
  • Context view：当前 Model Turn 真正送给模型的 history 视图，可以由 summary 加最近原文组成。

Raw history 是 summary 的来源；summary 是为了满足 Context Budget 生成的派生内容。只保留 summary，相当于用缓存替代了原始数据：一旦压错，就没有可靠依据修复。反过来，来源被删除或权限被撤销后，依赖它生成的 summary 也不能继续绕过原策略提供内容。

这里说的 compression checkpoint 是“历史压缩到哪个位置”的水位，不是 Runtime 恢复执行所用的 Checkpoint。它不负责恢复 Tool attempt、外部副作用或进程状态。

一次增量压缩包含三个区间

可以把当前 history 分成三部分：

checkpoint summary | stable raw prefix | recent raw window
     已压缩             可以继续压缩          暂时保留原文
  • checkpoint summary 覆盖更早、已经稳定的消息。
  • stable raw prefix 是上次 checkpoint 之后已经结束的话题或执行阶段。
  • recent raw window 保留正在讨论的内容、未完成 Tool Call 和用户最新更正。

“稳定”不是指消息足够旧，而是指它不再参与一个尚未收敛的动作。模型刚发出 Tool Call、结果还没回来时，不能只保留一句“正在查询”；否则下一个 Model Turn 可能失去 call/result 配对关系。

Checkpoint 需要记录覆盖范围

一条可用的 summary 记录不只有正文：

summary_id: summary_3
covers: event_seq 1..checkpoint_seq
dependencies:
  previous_summary_backlinks: [summary_2]
  source_spans:
    - event_seq 1..previous_checkpoint_seq
    - event_seq previous_checkpoint_seq+1..checkpoint_seq
  decision_refs: []
policy_revision: 4
authorization_revision: authz_19
retention_revision: retention_6
created_at: 2026-07-15T10:00:00Z

这里的 event_seq 是 Session Event Log 中的顺序，覆盖用户消息、模型回复、Tool Call 与 Tool Result；它与 message_id=msg_evidence_42 这类稳定内容 identity 不是同一种编号。covers 只描述 summary 代表哪段 event interval，让 Assembly 判断它与 recent window 是否重叠或存在缺口；dependencies 才记录影响 summary 内容的完整依赖，包括原始来源、Assembly Decision，以及生成时实际复用的 previous-summary backlink。依赖检查会递归沿 backlink 展开，所以不能用 coverage interval 代替 dependency closure。policy_revision 说明压缩规则，authorization 与 retention revision 则记录生成时采用的数据可见性边界。

正文还应尽量保留结构，而不是把所有内容写成一段散文：

当前目标：完成欧洲市场报告
已确认约束：只使用公开资料；引用必须可追踪
已完成：资料搜索、数据清洗
仍未解决：2025 年口径是否与 2024 年一致
关键证据：message_id msg_evidence_42、tool_result_id result_17、file_id file_8@revision_8

结构不能保证摘要一定正确，但能让后续压缩与冲突处理知道哪些内容是目标、约束、完成状态或证据，而不是把它们混成同一种“背景”。

增量更新不是无限总结 summary

到第 70 次用户交互对应的稳定 event 边界时，系统可以用 summary_2 + 上次 checkpoint 之后的 stable raw prefix 生成 summary_3，避免每次都重新处理此前的完整 history。下一次则继续从新的稳定边界推进。

但如果永远只总结上一版 summary，早期遗漏会被永久继承，多轮改写也会累积语义漂移。因此增量路径还需要一条 rebase 路径。在原始来源仍然可读时，下列变化应触发从受影响 raw history 重新生成，而不是继续叠加：

  • 用户明确更正了被 summary 保存的事实或约束。
  • 压缩 policy、模型或结构发生不兼容变化。
  • Eval 发现某类事实在连续压缩后经常丢失。

来源删除或权限撤销不是普通 rebase。系统应沿完整 dependency closure 将直接或传递依赖该来源的 summary 标记为不可用，而不能只查找 coverage interval；然后再只用剩余可读、仍获授权且不依赖失效来源的记录重建。后续消息、Assembly Decision 或 Tool Result 如果复述了该来源，也属于依赖链；无法确认独立时，应保守排除关联后缀。如果仍无法安全重建，就把这段 Context 标记为 needs_rebuild 并排除旧 summary；不能因为摘要还在，就继续暴露已经失效的来源内容。

这与数据库的增量物化视图类似：平时消费新增变化，发现依赖失效时重新构建受影响范围。它只是一个帮助理解的类比，并不要求实现成数据库视图。

用户更正后，summary 应该怎样更新

假设 active summary 仍写着“欧洲和北美”，用户随后明确要求“只保留欧洲”：

summary_3：报告覆盖欧洲与北美，covers event_seq 1..checkpoint_seq
correction_seq：用户说“只保留欧洲”（message_id=msg_scope_correction）

系统先把更正追加到 Raw history，不改写 summary_3。Context Assembly 再判断两件事：当前 Task 采用“只保留欧洲”，而且这项更正需要影响后续对话。由于旧 summary 与它冲突，Assembly 暂不渲染模型请求，而是让压缩层沿 dependencies 读取仍获授权的来源，重建 covers 对应的稳定区间：

summary_4：covers event_seq 1..checkpoint_seq
replaces：summary_3
dependencies：
  decision_refs：[correction_seq / msg_scope_correction]
当前目标：仅完成欧洲市场报告

summary_4 只重建旧的稳定区间；correction_seq 仍在 recent window 中以原文进入 Context。校验通过后，系统用 CAS 切换 active summary；CAS 同时检查 active version、event watermark 和 authorization/retention revision，任一项变化都放弃本次结果并重建。失败时保留 Raw history 和旧 summary 版本，当前 Run 以 failure_reason=context_needs_rebuild 结束，不把冲突内容交给模型。

如果用户说的是“这次展示先隐藏北美”，Assembly 只为当前 Run 生成 Context view，不重建 summary。是否重建，取决于更正的适用范围，而不是句子里是否出现“隐藏”或“删除”。

Recent window 不能只按固定轮数切

固定保留“最近 20 条消息”实现简单，却可能从一个执行单元中间切开：留下 Tool Result，删掉对应 Tool Call；留下模型的“已完成”，删掉用户随后指出的错误。

Recent window 的左边界至少应尊重完整的交互单元，例如：

  • 不切开一组 Tool Call 与 Tool Result。
  • 不切开尚未完成的确认或用户纠错。
  • 不越过当前 planning 或 execution 阶段仍引用的证据。
  • 为最新的明确 instruction 保留原文，而不是只依赖 summary。

因此它通常从目标 token 大小向前寻找安全边界，而不是严格保留 N 条消息。

怎样评测压缩是否可信

压缩率只说明变短了多少，不能说明重要内容是否仍在。一个长 conversation 的测试样本可以标注：

  • 哪些用户约束必须保留。
  • 哪些事实需要带 source reference。
  • 哪些完成状态不能被改写。
  • 哪些旧信息已被新消息更正。
  • 哪些 Tool Call 与 Tool Result 必须成对出现。

然后分别检查 summary 的事实保留、instruction 保留、provenance 完整性、冲突更新和重建成本。还应测试连续多次增量压缩，而不只检查第一次 summary；语义漂移往往在多轮之后才出现。

回到问题

长对话不能只靠反复全文总结，也不能维护一段不断覆盖的 summary。

更稳定的模型是在保留与授权允许范围内使用 raw history，把已稳定区间压成带覆盖范围和来源回链的 checkpoint summary，并让最近窗口继续使用原文。正常情况下增量推进；发生更正或压缩漂移时，从仍可读的受影响来源 rebase；来源删除或权限撤销时，则先让关联 summary 失效，再从剩余来源重建。

这样，summary 是可以检查和重建的 Context view，而不是一份逐渐取代原始事实的长期记忆。
