Agent 39：让 Eval 与生产执行形成闭环

让 Eval 与生产共享执行入口，再用 Shadow、Canary 和 Bad Case 回流形成可逆发布闭环。

2026/07/24 更新于 2026/07/27 阅读 次

问题

下面用一个构造例子。一个 Agent 版本在离线 Eval 中通过全部 regression case，进入生产后却持续调用不到 update_customer。两边虽然使用相同模型和 prompt，却不是同一个执行系统：

对象Eval生产
Tool surface手写 mock，只暴露 update_customer按用户权限动态生成
Argument validationmock 接受任意字符串Runtime 要求 expected revision
Timeoutfixture 立即返回provider 有 deadline
Context测试脚本直接拼接production assembly policy
Resultmock 返回 oknormalized effect evidence

离线通过只证明测试脚本里的 Agent 能工作。它没有证明生产 Runtime、Tool surface 和外部依赖下的行为。

评测闭环要解决两个问题：发布前，怎样证明 Eval 与生产执行的语义足够一致；发布后，怎样以与副作用风险匹配的方式验证，并把新 failure 变成下一轮可复现证据。

Eval 不应重新实现一套 Agent

最容易产生 drift 的做法，是让 Eval harness 自己：

  • 拼 Context；
  • 绑定 Tool；
  • 填默认参数；
  • 解释 Tool error；
  • 实现 retry；
  • 决定终止。

这些都属于被测 Runtime 的行为。Harness 一旦复制它们，就会随着生产代码演进而变成第二套实现。

更稳妥的结构是共享同一条执行主线：

Agent configuration
  → production Spec compiler
  → per-turn configuration snapshot
  → production executeRun / executeTurn
  → production Tool contract
  → normalized events

Eval 只注入：
  case input、fixture、isolated effect boundary、clock、grader

这里的 “production” 指真正拥有语义的实现，不要求 Eval 连接所有生产资源。外部依赖可以替换，但 Context decision、Tool validation、result normalization、retry 和 event schema 不应由测试脚本另写一遍。

共享执行路径，不等于共享所有外部环境

Eval 仍然需要控制变量。可以替换的对象包括：

可替换边界为什么替换必须记录什么
Model provider固定 response 或隔离成本stub/recording 版本、行为限制
Tool provider避免真实副作用fixture、effect contract、failure injection
Clock重放 timeout、expiryclock policy 与起始时间
External data固定 case 输入snapshot 或 content fingerprint
Grader评估结果grader、rubric 与 Judge configuration

关键区别是：替换 implementation，不改 contract。Mock Tool 若只返回 ok，而生产 Tool 返回 outcome、retryability 和 effect_reference，它不是可信替身；它已经删除了 Agent 做恢复决策所需的语义。

相反，一个 fixture provider 可以在同一 Tool contract 下模拟 succeeded、failed、unknown 和 revision conflict。这样 Eval 控制外部事实，Runtime 仍走真实分支。

用 Snapshot 与 Manifest 检查 Parity

“共享代码”仍不足以证明两次执行相同。生产会按用户权限、feature flag、资源和时间解析出具体 configuration；Eval 也必须保存实际 snapshot。

一次可比较记录至少包括：

spec_compiler_version: ...
runtime_version: ...
turn_snapshot:
  model_configuration: ...
  prompt_sha256: ...
  context_policy_sha256: ...
  tool_surface_sha256: ...
  authorization_fixture: ...
  timeout_policy: ...
  resource_budget: ...
external_environment:
  fixture_sha256: ...
  provider_mode: isolated
grader_sha256: ...

比较 production trace 与 Eval reproduction 时，先生成 parity diff：

相同：runtime、prompt、context policy、Tool contract
有意不同：production provider → isolated fixture
无法确认：某个历史 feature flag revision

有意不同的边界必须写入 manifest，并说明它限制了什么结论。无法确认关键配置时，可以保留 case 作为诊断材料，但不能宣称已经严格重现生产 failure。

Offline Gate 先守住确定 Contract

上线前仍应先运行：

  • schema、authorization 和 effect contract test；
  • smoke 与 regression suite；
  • per-case repeated trials；
  • Tool、Context 和 grader 的领域指标；
  • execution parity 检查。

这些证据用于排除已知 deterministic failure 和固定 regression。它们不能覆盖真实输入分布、共享资源竞争和不断变化的外部依赖，因此离线通过不是闭环的终点。

下一步也不必机械地依次经过 shadow、canary 和 A/B。验证方式应由这次变更要回答的问题和副作用风险决定。

Shadow 只适合副作用已经隔离的路径

Shadow 把真实或镜像输入交给候选版本，但不让候选结果直接影响用户。它适合观察：

  • Tool selection 与 arguments；
  • Context assembly；
  • latency、usage 和 failure taxonomy；
  • 候选回答与当前版本的差异。

但“用户看不到”不等于“没有副作用”。如果候选 Agent 仍能发消息、修改数据库或创建 Artifact，它已经对真实世界产生影响。

有 mutation 的 shadow 必须满足至少一种条件：

  • 所有写 Tool 被替换为 contract-compatible recorder；
  • 候选运行在隔离 tenant 或 sandbox；
  • effect owner 强制 dry-run，且 dry-run 语义明确；
  • authorization surface 根本不授予写能力。

仅在 prompt 里要求“不要真的执行”不是隔离。副作用控制必须由模型之外的可信边界执行。

Shadow 也可能受生产数据权限约束。输入复制、日志保留和人工审阅仍需遵循最小化与访问控制。

Canary 验证真实路径，但要先写退出条件

Canary 让一部分真实 work unit 进入候选版本，用实际 Runtime、依赖和副作用路径观察结果。Google SRE Workbook 对 canary 的定义 是对变更进行部分、限时部署和评估，再决定是否继续 rollout。

对 Agent，canary 的 work unit 可能是 request、Task、tenant 或某类低风险能力。选择单位时要避免同一个 Task 的不同 Turn 在两套不兼容 configuration 之间漂移。

开始前应写清：

  • eligible population；
  • 候选与 control 的 configuration identity；
  • safety、success、latency、cost 和 invalid 指标；
  • observation window 与最小有效 support；
  • 自动停止、rollback 和人工升级条件；
  • 已经发生的外部 mutation 怎样处理。

本文不提供通用流量比例或阈值。长任务、低频高风险动作和高方差 Agent 需要不同的 observation design；没有足够 support 时，正确结论是“证据不足”，不是自动放量。

Canary 与 A/B 也不是同义词。Canary 主要服务发布风险与回退；A/B 通常用于比较用户或产品结果，并需要额外处理分流、干扰和因果解释。一次变更若只需证明没有引入严重回归，不必把 rollout 包装成产品实验。

每个阶段都要能回答“现在为何可以继续”

一个概念发布记录可以是：

Offline
  gate: regression + parity pass
  evidence: manifest M18

Shadow（只读与 recorder Tool）
  gate: no forbidden proposal; trace schema complete
  exit: enough eligible cases or evidence remains insufficient

Canary（低风险 eligible population）
  gate: safety hard failures = 0 in observed valid cases
  monitor: success、latency、cost、invalid support
  rollback: any declared hard invariant violation

Staged rollout
  gate: repeat the same checks at each population boundary

这是流程结构示例，不是一次真实 rollout，也不包含虚构效果数字。某些低风险纯读变更可以从 offline 直接进入 canary；某些高风险写入即使 shadow 正常，也可能仍需要人工确认或根本不适合在线实验。

Bad Case 回流必须经过证据化

生产 failure 进入闭环时，不是把整条日志复制进 regression 目录。应经过：

production signal
  → 定位 Task / Run / configuration
  → 确认 failure owner 与 evidence horizon
  → 脱敏和最小切片
  → 冻结 fixture 或模拟依赖
  → 设计 grader
  → 重放确认
  → 加入 versioned dataset

无法在隔离环境重放的 trace 可以保留为 investigation evidence，却不应冒充 regression case。多个相同 failure 应去重为 canonical case；只有新的边界条件才扩充 fixture。

Case 还要记录来源类别、owner、tier、manifest、grader 和退役条件。修复后，应在候选 configuration 上运行多个 trial，并继续保留 baseline 结果，防止只修一个输出字符串而没有修真正机制。

Rollback 不是删除失败证据

Canary 触发停止后，系统需要回到已知 configuration，同时保留：

  • 候选接收过哪些 work unit；
  • 哪些外部 effects 已经提交；
  • rollback 是否只改变路由，还是还需 reconciliation；
  • 哪些 Task 需要恢复、补偿或人工处理；
  • 对应 trace 与 configuration manifest。

对 Agent 来说，二进制回滚不能撤销已经发送的邮件或已提交的数据库修改。发布计划必须在上线前定义 effect-level recovery，而不是把“流量切回旧版本”当成完整恢复。

回到问题

开场中的离线 Eval 全部通过，却没有覆盖生产 Tool surface、validation、Context 和 timeout，因此它验证的是另一套 Agent。

让 Eval 复用生产的 Spec compiler、per-turn snapshot、执行入口和 Tool contract，再用 manifest 明确哪些 provider 与 fixture 被有意替换，才能判断 parity gap。上线验证则按风险选择 shadow、canary 或阶段放量；任何 shadow mutation 都必须先在可信边界隔离或禁用。

最后，生产 failure 只有经过身份关联、脱敏、fixture 固定、grader 设计和重放确认，才成为 regression case。闭环不是“离线一次通过，再看线上指标”，而是让同一执行语义在离线证据、可逆发布和生产回流之间持续流动。
