LLM Infra 11：多模型与 Adapter 路由怎样避免冷启动放大

当模型与 Adapter 数量超过常驻容量时，区分 artifact identity 与 residency observation，用加载 reservation、热度和路由稳定性管理冷启动。

2026/07/29 阅读 次
LLM InfraInferenceModel RoutingLoRA

问题

同一个 Adapter 的突发请求同时到达多个 gateway。它们都发现目标 Adapter 尚未 ready，于是各自选择 Replica 并触发加载。重复下载和显存 reservation 挤掉了更热的 Adapter，随后更多 miss 出现，冷启动从一个对象扩散到整个 pool。

问题不是“Router 不知道模型在哪”，而是系统没有把 artifact identity、物理 residency 和正在进行的 load operation 分开。

逻辑名字不能代表不可变 Artifact

一个可路由的 Adapter 至少要绑定：

artifact_identity:
  base_model_commit: 8f3...
  adapter_repository: example/sql-adapter
  adapter_commit: 91a...
  adapter_config_digest: sha256:...

sql-lora 这样的名字适合请求，但不能作为部署 identity。同名 path 可以被替换，base model 不兼容也可能让 Adapter 无法正确加载。

vLLM 的 LoRA 文档允许为 Adapter 提供 name、path 和 base model lineage，也支持动态加载/卸载。其安全文档明确警告：Runtime LoRA updating 不应暴露给不可信客户端。

因此，请求只能引用经过 control plane resolved 的 artifact；下载路径、revision 和权限不能由终端用户任意注入。

Artifact 存在不等于 Endpoint 已 Ready

物理 residency 还需要观测：

residency_observation:
  endpoint_uid: replica_a
  artifact_id: adapter_91a
  state: ready
  active_slot: true
  cpu_cached: false
  observed_at: 2026-07-29T12:00:00Z
  generation: 18

本文用下面的概念状态描述 lifecycle：

absent
→ reserved
→ loading
→ ready
→ draining
→ evicted

这是跨 Endpoint control plane 的设计建议，不是 vLLM 标准状态机。vLLM 的 model manager 可以维护 registered/active adapters，并在容量限制下使用 LRU；Cluster 层仍要负责多个 Endpoint 同时加载、迟到完成和路由 observation 的一致性。

Single-flight 需要一个 Load owner

当多个 gateway 同时 miss 时，最小修复不是“随机挑一个 Replica”，而是让 load operation 有唯一 owner：

load_operation:
  load_id: load_442
  artifact_id: adapter_91a
  reconciliation_key: adapter_91a/pool_chat/generation_19
  owner: residency-controller
  pool: pool_chat
  desired_residency_count: 1
  selected_endpoints: [replica_a]
  reservation_expires_at: 2026-07-29T12:00:30Z
  publish_generation: 19

操作流程可以是：

  1. Controller 先按 artifact identity + pool/deployment generation 创建全局 reconciliation operation。
  2. 第一个创建者获得 ownership，其余 gateway 只能 join 同一 operation，不能各自先选择 Endpoint。
  3. Owner 明确 desired_residency_count，再选择目标 Endpoint；多副本预热必须是显式目标，不能由并发 miss 偶然形成。
  4. 每个目标 Endpoint 的 load lease 是该 operation 的子操作。Loader 验证 digest、base model compatibility 与容量后加载。
  5. 只有 operation generation 仍有效时，结果才发布为 ready；超时或取消后迟到的 loader 不能覆盖更新的 residency state。

Single-flight、reservation 和 publish generation 是本文建议，不应被描述成当前 vLLM 自带的集群协议。它们解决的是多个控制器对同一物理动作重复执行的问题。

LoRA affinity 与 Prefix affinity 不是一件事

一个 Replica 已加载 Adapter，意味着可以避免 Adapter cold load；它持有相关 Prefix KV，意味着可能减少 Prefill。两种 affinity 的 owner、命中条件和收益不同。

路由评分可以同时消费：

  • base model 与 adapter compatibility；
  • active adapter slot；
  • Prefix KV observation；
  • free KV / Token budget；
  • Adapter 加载时间与 deadline；
  • tenant isolation。

但顺序仍是先兼容、再容量、最后 affinity。不能因为 Prefix 命中就把请求发到缺少 Adapter 的 Endpoint，也不能因为 Adapter ready 就越过 tenant Cache isolation。

Eviction 要看重载代价，不只看最近访问

Adapter 数量超过 active slots 时，LRU 是合理起点，但不是全部策略。Control plane 还需要考虑：

输入影响
近期与预测热度被再次请求的可能性
Artifact 大小和 load timemiss 后恢复成本
与 base model 的共享关系可放置 Endpoint 范围
当前 in-flight requests是否可以安全 draining
tenant reservation是否有最低常驻保障
deadline classcold load 是否来得及

假设 A 很热、B 较冷、C 首次突发。无状态 gateway 让多个 Endpoint 同时加载 C，可能驱逐 A；residency-aware control plane 为 C 建立 desired_residency_count: 1 的全局 operation，由唯一 owner 选择一个 Endpoint，其他请求等待同一 operation 或显式拒绝。

这里不能提前声称命中率提高多少。收益必须用相同 workload、Adapter heat distribution 和 cold state 实测。

路由只能消费可信的 Residency

动态加载接口属于管理面，不应直接成为数据面 fallback。vLLM 官方安全指南要求限制 LoRA load/unload Endpoint 到可信管理员，并提醒动态加载不是面向不可信客户端的安全操作。

因此完整边界是：

request model name
→ resolve immutable artifact identity
→ query trusted residency observation
→ choose compatible Endpoint
→ local admission

Artifact registry、residency controller、Router 与 Runtime 各自拥有不同状态。把它们都塞进 gateway 内存，会让重启、并发 load 和 stale observation 很难解释。

回到问题

开篇的多个 gateway 会重复加载，是因为“Adapter 不在本地”被直接翻译成了多个物理动作。正确的模型是：先 resolve 不可变 artifact identity，再由一个 control plane 按 artifact 与 pool generation 管理全局 reconciliation operation、目标副本数和 Endpoint 子 lease，最后让 Router 只消费已经发布的 ready state。

这样，cold miss 不再自动扩散成重复 reservation、热 Adapter 驱逐和连锁 miss；代价是系统需要显式维护加载 owner、generation 与 eviction policy。
