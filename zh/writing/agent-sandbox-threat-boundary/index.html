Agent 28：Sandbox 要约束哪些 Runtime 威胁

从 command、filesystem、network egress、secret 与 resource 五个维度定义 Sandbox runtime threat boundary。

2026/07/24 更新于 2026/07/27 阅读 次
Agent ProductionAgentSandboxSecurity

问题

用户授权 Agent 在一个可信仓库里运行构建。仓库中的脚本没有 prompt injection，Agent 也确实选择了正确命令。但脚本会读取环境变量中的 cloud credential，向外部地址发送诊断数据，并因为错误递归不断 fork 子进程。

这里没有未授权的业务动作：用户确实要求构建。风险来自 Runtime 能力过大——进程看到了不需要的 secret、拥有任意 egress，也没有 process 和 CPU 上限。

因此，“运行在容器里”不是完整的 Sandbox 安全结论。Sandbox 必须把 workload identity 与最小权限 policy 绑定，并分别约束 command、filesystem、network/DNS、secret、resource 和 image/toolchain supply chain；readiness 只有在这些约束已被观测或证明生效后才有执行意义。

先定义要保护什么

开场的执行至少跨过三个保护域：

保护域主要资产需要阻止的路径
Host / control planekernel、metadata service、provider credentialprivilege escalation、host mount、控制面访问
当前 tenantWorkspace、Artifact、短期 credential越界读写、secret 泄漏
其他 tenant / 外部系统其他 workload、内部服务、互联网目标横向访问、资源耗尽、任意 egress

攻击者不一定是恶意用户。模型生成的代码、可信仓库里的依赖、构建脚本或编译器都可能出错或被污染。Sandbox policy 应按“执行内容不值得拥有宿主权限”来设计。

六类能力需要不同 enforcement

Command 与进程权限

只做字符串 command denylist 很容易被 shell、解释器或子进程绕过。更可信的控制在 Runtime 层：

  • 非 root 身份；
  • 删除不需要的 Linux capabilities；
  • 禁止 privilege escalation；
  • seccomp、AppArmor 或 SELinux profile；
  • 禁止 host PID/network namespace 和高风险 device。

Kubernetes securityContext 提供这些机制的配置入口，但是否真正生效取决于 Runtime、节点和集群 policy。使用容器不自动等于启用了这些限制。

Filesystem

Workspace 应按用途挂载：

/inputs       read-only
/workspace    writable, current tenant only
/outputs      writable, publish through Artifact service
/runtime      ephemeral
host paths    not mounted

只读 root filesystem 可以减少持久修改面，但并不阻止读取已暴露的 secret，也不保护错误挂载进来的 host path。文件访问仍需要最小 mount、UID/GID/label 隔离，以及 Workspace lease/fencing。

Network 与 DNS

Sandbox 默认允许任意 egress 时，文件隔离只防写宿主，无法防数据外传。Network policy 应明确允许的 destination、port、protocol，并特别处理 DNS 与 cloud metadata endpoint。

这里要区分两层：

  • Runtime egress policy 强制“进程实际上能连到哪里”；
  • Tool/backend allowlist 强制“某个业务 effect 允许发送给谁”。

只配置一个 HTTP Tool 的 allowlist 不能阻止 curl；只配置网络 allowlist 也不能判断目标 account 或 resource 是否属于当前用户。

Kubernetes NetworkPolicy 是网络包过滤接口，实际支持与行为依赖网络实现。DNS policy 也要显式设计，不能因为允许集群 DNS 就假设域名解析后的所有目标都安全。

Secret

最安全的 secret 是根本不进入 Sandbox。确实需要时，应尽量使用：

  • audience 和 scope 受限的短期 credential；
  • 由 workload identity 按需交换；
  • 只在执行该操作的进程或代理边界可见；
  • 不进入 prompt、命令行、Workspace、镜像和日志。

Secret 挂成环境变量虽然方便，却容易被子进程、错误报告或 /proc 暴露。更强的做法是让独立 broker/sidecar 代为执行受约束请求，但这会增加系统复杂度。

Image 与 Toolchain Supply Chain

可信仓库不等于执行链里的每个二进制和依赖都可信。Runtime image、基础包、package registry、安装脚本、编译器和自动下载的 Tool 都可能在进入 Sandbox 前后被替换。

Control Plane 应把 supply-chain 决策编译进 Runtime profile：

  • image 使用不可变 digest，而不是只依赖可变 tag；
  • 在平台支持时验证构建 provenance、签名或 attestation，并记录验证 policy revision；
  • package manager 只访问允许的 registry，lockfile 同时固定版本与可验证的 integrity；
  • 动态安装仍受 egress、credential、filesystem 和 resource policy 约束，不能因为命令来自构建脚本就获得额外权限；
  • 发现 digest、来源或验证结果漂移时，停止新的 admission，并隔离受影响 Runtime，而不是只在日志中告警。

这不能证明依赖没有漏洞，也不要求所有环境采用同一种签名系统。它建立的是更窄的执行前置条件：Control Plane 知道实际运行的是哪个 image/toolchain，以及它是否满足当前允许来源与验证政策。

Resource

CPU、memory、disk、process 数、open file、network bandwidth、wall-clock 和并发都可能成为拒绝服务路径。Limit 既要在 admission 前预留，也要在 Runtime 中强制。

超时通常只能触发取消或终止计算，不能证明外部副作用没有发生。强制回收 Sandbox 后，Control Plane 仍需把未知 effect 交给对应 backend 查询或 reconciliation。

Policy 必须进入 Acquire 证据

Control Plane 可以把目标 policy 编译为 provider-specific 配置，但 client 不应只看到 healthy: true。一个可执行 handle 至少关联：

{
  "workload_identity": "sandbox_91",
  "policy_revision": 12,
  "observed_enforcement": {
    "filesystem": "verified",
    "network": "verified",
    "secret": "none",
    "runtime_supply_chain": "verified",
    "resources": "verified"
  }
}

这仍是设计示例。不同平台能提供的 observed evidence 不同；有的平台只能证明配置已接受，不能证明每条规则的运行时效果。系统应如实区分 requested、configured 和 verified，不要用一个 ready 掩盖证据强度。

Policy 更新后，旧 Runtime 是否继续使用取决于变更风险。收紧 egress 或撤销 secret 通常不能等到下次自然重建；Control Plane 需要停止 admission、轮换 credential，并重建或隔离不再合规的 Runtime。

回到问题

开场的构建不应获得 cloud credential；若确实需要拉取依赖，应使用只对目标 registry 有效的短期凭证。Workspace 之外的 host path 不挂载，root filesystem 只读；egress 只允许必要的 registry；process、CPU、memory、disk 和 wall-clock 都有限额。

fork bomb 因 process/resource limit 被终止，向未知地址的连接被网络层拒绝，secret 也没有可供读取的值。之后 Control Plane 回收 workload，并单独核对任何结果不确定的外部 effect。

这些控制仍不能替代 backend authorization，也不能证明 image 或依赖没有漏洞。它们只建立 Runtime 威胁边界：实际 image/toolchain 满足当前来源政策，而且即使执行内容可信度判断出错，进程仍无法自然继承宿主和共享环境的全部能力。
