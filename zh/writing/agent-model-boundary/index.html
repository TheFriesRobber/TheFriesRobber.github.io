Agent 06：模型 Fallback 为什么需要 Router 与 Adapter

把模型选择与 provider protocol shaping 分开，避免 fallback 改变 Tool、消息和流式事件语义。

2026/07/24 更新于 2026/07/27 阅读 次
Agent CoreAgentModelsAdapter

问题

一个 Agent 使用支持并行 Tool Call 和特定 JSON Schema 方言的模型。主模型限流后，宿主把 model 字段换成备用名称，原请求原样重发。备用模型虽然返回了结果，却把两个本应并行提议的 Tool Call 合并成一段文本，其中一个参数还丢失了枚举约束。

这次 fallback 在 HTTP 层成功了，在 Agent 语义上却已经改变行为。安全 fallback 不能只是替换 model name。

Router 先决定谁有资格

模型选择通常同时考虑质量、延迟和成本，但这些只应该在 eligible set 内比较。一个模型是否 eligible，至少取决于：

  • 是否支持当前需要的 Tool 或 structured output 能力；
  • Context 和输出上限是否容纳当前请求；
  • 数据区域、内容政策和身份边界是否允许；
  • streaming、thinking 或 multimodal 语义是否满足调用方约定；
  • 当前 failure class 是否允许把未完成状态移交给它。

先按这些硬约束过滤，再优化成本和延迟，可以避免“便宜但无法表达当前 contract”的模型被选中。

Router 应留下可解释的 decision record，例如：

required: tools + parallel proposals + schema feature X
rejected model-b: schema feature X unsupported
selected model-c: eligible, lower current latency

这不是要求把所有模型差异做成一张永久表，而是要求路由决定能回到当时的能力和政策证据。

Adapter 负责协议转换

通过路由后，canonical AgentMessage、Tool definition 和 streaming event 还要转换成 provider protocol。不同 provider 对 role、Tool ID、schema、usage、reasoning block 和 chunk 形状的表示可能不同。

Adapter 的目标不是取“所有 provider 的最小交集”，而是在转换时显式报告能力：

canonical request
  → capability check
  → provider request shaping
  → provider response
  → canonical events/messages

若某个 schema 关键字无法表达，Adapter 应拒绝或返回明确降级决定，而不是悄悄删除。Prompt shaping 也不能把权限边界从结构化 policy 降成一句自然语言提醒。

Pi 提供注入边界，不提供 Router

Pi 当前有两条相关路径：

  • low-level Agent/loop 接收 selected Model 和注入的 streamFn；
  • AgentHarness 接收 selected Model 与 host-supplied Models provider collection。

这让 Core 不必硬编码某个 provider，但并不等于 packages/agent 已经实现 model catalog、route eligibility 或 fallback policy。Router 仍由 host 拥有。

相关边界可查看 Pi 的 stream-fn.ts 和 Harness types.ts。

Fallback 取决于失败位置

并非所有模型失败都能安全切换：

失败位置通常能否 fallback需要检查什么
Provider 明确返回 rate limit，且尚无可消费 output较容易能力、政策、Context、Tool schema，以及重复请求/计费 contract
尚未产生可消费输出的连接失败可能provider 是否已接受请求、计费与重复风险
已输出部分文本需谨慎是否丢弃部分输出并重新开始
已提出并执行 Tool Call不能只换模型effect 状态、Tool Result 和 operation identity
外部副作用结果未知Router 无权解决先 query/reconcile 外部事实

模型 fallback 只能处理模型 owner 范围内的失败。Tool 已执行后，新的模型可以继续解释已确认的结果，却不能把未知副作用重置成“尚未执行”。

Fallback 后必须重新 shape

回到开场请求。Provider 明确返回 rate limit，且没有产生可消费 output；在检查重复请求与计费 contract 后，宿主允许尝试备用模型，但仍要重新执行完整路径：

  1. Router 检查备用模型是否支持并行 Tool proposal 和所需 schema；
  2. Context 按备用模型窗口重新预算；
  3. Adapter 将 canonical Tool definitions 转成备用协议；
  4. 转换结果通过 contract test，确认 Tool identity、参数约束和事件语义没有丢失；
  5. 不兼容就停止 fallback，而不是把 Tool Call 降成自由文本。

Contract test 不需要证明所有 provider 行为完全等价。它只需要验证本文依赖的语义往返：必要约束仍在、Tool ID 可关联、错误不会伪装成成功、流式事件能恢复成一致的 canonical 结果。

回到问题

把 model name 换成另一个值，只完成了“选择另一个目标”这一步。安全 fallback 还需要：

  • Router 先筛出满足能力和政策的模型；
  • Adapter 对新 provider 重新转换请求和响应；
  • failure class 证明当前状态允许切换；
  • Tool、Context 和未完成 effect 重新通过兼容性检查；
  • 不可表达的语义明确失败，而不是静默降级。

Pi 提供了干净的模型注入点，这使 host-level Router 成为可能；它没有替宿主完成上述政策。把注入边界和路由能力分开，才能让 fallback 真正保持 Agent contract，而不是只保持一次 API 调用成功。
