LLM Infra 08：量化省下的显存为什么不等于可交付容量

区分 Weight、Activation 与 KV Cache quantization，用显存账本、Kernel 支持、质量约束和 workload-specific service curve 判断量化是否增加可交付容量。

2026/07/29 阅读 次
LLM InfraInferenceQuantizationCapacity Planning

问题

一个模型从 BF16 权重换成 4-bit weight-only quantization 后，checkpoint 和权重驻留明显变小，模型也能装进更少的 GPU。但长 Context 并发仍然受 KV Cache 限制，某些硬件/shape 下还走了不同 Kernel，满足 TTFT/TPOT 的 goodput 没有按压缩比例提高。

“模型变小”是 artifact 与权重内存的事实；“可交付容量提高”则要同时通过显存、执行与质量三个 gate。

Quantization 先要说明量化了什么

量化不是一个统一开关。

类型改变的主要对象没有自动改变的对象
Weight-only模型权重存储与部分矩阵计算路径KV Cache、许多 Activation、workspace
Weight + Activation权重与选定 Activation 的表示/计算未覆盖算子、KV Cache
KV Cache quantization每个 active Token 的 KV 表示模型权重、其他 Activation

AWQ 是 low-bit weight-only quantization；SmoothQuant 的目标是把 weight 与 activation 转成更易执行的 W8A8 路径。它们解决的不是同一块显存，也不应仅用 bit-width 比较。

当前 vLLM 也把模型 quantization 与 KV Cache dtype 分成不同配置，并维护依赖硬件与 quantization method 的支持矩阵。这说明“模型是 4-bit”仍不足以确定完整执行路径。

权重缩小后，瓶颈会移动

用抽象内存单位做一个合成账本：

项目BF16 配置4-bit weight-only
权重205
KV Cache88
Activation / workspace / Runtime44
合计3217

数字只表示关系，不对应具体模型或设备。权重缩小 4 倍，总占用在这个例子里只从 32 降到 17；随着 Context 和并发上升，KV 还会继续增长。

因此，weight-only quantization 可能带来三种不同结果：

  • 原本放不下的模型现在能加载；
  • 释放的空间可以分给更多 KV blocks；
  • 容量仍被 KV、Kernel、compute 或 SLO 限制。

第一项成立不代表第三项也成立。容量变化必须回到第 05 篇的完整显存账本。

格式可加载不等于走了高效 Kernel

低精度收益依赖硬件、Runtime 和 Kernel 共同支持：

  • 设备是否原生支持目标 dtype 或需要转换；
  • quantization method 是否有匹配的 Linear/MoE/attention Kernel；
  • group size、shape、batch 与并行方式是否满足 Kernel 条件；
  • 不支持的算子会以什么精度执行；
  • 是否存在 dequantize、repack 或 CPU/GPU offload。

Hugging Face 的 quantization 文档维护多个 backend 与硬件支持；vLLM 也明确区分 quantization methods 和 supported hardware。可加载 checkpoint 只证明格式能被解析，不证明目标请求实际使用了预期 Kernel。

部署验证至少要记录：

quantization_execution:
  weight_format: awq-int4
  activation_dtype: fp16
  kv_cache_dtype: fp16
  resolved_kernels:
    linear: observed-kernel-name
    attention: observed-kernel-name
  fallbacks:
    count: 0
    source: runtime-log-or-profiler

字段是概念建议。Kernel 名称和 fallback 必须从目标 Runtime 的日志、profiler 或代码路径观测，不能从 checkpoint 文件名推断。

质量必须先成为硬约束

Quantization 改变数值表示，可能影响 perplexity、生成质量、结构化输出、Tool 参数或特定语言/长 Context 任务。某篇论文在其模型和 benchmark 上保持准确度，不等于任意 workload 都没有变化。

因此比较顺序应该是：

  1. 固定 model revision、template、sampling 与 workload；
  2. 为业务契约选择质量 evaluation suite；
  3. 检查量化配置是否通过 quality gate；
  4. 只有通过的候选才比较 TTFT、TPOT、goodput 与成本。

如果一个候选更快，却降低了结构化输出成功率，它不是同一服务契约下的容量提升。

质量记录还要区分：

  • 量化算法论文报告的原始任务；
  • 当前模型的离线 evaluation；
  • 目标 application contract；
  • 允许的回归边界。

用同一条 Service Curve 重新做容量判断

量化后的配置是新的 deployment manifest，旧 service curve 必须失效。

重新 Benchmark 时应固定：

  • workload envelope 与 SLO；
  • hardware、Replica 数和并行拓扑；
  • warm/cold Cache state；
  • tokenized inputs、sampling/generation config、requested max/min output 与随机种子策略；
  • 记录 actual output length、EOS/stop reason，而不是把它们强行固定；
  • quality gate；
  • quantization method、scales、Runtime 与 Kernel。

如果纯 Kernel/throughput 实验为了可比性使用 ignore_eos 或固定 Output Sequence Length，必须标记为 synthetic fixed-OSL experiment；它不能替代正常停止语义下的 application quality 与 service curve 测量。

随后比较的不只是 memory：

Gate需要的证据
Fit权重、KV、Activation 与 peak allocation
ExecuteKernel/fallback、TTFT、TPOT、failure
Quality同一 evaluation suite 的结果
Capacity满足全部约束的 service curve / goodput

假设配置 Q 让单 Replica 从 2 张 GPU 缩到 1 张，但 SLO-constrained goodput 下降。它可能仍因 fleet placement 或成本更优而值得采用，也可能因需要更多 Replica 抵消收益。结论取决于完整 fleet 方案，不能只看“每 Replica 少一张卡”。

一份可审计的量化决策

quantization_decision:
  candidate:
    artifact_digest: sha256:...
    quantization_config_digest: sha256:...
    scales_digest: sha256:...
    kv_cache_dtype: fp16
  baseline:
    artifact_digest: sha256:...
  workload_fingerprint: wl_7fd2
  evidence:
    memory_ledger: artifact://memory-comparison
    kernel_trace: artifact://kernel-resolution
    quality_report: artifact://quality-gate
    service_curve: artifact://benchmark-curve
  result:
    quality_gate: pass
    capacity_change: measured
    cost_change: modeled-from-measured-capacity
  invalidate_on:
    - model_revision_changed
    - quantized_artifact_or_scales_changed
    - quantization_config_changed
    - kv_cache_dtype_changed
    - runtime_or_kernel_changed
    - hardware_changed
    - workload_distribution_changed

这份记录没有预设“低 bit 一定更好”。它只要求每次决策都能追溯到完整证据。

回到问题

4-bit weight-only 配置确实缩小了权重，却没有同时压缩 KV Cache，也没有保证目标硬件使用更快 Kernel，更没有自动满足原质量契约。

所以“省下多少显存”只是量化决策的一项输入。只有候选通过质量 gate，在目标 workload 下测出新的 service curve，并在 fleet 层形成更高 goodput 或更低合格交付成本，才能称为可交付容量提升。
