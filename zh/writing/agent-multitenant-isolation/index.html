Agent 27：多租户私有对象必须绑定隔离域

把 tenant identity 传播到 Queue、Cache、Artifact、Trace、Credential 与后台执行，防止派生对象跨租户泄漏。

2026/07/24 更新于 2026/07/27 阅读 次
Agent ProductionAgentSecurityMulti-Tenancy

问题

Tenant A 和 Tenant B 都让 Agent 总结名为 quarterly-report 的文件。入口 API 已经正确认证 tenant，但缓存只用下面的 key：

summary:quarterly-report

Tenant A 先执行后，Tenant B 命中同一条缓存，拿到了 A 的摘要。请求入口没有越权，泄漏发生在派生对象：cache entry 创建时丢掉了 tenant binding。

Agent 系统会不断产生 Message、Job、Memory、Artifact、Credential 和 Trace。只在 API Gateway 检查一次 tenant，无法保护这些对象后续的写入、索引、恢复和读取。每个派生对象都必须声明 isolation domain；含租户私有数据、资源身份或授权决策的对象必须绑定 tenant，并在真正拥有资源的边界强制检查。

Tenant 不是 user 的别名

同一个用户可能属于多个 tenant，service actor 也可能代表某个 tenant 执行任务。需要分开：

  • subject：目标代表谁；
  • actor：谁正在行动；
  • execution identity：哪个工作负载发起调用；
  • tenant：数据和策略属于哪个隔离域。

Tenant 应来自已认证的入口或可信 delegation，而不是模型参数、文件内容或未验证的 Queue attribute。下游可以携带 tenant reference，却不能自行改写它。

Cache 必须是授权路径的一部分

把开场 key 改成：

summary:{tenant_id}:{artifact_id}:{artifact_revision}:{policy_revision}

可以防止明显碰撞，但仅靠 key 仍不够。Cache value 还应保留 owner/reference，命中后由 adapter 确认当前请求的 tenant 与 scope。否则一次错误写 key 会长期放大泄漏。

还要防止以下隐性共享：

  • embedding cache 只按文本 hash 去重，却返回带租户私有 metadata 的对象；
  • retrieval cache 复用另一套 authorization filter 的结果；
  • negative cache 在权限变化后继续声称资源不存在；
  • model response cache 忽略 Tool Surface、policy 或 Context provenance 的差异。

可以共享不含租户数据的计算结果，例如公开文本的 tokenizer output；这类 value 应显式属于 public/shared isolation domain，而不是伪装成没有 owner。一旦 value 含有私有内容、资源身份或授权决策，就必须绑定 tenant，并把相应边界纳入 key 与读取检查。

Queue 与恢复最容易丢掉 binding

后台 Job 可能在原请求结束很久后执行。它至少需要稳定的 job_id、tenant reference、delegation reference 和目标 resource：

{
  "job_id": "job_42",
  "tenant_ref": "tenant_3",
  "delegation_ref": "del_81",
  "resource_ref": "artifact_19",
  "operation_id": "summarize_19_r4"
}

worker 不能信任裸字段就直接查询数据库；它要使用自己的 execution identity 领取 Job，再通过可信服务解析 delegation。重试 Attempt 必须复用同一个 tenant binding，不能从当前 worker 的默认 tenant 或全局配置重新推导。

恢复 Session、Workflow 或 Checkpoint 也一样：如果 durable state 没有 tenant ownership，系统无法安全决定由谁恢复。此时应停止并隔离，而不是根据资源名称猜测。

Workspace 与 Sandbox 复用必须重新证明 tenant binding

Runtime pool 或 Volume pool 最容易把“已清理”误当成“可以交给任意 tenant”。池中资源在未绑定时只能属于显式 shared/unbound domain；acquire 时，Control Plane 原子绑定目标 Session tenant、Workspace owner、lease generation 和 policy revision。Runtime 内的 mount observation 还要读到同一个 Workspace identity，不能因为 /workspace 路径存在就接受它。

Refresh 与恢复同样比较这组 binding。Tenant A 的 lease 过期后，即使旧 Runtime 仍健康，它也不能被 Tenant B 直接接管并保留旧 mount、credential、process 或 writable overlay。回池前需要停止 admission、撤销 tenant-scoped credential、卸载或隔离 Workspace，并让 cleanup evidence 收敛；无法证明 owner 的资源进入 quarantine。

Artifact materialize 和 Workspace export 也要检查两侧 owner。一个属于 Tenant A 的 Artifact reference 不能仅凭 path 或 Blob hash 导入 Tenant B 的 Workspace；从 Workspace 发布新 Artifact 时，输出默认继承当前 isolation domain，除非可信 policy 明确执行受审计的跨域复制。

Storage partition 不是完整授权

按 tenant 分库、分 schema 或分 partition 能减少误查询和故障半径，但不会自动解决所有路径：

  • 管理服务可能仍有跨 tenant credential；
  • export job 可能绕过在线查询过滤；
  • Artifact URL 可能泄露给另一个租户；
  • Trace backend 可能把所有 tenant 的 span 汇入同一可搜索索引。

因此 partition 是 defense in depth。读取与写入仍要在资源 owner 处基于当前 tenant、action 和 resource 授权。数据库支持 row-level security 时可以把一部分 enforcement 下推，但连接身份、session variable 和 bypass 权限仍需可信管理；不能把“使用了 RLS”当作端到端隔离证明。

用四条旁路检查设计

完成在线 API 后，再走四条容易被忽略的路径：

  1. 后台重试：Job 被重新投递，worker 是否仍解析原 tenant，而非采用默认值？
  2. 数据导出：导出服务是否对 Artifact、Memory 和关联文件逐项授权，而非只检查 export request？
  3. Sandbox 回池：Tenant A 的 Runtime 或 Volume 被 Tenant B acquire 前，旧 mount、credential、process 和 overlay 是否都已失效？
  4. 可观测系统：Trace 与 Log 的查询、采样和导出是否保留 tenant boundary，敏感字段是否最小化？

只要其中一条把 tenant 当成可选 metadata，入口隔离就可能被绕过。

回到问题

开场的摘要缓存应绑定 Tenant A、Artifact identity、revision 和产生结果时的 policy；Tenant B 即使使用相同文件名和 query，也不会命中 A 的 value。命中后，Cache adapter 仍验证当前 tenant 是否能读取对应 Artifact。

同样的 binding 随后进入 Job、Session、Workspace、Sandbox lease、Memory、Artifact、Credential 和 Trace，并由各自的可信 owner 在写入与读取两侧强制检查。

多租户隔离不是入口上的一个 WHERE tenant_id = ?。它是一条对象不变量：任何持久化或派生状态都必须声明 isolation domain；其中的租户私有状态如果无法证明属于哪个 tenant，就不能被自动消费、恢复或导出。
