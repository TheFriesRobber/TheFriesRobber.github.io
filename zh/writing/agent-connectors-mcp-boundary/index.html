Agent 21：Connector、MCP 与宿主 Control Plane 如何分工

区分 Connector credential boundary、MCP protocol 与宿主 control plane，解释能力发现、版本、健康和授权由谁负责。

2026/07/24 更新于 2026/07/27 阅读 次
Agent StateAgentMCPSecurity

问题

一个 MCP server 把 search Tool 从 v1 升级到 v2：新 Schema 增加必填的 workspace_id。部分 Runtime 重新连接后发现了 v2，另一部分仍沿用缓存的 v1 definition；与此同时，用户撤销了外部账户授权，但旧 worker 仍持有尚未清理的 token。

静态 endpoint 列表只能说明“可能连到哪里”，一枚 token 也只能作为某次访问的 credential。它们无法回答当前协议版本是否兼容、哪个 Tool definition 可以暴露给哪个 tenant、token 是否仍有效，以及故障时应该路由到哪里。

这需要三个边界协作：MCP protocol 负责连接内的版本与能力交换；Connector 负责外部账户和 credential 生命周期；宿主自建 control plane 才负责 fleet 的 desired version、observed health、tenant visibility 和 route。

MCP Protocol 提供什么，又不提供什么

以 MCP 2025-11-25 规范为版本边界，client 和 server 在 initialization 中协商 protocol version 与 capabilities。Server 可以暴露 Tools，client 通过 tools/list 获得当前可见 definitions；相关 capability 还可以声明 Tool list change notification。

对于 HTTP transport，MCP authorization 规范定义了基于 OAuth 的受保护资源发现，并要求 token 绑定目标 resource；authorization 是可选能力，stdio transport 也有不同的 credential 获取边界。

这些是 protocol contract。它们不自动提供：

  • 多实例 server fleet 的 desired rollout version；
  • 跨连接的长期 health evaluation；
  • tenant 到 server instance 的 route policy；
  • Schema compatibility gate 与 quarantine；
  • 外部 SaaS refresh token 的完整生命周期；
  • Runtime 本轮最终暴露哪些 Tool。

把这些能力统称为“MCP 自带 control plane”会混淆协议与宿主架构。

Connector 是 Credential 与外部主体边界

Connector 维护用户/tenant 与外部账户的受控映射：

internal subject + tenant
→ connection record
→ external account reference
→ credential reference
→ allowed audience/scope

模型只能提出业务参数，不能读取 access token、选择可信 tenant 或把 credential 转发给另一个 server。Connector 或 credential broker 在调用时解析 credential reference，检查 expiry、revocation、audience 和 scope，并尽量使用短期凭证。

MCP server 收到的 token 只应面向该 MCP resource。当前 MCP authorization 规范明确禁止把 client 提供给 MCP server 的 token 原样透传给下游 API；server 若调用第三方服务，应使用面向该服务的独立 token。这能避免 token passthrough 形成 confused deputy。

Connector 也不是 Tool。Connector 管连接和 credential；Tool definition 则是模型可见 API。一个 Connector 可以提供多个 Tool，同一个 Tool 也可能由不同 route 实现。

Capability Discovery 只是 Observed Fact

tools/list 返回的是这次连接、当前 authorization 下 server 声明的 Tool 集合。它不能自动成为模型的 Tool surface：

observed tools
→ protocol/schema validation
→ compatibility check
→ tenant and capability authorization
→ host policy selection
→ per-turn Tool surface

Host 需要保存 definition fingerprint、server identity、negotiated protocol version 和发现时间。若 v2 Schema 与当前 Runtime adapter 不兼容，正确结果是 route 不可用或继续使用明确兼容的 v1，而不是把新 definition 随机暴露给一部分 Model Turn。

即使 server 通知 Tool list changed，host 也应把变化当作重新发现信号，而不是立即修改已经开始的 Turn。正在执行的 Turn 仍使用自己的 configuration snapshot，下一轮再消费通过校验的新 surface。

Control Plane 管 Desired/Observed 与 Route

下面是本文建议的宿主 control plane，不是 MCP 规范要求：

register desired server/version
→ establish connection and negotiate protocol
→ discover capabilities
→ validate schema/compatibility
→ observe health and authorization state
→ promote route or quarantine
→ publish resolved capability revision

一条 route record 可以包含：

server: search-service
desired_release: v2
observed_protocol: "2025-11-25"
toolset_fingerprint: sha256:...
compatibility: incompatible_with_runtime_v7
health: reachable
route_state: quarantined

reachable 不等于 compatible，也不等于 authorized。Health probe 只证明某类请求得到响应；真正路由还需要 Tool definition、tenant visibility、credential state 和 Runtime contract 全部成立。

发生 timeout 时，control plane 也不能直接断言调用未执行。Tool Execution 仍按自己的 effect contract 记录 unknown/query/retry；route health 只消费这次观察，不能覆盖业务 outcome。

Schema 升级与 Token 撤销是两条状态链

对开场问题分别处理：

Schema breaking change

v2 discovered
→ fingerprint differs
→ required workspace_id unsupported by Runtime v7
→ v2 quarantined for v7
→ compatible clients may canary; others retain v1 route

是否允许 v1 fallback 取决于语义兼容与安全策略。若 v1 已被撤销或缺少必要授权字段，应停止能力，而不是为了可用性回退。

Token revocation

connection revoked
→ credential record becomes inactive
→ new lookup denied
→ affected routes no longer authorized
→ in-flight result handled by Tool effect contract

删除本地 token cache 不是唯一动作；route 和 capability surface 也要消费 connection revision。已经发出的外部请求可能仍然完成，不能从 revocation 倒推出 effect 没有发生。

走完一次 External Tool Call

一次调用可以经过：

Model proposes Tool arguments
→ Runtime validates against snapshotted Tool definition
→ trusted identity resolves tenant + connection_ref
→ control plane resolves compatible authorized route
→ credential broker returns audience-bound credential
→ MCP client invokes server
→ server validates token and arguments
→ Runtime normalizes result/effect evidence
→ audit links subject、actor、route、tool revision、Attempt

任何一步失败都要保留自己的 owner。模型的参数不能覆盖 connection identity；MCP response 不能替 backend 决定外部业务授权；control plane 的 route health 也不能替 Tool contract 宣告业务成功。

回到问题

开场中的 v2 server 虽然 reachable，当前 Runtime 却不支持新增必填字段，因此 control plane 应 quarantine 这条 route，直到兼容 adapter 和 Tool contract 就绪。用户撤销连接后，Connector 使 credential reference 失效，后续 Turn 也不再暴露依赖该连接的能力。

MCP initialization、capability discovery 和 HTTP authorization 提供连接级 protocol 事实；Connector 提供外部账户与 credential 事实；宿主 control plane 才把 desired version、observed compatibility、tenant policy 和 health 收敛成可消费 route。
