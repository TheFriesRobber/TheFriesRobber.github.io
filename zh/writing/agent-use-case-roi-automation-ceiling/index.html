Agent 45：可自动化不等于值得自动化

把端到端收益、人工审核、失败处理、Tool Coverage、可验证性与风险成本放进同一判断，估计真实自动化上限。

问题

一个退款 Agent 在离线测试中，对 80% 的案例给出了符合政策的文本答案。这个 Eval 到回答为止，没有执行退款动作，也没有验证外部结果。团队却据此估算：如果客服每天处理一百个退款申请，Agent 可以替代八十次人工处理。

Pilot 开始后，客服却需要重新检查每一项政策判断；Agent 无法访问一部分物流数据；少数失败集中在高金额订单；Tool timeout 后还要人工确认是否已经创建退款。虽然模型很快生成了结论，端到端处理时间并没有明显下降。

“80% 的案例产生了正确回答”只描述模型在测试条件下的表现。它没有说明业务任务完成了多少，也没有计算审核、失败和风险处理成本。

判断 Agent Use Case 是否值得建设，必须把可自动化能力放回完整任务系统。

价值的单位是任务，不是模型调用

一次模型调用可能生成摘要、选择 Tool、判断政策或提出下一步，但业务价值通常出现在更长的链条末端：

请求进入
→ 收集证据
→ 作出判断
→ 执行动作
→ 等待外部结果
→ 验证完成

如果 Agent 只缩短其中一个很短的步骤，局部效率不会自动转化成端到端收益。

例如在一个假设场景中，客服生成处理意见需要两分钟，等待审批需要两小时。即使 Agent 把前者缩短到十秒，客户感受到的周期仍由审批决定。相反，如果客服花大量时间跨系统收集信息，且 Agent 能可靠完成这部分，即使最终审批仍由人工执行，也可能产生真实收益。

因此，ROI 的分母和分子都应使用同一个 Task 边界。不能用整项任务的人工成本作为潜在收益，却只用一次模型调用的成功率作为能力证明。

收益和新增成本必须进入同一张账

Agent 可能带来的收益包括：

  • 减少人工操作时间；
  • 缩短等待和交接；
  • 降低遗漏或不一致；
  • 提高服务覆盖；
  • 让稀缺专家只处理例外；
  • 提供过去无法规模化的新能力。

同时会新增：

  • 模型、Runtime 和 Tool 调用成本；
  • 人工确认与抽样审核；
  • Clarification 和异常接管；
  • 数据接入、权限和审计建设；
  • 错误恢复与客户补救；
  • Eval、监控和持续维护。

因此，一个方向性的净收益模型可以写成：

净收益
= 人工与周期节省
+ 质量改善与新增能力
- 审核和接管成本
- 系统建设与运行成本
- 预期失败损失

这里不必在调研阶段伪造精确数字。更重要的是确认每一项是否存在、由什么证据估计，以及哪个假设最可能推翻结论。

例如，若所有退款草稿都必须逐字审核，审核时间可能吞掉生成节省；若错误退款可被快速发现并撤回，预期风险又可能低于不可逆动作。成本必须结合任务事实，不能只按“Agent 有风险”统一加权。

Tool Coverage 限制实际任务覆盖

模型知道该做什么，不代表系统能够做什么。

Tool Coverage 需要检查 Agent 在任务闭环中的实际能力：

能力层需要验证的问题
观察能否获得完成判断所需的数据
解释数据是否有明确语义、来源和时效
行动是否存在范围清晰的 Tool
授权当前身份是否拥有必要权限
验证动作后能否重新观察外部状态
恢复timeout 或部分失败后能否 reconcile

如果 Agent 无法访问物流状态，它可能只覆盖未发货商品；如果只能创建草稿，不能确认提交，它的 Task completion 就应停在草稿状态；如果写入后无法查询结果，高自主执行会被 unknown outcome 限制。

Tool Coverage 不是“接了多少 API”，而是完成目标任务所需的观察—行动—验证链覆盖了多少真实案例。

自动化上限由多项约束共同决定

实际自动化上限可以用一个概念乘积理解：

Automation Ceiling
≈ 可观察案例
× 可验证案例
× Tool 可执行案例
× 权限允许案例
× 异常可处理案例

这不是要求把几个比例机械相乘，而是提醒团队：任何一个缺口都可能让案例退出自动化范围。

假设常规退款中：

  • 有些缺少必要材料；
  • 有些物流状态无法可靠获取；
  • 有些金额超过 Agent 权限；
  • 有些政策例外没有确定规则；
  • 有些 Tool 失败后结果无法确认。

即使模型推理本身表现很好，这些案例仍然不应自动完成。更合理的目标可能是：

自动完成证据完整、政策明确、金额低风险且结果可验证的案例；其余案例由 Agent 整理证据并升级。

升级并不等于失败。若人工接管时获得了完整上下文、已验证证据和明确冲突，Agent 仍然减少了人工工作。关键是把“自动完成”和“有效辅助升级”分开计量。

风险不只看错误概率，还看可发现与可恢复

两个成功率相同的 Agent Use Case，风险可能完全不同。

生成内部会议摘要出现遗漏，通常可以由读者发现并修改；错误退款可能产生资金损失；错误关闭安全事件则可能让风险继续扩大。

评估失败成本至少考虑：

  • 错误是否会产生外部副作用；
  • 副作用是否可逆；
  • 错误能否在下一步自动发现；
  • 从错误到发现存在多长窗口；
  • 是否有明确 owner 接管；
  • 单次失败和批量失败的影响是否不同。

因此，高风险任务不一定完全不能使用 Agent，但自主范围需要缩小。例如让 Agent 收集证据和生成草稿，由授权者确认；或只自动执行金额低、可撤销且结果可立即验证的动作。

风险控制应改变 Task Contract，而不是在 ROI 表格末尾加一个模糊的“合规风险”分数。

Pilot 要验证最脆弱的假设

Pilot 不应只展示若干精心挑选的成功案例。它需要验证决定 ROI 的关键假设：

  • 真实输入中有多少案例满足自动化条件；
  • 人工审核实际花费多少时间；
  • Tool 和数据失败出现在哪里；
  • 升级是否把足够上下文交给人工；
  • 完成结果是否能够自动验证；
  • 用户是否真的把任务交给 Agent；
  • 局部节省是否改变端到端周期。

因此，Pilot 应主动收敛到：

  • 单一角色和单一 Task；
  • 有代表性的真实案例分布；
  • 有限、可审计的 Tool surface；
  • 低风险或可恢复动作；
  • 明确的人工边界；
  • 预先写明的继续与退出条件。

如果结果表明主要成本来自 Agent 无法改变的审批等待，就应该停止或重新定义范围，而不是通过增加模型能力继续扩大项目。

回到问题

退款 Agent 的离线政策回答正确率是 80%，但这个指标没有覆盖执行和结果验证；Pilot 中的审核、数据缺口和高风险异常又让端到端收益接近消失。

重新以 Task 为单位后，团队需要分别计算自动完成、有效升级、人工审核和失败恢复；同时用 Tool Coverage、可验证性、权限和异常分布估计 Automation Ceiling。

Agent 不必完成百分之百的案例才有价值，但每一类价值都必须发生在真实工作流中，也必须扣除为可信执行新增的成本。

可自动化说明系统可能做到什么；值得自动化则要求证明，在限定风险和人工边界后，业务结果仍然变得更好。
