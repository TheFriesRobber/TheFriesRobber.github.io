Agent Discovery

需求调研必须还原真实工作，而不是复述 SOP

用 Shadowing、Artifact Review、日志与关键案例复盘发现 SOP 之外的等待、补偿动作和隐性决策证据。

问题

退款团队提供了一份四步 SOP：

接收申请
→ 查询订单
→ 判断退款条件
→ 回复客户

团队据此设计 Agent：读取工单，调用订单查询 Tool，把订单和退款政策交给模型，再生成处理结论。

但第一次用真实案例走查时，客服在查询订单后又打开支付系统，因为订单状态可能延迟同步；接着去物流系统确认商品是否揽收；发现两个状态冲突后，他在聊天工具里询问财务，并把结果记入个人表格，等待主管确认后才继续。

SOP 没有写错。它只是省略了让工作真正完成的等待、补偿动作和经验判断。Agent 上线后面对的不是流程文档，而是这些被省略的现实。

SOP 描述责任，真实工作暴露依赖

SOP 通常服务于培训、责任划分和合规表达，因此倾向于保留稳定主干。它不会记录每次系统延迟、每个非正式沟通渠道，也很少解释熟练用户为什么在某一步停下来。

Agent 需求却依赖这些细节。它必须知道：

  • 订单系统什么时候不足以作为唯一证据；
  • 用户为何查询另一个系统；
  • 哪种冲突允许继续，哪种冲突必须停止；
  • 用户向谁请求缺失信息；
  • 等待期间任务状态保存在哪里；
  • 最后由什么证据确认退款完成。

因此，访谈中的“通常怎么做”只能提供流程入口，不能直接成为 Agent Task。

这里需要区分两种材料：

规范性材料：工作应该怎样发生
描述性证据：工作实际上怎样发生

两者都重要。规范性材料提供政策边界，描述性证据揭示执行条件。只看前者会漏掉异常，只看后者则可能把个人绕行误当成组织希望保留的流程。

Shadowing 要记录决策，不只记录点击

还原真实工作的第一种方法是 Shadowing：观察用户处理真实任务，并记录动作、证据和判断。

如果记录只停在页面操作，最终得到的可能只是另一份更详细的流程图：

打开订单系统
→ 复制订单号
→ 打开支付系统
→ 粘贴订单号

这足以支持界面自动化，却不足以支持 Agent 决策。更有用的观察记录应该是：

动作：查询支付系统
原因：订单状态存在同步延迟
所需证据：支付流水、金额、订单号
判断：支付记录与订单状态一致时才能继续
异常：状态冲突时交给财务确认

每当用户切换系统、停顿、回看历史记录或向同事求助，都可以追问三个问题：

  1. 你此刻想确认什么？
  2. 哪个结果会改变下一步？
  3. 如果拿不到这条信息，你会怎样处理？

这三个问题把操作序列转化成决策证据，也开始暴露 Agent 所需的数据和升级条件。

观察时不应要求用户只展示最标准的案例。一个近期处理过的普通案例可以建立主干，一个困难或失败案例则更容易暴露真实边界。

Artifact 暴露系统外的任务状态

很多任务的关键状态不在正式业务系统中，而在用户自己维护的 Artifact 里：

  • 记录等待对象和跟进时间的 Excel；
  • 保存常用判断依据的私人笔记；
  • 复制历史处理方式的聊天记录；
  • 为不同异常准备的回复模板；
  • 标记“系统显示完成但仍需复查”的工单标签。

这些 Artifact 不应被自动视为需要长期保留的产品功能，但它们是重要的需求证据。

例如，客服维护个人表格可能有三种原因：

  1. 正式系统没有等待状态；
  2. 正式系统有状态，但无法按责任人筛选；
  3. 团队流程要求记录，用户却不知道现有功能。

三种原因对应不同解法。第一种可能需要新的任务状态，第二种可能只是产品查询能力不足，第三种则不是 Agent 问题。

Artifact Review 的目的不是照搬用户表格，而是理解它补偿了哪个缺失能力、保存了什么状态，以及谁依赖这份状态继续工作。

日志用于校正访谈中的“经常”和“很少”

访谈适合发现机制，却不擅长确认分布。用户容易记住最近、最困难或情绪最强烈的案例。

在条件允许时，需要用工单、操作日志或历史记录校正：

  • 各类任务实际出现多少；
  • 哪些步骤占据最长等待；
  • 状态冲突出现在哪里；
  • 人工接管发生在什么条件；
  • 返工通常从哪一步返回；
  • 哪些案例最终没有完成。

日志不能自动解释原因。两个系统被连续打开，可能是交叉验证，也可能只是用户习惯；一次长时间停顿可能在等待审批，也可能用户暂时离开。它必须与观察和访谈互相验证。

因此，更可靠的需求证据通常来自三角验证：

用户解释为什么
+ 现场观察怎样做
+ 历史记录说明出现多少

三种证据一致时，可以形成较强判断；不一致时，差异本身就是调研对象。

关键案例比抽象意见更接近真实边界

询问“你希望 Agent 怎么帮助”容易得到功能愿望。复盘“最近一次没有按 SOP 处理的任务”则更容易得到可执行事实。

一次 Critical Incident Review 可以沿时间线追问：

  • 初始请求是什么；
  • 当时可见哪些信息；
  • 第一个无法继续的点在哪里；
  • 用户做了什么补偿动作；
  • 哪个角色作出关键决定；
  • 哪些证据在事后才获得；
  • 结果如何确认；
  • 如果 Agent 当时参与，在哪一步应该停下。

特别需要区分事中信息和事后信息。不能因为复盘时已经知道退款最终失败，就假定 Agent 在执行时也能看到这一事实。

这一点会直接影响后续 Eval。历史案例只有保留当时可见状态，才能成为有效测试；把事后结论泄漏给 Agent，只会制造虚假的成功率。

一张真实工作记录必须保留证据来源

完成调研后，不应只产出一个更复杂的流程图。对每个关键步骤，至少记录：

字段需要回答的问题
Trigger什么事件让任务开始
Actor谁正在推进任务
Action实际执行什么动作
Evidence依据什么信息
Decision什么判断改变下一步
Artifact状态保存在哪里
Handoff交给谁、等待什么
Exception什么情况偏离主路径
Completion谁根据什么确认结束

把开场案例填入这张记录，可以得到一个最小实例：

字段开场案例中的观察
Trigger客户提交退款申请
Actor一线客服推进当前工单
Action先查询订单，再查询支付和物流状态
Evidence订单记录、支付流水、物流状态及各自来源
Decision状态一致才继续；冲突时暂停退款判断
Artifact客服暂时用个人表格记录等待对象和跟进时间
Handoff支付状态冲突时联系财务，例外决定等待主管
Exception订单、支付或物流系统返回互相冲突的状态
Completion开场材料没有记录最终结果，仍需确认由谁、根据什么证据判断完成

这张表描述的是调研中观察到的现状，不表示未来系统应该保留个人表格或相同的非正式沟通。仍待确认和设计的问题是：等待状态应由哪个正式系统拥有，财务确认怎样进入可审计交接，以及哪一个系统拥有最终退款事实和完成证据。

这张记录仍不是最终 Task Contract。它描述的是现状，而不是未来系统应该保留的全部行为。

下一步需要把观察到的补偿动作分类：哪些应该由产品消除，哪些应该成为 Tool，哪些代表人工判断，哪些只是历史遗留流程。先忠实还原，再做设计选择，才能避免把现状中的低效永久编码进 Agent。

回到问题

退款 SOP 只有查询、判断和回复四步。真实工作还包含跨系统核对、状态冲突、私下沟通、个人表格和后续复查。

如果 Agent 只实现 SOP，它会在干净案例中表现正常，却在第一次遇到支付状态冲突时失去下一步，也无法解释为什么应该停止。

Shadowing 让动作背后的决策可见，Artifact Review 找到系统外的任务状态，日志校正异常分布，关键案例复盘则暴露失败边界。四种证据合在一起，才得到 Agent 实际需要面对的工作。

需求调研不是把用户描述整理得更漂亮，而是找到任务真正依赖的证据、判断和交接。
