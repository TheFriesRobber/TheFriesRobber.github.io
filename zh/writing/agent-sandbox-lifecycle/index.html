Agent 24：Sandbox 生命周期与 Control Plane

用 Session、lease、policy、acquire、readiness 和 reconciliation 解释 Sandbox 创建成功为何不等于可执行。

2026/07/24 更新于 2026/07/27 阅读 次
Agent ProductionAgentSandboxControl Plane

问题

一个 Agent Session 已经运行了一段时间。Control Plane 请求 provider 创建 Runtime，provider 返回 created，健康检查也通过，于是系统把原来的 Workspace 挂载进去并继续执行。

但这时存在另一条事实链：旧 lease 已经过期，新 Session 已经接管同一个 Workspace；新 Runtime 使用的还是上一版 policy。容器确实活着，却既不是当前 owner，也没有按当前策略启动。

create workload 成功只证明 provider 自己定义的创建契约成立；它可能表示请求已接受、资源记录已创建，或 workload 已存在。readiness 也只回答进程是否准备好响应探测。两者都不能证明 Agent 层的 ownership 与 policy contract。Agent 真正需要的是更强的结论：

当前 Session 对指定 Workspace 持有仍有效的 lease，并且一个符合目标 policy 的 Runtime 已经完成挂载和初始化，可以接受执行。

这正是 Sandbox Control Plane 要拥有的生命周期契约。

四个对象不能压成一个 sandbox ID

有状态 Sandbox 至少包含四个生命周期不同的对象：

对象稳定身份谁决定它是否有效
Sessionsession_idAgent Control Plane
Workspaceworkspace_id、revisionWorkspace store
Runtime workloadprovider resource IDprovider 与 Control Plane 共同观测
Leaseowner、generation、expiry可信 lease store

Runtime 可以被删除和重建，Workspace 仍然存在；Session 可以结束，provider workload 却因为网络超时暂时没有被删除；lease 可以过期，容器仍保持健康。只保存一个 sandbox_id，无法表达这些分叉。

因此，client-visible 的 Sandbox handle 应是多个已验证事实的组合，而不是 provider ID 的别名。下面是概念性记录，不代表某个 provider 的 API：

{
  "session_id": "session_42",
  "workspace": {"id": "ws_7", "revision": 18},
  "runtime": {"provider_id": "vm_91", "profile": "python-3.13@sha256:..."},
  "lease": {"owner": "session_42", "generation": 6, "expires_at": "..."},
  "policy_revision": 12,
  "state": "ready"
}

其中 ready 不是任意组件可以独立写入的布尔值。它是 Control Plane 根据 acquire 各阶段的持久事实计算出的 client-visible state。

Control Plane 拥有的是收敛，不是资源创建

Provider 擅长创建 workload、network 或 volume，也能报告这些资源的当前状态。但它通常不知道 Agent 领域里的 Session、Workspace ownership、delegation 或 policy revision。

Control Plane 因此需要分别保存：

  • desired state：这个 Session 希望绑定哪个 Workspace、使用哪个 Runtime profile 和 policy revision。
  • observed state：provider 当前能查到哪些 workload、mount、network，以及探测结果。
  • ownership evidence：谁持有哪一代 lease，Workspace 当前 revision 是什么。
  • client-visible state：调用者目前可以 acquire、等待、重试还是必须停止。

Kubernetes controller 用控制循环让 current state 接近 desired state，这提供了一个可参考的实现模式；它并不自动赋予 Agent Session 的 ownership 语义。这里的 Session contract 仍需业务 Control Plane 自己定义。

Acquire 是可恢复的多阶段协议

一次安全 acquire 可以按下面的状态推进：

requested
  → lease_acquired
  → runtime_allocated
  → workspace_attached
  → initialized
  → policy_verified
  → ready

每一步都可能发生“副作用已经完成，但响应丢失”。所以状态机需要稳定的 acquire identity，并让每个阶段可以通过查询事实继续，而不是把 timeout 解释成“什么都没发生”。

例如 allocate 超时后，reconciler 应先按 request tag 或 provider reference 查询已有 workload。查到匹配资源就记录 observed state 并继续；无法确认时进入 unknown 或 reconciling，而不是立即再创建一个。

同样，readiness probe 只证明进程在当前时刻符合探测条件。它不证明：

  • Workspace 挂载到了预期 revision；
  • lease 仍属于当前 Session；
  • egress、secret 和资源限制已经按目标 policy 生效；
  • 另一个 Runtime 不会继续写同一 Workspace。

所以 ready 必须由这些 evidence 汇合而成。某一步失败时，系统返回明确的等待或终止状态，不能先把句柄交给 Agent，再让第一个 Tool Call 去发现挂载尚未完成。

Ready 是一次条件提交，也需要持续刷新

把各项 Condition 读出来之后再无条件写 state=ready，仍会产生竞态。假设 generation 5 的初始化探针很慢；用户已经停止 Session，或 generation 6 已经接管，它才返回成功。这个迟到结果不能重新开放旧 Runtime。

Control Plane 可以用一次本地 CAS 阻止迟到结果覆盖新的 desired state，但这个 CAS 不能证明分属不同 owner 的 lease、Workspace 与 policy 在同一瞬间仍然有效。更强的 Ready Contract 需要这些 owner 参与：Control Plane 为本次准备分配 readiness_epoch，各 owner 返回绑定到该 epoch、Runtime generation 和自身 revision 的限时证明。

desired_state = active
desired_revision = 27
runtime_generation = 6
provider_ref = vm_91
readiness_epoch = ready_6_27
workspace_proof = ws_7@18, generation=6, valid_until=t1
lease_proof = lease_4@generation_6, valid_until=t1
policy_proof = policy_12, runtime=vm_91, valid_until=t1
control_plane_version = 44

任一 owner 发生接管、解绑或 policy 变更时，必须推进 generation/revision 或使旧 proof 失效。Control Plane 只有在 proof 尚未过期且仍绑定当前 epoch 时，才能通过 CAS 发布 Ready record；record 同时保存 proof reference 与最短的 valid_until。这里不要求多个 owner 共享分布式事务，但也不能把异步读取包装成“事实同时成立”的强保证：如果 owner 只提供异步 observation，Ready 就只是一个有过期时间的 projection。

Ready 也不是永久终态。每次 Tool admission 都要重新验证 lease generation、proof freshness 与 valid_until；真正的 Workspace 或 effect 写入还必须由 owner 在写边界检查 generation/fencing token。这样即使 Ready 发布后立刻发生接管，旧 Runtime 也无法利用 TOCTOU 窗口继续产生 effect。

一次 refresh 获取新的 owner proof，再按当前 readiness_epoch 条件更新 projection，并至少验证 lease 仍有足够 headroom、Runtime 和 Workspace binding 未漂移、目标 policy 仍生效。Refresh timeout 不能让 Runtime 自行假定续约成功；当 lease 或 Ready Contract 接近 expiry 时，Control Plane 先停止新的 Tool admission，再续约、替换或隔离。已经过期的 generation 不能通过 refresh 复活，只能重新 acquire 并获得新的执行权。

Lease 需要 generation，而不只是过期时间

只比较 expires_at 仍可能遇到旧 owner 复活：Runtime A 暂时失联，lease 过期；Runtime B 获得 lease 并接管 Workspace；随后 A 恢复网络并继续写入。

一个常见设计是给每次接管分配单调递增的 lease generation，并把 generation 传给 Workspace 写入边界。Workspace backend 只接受当前 generation：

Runtime A: generation 5 → rejected
Runtime B: generation 6 → accepted

这类 fencing check 必须发生在能强制拒绝写入的可信边界。仅靠旧 Runtime 自觉读取 lease，无法阻止失联进程使用缓存状态继续写。

Kubernetes 的 Lease API 展示了 lease 可用于 heartbeat 和 leader election，但本文的 generation、Workspace fencing 与 acquire 状态是面向 Agent Sandbox 的设计建议，不是 Kubernetes Lease 自动提供的保证。

Release 也必须由 reconciliation 完成

正常路径中的 release() 不是生命周期终点。删除 Runtime 成功后，写 Control Plane 数据库可能失败；反过来，数据库先标记 released 后，provider 删除也可能超时。

更可靠的做法是先把 desired state 改为不可 acquire，再由 reconciler 反复比较 observed state：

  1. 阻止新的 lease refresh 和 Tool admission。
  2. 撤销或推进 lease generation，使旧 owner 失效。
  3. 查询并删除失去所有权的 workload、network attachment 和临时资源。
  4. 按 retention policy 保留、隔离或释放 Workspace/volume。
  5. 只有 provider 事实与本地状态都收敛后，才标记终态。

删除操作要能重复执行，并把 not found 视为可能的已收敛证据，而不是新错误。对于无法识别 owner、超出重试窗口或仍有挂载冲突的资源，应进入 quarantine/manual review，而不是无限重试或直接回收到资源池。

回到问题

开场中的 workload 虽然已经创建、健康检查也通过，Control Plane 仍应拒绝 acquire：它的 policy revision 已过期，而且 Workspace 当前 lease generation 属于另一个 Session。

系统应把旧 workload 标记为失去所有权，停止 admission，并由 reconciliation 清理它；只有新的 Runtime 同时满足 Workspace binding、有效 lease、目标 policy 和 readiness，才返回可执行句柄。

Sandbox 因此不是“一台已启动的容器”，而是一份持续可验证的 Session contract。Provider 创建资源，Control Plane 则拥有这份 contract 的 desired state、ownership 和最终收敛。
