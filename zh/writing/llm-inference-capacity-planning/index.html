LLM Infra 04：怎样从 Token 负载推导推理容量

将 workload envelope、每 Replica service curve、故障余量与 provisioning lead time 组合成容量区间，而不是用平均 GPU 利用率猜 Replica 数。

2026/07/29 阅读 次
LLM InfraInferenceCapacity PlanningReliability

问题

一个推理集群日常 GPU utilization 不高，却在长 Prompt 突发时迅速积压。增加一个 Replica 后短时恢复；下一次模型升级沿用同样 Replica 数，容量又不够了。

这种问题常被解释成“GPU 数算少了”，于是容量规划退化成按平均利用率补卡。但利用率既没有说明等待中的 Token work，也没有绑定模型、Runtime 和 SLO，无法回答需要多少可交付容量。

容量规划要连接两份已经建立的证据：生产侧的 workload envelope，以及 Benchmark 产生的 service curve。

容量的分子是待交付 workload

上一篇的 workload envelope 提供了 arrival、输入/输出 Token 分布、deadline 和 workload class。容量计算不能把这些字段再次压成一个平均 QPS。

先按执行兼容性和服务契约划分 workload segment，例如：

SegmentModel requirement输入/输出特征SLO
interactive-shortchat-v3短输入、短输出严格 TTFT/TPOT
interactive-longchat-v3-long长 Context、中等输出放宽 TTFT
async-generationgenerate-v2中等输入、长输出completion deadline

这不是为了给每类请求独占集群，而是为了避免把不可互换的工作相加。一个只支持短 Context 的 Replica 不能计入 long segment 的容量；一个满足 Batch deadline 的配置也不一定满足交互 TTFT。

Forecast 还要表达区间，而不是一个精确点：

low / base / high arrival
× input-output distribution
× burst window
× deadline and priority

预测的不确定性应该留在模型里。用“下季度一定是 8.5 req/s”伪装精确，后续只会把误差藏进一个任意 headroom 百分比。

容量的分母是满足 SLO 的 Service Curve

单 Replica capacity 不是理论 FLOPs，也不是某个产品页面上的 peak tokens/s。它来自固定 deployment manifest 下的实测 service curve。

假设 Batch 1 的合成 Benchmark 在 1.0–1.5 req/s 之间继续做了更细的 sweep，给出：

workload fingerprint: wl_7fd2
deployment manifest: dep_a91c
maximum offered load meeting contract: 1.1 req/s per Replica

这里的 1.1 req/s 是在 good-request fraction ≥ 95% 的可行性约束下，单 Replica 能承受的最大 offered load。它只是演算输入，不代表真实 GPU。该数值来自包含输入/输出分布、Batching、TTFT/TPOT 与全部失败结果的实验，但它不是 application goodput：如果恰有 95% 的请求达标，对应 application goodput 约为 1.045 req/s。

如果 Replica 同构、Router 能均衡分配该 workload、没有共享 gateway/网络瓶颈，且 Cache/Adapter affinity 不会把流量固定在少数副本，最简单的 steady-state 初始估算是：

N_steady = ceil(forecast_offered_rps / max_supported_offered_rps_per_replica_at_target_fraction)

若 base forecast 为 8.5 req/s，则：

ceil(8.5 / 1.1) = 8 Replicas

这个除法的分子和分母都是 offered load，且共享同一个 good-request fraction 门槛。它只是候选规模，不是 fleet capacity 的证明。真实部署还要测多 Replica service curve，确认 routing、affinity 与共享组件没有破坏组合关系。结果也只在 workload fingerprint 与 deployment manifest 没有变化时有效；模型 revision、quantization、parallelism、scheduler policy、driver 或硬件变化，都可能使原 service curve 失效。

Headroom 不是固定百分比

在估算结果上机械加 30% 看似安全，实际混合了多种不同风险：

  • workload forecast 误差；
  • 短时 burst；
  • 单 Replica 性能波动；
  • 一个 Replica 或一个 failure domain 不可用；
  • 新容量启动前的 provisioning lead time。

这些风险的时间尺度和恢复方式不同，应该分别处理。

Steady-state headroom

不要把 Replica 长期运行在 service curve 刚好失去 SLO 的边界。应选择曲线上仍能容纳观测噪声与 workload 漂移的稳定区间。

Burst buffer

如果 burst 持续时间短于新 Replica 的启动时间，Autoscaling 无法及时解决。系统只能依赖已有 idle capacity、deadline 允许的 bounded queue，或者显式 admission。

Failure capacity

如果要求失去一个 Replica 后仍满足 base workload，则前述合成结果至少需要：

N_failure = N_steady + 1 = 9 Replicas

这条 N+1 只适用于“单个同构 Replica 是故障单位”的合成条件。若 Replica 跨多张 GPU，或多个 Replica 共享节点、交换机、电源域，故障单位就不能简单按单进程计算。真正的要求应写成：失去目标 failure domain 后，剩余 fleet 的实测 goodput 仍覆盖 target workload。

Provisioning reserve

新节点创建、镜像拉取、模型加载、并行组形成和 warmup 都需要时间。扩容请求发出不等于 capacity ready；只有通过 readiness 与 service curve 验证的 Replica 才能计入可交付容量。

因此，最终输出更适合写成容量区间和条件：

场景合成结果假设
Low steady state6 Replicaslow forecast，全部 healthy
Base + one Replica failure9 Replicasbase forecast，N+1
High + one Replica failure12 Replicashigh envelope 的 steady state 为 11，另加一个同构故障 reserve

表中数字仍然只是演算例子。它展示的是结构，而不是推荐配置。

GPU utilization 只能解释部分设备活动

GPU utilization 高，可能意味着设备计算繁忙；也可能是大 Batch 正在健康地兑现离线 workload。Utilization 低，也可能是：

  • 请求还在 gateway 或 scheduler queue；
  • Replica 因 KV/memory 限制无法 admission；
  • 多卡执行正在等待通信或同步；
  • 目标 model/adapter 尚未加载；
  • arrival 本身不足。

因此它适合做诊断证据，不适合作为容量公式。真正需要比较的是：

未来窗口内待交付的兼容 workload
vs.
当前 ready Replicas 在同一契约下的 service capacity

Utilization、queue age、pending Token、KV pressure 和 active sequences 可以解释这个差距，却不能替代 workload 与 service curve。

容量结果必须带失效条件

一份可执行的 capacity record 可以是：

capacity_plan:
  workload_fingerprint: wl_7fd2
  forecast_window: 2026-Q3
  scenarios:
    low_rps: 6.0
    base_rps: 8.5
    high_rps: 12.1
  service_curve:
    deployment_manifest: dep_a91c
    max_supported_offered_rps_per_replica: 1.1
    good_request_fraction_gte: 0.95
  failure_requirement:
    unavailable_replicas: 1
  provisioning:
    ready_lead_time_p95: measured-separately
  invalidate_on:
    - workload_distribution_changed
    - model_or_tokenizer_revision_changed
    - runtime_or_scheduler_changed
    - hardware_or_parallelism_changed

其中 lead time 必须由真实部署过程测量，不能用经验值填空。计划还应定期对照生产观测：实际 workload 是否落在 envelope 内，ready Replica 是否仍交付原 service curve。

回到问题

原集群的 GPU utilization 不高，不能证明容量充足。长 Prompt burst 可能在 GPU 取走请求前就形成队列；模型升级则会让旧 service curve 失效，所以同样 Replica 数不再代表同样的 goodput。

正确的容量结论必须写成：

指定 workload envelope
× 指定 SLO 与质量约束
÷ 指定 deployment manifest 的 service curve
+ burst / failure / provisioning 的独立约束

Batch 1 到这里形成闭环：01 定义工作，02 定义什么叫有效交付，03 测量 service curve，04 把二者转换为容量区间。下一批将进入单 Replica 内部，解释这条容量曲线为什么首先受显存、调度、Cache 与量化约束。
