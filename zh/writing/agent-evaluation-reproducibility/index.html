Agent 34：非确定性 Eval 怎样保持可比

用 case × configuration × trial、dataset tier 和完整 manifest 建立可复现的 Agent 评测。

2026/07/24 更新于 2026/07/27 阅读 次
Agent VerificationAgentEvaluationReproducibility

问题

下面是一个构造例子。两个 Agent 配置各评测 5 个 case，每个 case 重复 5 次，最后都通过 20/25 个有效 trial：

配置case 1case 2case 3case 4case 5
A4/54/54/54/54/5
B5/55/55/55/50/5

总体 pass rate 都是 20/25，但风险完全不同。A 在所有 case 上都有波动；B 在这组观测中对一个 case 持续失败。若只看总体均值，两种行为会被压成同一个数字。

反过来，同一个配置今天是 20/25，明天变成 18/25，也不能立刻归因于模型退化。Dataset revision、prompt、Tool surface、fixture、grader、timeout 或外部服务都可能已经改变。

非确定性 Eval 要先回答：比较的最小记录是什么，哪些输入相同，哪些环境条件只是被观察到，以及指标在哪个分母上聚合。

基本 Grain 是 Case × Configuration × Trial

一次 Eval 至少有三个相互独立的身份：

  • case 定义要验证的输入、目标、fixture 和成功条件；
  • configuration 定义被测系统的可比较版本；
  • trial 表示在这组条件下的一次实际执行。

一条最小 trial 记录可以是：

{
  "case_id": "address_update_17",
  "configuration_id": "config_sha256:...",
  "trial_id": "trial_03",
  "outcome": "task_failed",
  "failure_class": "wrong_tool_selection",
  "validity": "valid"
}

这里的 Attempt 仍属于运行时内部粒度。一个 trial 可能经过多个 model 或 Tool Attempt；评测最终要保留 trial outcome，同时允许从 trace 下钻到 Attempt failure。不能把 retry 自动算成新的 case，也不能让后一次成功覆盖同一 case 的前一次 trial。

总体指标必须写清聚合方法：

micro success
= 通过的有效 trials / 全部有效 trials

per-case success
= 某个 case 通过的有效 trials / 该 case 的全部有效 trials

all-valid-trials-pass
= 所有有效 trials 都通过的 cases / 有有效观测的 cases

Micro average 会让有效 trial 更多的 case 获得更高权重。若不同 case 的有效 trial 数不同，应同时报告每个 case 的 support，或先补齐相同次数后再比较。all-valid-trials-pass 也只描述有效观测；只要 case 存在 invalid trial，就不能单独用它冒充完整发布门禁。总体趋势用于导航，per-case 分布才暴露固定盲区和波动。

Invalid Trial 不能悄悄离开分母

Eval harness 崩溃、fixture 无法启动时，trial 可能没有产生对被测系统的有效观察。这类记录可以标为 infrastructure_invalid，但前提是先声明 system under test 的边界。

如果生产路径本来就依赖某个 provider、Runtime 或网络，而该依赖 timeout，那么它通常是被测系统的有效失败；不能为了提高成功率，把它移到 infrastructure denominator 之外。相反，评测侧测试数据损坏，不应被写成模型失败。

一个可解释的报告应同时给出：

scheduled trials
valid trials / scheduled trials
infrastructure-invalid trials / scheduled trials
task successes / valid trials

当某个 configuration 的 invalid rate 明显变化时，剩余有效 trials 可能已经不是可比样本。此时结论应该降级为“需要调查”，而不是继续比较两个 pass rate。

Dataset Tier 是运行与门禁契约

Case 的 tier 不只是筛选标签。它至少决定谁维护、何时运行、失败怎样处理，以及能否阻止发布。

Tier目的典型运行方式失败语义
Smoke快速证明关键路径可执行高频、少量、稳定 fixture通常直接阻断后续评测
Regression守住已经确认的重要行为每次候选变更或发布前按明确 owner 与 gate 处理
Capability探索能力边界与覆盖缺口周期性或专项运行形成分析，不默认阻断
Quarantine隔离暂时不可信的 case独立运行并持续治理不进入主 gate，但必须有退出条件

一条生产 bad case 被清理和复现后，可以先进入 capability；当目标、fixture 和 grader 稳定，并确认它代表必须守住的行为，再晋升为 regression。一个频繁因评测基础设施失败的 regression case 可以暂时 quarantine，但必须记录 owner、原因、进入时间与退出条件。

Quarantine 不是垃圾桶。长期没有 owner、没有重现计划的 case 已经不能提供可靠证据，应被修复、重定义或移除，而不是永久保留一个“以后再看”的标签。

Tier 也不规定固定数量。十个高价值 regression case 可能比一千个重复简单问答更能约束发布；重复 trial 只能帮助理解这些 case 的波动，不能扩大 dataset coverage。

Manifest 区分固定输入与观察环境

“模型名相同、代码 commit 相同”不足以证明两次 Eval 可比。一次 Agent trial 的行为还可能取决于：

  • dataset revision、case filter 与 tier policy；
  • system prompt、模板和 Context assembly 规则；
  • Tool name、description、schema、authorization 与 adapter；
  • fixture、初始数据库或文件状态；
  • Runtime、harness、grader 与 rubric；
  • timeout、并发、retry 与资源 budget；
  • model router、fallback policy，以及请求的 model 与 sampling configuration；
  • provider 对 seed 等可选参数的支持边界、实际解析到的 model 版本和响应元数据；
  • 执行时间以及无法 pin 的外部依赖状态。

Manifest 应把它们分成两类。

Pinned inputs 是评测方能够固定的内容。名称只是方便阅读，真正的身份应来自不可变版本或内容 fingerprint：

configuration_id: config_sha256:...
dataset: regression@18
case_filter_sha256: ...
prompt_sha256: ...
tool_surface_sha256: ...
tool_authorization_policy_sha256: ...
authorization_fixture_sha256: ...
tool_adapter_sha256: ...
fixture_image_digest: sha256:...
runtime_commit: ...
harness_commit: ...
grader_sha256: ...
model_request:
  router_policy_sha256: ...
  fallback_policy_sha256: ...
  requested_model: provider/model-family
  provider_contract_version: ...
  sampling:
    temperature: 0.2
    top_p: 1
    seed: 7
  seed_support: supported
timeout_ms: 30000
retry_policy_sha256: ...
concurrency_policy_sha256: ...
resource_budget_sha256: ...
trial_count_per_case: 5

configuration_id 应由除自身外这组 pinned inputs 的 canonical representation 或 manifest fingerprint 派生，而不是由实验名称人工填写。Sampling 参数即使采用默认值也要显式进入 identity；否则一次 provider 默认值变化会伪装成被测代码变化。seed 只有在 provider contract 明确支持并且实际请求没有被忽略时才是受控输入；不支持或无法确认时，它应进入 observed limitation，而不是提供虚假的确定性。

Observed environment 是无法完全固定、但必须记录的条件：

started_at: 2026-07-24T09:00:00Z
resolved_model_id: provider/model-version
resolved_router_target: provider/route
provider_response_metadata: ...
seed_honored: unknown
external_dependency_revision: unknown
region: ...

这只是字段结构示例，不代表任何真实实验配置。关键判断是：能控制的输入要固定，不能控制的条件要记录；未知不能被伪装成已复现。

可比性本身也需要结论

比较两个 experiment 以前，可以先生成一份差异表：

对象BaselineCandidate判断
Dataset fingerprint相同相同可比
Prompt fingerprint相同不同这是待测变量
Model request / router policy相同相同可比
Tool surface相同相同可比
Fixture相同相同可比
Grader相同相同可比
External dependencyrevision 未知revision 未知存在未控制混杂

只有 prompt 被有意改变，model request、router/fallback policy 与其余关键输入固定时，差异才可以在当前范围内归因给这次候选变更。若 dataset 与 grader 同时改变，或一侧的 seed 被支持而另一侧被忽略，结果仍可记录，却不能声称只测到了 prompt。

缺少旧 experiment 的 Tool surface fingerprint 时，也不该补一个看似合理的值。更诚实的结论是“历史结果不可严格比较”，然后从新的完整 manifest 建立 baseline。

严格可复现也有现实边界。即使 seed 相同，远程模型和服务仍可能不是确定性的；manifest 的作用不是承诺得到逐 token 相同的输出，而是让读者知道哪些条件已经固定、哪些差异仍可能来自环境。

用 Per-case 分布解释开场结果

回到构造数据，A 与 B 的 micro success 都是 20/25，但还应至少保留：

观察配置 A配置 B
每个 case 的有效 trial 数都是 5都是 5
最差 case 的观测成功数4/50/5
所有 trials 都通过的 case0/54/5
失败覆盖分散在 5 个 case集中在 1 个 case

这 5 次只是有限观测，不能把 4/5 或 0/5 宣称为系统的真实长期概率。它们足以支持一个较窄的判断：在这批 case 和这份 manifest 下，A 显示广泛波动，B 显示一个稳定盲区。

发布决策还必须结合产品语义。如果失败 case 是禁止越权写入，哪怕总体 pass rate 很高也可能是 hard gate；如果失败只影响可安全重试的无副作用候选，则可以另外评测真实 retry policy 的 Task outcome。

回到问题

相同 pass rate 不代表相同风险，同一版本两次分数不同也不自动代表模型漂移。

保留 case × configuration × trial，明确 valid 与 invalid denominator，再用 smoke、regression、capability 和 quarantine 管理 case 的责任，才能看见失败是集中盲区还是跨 case 波动。完整 manifest 则把固定输入、唯一待测变量与不可控环境分开，让每次比较先证明自己“可以比较”。

非确定性 Eval 的可复现性，不是要求每次输出完全相同，而是让结果差异能够被定位到明确的 case、配置、trial 和仍未控制的条件。
