LLM Infra 12：容量不足时，排队、拒绝与扩容怎样按时标协作

把 immediate admission、bounded queue、slow provisioning 与 scale-in draining 放进同一个多时间尺度容量控制回路。

2026/07/29 阅读 次
LLM InfraInferenceAdmission ControlAutoscaling

问题

突发流量进入无界队列，Autoscaler 开始拉起新 Replica。模型加载完成前，早期请求已经失去 deadline，排队中的无效工作却没有及时清理。扩容最终成功，满足 SLO 的 goodput 仍然下降。

问题不是扩容太慢或拒绝太早，而是系统把 admission、queue 与 provisioning 当成三套互不相干的机制。它们处理的是同一次容量不足，只是时间尺度不同。

四个时标构成一个控制回路

Immediate admission

请求到达时，判断当前兼容 deployment 是否可能接纳。结果可以是 accept、defer、route、degrade 或 reject。

Queue horizon

在 deadline 允许的短窗口内，bounded queue 吸收 burst。队列必须按 pending Token work 和 oldest age 解释，不能只看 request count。

Provisioning lead time

创建节点、拉取镜像、加载模型、形成并行组、warmup 到 Ready 需要时间。扩容只对晚于这个时间窗口的需求有效。

Scale-in draining

缩容时，停止接收新请求，等待或迁移已接纳工作，再移除 Replica。直接删除可能破坏 streaming 和 KV state。

四者必须消费同一 workload identity、deployment revision 和 capacity evidence，否则 Admission 认为“马上有容量”，Autoscaler 却只创建了不兼容的新 Replica。

Deadline 决定扩容能不能救当前请求

设：

  • D：请求距离 deadline 的剩余时间；
  • L_ready：该 deployment 实测的 Replica-ready lead time。

如果 D ≤ L_ready，新 Replica 即使立即启动，也无法服务当前请求。这是由时序得到的推论，不是某个 Autoscaler 的内置保证。

当前请求只能在以下结果中选择：

  • 现有 capacity 仍能接纳，并按请求契约在 deadline 内交付；
  • queue 一小段时间；
  • route 到已经 Ready 且兼容的 deployment；
  • 在调用方明确允许的契约内 degrade；
  • reject，并返回稳定 reason 与可用的 retry guidance。

扩容仍然有用，但它服务的是随后到达或 deadline 更远的请求。

Admission 需要可解释 Outcome

admission_outcome:
  request_id: req_123
  decision: reject
  reason_code: deadline_before_capacity_ready
  queue_deadline: 2026-07-29T12:00:02Z
  retry_after_seconds: 3
  compatible_release: null

这是本文的概念 schema。Retry-After 在 HTTP 中有标准语义，但是否返回以及数值怎样计算，需要结合 overload state，不能让所有客户端在同一秒重试形成新 burst。

degrade 也不能等于“换一个更小模型”。只有 release capability contract 明确兼容，且调用方允许时，Infra 才能选择替代 deployment；否则应显式拒绝。

Queue 必须 bounded。无界队列会让失去 deadline 的请求继续占用内存和调度开销，并把过载变成越来越长的失败延迟。

Autoscaling 要比较 Demand 与 Ready capacity

KServe 的 generative inference autoscaling 示例会使用 vLLM running、waiting 或 KV usage 等指标；Ray Serve 默认比较每 Replica ongoing requests 与目标值，并说明 startup delay、max ongoing requests 与 queue 对尾延迟的影响；Kubernetes HPA 则基于周期观测和稳定窗口调整副本。

这些实现证明了可用信号，但没有一个通用最优公式。推理平台可以把证据分为：

类型例子
Demandknown prompt Token、generated Token、remaining output estimate/upper bound、oldest queue age、arrival forecast
Ready capacity兼容 Ready Replicas、service curve、KV/Token budget
Provisioning实测 startup/load/warmup lead time、pending Replicas
SymptomGPU utilization、preemption、deadline miss

一份 capacity decision 可以是：

capacity_decision:
  deployment_revision: release_91a
  observed_at: 2026-07-29T12:00:00Z
  known_prompt_tokens: 520000
  generated_tokens: 80000
  remaining_output_estimate: 240000
  max_remaining_tokens: 610000
  output_estimator_version: output-length-v3
  demand_policy: expected_remaining_output
  oldest_queue_age_ms: 620
  ready_capacity_ref: fleet_curve_22
  measured_lead_time_ref: startup_dist_08
  desired_replicas: 10
  scale_reason: sustained_pressure_beyond_ready_capacity

字段组合是 workload-specific 的设计建议。未来输出 Token 在执行前并不知道，控制器必须说明使用有版本的期望估计还是请求上限，不能把预测值写成事实。这个例子也不是行业公式，startup 常数必须来自测量。

Scale-out 尚未 Ready 时，Admission 仍要工作

合成时间线：

t0      burst arrives
t0+Δ1   admission fills bounded queue, rejects requests without slack
t0+Δ2   scale-out requested
t0+Δ3   new Replica loading model; not counted as capacity
t0+Δ4   platform readiness passes; health probes only
t0+Δ5   release compatibility passes; controlled warmup/probes
t0+Δ6   capacity gate for the measured curve passes
t0+Δ7   Router sends production work; Autoscaler counts ready capacity

Kubernetes readiness 只说明 Pod 当前可以接收相应流量，不证明 model revision、并行组、warm state 与性能已经兑现容量规划使用的 service curve。因此这里拆成 platform_ready → release_compatible → capacity_ready_for_curve 三个 gate；只有 t0+Δ6 后，新 Replica 才能进入 Autoscaler 的 ready capacity。Pod Running、进程启动、model download 完成或单独的 readiness probe 都不够。

在 Δ2–Δ6 期间，Admission 不能停止。它需要持续更新 queue deadline、清理尚未执行且已经失效的排队请求，并防止 retry 把流量再次放大。已开始执行的 cancellation acknowledgement 与 unknown outcome 属于第 14 篇的流式失败协议，不在本文声称已经解决。

Scale-in 必须保护已接纳工作

GPU utilization 下降不代表 Replica 可以立即删除。它可能仍持有：

  • 正在 streaming 的 Decode sequence；
  • 尚未完成的 Prefill；
  • 本地 Prefix KV 或 Adapter residency；
  • 已被 placement 选择、尚未 arrival 的请求。

Draining 可以按以下状态执行：

ready
→ stop_new_admission
→ wait_or_cancel_by_policy
→ release_residency
→ removed

Scale-in delay、minimum warm capacity 和 stabilization window 都应根据 workload 与 measured lead time 选择。反复扩缩会重复模型加载，并让 cold state 进入每个性能窗口。

回到问题

开篇的扩容最终成功，却救不了已经失去 deadline 的请求；无界队列还让尚未执行的失效请求继续制造无效工作。

正确的控制回路按四个时标协作：Admission 处理此刻，bounded queue 处理短 burst，provisioning 处理持续压力，draining 保护已经接纳的工作。新 Replica 只有依次通过 platform、release 与 capacity gate，并能兑现对应 service curve 后，才算容量。

扩容不是拒绝的替代品，拒绝也不是失败的副作用。两者共同决定系统在容量不足时还能交付多少 goodput。
