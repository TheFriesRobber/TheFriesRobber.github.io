Agent Activity 建模先明确 Grain

2026/07/12
AgentData ModelingObservabilityLineage

问题

一次 Agent Run 调用了文件读取 Tool。第一次请求 timeout，第二次 retry 成功，Agent 最终生成了报告。

系统记录了两条 Tool 日志：一条失败、一条成功。现在要回答“这次 Tool 调用成功了吗”，至少会得到两个看似矛盾的答案：

按物理请求计算：1 次成功 / 2 次尝试 = 50%
按逻辑 Tool Call 计算：最终成功 / 1 次调用 = 100%

如果最终报告也正确生成，这次 Run 的结果就是成功；在这个只有一个 Run 的样本里，Run 层成功比例是 100%。这些数字都可能正确，只是回答的问题不同。

Agent Activity 建模最先要解决的不是字段够不够多，而是 grain：一行数据究竟代表一个用户目标、一个逻辑动作，还是一次物理尝试。

先沿一次执行把对象分开

继续使用生成报告的例子：

用户 Message：“根据这个文件生成报告”
  └─ Run：完成这次用户目标
       ├─ Turn 1：模型决定读取文件
       │    └─ Tool Call：读取 file_17
       │         ├─ Attempt 1：timeout
       │         └─ Attempt 2：succeeded
       ├─ Turn 2：模型根据内容生成报告
       └─ Artifact：report.md

这里的对象不是同一件事换了几个名字：

  • Message 是用户或 Agent 可见的一次表达。
  • Run 是为完成一个用户目标启动的一次逻辑执行。
  • Turn 是一次完整的模型请求与响应。
  • Tool Call 是模型提出的一个逻辑动作。
  • Attempt 是 Runtime 对这个动作的一次物理执行。
  • Artifact 是执行读取或产生的持久结果。

本文关注的是分析 grain，不在这里定义这些对象完整的 Runtime 状态机。需要先看清的一点是：它们之间通常不是一对一。

Retry 最容易暴露 Grain 错误

假设分析表把每次 HTTP 请求都当成一次 Tool Call。第一次 timeout 和第二次成功就会被统计成两个不同动作，系统看起来调用了两次读取 Tool。

如果反过来让 retry 覆盖同一行，最终状态会变成 succeeded，却看不到第一次 timeout 带来的延迟、成本和错误。

正确的关系是让逻辑身份与尝试身份同时存在：

tool_call_id = call_42
  ├─ attempt_id = attempt_1  → timeout
  └─ attempt_id = attempt_2  → succeeded

tool_call_id 回答“模型想完成哪个动作”，attempt_id 回答“Runtime 实际试了几次”。两者分开后，系统可以区分逻辑 Tool Call 的结果与 Attempt 层可靠性。要判断用户目标是否完成，还需要把 Tool Call 关联到所属 Run，并检查 Run 终止时的证据。

同样，用户主动点击“重新生成”通常应产生新的 Run，而不是上一个 Run 的 Attempt。判断依据不是两条日志时间是否接近，而是产品语义：它们是否代表同一个用户意图，是否允许产生两个独立结果。

不要用时间接近推断因果关系

Agent 执行可能跨 Queue、SubAgent 和外部 callback。两条 event 到达日志系统的顺序，不一定是实际发生顺序。

例如，第一次 Tool Attempt 的 timeout 先到达，外部服务稍后才回传“读取已完成”。如果只按 ingested_at 排序，分析可能把 callback 误认为 retry 之后发生的新动作。

因此，需要显式保存关系，而不是事后猜测：

Run run_12
  └─ Tool Call call_42
       ├─ Attempt attempt_1
       └─ Attempt attempt_2

Artifact report_7
  ← derived from file_17@v3
  ← produced by run_12

时间戳仍然用于计算等待和延迟，但 parent_id、逻辑 action ID 与 Artifact lineage 才负责表达“谁触发了谁”和“结果依赖什么”。

一个 Event Stream 不应直接充当所有指标

执行系统可以持续写入 event，记录 attempt started、timeout、retry scheduled 和 run completed。分析层则应根据问题派生不同 grain 的事实：

分析问题合适的 Grain
下游服务单次请求是否稳定一行一个 Tool Attempt
模型提出的 Tool Call 最终是否完成一行一个逻辑 Tool Call
用户目标是否完成一行一个 terminal Run
最终内容依赖哪些输入一行一条 Artifact lineage edge

把这些 grain 全塞进“一行一个 Run”的宽表，会产生大量嵌套数组；直接拿 raw event 做 dashboard，则会让每个查询重复处理 retry、迟到和去重。

更稳妥的做法是让 source event 保留过程，再按稳定 grain 幂等地产生分析事实。同一条底层事件可以进入多个派生模型，但每个模型仍需保留自己的 grain，不能在所有计算中都把它当成同一种记录。

指标必须把分母写清楚

“Tool 成功率”本身不是完整指标。它至少可能表示：

successful attempts / all terminal attempts
successful logical tool calls / all terminal logical tool calls
successful runs using this tool / all terminal runs using this tool

第一次失败、第二次成功时，Attempt success rate 下降，logical Tool Call 仍然算成功。这正是系统需要的信息：用户目标被恢复了，但底层可靠性正在变差。

Latency 和 cost 也一样。Run 的端到端耗时包含 model、queue wait、Tool Attempt、retry backoff 和 Artifact 写入。如果只保存最终总数，就无法判断时间和成本消耗在哪一层；如果只保存 Attempt，又无法回答一次用户目标总共付出了多少代价。

所以聚合必须沿显式关系向上进行，而不是把某张表里最容易相加的数字当成答案。

Artifact 让“成功”连接到实际结果

Run 状态为 succeeded，不一定意味着用户拿到了正确产物。报告可能引用了旧文件版本，也可能在生成后上传失败。

将 Artifact 作为独立对象，并记录它由哪个 Run 产生、读取了哪些 source version，可以回答：

  • 最终报告是否真的存在。
  • 它使用的是 file_17 的哪个版本。
  • 重跑后产生的是新 Artifact，还是覆盖旧版本。
  • 一条错误来源影响了哪些下游结果。

这类 lineage 只需要记录可观察的输入输出关系，不需要保存模型的隐藏推理过程。

什么时候简单日志已经足够

如果 Agent 每个请求只调用一次模型，不执行 Tool、不 retry，也不产生后台任务或 Artifact，那么一条 request log 加一条 response log 可能已经足够。

当一个用户目标开始包含多轮模型调用、多次物理尝试和持久产物时，单一“对话记录”才会失去解释力。此时增加更多 JSON 字段不是关键，先分清 grain 才是。

回到问题

日志很多却无法调试，通常不是少记录了某个字段，而是不同粒度的事实被混在了一起。

把 Run、逻辑 Tool Call、Attempt 和 Artifact 分开后，一次 retry 才能同时表达两件事：底层请求失败过，但用户目标最终恢复成功。随后，成功率、Latency、cost 和 lineage 才能各自使用正确的分母与因果关系。

Agent Activity 建模的起点不是一张覆盖所有场景的宽表，而是先确定每条记录代表什么。

后续问题

  • Run、Turn、Step 与后台 Task 的状态和 retry unit 应怎样定义。
  • Event log、current snapshot 与 analytics fact 应怎样派生和校验。
  • 跨服务 event 的 event time、sequence 与迟到数据怎样处理。
  • Token、Tool、Sandbox 和 Storage cost 怎样沿 causality 归因。
  • Trace、Eval dataset 与生产 bad case 应怎样关联同一组执行事实。
