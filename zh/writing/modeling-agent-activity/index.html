Agent Observability 一：建模前先明确 Grain

从一次 Tool retry 出发，解释为什么 Agent 的 Task、Run、Model Turn、Tool Execution 与 Attempt 不能混在同一行数据里。

2026/07/12 阅读 次
AgentData ModelingObservabilityLineage

问题

一次 Agent Run 执行了文件读取 Tool。第一次请求 timeout，第二次 retry 成功，Agent 最终回复“报告已生成”。

系统记录了两条 Tool 日志：一条 timeout、结果未知，一条确认成功。现在要回答“这次 Tool 执行成功了吗”，至少会得到两个看似矛盾的答案：

按物理请求计算：1 次成功 / 2 次尝试 = 50%
按逻辑 Tool Execution 计算：最终成功 / 1 次执行 = 100%

如果这次 Run 正常给出最终回复，Run 层也是成功；如果报告 Artifact 还没有交付，用户的 Task 则可能仍未完成。这些数字都可能正确，只是回答的问题不同。

Agent Activity 建模最先要解决的不是字段够不够多，而是 grain：一行数据究竟代表一个用户目标、一次 Agent Loop、一个模型轮次、一次逻辑执行，还是一次物理尝试。

先沿一次执行把对象分开

继续使用生成报告的例子：

用户 Message：“根据这个文件生成报告”
  └─ Task：生成并交付报告
       └─ Run：处理这次用户输入的 Agent Loop
            ├─ Model Turn 1：模型提出读取文件
            │    └─ Tool Call：read_file(file_17)
            │         └─ Tool Execution tool_exec_42
            │              ├─ Attempt 1：timeout
            │              └─ Attempt 2：succeeded
            ├─ Model Turn 2：模型根据内容生成报告
            └─ Artifact：report.md

这里的对象不是同一件事换了几个名字：

  • Message 是用户或 Agent 可见的一次表达。
  • Task 是应用持有的用户目标，可以跨多个 Run。
  • Run 是由一次新输入或恢复动作启动的 Agent Loop。
  • Model Turn 是 Loop 内一次模型响应及其 Tool 调用处理。
  • Tool Call 是模型提出的动作；Tool Execution 是 Runtime 校验并获准执行后的逻辑身份。
  • Attempt 是 Runtime 对同一个 Tool Execution 的一次物理尝试。
  • Artifact 是执行读取或产生的持久结果。

本文关注的是分析 grain，不在这里定义这些对象完整的 Runtime 状态机。需要先看清的一点是：它们之间通常不是一对一。

Retry 最容易暴露 Grain 错误

假设分析表把每次 HTTP 请求都当成一次 Tool Execution。第一次 timeout 和第二次成功就会被统计成两个不同动作，系统看起来读取了两次文件。

如果反过来让 retry 覆盖同一行，最终状态会变成 succeeded，却看不到第一次 timeout 带来的延迟、成本和错误。

正确的关系是让逻辑执行身份与尝试身份同时存在：

tool_execution_id = tool_exec_42
  ├─ attempt_id = attempt_1  → timeout
  └─ attempt_id = attempt_2  → succeeded

tool_call_id 可以继续保存模型的原始提议，tool_execution_id 回答“Runtime 最终执行的是哪个逻辑动作”，attempt_id 回答“物理上试了几次”。分开以后，系统才能同时分析模型行为、Tool 结果与下游可靠性。

用户主动点击“重新生成”通常会启动新的 Run，而不是上一个 Run 的 Attempt。它是否仍属于同一个 Task，要由产品语义决定：如果只是继续完成原目标，可以关联原 Task；如果要求保留第二份独立结果，则应创建新 Task 或新目标版本。不能只按两条日志的时间距离决定 identity。

不要用时间接近推断因果关系

Agent 执行可能跨 Queue、SubAgent 和外部 callback。两条 event 到达日志系统的顺序，不一定是实际发生顺序。

例如，第一次 Tool Attempt 的 timeout 先到达，外部服务稍后才回传“读取已完成”。如果只按 ingested_at 排序，分析可能把 callback 误认为 retry 之后发生的新动作。

因此，需要显式保存关系，而不是事后猜测：

Task task_report_7
  └─ Run run_12
       └─ Model Turn model_turn_3
            └─ Tool Execution tool_exec_42
                 ├─ Attempt attempt_1
                 └─ Attempt attempt_2

Artifact report_7
  ← derived from file_17@v3
  ← produced for task_report_7

时间戳仍然用于计算等待和延迟，但稳定 ID、causality edge 与 Artifact lineage 才负责表达“谁触发了谁”和“结果依赖什么”。

一个 Event Stream 不应直接充当所有指标

执行系统可以持续写入 event，记录 Attempt started、timeout、retry scheduled、Model Turn completed 和 Run completed。分析层则应根据问题派生不同 grain 的事实：

分析问题合适的 Grain
下游服务单次请求是否稳定一行一个 Tool Attempt
获准执行的 Tool 动作最终是否完成一行一个 Tool Execution
模型调用的 token 与 latency一行一个 Model Turn
一次 Agent Loop 怎样结束一行一个 terminal Run
用户目标最终是否完成一行一个 Task outcome
最终内容依赖哪些输入一行一条 Artifact lineage edge

把这些 grain 全塞进“一行一个 Run”的宽表，会产生大量嵌套数组，也无法表达跨 Run Task；直接拿 raw event 做 dashboard，则会让每个查询重复处理 retry、迟到和去重。

更稳妥的做法是让 source event 保留过程，再按稳定 grain 幂等地产生分析事实。同一条底层事件可以进入多个派生模型，但每个模型仍需保留自己的 grain，不能在所有计算中都把它当成同一种记录。

指标必须把分母写清楚

“Tool 成功率”本身不是完整指标。它至少可能表示：

successful attempts / all terminal attempts
successful tool executions / all terminal tool executions
successful runs using this tool / all terminal runs using this tool
successful tasks using this tool / all terminal tasks using this tool

第一次 Attempt timeout、第二次才确认成功时，Attempt success rate 是 50%，Tool Execution 仍然算成功。这正是系统需要的信息：逻辑动作最终被确认完成，但底层请求没有在时限内返回可确认结果。

Latency 和 cost 也一样。Run 耗时覆盖一次 Agent Loop 内的 Model Turn、Tool Execution、retry backoff 和等待；Task 的端到端耗时还可能跨越多个 Run 与后台 Job。如果只保存最终总数，就无法判断时间和成本消耗在哪一层；如果只保存 Attempt，又无法回答用户目标总共付出了多少代价。

所以聚合必须沿显式关系向上进行，而不是把某张表里最容易相加的数字当成答案。

Artifact 让“成功”连接到实际结果

Run 状态为 succeeded，只说明本次 Agent Loop 正常结束，不一定意味着用户拿到了正确产物。报告可能仍在后台转换，也可能引用了旧文件版本，或者在生成后上传失败。

将 Artifact 作为独立对象，并记录它服务于哪个 Task、由哪个 Run 或 Job 产生、读取了哪些 source version，可以回答：

  • 最终报告是否真的存在并已交付。
  • 它使用的是 file_17 的哪个版本。
  • 重跑后产生的是新 Artifact，还是覆盖旧版本。
  • 一条错误来源影响了哪些下游结果。

Task owner 应根据这些证据判断用户目标是否完成，而不是把 Run 或 Job 的 succeeded 直接向上复制。这类 lineage 只需要记录可观察的输入输出关系，不需要保存模型的隐藏推理过程。

回到问题

日志很多却无法调试，通常不是少记录了某个字段，而是不同粒度的事实被混在了一起。

把 Task、Run、Model Turn、Tool Execution、Attempt 和 Artifact 分开后，一次 retry 才能同时表达两件事：底层请求曾 timeout、结果一度未知，但逻辑 Tool Execution 最终确认成功。Run 是否正常结束、用户 Task 是否真正交付，则继续由各自的证据判断。

Agent Activity 建模的起点不是一张覆盖所有场景的宽表，而是先确定每条记录代表什么。

后续问题

  • Task、Run、Model Turn、Tool Execution 与后台 Job 的状态和 retry unit 应怎样定义。
  • Event log、current snapshot 与 analytics fact 应怎样派生和校验。
  • 跨服务 event 的 event time、sequence 与迟到数据怎样处理。
  • Token、Tool、Sandbox 和 Storage cost 怎样沿 causality 归因。
  • Trace、Eval dataset 与生产 bad case 应怎样关联同一组执行事实。
