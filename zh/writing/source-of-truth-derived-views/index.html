Agent Reliability 一：Source of Truth 与 Derived View 怎样分工

从下游报表修错出发，用 semantic owner、lineage 和 rebuild boundary 区分事实源与派生视图。

2026/07/12 阅读 次
ArchitectureData ModelingContractsSource of Truth

问题

假设一个任务系统已经把 terminal outcome 定义为跨系统 contract：它同时决定失败告警、自动重试、计费和报表口径。Task owner 新增了状态 cancelled_by_user，并规定用户主动取消不属于系统失败；但旧 event schema 只向下游发送原始 task.status，没有携带权威的 outcome_class。Warehouse 于是沿用旧逻辑，把所有非 succeeded 状态都归为 failed。

Dashboard 最先暴露问题：用户主动取消的任务突然被算成系统失败。最直接的修复是在查询里加一条判断：

CASE
  WHEN status = 'cancelled_by_user' THEN 'cancelled'
  WHEN status != 'succeeded' THEN 'failed'
  ELSE 'succeeded'
END

报表数字恢复正常了，但告警和 retry consumer 仍沿用旧规则；下个月新增 expired 时，几个下游又会各自解释一次。问题被看见的地方得到修补，权威分类没有进入传播 contract，consumer 对未知值的 catch-all 也没有改变。

这类故障需要先回答：哪一层拥有“这个状态在业务上意味着什么”的决定，其他层只是怎样读取和重组它。

最先发现错误的地方不一定拥有语义

Dashboard 拥有展示方式，却不一定拥有任务状态的业务定义。Warehouse 拥有分析模型，却不一定能决定一次取消是否算失败。Event stream 记录上游发出的变化，也不自动成为所有语义的 owner。

定位修复位置时，可以依次问四个问题：

  1. 哪个组件拥有让状态发生变化的合法 transition？
  2. 这个决定依据哪些当时可见的事实和 policy？
  3. 哪些下游只是复制、过滤、聚合或重新索引这个决定？
  4. 如果全部下游丢失，哪份记录足以确定性地重建它们？

在开场例子中，failure classification 同时影响告警、重试、计费和报表，不是 warehouse 私有的分析 bucket。Task owner 决定 cancelled_by_user 是合法终态，也拥有这份跨系统 outcome contract；Dashboard 只能看到已经产生的状态，无法补回当时的 actor、reason 和 transition rule。

因此，修复不应由“谁先报警”决定，而应由 semantic ownership 决定。

Source of Truth 是决定权，不是唯一副本

Source of Truth 经常被误解成“整个系统只能保存一份数据”。分布式系统当然会有数据库行、event、cache、search index、warehouse fact 和 dashboard aggregate 等多份表示。

真正需要唯一的是：同一个语义判断最终由谁负责。

如果下游只需要当前状态，Task owner 可以把 transition 持久化为 current state；如果计费、审计或 warehouse 需要重建历史，owner 还必须保留覆盖目标时间范围的 version history、correction record 或 immutable event。存储形式可以不同，但只有保留了目标视图所需的事实范围，记录才足以成为对应判断的事实源：

  • 只有权威 owner 能提交合法状态变化。
  • 每次决定具有稳定 identity、version 或 sequence。
  • 记录保留做出判断所需的最小 provenance。
  • 并发更新和 retry 不会产生互相矛盾的 current result。
  • 下游能够识别自己消费的是哪个 schema/version。

这并不意味着一个系统只有一个全局 Source of Truth。Task lifecycle、用户授权、Artifact 内容和部署意图通常由不同 owner 决定。把所有事实硬塞进一个数据库，并不会自动产生统一语义。

Derived View 可以改变形状，不能重新发明事实

Derived View 为读取需求服务，因此可以做很多 Source of Truth 不适合做的事情：

  • 把 normalized records 去规范化成宽表。
  • 按日期、tenant 或状态聚合。
  • 为全文检索建立倒排索引。
  • 把 event history 投影成 current snapshot。
  • 为 UI 生成低延迟 cache。

边界在于：变换规则必须可以解释，并且不能悄悄创造一个本应由上游决定的新业务含义。

例如，dashboard 可以把上游已经定义的 outcome_class = cancelled 按周聚合；它不应仅凭 status != succeeded 自行推断 outcome_class = failed。后一条逻辑不是展示格式，而是在创造新的业务分类。

如果下游确实需要一个上游没有的分析概念，应先判断它是否只服务分析。如果“首次响应是否超过 30 秒”是报表自己的 SLA bucket，warehouse 可以拥有这条派生规则，并记录 rule version；如果“用户取消是否算任务失败”会影响告警、重试和计费，它就应回到更靠近 Task owner 的 contract。

Lineage 让每个视图知道自己从哪里来

一份 Derived View 至少要能回答：输入是什么、使用了哪版规则、处理到哪里、能否重建。

Task owner
  task_17 outcome_class=cancelled version=8
        ↓ event schema v3
Event stream
        ↓ warehouse transform outcome_rule v5
Task outcome fact
        ↓ dashboard query v2
Failure-rate panel

这条 lineage 不要求所有系统共享同一 transaction。它要求每一跳保留足够的 identity 和版本，使错误可以被定位：

  • 是上游提交了错误 outcome。
  • 是 event producer 使用了旧 schema。
  • 是 warehouse transform 漏掉新枚举。
  • 还是 dashboard 读了过期 projection。

没有 lineage 时，下游只看到一个错误数字，修复者很容易在最近的一层覆盖它；有了 lineage，repair location 才能沿依赖关系回到真正发生偏差的边界。

修复要先补齐 Owner Contract，再重建 View

开场中，Task owner 已经把 cancelled_by_user 定义为 outcome_class = cancelled，只是旧 event schema 没有携带这个字段。安全修复可以分成六步：

  1. 在 Task owner 的 contract 中明确 outcome 定义和 schema version。
  2. 让新的 transition/event 携带权威 outcome_class，而不是只发原始 status 让每个 consumer 猜。
  3. 让 consumer 遇到未知枚举时进入 unknown、拒绝处理或显式降级，不能用 catch-all 把它归为 failure。
  4. 为历史记录执行可重复 backfill，记录输入范围和 rule version。
  5. 从修正后的 event，或保留了所需历史版本的 owner snapshot，重建 warehouse fact。
  6. 删除 dashboard 中临时的语义补丁，让它只负责展示和聚合。

Backfill 不是随意改历史。它需要区分两种情况：

  • 当时的事实正确，只是派生规则有 bug：用同一 source version 重新计算。
  • 上游事实本身被更正：产生新的 version 或 correction record，并保留旧值的 provenance。

Derived View 应该允许幂等重建。若只能手工改最终数字，却无法从同一输入再次得到相同结果，它仍然没有恢复 contract。

Reconciliation 处理事实正确但视图落后的情况

并不是每次不一致都需要修改业务语义。也可能 Source of Truth 已经正确，某个 projector 因 timeout 或漏消费而落后。

此时 repair location 就在派生层：比较 source version/sequence 与 projection cursor，重新处理缺失输入，并用幂等 upsert 收敛视图。修复的是“视图没有跟上”，不是重新决定任务结果。

这也是 rebuild 与 reconciliation 的区别：rebuild 通常从一个可信起点重新生成较大范围的数据；reconciliation 持续比较 desired/authoritative state 与 observed view，修复局部 drift。两者都依赖清楚的 Source of Truth 和确定性派生规则。

Agent Runtime 四：让 Event Log 成为事实源 展开了 Session Event Log 与 projection 的具体协议。本文关注的是更通用的判断方法：先找 semantic owner，再决定在哪一层重放或修复。

Contract 演进不能只改 Producer

开场中的根因并不只是 warehouse 少写一个 WHEN，而是两个独立缺口：传播 contract 只暴露原始 status，没有版本化表达 owner 已经定义的 outcome semantics；consumer 又用 status != succeeded 这样的 catch-all 解释未知值。只修其中一个，下一次枚举演进仍可能产生错误分类。

Contract 演进至少要说明：

  • 新字段或枚举的业务含义。
  • producer 从哪个版本开始提供。
  • consumer 遇到未知值时是保留、拒绝还是降级。
  • 历史数据是否 backfill，以及如何区分当时事实与后续更正。
  • 旧规则何时可以删除。

这比在每个下游增加兼容分支更慢，却把变化成本放回拥有语义的边界。后续新增 expired 时，producer 和 consumer 可以按版本 contract 演进，而不是再次散落五套推断。

回到问题

Dashboard 最先发现“用户取消被算成失败”，不代表 Dashboard 应该拥有取消的业务定义。

沿 lineage 回看，这个例子中的 Task owner 拥有合法 transition，以及同时影响告警、重试、计费和报表的 outcome semantics。正确修复是让 owner contract 明确 cancelled_by_user → cancelled，把这个决定以可版本化记录传播，要求 consumer 安全处理未知值，再 backfill 和 rebuild 下游视图；Dashboard 只负责按已经定义的 outcome 聚合。

Source of Truth 与 Derived View 的分工，不是禁止复制数据，而是让每个语义判断只有一个明确 owner，让其他副本可以解释、重建并在 drift 后收敛。
