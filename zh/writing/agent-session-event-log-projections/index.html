Agent Runtime 四：让 Event Log 成为事实源

用按序追加的 Session Event Log 统一执行事实，让消息、Run 状态和实时事件成为可重建的投影。

问题

假设 Agent 已经生成最终回复：“报告已经完成。”结束这次执行时，系统需要让同一个结果反映到三个地方：

  1. 在 Run 表中把这次 Agent Loop 标记为 succeeded。
  2. 把最终回复写进用户刷新页面后会读取的消息列表。
  3. 向当前打开的浏览器发送 run.completed 实时通知。

这三条写路径彼此独立，不保证按列表顺序完成。现在发生了下面这条时间线：

T1  Run 状态更新为 succeeded
T2  实时通道发送 run.completed
T3  保存最终 assistant message 时数据库写入失败

系统留下的结果是：

后台 Run 状态    succeeded
消息列表          没有“报告已经完成”这条回复
当前浏览器        收到过 run.completed

用户在当前页面可能短暂看到“已完成”，但刷新以后，实时通知已经过去，消息列表里又没有最终回复。后台只看到 Run 已经成功，也不会自动重新执行。此时系统无法回答一个很简单的问题：最终回复究竟有没有被可靠保存？

问题不只是给消息写入加一次 retry。真正的问题是：同一个执行结果被分别写进 Run 状态、消息列表和实时通知，任何一步失败后，都没有一份统一记录可以用来修复另外两份数据。

多写几张表不会自动保持一致

一种常见实现是在 Runtime 结束时分别执行下面几次写入；这里的顺序与开场时间线一致，但真正的问题是它们不在同一个原子边界里：

update_run_state("succeeded")
publish_realtime_event("run.completed")
insert_assistant_message(final_text)
increment_success_metric()

只要这些操作不在同一个原子边界里，进程就可能在任意两步之间退出。即使 Run 状态和消息列表位于同一数据库，可以放进一个 transaction，Redis、WebSocket 和 metric sink 也通常不在这个 transaction 中。

更关键的是，它们服务的读取需求不同：

  • Run state 用于快速判断当前状态。
  • Message view 用于渲染对话。
  • Realtime signal 用于低延迟刷新界面。
  • Metric 用于聚合分析。

让每个写入都成为一份独立事实，会把一次执行变成多个需要互相对账的 Source of Truth。

先记录事实，再生成视图

更清晰的边界是：Runtime 只向同一条有稳定顺序的 Event Log 追加执行事实，其他数据由这些事实生成。

这里的 Projector 是读取 Event Log、再生成某种查询视图的后台程序；它生成的 Projection 则是消息列表、Run 状态等读取视图。同一份事实可以被不同 Projector 按各自的读取需求解释。

一条最小事件可以包含：

{
  "session_id": "session_17",
  "seq": 42,
  "event_id": "event_9a2",
  "type": "assistant.message.completed",
  "run_id": "run_8",
  "model_turn_id": "model_turn_6",
  "payload": {
    "message_id": "message_31",
    "content_ref": "content_31"
  },
  "occurred_at": "2026-07-17T08:30:00Z",
  "schema_version": 2
}

seq 表示这个 Session 内已经提交的顺序，event_id 表示事件身份。两者不要混用：全局 UUID 可以去重，却不能告诉 projector 下一条该读什么；sequence 可以建立读取位置，但仍需要明确自己的作用域。

Run 的第一条生命周期事实还应把执行契约接进来，例如 run.created(run_8, runspec_ref, fingerprint)。Event Log 保存 Run 已按哪份契约开始，RunSpec 则保持为不可变、可独立读取的契约；Run snapshot 只是之后由这些事实派生的当前状态。

示例里的 content_ref 也必须指向已经持久化的内容。若内容和 event 位于同一数据库，应在同一 transaction 中提交；若跨越存储边界，就需要先写入不可变内容，再追加引用它的 event，并为失败清理保留 reconciliation。Event Log 不能通过引用一个尚未提交的对象来获得事实地位。

同一 Event Log 可以重建 Run、消息与通知

重新看最终回复丢失的例子。Runtime 不再让 Run 状态、消息列表和实时通知各自记录结果，而是先追加两条事件：

seq 41  assistant.message.completed(message_31)
seq 42  run.completed(run_8)

下面先讨论两条事件都已经提交、只有 projection 落后的情况。如果 Runtime 在两次 append 之间退出，应从 Event Log 中最后一条已提交的事件继续完成收尾，而不是重新调用模型；也可以让两条事件作为一个原子 batch 提交。

这里还需要说明 Cursor：它是每个 Projector 的读取进度。例如 cursor 为 40，表示它已经处理完 seq 40，下一条应该读取 seq 41。

假设故障后的状态是：

Event Log               已经写到 seq 42
Run-state projector     已经处理到 seq 42
Message projector       只处理到 seq 40

这表示 Agent 执行本身已经完成，只是消息列表落后了两条事件。恢复时不需要再次调用模型，也不需要把 Run 改回 running。Message projector 从 cursor 40 继续读取即可：

  1. 读到 seq 41，把 message_31 写入消息列表，再把 cursor 更新为 41。
  2. 读到 seq 42，发现它只影响 Run 状态，于是不修改消息列表，只把 cursor 更新为 42。

第一步最好在同一个数据库 transaction 中完成：

开始 transaction
→ 以 message_id 为唯一键写入 message_31
→ 把 Message projector 的 cursor 更新为 41
→ 提交 transaction

如果提交前崩溃，消息和 cursor 都不会生效，重启后重新处理 seq 41；如果提交后崩溃，两者都已经生效，重启后从 seq 42 继续。这样不会出现“消息写入了，但 cursor 仍是 40”的中间状态。

这个例子还假设同一个 (projection, session) 的事件按顺序由一个有效 owner 处理。可以给 partition/session 分配带 lease 与 fencing token 的单一 projector owner，也可以让 cursor 使用单调 CAS，例如只允许 UPDATE ... WHERE cursor = 40 把它推进到 41。CAS 方案中，projection mutation 和 cursor 更新必须位于同一个 transaction；否则慢 replica 可能先把旧状态写进视图，随后才发现 cursor CAS 失败。若两者跨存储，就应保留单一 fenced owner，或让每条视图记录也用 event seq 做 version check。无论采用哪种方式，慢 replica 都不能把 42 写回 41，seq 42 也不能越过尚未提交的 seq 41。

如果消息列表和 cursor 位于不同的存储，无法放进同一个 transaction，就必须允许同一事件被重复处理。处理顺序应固定为：

  1. 先按 message_id 写入消息；如果消息已经存在，还要确认保存的 content_ref 与当前事件一致。
  2. 确认消息写入成功后，才把 cursor 从 40 推进到 41。
  3. 如果消息写入结果未知，不更新 cursor，重启后再次处理 seq 41。
  4. 如果 cursor 更新结果未知，重启后重新读取它：仍为 40 就再次处理 seq 41，已经是 41 就从 seq 42 继续。

第一次处理会插入 message_31；如果消息已经写入、cursor 却没有推进，第二次处理只会确认同一条消息已经存在，然后继续推进 cursor。唯一键防止产生两条消息，固定的处理顺序防止 cursor 越过尚未保存的消息。这就是这里所说的幂等写入。

Event Log 提供的是“可以重新读取事件”，projector 自己仍要保证“重复读取不会产生重复结果”。

Append 边界必须比 projector 更可信

“Event Log 是事实源”只有在 append 自身可靠时才成立。对同一 Session，并发 writer 必须获得明确顺序，不能先各自在内存里计算 seq + 1 再写入。

一种概念性数据库操作是：

UPDATE sessions
SET next_seq = next_seq + 1
WHERE session_id = :session_id
RETURNING next_seq;

INSERT INTO session_events(session_id, seq, event_id, type, payload)
VALUES (:session_id, :seq, :event_id, :type, :payload);

分配 sequence 与插入事件需要处于同一原子边界，并由 unique constraint 约束 (session_id, seq) 和 event_id。实际实现也可以使用支持有序 append 的日志系统；关键是顺序由事实存储决定，而不是由某个短命 worker 猜测。

但“已经排好顺序”不等于“事件就是合法事实”。Run 的 lifecycle event 只能由权威的 transition owner 提交：它需要在同一个原子边界内校验 expected state/version、writer 的 fencing token、合法状态转移和“终态只能收敛一次”等 invariant，然后才分配 seq 并 append。否则取消和完成两个 writer 仍可能依次写入 run.cancelled 与 run.completed，把互相矛盾的结果都留在事实源中。

请求与已经成立的事实也要分开。例如用户点击取消时可以先写 run.cancel.requested；只有当前 owner 完成竞态裁决后，才能追加 run.cancelled 或 run.completed。Projector 可以拒绝旧事件覆盖新视图，但不能负责事后决定事实是否合法。

event_id 必须在第一次 append 前稳定分配，并在 append timeout 或响应丢失后的 retry 中复用。若同一个 ID 已存在，append 端应核对完整不可变 event envelope 的 digest：包括 Session、Run、Model Turn、type、schema version、payload 和内容引用，只排除服务端分配的 seq、提交时间等字段。内容一致才返回原 seq，任何作用域或内容不同都返回 conflict。提交结果未知时先按原 ID 查询，不能生成新 ID 再追加一次。

外部副作用仍然不在这个 transaction 中。Tool 已经写入外部系统但 Runtime 没有确认结果时，应记录“结果未知”或 effect identity，之后通过幂等查询与 reconciliation 收敛，而不是编造一条成功事件。

Projection 不是低一等的数据

消息列表和 Run snapshot 虽然不是事实源，却仍然是正式产品接口。Projection 的意义不是把一致性问题推给异步任务，而是允许每个读取模型拥有清晰的延迟和修复策略。

Projection优化目标可接受的恢复方式
Message view按对话顺序读取内容从 cursor 重放并幂等 upsert
Run snapshot快速读取当前状态应用状态转移并拒绝非法倒退
Realtime signal尽快提醒在线客户端可以丢失，客户端按 cursor 补齐
Metrics聚合趋势批量重放，明确去重 grain
Audit view解释谁在何时做了什么保留 identity 与 provenance

如果产品要求“提交事件后立刻读到新消息”，可以同步更新核心 projection，或者提供 read-your-write overlay。但这是一项读取一致性选择，不应让 message row 重新变成另一份独立事实。

回到问题

开场中的矛盾来自三条写入路径都在声明结果。把 Runtime 的持久化边界收敛为按序追加的 Session Event Log 后，Run state、消息、实时通知和指标有了共同输入。

某个 projection 失败时，系统修复的是读取视图，而不是重新执行 Agent。同一个逻辑事实以稳定 event_id 幂等提交，视图可以重复生成；这才是可恢复性的来源。

后续问题

  • Durable Event 进入 SSE、WebSocket 或 Redis Pub/Sub 后，客户端怎样断线补齐。
  • Checkpoint 应引用哪些 sequence，恢复时怎样结合外部副作用进行 reconciliation。
  • 多个 writer 竞争同一 Session 时，怎样用 ownership、version 或 fencing 保护 append。
  • Event schema 升级、projection rebuild、snapshot 与日志保留周期怎样协同。
