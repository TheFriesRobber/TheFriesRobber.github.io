Agent 10：执行 Journal 与 Checkpoint 如何共同支撑恢复

用权威执行 Journal、幂等 Projection 和带 cursor 的 Checkpoint 恢复 Agent 状态，而不重复未知副作用。

问题

Agent 创建报告文件后准备生成摘要。文件服务已经返回 report-42，但 worker 在保存 Tool Result 前退出。此时 Run 表仍是 running，Session message 中没有文件结果，在线客户端却可能已经看见过一条 tool_execution_end signal。

如果恢复器只相信 Run 表，它会认为工作仍在进行；只相信 messages，它会再次创建文件；只相信客户端 signal，它又无法证明 signal 对应的事实已经持久化。

恢复需要一份权威执行 Journal 记录已经提交的事实，再用 Projection 生成 Run、message 和客户端读取视图。Checkpoint 不是另一份事实源，而是指向 Journal 中稳定位置、并声明恢复前必须核对哪些外部条件的协议。

Journal 先提交事实，Projection 再服务读取

一次执行结果常同时更新 Run 状态、message view、实时通知和 metric。如果它们各自直接写入结果，任何中途故障都会留下多个互相矛盾的 Source of Truth。

更清楚的边界是：

authoritative execution journal
├─ Run-state projection
├─ Message projection
├─ Durable client feed
└─ Metric/Audit projection

Journal 保存“已经提交了什么”；Projection 根据读取需求解释同一组事实。客户端 feed 可以持久化，但它仍是 Journal 的读取投影，不与 Journal 竞争 Tool outcome 的所有权。SSE/WebSocket 则只发送 feed 中新事件的低延迟 signal。

Session Tree 继续保存分支化的对话历史和 Context-visible path。它可以消费已确认的 message projection，却不替代 operation、Attempt 和 effect evidence 的 Journal。

Effect Intent 必须先提交，再允许外部调用

Journal 不只记录完成结果。任何可能产生外部副作用的路径都必须先分配 operation、Attempt 与稳定 effect key，把 intent durable append 并确认提交，然后才允许 dispatch：

allocate operation / Attempt / effect key
→ append tool.effect.intent
→ commit Journal event
→ dispatch external call with the same effect key
→ append terminal outcome or unknown evidence

如果 intent commit 失败，Runtime 不得发送调用。只有所有 effect path 都执行这道 gate 时，“Journal 中没有 intent”才能证明该 Runtime 不应该已经 dispatch；绕过 gate 的 handler 或基础设施副作用会破坏这个证明边界。

恢复中的 replay 是重新应用已经记录的事实，不是重新调用模型或 Tool。Intent 没有 terminal outcome 时进入 reconciliation；它本身不是一次 retry 指令。

Sequence 与 Event Identity 解决不同问题

一条概念性 Journal event 可以是：

stream_ref: session:17
sequence: 74
event_id: event_9a2
type: tool.effect.succeeded
run_id: run_8
tool_execution_id: tool_exec_12
attempt_id: attempt_1
payload:
  effect_ref: report-42
schema_revision: execution-event.v3

sequence 表示某个 stream 内已经提交的顺序；event_id 表示逻辑事件身份。全局 UUID 可以去重，却不能告诉 projector 下一条该读什么；裸 sequence 也不能跨 stream 使用。

同一逻辑 append 因 timeout 重试时必须复用 event_id。若该 ID 已存在，Journal 比较不可变 envelope 的 digest：内容相同就返回原 sequence，内容不同就报 conflict。不能生成新 ID 再追加一遍。

分配 sequence、校验合法 transition 和写入 event 应位于同一个权威提交边界。取消请求可以记录为 run.cancel.requested；只有当前 transition owner 完成竞态裁决后，才能写入 run.cancelled 或 run.completed。Event Log 不能先接受互相冲突的终态，再把决定推给 projector。

Projection 必须允许重复消费

Projector 保存自己的 scoped cursor。假设 Journal 已到 sequence 74，而 message projector 只处理到 72：

Journal cursor: 74
Message projection cursor: 72

Projector 从 73 继续，并按稳定业务 ID 幂等更新 view。若 projection row 与 cursor 在同一数据库，二者应在同一 transaction 中提交；若跨存储，就先幂等写 view，再推进 cursor。写入结果未知时不跳过该 event，重启后重复消费。

这提供的是 at-least-once projection，不是端到端 exactly-once。幂等 key、单调 cursor、CAS 或 fenced projector owner 共同保证慢 worker 不能把新视图倒退。

因此 message projection 落后只需要 replay Journal，不需要重新调用模型或 Tool。

Checkpoint 记录恢复起点与核对条件

Journal 可以从头重建状态，但长 Run 通常需要 Snapshot 加速。Checkpoint 把 Snapshot、Journal cursor 和恢复条件绑定起来：

checkpoint_revision: 4
run_id: run_8
run_contract_ref: runspec-8@3
resume_contract_revision: report-agent.v3
snapshot_ref: snapshot_73
event_cursor:
  stream_ref: session:17
  sequence: 73
resume_at: reconcile_create_report
pending_effects:
  - operation_id: op-17
    attempt_id: attempt_1
    status: dispatched
    provider: file-service
    effect_key: run_8:create_report:v1
    idempotency_scope: create-report
    idempotency_expires_at: 2026-07-28T09:00:00Z
    effect_ref: null
waiting: null
budget:
  model_turns_used: 6

Checkpoint 回答“从哪里、按什么条件恢复”，不是“外部世界现在是什么”。snapshot_ref 必须明确覆盖到同一 stream 的 cursor；若没有 Snapshot，就从 Journal 起点重放，不能既缺少基础状态又从中间开始。

run_contract_ref 与 resume_contract_revision 分别固定原执行上限和恢复语义。Schema 能被读取，不代表新代码仍理解同一个 resume_at；存储格式和恢复状态机都需要版本兼容判断。

Pending Effect 先 Reconcile，再决定 Retry

恢复 run_8 时，步骤是：

load Checkpoint and referenced Run contract
→ validate Snapshot covers cursor 73
→ replay Journal events after 73
→ reconcile every non-terminal pending effect
→ revalidate authorization, Artifact, waiting condition, and budget
→ construct new Runtime state at the next legal boundary

如果文件服务成功后，Runtime 已经把 sequence 74 的 tool.effect.succeeded(report-42) 写入 Journal，只是没来得及更新 Checkpoint，replay 会吸收该事实，不再创建文件。

如果外部文件已创建，但 terminal event 也没有提交，Checkpoint 只看到 dispatched。恢复器先按 provider、稳定 effect key、idempotency scope 或外部业务引用查询。只有外部系统明确未执行，或 idempotency_expires_at 尚未到期且同一 key 仍由下游保证收敛时，才允许创建新 Attempt；无法查询、scope 不匹配或窗口已过期时，保持 unknown。

Checkpoint 因而不能代替外部幂等或 reconciliation。它只确保恢复器知道哪一个 operation 尚未得到结论。

Waiting Condition 与 Crash 使用同一恢复入口

主动 pause 也可以写入 waiting condition：

waiting:
  kind: confirmation
  request_id: confirm_9
  action_ref: delete:file-7@revision-3
  expires_at: 2026-07-28T09:00:00Z

Runtime 先提交 waiting event 和 Checkpoint，再释放 worker。Resume 时重新校验 action、resource revision、identity、expiry 和 current authorization，不能只检查“有人点击过确认”。

Crash 与 pause 的触发方式不同，恢复契约相同：都从最后一个已提交的 cursor 重建，再验证当前外部条件。Provider stream、socket、数据库连接和进程内 task 不进入 Checkpoint；它们在恢复时重新创建。

回到问题

开场中的 Run 表、Session messages 和客户端 signal 互相矛盾，是因为三种读取形式都在尝试声明执行事实。正确恢复路径是：

  1. Tool intent 先 durable commit，才允许 dispatch；Attempt 和 terminal/unknown outcome 继续进入同一权威 Journal；
  2. Run、message、client feed 与 metric 由幂等 projector 生成；
  3. Checkpoint 绑定 Snapshot、scoped event cursor、原 Run contract、pending effect、waiting condition 和恢复 revision；
  4. 恢复先 replay cursor 之后的事实，再 reconcile 未终结 effect；
  5. 只有证据允许时才产生新 Attempt；
  6. 最后生成新的 turn snapshot，客户端再从 durable feed cursor 补展示事件。

Journal 证明发生过什么，Checkpoint 说明从哪里继续，Session Tree 组织模型可见历史，客户端 feed 负责重建界面。让四者各守住自己的 owner，恢复才不会重新执行一个已经发生、却尚未被当前 view 看见的副作用。
