LLM Infra 02：延迟、吞吐与成本为什么不能分别优化

区分 TTFT、TPOT、端到端延迟、throughput、goodput 与单位 Token 成本，把性能目标改写成带 workload 和质量约束的服务决策。

问题

一次 batching 调整把 aggregate tokens/s 提高了。仪表盘显示吞吐变好，交互用户等待首 Token 的时间却更长，部分长请求还在完成前被客户端取消。

“吞吐提高”与“体验变差”可以同时成立，因为它们观察的是不同结果。前者数了 Runtime 完成多少 Token，后者关心请求是否在给定期限内交付了有用输出。

这篇文章要回答的是：TTFT、TPOT、端到端延迟、throughput 和成本怎样组合成一个可执行的推理 SLO，而不是五个互相争夺方向的目标。

先把一次流式请求拆开

从客户端发出请求到收到完整响应，至少经过以下时间：

arrival
  → gateway / scheduler queue
  → prefill
  → first output token
  → repeated decode + streaming delivery
  → completion or cancellation

常用指标对应不同区间：

指标回答的问题
TTFT用户多久看到第一段有效输出
TPOT / ITL首 Token 之后，输出推进得是否平滑
E2E latency请求从发出到完成一共用了多久
aggregate throughput整个系统在窗口内处理了多少请求或 Token
per-user token rate单个请求感受到的生成速度

指标定义还必须固定测量边界。AIPerf 的 TTFT 从客户端发出请求算到收到第一个非空响应 chunk，因此包含网络、排队和 Prompt 处理；一个 chunk 可能包含多个 Token。vLLM 当前的 per-request time_to_first_token_ms 从请求被 scheduler 接纳后开始，不包含 scheduler queue。两者都可以用于诊断，但不能在没有注明边界时直接比较。

这也是为什么“SLO 是 TTFT 小于 1 秒”仍不完整：从哪里开始计时？第一段 reasoning chunk 算不算有效输出？是否包含 gateway 和网络？答案必须写进契约。

Batching 把吞吐收益换成等待

Batching 让一次模型执行同时推进更多 Token，通常有利于聚合吞吐。但请求需要等待足够的同伴或调度机会，Batch 中不同阶段和长度的 sequence 也会互相影响。

用一个合成调度结果说明这种交换：

配置Aggregate output tokens/s交互请求 TTFT 达标率已开始后取消的请求
A1,00098%1%
B1,25082%9%

这些数字是概念输入，不是实测结果。它们只说明：如果配置 B 以更长等待换来更大 Batch，那么 raw throughput 可以提高，同时 TTFT 达标率下降。被取消请求已经消耗的 Prefill 或 Decode 仍会进入吞吐计数，却没有形成用户认可的完成。

因此，吞吐不应该脱离 deadline、取消结果和 workload class 单独最大化。

Goodput 给吞吐加上交付约束

主流 serving Benchmark 通常把 request goodput 定义为：同时满足全部 per-request latency SLO 的成功请求数除以测试时长。本文还需要把质量和输出协议加入产品判断，因此把这个扩展口径明确称为 application goodput，避免冒充工具自带指标。

概念上：

application goodput =
  同时满足输入/输出、质量、TTFT、TPOT 和完成条件的请求数
  / 观测窗口

DistServe 也采用基于 TTFT 与 TPOT SLO attainment 的 request goodput 来比较部署方案。重要的不是复用某篇论文的阈值，而是采用同一思想：每个请求先经过联合 pass predicate，再把合格请求聚合成有效容量。

这会改变对前述配置的判断。配置 B 的 raw throughput 更高，但如果主要 workload 是交互请求，它可能只是把等待和取消产生的无效工作也算进了收益。若 workload 是没有严格 TTFT 的离线 Batch，相同配置又可能合理。

Goodput 必须始终带限定词：

  • 哪个 workload envelope；
  • 哪组 TTFT、TPOT 或 completion deadline；
  • 需要达到的 SLO attainment；
  • 哪个模型质量和输出协议；
  • 失败、取消与 retry 怎样计数。

离开这些条件，“goodput 更高”同样会退化成口号。

成本必须跟有效交付使用同一分母

只看 GPU 小时，会把空转、排队、取消后的继续执行和失败 retry 混在一起。只看单位输出 Token 成本，又可能奖励更短甚至被截断的输出。

更可用的成本视图是把资源事实与交付结果分开：

资源事实：
  input_tokens
  output_tokens_computed
  output_tokens_delivered
  execution_time
  cancelled_work
  retry_attempts

交付结果：
  met_ttft
  met_tpot
  completed
  quality_gate_passed

随后再根据决策选择分母：

  • 规划集群成本时，看满足 SLO 的 requests/GPU-hour。
  • 优化 Decode 时，看合格 output tokens/GPU-hour。
  • 分析浪费时，看 cancelled 或 failed work 占总计算的比例。

这样，降低成本不再等于“让 GPU 更忙”，而是减少每次合格交付所消耗的资源。

不同 workload 需要不同约束

上一篇建立的 workload envelope 在这里开始发挥作用。

Workload class首要约束次要约束不应被误用的指标
交互对话TTFT、TPOT、取消率单位合格请求成本只看 aggregate tokens/s
异步长生成completion deadline、成功率单位合格输出成本过度强调首 Token
离线 Batch窗口内完成量、失败重跑GPU-hour、质量把单请求 P95 当唯一目标

这不是三套互不相干的监控。它们共享 Token、execution 和 outcome facts，但使用不同的约束判断是否形成 goodput。

一份可执行的 SLO decision record 可以写成：

workload_class: interactive
workload_fingerprint: wl_7fd2
latency:
  per_request_lte_ms:
    ttft: 1500
    tpot: 80
outcome:
  completion_rate_gte: 0.99
  cancelled_after_start_lte: 0.01
quality:
  evaluation_suite: chat-contract-v3
capacity_metric:
  name: application_goodput_rps
  good_request_fraction_gte: 0.95
diagnostics:
  report_percentiles: [p50, p95, p99]

字段是概念示例，阈值必须由具体产品要求和测量结果决定。每个 attempted request 都要同时判断 TTFT、TPOT、completion 与 quality；application_goodput_rps = good_request_count / duration，good_request_fraction = good_request_count / attempted_request_count。P95/P99 继续作为诊断分布，但不能替代联合达标率。

回到问题

Batching 调整后的 tokens/s 上升，并不能单独证明服务变好。对于交互 workload，增加的 Token 如果来自更长排队、超时后仍继续的执行，或者没有满足质量和交付期限，它们不会形成 goodput。

正确的判断是把这次配置放进同一份 workload-specific contract：TTFT、TPOT、完成和质量条件是否仍然满足？满足条件的请求速率是否提高？每次合格交付的成本是否下降？

下一篇的 Benchmark 必须完整复现这些约束。否则即使跑出更多 tokens/s，也测不出容量规划真正需要的 service curve。
