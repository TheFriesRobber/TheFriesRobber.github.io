Agent 22：同一个文件为什么需要 Artifact identity 与 Workspace reference

用 Artifact identity、Workspace reference 和结构化修改前置条件建模文件的跨阶段生命周期。

2026/07/24 更新于 2026/07/27 阅读 次
Agent StateAgentArtifactsCode Editing

问题

用户上传 src/config.ts，Agent 在 Sandbox 中看到它位于 /tmp/input/config.ts。Runtime 重启后，同一路径被另一次 materialization 复用；Session 中保存的旧消息仍让模型修改 /tmp/input/config.ts。

Path 字符串没有说明它指向哪个上传、哪个 revision，也没有证明编辑结果来自用户最初的文件。即使修改成功，下载端仍无法回答这份内容的 lineage。

文件跨消息、Workspace 和存储流动时，需要分开三个对象：Artifact 提供跨系统稳定身份与版本，Workspace reference 解析某次执行环境中的位置，message reference 只向模型暴露受限句柄；每次 mutation 再用 revision 与验证 evidence 连接输入和输出。

Blob、Artifact 与 Path 回答不同问题

对象回答的问题Owner
Blob这些 bytes 存在哪里、content hash 是什么Object/blob store
Artifact这是哪个逻辑文件、哪个 revision、来源是什么Artifact service
Workspace object这次 Session 使用哪个 Artifact revisionWorkspace service
Path当前 Runtime 在哪里访问它Runtime/VFS
Message reference模型可以引用哪个受限对象Agent host

Blob 可以按内容去重，但相同 bytes 可能属于两个 tenant 或两个业务 Artifact；Artifact identity 不能仅由 hash 推导授权。反过来，同一个 Artifact 的 revision 变化后，path 可以保持不变，content hash 则变化。

Path 只在一个明确的 Workspace/Runtime binding 中有意义。把 /tmp/input/config.ts 写进长期 Session，不足以在恢复后重新定位原文件。

上传先形成稳定 Artifact Revision

一次上传可以形成：

artifact_id: artifact_17
revision: 1
owner_ref: tenant_3/user_7
blob_ref: sha256:abc...
media_type: text/typescript
source:
  kind: user_upload
  message_id: message_41

这是概念性 contract，不代表某个存储产品的现有 schema。Artifact service 拥有 revision 和 lineage；Blob store 只保存内容；Message 保存 artifact_17@1 的引用，而不是复制一条未来会失效的临时路径。

下载授权也依据当前 subject、Artifact owner 和 revision。拥有一个可猜测的 path、blob URL 或 content hash，不自动获得读取权限。

Materialize 把 Artifact 映射到 Workspace

Sandbox acquire 后，Workspace service 为当前 lease 解析：

workspace_id: ws_9
workspace_revision: 12
artifact: artifact_17@1
workspace_ref: wsobj_33
runtime_path: /workspace/inputs/config.ts
mount_mode: read_only
lease_generation: 6

模型只需要看到受限 message reference 或 Workspace path；Tool handler 则从可信 Context 获得 workspace_ref、expected Artifact revision 和 lease generation。

Runtime 重建时，不复用旧 path 作为身份。它重新解析 wsobj_33 → artifact_17@1，materialize 到新的本地路径，并确认 Workspace lease 与 revision。若 Artifact 已被删除、权限撤销或引用不兼容，恢复应失败，而不是根据文件名寻找近似对象。

需要修改时，Workspace service 不直接写这个只读 base object，而是在当前 lease 下创建 copy-on-write staging：

base_workspace_ref: wsobj_33
workspace_ref: wsobj_34
mount_mode: copy_on_write
lease_generation: 6

后续 mutation、diff validation 和 publish 都引用 wsobj_34；wsobj_33 继续证明输入来自 artifact_17@1。

Mutation 先声明输入前置条件

Agent 要修改源代码时，Tool proposal 可以描述目标 symbol 和 patch，但可信执行层应绑定：

mutation_id: edit_52
input_artifact: artifact_17@1
base_workspace_ref: wsobj_33
workspace_ref: wsobj_34
expected_file_revision: 1
allowed_scope: export function loadConfig

执行前检查 writable staging object、lease generation 与 base content 仍对应输入 revision 1。这只能证明当前编辑基于预期输入，不能证明 Artifact 的 current head 尚未被另一个 actor 推进。

普通数据文件可能只需要 revision/hash 前置条件。对于源代码，结构化 evidence 可以进一步缩小误改：

  • 解析前后的目标 symbol 是否仍存在；
  • patch 是否只触及允许范围；
  • AST precondition 是否匹配预期结构；
  • formatter、type checker 或静态检查结果；
  • 实际 diff 与 Tool Result。

AST-aware editing 不是所有 Artifact 的必需语义，也不能证明业务正确或代码安全。它只是这次 source mutation 的一类可验证 evidence；测试、Sandbox 和必要的人工确认仍有独立边界。

Publish 创建新 Revision，不覆盖 Lineage

修改通过约定检查后，Artifact service 发布 revision 2：

artifact_17@1
  → materialized as read-only wsobj_33
  → staged as copy-on-write wsobj_34
  → mutation edit_52
  → checks: parse pass, scope pass, typecheck pass
  → artifact_17@2

发布时由 Artifact service 对 current head 执行 expected_current_revision: 1 的 CAS，避免两个编辑都从 v1 派生后静默 last-write-wins。若 head 已经是 v2，本次编辑结果可以保留为明确 branch，但不能推进 current head；调用方必须重新读取或交给 merge owner。Workspace binding 与 lease 检查不能替代这个发布冲突协议。

Artifact Result 应包含稳定 reference、content checksum、lineage 和验证摘要。typecheck pass 只证明执行过的配置与范围内没有类型错误，不等于所有测试通过；未运行的检查不能出现在 evidence 中。

Temporary、Persistent 与 Published 不要混用

Workspace 内文件可以分为：

  • temporary：Runtime 结束后可丢弃；
  • persistent workspace：跨 Runtime 保留，但仍属于 Workspace；
  • published Artifact：具有稳定 identity、revision、owner 与下载 contract。

把临时 cache 自动发布会泄漏中间数据；把所有 Workspace 文件当成 Artifact 会制造大量无意义版本。只有需要跨边界引用、交付或形成 lineage 的结果才进入 publish。

Retention 与删除也沿 owner 分开：删除 Artifact 需要使授权引用和派生下载失效；清理 Runtime path 只删除 materialized copy；Blob 是否物理回收还取决于其他合法 reference 和 retention policy。

把开场文件走完

正确流程是：

upload config.ts
→ artifact_17@1
→ message refers to artifact_17@1
→ materialize as wsobj_33 under lease generation 6
→ create copy-on-write staging wsobj_34
→ edit with expected input revision 1
→ validate actual diff
→ publish artifact_17@2 with expected current head 1
→ download resolves artifact_17@2

Runtime 重启后，即使 /tmp/input/config.ts 被复用，旧 Session 仍通过 artifact_17@1 和只读 wsobj_33 重新解析，再为当前 lease 创建新的 staging object。若本地 path 指向其他内容，Workspace identity/revision 检查会拒绝 mutation；若另一个 actor 已推进 Artifact head，则 publish CAS 会拒绝覆盖。

回到问题

同一个 path 在两个 Runtime 中可以指向不同文件，同一个 Artifact 也可以在不同 Workspace 中使用不同 path。Path 因而只能是执行环境中的位置，不能承担跨 Session identity。

让上传先形成 Artifact revision，Message 和 Workspace 只保存受限 reference，编辑绑定 input revision、mutation scope 和实际验证 evidence，发布再对 current head 做 CAS，系统才能证明最终下载的 artifact_17@2 确实从用户上传的 v1 派生，而不是来自被复用的临时路径或对并发更新的静默覆盖。
