Agent 30：Budget、Quota 与 Backpressure 怎样协作

区分单 Run 预算、主体配额、瞬时限流和热点 backpressure，并让 admission 决策沿执行链传播。

问题

一个 Agent Run 的模型 token 没有超限，却连续创建十个 Child Run。每个 child 都申请 Sandbox、调用外部 Tool 并写 Artifact。全局 CPU 和 Queue lag 的平均值仍然健康，但这一个 tenant 已经占满某类 Sandbox，其他请求开始排队。

给父 Run 设置 max_tokens 没有阻止这次故障，因为 token 只是一种累计消耗；它既不是 Sandbox 并发，也不是 tenant 在时间窗口内的总配额，更不能反映某个 queue partition 的热点。

资源治理要让四类限制协作：Budget 约束一次执行，Quota 约束主体在窗口内的总量，Rate Limit/并发上限保护瞬时容量，Backpressure 则把下游饱和事实传回真正的 admission 边界。

这些单位不能混用。Context token budget 决定一轮模型能看到多少输入；财务预算可能用货币或计费单位；Sandbox capacity 则是并发和持续时间。把它们都叫 budget 会让 policy 无法解释。

Delegation 不能凭空生成新额度

父 Run 创建 Child Run 时，最危险的默认值是让 child 获得一套新的全局限制。这样父 Run 可以通过不断 spawn 绕过自身约束。

一份概念性 resource envelope 可以是：

{
  "run_id": "run_19",
  "remaining": {
    "model_tokens": 40000,
    "tool_calls": 30,
    "sandbox_seconds": 600
  },
  "concurrency": {
    "child_runs": 3,
    "sandboxes": 2
  },
  "deadline": "..."
}

创建 child 时，Runtime 可以：

  • reserve：从父级剩余额度中预留一部分，child 未使用部分再归还；
  • share：父子对同一计数器累计，但需要原子消费；
  • reject：无法给出安全 envelope 时拒绝 delegation。

不同资源适合不同策略。Token 和 Sandbox-seconds 是累计量；并发槽位是某一时刻的 lease；deadline 通常取父级与 child 要求的较小值。不能用一个通用加减法覆盖它们。

Admission 要发生在占用资源之前

如果先创建 Sandbox，再检查 quota，治理已经太晚。一个 admission decision 应在真正占用稀缺资源前消费：

request
→ validate identity and tenant
→ check Run budget
→ check subject/tenant quota
→ check rate and concurrency
→ consume downstream backpressure
→ reserve capacity
→ admit / delay / reject / degrade

Decision 应返回机器可读原因，例如 run_budget_exhausted、tenant_concurrency_limit 或 sandbox_pool_saturated。父 Run 据此停止、等待、缩小任务或向用户解释，而不是从 timeout 猜测。

Reservation 也需要生命周期。创建资源失败、请求取消、worker 崩溃或 lease 到期都只能触发 reconciliation：确认资源从未创建时才 release；资源已经创建时则恢复 activation 并进入 settlement。否则系统可能让未使用的预留吞掉容量，也可能错误退回已经消耗的额度。

Reservation 需要稳定 identity 与条件结算

如果 admission timeout 后直接重新 reserve，同一个 Child Run 可能占用两份额度；如果 cleanup 根据 timeout 直接 refund，又可能归还已经被 Sandbox 消耗的容量。Reservation 因而不能只是计数器上的一次减法。

可信 admission owner 为同一个 logical spawn/operation 分配稳定 identity，同一意图的 retry 必须复用它：

reservation_id: reserve_spawn_81
operation_id: spawn_request_81
subject: tenant_3
resource:
  kind: sandbox_seconds
  amount: 120
state: held
owner_generation: 6
expires_at: ...
version: 4

资源真正创建后，owner 用稳定的 activation_id 或 resource_ref 把 reservation 激活；结算也有独立且稳定的 settlement_id。状态通过以 reservation_id + version 为条件的写入收敛：

held@v4 → activated(resource_ref=sandbox_92)@v5
held@v4 → released@v5
activated@v5 → settling(settlement_id=settle_81)@v6
settling@v6 → settled@v7

released 只适用于尚未激活、并且 owner 已确认没有资源产生的 reservation。只有持有匹配 operation、owner generation 和 version 的一方可以 activate、release 或进入 settlement；迟到的重复回包影响 0 条记录，再读取 current state。Reservation expiry 触发 reconciliation，不自动证明资源从未创建或使用。已激活的 reservation 不能因为 cleanup timeout 退回 released。

预留与实际用量也要分开。activated 表示容量已被合法占用；每笔真实 Sandbox-seconds、token 或 Tool units 使用稳定的 usage_event_id 或 charge_id 去重。任务结束时，同一个 settlement_id 汇总已用量，并用稳定的 adjustment_id 或 refund_id 记录可归还余额和超额策略，retry 仍通过条件写入同一结算。

如果 usage 查询 timeout 或结果未知，reservation 保持 settling，pending adjustment 也不能关闭；reconciler 继续用相同 identity 查询。只有已知 usage、charge 与 adjustment 都完成后才能写 settled，不能用整笔 refund 抹掉可能已发生的消耗。

平均值会掩盖 Hotspot

假设十个 queue partition 中九个没有 backlog，一个 partition 因单一 tenant 的长任务持续堆积。全局平均 lag 可能仍然很低，但这个 partition 的 oldest message age 和 worker utilization 已经恶化。

因此 backpressure 至少要按真正的竞争 key 观察，例如：

  • tenant；
  • queue partition 或 message group；
  • Tool/provider；
  • Sandbox profile；
  • destination service。

信号应回到能改变流量的 admission。只在 dashboard 上报警不构成 backpressure；worker 已经饱和后再无限扩展 Queue，也只是把延迟变成更长的持久 backlog。

Admission 可以选择 delay、reject、降低 fanout、切换更便宜的 execution mode，或保留公平份额。具体公平性策略属于产品决策；本文只要求下游压力能抵达上游，并且按热点维度而不是仅按全局平均值生效。

运行中超限只能收敛，不能倒推 effect

Budget 在执行中耗尽时，Runtime 可以停止新的 Model Turn、Tool admission 或 Child Run，向已有执行发送 cancellation request，并等待约定的收敛边界。

这不代表已经发出的外部 effect 被撤销。一个 Tool timeout 或 Sandbox 强制终止后，effect outcome 仍可能是 unknown，需要对应 backend 查询或 reconciliation。资源治理负责不再扩大消耗，不负责伪造业务回滚。

成本事实与 Policy 决策要分开

Observability 可以记录每个 Attempt 的 model、Tool、Sandbox、storage 和 retry 消耗，并按 logical operation 聚合。它回答“发生了多少”，而不是直接决定下一次该允许多少。

Policy owner 可以离线或近线消费这些事实，调整 quota、reservation 或降级阈值。把当前账单数字直接写成运行时授权，会把观测延迟、重算和价格变化带进 admission 的 Source of Truth。

本文不提供固定阈值或价格，因为这些必须来自具体容量、SLO 与成本数据。

回到问题

开场的父 Run 在创建 child 前就应面对 resource envelope：最多三个并发 Child Run、两个 Sandbox slot，并从父级剩余 Sandbox-seconds 中为每个 child 预留额度。

当该 tenant 对特定 Sandbox profile 的并发已满、对应 queue partition 的 oldest age持续上升时，backpressure 抵达 admission。后续 spawn 被延迟或拒绝，并返回 tenant_sandbox_saturated；已经运行的 child 在剩余 budget 内收敛，不能再产生新的无限 fanout。

因此，max_tokens 只解决一个局部问题。完整治理需要按资源类型和责任主体分别建模 Budget、Quota、Rate Limit、Concurrency 和 Backpressure，再让它们在资源被占用之前共同完成 admission。
