Agent 31：耐久 Job 的取消、结果与交付怎样收敛

用 claim lease、generation fencing、cancelling 中间态和条件交付，处理重复 worker、迟到结果与用户取消之间的竞态。

问题

Agent 提交一个 Job，把 report.md@v3 转成 PDF。Worker A 领取消息并开始转换，随后因为网络分区停止续约；Job service 让 Worker B 接管。此时用户又说“取消报告”。

系统把 Job 标成 cancelled 后，A 恢复网络并上传了 PDF。下载页随后显示这个迟到结果：调度系统认为任务已经取消，Artifact store 却只看见一次合法上传。

Queue 能重新投递消息，取消信号也能请求 worker 停止，但两者都不能独自回答谁仍有权提交结果。耐久 Job 需要一条更完整的生命周期：稳定 Job identity 接受多个 delivery Attempt；Job owner 用带 generation 的 claim lease 决定当前执行权；结果 owner 用 fencing 拒绝旧 Attempt；取消和完成通过条件状态转换竞争；Artifact ready 与用户可见交付再由不同 owner 提交。

Delivery、Claim 与 Job 不是同一个对象

同一项后台工作会经历几个不同 identity：

对象开场示例何时变化
Jobjob_pdf_9用户目标或输入版本变化时
Queue deliverydelivery_18、delivery_19每次重投可能变化
Execution Attemptattempt_a、attempt_bworker 实际开始执行时
Claim generation41、42Job owner 接管执行权时
Result/Artifactartifact_pdf_31@1成功提交输出时
Delivery commitmentdelivery_commit_7输出对用户可见时

Queue 的 visibility timeout 或 ack deadline 只约束 delivery mechanism。以 Amazon SQS Standard queue 为例，消息采用 at-least-once delivery，并且 visibility timeout 期间仍可能出现重复投递。收到消息不等于获得业务 Job 的唯一写权。

Worker 因而先用 job_id 向 Job owner 请求 claim，而不是直接执行：

job_id: job_pdf_9
input: report.md@v3
state: running
claim:
  owner: worker_b
  generation: 42
  expires_at: ...
state_version: 11

这个条件写入只在 Job 仍可执行、旧 claim 已失效且输入 revision 未变时成立。重复 delivery 可以解析到同一个 Job，却不会自动创建新的业务意图。

取得新 claim 也不表示旧 Attempt 没有越过外部 effect boundary。B 在重新渲染或调用 provider 前，先读取同一 result operation 的 intent、effect reference 和已提交结果；若 A 的结果仍可能在途，就查询或进入 reconciliation。Claim 转移执行权，不会把结果未知自动改成 not started。

Lease 决定当前执行权，fencing 才能拒绝旧结果

Claim lease 有效期让 Job owner 能在 worker 丢失后重新分配工作，但 lease 过期不能证明旧进程已经停止。Worker A 可能继续计算、调用外部服务或上传结果。

因此 generation 必须抵达能强制拒绝结果的边界。一个安全提交至少比较：

job_id = job_pdf_9
expected_job_state = running
expected_state_version = 11
claim_generation = 42
input_revision = report.md@v3
result_operation = render:report.md@v3

如果 Artifact store 与 Job store 能共享可信条件提交，owner 可以原子验证这些字段并发布结果。若二者跨存储，更常见的做法是让 worker 只上传隔离、不可见的 staging Blob，再由 Job owner 校验当前 generation 和 state 后，把稳定 Artifact reference 绑定为 Job result。

这样 A 的 generation=41 即使完成上传，也只能留下未认领 staging data，不能推进 job_pdf_9。后台 cleanup 可以按 retention 清理它，但不能把“Blob 存在”误写成 Job succeeded。

Lease refresh 同样需要比较 generation 和 state version。已经进入 cancelling、succeeded 或 cancelled 的 Job 不能被旧 worker 续活；一次 refresh timeout 也不能让 worker自行假设续约成功。

取消先进入中间态

用户请求取消时，Job owner 不应立即写 terminal cancelled。它先通过条件转换提交取消意图：

running@v11
  → cancelling@v12
  → cancelled@v13

进入 cancelling 后，owner：

  1. 停止派发新 Attempt；
  2. 拒绝旧 generation 的 refresh；
  3. 推进 fencing generation 或撤销 result-publish capability；
  4. 向当前 worker 发送 cancellation request；
  5. 查询可能已经越过 effect boundary 的外部动作。

Cancellation request 只证明请求已发出。进程退出也只证明计算停止；如果 worker 已经调用无法查询的外部服务，effect outcome 仍可能是 unknown。

只有旧 Attempt 已无法再提交结果、当前 Attempt 已停止或收敛，而且没有待确认 effect 时，Job owner 才能进入 cancelled。若存在 unknown effect，状态应保持 cancelling、reconciling 或进入 manual review，不能为了界面简洁伪造终态。

完成与取消由条件提交决定谁赢

取消和完成可能同时到达 Job owner。两条路径都必须比较同一个 state/version：

result commit: running@v11 → succeeded@v12
cancel commit: running@v11 → cancelling@v12

只有一条条件写入可以成功：

  • 结果先提交：Job 保持 succeeded；后到的取消不能改写已发生的完成事实。
  • 取消先提交：Job 进入 cancelling；带旧 version/generation 的结果提交失败。

失败的迟到提交不是可重试 conflict。Worker 应查询 Job current state；若 Job 已取消，就放弃或隔离 staging result。为迟到结果创建新 Job identity，会绕过用户已经提交的取消意图。

对于有独立外部副作用的 Job，结果竞争还要结合稳定 operation identity。若 provider 已执行、响应丢失，owner 先 query/reconcile；只有证据证明未 dispatch，才可在当前合法 claim 下创建新 Attempt。

Artifact ready 不等于用户目标已交付

PDF Job 成功只证明 report.md@v3 产生了一份通过约定检查的 Artifact。它不自动证明用户仍希望收到这份报告，也不证明下载授权已经发布。

可以把两个边界分开：

Job owner:
  job_pdf_9 → succeeded
  result = artifact_pdf_31@1

Task / product owner:
  goal_state = waiting
  expected_input = report.md@v3
  → publish download reference
  → delivery_committed
  → goal_state = succeeded

最终交付由拥有用户目标状态的 owner 条件提交。它重新检查目标是否仍处于 waiting、subject 是否仍获准、Artifact/input revision 是否匹配，以及确认或 policy 是否仍有效。

如果用户取消的是整个报告目标，Task owner 可以先把目标推进到 cancelling。即使 Job 在 fencing 生效前赢得竞态并成为 succeeded，交付提交也会因为目标状态不匹配而失败。Job 成功事实仍保留，未交付 Artifact 则按 retention 清理；系统不能为了让两个状态看起来一致，把已经完成的 Job 改写成 cancelled。

向邮件、支付或外部 API 交付时，本地目标状态与远端 effect 通常不能原子提交。此时需要独立 delivery operation、effect key 与 reconciliation；delivery_committed 只能在对应 evidence 成立后写入。

Fencing 让迟到结果停在 staging 边界

开场中，Worker A 持有 generation 41，B 接管后持有 generation 42：

  1. 用户取消时，Job owner 将 running@v11 条件推进到 cancelling@v12，并使 generation 42 的 result-publish capability 失效。
  2. B 收到 cancellation request 后停止；Job owner确认没有未知 effect，推进到 cancelled@v13。
  3. A 恢复并上传 PDF，但它只能写 staging Blob。绑定 Job result 时，generation=41 和 state=cancelled 都不匹配，提交被拒绝。
  4. Artifact cleanup 记录并删除未认领 staging data；产品层从未发布下载 reference。

如果 A 的合法结果在取消条件写之前已经提交，Job 会保持 succeeded，但产品 owner 仍根据用户目标的取消状态决定不交付。两个 owner 各自保留真实发生的状态。

回到问题

开场故障不是 Queue 重投本身造成的，而是系统把“收到消息”“仍有执行权”“结果已准备”和“用户已收到”压成了一个 Job status。

正确协议让每次 delivery 先解析稳定 Job，再通过 claim lease 获得当前 generation；fencing 把这项执行权落实到结果提交边界；取消先进入 cancelling，并与完成在同一个 state/version 上竞争；最后由产品 owner 单独提交用户可见交付。

这样，旧 Worker 即使恢复也只能产生被隔离的迟到数据，不能重新打开已取消 Job。Job 成功也不会自动覆盖用户目标的取消。耐久性的含义不是“工作最终总会跑完”，而是每次接管、取消、结果与交付都有可验证的 owner 和收敛边界。
