身份必须贯穿 Agent 调用链

2026/07/15
AgentSecurityIdentity

问题

用户要求 Agent 修改一份报告。API 收到请求时已经知道当前登录用户，也确认他可以编辑这份文件。Agent 随后把任务写入 Queue，几分钟后由另一个 worker 执行。

到了真正写文件的时候，worker 使用的是自己的 service credential。文件服务看到的调用者是 worker，而不是最初的用户。

如果 Queue 里只保存 user_id，下游无法证明这个 ID 是谁写进去的，也不知道用户究竟授权了什么动作；如果直接把用户的 access token 放进 Queue，token 又可能在等待期间过期、被撤销或泄漏给不需要它的执行环境。

这就是身份传播真正要解决的问题：执行跨过进程和时间边界后，系统怎样仍能证明当前 actor 正在代表哪个 subject、依据哪次授权、对哪个资源采取什么动作。

“用户是谁”和“谁在执行”不是同一个问题

这次文件修改至少涉及三种不同角色：

概念回答的问题本例
Subject这个目标与权限代表谁？发起请求的用户
Actor当前是谁决定或发起动作？Agent Runtime 或 worker
Execution identity哪个进程身份正在访问基础设施？worker 的 workload identity

此外，authorization 还需要 tenant、action 和 target resource。它们不是另一种“用户身份”，而是判断这次委派是否有效的上下文。

如果审计只记录 subject，最终看起来像用户亲自执行了每一步；如果只记录 worker service account，又无法知道动作影响了哪个用户。两者都没有完整表达事实。

OAuth 2.0 Token Exchange 中也区分 subject 与 actor：delegation 可以表达一个 actor 代表 subject 执行动作，而不必把两者伪装成同一个身份。Agent 系统不一定采用这套协议，但需要保留同样的语义区别。

身份连续，不等于 Credential 一路传到底

一种危险的实现，是让同一个用户 token 从 API 依次经过 Queue、worker、SubAgent 和 Sandbox。这样看似保持了身份，实际却把高价值 credential 暴露给了越来越多的边界。

更合理的流程是让语义连续，而让 credential 在每个可信边界重新获得：

用户请求
  ↓ 认证用户并确认初始权限
Agent Runtime
  ↓ 创建受约束的 delegation reference
Queue
  ↓ worker 使用自己的 workload identity 领取任务
Worker
  ↓ 重新验证 delegation，并获取面向文件服务的短期凭证
文件服务
  ↓ 检查 subject、actor、action 与 resource
写入并记录 audit

Queue 保存的是可验证的引用，而不是长期 bearer token：

{
  "task_id": "task_42",
  "subject_ref": "user_7",
  "actor_ref": "agent_run_19",
  "tenant_id": "tenant_3",
  "delegation_ref": "delegation_81",
  "action": "file.update",
  "resource_ref": "file_12"
}

worker 领取任务后，仍需检查 delegation 是否过期或撤销、用户是否保留权限、目标文件版本是否改变。Queue 保证任务能够稍后执行，并不会冻结外部世界的授权事实。

Delegation 必须随调用链逐步收窄

用户允许 Agent 修改一个项目目录，不等于后续每一层都需要相同权限。

如果 SubAgent 只负责总结资料，它可能只需要读取 /project/docs/**；真正写入 report.md 的 Tool 才需要针对该文件的写权限。一次委派可以从几个维度收窄：

  • action：从读写收窄为只读。
  • resource：从整个 workspace 收窄到单个目录或文件。
  • time：只在当前 Run 或短时间内有效。
  • audience：credential 只对目标服务有效。
  • depth：明确是否允许继续委派。
parent：files.read + files.write on /project/**
child： files.read on /project/docs/**

子级权限应当是父级授权的子集。调用链越深，权限不应因为“实现方便”反而变大。

模型不能提供可信身份

模型可以生成文件路径、修改内容和搜索条件，也可以提出需要哪项 capability，因为这些都属于任务提案。它不能提供具有权威性的 subject_id、tenant_id、已授予的 authorization scope、OAuth token 或 audit actor。

这类 identity 或 authorization 字段即使出现在 Tool Schema 中，也只是模型输出。它们可能来自错误的 memory、被文件中的文字诱导，或被模型直接编造。

Runtime 应从已认证 session、delegation record 和 workflow metadata 中注入可信 context：

async function updateFile(args: UpdateFileArgs, ctx: TrustedContext) {
  return fileService.update({
    subject: ctx.subject,
    actor: ctx.actor,
    tenant: ctx.tenant,
    path: args.path,
    patch: args.patch,
  })
}

backend 随后使用自己的资源状态验证：这个 subject 是否有权修改目标文件，以及当前 actor 是否被允许代表 subject 执行该 action。模型的业务参数不能覆盖 trusted context。

SubAgent、Connector 与 Sandbox 都遵循同一条规则

不同组件需要的 credential 不同，但身份问题没有变化：

  • SubAgent 需要知道任务代表哪个 subject，同时只获得被委派的 capability。
  • Connector 使用自己的 client identity 和用户授权访问外部 API，但不把 access token 暴露给模型。
  • Sandbox 使用 workload identity 挂载 workspace 或写 Artifact，而不是直接持有用户 credential。

这三种场景不需要共享同一枚 token。它们需要共享的是一条可验证的关系：当前 execution identity 属于哪个 Run，Run 代表哪个 subject，delegation 是否允许当前 action 和 resource。

同样，trace_id 只能关联调用路径，不能证明调用者身份。Trace context 与 identity context 可以互相关联，但不能彼此替代。

回到问题

身份传播不是把 user_id 或 access token 从入口复制到调用链末端。

它要保持的是授权关系：哪个 subject 的目标正在被执行，当前 actor 和 execution identity 是谁，权限经过怎样的 delegation，最终作用于哪个 tenant、action 和 resource。

当任务跨过 Queue 后仍能重新验证这条关系，并且每一层只获得当前动作所需的最小权限，Agent 系统才能同时做到授权、隔离和审计。

后续问题

  • Subject、Actor、Tool 与 Sandbox 应分别采用怎样的 identity model。
  • Connector 怎样管理 OAuth credential、rotation、revocation 与 audience。
  • 多租户数据怎样跨 Queue、Cache、Artifact 和 Sandbox 保持隔离。
  • 高风险动作的确认怎样绑定身份、参数、资源版本和有效期。
  • Audit record 怎样在可追溯性与敏感数据最小化之间取舍。
