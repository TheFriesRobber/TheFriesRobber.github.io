Agent 09：并发 Tool 的顺序、一致性与取消

区分事件宣告、handler 启动、完成顺序、Context 顺序、共享 mutation 和分层取消保证。

问题

模型在同一轮提出两个 Tool Call，都要更新资源 doc-7。Runtime 并发处理它们：第二个先完成，第一个随后被父 Run 取消。最终 Context 应按什么顺序写回？共享资源是否一致？父 Run 又要等到什么时候才算结束？

“并发执行”同时包含事件、函数调用、外部状态和父子生命周期。只说用了 Promise.all，无法回答这些问题。

Start event 不等于 handler 已启动

在 Pi 当前 agent-loop.ts 中，tool_execution_start 会在 validation、beforeToolCall 和 handler invocation 之前发出。并行路径还会先顺序完成各 Tool 的 preflight，再通过 Promise.all 等待可执行 handler。

因此需要区分：

event announcement
→ validation / callback preflight
→ handler invocation
→ external effect
→ completion event
→ Tool Result enters Context

一个 invalid、被 callback 阻断或已经取消的 Tool Call 也可能拥有 start/end event，却从未运行 handler。可观测系统若把 start event 当作“副作用代码已经开始”，会错误计算执行时间和风险窗口。

执行顺序与 Context 顺序不同

并发 Tool Call 至少有三种顺序：

  • invocation order：handler 何时真正开始；
  • completion/event order：哪个 handler 先结束；
  • assistant source order：模型在消息中提出 Tool Call 的顺序。

完成事件适合实时展示实际进展；写回 Context 时则需要稳定、可预测的 Tool Result 对应关系。Pi 的并行路径会并发等待执行，同时保持结果与 source Tool Call 的关联。不能因为第二个先完成，就让下一轮模型误以为它是第一个 Tool 的结果。

Pi 当前支持全局 toolExecution: "sequential" | "parallel" 和 per-tool executionMode；只要批次中包含 sequential Tool，整批就走串行路径。它没有内建 maxConcurrentTools 或 semaphore。并发上限若有需要，应明确标为 host/runtime 增强，而不是当前能力。

实现可参考 Pi 的 agent-loop.ts。

串行执行也不能保证外部一致性

即使单个 Run 顺序调用两个 Tool，另一个 Run 或外部用户仍可能同时修改 doc-7。Runtime 调度顺序不是数据库事务。

共享 mutation 应在资源 owner 处使用适当机制：

  • resource revision 或 ETag 做 optimistic concurrency control；
  • idempotency key 防止同一 logical operation 重复生效；
  • transaction 保证同一事实源内必须原子成立的更新；
  • query/reconcile 处理结果未知的外部 effect。

开场中的两个更新都应携带基于同一 revision 的前置条件。先在资源 owner 处成功提交的一次获胜，另一次因 revision 不匹配被拒绝，而不是静默覆盖；胜负取决于 commit order，不取决于 assistant source order。这一结果与它们在 Runtime 中并行还是串行无关。

Cancellation 有四层保证

“Agent 已取消”也不是单一语义：

  1. AbortSignal 表示取消请求已经发出；
  2. Tool promise convergence 表示已调用 handler 已返回或 reject；
  3. Agent settlement 表示 Loop 不再产生后续工作；
  4. Harness abort barrier 还包括清理队列并等待 idle。

Pi low-level Agent.abort() 只触发 signal，调用者需要另行 waitForIdle()；AgentHarness.abort() 会触发 signal、清理队列并等待 idle。Loop 会等待已经调用的 Tool promise，但无法强制终止忽略 signal 的 handler。

所以忽略 signal 的 handler 可能让等待长期不返回。已经发生或结果未知的外部 effect 也不会被 cancellation 自动回滚，只能进入 query/reconcile。

父级要等所有子工作收敛

Structured concurrency 的核心不是“同时跑得更多”，而是父作用域仍拥有子工作的生命周期。父 Run 可以发出取消，却不应在子 Tool 还可能继续写外部系统时提前宣告 settled。

对开场案例，完整时间线应是：

t1: 两个 start event 被宣告
t2: validation/preflight 完成，两个 handler 被调用
t3: tool-b 提交成功并返回
t4: 父 Run 发出取消 signal
t5: tool-a 响应 signal；其外部 outcome 仍需确认
t6: 两个 promise 收敛，结果按 source identity 写回
t7: Agent/Harness 达到各自的 settlement barrier

这条时间线同时保留完成顺序、消息顺序和外部事实，不需要用一个“cancelled”覆盖所有状态。

回到问题

两个 Tool 并发更新 doc-7 时，应分别回答：

  • start event 是否只表示 announcement；
  • handler 何时真正启动和完成；
  • Context 如何保持 Tool Call 与 Result 的稳定对应；
  • 资源 owner 如何用 revision 或 transaction 保护共享状态；
  • cancellation 发出了什么请求，父级等待到哪一层 barrier；
  • 未知外部 effect 由谁 reconcile。

Runtime 负责调度和父子收敛，外部系统负责共享 mutation 的一致性。把这两个 owner 分开后，并发就不再是一句 Promise.all，而是一条可以验证的执行协议。
