Agent 18：Memory 怎样检索并进入 Context

把候选生成、current-view filtering、reranking、权限和 Context budget 串成一次读取决策。

2026/07/24 更新于 2026/07/27 阅读 次
Agent StateAgentMemoryRetrieval

问题

用户问：“今天下午可以联系我吗？”Vector search 返回两条高相似 Memory：

0.94  v1: preferred_contact_time = morning
0.91  v2: preferred_contact_time = afternoon

v1 已被用户更正，v2 才是 current。如果系统直接取 top-1，最相似的旧版本会重新生效；如果简单提高 top_k，模型只会看到更完整的矛盾。

Retrieval score 只表示某种匹配关系，不证明记录当前有效、真实或获准使用。Memory 进入 Context 前需要一条分层决策链：先用可信 identity 和 scope 限定 query，在隔离域内生成候选；再按 current view、记录级权限、来源和 expiry 过滤；随后按当前任务 rerank；最后由 Context Assembly 分配跨来源预算。

Candidate Generation 只负责扩大候选

Keyword、vector 和 hybrid retrieval 各自适合不同匹配：

  • keyword 保留精确名称、ID 和枚举；
  • vector 发现表达不同但语义接近的内容；
  • hybrid 组合两类 signal。

它们产生的是候选，不是判决，但 query 也不能从一个未隔离的全局集合开始。可信 Runtime 应先绑定 tenant、subject、namespace 或允许访问的资源分区，由 Memory service 完成 coarse query admission；否则越权记录即使随后被过滤，也可能占满 top-k、制造侧信道或影响可用性。

在这个受限集合内，Embedding model、index revision 和 query expansion 都会改变 score；未经版本化和评测的 score 不能跨配置直接比较，更不能承担记录级授权。Candidate record 应至少带稳定 memory_id、version、source reference 和索引 revision，使下游能回到 Memory service 验证，而不是只消费搜索引擎复制的文本。

Hard Filter 要先于 Reranking

coarse isolation 之后，仍要对候选列表执行不能被相关性覆盖的 record-level 检查：

Filter拒绝条件
Current view已 superseded、revoked 或 deleted
Permission当前 subject/actor 无权读取
Tenant/scope不属于当前隔离域或资源范围
Expiry已超过允许使用时间
Source policy来源类型不允许用于该 Memory 类别

这些检查应由可信 service 基于当前状态完成。模型不能通过参数要求“也把旧版本返回”，搜索 index 里的 metadata 也不能替代 Source of Truth。

开场候选经过 filter 后：

v1 morning    → drop: superseded
v2 afternoon  → keep: current + authorized

这一步发生在 rerank 前，避免一个高 similarity 的越权或陈旧记录获得继续竞争的机会。

Reranking 回答当前任务需要什么

通过 hard filter 后，候选仍可能太多。Reranking 可以消费：

  • 与当前 Task 的相关性；
  • freshness 与有效期余量；
  • source/evidence class；
  • record specificity；
  • 与当前指令或其他 source 的冲突；
  • retrieval configuration。

Reranking 输出要保留 reason 和 score provenance。高 score 不把 observation 升级成用户明确偏好，也不把 Memory 变成 instruction；它只帮助 Context Assembly 在合法候选中分配注意力。

如果两个 current records 在适用范围上真正冲突，正确结果可能是保留冲突并要求澄清，而不是让 score 较高者静默覆盖。

Pinned、Hot、Cold 是 Memory 内部策略

Memory service 可以给记录定义可见性层级：

  • pinned：明确要求在匹配任务中优先考虑；
  • hot：近期或高频相关，但仍需 query；
  • cold：只在明确召回时进入候选。

Pinned 不等于永久进入每个 prompt，也不能越过 permission、expiry 或 supersede。它只是 Memory 候选内部的优先策略。

最终 Model Turn 还要同时容纳当前用户输入、system constraint、未解决 Tool Result、文件与其他数据源。跨来源的 Context budget 属于 Context Assembly；Memory service 应返回有 provenance 的候选和预算建议，不能自行占满总窗口。

Budget 降级要保护语义而不是尾部截断

假设合法候选为：

v2 contact_time=afternoon     required for task
timezone=Asia/Shanghai        required for interpretation
old meeting summaries        optional

预算不足时，应先保留当前任务约束和解释 v2 所需的 timezone，再压缩或丢弃无关摘要。简单按 score 截断或从尾部裁剪，可能留下“下午”却丢掉时区，也可能保护较长旧摘要而删除当前纠正。

每个 include/drop/compress decision 应关联 assembly revision。这样结果错误时可以区分：候选未召回、hard filter 拒错、rerank 排错，还是总预算阶段裁错。

把开场查询走完

一份概念性决策记录可以是：

query: contact availability this afternoon
query_scope:
  tenant: tenant_7
  subject: user_42
candidate_generation:
  returned: [contact_time@v1, contact_time@v2, timezone@v3]
hard_filter:
  dropped:
    - id: contact_time@v1
      reason: superseded
rerank:
  - contact_time@v2
  - timezone@v3
context_projection:
  included: [contact_time@v2, timezone@v3]
  provenance_preserved: true

这是设计示例，不代表特定产品的现有 schema。它的价值是让每层只有一个清楚的问题和 owner。

回到问题

开场中的 v1 similarity 更高，却不应该进入 Context，因为 current view 已经确认它被 v2 supersede。v2 与 timezone 通过权限、scope 和 expiry 检查，再按当前问题获得预算，并带着 source/version 进入投影。

因此，Memory retrieval 不是“找最相似的文本”。它要先把 query 限定在可信隔离域，再保证每条候选当前有效且获准使用，然后决定哪些内容对本轮任务最有价值；最后仍由 Context Assembly 在所有来源之间做统一取舍。
