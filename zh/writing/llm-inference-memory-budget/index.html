LLM Infra 05：显存还有空余，为什么 Runtime 仍会拒绝请求

区分 CUDA device、PyTorch allocator 与 Runtime KV pool 三个观测面，用权重、KV Cache、临时 Activation 和 workspace 建立可接纳请求的显存账本。

2026/07/29 阅读 次
LLM InfraInferenceGPU MemoryKV Cache

问题

一个 Replica 的 GPU 监控仍显示有空余显存，新增长 Context 请求却被 Runtime 推迟或拒绝；另一次相似流量直接触发 CUDA out of memory。重启后问题暂时消失，随后又出现。

这三个现象不能统一解释成“显存不够”：

  • Runtime 的 KV block pool 用完，不等于 CUDA allocator 已经 OOM。
  • PyTorch 无法满足一次新分配，不等于 device 上没有任何空闲字节。
  • nvidia-smi、PyTorch allocator 和 serving Runtime 展示的也不是同一个余额。

要判断还能不能接纳请求，平台需要的是分层显存账本，而不是一个 free-memory gauge。

先区分三个观测面

CUDA device

Driver 看到的是整张设备的物理与虚拟内存使用。这里还可能包含 NCCL、CUDA Graph、第三方 Kernel 或其他进程绕过 PyTorch allocator 的分配。

PyTorch caching allocator

PyTorch 区分：

  • memory_allocated()：当前 Tensor 实际占用；
  • memory_reserved()：caching allocator 已经向 CUDA 申请并管理的总量。

官方文档说明，未被 Tensor 使用但仍由 allocator 保留的内存，在 nvidia-smi 中也可能显示为已使用。empty_cache() 只能把完全空闲的 cached segments 归还给其他应用，不会释放仍被 Tensor 占用的内存，也不会凭空增加当前工作集的容量。

Runtime memory pools

Serving engine 往往会预留 KV Cache pool，并按 block 管理 sequence state。pool 没有可用 block 时，Runtime 可以选择等待、preempt、recompute、swap 或拒绝；只有某次底层分配失败时才是 CUDA OOM。

因此，下面三句话表达的是不同事实：

device free memory > 0
allocator has reclaimable cached segments
Runtime has enough compatible KV blocks for this request

任何一条都不能单独推出另外两条。

显存账本必须按生命周期拆分

一个推理 Replica 需要两个正交视图。第一份是逻辑用途账本：

M_allocated_working_set =
  M_weights
  + M_kv
  + M_activations
  + M_workspace
  + M_communication
  + M_runtime

第二份是 allocator/device 对账：

PyTorch allocated ≤ PyTorch reserved
device used =
  PyTorch reserved
  + direct CUDA / NCCL / other process allocations
  + driver and runtime overhead

权重、KV 与 Activation 是 allocated 内部的 owner 分类；reserved 是 allocator 观测，不可再与这些对象相加，否则会重复计数。Fragmentation 与 headroom 属于“reserved 是否能满足下一次具体分配”的解释，不是新的业务内存 owner。

这些项目的生命周期不同：

项目典型生命周期主要决定因素
权重Replica 常驻参数量、dtype、量化、并行切分
KV Cache随 active sequence 增长Token 数、层数、KV heads、dtype、sharding
Activation每次 Prefill/Decode 执行Batch、Token budget、Kernel
Workspace / CUDA GraphRuntime 或特定 shape 常驻/复用Kernel、graph capture、shape
通信 buffer并行组执行期间或常驻TP/PP、collective 实现
allocator / device 对账进程生命周期内变化分配历史、segment policy、allocator 外分配

这解释了为什么一个长 Context 请求会在“还有几 GB”时失败：它需要的不只是新的 KV block，也可能同时触发更大的 Prefill workspace 或新的 graph/Kernel 分配。标量 free memory 没有表达这些对象的大小和 pool 约束。

KV Cache 是随请求增长的状态

对于保存标准 K/V Tensor 的 Transformer，一种概念估算是：

KV bytes per token =
  2
  × layers
  × kv_heads
  × head_dim
  × bytes_per_element

其中 2 代表 Key 和 Value。这不是所有模型的通用公式：MLA、混合或 recurrent attention、KV quantization、Tensor/Context Parallel sharding 和特殊 layout 都会改变结果。

它仍然揭示了关键关系：KV 占用会随 active Token 数增长。长输出让 state 停留更久；长 Prompt 从一开始就需要更多 KV；并发则把多个 sequence 的 state 同时放进 pool。

容量与 admission 要分成三层：

静态 feasibility：
  model/context hard limit 是否允许该请求

平台保护性 admission / capacity planning：
  prompt tokens + max 或预测 output envelope
  → 是否值得接纳、需要保留多少 fleet headroom

Runtime iteration scheduling：
  本轮 scheduled tokens + lookahead
  → 增量分配本轮需要的 KV blocks

Actual output length 只有完成后才知道。平台可以用上限或预测做保护性 admission，但这不是所有 Runtime 的通用预留规则。以当前 vLLM 为例，scheduler 按本轮 num_new_tokens 与 lookahead 增量调用 KV allocation；请求可能先被接纳，随后随 Decode 增长因 KV 不足而 defer 或 preempt。采用“预留完整输出”和“增量分配”的系统会在不同时间暴露容量压力，reason code 也必须区分。

Paged KV 缓解的是布局，不是全部显存压力

PagedAttention 把逻辑连续的 KV sequence 映射到固定大小的物理 blocks，减少为最大长度预留整段连续空间造成的浪费，也支持 block 级共享与调度。

但它没有消除：

  • block 尾部尚未填满的内部浪费；
  • 权重、Activation、workspace 和通信 buffer；
  • allocator 外部的直接 CUDA 分配；
  • Runtime KV pool 本身的容量上限；
  • 新请求与已有请求之间的 admission 取舍。

Paged KV 的正确结论是“让 KV allocation 更细粒度”，不是“显存碎片问题已经消失”。

用三个结果定位开篇请求

假设一个合成长请求需要 12 个 KV blocks，并会触发一档更大的 Prefill workspace：

观测结果正确解释
KV pool 只剩 8 blocks，allocator 正常Runtime defer/preempt/rejectKV capacity 不足，不是 CUDA OOM
KV blocks 足够，新 workspace allocation 失败CUDA OOM底层无法满足该次分配
重启后暂时成功allocator/runtime state 改变不能证明 workload 已安全

诊断记录至少要同时保留：

memory_evidence:
  device: {free_bytes: ..., used_bytes: ...}
  pytorch: {allocated_bytes: ..., reserved_bytes: ...}
  runtime_kv: {total_blocks: ..., free_blocks: ...}
  request: {prompt_tokens: ..., max_output_tokens: ...}
  execution: {phase: prefill, requested_allocation_bytes: ...}
  outcome: {kind: kv_capacity_rejected | cuda_oom | preempted}

字段名称是设计建议，不是 vLLM API。重点是让 rejection reason 对齐真正失败的边界。

回到问题

“GPU 还有空余”只能说明某个观测面仍有未使用字节。它不能证明 Runtime KV pool 有足够 blocks，也不能证明下一次 Activation 或 workspace 分配一定成功。

开篇问题应该先被分类：这是 KV capacity rejection、allocator allocation failure，还是包含外部分配的 device OOM？只有显存账本把权重、KV、临时执行与各层 reservation 分开，admission 和诊断才能讨论同一个事实。
