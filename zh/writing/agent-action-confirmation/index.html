Agent 29：高风险动作需要可校验的确认协议

把用户确认绑定到具体动作、参数、资源版本、身份和有效期，避免陈旧确认被复用。

2026/07/24 更新于 2026/07/27 阅读 次
Agent ProductionAgentSecurityHuman-in-the-Loop

问题

Agent 准备删除 /reports/draft.md，向用户展示路径并询问是否继续。用户回复“确认”。但等待期间发生了两件事：文件被另一个进程替换，模型也在恢复后重新生成了 Tool Call，把路径改成 /reports/final.md。

如果 Runtime 只在 Session 中搜索最近一句“确认”，它可能把针对旧文件的同意用于新动作。自然语言表达了用户意图，却没有稳定绑定 Tool、参数、资源版本和有效期。

高风险确认需要变成一项可校验协议：用户确认的是一份规范化 action proposal；执行时只有同一身份、同一动作、同一参数和同一资源前置条件仍成立，确认才可消费。

先固定用户究竟看见了什么

模型产生的 Tool Call 先经过 Schema validation、可信参数归一化和风险分类，再形成 action proposal。不要在原始 JSON 上直接签名：对象字段顺序、默认值、路径别名或大小写差异都会造成歧义。

一份概念性 proposal 可以是：

{
  "proposal_id": "prop_41",
  "subject_ref": "user_7",
  "actor_ref": "agent_run_19",
  "tool": "delete_file",
  "arguments": {"artifact_id": "file_12"},
  "resource_revision": "etag_18",
  "policy_revision": 7,
  "risk": "destructive",
  "expires_at": "...",
  "nonce": "..."
}

用户界面根据这份规范化 proposal 显示可理解的差异：删除哪个文件、属于哪个项目、当前 revision 是什么、是否可恢复。确认对象与展示对象必须同源，不能一边显示模型摘要，一边执行未经比较的原始参数。

风险分类应由可信 policy 基于 Tool、effect 类型、resource、tenant 和参数计算。模型可以解释风险，但不能自行把 destructive action 标为 harmless。

Confirmation token 绑定的是 proposal

用户通过已认证交互确认后，确认服务签发或保存一条不可伪造的记录：

confirmation =
  subject + actor/delegation
  + proposal digest
  + resource revision
  + policy revision
  + issued_at + expiry
  + one-time nonce

这是一种设计建议，不是某个通用标准规定的固定字段。核心不变量是：任何会改变用户决策的信息发生变化，都不能继续复用旧确认。

resource_revision 尤其重要。HTTP 的 If-Match 展示了同类原则：状态改变请求可以带已有 representation 的强 validator；不匹配时，origin server 不执行该方法。具体 backend 可以使用 ETag、数据库 row version、Artifact revision 或其他强前置条件。

Pause/Resume 不能靠对话文本恢复

进入确认等待时，Runtime 应持久化：

  • proposal_id 与 canonical digest；
  • 等待哪个 authenticated subject；
  • 过期时间与撤销状态；
  • 关联的 Run、Tool Execution 和 resume point；
  • 当前资源与 policy revision。

Session 恢复后，Runtime 加载等待记录，再处理 confirmation event。它不应重新让模型从消息里判断“用户是否同意”，也不应重新生成一份看起来相似的 Tool Call 后直接消费旧确认。

如果模型需要修改参数，系统生成新的 proposal，并把差异重新展示给用户。纯展示文案变化可以保留同一个 canonical proposal；resource、recipient、amount、destination、scope 或 effect 类型变化则需要重新确认。

一次性消费不等于 effect 恰好一次

确认服务应通过一次持久化 CAS，把 token 从 issued 原子推进到 consumed(operation_id)；消费状态与领取它的 stable operation 必须同时落盘。这样可以阻止两个 operation 领取同一确认，也避免进程在标记 consumed 后、记录 owner 前崩溃而留下 orphan confirmation。但这只限制确认凭证的消费，不保证外部副作用恰好一次。

例如 backend 已删除文件，Runtime 在保存 Tool Result 前崩溃。恢复后不能因为 confirmation 已 consumed 就简单宣布失败，也不能重新签发确认后再删一次。系统需要稳定 operation_id 和 backend effect reference：

proposal prop_41
→ confirmation conf_9 consumed by operation delete_42
→ backend outcome unknown
→ query delete_42 / resource revision
→ confirmed 或 manual reconciliation

对于无幂等查询能力的 backend，结果可能长期是 unknown。确认协议不能消除这种不确定性。

恢复时只有同一个 operation_id 可以继续消费这条确认：若 evidence 证明尚未 dispatch，可以创建它的新 Attempt；若已经越过 effect boundary，则必须先 query/reconcile，不能把恢复解释成新的操作。

Backend 仍要重新授权和检查前置条件

即使 confirmation 完全匹配，真正执行前仍需：

  1. 重新验证 subject、actor、delegation 与 tenant。
  2. 确认当前 policy 仍允许该 action。
  3. 检查 resource revision 与状态。
  4. 使用 operation identity 执行或查询副作用。
  5. 把 authorization decision、confirmation 和 effect outcome 分开审计。

确认表示用户看见并同意特定 proposal，不表示用户永远拥有权限，也不证明 backend 当前状态适合执行。撤销权限、资源进入 legal hold 或 policy 升级都可能让已确认动作被拒绝。

并非所有 Tool 都需要确认。读取公开资料、无副作用的格式转换通常可以按 policy 直接执行；删除、向外发送敏感数据、不可逆提交或高金额动作更可能需要确认。阈值应由产品风险模型决定，而不是让用户对每一步都点“确认”。

回到问题

开场中的旧确认应被拒绝。/reports/draft.md 的 revision 已变化，而且恢复后的 Tool Call 指向 /reports/final.md，canonical proposal digest 不再相同。

Runtime 生成一份新 proposal，明确展示目标文件和当前 revision；只有用户再次确认，且执行时身份、policy 与 resource precondition 仍成立，backend 才接受删除。

因此，“确认”不是对 Agent 的泛化信任，也不是一段可复用的聊天文本。它是对一份具体 action proposal 的有期授权证据，并且不能替代 backend authorization、幂等副作用控制和审计。
