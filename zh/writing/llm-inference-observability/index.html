LLM Infra 13：推理可观测性必须对齐哪些执行粒度

对齐 logical request、attempt、execution、sequence、Replica 与 deployment 的 identity、timestamp 和 outcome，避免平均指标互相解释不了。

2026/07/29 阅读 次
LLM InfraInferenceObservabilityTracing

问题

监控显示 request P95 上升，GPU utilization 正常，aggregate tokens/s 也正常。没有 gateway queue timestamp、resolved deployment、engine arrival、first scheduling 和 cancellation outcome，平台无法区分三种解释：

  • workload 变长了；
  • placement 或 queue 变慢了；
  • 模型执行本身变慢了。

更多平均指标不会自动消除歧义。可观测模型必须先固定执行粒度，再让 latency、Token、memory 与 outcome 回到各自 owner。

一个请求会展开成多个执行对象

至少要区分：

粒度稳定身份拥有的事实
Logical requestlogical_request_id调用方意图、最终可见结果
Attemptattempt_id一次物理发送、timeout、retry
Model executionexecution_idengine 接纳、Prefill/Decode、Token
Sequencesequence_idsampling 分支、KV state、finish reason
Replicareplica_uidrunning/waiting、KV fraction、health
Deploymentmanifest digestresolved model、Runtime、配置、拓扑

一次 logical request 可能因 gateway retry 产生多个 attempts；一个 attempt 也可能生成多个 sequences。把所有 Token 都挂到 logical request counter，会掩盖重复计算；把 client timeout 直接写成 model failure，则混淆了观测边界。

OpenTelemetry 的 GenAI semantic conventions 已覆盖 client/server operation duration、Token usage 与 requested/response model，并分别定义 client 的 time_to_first_chunk 和 server 的 time_to_first_token。两者观测边界不同，不能统称为同一个 TTFT 或互换；这些 convention 当前仍标为 Development。Placement、batch iteration、KV block、Replica 和 TP group 也没有统一标准，因此必须使用带版本的本地 convention，不能声称行业已经统一。

TTFT 只有在打点完整时才能拆开

要解释首输出为什么变慢，可以记录：

request_received_at
→ admission_decided_at
→ placement_decided_at
→ engine_arrival_at
→ first_scheduled_at
→ first_token_generated_at
→ first_chunk_sent_at
→ client_first_chunk_at

由此才能计算：

区间可能含义
receive → admissiongateway policy 与 queue
admission → placementcluster scheduling
placement → engine arrivalnetwork / handoff
engine arrival → first scheduledRuntime queue
first scheduled → token generatedPrefill 与 first decode
generated → sent → receivedserver serialization 与 transport

如果系统只打了 request start 和 client first chunk，就只能确认端到端 TTFT 变慢，不能把差值“推断”为 Prefill。每一段 latency 都必须有同一时钟域或已处理 clock skew 的 timestamps。

Metrics、Trace 与 Event 分别承担不同工作

Replica 级指标适合低基数聚合：

running requests
waiting requests
KV cache usage
prompt / generation tokens
TTFT / ITL / E2E histograms
preemption and finish-reason counts

vLLM 的生产指标覆盖其中的 Runtime 维度，包括 running/waiting、KV、Token、TTFT/ITL/E2E、preemption 与 finish reason；它没有覆盖所有 engine/transport failure 的统一 counter。Gateway/Router failure 与 scheduling outcome 仍需由 llm-d 指标或带版本的本地 convention 补齐。

高基数 identity 不应直接成为 Prometheus labels。request_id、attempt_id、execution_id 和每个 batch iteration 更适合 trace、structured event 或抽样 profile：

  • Metrics 告诉我们异常是否存在；
  • Trace 关联一次请求跨越的边界；
  • Event 记录 admission、placement、cancel 与 finish 的状态变化；
  • Profile 解释 Kernel、通信和显存细节。

把每个 iteration 都永久写成指标标签，会制造 cardinality 与存储问题；完全不保留 iteration 证据，又无法解释 scheduler interference。合理方案是按错误、慢请求或抽样 trace 记录。

Outcome 必须区分失败与未知

一份 outcome taxonomy 可以是：

attempt_outcome:
  logical_request_id: req_123
  attempt_id: att_2
  execution_id: exec_91
  state: cancelled_after_start
  transport_status: deadline_exceeded
  cancel:
    requested_at: ...
    engine_observed_at: ...
    execution_stopped_at: ...
  usage:
    input_tokens: 2400
    generated_tokens: 91
  gateway_delivery:
    chunks_emitted: 6
    emitted_token_cursor: 47
    transport_status: disconnected
  client_ack:
    protocol: none
    acknowledged_cursor: null

需要区分：

  • rejected before execution；
  • cancelled before/after execution start；
  • engine error / CUDA OOM；
  • transport 在可能发生 partial delivery 后失败；
  • completed but client acknowledgement unknown。

Runtime 只能证明 Token 已生成；Gateway 能证明自己尝试发出了哪些 chunk；只有协议存在显式 application ACK 时，才能记录 Client 确认的 cursor。普通单向 stream 没有这类 ACK 时，Client 是否收到、解析并提交给应用仍是 unknown。

Timeout 也只能说明观察方没有在期限内得到所需结果，不能自动证明 server 未执行。unknown 不是监控缺陷，而是分布式调用在缺少更多证据时的诚实结果。

用证据排除开篇的三个解释

假设补齐数据后看到：

workload input-token distribution: unchanged
placement latency: unchanged
engine queue time: increased
prefill execution: unchanged
KV usage and preemption: increased

现在可以形成一个有边界的推断：首 Token 变慢主要与 Runtime queue 和 KV pressure 同期发生，而不是 model compute 自身变慢。仍不能只凭 correlation 宣称 root cause；下一步需要查看 scheduler decision 与 preemption events。

如果相反看到 P95 input tokens 上升，queue 与 execution 都按长度同步变化，则 workload drift 是更直接的解释。关键不是一次就找到答案，而是每个解释都能被下一条证据证伪。

回到问题

Request P95、GPU utilization 和 tokens/s 都正常或异常，仍不能直接解释 TTFT。只有 logical request、attempt、execution、Replica 与 deployment 的 identity 对齐，并在关键边界真实打点，才能把 queue、placement、Prefill、Decode 与 transport 分开。

可观测性的产出不是一张更大的 Dashboard，而是一套能让每个失败保持正确 grain、让每个解释可以被证伪的证据模型。
