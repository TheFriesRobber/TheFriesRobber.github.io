Agent 16：Delegation 的执行状态该由谁拥有

按完成状态、生命周期、持久性、取消和结果消费方选择父 Run、Child Run、Job 或 Workflow。

问题

Agent 遇到两个子问题：

  1. 并行读取两份公开文档并比较差异；
  2. 等待一批外部审批完成，可能跨进程持续数小时，然后继续执行。

如果两者都 spawn subagent，第二个任务会把耐久责任交给一个进程内对象；如果两者都升级成 Workflow，第一个任务又承担了不必要的持久化和运维成本。子问题的来源不决定执行原语，完成状态由谁拥有才决定。

先找到 completion owner

Delegation proposal 只描述“要解决什么”和“期望返回什么”。真正的执行选择要回答：

  • 谁能判断任务已经完成；
  • 父级退出后工作是否必须继续；
  • 是否需要独立权限、Context 或 Workspace；
  • cancellation 如何传播；
  • 结果由谁验证和消费；
  • 进程失败后由谁恢复。

如果父 Run 必须在线等待并拥有所有结果，进程内 child task 或 Child Run 可能足够；如果工作必须跨重启继续，completion owner 应转移给 Job 或 Workflow 系统。

四种选择解决不同生命周期

执行方式Completion owner适合情况
父 Run 内继续父 Run短小、顺序、无需隔离
Child Run / SubAgent父 Run 或明确 child owner需要独立 Context、Tool surface 或并行推理
后台 JobQueue/worker + 业务状态可以异步完成，有明确单任务结果
Durable WorkflowWorkflow state owner多步骤、长等待、补偿和跨进程恢复

这些不是能力等级。Workflow 不比 Child Run “更智能”，只是承担不同的 durability 和状态责任。

Child Run 不是复制父 Agent

创建 Child Run 时，默认复制父级全部 Context、Tool 和 credential 既昂贵又危险。模型产生的 Spawn Request 仍是不可信 proposal，只能表达：

subproblem
input references
requested capabilities
expected result schema

可信 Runtime 再从 registry 解析 Agent definition，分配 child identity，从父授权派生并收窄 delegation grant，决定实际 Tool surface、budget 和 Workspace owner，最后生成不可伪造的 execution envelope。模型不能自行指定 identity chain、credential 或最终授权集合。

创建流程还要穿过显式状态：

dedup by parent_run_id + spawn_request_id
→ admission
→ reserve child_run_id in preparing
→ compile delegation envelope
→ atomically persist ready + dispatch intent
→ idempotent dispatch by child_run_id
→ collect and validate result

Spawn retry 复用稳定 request identity，避免同一 proposal 因 timeout 创建多个 Child Run。若进程在 reserve 后退出，reconciler 可以继续 compilation 或收敛为明确失败；若在 ready 后、dispatch 前退出，持久化 dispatch intent 或 scheduler 对 ready record 的 claim 能让工作重新被发现。先写 ready、再只向内存 Queue 发送一次通知，会留下永远无人执行的 child。

父 Run 仍要知道 child handle、取消关系和结果验证方式。Child 返回一段自然语言“完成了”不能证明外部 effect；需要消费结构化结果或可查询 evidence。

Pi Core 提供 Agent/Harness、follow-up 和宿主控制边界，但没有内建完整 durable delegation protocol。宿主可以在这些边界上实现 Child Run，却不能把它写成 Pi 当前自动提供的工作流能力。

Job 与 Workflow 接管耐久责任

后台 Job 适合一个可独立识别、可重试或查询的异步任务。Queue 可能重复投递，所以 Job 仍需要 logical operation ID、幂等和业务事实 owner。

Durable Workflow 适合多个步骤、Timer、外部 Signal 和补偿关系。Workflow 拥有控制进度，业务数据库仍拥有业务事实。把所有长期状态都塞进 Workflow history，或反过来只在业务表中猜控制进度，都会造成双 owner。

选择 Job 或 Workflow 的关键不是“预计耗时超过多少分钟”，而是父进程退出后谁继续承担完成、等待和恢复责任。

用两个子问题做选择

对公开文档比较：

  • 两个读取动作只影响当前答案；
  • 父 Run 在线等待结果；
  • 子任务可以共享只读输入，但使用收窄 Tool surface；
  • 父级取消时应请求两个 child 收敛。

因此 Child Run 或父级 structured concurrency 足够。

对长时间审批：

  • 父进程可能退出；
  • 审批事件由外部系统到达；
  • 需要 durable timer、signal 和恢复；
  • 业务动作可能需要补偿。

因此 completion owner 应交给 durable Workflow。父 Run 只获得 workflow handle，可以结束当前交互或稍后恢复，不应靠内存 SubAgent 持续等待。

多个 child 还可能只有部分成功。结果策略必须在委派前由父级声明：

策略父级如何处理
all_required任一 child 失败都阻止目标完成
partial_allowed保留成功结果，并显式暴露缺口
fallback失败后由父 Run 或另一能力接管

策略属于最终目标 owner，不属于 child。Child 只报告自己的 completed、partial、failed 或 cancelled，并把 effect outcome、Artifact 与 evidence 分开返回；父级验证后才决定整个 Run 能否继续。

Plan 不是 Delegation 的前提

Plan item 可以产生 delegation proposal，但简单任务也可以直接发现子问题。反过来，一个复杂 Plan 中有些 item 仍应由父 Run 顺序完成。

保持二者分开有两个好处：

  • Plan revision 不会重写已经创建的 Job/Workflow 历史；
  • Delegation 可以按真实 lifecycle 选择 owner，而不是按 planner 输出格式机械 spawn。

回到问题

两个子问题不应该因为都叫“子任务”就使用同一种原语：

  • 短时文档比较由父 Run 或 Child Run 拥有，父级在线等待、验证并收敛；
  • 长时间审批由 durable Workflow 拥有，跨重启接收 Signal、推进状态并处理补偿。

选择 Delegation 原语时，先问“谁拥有完成状态和恢复责任”，再问是否需要独立 Context、权限、Workspace 与预算。选定 Child Run 后，创建仍要经过 dedup、admission、identity reserve、envelope compilation、durable dispatch intent 和结果验证；多个 child 的 partial policy 继续由父级拥有。Multi-Agent 不是默认答案；只有当 ownership 和隔离确实发生变化时，创建新的执行边界才有价值。
