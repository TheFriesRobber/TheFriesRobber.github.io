Agent 43：任务地图必须同时表达状态、决策与异常

从顺序流程图转向任务、状态、决策、证据和异常地图，让 Agent 知道何时继续、何时澄清、何时升级。

2026/07/29 阅读 次

问题

团队根据真实工作整理出退款流程：

查询订单
→ 查询支付
→ 查询物流
→ 检查退款政策
→ 创建退款草稿

Agent 查询后得到三个结果：订单系统显示已发货，物流系统显示尚未揽收，支付系统显示扣款成功。顺序流程只说明下一步是“检查退款政策”，却没有说明应该相信哪个状态，也没有说明冲突是否已经剥夺了 Agent 继续执行的权力。

流程图适合表达稳定路径。Agent 面对的却是一个会因每次观察而改变的任务状态。需求建模必须从“接下来调用什么”转向“当前知道什么、据此允许做什么”。

一个步骤不能同时代表动作和状态

“查询物流”是动作，不是任务状态。它可能得到已揽收、未揽收、订单不存在、系统不可用或结果超时。每个结果都会改变下一步。

传统流程经常把这些差异折叠在一个方框里：

[查询物流] → [判断退款]

对 Agent 而言，更完整的表达是：

动作：查询物流
观察：未揽收
证据：物流系统返回的运单状态
冲突：订单系统声称已发货
决策：当前事实不足以创建退款草稿
下一步：请求物流或人工 owner 确认

这不是要求在需求文档中实现完整状态机，而是要求把动作、观察和授权后果分开。否则模型可能把“Tool 调用成功”误认为“业务条件满足”。

Task State 是当前可证明的事实集合

任务状态不应该只是一个粗粒度标签，例如 processing 或 pending。Agent 作出下一步决策时，需要的是当前可证明的事实，以及这些事实的来源和时效。

退款任务可以有如下状态投影：

order:
  status: shipped
  source: order-system
payment:
  status: captured
  source: payment-system
shipment:
  status: not_collected
  source: logistics-system
policy:
  revision: refund-policy@18
authority:
  max_refund_amount: 1000

这是概念示例，不是建议所有系统都采用同一份 YAML。关键在于：状态必须保留足以支持决策的来源，而不是只留下模型总结后的“订单可能已经发货”。

当两个来源冲突时，任务不能通过自然语言平均掉差异。需求必须说明：

  • 哪个系统是该字段的 Source of Truth；
  • 冲突是否可能来自正常延迟；
  • 是否允许通过再次查询恢复；
  • 超过什么时间或条件必须升级；
  • 冲突期间禁止哪些动作。

来源和时效决定事实是否足以授权下一步。

决策点要绑定证据和 owner

一个决策点至少包含四个部分：

Decision：现在要判断什么
Evidence：判断允许使用什么证据
Outcome：不同结果允许哪些下一步
Owner：无法判断时谁拥有决定权

例如，“是否符合退款条件”可以拆成：

DecisionEvidenceOutcomeOwner
是否在退款期限内购买时间、政策版本继续或拒绝Policy/Workflow
商品是否已实际发出运单状态及可信来源继续、等待或升级物流 owner
金额是否在授权内退款金额、执行身份创建草稿或请求审批授权系统/主管
是否属于政策例外客户材料、例外条款提议或升级业务 owner

并非所有 Decision 都应交给模型。期限和金额阈值适合由确定性规则执行；开放文本中的材料归类可能由模型提出；政策例外仍由业务 owner 决定。

需求建模的价值正在于把这些 owner 分开，而不是把所有判断统一写成“由 Agent 决策”。

异常决定 Agent 何时失去继续权

Happy Path 只能说明 Agent 在理想输入下如何完成任务。自主边界由异常定义。

可以先从四类异常建立清单：

信息异常

必要字段缺失、格式无效或用户表达有歧义。Agent 可能通过 Clarification 获得新信息。

状态异常

不同系统返回冲突事实，或数据超过允许时效。Agent 可能重新查询，也可能必须等待真正的状态 owner。

执行异常

Tool timeout、权限拒绝或外部服务不可用。下一步取决于动作是否可能已经产生副作用，不能一律重试。

业务异常

当前政策没有覆盖、风险过高或动作不可逆。Agent 不应通过继续推理取得原本不存在的授权。

每个异常需要明确：

detect：怎样观察到
recover：允许采取什么恢复动作
limit：最多尝试多少次或等待多久
prohibit：期间禁止什么
escalate：交给谁
handoff：需要携带哪些状态和证据

“不确定时转人工”没有定义 detect，也没有定义 owner。它会让 Agent 在不同案例中任意选择继续或停止。

完成条件必须是可观察的状态迁移

任务地图的另一端是完成。完成不能只表示模型停止生成或某个 Tool 返回成功。

退款 Agent 如果只负责创建草稿，完成状态可能是：

refund_draft = created
draft_reference = 可查询
evidence_bundle = 完整
required_approval = 已识别

如果它负责确认退款提交，完成状态还需要支付系统中的业务记录。若负责客户通知，还要确保通知内容与已经观察到的外部状态一致。

因此，一个 Task 的最小闭环是：

初始状态
→ 基于证据的 Decision
→ 获准的 Action
→ 新的外部观察
→ 满足 Completion 或进入 Escalation

流程可以动态变化，但每一步都不能失去证据和 owner。

用同一张地图走过开场案例

回到订单状态冲突的退款申请。任务地图给出的不是“继续检查政策”，而是：

  1. Agent 观察到订单、支付和物流三个来源；
  2. 订单的 shipped 与物流的 not_collected 形成已定义冲突；
  3. 冲突状态禁止创建退款草稿；
  4. Agent 可以在限定时间后重新查询一次物流；
  5. 冲突仍存在时，任务升级给物流 owner，并携带订单号、运单号、两次查询结果和政策版本；
  6. 人工确认状态后，任务从显式记录的任务状态和交接点继续；是否将其持久化为可恢复 Checkpoint，由 Runtime 的恢复契约决定。

这里没有要求模型判断哪个系统“更像正确”。任务地图把可恢复动作和决定权交给了拥有事实的边界。

回到问题

退款流程原本把“查询物流”后面直接连接到“检查政策”。当订单和物流状态冲突时，这条线无法告诉 Agent 是否还拥有继续执行的权力。

把流程改写成任务、状态、证据、决策和异常地图后，冲突成为一种显式状态：允许一次重新查询，禁止创建草稿，仍无法消除时交给物流 owner。

顺序流程回答通常先做什么、后做什么；Agent Task 还必须回答当前事实是什么、谁拥有判断、哪种动作被授权，以及什么条件终止自主执行。

只有后者才能成为 Tool、权限、Human-in-the-Loop 和 Eval 的共同输入。
