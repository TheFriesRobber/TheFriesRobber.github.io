Agent 33：Agent 的 Log、Metric 与 Trace 怎样共用语义

先固定 grain、logical ID、Attempt 和 outcome taxonomy，再关联 Agent 的 Log、Metric、Trace 与成本事实。

2026/07/24 更新于 2026/07/27 阅读 次
Agent VerificationAgentObservabilityTracing

问题

下面用一个构造例子。一次 Agent Run 调用 write_report。两次请求复用同一个稳定 operation key：第一次请求在 deadline 前没有返回；Runtime 查询 backend 后仍无法确认，随后才发起第二次 Attempt。第二次返回成功，backend reconciliation 最终确认该 operation 只对应一个 Artifact revision，Task 因而完成。

这段执行可以同时产生几种看似矛盾的描述：

Attempt 指标：一次 timeout，一次成功
Trace：第一个 span 为 ERROR，第二个 span 为 OK
Tool Execution：经 backend reconciliation 确认最终成功
Task：最终完成
成本：两次请求都可能产生消耗

如果面板只写“Tool 成功率 50%”，值班工程师会以为一半用户操作失败；如果只写“Task 成功率 100%”，第一次 timeout 带来的延迟与成本又消失了。

矛盾不在数据本身，而在问题省略了两个条件：记录对应哪个执行粒度，分母又包含哪些对象。

先固定 Grain，再讨论成功率

同一次 Agent 活动包含多个不能互换的对象：

Task task_7
  └─ Run run_12
       ├─ Model Turn turn_3
       ├─ Tool Execution tool_exec_42，proposal_from=turn_3，operation_id=op_17
       │    ├─ Attempt attempt_1 → timeout，本地结果未知
       │    └─ Attempt attempt_2 → succeeded
       └─ Artifact report_9@v1 → delivered

它们回答的是不同问题：

Grain一条记录代表什么适合回答的问题
Task一个用户目标用户目标是否最终完成
Run一次 Agent Loop这次运行怎样终止
Model Turn一次模型响应模型调用的延迟与 usage
logical operation跨 Turn/Tool Execution 的稳定业务意图同一业务动作最终产生了什么 effect
Tool Execution一个获准执行的逻辑动作逻辑 Tool 动作最终是否完成
Attempt一次物理调用下游请求是否稳定
Artifact一个有版本的产物结果是否存在、交付并可追溯

因此，“Tool 成功率”不是完整定义。至少要写成下面两种形式之一：

确认成功的 terminal Attempts / 全部 terminal Attempts
最终成功的 Tool Executions / 全部 terminal Tool Executions

timeout 只能证明调用方没有及时得到确定结果。对于有外部副作用的调用，它不能自动证明外部写入失败。因此开场中的第一次 Attempt 保持 unknown；第二次成功也不能单独排除重复 effect。只有稳定 operation key 与 backend reconciliation 确认目标 Artifact 状态后，Tool Execution 和 logical operation 的 current verdict 才能记为 succeeded。若无法确认，两者都应保持 unknown。

Logical ID 连接业务对象，Trace Context 连接传播路径

一次 retry 需要同时保留稳定的逻辑身份和变化的物理尝试身份：

{
  "task_id": "task_7",
  "run_id": "run_12",
  "turn_id": "turn_3",
  "operation_id": "op_17",
  "tool_execution_id": "tool_exec_42",
  "attempt_id": "attempt_2",
  "artifact_id": "report_9",
  "trace_id": "91aa...",
  "span_id": "18c2..."
}

operation_id 关联稳定业务意图，可能跨越多个 Turn 或 Tool Execution；tool_execution_id 在自身 retry 中保持不变，attempt_id 每次物理调用都不同。开场例子里 operation 与 Tool Execution 恰好 1:1，但这不是普遍等式。Task、Run、Turn 和 Artifact 也各自拥有身份，而不是从时间接近或日志文本中猜测关系。

Trace ID 则描述一条观测传播链。跨 Queue、异步 callback 或新的 worker 时，retry 可能开启新 trace；即使两次 Attempt 仍在同一 trace 中，也不能用 trace ID 充当 Tool Execution ID。更稳妥的模型是：

业务关系：tool_exec_42 → attempt_1 / attempt_2
观测关系：attempt_1 → trace_4bf9，attempt_2 → trace_91aa

W3C Trace Context 定义了跨系统传播 trace context 的格式；OpenTelemetry Trace API 的 SpanContext 也使用 TraceId 和 SpanId。它们解决的是观测传播，不替 Agent Runtime 决定 Task、Tool Execution 或 Artifact 的业务身份。

Queue 传播必须同时携带业务身份和 Trace Context

知道两类 identity 不同以后，跨异步边界时就不能只传播其中一类。Queue message 可以把业务 identity 与观测 context 分开保存：

{
  "task_id": "task_7",
  "run_id": "run_12",
  "operation_id": "op_17",
  "tool_execution_id": "tool_exec_42",
  "message_id": "message_8",
  "trace_context": {
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
    "tracestate": "vendor=value"
  }
}

message_id 属于稳定 payload；delivery_id 不应写进会原样重投的消息体。Broker receive envelope 若提供原生 delivery identity，consumer 就解析并记录它；否则 consumer ingestion 为每次领取生成新的 delivery_id。Consumer 处理 retry delivery 时复用原有 operation 与 Tool Execution identity，但新的领取、物理调用分别获得新的 delivery_id 与 attempt_id。Queue delivery 本身不能用 Attempt 代替。

Trace 可以按 tracing policy 延续原 parent，或让异步处理开启新 trace 并用 Span Link 连接 message creation context。无论采用哪种拓扑，Span parent/link 只表达观测关系，业务 parent/child 与 retry 关系仍由显式 logical ID 表达。

SubAgent、callback 和后台 Job 也遵循同一原则。历史系统若没有传播 canonical identity，只能在可信入口保存已经证明的 correlation mapping；无法证明的关联应保持 unresolved，不能为了提高 join 完整率而按时间接近硬连。

三类 Signal 共享语义，不复制同一份数据

共享语义不等于让 Log、Metric 和 Trace 携带完全相同的字段。

Log 和 Trace 适合保存单次执行的高基数 identity。OpenTelemetry 的 Logs Data Model 允许 LogRecord 携带 TraceId 和 SpanId，因此结构化日志可以从业务 identity 跳到对应 span：

{
  "event": "tool.attempt.finished",
  "tool_execution_id": "tool_exec_42",
  "attempt_id": "attempt_1",
  "trace_id": "4bf9...",
  "effect.outcome": "unknown",
  "error.type": "deadline_exceeded"
}

Metric 用于聚合，不应把每个 run_id 或 tool_execution_id 都变成 label。它更适合携带有界维度：

agent.tool.attempts{
  tool="write_report",
  effect.outcome="unknown",
  error.type="deadline_exceeded"
} +1

Trace 保存调用路径、时间与相关 attributes；Log 保存离散事件和诊断上下文；Metric 保存按明确 grain 聚合的计数或分布。需要从聚合下钻到具体执行时，可以使用 exemplar、时间窗与 taxonomy 查询，或者由分析系统连接到高基数事实表。

这里可以复用 OpenTelemetry 对 error.type 的约定，但仍要注意它的边界。OpenTelemetry 的错误记录约定 建议错误 span 和相关 metric 使用 error.type，同时指出已经被处理、使逻辑操作正常完成的内部错误不应写在描述整个逻辑操作的 signal 上。换言之：

  • Attempt 1 可以是 error.type=deadline_exceeded。
  • 整个 Tool Execution 最终成功时，不应把 Attempt 1 的错误复制成它的终态。
  • Agent 领域的 outcome、failure_owner 和 retry_disposition 仍是应用自己的 contract，不是 OpenTelemetry 已经定义好的 Agent 标准。

Outcome Taxonomy 要把未知与责任边界留下来

只记录 error=true，无法驱动恢复。一个最小的应用层结果记录可以包含：

字段示例回答的问题
effect.outcomesucceeded、failed、unknown当前 effect evidence 能确认什么
control_statusactive、cancellation_requested、cancelled_before_dispatchTool Execution 的控制意图与结算边界是什么
error.typedeadline_exceeded观察到了哪类错误
failure_ownertool_provider哪个边界最先拥有修复动作
retry_dispositionquery_before_retry下一步允许怎样恢复

cancelled_before_dispatch 只适用于尚未创建 Attempt 的 Tool Execution；dispatch 后的取消请求不能覆盖 succeeded、failed 或 unknown。failure_owner 不是异常在哪个进程抛出，而是哪个边界最接近决定性事实。例如 gateway 抛出 timeout，但外部存储拥有写入事实，那么 Runtime 应先凭 operation key 查询存储，而不是把 gateway 当成结果 owner。

Taxonomy 还需要保持低基数和版本化。原始 status、异常文本与 provider response 可以作为诊断证据保留，但不应直接成为无限增长的 metric label。

成本事实也必须沿同一条 Lineage 归因

开场中的两次 Tool Attempt 都可能消耗 Tool API 与网络资源；提出 Tool Call 的 Model Turn 消耗模型资源；Sandbox、Storage 或共享 cache 的生命周期还可能跨越多个 Attempt。只保留“当天 provider 总额”，无法解释一次成功 Task 为何昂贵；反过来，把所有消耗都挂在 Tool Attempt 上，又会把不同 grain 混在一起。

成本模型应先记录 component-specific usage event，再沿业务 lineage 汇总：

Component原始资源 Grain典型 Usage
Model providerModel Turn 或 model provider Attemptinput/output token、request
Tool provider / networkTool Attemptrequest、byte、provider operation
Sandboxlease、session 或计量时间窗CPU-second、memory-second
StorageArtifact/Workspace revision 与计量时间窗byte-hour、operation
Shared cache / batch共享资源事件通过 allocation key 分摊

一条概念 usage event 可以是：

{
  "usage_event_id": "usage_51",
  "component": "tool_provider",
  "resource_grain": "tool_attempt",
  "resource_id": "attempt_1",
  "quantity": 3,
  "unit": "constructed_request_unit",
  "task_id": "task_7",
  "run_id": "run_12",
  "operation_id": "op_17",
  "observed_at": "2026-07-24T09:00:00Z"
}

这是合成字段结构，不是某个 provider 的账单 schema。关键是原始 event 先绑定真正发生消耗的对象，再通过显式关系聚合；不同单位的 usage 不能在换算以前直接相加。

建议先区分三类值：

  • observed usage：provider response、资源计量或 usage event 中直接观察到的数量；
  • billed cost：可与账单或明确价格版本核对的费用；
  • allocated cost：共享 cache、batch、Sandbox 或存储按某条版本化规则分摊后的费用。

Usage 换算为 billed cost 时应保存 price_version；共享资源分摊时应保存 allocation key、allocation_rule_version 与未分摊余额。否则账单价格或分摊规则变化后，同一 Task 的历史成本会在没有解释的情况下改变。

“最终没有交付，因此这部分费用是 wasted”是对已发生 billed/allocated cost 的结果分类，应保存 classification rule version，不能伪装成 provider 直接观察到的字段。“如果没有 cache 本来会花多少钱”则是带 baseline 的 avoided-cost 反事实估计，必须另外保存 method、baseline、version 与 uncertainty。两者都不能覆盖原始 usage 与 cost fact。

回到构造例子，两个 Tool Attempt 的同单位 usage 可以先在 Tool Execution 内汇总：

attempt_1 constructed request usage = 3
attempt_2 constructed request usage = 2

tool_exec_42 constructed request usage = 3 + 2 = 5

task_7 cost
  = model_turn cost
  + tool_exec_42 cost
  + allocated sandbox/storage cost
  + 其他关联执行的 cost

Tool request usage 的分母是一条物理 Tool Attempt；Tool Execution request usage 是其全部相关 Attempt 的合计。Model usage 保持在 Model Turn/model Attempt grain，Sandbox 与 Storage 也保留自己的资源 grain；只有换算到同一货币、price version 和 allocation method 后，才沿 Run/Task lineage 合计 cost。Cost per successful Task 还必须写明时间窗和成功 Task 的定义。

用同一段执行重新计算

对开场这个构造例子，假设只观察一个 Task、一个 Tool Execution 和两个 terminal Attempts：

指标分子 / 分母结果表达
Attempt confirmed-success rate1 个确认成功 Attempt / 2 个 terminal Attempts1/2
Attempt unknown-outcome rate1 个未知结果 Attempt / 2 个 terminal Attempts1/2
Tool Execution success rate1 个最终成功 Tool Execution / 1 个 terminal Tool Execution1/1
Task completion rate1 个已交付 Task / 1 个 terminal Task1/1
Tool Execution constructed request usage两个 Tool Attempt 的同单位 usage 之和5 个构造 request unit

这些答案不再互相冲突。它们分别描述底层调用稳定性、逻辑动作恢复能力、用户结果和这次 Tool Execution 的 request usage。

一个小系统如果没有 retry、异步任务或外部副作用，可以暂时少建几个对象；但只要需要解释“结果未知后重试”“跨进程恢复”或“失败尝试也产生费用”，就必须把逻辑身份与物理尝试分开。

回到问题

第一次 Tool Attempt timeout、第二次成功，并且 backend reconciliation 确认同一 operation 只产生一个目标 Artifact 后，50% 和 100% 才可能同时成为合法答案，前提是它们明确写出 grain 与 denominator。

稳定的 Task、Run、Turn、logical operation、Tool Execution、Attempt 和 Artifact identity 负责表达业务因果；trace context 负责连接观测传播路径。Log 与 Trace 保存高基数执行证据，Metric 保存有界聚合维度；Model、Tool、Sandbox 与 Storage usage 先绑定各自的资源 grain，再沿同一 Run/Task lineage 汇总成本。

真正统一三类 signal 的，不是把所有字段复制三遍，而是让它们对“观察的是哪个对象、当前能确认什么结果、谁拥有下一步动作”给出一致答案。
