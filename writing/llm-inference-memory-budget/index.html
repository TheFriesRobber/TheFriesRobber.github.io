LLM Infra 05: Why a Runtime Can Reject Requests While GPU Memory Is Still Free

Separate the CUDA device, PyTorch allocator, and Runtime KV pool as three observation surfaces, then build an admission memory ledger for weights, KV Cache, temporary Activations, and workspace.

07/29/2026 Views
LLM InfraInferenceGPU MemoryKV Cache

The problem

GPU monitoring for a Replica still shows free memory, yet the Runtime defers or rejects a new long-Context request. A similar burst at another time triggers a CUDA out-of-memory error instead. Restarting temporarily clears the problem, but it later returns.

These three observations cannot all be reduced to “not enough GPU memory”:

  • Exhausting the Runtime’s KV block pool does not mean the CUDA allocator is already out of memory.
  • PyTorch failing to satisfy one new allocation does not mean the device has no free bytes at all.
  • nvidia-smi, the PyTorch allocator, and the serving Runtime do not report the same balance.

To decide whether another request can be admitted, the platform needs a layered GPU-memory ledger, not a single free-memory gauge.

Separate the three observation surfaces first

CUDA device

The driver sees physical and virtual memory use across the whole device. This can include allocations made by NCCL, CUDA Graphs, third-party Kernels, or other processes outside the PyTorch allocator.

PyTorch caching allocator

PyTorch distinguishes between:

  • memory_allocated(): memory currently occupied by live Tensors;
  • memory_reserved(): the total memory obtained from CUDA and managed by the caching allocator.

The official documentation explains that memory retained by the allocator but not currently used by Tensors can still appear as used in nvidia-smi. empty_cache() can return fully unused cached segments to other applications, but it cannot free memory still occupied by Tensors or create additional capacity for the current working set.

Runtime memory pools

A serving engine often reserves a KV Cache pool and manages sequence state in blocks. When that pool has no suitable free block, the Runtime may wait, preempt, recompute, swap, or reject. It becomes a CUDA OOM only when an underlying allocation actually fails.

The following statements therefore describe different facts:

device free memory > 0
allocator has reclaimable cached segments
Runtime has enough compatible KV blocks for this request

None of them alone implies either of the others.

The memory ledger must follow lifecycle boundaries

An inference Replica needs two orthogonal views. The first is a ledger of logical uses:

M_allocated_working_set =
  M_weights
  + M_kv
  + M_activations
  + M_workspace
  + M_communication
  + M_runtime

The second reconciles allocator and device observations:

PyTorch allocated ≤ PyTorch reserved
device used =
  PyTorch reserved
  + direct CUDA / NCCL / other process allocations
  + driver and runtime overhead

Weights, KV, and Activations are owner categories within allocated. reserved is an allocator observation and must not be added to those objects again, or the ledger double-counts memory. Fragmentation and headroom explain whether reserved memory can satisfy a particular next allocation; they are not additional business-memory owners.

These items also have different lifecycles:

ItemTypical lifecycleMain drivers
WeightsResident for the Replica lifetimeParameter count, dtype, quantization, parallel sharding
KV CacheGrows with active sequencesToken count, layers, KV heads, dtype, sharding
ActivationsPer Prefill/Decode executionBatch, Token budget, Kernel
Workspace / CUDA GraphResident or reused by the Runtime or a specific shapeKernel, graph capture, shape
Communication buffersResident or live during parallel-group executionTP/PP, collective implementation
Allocator / device reconciliationChanges over the process lifetimeAllocation history, segment policy, allocations outside the allocator

This explains why a long-Context request can fail while “several GB remain”: it may need not only another KV block, but also a larger Prefill workspace or a new graph/Kernel allocation. A scalar free-memory value does not express the size and pool constraints of those objects.

KV Cache is request state that grows over time

For a Transformer that stores conventional K/V Tensors, one conceptual estimate is:

KV bytes per token =
  2
  × layers
  × kv_heads
  × head_dim
  × bytes_per_element

The 2 represents Key and Value. This is not a universal formula for every model: MLA, hybrid or recurrent attention, KV quantization, Tensor/Context Parallel sharding, and specialized layouts can all change the result.

The estimate still exposes the important relationship: KV use grows with the number of active Tokens. Long outputs keep state resident for longer; long Prompts require more KV from the beginning; concurrency places multiple sequences’ state in the pool at the same time.

Capacity and admission should be divided into three layers:

static feasibility:
  whether the model/context hard limit allows the request

platform protection admission / capacity planning:
  prompt tokens + max or predicted output envelope
  → whether the request should be admitted and how much fleet headroom to retain

Runtime iteration scheduling:
  scheduled tokens for this iteration + lookahead
  → incrementally allocate the KV blocks needed for this iteration

Actual output length is known only after completion. A platform may use an upper bound or prediction for protective admission, but that is not a universal reservation rule across Runtimes. In current vLLM, for example, the scheduler incrementally invokes KV allocation using the iteration’s num_new_tokens and lookahead. A request can be admitted first and later be deferred or preempted as Decode grows and KV becomes scarce. Systems that reserve the entire output and systems that allocate incrementally expose capacity pressure at different times, and their reason codes must distinguish those cases.

Paged KV improves layout, not every source of memory pressure

PagedAttention maps a logically contiguous KV sequence onto fixed-size physical blocks. This reduces the waste caused by reserving one contiguous region for the maximum sequence length and supports block-level sharing and scheduling.

It does not eliminate:

  • internal waste in a block that has not been completely filled;
  • weights, Activations, workspace, and communication buffers;
  • direct CUDA allocations outside the allocator;
  • the capacity limit of the Runtime KV pool itself;
  • admission tradeoffs between new and existing requests.

The correct conclusion from Paged KV is “KV allocation becomes more fine-grained,” not “GPU-memory fragmentation has disappeared.”

Use three outcomes to locate the opening request

Suppose a synthetic long request needs 12 KV blocks and will trigger a larger Prefill workspace:

ObservationOutcomeCorrect interpretation
Only 8 blocks remain in the KV pool; allocator is healthyRuntime defer/preempt/rejectInsufficient KV capacity, not CUDA OOM
Enough KV blocks; new workspace allocation failsCUDA OOMThe underlying layer cannot satisfy this allocation
Temporarily succeeds after restartAllocator/Runtime state changedDoes not prove that the workload is safe

A diagnostic record should retain at least:

memory_evidence:
  device: {free_bytes: ..., used_bytes: ...}
  pytorch: {allocated_bytes: ..., reserved_bytes: ...}
  runtime_kv: {total_blocks: ..., free_blocks: ...}
  request: {prompt_tokens: ..., max_output_tokens: ...}
  execution: {phase: prefill, requested_allocation_bytes: ...}
  outcome: {kind: kv_capacity_rejected | cuda_oom | preempted}

The field names are design suggestions, not a vLLM API. The point is to align the rejection reason with the boundary that actually failed.

Back to the problem

“The GPU still has free memory” only says that one observation surface reports unused bytes. It does not prove that the Runtime KV pool has enough blocks, or that the next Activation or workspace allocation will succeed.

The opening problem should first be classified: is this a KV-capacity rejection, an allocator allocation failure, or a device OOM that includes allocations outside the allocator? Only when the memory ledger separates weights, KV, temporary execution state, and each layer’s reservations can admission and diagnostics reason about the same fact.
