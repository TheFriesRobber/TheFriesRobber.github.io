Agent Runtime 7: Live Output Is Not an Execution Record

07/15/2026 Views
AgentRuntimeStreaming

The problem

A user asks an Agent to generate a report. The browser displays model output and Tool progress, then loses its network connection just after the file write completes. When the connection returns, the page still says “Generating”:

Runtime     file.created(seq=27) → run.completed(seq=28)
Browser     last saw seq=26, then disconnected

Here, “live output” means more than token-by-token model output. It also includes Tool progress, Run state changes, and the final result continuously reaching the client.

SSE usually reconnects automatically, and an application can reestablish a WebSocket connection. Why does neither mechanism guarantee that the user will see seq 27 and 28?

Reestablishing a connection proves only that the client can receive new data again. It does not prove that anything from the disconnected interval was retained. A streaming transport handles live delivery; execution recovery needs a separate source of facts.

Reconnection is not replay

SSE’s Last-Event-ID lets a browser send the ID of the event most recently dispatched by EventSource when it reconnects. But this is a transport cursor: it does not prove that the application successfully applied the event to the UI or local state. The protocol also does not retain history for the server or tell the server where missing events must be replayed from.

WebSocket provides a bidirectional connection, but it also has no built-in persistent event log. If the server writes in-memory token deltas and state changes directly to the socket, those updates have no second read path after the connection closes.

Redis Pub/Sub does not change this result. Redis documents Pub/Sub as at-most-once: after a subscriber disconnects or fails to process a message, Redis will not send that published message again. Pub/Sub is suitable for low-latency fanout, but not as the only recovery mechanism.

The system therefore needs to distinguish two kinds of data:

TypePurposeWhat happens if it is lost?
Durable EventProve which execution fact was committedResume reading from a stable cursor
Lossy SignalTell an online consumer that new facts are availableIt may be lost; the consumer reads the source of facts again

A signal may carry the complete event to avoid one read, but receiving that payload still does not make the transport a source of truth.

A recoverable read path

When the Runtime commits an event, the order should be:

1. append the durable event and obtain a stable seq
2. commit
3. publish signal(session_id, high_watermark=seq)

Here, high_watermark is the largest committed Session sequence in the same Event Log. It is not the latest signal observed by a gateway or the local progress of one connection. Only a watermark from the source of facts can tell the client how far catch-up may proceed.

Do not publish the signal before writing the event. A client could wake up before the fact is readable and, if no later signal arrives, never know that it should query again.

The first page load and every reconnection should use an explicit application cursor. It advances only after events have been applied successfully, idempotently, and in order. If the cursor and local state cannot be saved atomically, the client should replay from an earlier position rather than skip an event merely because EventSource dispatched it.

GET /sessions/session_17/events?after=26
→ seq 27 file.created
→ seq 28 run.completed
→ next_cursor=28

After catching up to the current high watermark, the client continues receiving real-time signals. Each signal triggers a read after the client’s applied cursor rather than blind trust in the signal payload. Duplicate signals may cause redundant empty reads, but they do not change already applied state; a gateway or client that wants to reduce those reads can coalesce equal or lower watermarks. A missed signal can be repaired by reconnection, periodic reconciliation, or a later signal with a higher watermark.

Catch-up and subscription have a race too

One easy-to-miss window remains: the client reads through seq 28, but seq 29 appears before the subscription starts. If the signal for seq 29 is also published before subscription, the client still misses it.

Several approaches can close that window:

  • Establish the subscription first, then read the durable log and deduplicate by cursor.
  • During subscription setup, return a watermark in the same handshake after the subscription is active, then read through that watermark.
  • Treat signals only as wake-ups and keep a low-frequency reconciliation loop.

The common principle is not a particular API: correctness comes from cursor-based reads against the source of facts; subscription only reduces discovery latency.

Return to the opening example. Even if the browser misses every real-time notification for seq 27 and 28, it can reconnect and recover both from cursor 26. Recovery no longer depends on the exact millisecond when the network failed.

That catch-up guarantee holds only within the Event Log’s retention window. If the client’s cursor predates the oldest retained sequence, the server should return an explicit cursor_expired response or gap instead of silently starting from a later position. The client then rebuilds the page from a current Snapshot or complete Message projection. That response must carry its own as_of_seq, and the client catches up from seq > as_of_seq. It must not read a Snapshot and then use a separately fetched, later high watermark as its new cursor, because an event committed between those reads would be skipped permanently.

Token streaming and execution events have different grains

Model tokens can be numerous, and many intermediate deltas do not need permanent storage. They can remain lossy while the Runtime periodically commits coarser durable events:

assistant.output.started
assistant.output.delta      # lossy real-time fragment
assistant.message.completed # durable final message

If the product must restore output character by character after a disconnect, it needs to persist chunked deltas and accept the additional storage and replay cost. Otherwise, a more common boundary is recovery to the latest complete message or Tool event rather than reconstruction of every token the user once saw.

This is a product semantic choice. Using SSE does not decide it automatically.

Slow consumers need bounded buffers

A durable log prevents lost facts, but it does not justify unbounded buffering in the real-time path. If the model generates deltas quickly while a mobile client reads slowly, an unbounded queue turns backpressure into unbounded memory growth.

The real-time layer needs explicit answers to these questions:

  • How many messages or bytes can one connection buffer?
  • Which deltas may be coalesced or dropped?
  • How far may a consumer fall behind before the server disconnects it and requires cursor-based recovery?
  • Must terminal events and approval requests enter the durable log first?

A full bounded queue should not block the entire Agent Runtime while it waits for one slow browser. If the event is already durable, the server can disconnect that subscriber. If the update is only a lossy delta, the server can coalesce or drop it and make the UI degradation explicit.

Cancellation cannot depend on the connection either

A closed WebSocket does not necessarily mean that the user cancelled the Run; the network may simply have changed. Conversely, if the socket closes after the user clicks Stop, the cancellation intent must not disappear with the connection.

Cancellation should therefore use an independent, confirmable control path that writes durable state before notifying the executor. A transport disconnect may trigger resource cleanup or a short grace period, but it must not be interpreted directly as business cancellation.

Likewise, propagating cancellation from the Runtime to a Provider proves only that the local system requested a stop. Whether the Provider or Tool has already produced output or a side effect still has to be confirmed through its own protocol.

Back to the problem

SSE, WebSocket, and Redis Pub/Sub can all make updates visible to online users faster. Reestablishing a connection, however, does not replay history.

A recoverable Agent Streaming design first commits a Durable Event with a stable sequence, then sends a lossy real-time signal. The client maintains an applied cursor, catches up incrementally within the retention window, and rebuilds from a complete view after the cursor expires. The real-time path can then optimize for latency while the fact path independently provides recovery; neither has to pretend to be the other.
