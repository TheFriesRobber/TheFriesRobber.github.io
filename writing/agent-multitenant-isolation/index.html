Agent 27: Tenant-Private Objects Must Carry Their Isolation Domain

Propagate tenant identity into Queues, caches, Artifacts, Traces, Credentials, and background execution to prevent derived objects from leaking across tenants.

07/24/2026 Updated 07/27/2026 Views
Agent ProductionAgentSecurityMulti-Tenancy

The problem

Tenant A and Tenant B each ask an Agent to summarize a file named quarterly-report. The API entry point authenticates the tenant correctly, but the cache uses only this key:

summary:quarterly-report

After Tenant A runs first, Tenant B hits the same cache entry and receives A’s summary. The request did not cross the authorization boundary at the entry point. The leak occurred in a derived object: the cache entry lost its tenant binding when it was created.

An Agent system continuously creates Messages, Jobs, Memory, Artifacts, Credentials, and Traces. Checking the tenant once at the API Gateway cannot protect the later writes, indexing, recovery, and reads of those objects. Every derived object must declare an isolation domain. An object containing tenant-private data, resource identity, or an authorization decision must bind the tenant and enforce that binding at the boundary that owns the resource.

Tenant is not an alias for user

One user may belong to several tenants, and a service actor may execute work on behalf of one tenant. Keep these concepts separate:

  • subject: whose goal is represented;
  • actor: who is acting;
  • execution identity: which workload sends the call;
  • tenant: which isolation domain owns the data and policy.

The tenant must come from an authenticated entry point or trusted delegation—not model arguments, file content, or an unverified Queue attribute. Downstream code can carry a tenant reference but cannot rewrite it.

These bindings may be implemented as explicit fields, controlled namespaces, opaque owner references, or tenant-scoped credentials. Not every table needs a column named tenant_id. The invariant is that the association cannot degrade into “the caller must remember to filter” when it crosses a boundary.

A cache is part of the authorization path

Change the opening key to:

summary:{tenant_id}:{artifact_id}:{artifact_revision}:{policy_revision}

This prevents the obvious collision, but a key alone is insufficient. The cached value should also retain its owner or reference, and the adapter should verify the current request’s tenant and scope after a hit. Otherwise, one incorrect key write amplifies the leak over time.

Other implicit sharing paths include:

  • an embedding cache deduplicated only by text hash that returns tenant-private metadata;
  • a retrieval cache reusing results from a different authorization filter;
  • a negative cache still claiming that a resource does not exist after permissions change;
  • a model-response cache ignoring differences in Tool Surface, policy, or Context provenance.

Computed results that contain no tenant data can be shared, such as tokenizer output for public text. Such a value should explicitly belong to a public/shared isolation domain rather than masquerade as ownerless. Once a value includes private content, resource identity, or an authorization decision, it must bind the tenant and include the relevant boundaries in both the key and the read check.

Queues and recovery most easily lose the binding

A background Job may run long after the original request ends. It needs at least a stable job_id, tenant reference, delegation reference, and target resource:

{
  "job_id": "job_42",
  "tenant_ref": "tenant_3",
  "delegation_ref": "del_81",
  "resource_ref": "artifact_19",
  "operation_id": "summarize_19_r4"
}

A worker cannot trust these bare fields and query the database directly. It claims the Job with its own execution identity and resolves the delegation through a trusted service. A retry Attempt must reuse the same tenant binding rather than derive it from the current worker’s default tenant or global configuration.

The same applies when restoring a Session, Workflow, or Checkpoint. If durable state has no tenant ownership, the system cannot safely determine who may restore it. It should stop and quarantine the state instead of guessing from a resource name.

Workspace and Sandbox reuse must reestablish the tenant binding

A Runtime pool or volume pool can easily confuse “cleaned” with “safe for any tenant.” An unbound pooled resource belongs only to an explicit shared/unbound domain. During acquire, the Control Plane atomically binds the target Session tenant, Workspace owner, lease generation, and policy revision. The Runtime’s mount observation must read the same Workspace identity; the existence of a /workspace path is insufficient.

Refresh and recovery compare the same bindings. After Tenant A’s lease expires, a healthy old Runtime cannot be handed directly to Tenant B while retaining A’s mount, credentials, processes, or writable overlay. Before returning it to a pool, the Control Plane stops admission, revokes tenant-scoped credentials, detaches or quarantines the Workspace, and waits for cleanup evidence to converge. A resource whose owner cannot be proved enters quarantine.

Artifact materialization and Workspace export check both owners too. An Artifact reference owned by Tenant A cannot enter Tenant B’s Workspace merely because a path or Blob hash matches. When a Workspace publishes a new Artifact, the output inherits the current isolation domain unless trusted policy performs an audited cross-domain copy.

Storage partitioning is not complete authorization

Separate databases, schemas, or partitions per tenant can reduce accidental queries and the failure radius, but they do not automatically protect every path:

  • an administrative service may still hold a cross-tenant credential;
  • an export Job may bypass online query filters;
  • an Artifact URL may leak to another tenant;
  • a Trace backend may place spans from all tenants in one searchable index.

Partitioning is therefore defense in depth. Reads and writes still require authorization against the current tenant, action, and resource at the resource owner. When a database supports row-level security, some enforcement can move into the database, but connection identity, session variables, and bypass privileges still need trusted management. “We use RLS” is not proof of end-to-end isolation.

Check four bypass paths during design

After the online API works, test four paths that are easy to miss:

  1. Background retry: when the Job is redelivered, does the worker still resolve the original tenant rather than use a default?
  2. Data export: does the export service authorize each Artifact, Memory record, and related file instead of checking only the export request?
  3. Sandbox pooling: before Tenant B acquires Tenant A’s old Runtime or volume, have the old mount, credentials, processes, and overlay all become unusable?
  4. Observability: do Trace and Log queries, sampling, and export retain the tenant boundary and minimize sensitive fields?

If any one of these paths treats tenant as optional metadata, it can bypass isolation at the entry point.

Back to the problem

The opening summary cache should bind Tenant A, the Artifact identity, its revision, and the policy that produced the result. Tenant B cannot hit A’s value even with the same filename and query. After a cache hit, the adapter still verifies that the current tenant may read the corresponding Artifact.

The same binding then enters Jobs, Sessions, Workspaces, Sandbox leases, Memory, Artifacts, Credentials, and Traces, where each trusted owner enforces it on both writes and reads.

Multi-tenant isolation is not one WHERE tenant_id = ? at the entry point. It is an object invariant: every durable or derived state must declare an isolation domain. Tenant-private state that cannot prove which tenant owns it must not be consumed, restored, or exported automatically.
