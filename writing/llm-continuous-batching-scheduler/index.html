LLM Infra 06: How Continuous Batching Changes Request Scheduling

Start from sequences of different lengths arriving continuously, then explain iteration-level scheduling, Token/KV budgets, fairness, chunked prefill, and preemption.

07/29/2026 Views
LLM InfraInferenceContinuous BatchingScheduling

The problem

Three requests enter the model together: A produces a long output, while B and C finish quickly. If request-level batching must preserve that group, the execution slots vacated by B and C remain idle. Allowing new requests to join each iteration can improve throughput, but A may then be deferred repeatedly by new arrivals or KV pressure.

Continuous Batching does not solve “the Batch size is too small.” It moves the boundary where the execution set may be regrouped to the model iteration. That change creates more reuse opportunities while making Token budget, KV capacity, ordering, and preemption explicit scheduler responsibilities.

A request batch and an iteration batch are different objects

Orca distinguishes traditional request-level scheduling from iteration-level scheduling. The latter executes one model iteration, then reconstructs the next batch according to which requests have finished and which new requests have arrived.

The following conceptual trace does not represent actual GPU timing:

Iteration 1: active = {A, B, C}
Iteration 2: B finished; active = {A, C, D}
Iteration 3: C finished; active = {A, D, E}

Three kinds of order must remain distinct:

request arrival order
≠ per-iteration execution grouping
≠ request completion order

Not every non-continuous implementation mechanically waits for the entire batch to finish; an implementation can also shrink the active batch. The real distinction is whether the scheduler can admit new work at an iteration boundary and safely map the changed state into the next model execution.

The scheduler allocates Token and state budgets each iteration

For each runnable request, the scheduler needs to know at least:

  • which Token has already been computed;
  • whether the request is currently in Prefill or Decode;
  • how many Tokens it may advance in this iteration;
  • how many KV blocks it already holds and how many more it needs;
  • whether it has reached max tokens, a stop condition, or cancellation;
  • its priority and arrival time, plus any platform-specific deadline policy.

Current vLLM SchedulerConfig includes per-iteration max_num_batched_tokens, max_num_seqs, chunked prefill, and FCFS/priority policies. Its V1 scheduler processes running requests within a token budget and allocates KV slots; when it cannot allocate them, it may preempt according to policy.

These are implementation facts from one Runtime, not a universal state machine for every serving engine. Deadline-aware scheduling, pause/resume terminology, and preemption cost are still defined by each implementation and platform policy.

Chunked Prefill lets both phases share an iteration

If one long Prefill enters an execution as a single unit, existing Decode sequences may wait longer. Chunked Prefill divides a long Prompt into token chunks so the scheduler can mix Prefill and Decode within its token budget.

This introduces new tradeoffs:

  • If the chunk is too large, Decode can still experience long gaps.
  • If the chunk is too small, scheduling and Kernel efficiency may deteriorate.
  • Prioritizing Decode can protect TPOT while increasing TTFT for a new long Prompt.
  • Prioritizing Prefill can establish a new sequence quickly while affecting requests that are already streaming.

max_num_batched_tokens is therefore not merely a throughput parameter. Together with the Prefill chunk policy, it determines TTFT, TPOT, Batch opportunities, and fairness.

When KV is scarce, preemption is not a free pause

The previous article’s memory ledger showed that active sequences continue to hold KV blocks. When new requests need more blocks than the pool can provide, the scheduler can:

  • decline to admit a new request;
  • defer a lower-priority request;
  • preempt a running request and recompute or swap its state when it resumes;
  • reject the request with a stable reason code.

Regardless of the choice, preemption is more than “put the task back in the queue.” It changes:

  • whether previously computed Tokens remain available;
  • whether KV state must be rebuilt;
  • whether earlier computation becomes repeated work;
  • whether the request can still meet its deadline;
  • how usage and outcome should be recorded.

The Runtime’s preemption count and KV usage are therefore important evidence. Frequent preemption may mean the Token/KV budget does not match the workload, rather than that “the GPU is not busy enough.”

Throughput, fairness, and latency require different policies

Continuous Batching does not inherently cause starvation, and it does not automatically provide fairness. The result depends on policy.

Policy preferencePotential benefitMain risk
Maximize Tokens in this iterationAggregate throughputLong Prefills or large requests consume the budget
Prioritize DecodeStable streaming TPOTHigher TTFT for new long Prompts
Shortest-job-likeShort requests finish soonerLong requests wait indefinitely
FCFSEasy-to-explain orderingHead-of-line blocking
Priority / deadlineProtect important requestsLow-priority starvation; requires aging

The platform should treat policy as an SLO decision rather than hiding it in a batch-size default. If the Runtime only exposes FCFS/priority, deadline and tenant fairness may need to be enforced by upper-layer admission. That upper layer still cannot pretend to own iteration-local KV state.

Walk the opening requests through the scheduler

Suppose A, B, and C start together, while D and E arrive later:

I1: A/B/C Prefill
I2: A/B/C Decode
I3: B finish; admit D; A/C/D active
I4: C finish; E arrives, but KV budget insufficient

At I4, the correct record is not merely “E is queued”:

scheduling_decision:
  iteration: 4
  runnable: [A, D]
  waiting: [E]
  token_budget_remaining: 32
  kv_blocks_free: 1
  kv_blocks_required_for_E_this_iteration: 2
  decision: defer_E
  reason: insufficient_kv_budget
  policy: fcfs_with_decode_priority

If A is later preempted, the record must also describe its KV state and recompute outcome. The same trace can then explain both the throughput gain and the harm to the long request.

Back to the problem

Continuous Batching allows D and E to enter as soon as B and C finish, reducing idle capacity caused by a fixed request-level group. It also forces the scheduler to reallocate Token and KV budgets every iteration and to make Prefill/Decode ordering, fairness, and preemption explicit.

The optimization goal therefore should not be “make the Batch larger.” It should be: for a specified workload and SLO, which iteration policy produces higher goodput without making long requests, low-priority requests, or already-streaming requests lose explainable progress?
