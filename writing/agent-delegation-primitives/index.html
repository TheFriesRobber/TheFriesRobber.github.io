Agent Runtime 10: Who Should Execute a Subtask?

07/17/2026 Views
AgentRuntimeWorkflow

The problem

A user asks an Agent to compare three technical approaches. The primary Agent may split its Plan into three research directions, or discover them dynamically while reasoning:

subproblem A  research approach A
subproblem B  research approach B
subproblem C  research approach C

Three terms need stable meanings up front. A SubAgent is a Child Run started dynamically and still owned by the parent Agent’s current Run. A Child Job is a unit of work owned by a durable job system and claimable by another worker. Workflow Fanout means that a workflow controller starts several nodes according to known dependencies and owns their join. Frameworks may use different names; this article compares their state owners.

These records say only that three subproblems remain. They have not created a SubAgent or background Job. A Plan item does not own an execution lifecycle, and a delegation proposed by the model is still only a request. The Runtime or business controller must decide whether the current parent Run will wait for a child, a durable Job system will take ownership, or a workflow controller will manage the branches and their join.

All three implementations can be drawn as parallel arrows. Yet they require completely different behavior when the parent process exits, the user cancels, or only two branches complete.

“Can run in parallel” is therefore not enough to choose an execution primitive. The real questions are: who converges the child work’s state, who consumes its result and completes delivery, and where is its content stored?

The source of a subproblem does not choose the execution primitive

A subproblem can originate in three places:

  • The Agent Loop discovers that more research is needed during the current reasoning process.
  • A revisable Plan adds another unfinished item.
  • A deterministic business process declares a set of branches in advance.

The source explains why the work exists, but not who is responsible for completing it. Before comparing execution primitives, compress the request into a few ownership-related conditions:

goal                  what must be delivered
needed_within_parent  whether the parent Run must consume the result before becoming terminal
survive_restart       whether recovery across workers or processes is required
independent_lifecycle whether the parent Run may finish first, or the work may be cancelled, retried, or delivered independently
known_dependencies    whether branches and joins are known in advance
delivery_owner        who consumes the result and completes the user-facing delivery

At this point, the delegation proposal is still a request for child work that does not depend on a particular execution primitive. Only after the system chooses SubAgent should the model or parent Runtime create a SubAgent-specific spawn_agent request. A trusted Runtime must still validate the Tool Surface, budget, and authorization before it creates the actual Child Run. The next article, Agent Runtime 11: How a Spawn Request Becomes a Controlled Child Run, covers that process. This article first decides which state owner should receive the proposal.

The core differences among three delegation primitives

These names are semantic categories. Workflow Fanout provides recovery across processes only when its history or state is durable. The decision rests on the following dimensions:

This is a semantic classification, not a product feature comparison. An Artifact store provides storage and retention; it does not decide whether work is complete and does not necessarily deliver results to the user. A SubAgent framework may also persist its Child Runs. That persistence adds recovery responsibility, but the work becomes a Child Job in the sense used here only when state ownership explicitly moves to a durable job system.

When to choose a SubAgent

Suppose the primary Agent discovers during reasoning that it needs a temporary specialist. If the parent Run will consume the result before becoming terminal and remains responsible for converging child state, a SubAgent is usually the most natural choice:

parent Agent: I need to compare database options first
→ start a database-research SubAgent
→ wait for structured conclusions and evidence
→ parent Agent validates them and continues the response

This work has three defining properties: the model creates the goal dynamically, the child result serves the current Run, and the parent Agent remains responsible for the final answer. Cancelling the parent Run should usually cancel the child as well. Once the parent Run has ended, an orphaned child result often has no consumer. A parent Tool Execution can wait synchronously, or save a handle and collect the result later; synchronous versus asynchronous collection changes how the result is gathered, not who owns the state.

If the child is only an in-process async work item, it disappears when the worker crashes. That is not an error if the API never promised recovery. A durable Runtime can instead persist the parent Run, Child Run, and handle, then recover them in a new worker while the parent Run continues to own the child. Recovery across processes determines persistence responsibilities; it does not automatically determine lifecycle ownership.

When to promote work to a Child Job

Suppose one branch must crawl a large collection of public documents, generate a PDF, and remain available for the user to inspect after the parent Run has already become terminal. That work now has an independent lifecycle:

  • The parent Run may return “Job created” first.
  • The work must continue after the parent Run ends.
  • The Job needs its own retry budget, state, and Artifact.
  • The user may cancel or retry it independently.
  • A later Run or product page may consume its result independently.

A durable Child Job is a better fit. The parent Run stores the job_id, but it does not own the Job’s complete runtime state. The job system owns claiming, leases, recovery, and terminal state. The result is returned through a stable Artifact or completion event.

A Child Job is not complete merely because it was placed on a queue. A queue may deliver more than once, external side effects still need idempotency, and parent and child need explicit cancellation and result-retention policies.

When to use durable Workflow Fanout

If the business process defines all three branches before execution and a fixed aggregation step can begin only after they finish, workflow fanout is the better fit:

prepare input
├─ analyze A
├─ analyze B
└─ analyze C
   ↓
compare results
   ↓
publish report

The point is not to let three Agents negotiate freely. The controller needs to understand dependencies, retries, partial completion, and join conditions. If it persists workflow history or state and defines a replay and recovery contract, those records can become recoverable control-flow facts. A fanout-and-join shape by itself does not create durability. Branch results may still live in a business database or Artifact store.

A model may participate in one node, but it should not rewrite workflow terminal semantics that have already been promised. For example, “continue when two branches succeed” should be an explicit join policy, not a decision improvised by the aggregation Agent.

Choosing for the same example

Return to the request to compare three technical approaches and ask these questions in order:

  1. Who owns the child work’s state, retries, and terminal outcome? It is a SubAgent in this article only when the parent Runtime converges a Child Run for the current Run. It is a Child Job when a job system claims, retries, and terminates the work independently, even if the parent Run waits for it.
  2. Must the parent Run consume the result before it ends? This determines whether the parent waits and who completes final delivery; it does not determine the work-state owner by itself.
  3. Must the work continue, be cancelled separately, or deliver independently after the parent Run ends? That is a strong signal for a Child Job or durable workflow node, but it is not a requirement for every Child Job.
  4. Are the branches and dependencies defined in advance by a deterministic business process? If yes, prefer Workflow Fanout.
  5. Who consumes the branch results and completes final delivery? That object must define join, cancellation, and failure policies. It is not necessarily the component that stores the Artifact or owns the child execution state.

For a single interactive response where all three research branches finish within tens of seconds and their results do not need to survive user cancellation, three SubAgents managed by the parent Run are enough.

Suppose one branch converts report.md to PDF. The parent Run waits for the result, but a durable scheduler owns queue delivery, worker claims, retries, and the Job terminal state. It is still a Child Job. The parent Run consumes the result; it does not own the work state.

If every branch produces an independent report, the parent Run may finish first, and later Runs or product pages consume those reports separately, create three Child Jobs and let a later aggregation Job wait for their Artifacts. Long duration by itself is not the promotion criterion; independent lifecycle and delivery responsibility are.

If the same analysis pipeline runs every day with a branch set and aggregation rules known in advance, use workflow fanout. The primary Agent does not need to “invent” the scheduling structure again.

Do not record “cancellation request sent” as “child work stopped.” Every primitive must distinguish the request, its acknowledgement, and final convergence.

Workflow systems such as Temporal even expose a Parent Close Policy that can terminate a child, request cancellation, or let it continue when the parent ends. That is direct evidence that parent-child lifecycle is not determined automatically by a nested call.

Composition is usually better than unification

A complex system does not have to choose exactly one primitive. A durable workflow node may start an Agent Run, and that Agent may use a SubAgent inside one Model Turn. If the SubAgent discovers long-running work, it may create a Child Job through a controlled Tool.

Composition must preserve identity:

workflow_execution_id
→ job_id
→ run_id
→ child_run_id

These IDs represent different grains and cannot all collapse into one parent_id. A Trace may connect them, but retry, state, and cost still belong to their respective owners.

Back to the problem

Three subproblems produced by a Plan or Agent Loop do not mean that three SubAgents already exist. They reveal only three units of work that still need completion.

SubAgent fits dynamic collaboration whose state the parent Run converges. Child Job fits work whose claims, retries, and terminal outcome belong to a durable job system. Durable Workflow Fanout fits control flow with explicit dependencies and join rules managed by a persistent controller. Choose only after deciding who converges the work state, who consumes and delivers the result, and where the content is stored. Otherwise the system may wait until the parent process exits to discover that nobody was ever responsible for finishing the work.
