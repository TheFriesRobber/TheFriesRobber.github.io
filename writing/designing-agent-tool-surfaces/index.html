Agent Tools 3: Assemble a Tool Surface for Each Task

07/14/2026
AgentToolsAPI Design

The problem

An Agent may start with only five Tools: search the web, read a file, write a file, inspect a calendar, and send a message. As connectors (adapters to external systems), device capabilities, business operations, and administrative actions accumulate, the registry can quickly grow to dozens or hundreds of definitions.

Sending every Tool name, description, and parameter schema to the model on every Model Turn creates at least three problems:

  • Tool definitions consume input tokens. A token is a basic unit used to measure model input; more complex schemas generally mean more input.
  • Similar capabilities appear together, so the model must route within a larger choice set.
  • Capabilities irrelevant to the task—or unavailable to the current user—may enter the model context.

Simply hiding every low-frequency Tool does not work either. A model cannot choose a capability it cannot see. If discovery fails, a capability can exist in the system while remaining unreachable in practice.

The central Tool-surface question is not how to fit more Tools. It is: for this Run, which capabilities should be immediately callable, which should be discoverable on demand, and which should not appear at all?

Think of the registry as every tool in a warehouse and the Tool surface as the small set placed on the model’s desk for this task. The warehouse can be large; the desk should contain only what is both allowed and likely to be useful now.

A Run here means one Agent Loop: it begins with user input or a resume action and ends with final output, an explicit resumable pause, failure, or cancellation.

Define the sets first

Four sets need to remain distinct:

SetMeaningTypical decision owner
RegistryEvery Tool installed by the system and available to constructCode, plugins, connector catalog
Allowed setTools permitted for the current user, situation, and resource scopeAuthentication, authorization policy, feature flags, dependency availability
Initial surfaceComplete definitions the model can call when the Run beginsSurface policy
Unlocked setTools loaded during the Run through on-demand discoverySearch results and renewed authorization

These sets should not collapse into one allTools array. The registry answers “what does the system have?” The allowed set answers “what may this Run use?” The surface answers “what can the model see now?”

The order matters: filter for permissions and context first, then divide the allowed set into eager and deferred Tools. Discovery finds a capability; it does not authorize one.

If the application indexes the complete registry and checks authorization only at call time, search results can still reveal the names and descriptions of unauthorized Tools. That leaks capability information and encourages the model to plan a path that is guaranteed to fail.

Eager, deferred, and disabled are different states

A Tool can occupy one of three states in a Run:

StateWhat the model sees initiallyGood fitMain cost
eagerFull name, description, and schema; immediately callableFrequent, clearly required by the task, or expensive to missPersistent context cost and a larger direct choice set
deferredA searchable summary, namespace, or index entry; full definition loaded on demandInfrequent, large-schema, or specialized connector capabilitiesAn extra discovery step and possible missed recall
disabledNothing; unavailable even through discoveryUnauthorized, missing a dependency, disallowed in this context, or turned offCompletely unreachable in the current Run

disabled is not a deeper form of deferred. If the current user may not send an external message, that capability should not enter the searchable set. The system cannot show it to the model and rely on restraint.

A Tool also need not stay in the same category forever. search_web may be eager during research and disabled during a local formatting task. export_spreadsheet may be deferred in a general conversation and eager in an explicit data-export task.

Classification is therefore a property of a Tool within this Run, not a permanent attribute of the Tool class.

How to decide whether a Tool should be eager

“Frequent means eager; infrequent means deferred” is only a starting point. A useful decision considers at least five dimensions.

Need that can be predicted from the task

When the task type already signals its goal, use that information to narrow the surface. File-editing tasks normally need file reads and writes; research tasks normally need search and page retrieval. The model should not have to perform an extra search to discover the basic capabilities of its assigned task.

Cost of missed recall

Some Tools are infrequent but serve as critical controls. request_user_confirmation and report_blocker may rarely be called, but without them a model may guess or continue down an invalid path. Such Tools often belong in the eager set.

Context occupied by the definition

A query Tool with two arguments and an enterprise-system connector with dozens of fields and several operations do not have the same initial cost. Measure the serialized tool-definition tokens rather than counting Tool names.

How naturally the capability can be discovered

The model must form a search query from the current conversation. If a user says, “sync these results to my knowledge base,” a knowledge_base namespace—a named group of related Tools—is easy to discover. If the capability name differs sharply from user language or requires an internal term that the model cannot know, deferring it raises the risk of missed recall.

Whether an extra round trip is acceptable

On-demand discovery usually adds a search, a load, or another Model Turn: one more round trip between the application and model. For a short interactive Task, that delay may cost more than the tokens it saves. For a long Task, avoiding a large schema on every Model Turn can be more valuable.

Turn these dimensions into an explicit review table instead of relying on intuition:

QuestionFavors eagerFavors deferred
Is the current task likely to need it?YesNo
Would missing it derail the task or prevent recovery?High costLow cost
Is the full schema large?SmallLarge
Does user intent map naturally to its namespace or summary?DifficultEasy
Is the additional discovery latency acceptable?NoYes

The table deliberately has no universal thresholds. Classification should be calibrated with evals and traces, not by mechanically deferring every “large Tool.”

The full lifecycle of on-demand discovery

A provider-neutral flow can look like this:

1. Resolve Run context
   user identity + scenario + policy + available dependencies

2. Build allowed set
   registry -> authorization -> scenario policy -> dependency checks

3. Build initial surface
   eager tools: full definitions
   deferred tools: searchable summaries or namespaces

4. Discover
   model emits a capability query or selects a namespace

5. Re-authorize and load
   validate result is still allowed -> load full definitions -> deduplicate names

6. Call
   model invokes the unlocked Tool -> handler and backend validate again

Several checkpoints in this flow are essential.

First, a search result is not permission to execute. Before unlock, the application must recheck identity, feature flags, and dependencies because those conditions can change during a long Run.

Second, the contract must specify when an unlocked Tool becomes callable. Some runtimes can search, inject a definition, and continue the call within one model response. Others add the definition to context only on the next Model Turn. The application must trace this transition instead of assuming identical Model Turn behavior across platforms.

Third, Tool names must be unique in the final surface. Different connectors in the registry may both export search or list_items. If their names collide after loading, neither the model nor the gateway can route reliably. Namespaces, stable prefixes, or an explicit transformation should resolve collisions before definitions reach the model.

OpenAI’s current Tool search supports both hosted search, where the platform performs the search, and client-executed search, where the application does. The former suits candidate sets known at the start of a request; the latter lets the application resolve candidates from its own state. At the time of this article’s update, the official documentation limits this feature to GPT-5.4 and later models, so applications should verify current support before depending on it. The product interface will evolve, but the underlying boundary is general: a platform or an application may perform the search, while the application must still define candidate capabilities and own authorization.

What belongs in a discovery index

Deferred does not mean invisible. The model needs enough information to decide which capability category is worth searching.

A namespace or index entry might contain:

{
  "name": "calendar",
  "summary": "Read availability and create calendar events.",
  "capabilities": ["availability", "scheduling"],
  "side_effects": ["create_event"]
}

It does not need the complete parameters for every function, but it should meet three conditions:

  1. Use the language of user tasks rather than only an internal service name.
  2. Distinguish reads from writes so a model does not load a high-risk mutation surface merely to inspect data.
  3. Exclude capability metadata that the current user is not allowed to know.

An entry that is too short hurts recall. One that is too long merely moves the token cost of a full schema into another location. A small number of clear namespaces, each containing semantically related Tools, is generally more reliable than one enormous “misc” directory.

Search results should also be bounded. Loading too many Tools causes the surface to expand again during the Run and defeats the purpose of discovery. Returning only the top-scoring k results—Top-k—is common, but k should depend on Tool similarity, task complexity, and eval results rather than a universal constant.

Failure and fallback must be explicit

Discovery can fail because search returns no result, the index is stale, a provider lacks support, the network is unavailable, or the model never searches.

A tempting but dangerous fallback is to expand every deferred Tool whenever Tool search fails. That may improve recall, but it can abruptly increase token use, disrupt prompt caching, and replace the capacity-controlled surface with different behavior.

More explicit fallback options include:

  • Keep a core eager set whose token budget has been measured.
  • Provide a limited static fallback for high-value namespaces.
  • When search returns no result, provide a recoverable response that lets the model rewrite the query or explain the missing capability.
  • If the current model platform does not support dynamic loading, let an application router select a smaller static surface before the Run begins.
  • Apply the same allowed set to every fallback. A discovery failure must never broaden permissions.

The lifetime of an unlock must also be defined:

  • Model-Turn-scoped: recompute on the next Model Turn; strictest, but repeats more discovery.
  • Run-scoped: remain visible during the current Agent Run; often a good fit for multi-step tasks.
  • Session-scoped: cache across several Runs; lower latency, but greater risk from permission, version, and dependency drift.

The longer the lifetime, the more important it is to record the Tool-definition version, the policy snapshot in effect when it was unlocked, and invalidation conditions. A Tool unlocked ten minutes ago is not necessarily still permitted now.

The surface is not the entire security boundary

Removing a Tool from model context reduces accidental calls and capability leakage. It does not replace handler and backend authorization.

The reasons are straightforward:

  • Internal code may call the handler without going through the model.
  • A cache or adapter bug may inject the wrong Tool definition.
  • Resource permissions may change after the Run begins.
  • An allowed Tool can still carry an unauthorized resource ID.

The complete path still requires layered checks:

registry policy
  -> allowed-set filtering
  -> model-visible surface
  -> handler validation
  -> backend authorization
  -> storage consistency and audit

The surface follows minimum capability exposure: show the model only the capabilities required for the task. The backend enforces least privilege: the caller can access only authorized resources. The first principle reduces irrelevant model choices; the second ensures that a surface mistake cannot cross a resource boundary.

How to evaluate the eager/deferred trade-off

Reporting only “tool-definition tokens saved” encourages teams to defer more Tools while hiding losses in task success and latency. A useful evaluation should measure at least:

MetricQuestion answered
Initial tool-definition tokensHow much input did the initial surface actually remove?
Discovery recallWhen a deferred capability is needed, is it found?
Tool selection accuracyAfter loading, does the model choose the right Tool instead of a similar one?
Extra Model TurnsHow many model cycles does discovery add?
Time to first useful Tool CallHow long from the user request to the first useful Tool Call?
Task success rateDoes the token optimization hurt final completion?
Unauthorized exposure rateDo unauthorized names or schemas enter search results or the surface?
Fallback rateHow often does normal discovery fail, and which fallback follows?

Comparisons should hold the model, task set, Tool versions, and permission context constant. Include at least four kinds of cases:

  1. The task needs only core eager Tools.
  2. The task clearly needs one deferred Tool.
  3. User language differs from the Tool name, requiring semantic discovery.
  4. The user requests a capability that exists in the registry but is not authorized now.

The fourth case is especially important. The correct result is not “find it successfully, then let the backend reject it.” The capability should be absent from the candidate set, while the system explains the boundary without leaking internal details.

The optimization target is not minimum tokens. It is a verifiable balance of quality, latency, cost, and permission boundaries:

useful surface
  = enough capability to finish the task
  - irrelevant choice and schema cost
  - unauthorized exposure

This is not a single computable score. It highlights two opposing constraints: reducing the surface and keeping necessary capabilities reachable. A set of metrics must judge both.

Design boundaries

  • When an Agent has only a few clear Tools, making all of them eager is often the simplest and most reliable design.
  • Deferred loading reduces definition exposure and selection space. It does not automatically shorten Tool results, conversation history, or other context.
  • A namespace improves discovery but cannot repair an ambiguous name, description, or schema within one Tool.
  • A high-risk Tool should not be deferred merely because it is infrequent. It must be disabled when unauthorized and still needs a separate confirmation or policy step when appropriate.
  • The API for dynamic loading, current- versus next-Model-Turn behavior, and caching vary by model platform. Applications should encapsulate those differences in a surface contract: an explicit agreement about Tool visibility and loading time.

Back to the problem

As the Tool count grows, the system should not choose only between “show everything” and “hide everything.”

A more reliable order of design is:

  1. Keep every capability the system can construct in the registry.
  2. Derive the allowed set from current identity, context, dependencies, and policy.
  3. Within the allowed set, make core and recall-sensitive capabilities eager.
  4. Organize infrequent, large-schema, and discoverable capabilities into deferred namespaces or an index.
  5. Disable unauthorized or currently invalid capabilities so discovery cannot reveal them.
  6. Evaluate tokens, recall, extra Model Turns, latency, Task success, and permission exposure together.

The value of on-demand discovery is not that one Agent can theoretically connect to unlimited Tools. It is that each concrete task exposes only the small set needed to complete it.
