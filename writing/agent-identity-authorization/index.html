Identity and Authorization Must Survive the Execution Chain

Separate subject, actor, execution identity, credential, and authorization so authority can cross Queues, Tools, and Child Runs.

07/24/2026 Views
Agent ProductionAgentSecurityAuthorization

The problem

A user asks an Agent to update a report. The API entry point authenticates the user and confirms that they may currently edit the file. The system then places the task on a Queue, a background worker creates a Child Run, and the Child Run eventually calls a file Tool.

At write time, the backend sees the worker’s service credential. The audit log can say only that a worker called the API. It cannot prove which user the worker represented, which Agents participated in the delegation, or whether the original permission has since been revoked.

One apparent fix is to put the user’s access token in the Job and pass it through the Queue, Child Run, and Sandbox. This expands the exposure of a bearer credential, and the token may expire while it waits.

The execution chain does not need one continuous token. It needs a verifiable relationship: whose goal is being executed, who is currently acting, which workload sent the request, and whether the current action on the current resource is still authorized.

Five concepts answer different questions

ConceptQuestion it answersFile-update example
SubjectWhose goal and authority are represented?The user who made the request
ActorWho is acting on behalf of the subject?Agent, Child Run, or worker
Execution identityWhich workload accesses infrastructure?Worker workload identity
CredentialHow does the caller prove identity to a service?Audience-bound short-lived token
AuthorizationIs the current action allowed?file.update on file_12

These concepts cannot replace one another. A trace_id can correlate a call path but is not identity. A user_id is a claim; placing it in a Queue does not prove who wrote it. A service credential proves the worker’s identity but does not automatically express which subject it represents.

RFC 8693 OAuth Token Exchange explicitly distinguishes subject and actor tokens, as well as delegation and impersonation. An Agent system does not have to use this protocol, but it should preserve the same semantic distinction: delegation should not disguise the actor as the subject.

A Queue stores a delegation reference, not unlimited authority

After authentication at the entry point, the system can create a constrained delegation record:

{
  "delegation_id": "del_81",
  "subject_ref": "user_7",
  "actor_ref": "agent_run_19",
  "tenant_id": "tenant_3",
  "actions": ["file.update"],
  "resources": ["file_12"],
  "audience": ["file-service"],
  "expires_at": "...",
  "parent_delegation": null,
  "status": "active"
}

The Job carries only the delegation_id and the stable identities needed to complete the work. The worker claims the Job with its own workload identity, resolves the delegation through a trusted authorization service, and obtains a short-lived credential for the file service. A long-lived user token never enters the prompt, Queue payload, or Workspace.

This design does not freeze permission at the entry point. Before execution, the worker still checks whether the delegation has expired or been revoked, whether the subject may still access the resource, and whether the action and audience match.

A Child Run may only narrow delegation

A parent Agent that can modify an entire project does not imply that a summarization Child Run needs write permission. When creating the child, a trusted Runtime should establish that the child’s authority is a subset of the parent’s:

parent: files.read + files.write on /project/**
child:  files.read on /project/docs/**

Delegation can narrow the action, resource, tenant, audience, validity period, and delegation depth. Natural language returned by a Child Run cannot expand these boundaries. Its execution identity also cannot be derived from run_id alone; a trusted execution environment must bind and authenticate it.

If a later step truly requires broader authority, the system should return to the subject that can grant it instead of letting the model place a larger scope in Tool arguments.

RBAC, ABAC, and capabilities are complementary layers

These models are often presented as alternatives, but they fit state with different degrees of stability:

  • RBAC expresses stable responsibilities, such as an editor being able to propose file updates.
  • ABAC evaluates attributes such as tenant, resource owner, classification, and time.
  • A capability or delegation grant expresses temporary, transferable but constrained authority over a particular action and resource.

A practical decision might use RBAC to establish that the subject has an editing role, ABAC to check the file’s tenant and current state, and then issue a short-lived grant valid only for file_12, file.update, and the file service.

This is a design composition, not a fixed sequence required by a standard. In a simple system where requests do not cross a boundary, direct RBAC/ABAC evaluation by the backend against the authenticated user may be enough. A stable delegation reference becomes necessary when execution is asynchronous or delegated.

The model proposes arguments; the backend authorizes execution

The model may propose:

{"tool": "update_file", "fileId": "file_12", "expectedRevision": 7, "patch": "..."}

The model-visible fileId must come from a canonical resource reference that the Runtime has resolved and is authorized to expose. If the user initially supplied a path, a trusted boundary first resolves it to a resource identity bound to a revision before it enters the proposal. The model cannot authoritatively supply subject_id, tenant_id, an authorization decision, or a credential. The Runtime injects those fields from the trusted Session and delegation. The Tool handler checks arguments, revision, and policy, and the backend that owns the resource facts authorizes again:

// Conceptual example
await fileService.update(
  {fileId: args.fileId, expectedRevision: args.expectedRevision, patch: args.patch},
  {
    subject: trusted.subject,
    actor: trusted.actor,
    executionIdentity: trusted.executionIdentity,
    delegation: trusted.delegationRef,
    tenant: trusted.tenant
  }
);

Final enforcement must be close to the resource because only the backend knows the file’s current owner, revision, classification, and policy. A Tool description, system prompt, or model claim that an action is authorized is not a trusted authorization fact.

Audit the identity chain, not only the caller

A useful audit record links at least:

subject → actor chain → execution identity
        → delegation revision
        → tenant + action + resource
        → authorization decision + effect outcome

This does not mean recording every token or prompt. Credential records normally contain only issuer, audience, key/token reference, and expiry metadata; the secret itself should not enter logs. Audit also needs to separate the authorization decision from the eventual effect so that “the call was permitted” is not recorded as “the update succeeded.”

Back to the problem

The opening worker should not update the report using only a shared service token. After claiming the Job, it uses its workload identity to resolve a still-valid delegation and obtains a short-lived credential for the file service. The file service then authorizes against the current subject, actor, tenant, action, and state of file_12.

The backend can now reject the action after user permission is revoked. The Child Run can use only its narrowed grant. The audit record can identify whose goal, which actor, and which workload participated in the action.

Identity continuity does not mean forwarding one credential to the end of the chain. The verifiable delegation chain is continuous; authorization is evaluated again at the boundary that owns the current resource facts.
