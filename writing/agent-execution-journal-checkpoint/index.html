Agent 10: Execution Journals and Checkpoints Must Recover Together

Recover Agent state without repeating unknown effects by combining an authoritative Journal, idempotent projections, and cursor-bound Checkpoints.

07/27/2026 Updated 07/27/2026 Views
Agent CoreAgentRecoveryEvent Log

The problem

An Agent creates a report file and is about to generate a summary. The file service has returned report-42, but the worker exits before saving the Tool Result. The Run row still says running, the Session messages contain no file result, and an online client may already have seen a tool_execution_end signal.

A recovery process that trusts only the Run row assumes work is still in progress. One that trusts only messages creates the file again. One that trusts the client signal cannot prove that the fact behind the signal was committed.

Recovery needs one authoritative execution Journal for committed facts, with Projections that produce Run, message, and client read models. A Checkpoint is not another fact source. It points to a stable position in the Journal and declares which external conditions recovery must verify before continuing.

The Journal commits facts before Projections serve reads

One execution outcome often updates Run state, a message view, a realtime notification, and a metric. If every path writes its own result directly, a failure between writes leaves several contradictory Sources of Truth.

A clearer boundary is:

authoritative execution journal
├─ Run-state projection
├─ Message projection
├─ Durable client feed
└─ Metric/Audit projection

The Journal preserves what was committed. A Projection interprets those facts for a read requirement. A client feed may itself be durable, but it remains a read projection of the Journal rather than a competing owner of Tool outcomes. SSE or WebSocket sends low-latency signals for new feed entries.

The Session Tree continues to preserve branched conversation history and the Context-visible path. It may consume confirmed message projections, but it does not replace the Journal’s operation, Attempt, and effect evidence.

Effect Intent commits before any external call

The Journal records more than completed outcomes. Every path that may create an external effect must first allocate an operation, Attempt, and stable effect key, durably append and commit the intent, and only then dispatch:

allocate operation / Attempt / effect key
→ append tool.effect.intent
→ commit Journal event
→ dispatch external call with the same effect key
→ append terminal outcome or unknown evidence

If the intent commit fails, the Runtime must not send the call. Only when every effect path enforces this gate does the absence of an intent prove that this Runtime should not have dispatched. A handler or infrastructure effect that bypasses the gate destroys that proof boundary.

Replay during recovery reapplies recorded facts; it does not call the model or Tool again. An Intent without a terminal outcome enters reconciliation. It is not itself an instruction to retry.

Sequence and event identity solve different problems

A conceptual Journal event can look like this:

stream_ref: session:17
sequence: 74
event_id: event_9a2
type: tool.effect.succeeded
run_id: run_8
tool_execution_id: tool_exec_12
attempt_id: attempt_1
payload:
  effect_ref: report-42
schema_revision: execution-event.v3

sequence expresses committed order within one stream. event_id identifies the logical event. A global UUID can deduplicate but cannot tell a projector what to read next. A bare sequence has no meaning outside its stream.

A retry after an append timeout must reuse the same event_id. If that ID already exists, the Journal compares the immutable envelope digest. Matching content returns the existing sequence; different content is a conflict. The caller must not generate a new ID and append again.

Sequence allocation, legal-transition validation, and event insertion belong in one authoritative commit boundary. A cancellation request may be recorded as run.cancel.requested; only the current transition owner may resolve the race and append run.cancelled or run.completed. The Journal must not accept contradictory terminal facts and delegate the decision to a projector.

Projections must tolerate repeated consumption

Each Projector stores a scoped cursor. Suppose the Journal has reached sequence 74 while the message Projector has processed only through 72:

Journal cursor: 74
Message projection cursor: 72

The Projector resumes at 73 and updates its view idempotently by stable business ID. If the projection row and cursor share a database, it commits both in one transaction. Across stores, it writes the view idempotently before advancing the cursor. An unknown write result never causes the event to be skipped; restart may consume it again.

This is at-least-once projection, not end-to-end exactly-once execution. Idempotency keys, monotonic cursor updates, CAS, or a fenced Projector owner prevent a slow worker from moving a newer view backward.

A lagging message projection therefore replays the Journal. It does not invoke the model or Tool again.

A Checkpoint records the recovery position and its conditions

The Journal can rebuild state from the beginning, but a long Run usually uses a Snapshot for speed. A Checkpoint binds the Snapshot, Journal cursor, and recovery conditions:

checkpoint_revision: 4
run_id: run_8
run_contract_ref: runspec-8@3
resume_contract_revision: report-agent.v3
snapshot_ref: snapshot_73
event_cursor:
  stream_ref: session:17
  sequence: 73
resume_at: reconcile_create_report
pending_effects:
  - operation_id: op-17
    attempt_id: attempt_1
    status: dispatched
    provider: file-service
    effect_key: run_8:create_report:v1
    idempotency_scope: create-report
    idempotency_expires_at: 2026-07-28T09:00:00Z
    effect_ref: null
waiting: null
budget:
  model_turns_used: 6

A Checkpoint answers where and under which conditions to resume. It does not state what the external world looks like now. snapshot_ref must cover exactly the cursor in the same stream. Without a Snapshot, recovery replays from the start of the Journal; it cannot omit base state and begin at an arbitrary middle cursor.

run_contract_ref fixes the original execution ceiling, while resume_contract_revision fixes the semantics of recovery. Being able to parse a schema does not prove that new code interprets resume_at the same way. Storage format and recovery state machine both need compatibility checks.

Pending Effects are reconciled before Retry

Recovery for run_8 follows this order:

load Checkpoint and referenced Run contract
→ validate Snapshot covers cursor 73
→ replay Journal events after 73
→ reconcile every non-terminal pending effect
→ revalidate authorization, Artifact, waiting condition, and budget
→ construct new Runtime state at the next legal boundary

If the Runtime appended tool.effect.succeeded(report-42) at sequence 74 after the file service succeeded but before updating the Checkpoint, replay absorbs that fact and does not create the file again.

If the file exists externally but no terminal event was appended, the Checkpoint shows only dispatched. Recovery first queries by provider, stable effect key, idempotency scope, or external business reference. It may create a new Attempt only when the external owner proves that the action did not happen, or while idempotency_expires_at remains valid and the downstream system still guarantees convergence under the same key. If the query is unavailable, the scope differs, or the window has expired, the outcome remains unknown.

A Checkpoint therefore cannot replace external idempotency or reconciliation. It ensures that recovery knows which operation remains unresolved.

Waiting Conditions and crashes use the same recovery entry point

An intentional pause can persist a Waiting Condition:

waiting:
  kind: confirmation
  request_id: confirm_9
  action_ref: delete:file-7@revision-3
  expires_at: 2026-07-28T09:00:00Z

The Runtime commits the waiting event and Checkpoint before releasing its worker. Resume revalidates the action, resource revision, identity, expiry, and current authorization. It cannot merely check that somebody clicked a confirmation button.

A crash and a pause have different triggers but use the same recovery contract: rebuild from the last committed cursor and then validate current external conditions. Provider streams, sockets, database connections, and in-process tasks do not belong in the Checkpoint. Recovery recreates them.

Back to the problem

The Run row, Session messages, and client signal in the opening example disagree because three read forms are trying to declare execution fact. The recovery path should instead be:

  1. Tool Intent commits durably before dispatch; Attempts and terminal or unknown outcomes continue into the same authoritative Journal.
  2. Idempotent Projectors create Run, message, client-feed, and metric views.
  3. A Checkpoint binds a Snapshot, scoped cursor, original Run contract, Pending Effects, Waiting Condition, and recovery revisions.
  4. Recovery replays facts after the cursor, then reconciles unresolved effects.
  5. A new Attempt is created only when evidence permits it.
  6. The Runtime finally creates a new turn snapshot, while the client fills display gaps from the durable-feed cursor.

The Journal proves what happened. The Checkpoint says where to continue. The Session Tree organizes model-visible history. The client feed rebuilds the interface. Keeping those owners separate prevents recovery from repeating an effect that already happened but has not yet reached the current read view.
