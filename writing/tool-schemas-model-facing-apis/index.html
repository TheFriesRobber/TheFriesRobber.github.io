Agent Tools 1: Tool Schemas Are Model-Facing APIs

07/12/2026 Updated 07/14/2026
AgentToolsAPI Design

The problem

Suppose a backend already has an endpoint for creating calendar events. It accepts more than a dozen fields: user ID, organization ID, title, start and end times, attendees, notification policy, audit source, request ID, and retry settings.

The most direct approach is to convert that request DTO (Data Transfer Object, a data structure used to pass parameters between services) into JSON Schema (a vocabulary for describing the shape and constraints of JSON data), then register it as an Agent Tool. The types line up and the execution code can be reused, so another interface may seem unnecessary.

But a model is not an API client following fixed code. It must infer whether to call a Tool, which Tool to call, and then generate arguments that satisfy the contract. Every ambiguous field in a DTO—and every missing constraint—forces the model to make another unnecessary guess.

A Tool schema therefore should not be a copy of a backend DTO. It is a model-facing API: the Tool name and description help the model route to a capability, the input schema constrains the intent it can express, and the handler turns untrusted model input into an authorized, deterministic operation.

Think of a Tool schema as an operation form placed in front of the model. The name and description are the form’s title and instructions, the input schema defines what the model may fill in, and the handler checks and submits it. A backend DTO is more like an internal work order: it may contain identity and execution details that the model should never provide.

This article uses a few terms repeatedly:

TermMeaning in this article
model-facing APIAn interface designed for a model to select, populate, and repair correctly
runtimeThe framework around the model that supplies Tools, validates calls, and executes handlers
handlerThe function that receives Tool arguments and performs the actual operation
backendThe deterministic service, database, or external API called by the handler
trusted contextInformation derived from authentication or generated by the system, such as identity, permissions, and request ID
trace / evalA trace records one real execution; an eval repeatedly tests the system against a fixed set of cases

One Tool participates in two decisions

Function calling is often described as “the model generates JSON, then the application executes a function.” That skips an earlier step: the model must first select a capability from the Tools it can see.

At minimum, one Tool call involves two separate decisions:

DecisionMain inputsCommon failures
Whether to call a Tool, and which onename, description, current taskChoosing a similar Tool, failing to call when needed, treating a write as a read
How to construct the argumentsproperty names, types, required fields, enums, property descriptionsMissing fields, type errors, invented fields, confused empty-value semantics

That is why checking only whether the JSON passes schema validation is insufficient. A call can be structurally valid but target the wrong capability. It can also select the right Tool and still fail because the interface exposes irrelevant fields.

The full Tool boundary also includes identity, permissions, and audit data injected by the runtime. The model should express only the business parameters that can be inferred from the user’s task. It should not generate trusted context.

Start with a bad backend DTO

The following input may be appropriate between services, but it is a poor interface for a model:

{
  "user_id": "u_123",
  "tenant_id": "t_456",
  "title": "Project sync",
  "starts_at": "2026-07-16T10:00:00+08:00",
  "ends_at": "2026-07-16T10:30:00+08:00",
  "notification_policy": "default",
  "actor_type": "assistant",
  "request_id": "req_789",
  "retry_mode": "safe"
}

These fields mix three kinds of information:

  1. Business intent explicitly stated by the user, such as the title, time, and attendees.
  2. Context the application can derive from the current session, such as user identity, time zone, and scope.
  3. Internal control data required by infrastructure, such as request ID, actor, and retry policy.

Once the last two categories enter the schema, the model has to make decisions about them. More importantly, fields such as user_id and actor_type may look like ordinary strings while actually belonging to the authorization and audit boundary. Even if a model usually fills them correctly, authorization cannot depend on the assumption that it usually will not fabricate them.

A narrower model-facing Tool can accept only the information required to complete the task. To illustrate range constraints, assume this example product allows events from 5 to 480 minutes and at most 50 attendees. These numbers are example product policies, not universal calendar limits:

{
  "type": "object",
  "properties": {
    "title": {
      "type": "string",
      "minLength": 1,
      "description": "Event title visible to attendees."
    },
    "starts_at": {
      "type": "string",
      "description": "Start time with an explicit UTC offset."
    },
    "duration_minutes": {
      "type": "integer",
      "minimum": 5,
      "maximum": 480,
      "description": "Event duration in minutes."
    },
    "attendee_emails": {
      "type": "array",
      "items": { "type": "string" },
      "minItems": 1,
      "maxItems": 50,
      "description": "Confirmed attendee email addresses. Omit when there are no attendees."
    }
  },
  "required": ["title", "starts_at", "duration_minutes"],
  "additionalProperties": false
}

The runtime then adds trusted context:

async function executeScheduleEvent(args: ScheduleEventArgs, ctx: ToolContext) {
  const input = validateBusinessRules(args, ctx.timezone)

  return calendarClient.createEvent({
    ...input,
    userId: ctx.authenticatedUserId,
    permissionScope: ctx.permissionScope,
    actor: ctx.actor,
    requestId: ctx.requestId,
  })
}

The point is not to make the Tool look simpler. It is to assign responsibilities clearly: the model expresses the task, the runtime supplies trusted context, and the backend performs final authorization and consistency checks.

Name and description form a routing interface

A Tool name should describe a stable action, not an internal service or class name.

calendar_api_v2_execute       # exposes implementation, unclear intent
manage_calendar              # too broad
schedule_calendar_event      # explicit action and resource

The description should answer a few routing questions:

  • What result does this Tool produce?
  • When should it be called?
  • When should it not be called?
  • Does it read data, or create a persistent side effect?
  • What is the most important precondition?

For example:

Create one calendar event for the current user. Use only after the title,
start time, and duration are known. This tool writes to the calendar; it
does not search for availability or resolve ambiguous time zones.

This description does not explain how the backend stores an event or repeat every property type. It provides the distinctions needed to select the Tool.

Longer is not automatically better. If permissions, field documentation, retry rules, and product background are all packed into the description, they dilute the signals that affect selection. A useful division of responsibility is:

InformationBetter location
When to call; whether it has side effectsTool description
How to fill one argumentProperty description
Behavioral rules for the current taskSystem/developer instruction
User identity and resource scopeTrusted runtime context
Final authorization and business constraintsHandler and backend

Some repetition is appropriate. A write operation, for example, may be marked as a side effect in both its Tool description and the confirmation UI. But a prompt that says “do not exceed your permissions” is never a replacement for backend authorization.

A schema should express the minimum sufficient input

“Minimum” does not mean removing useful constraints. “Sufficient” does not mean handing every internal option to the model. The goal is to expose only the decisions the model must make to complete the user’s task.

Every field should answer these questions:

  • Which part of user intent does it represent?
  • If it is absent, can the handler derive it safely and deterministically?
  • Do missing, empty string, empty array, and null have different meanings?
  • Can the valid range be expressed directly in the schema?
  • Does the field actually belong to identity, permissions, audit, or infrastructure configuration?

In JSON Schema, a property listed under properties is optional by default; it must also appear under required to be mandatory. Undeclared properties are also allowed by default. Only additionalProperties: false rejects near-synonyms invented by the model.

Three states deserve separate treatment:

{}

The property is missing.

{ "note": "" }

The caller explicitly supplied an empty string.

{ "note": null }

The caller explicitly supplied null, which is valid only when the schema allows it.

If the handler collapses all three with value ?? "", a precise schema cannot preserve the distinction. For an interface where an empty string means “delete the current content,” the value may be empty while the property itself should still be required.

Schema validation does not replace handler validation

A strict schema reduces syntactically invalid input. It does not prove that the call is authorized, nor can it capture every business condition.

The handler still needs to check, for example:

  • whether starts_at can be parsed and includes an explicit time zone;
  • whether the current user may invite the listed attendees;
  • whether a write has received the confirmation required in this context;
  • whether the runtime actually supports the JSON Schema keywords used by the definition.

The last point is easy to miss. Model platforms, gateways, and runtimes may implement only a subset of JSON Schema. A keyword such as minItems appearing in a type definition does not mean every execution path enforces it. A reliable design gives the model-facing schema contract tests—tests that confirm each execution path follows the same schema—and preserves critical business checks in the handler. Correctness should not depend on one adapter happening to support a keyword.

The validation boundary can be divided into three layers:

LayerAppropriate checks
Schema/runtime validatorTypes, required fields, enums, ranges, additional properties
HandlerCross-field relationships, current state, confirmation requirements, recoverable business errors
Backend/storageIdentity authorization, resource ownership, transactions, versions, and idempotency—the same repeated submission produces the same business result

Critical checks may intentionally overlap. The goal is not mutual distrust. Each layer should reject invalid states that it is capable of recognizing.

Errors are also part of the model-facing API

If the application or runtime returns a Tool error to the model, that error becomes input to the model’s next decision. 400 invalid body may be enough for an engineer to start reading logs, but it tells a model almost nothing about what to do next.

A recoverable error should at least include a stable code, the problematic field, and a repair hint. It can use a fixed error envelope:

{
  "ok": false,
  "error": "ambiguous_time_zone",
  "field": "starts_at",
  "message": "The start time does not include a UTC offset.",
  "hint": "Ask the user for a time zone, then retry with an explicit offset.",
  "recoverable": true,
  "requires_user_input": true,
  "retryable": false
}

The envelope needs clear boundaries:

  • error should be a stable, low-cardinality machine code so traces and evals can aggregate it.
  • message should explain the failure without leaking a stack trace or an internal service response.
  • hint should describe a valid next step without inventing missing facts for the model.
  • recoverable indicates whether a legal repair path exists; requires_user_input says the current information is insufficient and the user must be asked.
  • retryable means only that retrying under the same conditions might succeed. A missing time zone is recoverable but not directly retryable. A transient network failure may be both recoverable and retryable.
  • Candidate values should be permission-filtered and bounded in number.

This makes recovery behavior part of the interface design instead of leaving it to model guesswork.

Improve the schema with traces and evals

A schema that looks reasonable in code review may still be hard for a model to use reliably. A fixed task set should measure at least:

MetricWhat it reveals
Tool selection accuracyWhether the name and description lead to the right capability
First-call valid rateWhether the schema and property descriptions are clear enough
Repair success rateWhether errors support a successful next step
Redundant call rateWhether the Tool encourages duplicate reads or writes
Task success rateWhether valid calls actually complete the user’s goal
Permission violation attemptsWhether the visible Tools, prompt, or arguments encourage unauthorized actions

Do not diagnose only from final task success. Two versions may both complete a task, while one succeeds on the first call and the other needs three invalid-argument retries. Their latency, cost, and fragility are very different.

Change a small number of variables at a time. Keep the schema fixed while revising only the Tool name and description, then observe selection accuracy. Next, tighten fields and error messages, then observe first-call validity and repair success. If everything changes together, an improvement is hard to attribute to the right layer.

Design boundaries

A Tool schema is not the answer to every Tool problem:

  • If too many Tools create an oversized selection space, the system needs a Tool registry, permission filtering, and on-demand discovery. That is a Tool-surface problem, not a single-schema problem.
  • A Tool with several commands and substantially different arguments may need to be split, but failure distributions should first show that the granularity is the problem.
  • Long-running, recoverable, multi-stage work belongs in a workflow or task state machine. A Tool should remain an atomic capability within it.
  • High-risk side effects usually need user confirmation, policy hooks, or approval flows. One sentence in a description cannot replace them.
  • A schema guarantees an input shape. It does not guarantee that facts are true, the call is appropriate, or execution will succeed.

Back to the problem

An Agent Tool and a backend API can reuse the same business capability without reusing the same interface shape.

A backend DTO serves controlled programmatic callers and often carries full execution context. A Tool schema serves a model that must interpret natural language, select a capability, and then generate arguments. A reliable model-facing API should:

  1. Use a clear name and description to reduce ambiguity in capability selection.
  2. Expose only the minimum sufficient input needed to complete the user’s task.
  3. Let the trusted runtime inject identity, permissions, audit data, and infrastructure context.
  4. Validate in the schema, handler, and backend instead of betting correctness on one validator.
  5. Treat error recovery and real-call evaluation as part of the interface lifecycle.

Code is the Tool’s execution implementation. The schema is the product surface shown to the model. They support the same operation, but they carry different responsibilities.
