Agent Tools 5: Make Tool Errors Repairable

An ambiguous argument error shows how a Tool Error contract can tell the model what may change and whether the unchanged request is worth retrying.

07/14/2026 Views
AgentToolsAPI Design

The problem

A user asks an Agent to assign a task to “Alex.” The model calls assign_task:

{
  "task_id": "task_17",
  "assignee": "Alex"
}

The backend finds more than one user with that name and returns:

400 invalid body

The model knows the call failed, but not whether the problem is field format, permission, resource state, or an ambiguous match for Alex. On the next turn it can only guess: lowercase the name, repeat the same call, or invent a field that does not exist. Even if repeated attempts eventually work, recovery mostly comes from luck.

For a human developer, an exception string can be a useful debugging entry point. For a model inside a control loop, a Tool Error must answer a different question: what may change next, and is another call worthwhile after that change?

An error that only describes the exception provides no repair path

A Tool Call can fail at different boundaries: before the request reaches the handler, while arguments are parsed, when the business object violates a current constraint, when the caller lacks permission, or after an external side effect whose result cannot be confirmed.

If all of these become invalid request, the Runtime loses three kinds of information:

  • Which boundary rejected the call.
  • Whether the model can repair it by changing arguments.
  • Whether another execution could repeat a side effect that already happened.

A model-facing error therefore cannot be a stringified internal exception. It needs a stable contract that translates implementation details into a bounded set of actions the model may take.

The JSON-RPC 2.0 Error Object already separates code, message, and implementation-defined data. RFC 9457 defines machine-readable problem details for HTTP APIs. Both establish the value of structured error responses, but neither decides which fields an Agent Runtime may safely expose to a model or how a Tool Call should be repaired.

Classify the failure boundary before deciding who can repair it

A minimal classification does not need every exception type, but it must preserve ownership boundaries:

Failure classWhere it occursCan the model usually repair it?Example
transportRequest, connection, or protocol layerNot necessarilyconnection reset, unparseable response
validationArgument structure and field constraintsUsuallymissing task_id, invalid date format
domainCurrent business stateDepends on the errorambiguous object, closed task
policyAuthorization or safety policyUsually not by rewriting argumentsthe current actor cannot assign the task

This classification is not meant to teach the model the backend architecture. It constrains what happens after an error.

A validation error may identify the field to fix. A domain error may return a bounded candidate set or require a fresh read. A policy error should reject the action without suggesting an argument-level bypass. A transport error requires idempotency and side-effect evidence before the Runtime can decide whether retry is safe.

After classification, the opening error is no longer a generic 400. It is an actionable domain failure: the name exists, but it does not uniquely identify an assignee.

The error envelope should say what may happen next

A conceptual envelope could look like this:

{
  "status": "failed",
  "error": {
    "code": "assignee_ambiguous",
    "class": "domain",
    "message": "More than one assignee matches 'Alex'.",
    "field": "assignee",
    "same_request_retryable": false,
    "repairable": true,
    "requires_user_input": true,
    "next_action": {
      "type": "ask_user_to_choose",
      "field": "assignee",
      "max_resubmissions": 1
    },
    "hint": "Ask the user to choose one candidate before resubmitting.",
    "candidates": [
      {"id": "user_12", "label": "Alex Chen · Payments"},
      {"id": "user_29", "label": "Alex Li · Risk"}
    ]
  }
}

These fields have different responsibilities:

  • code is a low-cardinality, versionable machine decision, not an exception class name.
  • class identifies the failure boundary so the Runtime can choose repair, retry, rejection, or confirmation.
  • field locates the input the model is allowed to change.
  • hint gives a short explanation to humans and models; machine policy must not depend on parsing it.
  • candidates contains backend-confirmed options so the model does not invent an ID.
  • same_request_retryable answers only whether the unchanged arguments are worth retrying. It does not prove that no side effect occurred.
  • repairable says that the flow can still recover; it does not mean the model already has the facts needed to resolve the ambiguity.
  • requires_user_input and structured next_action say who must provide the missing fact, what may change, and how many resubmissions are allowed.

The Agent presents the two authorized candidates to the user. Only after the user confirms Alex Chen · Payments does the model replace the ambiguous name with user_12. The Runtime still repeats Schema validation, authorization, and backend-state checks. The error and the user’s choice produce a new proposal, not a credential for bypassing trusted validation.

If the backend can derive one unique result from the user’s original constraints, next_action may allow the model to rewrite the argument autonomously. While multiple valid candidates remain, repairable should route the flow to clarification instead of authorizing the model to guess from display labels.

Candidates and hints must be bounded

Returning every search result, database field, or stack trace may appear to improve repair, but it expands data exposure and the prompt-injection surface.

A candidate set should satisfy three conditions:

  1. It contains only objects the current subject may see.
  2. Its size is bounded, with stable IDs and only the information needed to distinguish candidates.
  3. Its contents remain external data, not trusted instructions merely because they appear inside an error.

If too many objects match, the correct response is not to place hundreds of users in Context. Ask the model to add a filter, or require a controlled search Tool first.

Hints should not expose internal table names, SQL, paths, or raw exception messages either. task row lock failed in shard_3 belongs in internal logs. task_state_changed with “read the task again before deciding” is an appropriate model-facing action boundary.

A retry flag cannot hide an unknown side effect

An argument error that occurs before execution can safely return failed. If the Tool sends a write to an external service and then times out while waiting for the response, the Runtime can observe only unknown: the action may have failed, or it may already have succeeded.

{
  "status": "unknown",
  "error": {
    "code": "result_not_confirmed",
    "class": "transport",
    "same_request_retryable": false,
    "hint": "Query the operation by idempotency key before retrying."
  },
  "effect": {
    "tool_execution_id": "tool_exec_42",
    "idempotency_key": "idem_8f1c..."
  }
}

Setting same_request_retryable to false does not mean recovery is impossible. It prevents the model from immediately proposing another write. The tool_execution_id and idempotency key should be allocated before the first Attempt and reused by later Attempts of the same logical action. They must not be derived only from business arguments, or two distinct actions with identical arguments may be mistaken for one retry. The Runtime should query the stable operation identity first and replay it only when the downstream system explicitly supports idempotent replay.

This matches the boundary in Agent Tools 4: Tool Calls Need a Complete Lifecycle: an exception is one observation, not proof that the external fact did not happen.

Evaluate repair across the complete trajectory

Evaluating a Tool Error cannot stop at whether the handler returned the expected code. The real question is whether the system can recover within a bounded number of steps after the error enters the next Model Turn, without creating another unsafe side effect.

The opening case produces two contrasting trajectories:

ambiguous error
assign_task("Alex")
→ 400 invalid body
→ assign_task("alex")
→ 400 invalid body
→ task incomplete

structured error
assign_task("Alex")
→ assignee_ambiguous + 2 candidates
→ Agent asks the user to choose
→ user selects user_12
→ assign_task("user_12")
→ succeeded

At minimum, measure these separately:

  • repair success: whether the Task eventually completes after a repairable error.
  • repair attempts: how many additional Tool Calls occur before success.
  • repeated identical call rate: whether the model repeats the same failed arguments.
  • unsafe retry count: whether a new side effect is proposed while the prior result is unknown.
  • candidate precision: whether every returned candidate is visible, valid, and relevant to the field.

Every rate needs an explicit denominator. The denominator for repair success should be cases that actually received a repairable error, not all Tool Calls.

Back to the problem

400 invalid body says only that the call did not return success. It does not tell the model which field may change or tell the Runtime whether another execution is safe.

With a stable Tool Error contract, the ambiguous assignee becomes assignee_ambiguous. The backend returns a bounded set of candidates visible to the current user and uses requires_user_input to require a user choice. The model can then form a new proposal from the confirmed stable ID, and trusted boundaries validate it again. If the error happens after a possible side effect, the response preserves unknown and queries the original operation instead of encouraging a blind retry.

The value of a Tool Error is not friendlier wording. It keeps the next step after failure inside a controlled execution protocol.
