Agent 15: The Owner of a Failure State Chooses the Recovery Action

Choose retry, fallback, repair, reconciliation, or replanning according to whether the Model, Tool, Plan, or Service owns the failure.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentRecoveryReliability

The problem

One Agent Run first encounters model rate limiting, then a write_note timeout, and finally discovers that an API assumed by its plan no longer supports batch writes. All three errors enter one retry middleware, which retries each of them up to three times.

The result is that model rate limiting continues to consume time and the same route’s retry budget and may intensify the limit; the write with an unknown outcome is executed again; and an invalid plan continues under its old assumption. Uniform retry looks simple because it collapses failures owned by three different boundaries into function exceptions.

First ask who can determine the result

The boundary that can determine the result and owns the repairable state should select the recovery action:

FailureFact ownerPossible actions
Model request is rate-limitedmodel boundary / host routerwait, fallback, stop
Tool arguments are invalidTool contractrepair arguments
Tool effect outcome is unknownexternal systemquery, reconcile
A plan assumption is invalidPlan Artifactreplan
A downstream service is temporarily unavailableservice/runtime boundaryretry, defer, degrade

The Plan owner here manages trusted plan state with revisions, assumptions, and dependencies. It does not own a temporary block of text generated by the model.

The Runtime may coordinate these actions, but it must not pretend to own every fact. For an external side effect in particular, a rejected promise proves only that the local process did not receive a normal response. It does not prove that the business action failed.

Retry is only one recovery action

Recovery actions have different semantics:

  • retry: create a new Attempt under the same contract;
  • fallback: switch to another compatible implementation or model;
  • repair: change model-controlled input and propose a new action;
  • query/reconcile: read the external fact and converge an unknown outcome;
  • replan: revise the Plan after an assumption changes;
  • stop: preserve the failure and exit when evidence is insufficient or risk is too high.

Before retrying, the system must establish at least that the failure occurred at a retryable boundary, the current action permits a new Attempt, budget remains, and retry will not conceal an unknown side effect.

For a write_note timeout, the first action is query or reconciliation. The model may repair a schema validation error. When an API capability changes, repeated calls to the old approach cannot succeed; the Plan must be revised.

Fallback must not cross the failure boundary

Model rate limiting may permit fallback, but the fallback model’s capabilities, policy, and Context compatibility still need to be checked. Switching models after a Tool has executed cannot reset the effect state.

Service degradation must not silently weaken the security contract either. If the primary write API is unavailable, the system cannot fall back to “write a local file and handle it later” unless that file is already an authorized durable owner and the responsibility for later delivery is explicit.

The criterion for fallback is not merely whether another implementation exists. It is whether that implementation preserves the current operation’s semantics and responsibility.

Retry budget must be shared across layers

If the model layer, Tool layer, HTTP client, and Queue each retry three times, one user request may produce far more than three physical Attempts.

A more coherent budget travels along the call chain:

run recovery budget
├── model attempts
├── tool attempts
└── service attempts

Each recovery action records why budget was consumed, which failure owner selected it, and which operation ID it affects. The system can then choose between another attempt and preserving budget for a more valuable fallback.

A budget is not another name for a fixed attempt count. A high-risk write may stop after one unknown outcome. A repeatable read-only query may permit more Attempts. An invalid plan assumption should not consume retry budget at all; it should trigger replanning.

Walk one Run through the recovery decisions

Return to the opening Run:

  1. Model rate limiting occurs before generation. The Router determines that a fallback model satisfies capability and policy, then performs fallback.
  2. write_note times out. The Runtime records outcome: unknown and queries by effect reference.
  3. The external system confirms that the note was created. The original operation converges to succeeded without a duplicate Attempt.
  4. A later step discovers that the batch API is no longer supported. The Plan owner marks the relevant assumption invalid and creates a new revision.
  5. The Run continues with plan items that remain valid instead of retrying the old call.

Pi currently exposes model and Tool errors and a host-injected model boundary, but it does not provide a complete cross-layer recovery policy. See its Agent Loop in agent-loop.ts. The failure owners, budget, and action selection described here belong to host design.

Back to the problem

Model rate limiting, a Tool timeout, and an invalid plan assumption cannot share one retry behavior because different owners determine their results and repair their state.

A useful recovery-decision order is:

  1. Locate the failure owner.
  2. Determine the known outcome and preserve unknown.
  3. Select retry, fallback, repair, reconciliation, replanning, or stop.
  4. Check operation identity, side-effect boundaries, and remaining budget.
  5. Record a new Attempt or Plan revision instead of overwriting history.

The goal of recovery is not to “eventually succeed whenever possible.” It is to choose the next action without falsifying facts or repeating side effects. A success rate is meaningful only when reported at the correct failure grain.
