Spark / Yarn

Notes on Spark Resource Requests and Data Representation on YARN

04/15/2020
SparkBigdata

The questions

How should a Spark application request resources from a YARN cluster with six nodes, each providing 16 cores and 64 GB of memory, in order to use the cluster efficiently? How many partitions should it use, and how should records in an RDD be represented?

Requesting cluster resources from YARN

This discussion considers only CPU and memory. Disk and network performance also matter greatly to Spark, but neither Spark nor YARN directly manages them as allocatable resources in the same way.

A Spark application requests cluster resources by setting the number of executors and the cores and memory assigned to each executor.

Number of executors

This setting determines how many executors a Spark application uses. Dynamic allocation can acquire and release executors at runtime through settings such as spark.dynamicAllocation.enabled.

// spark-submit
--num-executors
// spark-defaults.conf or a SparkConf object
spark.executor.instances

CPU

The number of executor cores controls how many tasks one executor can run concurrently.

// spark-submit
--executor-cores
// spark-defaults.conf or a SparkConf object
spark.executor.cores

For example, --executor-cores 5 allows each executor to run five tasks at the same time.

Memory

Executor memory controls the heap-size limit of each executor. Too much can waste resources and increase garbage-collection pauses; too little restricts the amount of data processed in memory and pushes more work to external storage.

// spark-submit
--executor-memory
// spark-defaults.conf or a SparkConf object
spark.executor.memory

Mapping Spark requests to YARN resources

Spark cannot request more than YARN makes available. Two YARN settings define the per-node limits:

  • yarn.nodemanager.resource.memory-mb controls the maximum sum of memory used by the containers on each node.
  • yarn.nodemanager.resource.cpu-vcores controls the maximum sum of cores used by the containers on each node.

For CPU, one Spark executor core maps to one YARN virtual core. Memory requires several additional considerations:

  • --executor-memory or spark.executor.memory controls the executor heap, but the JVM also uses off-heap memory, including DirectByteBuffer. YARN therefore includes spark.yarn.executor.memoryOverhead in the container’s total memory request. In the version considered here, its default is max(384, .07 * spark.executor.memory).
  • YARN rounds memory requests according to yarn.scheduler.minimum-allocation-mb and yarn.scheduler.increment-allocation-mb.

There are several more practical constraints:

  • Reserve resources for the ApplicationMaster. In YARN client mode it commonly needs one virtual core and 1 GB of memory by default. In cluster mode it also runs the driver, so --driver-memory and --driver-cores often need to be larger.
  • Very large executor heaps can lead to expensive garbage collection. 64 GB is a reasonable upper bound for a single executor in this example, not a universal rule.
  • Five cores per executor is a commonly used upper bound when HDFS throughput is a concern.
  • Avoid single-core executors when possible, because they lose some benefits of JVM multithreading and shared in-process state. A broadcast variable, for example, is copied to every executor; multiple cores in one executor can share that in-memory copy.

Applying this to the example

How should an application request resources from a six-node YARN cluster where each node has 16 cores and 64 GB of memory?

  • First, set yarn.nodemanager.resource.memory-mb and yarn.nodemanager.resource.cpu-vcores to approximately 63 * 1024 = 64512 MB and 15, respectively. This reserves one core and 1 GB per node for the operating system and Hadoop daemons.
  • An obvious first answer is --num-executors 6 --executor-cores 15 --executor-memory 63G, but it has several problems:
    • --executor-memory covers only the heap. Adding executor memory overhead would exceed the 63 GB allocatable limit.
    • The ApplicationMaster also requires resources, so executors cannot consume every virtual core.
    • Fifteen cores in one executor may reduce HDFS I/O throughput and increase contention.
  • A more balanced starting point is --num-executors 17 --executor-cores 5 --executor-memory 19G:
    • CPU: Five nodes host three executors each. The sixth hosts two executors plus the ApplicationMaster, leaving five virtual cores available there.
    • Memory: With 63 GB available on a node, three executors can use at most about 21 GB each including overhead. Subtracting roughly 7% overhead leaves about 19 GB for the executor heap.

These numbers are a starting point for the stated cluster shape and the defaults assumed by the original calculation. Real workloads still require measurement because Spark and YARN defaults, storage behavior, and executor overhead vary by version and environment.

Keep the data lean

A Spark data flow consists primarily of records represented in two forms: deserialized Java objects in memory and serialized binary data on disk or over the network.

The spark.serializer setting selects the serializer. Kryo—org.apache.spark.serializer.KryoSerializer—is generally a good choice when the application can register and handle its types correctly.

Data formats such as Avro, Parquet, Thrift, and Protobuf can also reduce data size. Their format-specific features, such as columnar storage in Parquet, may accelerate processing as well.

Back to the questions

Choosing appropriate CPU and memory requests is an important part of Spark application performance. At the same time, records move across the network and disk between stages, so serializer and data-format choices also deserve deliberate attention.
