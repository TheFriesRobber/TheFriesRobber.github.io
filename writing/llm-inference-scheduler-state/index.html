LLM Infra 10: What State Must an Inference Scheduler Own?

Explain why cross-Replica scheduling cannot rely on queue length alone, and define the state boundaries among requests, Endpoint observations, placement decisions, affinity, and admission outcomes.

07/29/2026 Views
LLM InfraInferenceSchedulingControl Plane

The problem

Two Replicas both have queue lengths near zero. One has already loaded the required Adapter and holds a reusable prefix. The other needs a cold load, and its KV pool is nearly full. Least-queue routing sends the request to the second Replica. The gateway then times out, and the retry reaches a different deployment generation.

The queue length was not wrong. It simply did not describe whether the request could execute, how much Token work it required, or whether the Endpoint observation was still fresh.

Cross-Replica inference scheduling is not stateless load balancing. It needs to keep request constraints, Endpoint observations, placement decisions, and execution admission separate.

Request count is not service demand

“Three requests in the queue” could mean:

  • Three short Decodes.
  • One very long Prefill plus two short requests.
  • Three requests waiting for an Adapter that has not been loaded.
  • Three requests that have already missed their deadlines and are about to be cancelled.

At minimum, the cluster scheduler needs to consume:

request_spec:
  request_id: req_123
  required_model_revision: release_91a
  adapter: adapter_sql_v4
  token_envelope:
    prompt_tokens: 2400
    max_output_tokens: 300
  deadline: 2026-07-29T12:00:02Z
  affinity:
    prefix_key: optional
    session_key: optional

These fields come from the request and a trusted control plane. The Agent/model boundary has already resolved the business question of “which capability is required.” The Infra scheduler handles only requirements for an already resolved, compatible deployment.

Endpoint state is a time-bound observation

The public scheduling designs of llm-d and the Gateway API Inference Extension observe signals such as queues, running requests, KV utilization, LoRA affinity, and prefix or session affinity before filtering, scoring, and picking. They show that these signals can support inference-aware routing, but also reveal an important fact: the scheduler sees observations, not instantaneous truth inside the device.

An observation should carry its source and freshness:

endpoint_observation:
  observation_id: obs_b_91
  endpoint_uid: replica_b
  deployment_revision: release_91a
  endpoint_generation: 42
  collected_at: 2026-07-29T12:00:00.100Z
  signals:
    queue:
      source: runtime-metrics
      observed_at: 2026-07-29T12:00:00.080Z
      ttl_ms: 250
      running: 2
      waiting: 0
    kv:
      source: runtime-kv-events
      watermark: 18442
      observed_at: 2026-07-29T12:00:00.020Z
      ttl_ms: 150
      utilization: 0.91
    adapters:
      source: residency-controller
      observed_at: 2026-07-29T11:59:59.900Z
      ttl_ms: 500
      active: [adapter_chat_v2]
    health:
      source: endpoint-health-controller
      observed_at: 2026-07-29T12:00:00.090Z
      ttl_ms: 200
      state: ready

The ttl_ms values, field set, and generation fence are design suggestions in this article, not a shared protocol implemented by those projects. Each source retains its own timestamp and watermark so that a recent aggregate does not hide stale KV or residency data. A stale or missing hard-constraint signal should filter the Endpoint out. When an optimization signal is missing, the scheduler should assign a conservative score instead of treating the unknown as a hit. The placement record must identify the observation_id values it actually consumed. The principle is: without an observation age, “idle” has no defined freshness.

Filter, Score, and Pick should leave decision evidence

Scheduling can be separated into three steps:

  1. Filter out Endpoints whose model revision, Context, adapter, topology, or health state is incompatible.
  2. Score candidate cost using pending Tokens, KV capacity, adapter or prefix affinity, queue age, and deadline.
  3. Pick one Endpoint and retain the observation references behind that decision.
placement_decision:
  placement_id: place_456
  request_id: req_123
  observation_refs: [obs_a_77, obs_b_91]
  candidates:
    - endpoint: replica_a
      score: 0.82
      reasons: [adapter_ready, prefix_affinity]
    - endpoint: replica_b
      score: 0.21
      reasons: [adapter_missing, kv_pressure]
  selected_endpoint: replica_a
  policy_version: placement-v5

This is an auditable decision record. It does not guarantee that replaying the same input in the future will reproduce the same result. Observations, heat, and Runtime state all change.

Successful placement does not mean execution was admitted

Even after the scheduler selects a Replica, state may change while the request crosses the network. The Replica still needs to perform admission against its latest local KV state, Token budget, and generation.

This article suggests expressing the result as:

admission_receipt:
  placement_id: place_456
  attempt_id: attempt_07
  admission_id: admit_802
  endpoint_uid: replica_a
  outcome: accepted # accepted | queued | rejected
  execution_id: exec_991
  reason: kv_capacity_available
  returned_at: 2026-07-29T12:00:00.220Z

AdmissionReceipt is not an industry standard either. It clarifies the state boundary: the cluster scheduler owns the placement decision, while the Replica scheduler returns only the local execution-admission decision it has actually made.

The gateway separately owns its observation of this call:

receipt_observation:
  attempt_id: attempt_07
  state: unknown # received | unknown
  reason: upstream_timeout_before_receipt

unknown is not the Replica’s admission decision. It is the gateway’s assessment of an attempt when no receipt arrived. A missing receipt proves neither that the request was not admitted nor that execution did not begin.

If the gateway times out, it cannot conclude that:

  • Placement never arrived.
  • Execution never started.
  • Cancellation already took effect.
  • The business operation is exactly-once.

A retry must use a new attempt identity and follow the partial-delivery and unknown-outcome rules defined in Article 14.

Affinity may optimize only compatible candidates

Prefix, session, and Adapter affinity can avoid repeated Prefill work or a cold load, but they cannot override hard constraints.

The correct order is:

compatibility and health filter
→ capacity / deadline feasibility
→ affinity score

If an Endpoint holds a Prefix Cache but cannot satisfy the KV or Token budget required by the current scheduling step and local admission policy, a Cache hit does not make it feasible. A paged-KV Runtime may allocate blocks incrementally; only a platform with an explicit full-envelope reservation policy needs to make a conservative decision against the complete request limit. Likewise, an adapter being ready cannot override an incompatible deployment revision or tenant-isolation boundary.

llm-d’s precise prefix-aware routing depends on Runtime KV events, while its approximate approach maintains an inferred in-memory LRU. Their freshness and accuracy differ and must remain visible in the observation source instead of being collapsed into the label “Cache aware.”

Reschedule the opening request

Least-queue saw only:

replica_a.queue = 0
replica_b.queue = 0

The inference-aware decision also sees:

replica_a: adapter ready, prefix affinity, KV sufficient
replica_b: adapter missing, KV pressure, observation older

Filter, Score, and Pick therefore select A, and A’s local scheduler returns accepted. If the gateway does not receive A’s receipt, only the gateway observation for this attempt becomes unknown. The gateway must not pretend that the request did not execute; it must enter the streaming-failure protocol from Article 14.

Back to the problem

The opening request should not have been sent to a Replica with an equally short queue but a cold Adapter load and KV pressure. The scheduler needs four explicit objects, not more disconnected metrics: a RequestSpec, a time-bound EndpointObservation, an auditable PlacementDecision, and a local Admission outcome from the Replica.

Once they are separate, stale state, affinity, timeout, and retry no longer collapse into a single claim that “load balancing succeeded.”
