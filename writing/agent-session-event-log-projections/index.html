Agent Runtime 4: Make the Event Log the Source of Truth

An ordered Session Event Log unifies execution facts while messages, Run state, and realtime events become rebuildable projections.

07/17/2026 Views
AgentRuntimeEvent LogData Modeling

The problem

Suppose an Agent has generated its final reply: “The report is complete.” Finishing the execution must reflect that result in three places:

  1. Mark this Agent Loop as succeeded in the Run table.
  2. Insert the final reply into the message list that a refreshed page will read.
  3. Send a realtime run.completed notification to the browser that is currently open.

These write paths are independent and are not guaranteed to finish in list order. Now suppose this timeline occurs:

T1  Run state is updated to succeeded
T2  the realtime channel sends run.completed
T3  the database write for the final assistant message fails

The system is left with:

backend Run state   succeeded
message list        missing “The report is complete”
current browser     received run.completed once

The user may briefly see “complete” on the current page, but after a refresh the realtime notification is gone and the message list still lacks the final reply. The backend sees a successful Run and will not automatically execute it again. The system cannot answer a basic question: was the final reply saved reliably?

Retrying the message write once does not solve the underlying problem. The same execution result was written independently into Run state, the message list, and the realtime channel. After any write fails, no unified record exists from which the other copies can be repaired.

More tables do not create consistency

A common implementation performs several writes when the Runtime finishes. The order below matches the opening timeline, but the actual problem is that the writes do not share one atomic boundary:

update_run_state("succeeded")
publish_realtime_event("run.completed")
insert_assistant_message(final_text)
increment_success_metric()

If these operations are not atomic together, the process may exit between any two of them. Even when Run state and the message list share a database and can use one transaction, Redis, WebSocket, and a metric sink usually do not participate in that transaction.

More importantly, they serve different read requirements:

  • Run state supports a fast current-state lookup.
  • The Message view renders a conversation.
  • A Realtime signal refreshes an online interface with low latency.
  • A Metric supports aggregate analysis.

Treating every write as an independent fact turns one execution into several Sources of Truth that must be reconciled with each other.

Record facts first, then build views

A clearer boundary is for the Runtime to append execution facts to one Event Log with a stable order. Other data is generated from those facts.

A Projector is a background process that reads the Event Log and builds one query view. The resulting Projection may be a message list, Run state, or another read model. Different Projectors can interpret the same facts for different read requirements.

A minimal event might contain:

{
  "session_id": "session_17",
  "seq": 42,
  "event_id": "event_9a2",
  "type": "assistant.message.completed",
  "run_id": "run_8",
  "model_turn_id": "model_turn_6",
  "payload": {
    "message_id": "message_31",
    "content_ref": "content_31"
  },
  "occurred_at": "2026-07-17T08:30:00Z",
  "schema_version": 2
}

seq records the committed order within this Session. event_id identifies an event. They are not interchangeable: a global UUID can support deduplication but cannot tell a projector what to read next; a sequence establishes a read position but still needs an explicit scope.

The first lifecycle fact for a Run should also connect its execution contract, for example run.created(run_8, runspec_ref, fingerprint). The Event Log records which contract started the Run. The RunSpec remains an immutable contract that can be read independently, while the Run snapshot is current state derived from subsequent facts.

The content_ref in the example must also point to content that has already been persisted. If content and event share a database, they should commit in the same transaction. Across storage boundaries, write immutable content first, then append an event that references it, and retain reconciliation for cleanup after failure. An Event Log cannot become authoritative by referencing an object that has not committed.

Repairing the opening failure

Return to the missing final reply. Instead of letting Run state, the message list, and the realtime channel each record the result, the Runtime first appends two events:

seq 41  assistant.message.completed(message_31)
seq 42  run.completed(run_8)

First consider the case where both events committed and only a projection is behind. If the Runtime exits between the two appends, it should resume finalization from the last committed event instead of invoking the model again. The two events may also be submitted as one atomic batch.

One more term matters here: a Cursor is the read position of one Projector. A cursor of 40 means it has finished processing seq 40 and should read seq 41 next.

Suppose the system looks like this after the failure:

Event Log              committed through seq 42
Run-state projector    processed through seq 42
Message projector      processed only through seq 40

The Agent execution itself has completed; only the message list is two events behind. Recovery does not invoke the model again or move the Run back to running. The Message projector resumes after cursor 40:

  1. It reads seq 41, writes message_31 to the message list, and advances its cursor to 41.
  2. It reads seq 42, determines that the event affects only Run state, leaves the message list unchanged, and advances its cursor to 42.

The first step should ideally use one database transaction:

begin transaction
→ write message_31 with message_id as a unique key
→ update the Message projector cursor to 41
→ commit transaction

If the process exits before commit, neither message nor cursor takes effect, so restart processes seq 41 again. If it exits after commit, both changes are durable and restart continues from seq 42. There is no intermediate state in which the message was written but the cursor remains 40.

This example also assumes that one valid owner processes events for each (projection, session) in order. A partition or Session may be assigned to one projector owner with a lease and fencing token. Alternatively, the cursor may use monotonic compare-and-set, such as allowing only UPDATE ... WHERE cursor = 40 to advance it to 41. Under the CAS design, the projection mutation and cursor update must share a transaction; otherwise a slow replica may write stale state into the view before discovering that its cursor CAS failed. Across stores, retain a single fenced owner or give every view record its own version check against event sequence. In every design, a slow replica must not move 42 back to 41, and seq 42 must not overtake an uncommitted seq 41.

If the message list and cursor live in different stores and cannot share a transaction, repeated processing of the same event must be safe. Processing follows a fixed order:

  1. Write the message by message_id. If it already exists, also confirm that its stored content_ref matches the current event.
  2. Advance the cursor from 40 to 41 only after the message write is confirmed.
  3. If the message-write result is unknown, do not advance the cursor; process seq 41 again after restart.
  4. If the cursor-update result is unknown, read it again after restart. If it remains 40, process seq 41 again. If it is already 41, continue from seq 42.

The first pass inserts message_31. If the message commits but the cursor does not advance, the second pass only confirms that the same message already exists before advancing the cursor. The unique key prevents a duplicate message, and the fixed processing order prevents the cursor from passing a message that has not been saved. That is the idempotent write in this example.

The Event Log provides the ability to read an event again. Each projector remains responsible for ensuring that repeated reads do not create duplicate results.

The append boundary must be more trustworthy than a projector

“The Event Log is the source of truth” is valid only when append itself is reliable. Concurrent writers for one Session must obtain an explicit order. They cannot each compute seq + 1 in memory and then write independently.

One conceptual database operation is:

UPDATE sessions
SET next_seq = next_seq + 1
WHERE session_id = :session_id
RETURNING next_seq;

INSERT INTO session_events(session_id, seq, event_id, type, payload)
VALUES (:session_id, :seq, :event_id, :type, :payload);

Sequence allocation and event insertion must share one atomic boundary, with unique constraints on (session_id, seq) and event_id. An implementation may instead use a log system that supports ordered append. The important point is that the fact store decides the order; a short-lived worker does not guess it.

An established order does not by itself make every event a valid fact. A Run lifecycle event must be submitted by its authoritative transition owner. In the same atomic boundary, the owner checks the expected state and version, the writer’s fencing token, the legal transition, and invariants such as “a Run converges to only one terminal state” before it allocates seq and appends. Otherwise, competing cancellation and completion writers could append both run.cancelled and run.completed, leaving contradictory outcomes in the source of truth.

Requests must also remain distinct from facts that have taken effect. A user cancellation can first append run.cancel.requested; only after the current owner resolves the race may it append run.cancelled or run.completed. A Projector may prevent an older event from overwriting a newer read view, but it cannot decide after the fact whether an authoritative event was legal.

event_id must be assigned stably before the first append and reused after an append timeout or lost response. If the ID already exists, the append boundary should compare a digest of the complete immutable event envelope: Session, Run, Model Turn, type, schema version, payload, and content references, excluding only fields assigned by the server such as seq and commit time. Matching content returns the original seq; any difference in scope or content returns a conflict. When the commit result is unknown, query by the original ID rather than generating a new one and appending again.

External side effects remain outside this transaction. If a Tool wrote to an external system but the Runtime did not receive a definite result, it should record an unknown outcome or effect identity and later converge through idempotent lookup and reconciliation. It must not fabricate a success event.

A projection is not second-class data

The message list and Run snapshot are not the source of truth, but they remain formal product interfaces. Projection does not move consistency problems into an asynchronous task. It gives each read model an explicit latency and repair strategy.

ProjectionOptimization goalAcceptable recovery path
Message viewRead content in conversation orderReplay from a cursor and upsert idempotently
Run snapshotRead current state quicklyApply state transitions and reject invalid regression
Realtime signalNotify online clients quicklyMay be lost; the client catches up by cursor
MetricsAggregate trendsReplay in batches with an explicit deduplication grain
Audit viewExplain who did what and whenPreserve identity and provenance

If the product requires a new message to be visible immediately after event commit, it may update a core projection synchronously or provide a read-your-write overlay. That is a read-consistency choice; it should not turn the message row back into another independent fact.

Back to the problem

The opening contradiction arose because three write paths all claimed to record the result. Once the Runtime’s persistence boundary becomes an ordered append to the Session Event Log, Run state, messages, realtime notifications, and metrics share one input.

When a projection fails, the system repairs a read view instead of executing the Agent again. One logical fact is submitted idempotently under a stable event_id, and views may be generated repeatedly. That is the source of recoverability.
