Agent 13: How New Input Enters the Next Turn During Execution

Separate steering, follow-up, cancellation, and durable admission to define when new input is accepted and consumed during a Run.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentRuntimeSteering

The problem

While an Agent is executing a write Tool, the user sends, “Stop writing and perform a read-only check first.” Should this message interrupt the handler immediately, or wait for the next Turn before reaching the model?

Appending it as an ordinary chat message may be too late if the current Run has already ended. Treating it as mandatory cancellation does not roll back a write that already occurred. Steering is a new control input, not time travel.

Steering enters Context only at a stable boundary

Context should remain stable while a model request or Tool batch is executing. Inserting a new message into a model request already sent has no effect. Modifying the message sequence before a batch of Tool Results has converged also breaks Tool Call/Result correspondence.

Pi therefore polls steering messages at a turn boundary: current Tool work converges first, then the new input enters the next model call. It may change the subsequent plan, but it cannot rewrite the facts of an Attempt that already started.

The opening message has two distinct meanings:

  • “Do not start another write” is a control intent for later work.
  • “What should happen to the write already started?” is decided by cancellation and effect reconciliation.

Only by separating them can the Runtime avoid mistaking steering for a rollback protocol.

Follow-up handles the race around stopping

Follow-up and steering are consumed at different times. Steering changes the next Turn while the Run is active. A follow-up is consumed when the Agent would otherwise stop and has no more Tool Calls or steering messages.

Pi’s current Loop order reflects this distinction: it checks steering at a turn boundary and checks follow-up on the otherwise-stop path. That order reduces omission on the ordinary termination path, but it does not close the terminal race atomically. New input can still enter the queue after the final drain returns empty but before Run settlement and remain unconsumed by the current Run.

Both input types can support queue modes such as one-at-a-time or batch drain. Queue mode decides only how the current process retrieves messages. It provides no cross-restart guarantee.

“Accepted” must declare its commitment level

When an API returns 202 Accepted, a caller may assume that the message has been saved durably. The actual system must distinguish:

received   the service received the request
admitted   policy accepted the input
durable    the input remains recoverable after restart
consumed   the input entered a specific Turn

Pi’s current Agent and Harness use in-memory queues. A return from steer() or followUp() means only that the message entered the queue in the current process. It must not be described as restart-safe admission.

Only if the product promises that an accepted message will still be processed after a process exit does the host need a durable inbox with:

  • a stable input ID and target Run/Session;
  • accepted, admitted, and consumed states;
  • idempotent submission and duplicate detection;
  • a wake-up mechanism for unconsumed input;
  • a rule to reject input or create a new Run when the target Run is terminal.

See Pi’s current implementation in agent.ts and agent-loop.ts.

A terminal race needs one owner

The hardest case occurs when the Agent is about to return its final answer just as a follow-up arrives. If the termination decision and queue admission do not share a boundary, the system may return accepted for a message that no Run ever consumes.

Closing this gap fully requires a host enhancement in which one owner serializes input admission, queue inspection, and the transition to terminal. Pi does not currently provide that atomic guarantee. A durable implementation can use a conditional update:

if run is accepting_input:
  append inbox item
else:
  reject or create a new run

There is no universal product choice. A conversational product may create a new Run for input that arrives after terminal; a strict workflow may reject it. What matters is that acceptance and the terminal transition are decided by the same fact source.

Stop, Steer, and Follow-up are different actions

They express different intent:

  • stop/abort: request that current work stop and wait for convergence;
  • steer: change the direction of the current Run’s next Turn;
  • follow-up: append the next input when the original task would otherwise end.

Putting all three into one free-text queue makes cancellation, ordering, and durability impossible to explain. The APIs may share a transport, but their durable state and consumption conditions should remain separate.

Back to the problem

When the user says, “Stop writing and perform a read-only check first”:

  1. The Runtime may issue a cancellation request, block new writes, and wait for invoked handlers to converge.
  2. A write that occurred or remains unknown enters query/reconciliation and is not overwritten by steering.
  3. The message enters Context at the next turn boundary.
  4. If the current Run has become terminal, product policy either rejects the input or creates a new Run.
  5. The message enters a durable inbox only if the product promises processing across restarts.

Pi currently provides clear in-memory queues and a defined consumption order. The host should describe their commitment honestly: an in-memory queue is a runtime control mechanism, while durable admission is a separate product protocol.
