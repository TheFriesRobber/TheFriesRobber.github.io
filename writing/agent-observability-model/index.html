Agent 33: A Shared Semantic Model for Agent Logs, Metrics, and Traces

Fix the grain, logical IDs, Attempts, and outcome taxonomy before connecting Agent logs, metrics, traces, and cost facts.

07/24/2026 Updated 07/27/2026 Views
Agent VerificationAgentObservabilityTracing

The problem

Consider a constructed example. An Agent Run calls write_report. Two requests reuse one stable operation key. The first does not return before its deadline; the Runtime queries the backend but still cannot determine the outcome, so it starts a second Attempt. The second returns successfully, and backend reconciliation eventually confirms that the operation produced only one Artifact revision. The Task is complete.

The same execution supports several apparently contradictory descriptions:

Attempt metric: one timeout, one success
Trace: first span ERROR, second span OK
Tool Execution: ultimately succeeded after backend reconciliation
Task: completed
Cost: both requests may have consumed resources

A dashboard that reports “50% Tool success” suggests that half of user operations failed. A dashboard that reports “100% Task success” hides the latency and cost of the first timeout.

The data is not contradictory. The question omitted two conditions: which execution grain a record describes and which objects its denominator contains.

Fix the grain before discussing success rates

One Agent activity contains several non-interchangeable objects:

Task task_7
  └─ Run run_12
       ├─ Model Turn turn_3
       ├─ Tool Execution tool_exec_42, proposal_from=turn_3, operation_id=op_17
       │    ├─ Attempt attempt_1 → timeout, local outcome unknown
       │    └─ Attempt attempt_2 → succeeded
       └─ Artifact report_9@v1 → delivered
GrainWhat one record representsQuestion it can answer
TaskOne user goalDid the user goal ultimately complete?
RunOne execution of the Agent LoopHow did this execution terminate?
Model TurnOne model responseWhat were model latency and usage?
logical operationStable business intent across Turns or Tool ExecutionsWhat effect did the same business action ultimately produce?
Tool ExecutionOne authorized logical actionDid the logical Tool action complete?
AttemptOne physical callHow stable was the downstream call?
ArtifactOne versioned outputDoes the result exist, was it delivered, and is it traceable?

“Tool success rate” is therefore incomplete. It must mean something such as:

confirmed-success terminal Attempts / all terminal Attempts
successful Tool Executions / all terminal Tool Executions

A timeout proves only that the caller did not obtain a result in time. For a side-effecting call, it does not prove that the write failed. The first Attempt remains unknown, and the second success alone cannot exclude a duplicate effect. Only after the stable operation key and backend reconciliation confirm the target Artifact state may the current verdicts of the Tool Execution and logical operation become succeeded. Otherwise, both remain unknown.

Logical IDs connect business objects; Trace Context connects propagation

A retry must preserve stable logical identity while assigning a new identity to each physical attempt:

{
  "task_id": "task_7",
  "run_id": "run_12",
  "turn_id": "turn_3",
  "operation_id": "op_17",
  "tool_execution_id": "tool_exec_42",
  "attempt_id": "attempt_2",
  "artifact_id": "report_9",
  "trace_id": "91aa...",
  "span_id": "18c2..."
}

operation_id identifies stable business intent and may span several Turns or Tool Executions. tool_execution_id remains stable across retries of that execution; attempt_id changes for every physical call. In this example the operation and Tool Execution happen to be 1:1, but that is not a general equality. Task, Run, Turn, and Artifact also need their own identities instead of being inferred from nearby timestamps or log text.

A Trace ID describes an observation-propagation path. A retry may start a new trace after crossing a Queue, callback, or worker boundary. Even when two Attempts remain in one trace, the trace ID is not the Tool Execution ID:

business relation: tool_exec_42 → attempt_1 / attempt_2
observation relation: attempt_1 → trace_4bf9, attempt_2 → trace_91aa

W3C Trace Context defines how trace context propagates across systems. The OpenTelemetry Trace API likewise uses TraceId and SpanId in SpanContext. These standards address observation propagation; they do not define Agent Task, Tool Execution, or Artifact identity.

Queue propagation must carry both business identity and Trace Context

An asynchronous boundary cannot propagate only one identity class. A Queue message can store business identity separately from observation context:

{
  "task_id": "task_7",
  "run_id": "run_12",
  "operation_id": "op_17",
  "tool_execution_id": "tool_exec_42",
  "message_id": "message_8",
  "trace_context": {
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
    "tracestate": "vendor=value"
  }
}

message_id belongs to the stable payload; delivery_id must not live in a message body that is redelivered unchanged. If the broker receive envelope supplies a native delivery identity, consumer ingestion parses and records it. Otherwise, ingestion generates a new delivery_id for every receive. A retry delivery reuses the operation and Tool Execution identities, while the new receive and physical call get new delivery_id and attempt_id values respectively. A Queue delivery is not an Attempt.

Depending on tracing policy, processing may continue the original parent or start a new trace linked to the message-creation context. Either topology uses Span parent/link for observation relations; explicit logical IDs still carry business parent/child and retry relations.

The same rule applies to SubAgents, callbacks, and background Jobs. If a legacy system did not propagate canonical identity, record only correlation mappings established at a trusted boundary. Leave unproven relations unresolved instead of forcing a join from timestamp proximity.

Three signal types share semantics, not identical payloads

Logs and Traces are suitable for high-cardinality identity. The OpenTelemetry Logs Data Model lets a LogRecord carry TraceId and SpanId, so a structured event can link to its span:

{
  "event": "tool.attempt.finished",
  "tool_execution_id": "tool_exec_42",
  "attempt_id": "attempt_1",
  "trace_id": "4bf9...",
  "effect.outcome": "unknown",
  "error.type": "deadline_exceeded"
}

Metrics aggregate and should not turn every run_id or tool_execution_id into a label. They are better suited to bounded dimensions:

agent.tool.attempts{
  tool="write_report",
  effect.outcome="unknown",
  error.type="deadline_exceeded"
} +1

Traces retain call paths, time, and attributes; Logs retain discrete events and diagnostic context; Metrics retain counts and distributions for an explicit grain. Exemplars, time-window and taxonomy queries, or a high-cardinality fact table can support drill-down.

OpenTelemetry’s error.type convention is useful within its scope. It recommends error.type for erroneous spans and related metrics, while noting that a handled internal error should not be copied onto the signal for a logical operation that completed normally:

  • Attempt 1 may have error.type=deadline_exceeded.
  • A successful Tool Execution must not inherit Attempt 1’s error as its terminal result.
  • Agent-specific outcome, failure_owner, and retry_disposition remain application contracts, not an existing OpenTelemetry Agent standard.

The outcome taxonomy must preserve uncertainty and ownership

An application-level result may include:

FieldExampleQuestion answered
effect.outcomesucceeded, failed, unknownWhat does current effect evidence establish?
control_statusactive, cancellation_requested, cancelled_before_dispatchWhat is the Tool Execution’s control and settlement state?
error.typedeadline_exceededWhat error was observed?
failure_ownertool_providerWhich boundary first owns the recovery decision?
retry_dispositionquery_before_retryWhat recovery is currently allowed?

cancelled_before_dispatch applies only to a Tool Execution with no Attempt. A cancellation request after dispatch cannot overwrite succeeded, failed, or unknown. failure_owner is not the process that threw an exception; it is the boundary closest to decisive facts. A gateway may emit the timeout while external storage owns the write fact, so the Runtime should query storage by operation key rather than treating the gateway as result owner.

The taxonomy should stay low-cardinality and versioned. Raw statuses, exception text, and provider responses can remain diagnostic evidence without becoming unbounded metric labels.

Cost facts follow the same lineage

The two Tool Attempts may consume Tool API and network resources. The Model Turn that proposed the Tool Call consumes model resources, while Sandbox, storage, or shared-cache lifetimes may span several Attempts. A provider’s daily total cannot explain why a successful Task was expensive, but attaching every resource to a Tool Attempt also mixes incompatible grains.

Record component-specific usage events first, then aggregate them along business lineage:

ComponentNative resource grainTypical usage
Model providerModel Turn or model-provider Attemptinput/output tokens, request
Tool provider / networkTool Attemptrequest, bytes, provider operation
Sandboxlease, session, or metering windowCPU-second, memory-second
StorageArtifact/Workspace revision and metering windowbyte-hour, operation
Shared cache / batchshared resource eventallocated through an allocation key

A conceptual usage event may look like:

{
  "usage_event_id": "usage_51",
  "component": "tool_provider",
  "resource_grain": "tool_attempt",
  "resource_id": "attempt_1",
  "quantity": 3,
  "unit": "constructed_request_unit",
  "task_id": "task_7",
  "run_id": "run_12",
  "operation_id": "op_17",
  "observed_at": "2026-07-24T09:00:00Z"
}

This is a synthetic field structure, not a provider billing schema. The raw event first binds to the object that consumed the resource, then rolls up through explicit relations. Usage with different units cannot be summed before conversion.

Separate:

  • observed usage: quantities directly observed in provider responses, meters, or usage events;
  • billed cost: charges reconcilable with a bill or explicit price version;
  • allocated cost: shared cache, batch, Sandbox, or storage costs distributed under a versioned rule.

Converting usage to billed cost requires a price_version. Allocating shared resources requires an allocation key, allocation_rule_version, and any unallocated remainder. Without them, a price or allocation change can silently rewrite historical Task cost.

“The Task was not delivered, so this cost was wasted” classifies an existing billed or allocated cost under a versioned result rule; it is not a field observed from the provider. Counterfactual “cost without the cache” is avoided-cost estimation and must separately preserve its method, baseline, version, and uncertainty. Neither value may overwrite the underlying usage and cost facts.

attempt_1 constructed request usage = 3
attempt_2 constructed request usage = 2

tool_exec_42 constructed request usage = 3 + 2 = 5

task_7 cost
  = model_turn cost
  + tool_exec_42 cost
  + allocated sandbox/storage cost
  + cost from other linked execution

Tool-request usage has one physical Tool Attempt as its denominator, and Tool Execution request usage sums its Attempts. Model usage remains at Model Turn/model-Attempt grain; Sandbox and storage preserve their own resource grains. Only after conversion under one currency, price version, and allocation method may cost roll up through Run and Task lineage. Cost per successful Task also needs an explicit time window and Task-success definition.

Recalculate the same execution

For one Task, one Tool Execution, and two terminal Attempts:

MetricNumerator / denominatorResult
Attempt confirmed-success rate1 confirmed-success Attempt / 2 terminal Attempts1/2
Attempt unknown-outcome rate1 unknown Attempt / 2 terminal Attempts1/2
Tool Execution success rate1 successful Tool Execution / 1 terminal Tool Execution1/1
Task completion rate1 delivered Task / 1 terminal Task1/1
Tool Execution constructed request usagesum of both Tool Attempts in the same unit5 constructed request units

These answers describe downstream stability, logical recovery, user outcome, and the request usage of this Tool Execution. They no longer conflict.

Back to the problem

After the first Attempt times out, the second succeeds, and backend reconciliation confirms that one operation produced one target Artifact, 50% and 100% can both be valid answers—if each names its grain and denominator.

Stable Task, Run, Turn, logical operation, Tool Execution, Attempt, and Artifact identities express business causality. Trace context expresses observation propagation. Logs and Traces retain high-cardinality evidence, while Metrics retain bounded aggregate dimensions. Model, Tool, Sandbox, and storage usage first bind to their native resource grains, then cost rolls up through the same Run and Task lineage.

Shared semantics means the three signal types agree on which object they observe, what result current evidence establishes, and who owns the next action. It does not mean copying every field three times.
