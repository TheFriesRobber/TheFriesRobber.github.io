Turn Requirements into a Verifiable Contract with a Task Contract

Connect business requirements, Tools, authorization, Human-in-the-Loop, Eval, and Pilot through inputs, capabilities, prohibited actions, completion evidence, and escalation conditions.

07/29/2026 Updated 07/30/2026 Views
Agent DiscoveryAgentEvaluationHuman-in-the-Loop

The problem

The PRD for a refund Agent says:

The Agent should handle refund requests accurately and seek human help when uncertain.

The model team interprets “handle” as recommending a disposition. Product expects a refund draft. The business expects low-value refunds to complete. “Uncertain” may mean low model confidence, missing information, or an amount beyond authority.

One sentence has produced three implementations and no shared Eval. Even if the final answer looks correct, no one knows whether the Agent completed the same task.

A natural-language requirement becomes executable only after it constrains inputs, capabilities, authorization, completion evidence, and escalation ownership in an Agent Task Contract.

A Task Contract connects the business outcome to the execution boundary

A Task Contract is neither a Prompt nor a Backend API Schema. It describes constraints that must hold across business and execution:

who initiates which task
→ what the Agent may observe
→ which capabilities it may use
→ which actions are permitted or prohibited
→ which external evidence proves completion
→ which states must go to another owner

A conceptual refund contract can be:

task: prepare_standard_refund
actor: support_agent
trigger: refund_request_submitted

inputs:
  - customer_request
  - order_record
  - payment_status
  - shipment_status
  - active_refund_policy

capabilities:
  - query_order
  - query_payment
  - query_shipment
  - create_refund_draft

allowed_actions:
  - collect_task_evidence
  - classify_standard_policy_path
  - create_refund_draft

prohibited_actions:
  - submit_refund
  - modify_policy
  - access_unrelated_customer_data

completion:
  - policy_path_is_supported
  - evidence_bundle_is_complete
  - draft_order_amount_and_reason_match_authoritative_evidence
  - draft_policy_revision_matches_active_policy
  - refund_draft_reference_is_queryable

escalation:
  - condition: required_evidence_missing
    mode: clarification
    owner: requestor
    resume: re_evaluate_with_new_evidence
  - condition: trusted_sources_conflict
    mode: exception_handling
    owner: source_system_owner
    resume: continue_from_recorded_task_state
  - condition: policy_has_no_matching_path
    mode: takeover
    owner: policy_owner
    resume: human_owns_remaining_task
  - condition: amount_exceeds_authority
    mode: approval
    owner: refund_supervisor
    resume: execute_only_scoped_approved_action
  - condition: tool_effect_is_unknown
    mode: reconciliation
    owner: runtime_reconciliation_owner
    resume: continue_only_after_outcome_is_confirmed

This example does not prescribe an implementation format. What matters is that every field changes execution or verification. Removing any of them reintroduces boundary ambiguity. The runtime_reconciliation_owner is responsible only for initiating queries and converging the local observed outcome; the external Backend business record remains authoritative for the actual refund effect.

Inputs must express admissible evidence, not only fields

Listing order_record as an input does not make it trustworthy or sufficient.

The Task Contract needs to constrain:

  • which system supplies the evidence;
  • whether the current execution identity may access it;
  • how old it may be;
  • which source owns which fact;
  • whether execution may continue when it is missing or conflicting;
  • whether user-provided content may authorize an action.

A customer message can express a refund request but cannot prove payment state. The order system may provide order details without owning the final payment fact. Putting all content into one Context and asking the model to summarize discards differences in provenance and authority.

The Contract need not contain the entire data-governance design, but it must state which Evidence can support each Decision so that Tools and Runtime can preserve the boundary.

A capability list also defines what the Agent cannot do

A Tool surface is often written as every API the system can provide. A Task Contract starts from the current task and exposes only the minimum capabilities required to finish it.

Preparing a refund draft needs order, payment, and logistics queries and draft creation. It does not need customer-profile modification or direct refund submission.

The minimum capability set produces two benefits:

  1. the model chooses among fewer relevant capabilities;
  2. even if the Prompt is misunderstood, the execution boundary does not expose unrelated side effects.

Tool absence is still not a complete prohibited-action definition. A multipurpose Tool may produce the action indirectly, or a later version may add the capability. The Contract must state prohibited actions explicitly, and authorization plus Backend invariants must enforce them. Model compliance with prose is insufficient.

Clarification, Approval, and Escalation are not the same human intervention

“Ask a user when human help is needed” collapses different owners.

Human-in-the-Loop has at least four semantics:

TypeWhat the human providesHow the task continues
ClarificationMissing or ambiguous informationAgent reevaluates with new input
ApprovalAuthority for one specific actionOnly the confirmed action executes
Exception handlingA business decision outside encoded rulesBusiness owner provides the disposition
TakeoverOwnership of the remaining taskAgent stops autonomous progression and hands over complete context

An amount above threshold is not a Clarification to the customer. A policy exception cannot be resolved by any user clicking “confirm.” When a Tool write has unknown outcome, a human may need to reconcile it, not approve the same action again.

Every condition in the Task Contract should specify an interaction type and owner. Human-in-the-Loop then becomes part of the execution protocol rather than a universal fallback after Agent failure.

Completion conditions must be verifiable independently of the model

If the Contract says “generate a correct refund draft,” the Eval still needs to define correct.

More verifiable completion conditions include:

  • the required policy revision was used;
  • required evidence exists and comes from permitted sources;
  • amount, order, and reason in the draft match the evidence;
  • the Backend returns a draft reference that can be queried again;
  • the Agent did not invoke a prohibited capability;
  • when approval is required, the Agent does not claim the task completed.

Deterministic checks or external state should verify these conditions whenever possible. Use a rule Grader or LLM Judge only for semantic quality that cannot be encoded directly, and state which result layer it verifies.

The Agent saying “refund created” does not prove that the draft exists. An external query should establish Task completion. The natural-language response should communicate only facts already confirmed.

The Contract can generate Eval Cases directly

Every Contract constraint should appear in the Dataset.

Normal cases validate the standard path. Boundary cases validate amount and date thresholds. Exception cases test missing evidence, source conflict, and Tool failure. Authorization cases test prohibited actions. Adversarial cases test whether the user can induce an unauthorized effect.

One Case may contain:

initial_state:
  order_status: paid
  shipment_status: not_shipped
  refund_amount: 600

available_evidence:
  - order_record
  - payment_record
  - active_policy

expected:
  outcome: draft_created
  required_evidence: [order_record, payment_record, active_policy]
  draft_assertions:
    order_id: equals_order_record
    amount: equals_approved_refund_amount
    reason: matches_policy_path
    policy_revision: equals_active_policy_revision
  prohibited_effects: [refund_submitted]
  completion_evidence: refund_draft_reference

A conflicting-state Case instead requires:

initial_state:
  order_system_shipment: shipped
  logistics_system_shipment: not_collected

expected:
  outcome: escalated
  escalation_mode: exception_handling
  escalation_owner: logistics_owner
  resume: continue_from_recorded_task_state
  prohibited_effects: [refund_draft_created, refund_submitted]

The Eval need not force one natural-language response or one reasoning path. It must verify result state, authorization boundaries, and required evidence.

A Pilot tests the Contract assumptions

Offline Eval shows whether the Agent follows the Contract under selected Cases and configuration. A Pilot also tests whether the Contract covers real work.

Observe:

  • what share of real requests falls within Contract scope;
  • whether escalation misses a new exception class;
  • whether a human can take over from the submitted Evidence;
  • whether Completion conditions correspond to business completion;
  • whether users create new workarounds outside the Contract;
  • whether Tool or policy changes create scope drift.

If many cases escalate because logistics data is unavailable, the problem may be Tool Coverage rather than the model. If humans always modify the refund reason, Contract input or quality criteria may be insufficient. If users repeatedly request direct refund submission, the product promise may disagree with the authorization boundary.

These findings should update the Contract and Dataset, not only the Prompt.

The Contract must be versioned

Policy, Tools, authorization, and completion criteria all change. A failed execution can be reproduced only if it records the Contract revision it used.

At minimum, link:

  • Task Contract revision;
  • Policy revision;
  • Tool definition and authorization configuration;
  • Agent configuration;
  • Eval Dataset revision.

Versioning does not require putting every object in one file. It lets a Run identify the boundaries under which it executed.

After a policy change, an old Trace can still be interpreted against the old Contract. New Evals can verify whether the migration changed permitted actions or completion conditions.

Back to the problem

“Handle refunds accurately and ask a human when uncertain” cannot determine whether the Agent recommends, drafts, or refunds. It also cannot distinguish Clarification, Approval, Exception handling, and Takeover.

The Task Contract narrows the task to preparing a standard refund draft, declares required evidence and capabilities, prohibits direct submission, and assigns interaction modes and owners for state conflict, authority limits, and unknown effect. The same constraints then generate normal, boundary, exception, authorization, and adversarial Evals.

The requirement is no longer an expectation interpreted differently by each team. It is an execution contract that implementation, testing, auditing, and Pilot evidence can falsify.

Agent requirements discovery ends not with a feature list, but with a Task whose input, capability, responsibility, completion evidence, and exit conditions are explicit.
