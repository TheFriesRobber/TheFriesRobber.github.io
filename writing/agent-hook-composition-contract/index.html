Agent 03: Hook Composition Order Must Be an Execution Contract

Define Hook phases, mutation rights, short-circuiting, cleanup, failure, and replay from a disabled Tool that reappears in a request.

07/27/2026 Updated 07/27/2026 Views
Agent CoreAgentRuntimeHooks

The problem

Before a Model Turn, a Runtime runs three Hooks:

  • a capability policy removes delete_file, which the current user is not allowed to use;
  • a provider transformer converts the internal request into a provider payload;
  • a trace observer records the Tool surface that the model actually sees.

If they merely share and mutate one object in registration order, the transformer may read delete_file from the original registry and add it back. The observer may record the candidates from before policy evaluation rather than the actual request. Each Hook is reasonable in isolation, yet their composition changes both authorization and observable fact.

beforeModel says only that a callback runs before the model. It does not say which callback runs first, what it may mutate, or whether its failure may repeat work that already happened. Hook composition must become part of the Runtime contract before Hooks can serve as stable extension points.

Pi currently exposes Hook slots, not this composition protocol

In the Pi source snapshot checked for this review, the Tool path has one beforeToolCall slot and one afterToolCall slot. beforeToolCall runs after argument validation and before the handler; afterToolCall runs after the handler returns. The current implementation has no multi-Hook phases or priorities, scope unwind, or stable hook_event_id. More importantly, an exception from afterToolCall enters the current Tool execution’s catch path and can present an already successful handler result as an error instead of isolating an Observer-delivery failure.

That does not make Pi’s behavior incorrect. A single-callback contract need not pretend to provide plugin composition semantics. The rest of this article defines a target contract that a host or higher-level Runtime needs when composing several extensions inside those slots. It must not be read as a guarantee Pi already supplies. See the pinned agent-loop.ts.

Registration order cannot carry authorization order

The position of a Hook in an array is often determined by module initialization. It should not implicitly define policy precedence. A safer design defines phases first, then uses explicit dependencies or priorities within a phase:

trusted inputs
→ policy decision
→ request transformation
→ observation scope
→ model or Tool execution
→ result normalization
→ output policy
→ observation close

This ordering establishes three constraints:

  1. policy narrows capabilities from trusted identity and current authorization;
  2. transformation may convert approved input but may not restore a removed capability;
  3. observation reads the final request and normalized result instead of treating an intermediate object as execution fact.

Runtimes may use different phase names. What matters is fixing which boundary owns decisions, which only transforms, and which only observes. Otherwise, adding a plugin can silently change a security boundary.

Each Hook receives only the mutation rights it needs

Phases alone are insufficient. Hooks within a phase should not automatically receive a mutable view of the entire Context.

Hook kindMay doMust not do
Policyallow, deny, require confirmation, narrow a surfaceadd capability beyond the Run envelope
Transformationproduce a new typed value from approved inputchange subject, authorization, or effect identity
Controlchoose a declared control branchdisguise an arbitrary string as a normal result
Observationrecord events, metrics, and tracesmutate requests or results, or trigger a business effect

Returning a new value makes a transformation easier to audit than mutating a shared object. An Observer should receive a read-only view. Sharing a process does not make “please do not mutate this object” an adequate fact boundary.

In the opening example, policy receives the three candidates and trusted authorization, then produces an allowed request containing only read_file and write_file. The transformer receives only that result. The trace observer records final Tool identities or a stable fingerprint after provider shaping. There is no path by which delete_file can re-enter the request.

A short-circuit must produce an observable typed outcome

Policy denial, a cache hit, budget exhaustion, or a pending user confirmation may all skip the normal invocation. Representing every branch with null or an early return makes denial, cache use, waiting, and a Hook bug indistinguishable.

A control Hook should return a bounded outcome:

continue(transformed_input)
deny(reason, policy_ref)
require_confirmation(action_ref)
use_cached(result_ref)
fail(error_class, retryable)

Each outcome defines where execution continues. deny and require_confirmation do not call the handler. use_cached skips the live request, but the cached result still passes through the same normalization and output policy. Every branch emits an execution event.

Short-circuiting then changes explicit control flow rather than hiding an early return inside a callback.

Before and After Hooks unwind as scopes

Tracing spans, temporary credentials, and resource leases usually come in pairs. They behave like nested scopes, not unrelated lists:

before A
  before B
    execute
  after B
after A

If After Hooks run in registration order, A may release a resource that B still uses. The Runtime should declare reverse unwind and use the same cleanup path for cancellation: every entered scope exits in reverse order, while cleanup errors are recorded separately and never overwrite the original cancellation or execution result.

A scope that was never entered needs no cleanup. An external effect that was already committed is not rolled back by unwind. Hook cleanup releases Runtime resources; it does not rewrite the external world.

Observer failure must not repeat a business action

Suppose write_file succeeds and the trace observer then times out while delivering an event to a collector. Marking the entire Hook chain as failed may cause an outer retry to run write_file again.

The record must preserve two owners:

Tool Execution: succeeded, artifact=report.md@v3
Trace delivery: unknown or failed, event_id=trace-19

When policy cannot decide, a high-risk action should generally fail closed. A pure transformation that fails before invocation can stop the current phase safely. Observer failure usually degrades or recovers independently. A compliance-sensitive system may require the audit channel to be ready before an effect, but that gate must happen before the effect. It cannot retroactively turn a completed write into a failure.

Replay reuses a stable Hook event identity

Recovery or retry may enter the same Hook again. Pure validation can be recomputed. A Hook with an external effect must declare its delivery contract.

Consider an After Hook that sends a notification. The notification arrives, but the process exits before its checkpoint advances. If recovery generates a new message ID, the user receives the notification twice. Two safe choices are:

  • promote the notification to an explicit Tool Execution with a logical operation and Attempts;
  • keep it as infrastructure behavior, but reuse a stable hook_event_id and require downstream deduplication or idempotent upsert by that identity.

A stable ID does not prevent a duplicate effect by itself. It gives the receiver a way to recognize one logical delivery. Whether at-least-once delivery is allowed and whether writes are idempotent must remain explicit parts of the Hook contract.

Counterexamples must verify the composition contract

Successful Hook registration does not prove safe composition. A minimum contract suite should verify that:

  • policy always precedes transformation, and a removed Tool cannot return from the registry;
  • deny and require_confirmation never enter the handler;
  • a cached result still passes output policy even though it skips the handler;
  • Before scopes enter in order and reverse-unwind on error and cancellation;
  • Observer delivery failure does not rewrite a settled business result;
  • replay reuses the same hook_event_id, with repeated delivery converging under the declared downstream contract.

Tool System Evaluation may continue to measure final selection and mutation, but deterministic composition invariants belong in direct Runtime contract tests first.

Back to the problem

The transformer must not bring delete_file back from the registry, and the trace must not record a surface that the model never saw. That requires:

  1. declared phases for policy, transformation, control, and observation;
  2. minimum mutation rights for each Hook kind;
  3. typed short-circuit outcomes recorded as execution facts;
  4. reverse scope unwind on success, error, and cancellation;
  5. independent recovery for Observer failure and business outcomes;
  6. stable Hook event identity and a declared delivery contract for replay.

Hooks are valuable because they extend a Runtime without breaking its existing execution contract—not because they let arbitrary code run at arbitrary points. Once composition order is explicit, adding a Hook no longer creates a hidden authorization branch or duplicate-effect path.
