Agent 34: Making Nondeterministic Evaluations Comparable

Use case × configuration × trial, dataset tiers, and a complete manifest to make Agent evaluations reproducible and comparable.

07/24/2026 Updated 07/27/2026 Views
Agent VerificationAgentEvaluationReproducibility

The problem

Consider two Agent configurations evaluated on five cases with five repetitions each. Both pass 20 of 25 valid trials:

Configurationcase 1case 2case 3case 4case 5
A4/54/54/54/54/5
B5/55/55/55/50/5

The overall pass rate is identical, but the risks are not. A varies on every case; B consistently fails one case in these observations. An overall mean erases the difference.

Likewise, a configuration scoring 20/25 today and 18/25 tomorrow does not by itself prove model regression. The dataset revision, prompt, Tool surface, fixture, grader, timeout, or external service may have changed.

A nondeterministic Eval must first establish the smallest comparison record, which inputs are equal, which environmental conditions are merely observed, and the denominator used for aggregation.

The base grain is Case × Configuration × Trial

An Eval needs three independent identities:

  • case: input, goal, fixture, and success conditions;
  • configuration: a comparable identity for the system under test;
  • trial: one actual execution under those conditions.
{
  "case_id": "address_update_17",
  "configuration_id": "config_sha256:...",
  "trial_id": "trial_03",
  "outcome": "task_failed",
  "failure_class": "wrong_tool_selection",
  "validity": "valid"
}

Runtime Attempts remain a lower-level grain. One trial may include several model or Tool Attempts. The Eval preserves the trial outcome while allowing drill-down into Attempt failures. A retry must not become a new case, and a later success must not overwrite an earlier trial.

Aggregation must be explicit:

micro success
= successful valid trials / all valid trials

per-case success
= successful valid trials for one case / all valid trials for that case

all-valid-trials-pass
= cases whose valid trials all passed / cases with at least one valid observation

A micro average gives more weight to cases with more valid trials. Report per-case support or equalize repetitions before comparison. all-valid-trials-pass describes valid observations only; if a case has an invalid trial, this metric alone cannot stand in for a complete release gate. Overall trends aid navigation, while per-case distributions reveal fixed blind spots and variance.

Invalid trials cannot disappear silently

If the Eval harness crashes or a fixture cannot start, a trial may produce no valid observation of the system under test. It can be marked infrastructure_invalid, but only after defining the boundary of that system.

If the production path depends on a provider, Runtime, or network and that dependency times out, the timeout is usually a valid system failure—not infrastructure noise to remove from the denominator. Corrupted evaluation data, by contrast, should not be reported as a model failure.

Report:

scheduled trials
valid trials / scheduled trials
infrastructure-invalid trials / scheduled trials
task successes / valid trials

If invalid rate changes materially between configurations, the remaining valid trials may no longer be comparable. The right conclusion is “investigate,” not another pass-rate comparison.

Dataset tiers are execution and gate contracts

TierPurposeTypical executionFailure meaning
SmokeShow quickly that the critical path runsfrequent, small, stable fixturesusually blocks later evaluation
RegressionPreserve confirmed important behaviorevery candidate change or before releasehandled by an explicit owner and gate
CapabilityExplore capability boundaries and coverage gapsperiodic or focused runsinforms analysis, not a default block
QuarantineIsolate a temporarily untrusted caseseparate execution and governanceexcluded from the main gate but requires exit criteria

A sanitized, reproduced production failure may enter capability first. It becomes regression only when the objective, fixture, and grader are stable and the behavior must be preserved. An infrastructure-flaky regression case may temporarily enter quarantine, but needs an owner, reason, entry time, and exit condition.

Quarantine is not a trash can. A case without an owner or reproduction plan no longer provides reliable evidence and should be fixed, redefined, or removed.

Tier does not imply a fixed size. Ten valuable regression cases may constrain a release better than a thousand repetitive questions. Repeated trials reveal variance; they do not increase dataset coverage.

A manifest separates pinned inputs from observed environment

The same model name and code commit do not make two Eval runs comparable. Behavior may also depend on:

  • dataset revision, case filter, and tier policy;
  • system prompt, templates, and Context assembly;
  • Tool names, descriptions, schemas, authorization, and adapters;
  • fixture and initial database or filesystem state;
  • Runtime, harness, grader, and rubric;
  • timeout, concurrency, retry, and resource Budget;
  • model router, fallback policy, and the requested model and sampling configuration;
  • provider support for optional parameters such as seed, the model version actually resolved, and response metadata;
  • execution time and unpinned external dependencies.

Pinned inputs are controlled by the evaluator. Their real identities come from immutable versions or content fingerprints:

dataset: regression@18
case_filter_sha256: ...
prompt_sha256: ...
tool_surface_sha256: ...
tool_authorization_policy_sha256: ...
authorization_fixture_sha256: ...
tool_adapter_sha256: ...
fixture_image_digest: sha256:...
runtime_commit: ...
harness_commit: ...
grader_sha256: ...
model_request:
  router_policy_sha256: ...
  fallback_policy_sha256: ...
  requested_model: provider/model-family
  provider_contract_version: ...
  sampling:
    temperature: 0.2
    top_p: 1
    seed: 7
  seed_support: supported
timeout_ms: 30000
retry_policy_sha256: ...
concurrency_policy_sha256: ...
resource_budget_sha256: ...
trial_count_per_case: 5

Derive configuration_id from a canonical representation of these pinned inputs excluding the ID itself, or from that manifest fingerprint; do not assign it from an experiment name. Sampling defaults also belong in the identity, or a provider-default change can masquerade as a change in the system under test. A seed is controlled only when the provider contract supports it and the request is not ignored. Unsupported or unverified seed behavior is an observed limitation, not evidence of determinism.

Observed environment records conditions that cannot be pinned completely:

started_at: 2026-07-24T09:00:00Z
resolved_model_id: provider/model-version
resolved_router_target: provider/route
provider_response_metadata: ...
seed_honored: unknown
external_dependency_revision: unknown
region: ...

This is a field-structure example, not a real experiment configuration. Controllable inputs should be fixed, uncontrollable conditions recorded, and unknowns never presented as reproduced facts.

Comparability needs its own verdict

Before comparing experiments, produce a diff:

Prompt fingerprintsamedifferentintended variable

Tool surfacesamesamecomparable
Fixturesamesamecomparable
Gradersamesamecomparable
External dependencyrevision unknownrevision unknownuncontrolled confounder

Only when the prompt is intentionally changed, the model request and router/fallback policy are fixed, and other critical inputs are equal can the observed difference be attributed to that candidate change within the stated scope. If dataset and grader both change, or one side honors a seed while the other ignores it, the results remain recordable but do not isolate the prompt.

Do not invent a plausible value for a missing historical Tool-surface fingerprint. State that the historical result is not strictly comparable and establish a new complete baseline.

Reproducibility also has practical limits. Even with the same seed, remote models and services may remain nondeterministic. A manifest does not promise token-for-token repetition; it identifies what was fixed and what could still vary.

Use per-case distributions to explain the opening result

ObservationConfiguration AConfiguration B
Valid trials per case5 each5 each
Observed successes for the worst case4/50/5
Cases whose trials all passed0/54/5
Failure coveragespread across 5 casesconcentrated in 1 case

Five trials are finite observations, not the system’s true long-run probability. They support a narrower statement: for these cases under this manifest, A shows broad variance while B shows a stable blind spot.

Release decisions still depend on product semantics. One forbidden unauthorized write may be a hard gate despite a high overall pass rate. A safely retryable, side-effect-free failure can instead be evaluated under the real retry policy at the Task-outcome grain.

Back to the problem

The same pass rate does not imply the same risk, and different scores from the same version do not automatically prove model drift.

Preserving case × configuration × trial, explicitly separating valid and invalid denominators, and assigning smoke, regression, capability, and quarantine responsibilities reveals whether failures are concentrated or broadly variable. A complete manifest separates pinned inputs, the intended variable, and uncontrolled environment so that every comparison must first establish that it is comparable.

Reproducibility for a nondeterministic Eval does not require identical output. It requires every difference to remain attributable to a case, configuration, trial, and any conditions that were not controlled.
