State Machines, Leases, and Idempotency for Long-Running Tasks

07/12/2026
Distributed SystemsState MachineLeaseIdempotency

The Problem

Consider a task that runs for half an hour: read its input, generate a result, call an external API, and finally persist the artifact location. Worker A claims the task and calls the external API, but receives no response. It then loses network connectivity and its lease expires. Worker B takes over and starts the work again. At that point, A resumes and the delayed API response arrives.

The system now has to answer several questions:

  • How far has the task actually progressed, and which facts are durable?
  • If A and B can both continue running, whose writes are still valid?
  • If the external operation may already have succeeded, can B call it again?
  • If the user cancels now, does that represent a request or an accomplished fact?

A single running field and a try/catch block collapse these questions into one. Reliable long-running tasks usually need three independent mechanisms: a state machine records progress, a lease manages temporary ownership, and idempotency plus reconciliation constrains side effects.

Three Mechanisms for Three Different Problems

MechanismQuestion it answersWhat it does not provide
State machineWhich business facts are committed, and which step is legal next?It cannot prove that only one worker is currently running
Lease + fencing tokenWho temporarily owns execution, and whether a delayed write is still validIt cannot automatically remove duplicate side effects in an external system
Idempotency + reconciliationHow retries of the same business intent reuse a result, and how uncertain outcomes convergeIt cannot replace the task lifecycle itself

Leaving out any one of these layers makes correctness depend on an assumption that does not hold: processes never pause, a timeout means execution failed, a message is delivered only once, or an old worker immediately stops when its lease expires.

A State Machine Records Committed Facts

  • retryable_failed means the error has been classified and remains within the retry budget. It is not the default destination for every exception.
  • waiting_external means the external outcome is unknown and requires a query or reconciliation. It does not mean that the call failed.
  • cancel_requested means the user’s intent is durable. The task can enter cancelled only after the system knows that no unresolved side effect remains.
  • succeeded, terminal_failed, and cancelled are terminal. A delayed callback must not move the task back to running.

state_version provides optimistic concurrency control. A worker transition must be an atomic conditional write, not a read followed by an unconditional overwrite:

UPDATE tasks
SET state = :next_state,
    state_version = state_version + 1
WHERE task_id = :task_id
  AND state = :expected_state
  AND state_version = :expected_version
  AND fencing_token = :fencing_token;

If this statement updates zero rows, the state, version, or owner has changed. The worker must reload the durable facts instead of continuing under the assumption that it still controls the task.

User cancellation is a control-plane write. It should also check the current state and state_version, but it should not impersonate a worker by reusing the worker’s fencing token. The two write paths can use different permissions while the state machine resolves their ordering. If cancellation commits first, a completion based on the worker’s old version must fail. If success commits first, a delayed cancellation must not replace the terminal state with cancel_requested.

A snapshot answers “what state is the task in now?” but cannot explain how it got there. A practical design normally appends transition events containing from_state, to_state, reason, actor, attempt, fencing token, and timestamp. The snapshot serves online reads; the event log serves audit, debugging, and recovery analysis. History should not be encoded in an ever-growing state string.

A Lease Represents Temporary Ownership

Long-running work should not hold a database transaction or row lock for its entire execution. A worker can claim a task in a short transaction, receive an expiring lease, and renew it periodically while it runs.

The following is a conceptual claim operation; exact syntax depends on the database:

UPDATE tasks
SET lease_owner = :worker_id,
    lease_expires_at = CURRENT_TIMESTAMP + :lease_duration,
    fencing_token = COALESCE(fencing_token, 0) + 1,
    state = 'running',
    state_version = state_version + 1,
    attempt = attempt + 1
WHERE task_id = :task_id
  AND state IN ('pending', 'running', 'retryable_failed')
  AND (next_attempt_at IS NULL OR next_attempt_at <= CURRENT_TIMESTAMP)
  AND (lease_expires_at IS NULL OR lease_expires_at <= CURRENT_TIMESTAMP)
RETURNING fencing_token, state_version, lease_expires_at;

Claiming the task and incrementing the fencing token must be one atomic operation. Expiration should preferably be decided using the clock of the system that stores the lease, rather than each worker’s local clock. Otherwise, clock skew becomes part of the ownership decision.

Renewal must also match the current owner and token:

UPDATE tasks
SET lease_expires_at = CURRENT_TIMESTAMP + :lease_duration
WHERE task_id = :task_id
  AND lease_owner = :worker_id
  AND fencing_token = :fencing_token
  AND lease_expires_at > CURRENT_TIMESTAMP;

After a renewal updates zero rows, the worker should stop starting new work. That is still not a correctness guarantee: the process may pause before renewal, resume after another worker has taken over, and have no opportunity to observe the failed renewal first.

Lease duration trades off two costs. A lease that is too short causes unnecessary takeovers during transient delays; one that is too long delays recovery after a real failure. The heartbeat interval should be comfortably shorter than the lease and leave room for storage latency and short pauses. This choice affects availability, but it does not replace fencing.

Lease Expiration Does Not Stop the Old Worker

Worker A can start while its lease is valid and then pause because of GC, process suspension, or a network partition. Once its lease expires, Worker B obtains a new lease. When A resumes, both processes may still be executing.

A fencing token is a strictly increasing number issued on every successful acquisition. The protected resource stores the greatest token it has accepted and rejects smaller values:

UPDATE task_outputs
SET payload = :payload,
    last_fencing_token = :fencing_token
WHERE task_id = :task_id
  AND (last_fencing_token IS NULL
       OR last_fencing_token < :fencing_token);

A random UUID can distinguish owners, but it does not order them and therefore cannot serve as a fencing token by itself. Another common mistake is checking the owner only when releasing the lease. That prevents A from deleting B’s lease, but it does not stop A from modifying the actual business resource after it resumes.

The final resource that receives the write must enforce fencing. If an external API does not understand the token, fencing does not protect that side effect. The design then has to depend on the API’s idempotency contract, a stable business identifier, and reconciliation.

An Idempotency Key Must Represent a Business Intent

Retries are unavoidable. The goal is not to make code “run only once,” but to ensure that every attempt and every worker uses the same idempotency key for the same logical action.

For example, “publish revision 3 of the report for this task” could use:

effect_key = hash(task_id, "publish-report", input_revision=3)

The following keys are usually wrong:

request_uuid()       # different on every retry
worker_id            # changes after takeover
attempt_number       # deliberately turns each retry into a new action
current_timestamp    # cannot identify two calls as the same intent

The system can maintain an effect ledger:

effect_key        unique
task_id
step_name
input_revision
payload_hash
status            pending | in_progress | unknown | succeeded | terminal_failed
external_ref
result
created_at
updated_at

The unique constraint on effect_key merges concurrent requests. payload_hash prevents the same key from being reused with different parameters. The handling rules are:

  1. Atomically create a record the first time the key appears.
  2. For a succeeded key, return the stored result or external_ref.
  3. If the same key is in_progress or unknown, do not create a new logical action. Query or wait, or recover with the same key after confirming that the original owner is gone.
  4. If the same key arrives with a different payload, return a conflict instead of replaying the old result.

An idempotency contract also needs a scope and a retention period. If the downstream system retains a key for 24 hours but the task may retry after three days, a duplicate can still be created once the old key is removed. A caller needs to know more than whether idempotency is “supported”: it needs to know how parameters are compared, which results are cached, how long keys live, and how concurrent requests are handled.

A Timeout Means Unknown, Not Failed

An external call can time out before the request arrives, while the remote system is committing it, or after the operation succeeds but before the response reaches the caller. The caller sees the same timeout in all three cases and cannot infer whether the side effect occurred.

The safe response is not to generate a new key and resend immediately. A more reliable path is:

  1. Persist an effect intent and stable key before the call.
  2. If the external system supports idempotency keys, retry with the same key.
  3. If it can query by a client reference, look for the existing result first.
  4. If the outcome remains uncertain, mark the effect unknown and move the task to waiting_external.
  5. Let a reconciliation job query until it confirms success, confirms failure, or reaches a terminal state that requires manual handling.

If an external system supports neither an idempotency key nor lookup by a stable business identifier, no generic technique can guarantee both “never duplicate” and “eventually execute.” The system has to choose a risk: refusing to resend can lose an action, while resending can duplicate it. High-risk operations also need compensation or manual review.

A transactional outbox solves the dual write between committing local database state and publishing a message: update business data and insert an outbox row in one transaction, then let a relay deliver the message. The relay or broker can still deliver duplicates, so the consumer remains responsible for idempotency. An outbox also cannot make an arbitrary external API atomic with the local database.

How One Execution Converges

Putting these mechanisms together, a worker execution looks roughly like this:

def run(task_id, worker_id):
    lease = claim_task(task_id, worker_id)
    if lease is None:
        return

    # A separate heartbeat renews only a lease matching owner + fencing_token.
    heartbeat.start(task_id, worker_id, lease.fencing_token)

    try:
        task = load_task(task_id)
        if task.state == "cancel_requested":
            reconcile_then_cancel(task, lease)
            return

        key = stable_effect_key(
            task_id=task.id,
            step="publish-report",
            input_revision=task.input_revision,
        )
        effect = get_or_create_effect(key, payload_hash(task.input))

        if effect.status == "succeeded":
            complete_task(task, effect.result, lease.fencing_token)
            return

        result = provider.publish_report(
            task.input,
            idempotency_key=key,
        )
        record_effect_and_complete_task(
            task=task,
            effect_key=key,
            result=result,
            expected_state_version=task.state_version,
            fencing_token=lease.fencing_token,
        )
    except NetworkTimeout:
        mark_effect_unknown_if_owner(task_id, key, lease.fencing_token)
        move_to_waiting_external_if_owner(task_id, lease.fencing_token)
    finally:
        heartbeat.stop()

The example omits database-specific transactions and error classification, but preserves the important boundaries: the effect intent exists before the remote call; retries reuse a stable key; completion is guarded by the state version and fencing token; and a timeout enters unknown-outcome handling instead of becoming a confirmed failure.

If record_effect_and_complete_task writes the effect and task to the same database, it should commit them in one short transaction where possible. If they do not share a transaction boundary, the design must identify the source of truth and define how the other view converges through reconciliation.

Recovering from Common Failures

Failure pointUnsafe responseConvergence path
Worker crashes before the external callLeave the task running foreverLease expires; the new worker reuses the persisted effect intent
External call succeeds before the result is recordedCall again with a new keyRetry with the original key or query by client reference, then persist the result
Worker pauses beyond its leaseAssume the old worker stoppedNew owner receives a larger token; the resource rejects the old token
Heartbeat renewal failsContinue starting new side effectsStop new work; keep checking token and version on every later write
Callback arrives after a terminal stateMove the task back to runningAssociate it by effect key and validate the transition; keep the terminal state
Cancellation races with external successReport cancelled immediatelyPersist cancel_requested; reconcile or compensate before entering a terminal state

Recovery should resume from the last durable boundary, not blindly restart the function from the top. If different steps have different side-effect semantics, each step needs its own stable key and result record.

Retry Needs a Budget, Not Just a Loop

Idempotency makes retries safer, but it does not justify retrying forever. The task model should record:

  • Which errors are retryable and which represent invalid input, missing permission, or a terminal business constraint.
  • attempt, next_attempt_at, and a maximum attempt count or maximum elapsed time.
  • Exponential backoff and jitter, so recovery does not send a synchronized burst to a downstream dependency.
  • The reconciliation interval and the maximum acceptable age of an unknown effect.
  • Whether an exhausted budget leads to terminal_failed, a compensation queue, or manual handling.

A task waiting for backoff should not keep its lease. Persist retryable_failed and next_attempt_at, release ownership, and let the scheduler reclaim it when the time arrives.

Observe State Transitions and Uncertainty

Average task duration is not enough to explain the reliability of long-running work. More useful signals include:

  • Entries into each state and time spent there, especially the age of waiting_external.
  • Lease acquisitions, failed renewals, expired takeovers, and concurrent owners observed for one task.
  • Fencing rejections, which are evidence that an old worker or delayed request actually existed.
  • Idempotency hits, payload conflicts, and retries that reused a stored result.
  • Effects in unknown, their reconciliation attempts, and their eventual outcomes.
  • Invalid transitions, optimistic concurrency conflicts, and callbacks arriving after a terminal state.

Logs and traces should carry task_id, attempt, effect_key, state_version, and fencing_token. A task ID alone often cannot distinguish a legitimate takeover from duplicate logs emitted by the same worker.

Design Boundaries

This is not the minimum implementation for every background job.

  • If an operation is short and all reads and writes fit in one database transaction, a simple queue table or transactional lock may be enough.
  • A queue visibility timeout is itself a kind of lease. Messages can still be delivered more than once, so it does not replace business idempotency.
  • A workflow engine can provide durable timers, retries, and state recovery, but the application still defines idempotency keys, business terminal states, and compensation semantics for external side effects.
  • Fencing works only when the resource checks the token. An external system that cannot do so needs a stable business key, lookup, and reconciliation.
  • “Exactly once” should be decomposed into a concrete contract: a message may be delivered more than once, but one business effect produces at most one observable result; or duplicate results can be detected and compensated. The entire distributed execution should not be described loosely as running once.

Back to the Problem

The core of reliable long-running work is not preventing every failure and retry. It is giving each recovery a precise boundary:

  1. The state machine states which facts are committed and which transitions remain legal.
  2. The lease makes work recoverable after a worker disappears, while the fencing token stops an old owner from overwriting a newer result.
  3. A stable idempotency key identifies attempts as the same business intent.
  4. A timeout becomes an unknown outcome that converges through lookup, a retry with the same key, or reconciliation.
  5. Cancellation, failure, and success are durable facts—not return statements inside one process.

Once state, ownership, and side effects each have their own protocol, worker crashes, duplicate messages, network partitions, and delayed callbacks no longer collapse into the vague instruction to “try again.”
