How a Spawn Request Becomes a Controlled Child Run

07/15/2026
AgentRuntimeMulti-Agent

The problem

While executing, the primary Agent discovers two temporary subproblems: comparing database options and analyzing deployment approaches. It submits two Spawn Requests to the Runtime:

spawn_agent(type="research", goal="compare database options", mode="sync")
spawn_agent(type="research", goal="analyze deployment approaches", mode="sync")

The example does not let the model choose a request ID. When this Tool Call first enters admission, the trusted Runtime allocates and persists a spawn_request_id for that Tool Call within the parent Tool Execution. Every retry Attempt for the same logical Tool Call reuses it; only a new delegation intent receives a new ID.

These two Tool Calls are only creation requests; they are not SubAgents that have already been created. The real questions begin here: should the Runtime allow them? Which Agent definition should it use? What is the relationship between each child and the parent Run? What can a child see, and how does it return a result?

One expedient implementation creates a new model session for every request, then copies the parent Agent’s complete Context, every Tool, its credentials, and the same workspace.

Both children write their results to report.md. The one that finishes later overwrites the earlier file, and one child also reads unrelated user information from the parent Context. In the end, the parent Agent receives only two messages saying “completed.” It cannot tell which file to trust or verify where each conclusion came from.

The problem is not that there are too many SubAgents. It is that the Runtime interprets a Spawn Request directly as “copy the parent Agent.” Without a creation protocol, sharing becomes the default: shared Context, credentials, workspace, and budget—and ultimately shared responsibility.

The previous article, “When an Agent Creates a Subtask, Who Should Execute It?”, explained why this subproblem is suitable for a SubAgent. This article takes the next step: once SubAgent has been selected, how does the Runtime turn one creation request into a Child Run managed by its parent Run?

A Spawn Request is only a creation proposal

The model may propose a goal, a SubAgent type, and the desired return mode, but it cannot create a trusted Agent definition, authorization, or credential by itself. A retry of the parent Tool Execution may also submit the same request again, so the creation flow must first define an idempotency boundary. The Runtime needs at least the following steps:

parent Agent produces Spawn Request
→ dedup: look up an existing result by parent_run_id + spawn_request_id
→ admission: check Tool Surface, nesting depth, concurrency, and remaining budget
→ resolution: resolve the Agent definition and revision from a trusted Registry
→ reserve: allocate child_run_id and atomically record the request, parent,
  definition revision, and preparing state
→ compilation: narrow Context, capabilities, workspace, and deadline for this child_run_id
→ activation: atomically persist the envelope, ready state, and dispatch intent or outbox
→ dispatch: deliver idempotently by child_run_id, or claim the durable ready record
→ collection: return a structured result or handle to the parent Agent

Here, a Child Run is an Agent execution with its own run_id and execution state whose lifecycle is still managed by the parent Run. It may be ephemeral, or a durable Runtime may persist and restore it together with the parent Run. The parent Runtime can cancel an owned Child Run and owns its retry policy: an explicitly paused or otherwise incomplete Child Run may resume with the same run_id, while retry after terminal failure creates a causally linked new Child Run. Promotion to a Child Job is warranted only when state, retries, and control must leave the parent Run and be owned and converged by a persistent job system. A worker or process restart alone does not require an ownership transfer.

spawn_request_id is an idempotency key scoped to the parent Run and bound by the trusted Runtime to a stable parent Tool Execution or Tool Call identity. When the same logical request is retried because of a timeout or a lost Tool Result, the Runtime returns the same child_run_id, or the admission failure already determined by the first attempt. It must not create a second Child Run.

If the preparing record lives in a durable store, a reconciler can resume compilation after a crash between reserve and activation, or converge the record to an explicit failure. Activation cannot mean “write ready, then enqueue only in memory.” The envelope, ready state, and dispatch intent or outbox commit together; a dispatcher then delivers idempotently by child_run_id. Alternatively, a scheduler can poll and claim durable ready records directly. Either design lets the child be rediscovered after a crash in the ready-to-dispatch window. Reconciliation also scans records stuck in preparing or ready instead of waiting on one lossy notification. A purely in-process implementation can deduplicate and execute only while its records and scheduler remain alive; it provides no cross-crash guarantee.

An admission failure should also become an explicit Tool Result, such as spawn_not_allowed, depth_exceeded, or budget_exhausted. The system must not start a child first and then leave the model to infer from a timeout whether creation succeeded.

Delegation is not copying the parent Agent

A SubAgent exists to complete a constrained subproblem, not to clone every aspect of the parent Agent’s identity and capabilities. A delegation contract needs to answer at least these questions:

What is the goal?
Which Context may it read?
Which Tools may it call, and under whose identity?
Which workspace may it read and write?
How much time, token usage, and cost may it consume, and how many concurrency slots may it occupy?
What happens when the parent is cancelled?
Which schema must the result follow, and who validates it?

These details can form a delegation envelope:

{
  "delegation_id": "delegation_7",
  "spawn_request_id": "spawn_19",
  "parent_run_id": "run_8",
  "parent_tool_execution_id": "tool_exec_12",
  "child_run_id": "run_21",
  "definition": {"id": "research", "revision": 4},
  "mode": "sync",
  "goal": "compare the tradeoffs between two database options under the current constraints",
  "context_refs": ["requirements_v3", "traffic_assumptions_v2"],
  "tool_surface": ["web_search", "read_workspace"],
  "authority": {
    "actor_ref": "principal_21",
    "subject_ref": "subject_8",
    "grant_ref": "grant_41",
    "audience": ["search-service", "workspace-service"],
    "scopes": ["web:search", "workspace:read"],
    "expires_at": "2026-07-17T09:03:00Z"
  },
  "workspace": {"read": ["/inputs"], "write": ["/outputs/db"]},
  "limits": {"deadline_seconds": 180, "max_model_turns": 8},
  "result_schema": "research_result.v2"
}

The envelope contains execution-authorization references and result expectations; it is not a long prompt for the model. principal_21 is a per-Run execution principal bound and authenticated by the trusted Runtime for this Child Run. The bare execution-record ID run_21 never authorizes anything by itself. The trusted execution layer resolves actor, subject, audience, scope, and expiry again from the unforgeable grant_ref, then checks path and resource limits. These fields constrain and audit execution. A child must not be able to expand its authority merely by modifying the JSON.

Synchronous results and asynchronous handles are still owned by the parent Run

In synchronous mode, the parent Tool Execution waits for the Child Run to reach a terminal state, then passes the structured result to the next model round as the Tool Result of this spawn_agent call:

parent Tool Execution waiting_for_child
→ child Run completed
→ validate child result
→ parent Tool Execution succeeded
→ result enters next parent Model Turn

Asynchronous mode can return a stable child_run_id first, allowing the parent Agent to continue other work and collect the result later through get_child_result or a completion event. But a handle does not automatically provide durability. If the Child Run exists only in the current process, it is still lost when that process exits. If a durable Runtime persists parent and child state, both can resume in a new worker while the parent Run remains the owner. Promotion to a Child Job or durable workflow node is warranted only when the child’s state, retries, and control must leave the parent Run and be owned and converged by the job system or workflow.

In either mode, the parent Run must record who created the child, which Tool Execution is waiting for its result, how cancellation propagates, and whether the result has already been consumed. Otherwise, “background execution” merely leaves an unowned coroutine inside a process.

Context should be selected for the task, not inherited by default

Inheriting the complete parent conversation is convenient, but it creates three problems:

  • Irrelevant information consumes the child’s Context budget.
  • User information and content from other tasks may cross a boundary where they are not needed.
  • Once the parent Context changes, the same delegation becomes difficult to reproduce.

A more reliable design passes identified Context references and records their versions. The database-research child needs only requirements, traffic assumptions, and the public sources it is allowed to use. The deployment child receives deployment constraints; it does not need to read user preferences or other conversations.

When necessary, the parent Agent may attach a briefing, but it should be marked as a derived summary and retain references to its sources. A summary must not become a new, unsourced truth after being separated from the original facts.

Tools and credentials are two separate boundaries

Registering read_file for a child does not authorize it to read every file. Registering a Connector does not mean copying the parent’s OAuth token into the child.

The system should control two layers separately:

  1. Tool Surface: which actions the model can see.
  2. Capability grant: which actor is acting for which subject, against which audience or resource, with which scopes, and until when.

For example, a child may see read_workspace, while its grant permits only /inputs. It may see web_search but have no access to the internal network. When it needs to call an external API on a user’s behalf, it uses a short-lived delegation reference; the backend validates actor, subject, audience, scope, and expiry again. Delegation must also be distinguished from impersonation: delegation preserves the child actor’s identity, while impersonation presents only the subject, so their audit semantics differ.

Secrets do not enter the prompt, RunSpec, or result. Even when the child and parent Agent run in the same process, a logical credential boundary should remain. Otherwise, moving them to separate workers later will expose hidden dependencies.

Workspace isolation must turn paths into ownership

The overwrite in the opening example happens because both children write to report.md. Telling the models “do not overwrite each other” is not isolation.

The Runtime can allocate a separate directory to each delegation:

/inputs                         read-only shared inputs
/outputs/delegation_7/          database child writes here
/outputs/delegation_8/          deployment child writes here

The parent Agent reads only declared artifacts after a child completes. If several children must modify the same object, they need a separate merge protocol, version preconditions, or serialized commits by the parent. The design must not rely on last-write-wins.

After the opening example uses isolated directories, the two children each return a result like this:

{
  "status": "completed",
  "summary": "...",
  "artifacts": ["/outputs/delegation_7/comparison.md"],
  "evidence": [{"claim": "...", "source": "https://..."}],
  "limitations": ["not validated against a real workload"]
}

The parent Agent no longer has to guess which file in a shared directory is the final result.

Budgets and cancellation need a parent–child relationship

A child’s own timeout cannot replace the parent budget. If the parent Run has only 60 seconds remaining, it should not start a child with a five-minute deadline unless that child has already been promoted to an independent Child Job.

The effective child deadline is usually:

min(parent_deadline, delegation_deadline, system_limit)

Token usage, Tool Calls, and cost are cumulative consumption and need to roll up to the parent. Concurrency is not a cumulative budget; it is a capacity or admission limit at a particular moment. Nesting depth and rate limits are checked separately as well. Otherwise, the primary Agent can still evade its own limits by continually spawning children.

When the parent is cancelled, the Runtime should propagate a cancellation request to the child and wait until the agreed boundary. Cancellation begins as a cooperative request. The Runtime can forcibly stop computation after a grace period only when the child runs in a separately terminable process, worker, or sandbox. A coroutine in the same process may delay or even suppress cancellation.

Whether computation stopped says nothing by itself about whether an external side effect occurred. A terminated child may also be unable to return a result. A trusted Runtime or external effect owner should therefore use execution records and reconciliation to produce a separate effect outcome: confirmed, not_applied, or unknown. The system must not infer from cancelled that no external side effect occurred.

Results must be verifiable, not just natural language

The parent Agent remains responsible for the final answer to the user. A SubAgent response saying “research complete” does not transfer that responsibility.

At minimum, the result schema should distinguish:

  • completed, partial, failed, and cancelled.
  • An effect outcome separate from Child Run state: confirmed, not_applied, or unknown.
  • Conclusions that can be used directly from inferences that still require validation.
  • Artifact references and content summaries.
  • Evidence and provenance for every important claim.
  • Known limitations and unfinished work.

The parent Agent can validate the schema, read artifacts, spot-check references, and decide whether to accept, reject, or request more work when children disagree. If a result would trigger a high-risk action, it must pass through parent authorization or user confirmation again. A child’s natural-language conclusion cannot be treated as approval.

Those checks do not upgrade child output into trusted instructions. The child’s summary, Artifacts, and evidence enter the parent Context as untrusted data. They cannot override parent instructions, policy, Tool Surface, or authorization. Provenance, schemas, and renewed authorization are additional controls; they do not turn text from an external source into an executable command.

How to handle partial failure

If one of two children succeeds and the other times out, the parent cannot rely only on whether gather() raises an exception. The delegation contract should define its result policy in advance:

  • all_required: any child failure prevents the parent from continuing.
  • partial_allowed: retain successful results and identify the gap in the final answer.
  • fallback: after failure, switch to the parent Agent or another capability.

The policy belongs to the parent because the parent owns the final goal. A child reports only its own state and evidence; it does not declare the entire Run successful.

Isolation is about ownership, not container count

Isolation does not mean every piece of data must be copied. Read-only, version-pinned inputs can be shared safely. A connection pool in the same process can also be reused as a Runtime mechanism. The design needs to isolate semantic ownership and authorization, not create more containers for appearance’s sake.

If a child performs only a few seconds of text classification, with no Tools, workspace, or sensitive Context, a focused prompt and structured output may be enough. The delegation contract should be proportional to the risk.

Back to the problem

A SubAgent is neither a complete Agent created directly by the model nor merely one more isolated model call. The model produces a Spawn Request. A trusted Runtime deduplicates it by request identity, performs admission and definition resolution, reserves a Child Run identity, then compiles the delegation, activates it, and schedules execution.

An explicit envelope gives the goal, Context, Tools, credentials, workspace, budget, cancellation, and result their own boundaries. Stable parent–child identities connect the creation request, Child Run, and parent Tool Execution. A structured result returns evidence and limitations to the parent. The parent Agent remains responsible for validation and the final decision, so parallel collaboration no longer depends on default sharing that makes results impossible to attribute.
