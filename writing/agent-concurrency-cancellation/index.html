Agent 09: Ordering, Consistency, and Cancellation for Concurrent Tools

Separate event announcement, handler invocation, completion order, Context order, shared mutation, and layered cancellation guarantees.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentConcurrencyTools

The problem

In one Turn, the model proposes two Tool Calls that both update resource doc-7. The Runtime executes them concurrently. The second completes first, and then the parent Run cancels the first. In what order should the final Context receive their results? Is the shared resource consistent? When may the parent Run be considered finished?

“Concurrent execution” spans events, function calls, external state, and parent-child lifecycles. Saying that the implementation uses Promise.all does not answer any of these questions.

A start event does not mean that the handler has started

In Pi’s current agent-loop.ts, tool_execution_start is emitted before validation, beforeToolCall, and handler invocation. The parallel path also performs preflight for each Tool in sequence before using Promise.all to await executable handlers.

The following boundaries must therefore remain distinct:

event announcement
→ validation / callback preflight
→ handler invocation
→ external effect
→ completion event
→ Tool Result enters Context

An invalid Tool Call, one blocked by a callback, or one already cancelled may still have start/end events without ever running a handler. An observability system that treats the start event as “side-effecting code has begun” will calculate both execution time and the risk window incorrectly.

Execution order and Context order are different

Concurrent Tool Calls have at least three orders:

  • invocation order: when each handler actually starts;
  • completion/event order: which handler finishes first;
  • assistant source order: the order in which the model proposed Tool Calls in its message.

Completion events are useful for displaying real progress. Context writeback needs a stable and predictable correspondence between each Tool Call and its Tool Result. Pi’s parallel path awaits execution concurrently while preserving the association between results and source Tool Calls. The second Tool finishing first must not cause the next model Turn to treat its result as the result of the first Tool.

Pi currently supports global toolExecution: "sequential" | "parallel" and per-tool executionMode. If a batch contains any sequential Tool, the entire batch follows the sequential path. Pi does not have a built-in maxConcurrentTools or semaphore. A concurrency limit, if needed, should be described explicitly as a host or Runtime enhancement rather than a current feature.

Sequential execution still does not guarantee external consistency

Even if one Run invokes two Tools sequentially, another Run or an external user may modify doc-7 at the same time. Runtime scheduling order is not a database transaction.

Shared mutation should use mechanisms appropriate to the resource owner:

  • a resource revision or ETag for optimistic concurrency control;
  • an idempotency key to stop one logical operation from taking effect twice;
  • a transaction for updates that must be atomic within one fact source;
  • query or reconciliation for an external effect with an unknown outcome.

Both updates in the opening example should carry a precondition derived from the same revision. The first update to commit successfully at the resource owner wins. The other is rejected for a revision mismatch instead of overwriting silently. The winner is determined by commit order, not assistant source order. The same rule applies whether the Runtime schedules the calls concurrently or sequentially.

Cancellation has four layers of guarantees

“The Agent has been cancelled” is not one semantic fact:

  1. AbortSignal means a cancellation request has been sent.
  2. Tool promise convergence means invoked handlers have returned or rejected.
  3. Agent settlement means the Loop will not produce more work.
  4. The Harness abort barrier additionally clears queues and waits for idle.

Pi’s low-level Agent.abort() only triggers the signal; its caller must invoke waitForIdle() separately. AgentHarness.abort() triggers the signal, clears queues, and waits for idle. The Loop waits for Tool promises that have already been invoked, but it cannot forcibly terminate a handler that ignores the signal.

A handler that ignores the signal may therefore keep the wait open indefinitely. Cancellation also does not roll back an external effect that already occurred or whose outcome is unknown. That effect must enter query or reconciliation.

The parent must wait for all child work to converge

The point of structured concurrency is not merely to run more work at once. The parent scope still owns the lifecycle of its children. A parent Run may issue cancellation, but it should not report itself settled while a child Tool may still write to an external system.

For the opening example, the complete timeline is:

t1: two start events are announced
t2: validation/preflight completes; both handlers are invoked
t3: tool-b commits successfully and returns
t4: the parent Run sends a cancellation signal
t5: tool-a responds to the signal; its external outcome still needs confirmation
t6: both promises converge; results are written back by source identity
t7: Agent/Harness reaches its respective settlement barrier

This timeline preserves completion order, message order, and external facts without using one cancelled value to overwrite them all.

Back to the problem

When two Tools concurrently update doc-7, answer each of these questions independently:

  • Does a start event represent only an announcement?
  • When did the handler actually start and finish?
  • How does Context preserve the stable Tool Call/Result association?
  • How does the resource owner protect shared state with a revision or transaction?
  • What request did cancellation send, and through which barrier must the parent wait?
  • Who reconciles an unknown external effect?

The Runtime owns scheduling and parent-child convergence. The external system owns consistency of shared mutations. Once these owners are separated, concurrency is no longer one call to Promise.all; it becomes an execution protocol that can be verified.
