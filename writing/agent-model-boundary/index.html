Why Model Fallback Needs Both a Router and an Adapter

Separate model selection from provider protocol shaping so that fallback does not change Tool, message, or streaming-event semantics.

07/24/2026 Views
Agent CoreAgentModelsAdapter

The problem

An Agent uses a model that supports parallel Tool Calls and a particular JSON Schema dialect. The primary model is rate-limited, so the host replaces the model field with a fallback model name and resends the original request unchanged. The fallback returns a response, but turns two parallel Tool proposals into plain text and drops an enum constraint from one argument.

The fallback succeeded at the HTTP layer while changing Agent semantics. Safe fallback cannot be only a model-name substitution.

The Router first decides which models are eligible

Model selection often considers quality, latency, and cost, but it should compare those attributes only within an eligible set. Eligibility depends at least on:

  • support for the Tool or structured-output capabilities required by the current request;
  • context and output limits large enough for the request;
  • data-region, content-policy, and identity boundaries that permit use of the model;
  • streaming, thinking, or multimodal semantics that satisfy the caller’s contract;
  • a current failure class that permits handing incomplete state to another model.

Filtering on these hard constraints before optimizing cost and latency prevents the selection of a model that is inexpensive but cannot express the current contract.

The Router should preserve an explainable decision record:

required: tools + parallel proposals + schema feature X
rejected model-b: schema feature X unsupported
selected model-c: eligible, lower current latency

This does not require one permanent table that captures every model difference. It requires each routing decision to remain traceable to the capability and policy evidence available at the time.

The Adapter owns protocol conversion

After routing, canonical AgentMessages, Tool definitions, and streaming events still have to be converted into the provider protocol. Providers may represent roles, Tool IDs, schemas, usage, reasoning blocks, and chunk shapes differently.

The Adapter’s goal is not to reduce all providers to the smallest common denominator. It should report conversion capability explicitly:

canonical request
  → capability check
  → provider request shaping
  → provider response
  → canonical events/messages

If a required schema keyword cannot be represented, the Adapter should reject the conversion or return an explicit degradation decision instead of silently deleting the keyword. Prompt shaping must not reduce a structured policy boundary to a natural-language reminder.

Pi provides injection boundaries, not a Router

Pi currently exposes two related paths:

  • the low-level Agent/loop receives a selected Model and an injected streamFn;
  • AgentHarness receives a selected Model and a host-supplied Models provider collection.

These boundaries keep Core from hard-coding a provider. They do not mean that packages/agent already implements a model catalog, route eligibility, or fallback policy. The host still owns the Router.

See Pi’s stream-fn.ts and Harness types.ts for the relevant boundaries.

Fallback depends on where the failure occurred

Not every model failure permits a safe switch:

Failure pointIs fallback usually safe?What must be checked
Provider explicitly returns rate limit before any consumable outputRelatively straightforwardCapabilities, policy, Context, Tool schema, and the duplicate-request/billing contract
Connection failure before any consumable outputPossiblyWhether the provider accepted the request, billing behavior, and duplicate risk
Partial text has already streamedUse cautionWhether to discard the partial output and restart
A Tool Call has already been proposed and executedA model switch is insufficientEffect state, Tool Result, and operation identity
External side-effect outcome is unknownOutside the Router’s authorityQuery or reconcile the external fact first

Model fallback can handle only failures inside the model owner’s boundary. After a Tool executes, another model may continue from a confirmed result, but it cannot reset an unknown side effect to “not yet executed.”

Shape the request again after fallback

Return to the opening request. The provider explicitly returned rate limit without producing consumable output. After checking the duplicate-request and billing contract, the host permits a fallback attempt, but it must run the full path again:

  1. The Router checks whether the fallback model supports parallel Tool proposals and the required schema features.
  2. Context is rebudgeted for the fallback model’s window.
  3. The Adapter converts the canonical Tool definitions into the fallback protocol.
  4. Contract tests verify that Tool identity, argument constraints, and event semantics survive conversion.
  5. If the model is incompatible, fallback stops instead of degrading the Tool Call into plain text.

The contract tests do not need to prove that every provider behaves identically. They need to verify the semantic round trip on which this article depends: required constraints remain present, Tool IDs remain correlatable, errors do not masquerade as success, and streaming events reconstruct a consistent canonical result.

Back to the problem

Replacing the model name completes only the step of selecting another target. Safe fallback also requires:

  • a Router that first finds models satisfying capability and policy;
  • an Adapter that reshapes requests and responses for the new provider;
  • a failure class proving that the current state permits a switch;
  • renewed compatibility checks for Tools, Context, and unresolved effects;
  • explicit failure when required semantics cannot be represented, rather than silent degradation.

Pi’s clean model-injection point makes a host-level Router possible, but it does not implement that policy for the host. Separating the injection boundary from routing capability lets fallback preserve the Agent contract instead of merely preserving the success of one API call.
