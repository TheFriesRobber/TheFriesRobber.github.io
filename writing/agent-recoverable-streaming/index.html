Why Real-Time Output Is Not an Execution Record

Separate durable execution events, lossy transport signals, and client cursors so that reconnection does not rewrite execution facts.

07/24/2026 Views
Agent CoreAgentStreamingRecovery

The problem

An Agent has completed a Tool, and the server has emitted tool_execution_end. The client disconnects before receiving the event. After reconnecting, it sees only later tokens, so the interface continues to show the Tool as “running.”

Rerunning the Agent to repair the interface may repeat the side effect. Reconnecting only to SSE or WebSocket cannot recover events lost during the disconnection. A real-time connection can deliver quickly without preserving execution facts.

An in-process event is not a durable event

Pi’s AgentEvent represents model, Tool, and Agent lifecycle signals, and subscribers can be awaited. That supports propagation and convergence inside the current process, but the event does not automatically acquire a stable durable ID, persistent storage, or replay across restarts.

To promise reconnection recovery, the host must separate two layers:

LayerResponsibility
Durable execution eventRecords a confirmed execution fact and supports lookup by ID
Delivery signalNotifies clients quickly through SSE, WebSocket, or another transport; signals may be lost and clients may reconnect

The network connection may disappear while the durable event remains. Conversely, emitting a signal does not prove that the corresponding fact has been committed.

A Cursor lets the client rebuild its view

Each recoverable event needs a stable ID and belongs to an explicit stream or Run:

run_id: run-9
event_id: 1042
type: tool_execution_completed
tool_call_id: call-3
outcome: succeeded

The client stores its last acknowledged cursor. On reconnection, it first requests history after=1041, then subscribes to new events. The UI is a projection of those events and can be rebuilt repeatedly; it is not unrecoverable in-memory state left by one connection.

This does not require every token to enter a permanent log. Tool outcomes, state transitions, user confirmations, and final messages usually have recovery value. Model token deltas are closer to lossy display signals. When text recovery is required, save the completed message or segmented checkpoints rather than treating every token as a business fact.

Catch-up and subscription have a race too

A common incorrect flow is:

  1. Query history after the cursor.
  2. Receive the history response.
  3. Establish the live subscription.

An event can occur between steps 1 and 3. A safe implementation needs an explicit boundary, such as establishing a buffered subscription before catching up and deduplicating by event ID, or having the server provide an atomic “subscribe from cursor” operation.

Whichever implementation is used, it must allow at-least-once delivery and apply projection updates idempotently by event ID. Trying to make the connection layer guarantee “never duplicate and never lose” usually overstates the transport contract.

A slow consumer must not hold execution facts open

If a live subscriber can block the execution path indefinitely, a slow browser can delay Tool settlement. If the path never waits, memory may grow without bound.

A safer boundary is:

  • committing a durable event does not depend on any individual client being online;
  • delivery uses a bounded buffer;
  • exceeding the limit disconnects the client or degrades token signals;
  • after reconnecting, the client catches up on critical events from the durable cursor;
  • cancellation enters the Runtime through an independent control protocol and does not depend on closing the socket.

Pi’s current settlement semantics for awaited subscribers can serve as an in-process coordination mechanism, but they must not be generalized into cross-process durability. See the current event types in types.ts.

Back to the problem

After the client misses tool_execution_end, it should neither rerun the Agent nor expect a new connection to recover a signal that already vanished in transit. The correct path is:

  1. Tool completion first becomes a durable execution event with a stable ID.
  2. SSE or WebSocket carries only a notification that may be lost.
  3. The client queries missing events from its cursor.
  4. The projection rebuilds idempotently by event ID.
  5. Token deltas may degrade; confirmed execution outcomes must not disappear.

Real-time output answers, “How can the client see this quickly now?” An execution record answers, “How can the system still prove this later?” Reconnection becomes safe only when those two problems are separated.
