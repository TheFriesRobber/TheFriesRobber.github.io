Agent Observability 2: Correlate Logs, Metrics, and Traces with Logical IDs and Taxonomy

A Tool retry separates business identity, physical Attempts, and trace context while establishing error semantics shared across signals.

07/15/2026 Views
AgentObservabilityTracing

The problem

An Agent Run calls read_file. The first request times out, and a Queue retry succeeds on another worker. All three observability systems receive data:

Log
  run_id=run_12 tool=read_file message="request timeout"

Trace
  trace_id=4bf9... span_id=00f0... status=ERROR
  the retry worker creates another trace_id=91aa...

Metric
  agent_tool_requests_total{tool="read_file", status="error"} += 1
  agent_tool_requests_total{tool="read_file", status="ok"} += 1

To answer “why was this user task slow even though it eventually succeeded?”, an engineer must guess whether the two metric points belong to one Run, whether the second trace is a retry of the first timeout, and which span corresponds to run_12 in the log.

The problem is not a lack of traces. Logs, Metrics, and Traces share only a technical component name, not the logical identity, Attempt boundary, and failure taxonomy of the Agent execution.

A Trace ID describes a propagation path, not business identity

W3C Trace Context defines trace context propagation across processes. OpenTelemetry uses TraceId and SpanId to correlate spans along a distributed request path. This is useful for asking which services a request traversed.

Agent execution also contains longer-lived objects. A Task can span Runs. A Run can wait on a Queue. One Tool Execution can contain several Attempts. An Artifact may finish after the originating Run ends. Their lifecycles do not necessarily match one trace.

If the retry worker does not continue the original trace context, the second Attempt starts another trace. Even when propagation is correct, trace-backend retention, sampling, and span structure should not determine business-object identity.

Two kinds of relationships therefore need to remain explicit:

business relationships
task_7 → run_12 → tool_execution_42 → attempt_1 / attempt_2

observability relationships
attempt_1 → trace_4bf9 / span_00f0
attempt_2 → trace_91aa / span_18c2

The Trace ID may change while tool_execution_42 continues to identify one authorized logical action. Conversely, one trace may contain several Tool Executions, so the Trace ID cannot serve as Tool identity.

Preserve both Logical ID and Attempt ID

The opening retry needs at least these fields:

FieldGrainPurpose
task_idUser goalConnect the final result across Runs
run_idOne Agent LoopConnect the current input to a terminal Run
tool_execution_idOne authorized logical actionRemain stable across retries
attempt_idOne physical tryRecord timeout, latency, and provider response
trace_id / span_idObservability propagation pathLocate the request in the tracing backend

This extends Agent Observability 1: Define the Grain before Modeling: Tool Execution success rate and Attempt success rate can differ. O2 requires those grains to keep the same meaning and field names across signals.

Stable does not mean every field must be client-generated. The real owner should allocate identity when the object is first submitted and propagate it through Queue messages, retry requests, and callbacks. When a consumer receives a duplicate message, it reuses the original tool_execution_id but creates a new attempt_id for the new physical call.

Logs and Spans can carry high-cardinality correlation fields

The OpenTelemetry Log Data Model defines optional TraceId and SpanId on a LogRecord, allowing a log to link directly to its span. An Agent system should also record logical identity as structured fields rather than concatenate it into the message:

{
  "event": "tool.attempt.finished",
  "task_id": "task_7",
  "run_id": "run_12",
  "tool_execution_id": "tool_execution_42",
  "attempt_id": "attempt_1",
  "trace_id": "4bf9...",
  "span_id": "00f0...",
  "outcome": "unknown",
  "error.type": "deadline_exceeded"
}

The corresponding span can carry the same attributes. A trace can then find other Attempts of the same Tool Execution, and a business log can return to the actual network path.

These IDs have high cardinality, but Logs and Traces already store individual events or spans. They still need access controls and retention policy. Correlation is not a reason to copy user input, credentials, or sensitive resource names into every signal.

Metrics share Taxonomy, not every high-cardinality ID

“Shared correlation semantics across three signals” does not mean using run_id, task_id, or tool_execution_id as ordinary metric labels.

Metrics create time series from attribute combinations. The OpenTelemetry Metrics SDK has explicit cardinality limits. If every Run creates a new series, cost and memory increase with traffic and may eventually trigger overflow aggregation, destroying the observability the labels were meant to provide.

Metrics should share field semantics and low-cardinality taxonomy:

agent_tool_attempts_total{
  tool="read_file",
  outcome="unknown",
  error.type="deadline_exceeded"
}

If the backend supports exemplars, a small number of metric data points can refer to representative trace context. An alert can also query Logs and Traces by the same time window, Tool, and error type. The important contract is that all three signals agree on outcome and error.type, not that every metric carries every business ID.

A practical boundary is:

  • Logs and Traces retain high-cardinality identity for locating one execution.
  • Metrics use bounded dimensions for trends and alerts.
  • Exemplars or query links connect an aggregate to individual samples.

Recovery also needs a Failure Owner in the taxonomy

If the Log records timeout, the Trace records DEADLINE_EXCEEDED, and the Metric records only error=true, correlation still cannot say whether the model, Tool, Runtime, or provider owns the repair.

OpenTelemetry Semantic Conventions define error.type and say that corresponding Spans and Metrics should use the same value for a failure. A successful operation should not carry that attribute. An Agent Runtime may maintain an internal canonical error class, but it should map that class to error.type when exporting OpenTelemetry data. outcome, failure_owner, and retry_disposition are the application-level fields proposed here:

{
  "outcome": "unknown",
  "error.type": "deadline_exceeded",
  "failure_owner": "tool_provider",
  "retry_disposition": "query_before_retry"
}
  • outcome says what the system can currently confirm, such as succeeded, failed, cancelled, or unknown.
  • error.type is the stable, low-cardinality failure type aligned across Span, Metric, and Log.
  • failure_owner identifies the first boundary that owns a repair action, not merely the service that threw an exception.
  • retry_disposition says what the Runtime may do next.

The same HTTP 504 may represent a provider deadline or a local gateway timeout. The boundary closest to the fact should normalize the taxonomy while preserving raw status as diagnostic evidence. Consistency must not erase source evidence, and a successful signal must not retain a previous failure’s error.type.

How one Retry appears in all three Signals

Record the two Attempts from the opening example again:

tool_execution_42
  attempt_1
    log:   outcome=unknown error.type=deadline_exceeded
    span:  trace_4bf9 span_00f0 status=ERROR
    metric: tool_attempts{tool=read_file,outcome=unknown,error.type=deadline_exceeded} +1

  attempt_2
    log:   outcome=succeeded
    span:  trace_91aa span_18c2 status=OK
    metric: tool_attempts{tool=read_file,outcome=succeeded,...} +1

terminal logical result
  log/event: tool_execution_42 outcome=succeeded attempts=2
  metric: tool_executions{tool=read_file,outcome=succeeded} +1

The data can now answer three questions:

  • Of two provider Attempts, one is confirmed successful and one has an unknown result. It can be reported as 1/2 only when the metric explicitly uses “confirmed success / all terminal Attempts” as its denominator.
  • Did the logical Tool action complete? At the logical grain, the single Tool Execution eventually succeeded.
  • Why did the user experience delay? Attempt 1 consumed its deadline before Attempt 2 confirmed the result.

Even if the Attempts belong to different traces, tool_execution_id connects them. Even though Metrics do not retain that ID, the shared Tool, outcome, and error.type taxonomy still align the aggregate with detailed signals.

Queue and SubAgent boundaries require explicit propagation

Across a Queue, the producer should put business identity and trace context in separate fields of the message envelope:

{
  "task_id": "task_7",
  "run_id": "run_12",
  "tool_execution_id": "tool_execution_42",
  "attempt_no": 2,
  "trace_context": {
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
    "tracestate": "vendor=value"
  }
}

Receive spans and batch Process spans use a Span Link to the message-creation context by default. Only a Process span handling one message may instead use that context as the parent under the tracing policy. If a security boundary or sampling policy starts a new trace, the Span Link should still be preserved. traceparent and tracestate, when present, form the propagated context. Regardless of trace topology, logical identity must remain intact. The same rule applies to SubAgents, callbacks, and background Jobs: Span parent and link relationships serve observability, while business parent-child relationships serve execution semantics.

If a legacy system already produced several incompatible ID schemes, permanent joins should not depend on timestamp proximity. A trusted entry point can build correlation mappings while new events gradually carry canonical identity. Historical records whose relationships cannot be proved should remain unresolved; they should not be force-linked to improve a completeness metric.

Back to the problem

The opening Logs, Metrics, and Traces all contain data but cannot explain one retry because each records only the technical identifiers convenient for its own backend.

Preserve the business relationship task_id → run_id → tool_execution_id → attempt_id, then associate every Attempt with its trace and span. The requests on two workers remain one logical action. Logs and Traces keep high-cardinality identity. Metrics use the same outcome and error taxonomy with bounded dimensions, optionally linking back through exemplars or queries.

Shared semantics does not copy every field into every signal. It makes all three systems agree on which grain they record, what the outcome means, and who owns the failure response.
