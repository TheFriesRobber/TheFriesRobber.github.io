Agent 42: Requirements Research Must Reconstruct Real Work, Not Repeat the SOP

Use shadowing, artifact review, logs, and critical-incident reconstruction to find waiting, compensating actions, and implicit decision evidence outside the SOP.

07/29/2026 Views
Agent DiscoveryAgentProduct Discovery

The problem

The refund team provides a four-step SOP:

receive request
→ query order
→ evaluate refund eligibility
→ reply to customer

The team designs the Agent from it: read the ticket, call the order-query Tool, give the order and refund policy to the model, and generate a disposition.

The first walkthrough with a real case tells a different story. After querying the order, the support agent opens the payment system because order status may synchronize late. They then check whether logistics has collected the shipment. When two states conflict, they message finance, record the result in a personal spreadsheet, and wait for supervisor confirmation before continuing.

The SOP is not wrong. It simply omits the waits, compensating actions, and experiential judgments that make the work complete. The Agent will face this omitted reality, not the process document.

The SOP describes responsibility; real work exposes dependencies

An SOP usually supports training, responsibility assignment, and compliance, so it preserves the stable path. It does not record every system delay or informal communication channel, and it rarely explains why an experienced operator pauses at a particular step.

Agent requirements depend on those details. The Agent needs to know:

  • when the order system is insufficient as the only evidence;
  • why the user queries another system;
  • which conflicts permit continuation and which require a stop;
  • who supplies missing information;
  • where task state lives while the user waits;
  • which evidence eventually confirms completion.

“How do you usually do this?” is therefore an entry point, not an Agent Task.

The research must distinguish:

normative material: how work is supposed to happen
descriptive evidence: how work actually happens

Both matter. Normative material supplies the policy boundary, while descriptive evidence reveals execution conditions. Looking only at the first misses exceptions. Looking only at the second can mistake a personal workaround for a process the organization wants to preserve.

Shadowing should record decisions, not only clicks

One way to reconstruct real work is shadowing: observe a user handling a real task and record actions, evidence, and decisions.

If the notes stop at screen operations, the result is only a more detailed flowchart:

open order system
→ copy order ID
→ open payment system
→ paste order ID

That may support UI automation, but it does not support Agent decisions. A more useful observation looks like:

action: query payment system
reason: order status may be delayed
required evidence: payment record, amount, order ID
decision: continue only when payment and order state agree
exception: send state conflicts to finance

Whenever the user changes systems, pauses, reviews history, or asks a colleague, ask:

  1. What are you trying to establish now?
  2. Which result would change the next step?
  3. What would you do if this information were unavailable?

These questions convert an operation sequence into decision evidence and begin to reveal the data and escalation conditions the Agent needs.

Do not ask users to demonstrate only the standard case. A recent ordinary case can establish the main path; a difficult or failed case is more likely to expose the real boundary.

Artifacts expose task state outside the official system

Critical task state often lives outside the official business system in user-maintained Artifacts:

  • a spreadsheet that tracks who is expected to respond and when to follow up;
  • private notes containing common decision evidence;
  • copied chat threads showing how similar cases were handled;
  • reply templates for different exceptions;
  • ticket labels meaning “system says complete, but verify again.”

These Artifacts should not automatically become long-lived product features, but they are valuable requirements evidence.

A support agent may keep a personal spreadsheet for three different reasons:

  1. the official system lacks a waiting state;
  2. it has the state but cannot filter by responsible person;
  3. the process requires tracking, but the user does not know the existing feature.

The three causes require different responses. The first may need a new task state. The second may be a product-query limitation. The third is not an Agent problem.

Artifact review should not copy the spreadsheet. It should identify which missing capability it compensates for, which state it stores, and who depends on that state to continue work.

Logs calibrate “often” and “rarely”

Interviews reveal mechanisms but estimate distributions poorly. Users remember recent, difficult, or emotionally salient cases.

When available, tickets, operation logs, and historical records can establish:

  • how often each task type occurs;
  • which steps contain the longest waits;
  • where state conflicts appear;
  • under which conditions humans take over;
  • which step rework returns to;
  • which cases never complete.

Logs do not explain cause automatically. Opening two systems in sequence may be cross-checking or simply habit. A long pause may be approval wait or the user stepping away. Logs must be interpreted together with observation and interviews.

Reliable requirements evidence usually comes from triangulation:

the user explains why
+ observation shows how
+ historical records show how often

Agreement across the three supports a stronger conclusion. Disagreement is itself a research question.

Critical cases reveal boundaries better than abstract preferences

“How should an Agent help?” tends to produce a feature wish list. “Walk through the last case that did not follow the SOP” produces execution facts.

A critical-incident review can follow the timeline:

  • What was the initial request?
  • Which information was visible then?
  • Where did progress first stop?
  • Which compensating action did the user take?
  • Which role made the key decision?
  • Which evidence became available only afterward?
  • How was the result confirmed?
  • If an Agent had participated, where should it have stopped?

Evidence available during execution must remain distinct from hindsight. Knowing during review that the refund eventually failed does not mean the Agent could observe that fact at execution time.

This distinction feeds directly into Eval. A historical case is valid only if it preserves the state visible at the time. Leaking the later outcome to the Agent manufactures a false success rate.

A real-work record must preserve evidence provenance

The output should not be only a larger flowchart. Each important step should record:

FieldQuestion
TriggerWhat event starts the task?
ActorWho is advancing it?
ActionWhat do they actually do?
EvidenceWhich information supports the action?
DecisionWhich judgment changes the next step?
ArtifactWhere is task state stored?
HandoffWho receives it, and what is awaited?
ExceptionWhat departs from the main path?
CompletionWho confirms completion, using which evidence?

Filling this record with the opening case produces a minimal example:

FieldObservation from the opening case
TriggerA customer submits a refund request
ActorA frontline support agent advances the ticket
ActionQuery order state, then payment and logistics state
EvidenceOrder record, payment record, logistics state, and their respective sources
DecisionContinue only when states agree; pause refund evaluation on conflict
ArtifactThe support agent temporarily records the waiting owner and follow-up time in a personal spreadsheet
HandoffContact finance on payment conflict; wait for a supervisor on an exception decision
ExceptionOrder, payment, or logistics systems return conflicting states
CompletionThe opening material does not record the final outcome; the completion owner and evidence still require confirmation

This table describes the observed current state. It does not say that the future system should preserve the personal spreadsheet or the same informal communication. Open design questions remain: which official system should own the waiting state, how finance confirmation should enter an auditable handoff, and which system owns the final refund fact and completion evidence.

This record is still not the final Task Contract. It describes the present, not every behavior the future system should preserve.

The next step classifies the compensating actions: which should be eliminated by product design, which should become Tools, which represent human decisions, and which are historical process residue. Reconstruct first and design second, or the Agent will permanently encode the inefficiency of the current process.

Back to the problem

The refund SOP contained only query, evaluate, and reply. Real work also contained cross-system verification, state conflicts, informal communication, a personal spreadsheet, and later rechecking.

An Agent that implements only the SOP may work on clean cases but will lose its next step at the first payment-state conflict and cannot explain why it should stop.

Shadowing exposes the decisions behind actions, Artifact review finds task state outside the system, logs calibrate exception distributions, and critical-case reconstruction exposes the failure boundary. Together, they describe the work the Agent will actually face.

Requirements research is not a cleaner transcription of what users say. It identifies the evidence, decisions, and handoffs on which the task truly depends.
