Capability Integration 1: How Tools, Skills, Connectors, and MCP Divide Responsibilities

A failed external-capability upgrade separates Tools, Skills, Connectors, and MCP by model visibility, versioning, credentials, and execution ownership.

07/17/2026 Views
AgentToolsSkillsConnectorsMCP

The problem

Suppose an Agent needs the ability to send a weekly report by email. Four descriptions quickly appear in the system:

  • Register a send_email Tool for the model.
  • Install a “send weekly report” Skill.
  • Connect an email Connector.
  • Configure an MCP server that provides email capabilities.

The first version works. Later, the email service requires a new workspace_id. Only some Runtimes have the new Tool Schema. The Skill still generates arguments using the old procedure. The Connector holds the user’s OAuth credential. The MCP server already exposes the new Tool version. When calls begin to fail, the team cannot answer which layer should be upgraded, who owns compatibility, or who may use the credential.

The problem is not that there are too many names. It is that all four names have been treated as the same kind of “model capability.” They may appear in one call chain, but they answer different questions.

Start by separating responsibility questions

To classify an object, do not begin with the product label. Ask four questions:

  1. Which concrete actions may the model propose?
  2. Which reusable instructions, scripts, and dependencies must be loaded together?
  3. Who holds user authorization and accesses the external system?
  4. Which protocol lets a Client and Server discover and invoke the capability?

These questions roughly correspond to Tool, Skill, Connector, and MCP. They are not a fixed hierarchy. A Skill may coordinate only local file operations without a Connector. A Connector may expose a Tool through a private application API without using MCP. An MCP server may provide a read-only resource that needs no user credential.

The definitions below are therefore an engineering responsibility map, not a requirement that every framework adopt the same type system.

A Tool defines the action the model may propose

A Tool is a model-facing action contract. Its name, description, input Schema, and result semantics tell the model which action it can select in the current Model Turn and how to generate the arguments.

For the email example, the Tool could be:

{
  "name": "send_email",
  "description": "Send a prepared report to approved recipients.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "recipient": {"type": "string"},
      "subject": {"type": "string"},
      "body": {"type": "string"}
    },
    "required": ["recipient", "subject", "body"]
  }
}

The model should not fill in an OAuth token, tenant identity, or granted scope. Those are trusted execution context, not task arguments.

The Tool owner is responsible for whether the model can distinguish the action, how the Schema evolves, how errors enter the next turn, and whether the Tool should appear in the current surface. The Tool does not need to own an external credential or decide how an entire capability package is installed.

A Skill packages a reusable way of working

For Skills that need discovery, loading, upgrade, and rollback, this article treats a Skill as a versioned package of instructions, references, scripts, assets, and dependency declarations. It answers “how should the Agent complete this class of work?” rather than only “which function should it call?”

A weekly-report Skill might instruct the model to read this week’s Artifact and produce a template-based summary, run a deterministic validation script to check recipient scope, and finally have the model propose a send_email Tool Call for the Runtime to validate and execute. The Skill packages these steps and dependencies; it does not itself generate the summary, perform validation, or send the email. Only the last step is a Tool action, while the instructions, template, and script belong to the loadable method.

The public SKILL.md format is one example of this design. A Skill directory contains at least a SKILL.md with metadata and may also include scripts/, references/, and assets/. The exact format is not the conclusion here. The more important contract is:

  • The Skill has a stable identity and a version that can be pinned.
  • Its dependencies and Runtime compatibility can be checked before loading.
  • It declares required Tools or Connectors without expanding authority by declaration.
  • Execution still inherits the current Run’s identity, budget, observability, and sandbox policy.

A Skill can teach the Agent how to use a capability. Text saying “sending is allowed” cannot replace backend authorization.

A Connector is the trusted boundary for credentials and external systems

A Connector represents a user or tenant when accessing an external system. It commonly manages OAuth authorization, token storage and refresh, scope, provider-account mapping, and API normalization.

RFC 6749 defines an access token as a credential used to access protected resources and requires it to remain confidential in transit and storage. For an Agent system, the direct consequence is that the model, ordinary Skill text, and an untrusted Sandbox should not see the raw token.

An email Connector can expose a trusted execution interface:

send_email(args, trusted_context)
  → locate the authorization record from trusted_context
  → obtain or refresh a short-lived credential for the provider
  → check scope, recipient policy, and account binding
  → call the external email API
  → return a normalized result

The Connector owner manages the credential lifecycle and provider-specific failures. Renaming a Tool Schema should not force a Skill to store a token. Changing the MCP transport should not change who owns the OAuth credential.

MCP defines discovery and invocation, not all governance

Model Context Protocol uses a client-host-server architecture and JSON-RPC, initialization, and capability negotiation to expose Tools, Resources, and Prompts. It answers how a Host and Server establish a connection, declare supported protocol capabilities, discover primitives, and issue calls.

MCP can therefore carry discovery and invocation of the email Tool. “Using MCP,” however, does not automatically decide:

  • Which tenant may see the server.
  • Whether the Runtime should route to v1 or v2.
  • Where the OAuth credential is stored.
  • How a Tool Schema change is rolled out and rolled back.
  • Whether routing should continue when the server is healthy but a business dependency is unavailable.

Those decisions belong to the application’s or MCP Hub’s control plane. The protocol supplies negotiation facts; the Hub forms a route decision from version, health, authorization, and rollout policy. Calling a static server-endpoint list a governance layer confuses protocol connectivity with operational safety.

One call chain can contain all four abstractions

Return to the weekly-report example. A complete path could be:

Skill: weekly-report@3
  the model reads the Artifact and produces the summary; a validation script checks the send procedure
          ↓ requires
Tool: send_email schema v2
  the model generates only recipient, subject, and body
          ↓ discovered and called through
MCP connection: mail-server route v2
  negotiate protocol capabilities and transport Tool Call and Result
          ↓ invokes trusted integration
Connector: mail-account-7
  hold the OAuth grant and inject workspace and provider account
          ↓ calls
Mail provider API

When the external API adds workspace_id, first decide what kind of fact it is:

  • If the model must choose a workspace from the task, it may belong in the Tool Schema.
  • If the workspace comes from the authenticated tenant, the Connector or Runtime context should inject it; the model must not provide it.
  • The Skill needs an upgrade only if the work procedure or dependencies change.
  • The MCP server may publish a new implementation, but the control plane decides whether routing switches to it.

The upgrade is no longer “upgrade every capability layer together.” It follows ownership to the contract that actually changed.

The table does not require each component to be deployed independently. Its purpose is to prevent one object from acquiring conflicting responsibilities, such as Skill text holding credentials or an MCP endpoint configuration silently deciding tenant authorization.

Back to the problem

Sending a weekly report can use a Tool, Skill, Connector, and MCP at the same time because they describe different dimensions of one capability.

The Tool lets the model propose a concrete action. The Skill packages a versioned way of working. The Connector manages user authorization and the external API inside a trusted boundary. MCP specifies how the Host and Server discover and invoke primitives. When a version, credential, or call fails, locating the owner through these four responsibilities reveals which contract must change.

Calling all of them “model capabilities” is not wrong. The mistake is assuming that they therefore share one version, permission boundary, and failure boundary.
