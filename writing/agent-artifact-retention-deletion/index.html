Agent 23: Artifact References, Retention, and Deletion Must Be Separate Layers

Separate Message references, existing download capabilities, logical Artifact deletion, lineage retention, and provider deletion of a scoped object-version target set.

07/27/2026 Updated 07/27/2026 Views
Agent ProductionAgentArtifactsData Governance

The problem

A user uploads a contract to an Agent, which produces a summary and a final report. A week later, the user deletes the original upload message and asks to delete the source file.

The Conversation service removes the attachment reference from the Message, and the Artifact service marks the source file as deleted. Yet a previously issued download URL still works. Object versioning is enabled, so deleting the current key only inserts a delete marker. The final report must also remain because it has already been delivered.

If the system calls every one of these operations “file deletion,” it cannot answer the question that matters most to the user: is the file merely absent from the conversation, are new and previously issued access capabilities both unusable, or have the targeted object versions been permanently deleted under the provider contract?

Deletion must converge through states owned by different boundaries: remove references and block new access first, converge previously issued capabilities separately, let the Artifact owner use lineage and retention to define the deletion target set, and then let the Blob owner record the provider deletion outcome for each targeted object version and governed copy.

Deleting a reference changes only who still refers to the Artifact

Several objects may refer to the same Artifact revision:

Message message_8 ───────┐
Task task_12 ────────────┼─> artifact_source_17@1
Workspace ws_9 ──────────┘

When message_8 is deleted, the Conversation owner can authoritatively remove only that reference. It cannot infer that the Task has ended, that the Workspace no longer uses the input, or that the Artifact has satisfied its retention period.

A reference therefore needs its own identity and state:

reference_id: msgref_31
owner: message_8
artifact: artifact_source_17@1
state: detached
detached_at: ...

The Artifact service can then recompute valid references and policy. A caller must not bypass that decision using a filename, an old path, or a Blob hash. Identical bytes may belong to different tenants or business Artifacts; content identity is not business ownership.

Revoking access and reclaiming bytes are different commit boundaries

When an Artifact enters deletion, the first requirement is to block new normal reads. A conceptual state machine is:

active
  → delete_requested
  → new_access_blocked
  → existing_capabilities_revoked | pending_expiry | unknown
  → retention_blocked | erase_eligible
  → erasing
  → provider_deleted | deletion_failed

new_access_blocked is the first business-visible boundary. New resolve, download, and materialize requests are denied, and capability surfaces no longer expose the Artifact. It does not prove that an already issued bearer capability is unusable or that the provider has deleted object versions.

A download URL is also an access capability, not Artifact identity. A more revocable design gives the client a short-lived capability bound to a subject, Artifact revision, and audience, then rechecks Artifact state at redemption or download time. With a direct object-store presigned URL, immediate revocation depends on the signing credential, bucket policy, object state, and cache path. Updating a database row to deleted does not by itself prove that every existing URL has stopped working.

The Artifact owner therefore tracks the maximum lifetime of issued capabilities, credential or policy revocation results, and exposure windows it cannot enumerate. State becomes existing_capabilities_revoked only after old capabilities are forcibly revoked or have all passed a provable expiry. Otherwise it remains pending_expiry or unknown, with the latest expiry or uncertainty returned to the caller.

The deletion API should therefore distinguish:

{
  "artifact": "artifact_source_17@1",
  "logical_state": "new_access_blocked",
  "existing_capabilities": "pending_expiry",
  "provider_deletion": "pending"
}

The user can immediately receive the accurate result that no new access will be issued while still seeing the remaining exposure window for old URLs and pending provider deletion. The system reports fully revoked access only after existing_capabilities_revoked holds.

Lineage and retention determine the erasure set

The source contract may already have produced two derived Artifacts:

artifact_source_17@1
  ├─ extracted_text_18@1
  └─ final_report_25@3

Lineage proves derivation; it does not automatically define cascading deletion. The final report may have been delivered and be subject to an independent retention policy. Extracted text may be a reversible intermediate that must be deleted with the source. An audit record may retain only a tombstone without the original content.

The Artifact owner should compile the request into a deletion plan with explicit reasons:

ObjectDecisionReason
artifact_source_17@1revoke + erase when eligibleuser requested deletion of the source
extracted_text_18@1revoke + erasepolicy classifies it as a reversible derivative
final_report_25@3retaindelivered with an independent business owner
lineage edgeretain as tombstoneproves report provenance without retaining source bytes

If a legal hold, minimum retention period, active Workspace reference, or another lawful owner remains, the Artifact enters retention_blocked. The blocking reason, policy revision, and reevaluation time must be durable. They cannot exist only in the log of one failed deletion Job.

Blob deletion needs evidence for every version and governed copy

Only after deletion is allowed does the Blob owner reclaim immutable content. It first confirms that no other lawful Artifact reference points to the same Blob. Content deduplication must not let one tenant’s request remove an object another tenant still uses.

The deletion plan also fixes a target set: which primary-object versions, system-managed replicas, backups, and exported copies are included, plus the owner and retention policy of each. A backup outside that set cannot be hidden behind “the Blob was deleted.” Copies the current system cannot control remain explicit limitations.

A versioned object store also requires handling each physical version. In Amazon S3, for example, a simple delete without a version ID on a versioning-enabled object normally inserts a delete marker instead of permanently removing existing versions. The business layer therefore records them separately:

blob_ref: sha256:ab12...
target_versions:
  - version_id: v7
    outcome: provider_deleted
  - version_id: v5
    outcome: retention_blocked
delete_marker:
  observed: true
provider_deletion_state: partial

Even not found is only an observation at a particular query boundary. The system combines an explicit version ID, the provider’s permanent-deletion response, and a subsequent unaddressability check before promoting it to provider_deleted evidence under that provider contract. A deletion timeout remains unknown or erasing; the same deletion operation identity continues querying instead of hiding uncertainty behind a new Artifact identity.

provider_deleted means only that object versions in the target set were permanently removed under provider service semantics and can no longer be recovered or addressed through those object identities. It does not prove byte-by-byte overwriting of storage media. The product may use the stronger claim “physical erasure complete” only when provider contracts, independent audit, or applicable compliance evidence covers the media and every governed copy.

After provider deletion, the system may retain a minimal tombstone containing the Artifact identity, deletion-request actor, target set, policy revision, completion time, and deletion evidence without sensitive content. It proves which governance action occurred without preserving a route to the content.

One deletion plan commits layer by layer under different owners

The opening request advances by owner:

  1. The Conversation owner removes message_8 → artifact_source_17@1 without claiming that the Artifact is deleted.
  2. The Artifact owner accepts the user request and moves the source and reversible extraction to new_access_blocked; new resolves and downloads fail. The old URL remains pending_expiry until credential or policy revocation, or expiry evidence, is established.
  3. The delivered report remains under its independent retention policy, while its lineage becomes a tombstone.
  4. The plan includes primary-object versions and system-managed replicas in its target set and records backups outside current control as limitations.
  5. The Blob owner deletes and verifies versions individually and keeps aggregate state partial while any version remains retention-blocked. Only after the whole target set has evidence does the Artifact report provider_deletion=complete.

These states may differ temporarily, but every gap has an owner, a reason, and a next reconciliation action. The protocol also prevents a fast “deletion succeeded” response from confusing logical invisibility with physical erasure.

Back to the problem

When the user deletes the upload message, the system first loses a Message reference. The source-deletion request then blocks new access and separately tracks whether old URLs have been revoked or expired. It computes a target set from lineage, valid references, and retention. The final report can remain under its own owner, while the Blob owner removes the source and reversible derivatives version by version.

If the object store has inserted only a delete marker, an old capability remains valid, or a version is retention-blocked, the system reports new_access_blocked, pending_expiry, and provider deletion pending or partial separately. It reports scoped provider deletion complete only when every object version and governed copy in the target set has a verifiable permanent-deletion result. That is still not proof of media overwriting.

Artifact deletion is therefore not one DELETE call. It is a recoverable convergence protocol from references and capabilities through business identity to scoped provider deletion evidence.
