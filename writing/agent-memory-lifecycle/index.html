Agent 17: Memory Writes, Versions, and the Current View

Connect write gates, Writer trust domains, version chains, and the current view into a complete lifecycle for long-term Memory.

07/24/2026 Updated 07/27/2026 Views
Agent StateAgentMemoryData Modeling

The problem

A user first tells an Agent, “When possible, contact me in the morning from now on.” The system saves this as a long-term preference. A few weeks later, the user explicitly corrects it: “Use the afternoon from now on.” A background consolidation job nevertheless regenerates “morning” from the old record, and the next Session still contacts the user at the wrong time.

No historical message was lost, and retrieval did find relevant content. The problem occurred earlier: the system treated every extraction result as a new long-term fact without defining who may write, which version is current, or what correction, revocation, and deletion each mean.

Long-term Memory needs a complete lifecycle: candidate information first passes through a write gate; a constrained Writer commits a sourced version; readers consume the current view by default; and correction, revocation, deletion, and undo change future visibility according to distinct semantics.

Extraction does not make something worth preserving

Content extracted from a conversation by a model or rule can only become a memory_candidate. A trusted Runtime adds the subject, source reference, and actor; the model cannot declare those identities itself:

candidate:
  claim: preferred_contact_time = morning
  observed_scope: future
trusted_envelope:
  subject: user_42
  source_ref: message_61
  actor: in_loop_agent

The write gate then asks:

GateQuestion
DurableCould this still hold after the current Task ends?
User-specificDoes it describe the current subject rather than a third party?
Future-usefulIs there a clear future use for it?
Source-groundedDoes the source support both the claim and its scope?
Permission-safeMay the current actor retain this kind of data?

These are not weighted scores. Usefulness cannot compensate for weak sourcing or missing permission to retain the data. A temporary location, a one-time formatting request, or fast-changing external state should usually remain in the current Task—or carry an explicit expiry—instead of being promoted to a permanent user attribute.

Writer authority must apply to every mutation

An in-conversation Agent, a background consolidation job, a bulk import, and a user edit have different evidence and authority:

WriterReasonable actionsAuthority it should not have
In-loop AgentSubmit a candidate supported by the currently authorized ContextModify another subject
Background consolidationAppend an observation or propose a changeOverride an explicit user statement
Import jobWrite into a mapped namespaceCross that mapping into another namespace
User editCorrect, revoke, or delete manageable recordsBypass retention and third-party data rules

The Memory service should obtain the actor from the trusted execution environment instead of accepting writer: user in Tool arguments. Every mutation should validate at least the subject, namespace, action, evidence class, source references, and expected revision.

A background job may therefore record that “the last three contacts happened in the morning,” but it cannot use that observation to override the user’s explicit afternoon preference. An observed event and a user’s intent can both be true; they should not be flattened into one string and compared by similarity.

A version chain lets a correction change the current view

The first write creates version 1:

memory_id: contact_time
version: 1
value: morning
status: current
source_ref: message_61

When the user corrects it, an authorized Writer submits version 2 with expected_current_version: 1:

memory_id: contact_time
version: 2
value: afternoon
status: current
source_ref: message_82
supersedes: 1

The same commit boundary marks v1 as superseded and advances the current pointer. If another Writer concurrently submits a change still based on v1, the expected revision no longer matches. The service should return a conflict so that the caller can reread and decide again, rather than apply last-write-wins.

Repeated delivery of the same logical mutation should reuse a stable operation ID and return the version already created. Different intents must not share an idempotency key merely because their content is similar.

Supersede, revoke, delete, and undo are not synonyms

OperationFuture readsHistorical content
SupersedeUse the new versionRetain the old version according to retention policy
RevokeStop applying the current valueMay retain the revocation fact and authorized history
Delete/erasureRemove the content from ordinary reads and derived pathsWhen retention is not mandatory, retain only a tombstone that excludes the original value
UndoCreate a new version that restores an earlier business valueKeep moving the version chain forward

Undo must not silently move the current pointer back to v1. That would hide the fact that the value changed to afternoon and was later restored to morning. It should create v3 and point the restoration reason to v1.

Deletion also cannot mean setting hidden=true while leaving the original text in an index, cache, summary, and ordinary backup read path. The original content should leave business reads and derived paths. If an applicable policy mandates legal or security retention, any retained copy must be isolated, restricted in purpose and access, and accompanied by a record of the deletion’s coverage, exception period, and final purge time. If policy forbids retaining history, superseded values must also be erased, leaving only content-free version metadata.

The current view is a read contract

The current view is not another independent fact. It is the canonical projection produced by the Memory service from versions, expiry, and revoke/delete state. Ordinary retrieval starts from this view and then applies a separate authorization filter for the current subject or actor; it must not search all history and ask similarity to decide which version is effective.

Audit or repair actors may read history only when retention and authorization permit it. Their access to history does not mean that history may reenter a new Model Turn. Indexes, caches, and summaries should carry the Memory revision so that advancing the current view invalidates stale derived results.

Walk the opening preference through the lifecycle

The opening lifecycle can be represented as:

message_61 “morning” → write gate pass → v1 current
message_82 “afternoon” → authorized supersede(v1) → v2 current
background observation “recent contacts were in the morning” → append observation
                                                         → cannot supersede v2

If the user later revokes the contact-time preference, the system creates a revoke event and the current view stops returning it. If the user requests deletion, the content is removed from permitted read and derived paths. If the user later chooses mornings again, that is a new v3—not a chance for a deleted or superseded old value to revive itself.

Back to the problem

The old morning preference overriding the afternoon correction was not a retrieval-ranking problem. It was a Memory system without controlled mutation and a current view.

When candidates first pass a write gate, Writers are authorized by subject, namespace, action, and evidence, and version-chain commits use an expected revision, readers receive only v2. Background consolidation can still preserve a sourced observation, but it cannot change the user’s explicit preference.

The long-term value of Memory is not storing more text. It is making every current state answer three questions: who wrote it based on what evidence, whether it is still effective, and how it can be corrected, revoked, or deleted.
