Identity Must Flow Through the Agent Call Chain

07/15/2026
AgentSecurityIdentity

The problem

A user asks an agent to update a report. When the API receives the request, it knows who is signed in and confirms that the user may edit the file. The agent then creates a Job for the background work and places it on a queue; another worker executes it several minutes later.

When the file is finally written, the worker uses its own service credential. The file service sees the worker as the caller, not the original user.

If the queue stores only a user_id, downstream services cannot prove who placed that ID there or what the user authorized. If it stores the user’s access token instead, the token may expire while waiting, be revoked, or leak into an execution environment that should never receive it.

This is the actual identity-propagation problem: after execution crosses process and time boundaries, how can the system still prove which actor is acting for which subject, under which delegation, against which resource, and for which action?

“Who is the user?” and “Who is executing?” are different questions

The file update involves at least three roles:

ConceptQuestion it answersIn this example
SubjectWhose goal and permissions are represented?The user who made the request
ActorWho is currently deciding or initiating the action?The Agent Runtime or worker
Execution identityWhich process identity is accessing infrastructure?The worker’s workload identity

Authorization also needs the tenant, action, and target resource. These are not additional kinds of user identity; they are context for deciding whether the delegation is valid.

An audit record containing only the subject makes it look as though the user personally executed every step. A record containing only the worker service account cannot say which user the action affected. Neither represents the full event.

OAuth 2.0 Token Exchange makes a similar distinction between subject and actor: delegation can express that an actor operates on behalf of a subject without pretending they are the same identity. An agent system does not have to adopt that protocol, but it needs to preserve the same semantic distinction.

Identity continuity does not mean forwarding one credential everywhere

A dangerous implementation passes one user token through the API, queue, worker, SubAgent, and Sandbox. It appears to preserve identity, but actually exposes a high-value credential across more and more trust boundaries.

A safer design preserves the meaning of the delegation while obtaining an appropriate credential again at each trusted boundary:

user request
  ↓ authenticate the user and check initial permission
Agent Runtime
  ↓ create a constrained delegation reference
queue
  ↓ worker claims the Job with its own workload identity
worker
  ↓ validate delegation again and obtain a short-lived file-service credential
file service
  ↓ check subject, actor, action, and resource
write and record an audit event

The queue stores a verifiable reference, not a long-lived bearer token:

{
  "job_id": "job_42",
  "subject_ref": "user_7",
  "actor_ref": "agent_run_19",
  "tenant_id": "tenant_3",
  "delegation_ref": "delegation_81",
  "action": "file.update",
  "resource_ref": "file_12"
}

After claiming the Job, the worker still checks whether the delegation has expired or been revoked, whether the user retains permission, and whether the target file version has changed. A queue makes later execution possible; it does not freeze authorization facts in the outside world.

Delegation should narrow along the call chain

Allowing an agent to modify a project directory does not mean every downstream component needs the same permission.

A SubAgent that only summarizes documents may need read access to /project/docs/**. Only the Tool that writes report.md needs write access to that file. Delegation can narrow along several dimensions:

  • action: from read-write to read-only;
  • resource: from a workspace to one directory or file;
  • time: valid only for a specific Run, Job, or short interval;
  • audience: usable only by the target service;
  • depth: whether further delegation is allowed.
parent: files.read + files.write on /project/**
child:  files.read on /project/docs/**

Child permissions should be a subset of the parent’s authorization. A deeper call chain should not gain authority merely because broader access is easier to implement.

The model cannot supply trusted identity

A model may generate a file path, patch, or search condition, and it may propose a requested capability, because these are task proposals. It must not supply the authoritative subject_id, tenant_id, granted authorization scope, OAuth token, or audit actor.

Any such identity or authorization fields remain model output even when they appear in a Tool Schema. They may come from incorrect memory, be induced by text in a file, or simply be fabricated.

The Runtime should inject trusted context from the authenticated session, delegation record, and workflow metadata:

async function updateFile(args: UpdateFileArgs, ctx: TrustedContext) {
  return fileService.update({
    subject: ctx.subject,
    actor: ctx.actor,
    tenant: ctx.tenant,
    path: args.path,
    patch: args.patch,
  })
}

The backend then validates against its own resource state: may this subject modify the target file, and may this actor perform that action on the subject’s behalf? Model-generated business arguments cannot override trusted context.

SubAgents, Connectors, and Sandboxes follow the same rule

These components need different credentials, but the identity problem remains the same:

  • A SubAgent needs to know which subject the task represents while receiving only its delegated capability.
  • A Connector uses its client identity and the user’s authorization to access an external API without exposing the access token to the model.
  • A Sandbox uses a workload identity to mount a workspace or write an Artifact instead of directly holding a user credential.

They do not need to share one token. They need a verifiable relationship: which execution identity the current Tool Execution or Job uses, which Run and Task originated that work, which subject the Task represents, and whether the delegation permits this action on this resource. That relationship remains attributable after the originating Run ends, but the worker must still revalidate the delegation and current authorization before a later Job acts.

A trace_id can correlate calls but cannot prove caller identity. Trace context and identity context may be linked; they cannot replace each other.

Back to the problem

Identity propagation is not copying a user_id or access token from the entry point to the end of the call chain.

It preserves an authorization relationship: whose goal is being executed, who the current actor and execution identity are, how authority was delegated, and which tenant, action, and resource are affected.

When that relationship can be validated again after a Job crosses a queue—and each layer receives only the authority needed for its current action—the agent system can support authorization, isolation, and auditability at the same time.
