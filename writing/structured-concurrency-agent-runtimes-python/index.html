Agent Runtime 13: Own Concurrent Work with Structured Concurrency

A group of ownerless Tool `asyncio.Task` objects shows how TaskGroup makes concurrent work awaitable, cancellable, and able to propagate failures.

07/15/2026 Views
AgentRuntimePythonAsyncio

The problem

A Python Agent Runtime has admitted three Tool Calls and created three Tool Executions that can advance concurrently. The most direct implementation is:

async def start_tools(executions):
    for execution in executions:
        asyncio.create_task(execute_tool_execution(execution))

    return "started"

The code starts three coroutines concurrently, then returns immediately after creating their Tasks. Several questions no longer have an owner:

  • When may the parent Run enter a completed state?
  • Who retrieves an exception from one failed Tool Execution?
  • Who stops the remaining Tool Executions when the user cancels the Run?
  • Which work must finish before process shutdown?

Structured Concurrency is not primarily about creating Tasks faster. It is about ownership: a group of concurrent work belongs to an explicit lifecycle; the parent waits for its children and receives their failures.

This article uses asyncio.TaskGroup, available in Python 3.11 and later. Unless an application-level Task is named explicitly, Task below means Python’s asyncio.Task; work transferred to a queue or workflow is a Job.

create_task() is not the problem; discarding the Task is

asyncio.create_task() returns a Task. If the caller keeps it, the caller can await the result, retrieve an exception, or request cancellation. Discarding the reference also discards the program’s management handle for that work.

Python’s documentation explicitly recommends retaining references returned by create_task(). The event loop keeps only weak references to Tasks, so a Task without another strong reference may even be garbage-collected before completion.

Even if the Task remains alive, the earlier example has a deeper problem: the lifetime of start_tools() is detached from the work it starts. The function has returned while a Tool Execution may still be modifying external state.

That creates two conflicting facts. The parent Run says the stage ended, while a child Task still believes it may continue executing.

TaskGroup puts concurrent work back inside the parent scope

asyncio.TaskGroup is an async context manager. Exiting the async with block waits for every Task in the group:

import asyncio


async def execute_tools(executions):
    tasks = {}

    async with asyncio.TaskGroup() as group:
        for execution in executions:
            tasks[execution.id] = group.create_task(
                execute_tool_execution(execution),
                name=f"tool:{execution.id}",
            )

    return {
        execution_id: task.result()
        for execution_id, task in tasks.items()
    }

execute_tools() now has three clear convergence paths. On normal completion, all child Tasks have finished and their results can be returned. An unhandled failure inside the group propagates to the parent. If the parent or group is cancelled externally, cancellation continues through the parent scope after the child Tasks converge. The function no longer reports completion while children are still running.

By default, when a child raises an unhandled exception other than CancelledError, TaskGroup requests cancellation of the remaining Tasks and waits for them to finish. It then combines ordinary failures into an ExceptionGroup or BaseExceptionGroup as appropriate; KeyboardInterrupt and SystemExit are re-raised after sibling cancellation instead.

That does not mean every Tool Execution failure should make the group fail fast. Expected business failures such as invalid arguments or a missing resource can be converted inside execute_tool_execution() into typed results, allowing independent Tool Executions to continue. A Runtime bug or unclassified exception can keep propagating so the parent knows the stage did not complete reliably.

Structured Concurrency provides a clear failure path. Whether partial success is acceptable remains a business policy.

Cancellation requires children to converge cooperatively

TaskGroup failure handling depends on cancellation. In Python, task.cancel() requests cancellation; CancelledError is raised the next time the coroutine gets a chance to run. Cancellation is not forced immediate termination.

A child should release resources in finally and, after performing necessary cleanup in an except asyncio.CancelledError block, propagate the cancellation again:

async def write_artifact(stream, sink):
    try:
        async for chunk in stream:
            await sink.write(chunk)
    except asyncio.CancelledError:
        await sink.mark_interrupted()
        raise
    finally:
        await stream.aclose()

If code swallows CancelledError, the parent TaskGroup may not converge as expected. Conversely, cancellation of a local Task does not prove that a remote side effect was reversed. An HTTP request may already have committed a write, and a subprocess may already have changed a file.

Structured Concurrency gives local Task lifecycles an owner. It does not replace Tool Runtime logic for confirming external outcomes.

A real background Job needs more than a bare Task

Some Jobs are supposed to continue after a request returns—for example, report generation that takes several minutes. That does not make a fire-and-forget in-memory Task safe.

Work that outlives the request should first receive a durable Job identity and recoverable state, then be handed to a queue or workflow worker. The background worker becomes the new owner rather than leaving ownership with an HTTP request scope that no longer exists.

in-request concurrency: TaskGroup owns and awaits child Tasks
out-of-request work:     queue or workflow owns a durable Job
ownerless Task:          lifecycle has no explicit owner

The distinction is not how long the work runs. It is who remains responsible for explaining its state after process restart, cancellation, or failure.

TaskGroup governs only the lifecycle of concurrent work

TaskGroup answers “who owns these Tasks?” It does not answer “how many Tasks may run at once?” Sending ten thousand requests concurrently can still exhaust a connection pool or provider limit even when every Task belongs to one group.

Semaphores, bounded queues, and admission control limit concurrency and propagate backpressure. A deadline limits how much time the entire stage may consume. These mechanisms complement ownership; they are not part of Structured Concurrency itself.

Similarly, two Tool Executions modifying the same resource concurrently still need optimistic concurrency control, a transaction, or serialization by key. TaskGroup manages Python Task lifecycles, not business-state consistency.

These boundaries also show that create_task() itself is not an anti-pattern. It remains an appropriate low-level API when the caller:

  • retains the Task reference;
  • explicitly assigns responsibility for awaiting the result or handling the exception;
  • converges the Task during parent cancellation and shutdown;
  • does not mark the parent stage complete while the child is still running.

TaskGroup makes these responsibilities the default for a set of Tasks that jointly complete one stage, reducing the chance that one is forgotten.

Back to the problem

The first question for concurrent Tool Executions is not how to replace a loop with create_task(). It is who owns the asyncio.Task objects after they are created.

TaskGroup makes the parent wait for children, propagates unhandled failures, and uses cancellation to help the group converge. Work that must outlive the parent should transfer ownership explicitly to a queue or workflow instead of leaving an ownerless in-memory Task.

When every Task can answer “which scope do I belong to, who awaits me, and who receives my failure?”, Python async becomes an interpretable execution structure instead of merely many coroutines running at the same time.
