Agent 22: Why One File Needs Both an Artifact Identity and a Workspace Reference

Model a file's cross-stage lifecycle with Artifact identity, Workspace references, and structured mutation preconditions.

07/24/2026 Updated 07/27/2026 Views
Agent StateAgentArtifactsCode Editing

The problem

A user uploads src/config.ts, and the Agent sees it at /tmp/input/config.ts inside a Sandbox. After the Runtime restarts, the same path is reused by another materialization. A stale message in the Session still tells the model to edit /tmp/input/config.ts.

The path string does not identify which upload or revision it refers to, and it does not prove that the edited result derives from the user’s original file. Even when the edit succeeds, the download side still cannot explain the content’s lineage.

When a file moves across messages, Workspaces, and storage, three objects must remain distinct: the Artifact provides a stable cross-system identity and version; a Workspace reference resolves its location in a particular execution environment; and a message reference exposes only a constrained handle to the model. Every mutation then connects input and output through revisions and validation evidence.

Blob, Artifact, and path answer different questions

ObjectQuestion it answersOwner
BlobWhere are these bytes stored, and what is their content hash?Object/blob store
ArtifactWhich logical file and revision is this, and where did it come from?Artifact service
Workspace objectWhich Artifact revision does this Session use?Workspace service
PathWhere can the current Runtime access it?Runtime/VFS
Message referenceWhich constrained object may the model reference?Agent host

A Blob may be deduplicated by content, but identical bytes can belong to two tenants or two business Artifacts. Authorization for an Artifact identity cannot be derived from the hash alone. Conversely, a path can remain unchanged when an Artifact advances to a new revision, while the content hash changes.

A path is meaningful only inside an explicit Workspace/Runtime binding. Persisting /tmp/input/config.ts in a long-lived Session is not enough to locate the original file after recovery.

An upload first creates a stable Artifact revision

An upload can create:

artifact_id: artifact_17
revision: 1
owner_ref: tenant_3/user_7
blob_ref: sha256:abc...
media_type: text/typescript
source:
  kind: user_upload
  message_id: message_41

This is a conceptual contract, not the current schema of a storage product. The Artifact service owns the revision and lineage. The Blob store retains the content. The Message stores a reference to artifact_17@1 rather than copying a temporary path that will later become stale.

Download authorization also depends on the current subject, Artifact owner, and revision. Possessing a guessable path, Blob URL, or content hash does not automatically grant read access.

Materialization maps an Artifact into a Workspace

After Sandbox acquire, the Workspace service resolves the following for the current lease:

workspace_id: ws_9
workspace_revision: 12
artifact: artifact_17@1
workspace_ref: wsobj_33
runtime_path: /workspace/inputs/config.ts
mount_mode: read_only
lease_generation: 6

The model only needs a constrained message reference or Workspace path. The Tool handler obtains the workspace_ref, expected Artifact revision, and lease generation from trusted Context.

When the Runtime is rebuilt, it does not reuse the old path as identity. It resolves wsobj_33 → artifact_17@1 again, materializes it at a new local path, and verifies the Workspace lease and revision. If the Artifact was deleted, permission was revoked, or the reference is incompatible, recovery should fail instead of searching for a similar object by filename.

When a modification is required, the Workspace service does not write to this read-only base object. It creates copy-on-write staging under the current lease:

base_workspace_ref: wsobj_33
workspace_ref: wsobj_34
mount_mode: copy_on_write
lease_generation: 6

The mutation, diff validation, and publish steps all refer to wsobj_34; wsobj_33 continues to prove that the input came from artifact_17@1.

A mutation declares its input preconditions first

When the Agent edits source code, the Tool proposal can describe a target symbol and patch, but the trusted execution layer should bind:

mutation_id: edit_52
input_artifact: artifact_17@1
base_workspace_ref: wsobj_33
workspace_ref: wsobj_34
expected_file_revision: 1
allowed_scope: export function loadConfig

Before execution, it verifies that the writable staging object, lease generation, and base content still correspond to input revision 1. This proves only that the edit uses the expected input. It does not prove that another actor has not advanced the Artifact’s current head.

A normal data file may need only a revision or hash precondition. For source code, structured evidence can further reduce accidental edits:

  • whether the target symbol still exists before and after parsing;
  • whether the patch touches only the allowed scope;
  • whether the AST precondition matches the expected structure;
  • formatter, type-checker, or static-analysis results;
  • the actual diff and Tool Result.

AST-aware editing is not required for every Artifact, and it cannot prove business correctness or code safety. It is only one form of verifiable evidence for this source mutation. Tests, the Sandbox, and any required human confirmation remain separate boundaries.

Publish creates a new revision without overwriting lineage

After the edit passes the agreed checks, the Artifact service publishes revision 2:

artifact_17@1
  → materialized as read-only wsobj_33
  → staged as copy-on-write wsobj_34
  → mutation edit_52
  → checks: parse pass, scope pass, typecheck pass
  → artifact_17@2

At publish time, the Artifact service performs a CAS against the current head with expected_current_revision: 1, preventing two edits derived from v1 from silently applying last-write-wins. If the head is already v2, this edit result may remain as an explicit branch but cannot advance the current head. The caller must reread or hand the conflict to the merge owner. Workspace binding and lease checks cannot replace this publish-conflict protocol.

An Artifact Result should include a stable reference, content checksum, lineage, and validation summary. typecheck pass proves only that the executed configuration found no type errors within its scope. It does not mean that every test passed, and a check that was never run cannot appear in the evidence.

Do not conflate temporary, persistent, and published

Files inside a Workspace can be:

  • temporary: disposable when the Runtime ends;
  • persistent workspace: retained across Runtimes but still owned by the Workspace;
  • published Artifact: governed by a stable identity, revision, owner, and download contract.

Automatically publishing a temporary cache can leak intermediate data. Treating every Workspace file as an Artifact creates many meaningless versions. Only a result that must be referenced across boundaries, delivered, or recorded in lineage should enter publish.

Retention and deletion also follow separate owners. Deleting an Artifact must invalidate authorized references and derived downloads. Cleaning a Runtime path removes only the materialized copy. Whether the Blob is physically reclaimed still depends on other legitimate references and retention policy.

Walk the opening file through the lifecycle

The correct flow is:

upload config.ts
→ artifact_17@1
→ message refers to artifact_17@1
→ materialize as wsobj_33 under lease generation 6
→ create copy-on-write staging wsobj_34
→ edit with expected input revision 1
→ validate actual diff
→ publish artifact_17@2 with expected current head 1
→ download resolves artifact_17@2

After a Runtime restart, even if /tmp/input/config.ts has been reused, the old Session still resolves through artifact_17@1 and read-only wsobj_33, then creates a new staging object for the current lease. If the local path points to other content, the Workspace identity/revision check rejects the mutation. If another actor has advanced the Artifact head, publish CAS rejects the overwrite.

Back to the problem

The same path can refer to different files in two Runtimes, and the same Artifact can use different paths in different Workspaces. A path is therefore only a location inside an execution environment; it cannot carry cross-Session identity.

When an upload first creates an Artifact revision, Messages and Workspaces retain constrained references, edits bind the input revision, mutation scope, and actual validation evidence, and publish performs a CAS against the current head, the system can prove that the downloaded artifact_17@2 derives from the user’s v1 upload rather than from a reused temporary path or a silent overwrite of a concurrent update.
