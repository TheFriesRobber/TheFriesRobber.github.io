LLM Infra 12: Coordinating Queuing, Rejection, and Scaling Across Time Scales

Put immediate admission, a bounded queue, slow provisioning, and scale-in draining into one capacity-control loop operating across multiple time scales.

07/29/2026 Views
LLM InfraInferenceAdmission ControlAutoscaling

The problem

A traffic burst enters an unbounded queue, and the Autoscaler begins bringing up new Replicas. Before the models finish loading, early requests have already missed their deadlines, yet invalid work remains in the queue. Scale-out eventually succeeds, but goodput within the SLO still falls.

The problem is not that scaling is too slow or rejection happens too early. The system has treated admission, queuing, and provisioning as three unrelated mechanisms. They all respond to the same capacity shortage, at different time scales.

Four time scales form one control loop

Immediate admission

When a request arrives, decide whether the current compatible deployment can plausibly admit it. The outcome may be accept, defer, route, degrade, or reject.

Queue horizon

Within the short window allowed by the deadline, a bounded queue absorbs the burst. The queue must be described by pending Token work and oldest age, not only by request count.

Provisioning lead time

Creating nodes, pulling images, loading models, forming parallel groups, and warming up to Ready all take time. Scale-out can help only demand that extends beyond this window.

Scale-in draining

During scale-in, stop accepting new requests, wait for or migrate admitted work, and only then remove the Replica. Immediate removal can break streaming and KV state.

All four mechanisms must consume the same workload identity, deployment revision, and capacity evidence. Otherwise, Admission may assume capacity is imminent while the Autoscaler creates only incompatible new Replicas.

The deadline determines whether scaling can save the current request

Let:

  • D be the time remaining until the request deadline;
  • L_ready be the measured Replica-ready lead time for the deployment.

If D ≤ L_ready, even a Replica started immediately cannot serve the current request. This is an inference from the timing relationship, not a guarantee built into any Autoscaler.

The current request must choose among these outcomes:

  • have existing capacity accept the request and satisfy its delivery contract before the deadline;
  • queue for a short period;
  • route to a compatible deployment that is already Ready;
  • degrade within a contract explicitly permitted by the caller;
  • reject with a stable reason and useful retry guidance.

Scale-out remains useful, but it serves later arrivals or requests with more distant deadlines.

Admission needs an explainable Outcome

admission_outcome:
  request_id: req_123
  decision: reject
  reason_code: deadline_before_capacity_ready
  queue_deadline: 2026-07-29T12:00:02Z
  retry_after_seconds: 3
  compatible_release: null

This is a conceptual schema for this article. Retry-After has standardized HTTP semantics, but whether to return it and how to calculate its value depend on overload state. A response must not cause every client to retry in the same second and create another burst.

degrade also cannot simply mean “switch to a smaller model.” Infra may choose an alternative deployment only when the release capability contract declares it compatible and the caller allows the substitution. Otherwise, it should reject explicitly.

The queue must be bounded. An unbounded queue lets requests that have already missed their deadlines continue consuming memory and scheduling overhead, turning overload into an ever-longer failure latency.

Autoscaling must compare Demand with Ready capacity

KServe’s generative-inference autoscaling examples use signals such as vLLM running requests, waiting requests, or KV usage. Ray Serve compares ongoing requests per Replica with a target by default and explains how startup delay, maximum ongoing requests, and queuing affect tail latency. Kubernetes HPA adjusts replica counts from periodic observations and stabilization windows.

These implementations establish which signals are available, but none supplies a universally optimal formula. An inference platform can divide the evidence into:

TypeExamples
Demandknown prompt Tokens, generated Tokens, remaining-output estimate or upper bound, oldest queue age, arrival forecast
Ready capacitycompatible Ready Replicas, service curve, KV or Token budget
Provisioningmeasured startup, load, and warmup lead time; pending Replicas
SymptomGPU utilization, preemption, deadline misses

A capacity decision might be:

capacity_decision:
  deployment_revision: release_91a
  observed_at: 2026-07-29T12:00:00Z
  known_prompt_tokens: 520000
  generated_tokens: 80000
  remaining_output_estimate: 240000
  max_remaining_tokens: 610000
  output_estimator_version: output-length-v3
  demand_policy: expected_remaining_output
  oldest_queue_age_ms: 620
  ready_capacity_ref: fleet_curve_22
  measured_lead_time_ref: startup_dist_08
  desired_replicas: 10
  scale_reason: sustained_pressure_beyond_ready_capacity

The combination of fields is a workload-specific design suggestion. Future output Tokens are unknown before execution, so the controller must state whether it uses a versioned expected-value estimate or a request upper bound; it cannot present a prediction as fact. This example is not an industry-standard formula either, and startup constants must come from measurement.

Admission must continue while scale-out is not Ready

Consider this synthetic timeline:

t0      burst arrives
t0+Δ1   admission fills bounded queue, rejects requests without slack
t0+Δ2   scale-out requested
t0+Δ3   new Replica loading model; not counted as capacity
t0+Δ4   platform readiness passes; health probes only
t0+Δ5   release compatibility passes; controlled warmup/probes
t0+Δ6   capacity gate for the measured curve passes
t0+Δ7   Router sends production work; Autoscaler counts ready capacity

Kubernetes readiness says only that a Pod can currently receive the corresponding traffic. It does not prove that the model revision, parallel group, warm state, and performance deliver the service curve used for capacity planning. This article therefore separates three gates: platform_ready → release_compatible → capacity_ready_for_curve. Only after t0+Δ6 may a new Replica enter the Autoscaler’s ready capacity. A running Pod, a started process, completed model download, or a readiness probe alone is insufficient.

Admission cannot stop during Δ2–Δ6. It must keep updating queue deadlines, remove queued requests that have expired before execution, and prevent retries from amplifying traffic again. Cancellation acknowledgement and unknown outcomes for work that has already started belong to the streaming-failure protocol in Article 14; this article does not claim to solve them.

Scale-in must protect admitted work

Falling GPU utilization does not mean a Replica can be removed immediately. It may still hold:

  • Decode sequences that are currently streaming;
  • unfinished Prefill work;
  • local Prefix KV or Adapter residency;
  • requests selected for placement but not yet arrived.

Draining can follow these states:

ready
→ stop_new_admission
→ wait_or_cancel_by_policy
→ release_residency
→ removed

Scale-in delay, minimum warm capacity, and the stabilization window should all be chosen according to the workload and measured lead time. Repeated scaling reloads the model again and again, bringing a cold state into every performance window.

Back to the problem

Scale-out in the opening scenario eventually succeeds, but cannot save requests that have already missed their deadlines. The unbounded queue also lets expired, unstarted requests continue creating useless work.

The correct control loop coordinates four time scales: Admission handles the present moment, the bounded queue handles a short burst, provisioning handles sustained pressure, and draining protects admitted work. A new Replica counts as capacity only after it passes the platform, release, and capacity gates in sequence and can deliver the corresponding service curve.

Scale-out is not a substitute for rejection, and rejection is not merely a side effect of failure. Together, they determine how much goodput the system can still deliver when capacity is insufficient.
