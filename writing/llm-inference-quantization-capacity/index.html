LLM Infra 08: Why Quantization's Memory Savings Do Not Equal Deliverable Capacity

Separate Weight, Activation, and KV Cache quantization, then use a memory ledger, Kernel support, quality constraints, and a workload-specific service curve to determine whether quantization adds deliverable capacity.

07/29/2026 Views
LLM InfraInferenceQuantizationCapacity Planning

The problem

After a model moves from BF16 weights to 4-bit weight-only quantization, its checkpoint and resident weights become substantially smaller, and the model fits on fewer GPUs. Yet long-Context concurrency remains limited by KV Cache, some hardware/shape combinations take different Kernel paths, and goodput within the TTFT/TPOT contract does not increase in proportion to compression.

“The model became smaller” is a fact about the artifact and weight memory. “Deliverable capacity increased” must pass three gates: memory, execution, and quality.

Quantization must first say what was quantized

Quantization is not one uniform switch.

TypeMain object changedObjects not changed automatically
Weight-onlyModel-weight storage and some matrix-compute pathsKV Cache, many Activations, workspace
Weight + ActivationWeights and selected Activation representations/computationUncovered operators, KV Cache
KV Cache quantizationKV representation for each active TokenModel weights, other Activations

AWQ is low-bit weight-only quantization. SmoothQuant aims to make weights and activations easier to execute through a W8A8 path. They do not address the same GPU-memory region and should not be compared by bit width alone.

Current vLLM likewise separates model quantization from KV Cache dtype and maintains a support matrix that depends on hardware and quantization method. “The model is 4-bit” is therefore still insufficient to determine the complete execution path.

When weights shrink, the bottleneck moves

Consider a synthetic ledger in abstract memory units:

ItemBF16 configuration4-bit weight-only
Weights205
KV Cache88
Activations / workspace / Runtime44
Total3217

The numbers express only the relationship and do not correspond to a specific model or device. In this example, shrinking weights by 4× reduces total use only from 32 to 17. As Context and concurrency grow, KV continues to grow as well.

Weight-only quantization can therefore produce three different results:

  • A model that did not fit can now load.
  • Freed memory can be assigned to more KV blocks.
  • Capacity remains bounded by KV, Kernels, compute, or the SLO.

The first result does not imply the third. Capacity changes must return to the complete memory ledger from article 05.

A loadable format does not prove an efficient Kernel path

Low-precision gains depend on joint support from hardware, the Runtime, and Kernels:

  • whether the device natively supports the target dtype or requires conversion;
  • whether the quantization method has matching Linear/MoE/attention Kernels;
  • whether group size, shape, batch, and parallelism satisfy Kernel conditions;
  • which precision unsupported operators use;
  • whether dequantization, repacking, or CPU/GPU offload occurs.

Hugging Face quantization documentation maintains multiple backends and their hardware support. vLLM also distinguishes quantization methods and supported hardware. Loading a checkpoint proves only that its format can be parsed; it does not prove that the target requests used the intended Kernels.

Deployment validation should record at least:

quantization_execution:
  weight_format: awq-int4
  activation_dtype: fp16
  kv_cache_dtype: fp16
  resolved_kernels:
    linear: observed-kernel-name
    attention: observed-kernel-name
  fallbacks:
    count: 0
    source: runtime-log-or-profiler

These fields are conceptual suggestions. Kernel names and fallback behavior must be observed from the target Runtime’s logs, profiler, or code path; they cannot be inferred from a checkpoint filename.

Quality must be a hard constraint first

Quantization changes numeric representation and can affect perplexity, generation quality, structured output, Tool arguments, or tasks involving particular languages or long Contexts. A paper preserving accuracy for its models and benchmarks does not prove that every workload is unchanged.

The comparison order should therefore be:

  1. Fix the model revision, template, sampling, and workload.
  2. Choose a quality evaluation suite for the application contract.
  3. Check whether the quantized configuration passes the quality gate.
  4. Compare TTFT, TPOT, goodput, and cost only among candidates that pass.

If a candidate is faster but lowers the success rate of structured output, it is not a capacity increase under the same service contract.

The quality record must also distinguish:

  • the original tasks reported in the quantization paper;
  • offline evaluation of the current model;
  • the target application contract;
  • the permitted regression boundary.

Rebuild capacity from the same service-curve method

A quantized configuration is a new deployment manifest, so the old service curve must be invalidated.

A new Benchmark should control and record the following as specified:

  • the workload envelope and SLO;
  • hardware, Replica count, and parallel topology;
  • warm/cold Cache state;
  • tokenized inputs, sampling/generation configuration, requested minimum/maximum output, and random-seed policy;
  • record actual output length and EOS/stop reason rather than forcing them to be constant;
  • the quality gate;
  • quantization method, scales, Runtime, and Kernels.

If a pure Kernel/throughput experiment uses ignore_eos or a fixed Output Sequence Length for comparability, it must be labeled as a synthetic fixed-OSL experiment. It cannot replace application-quality and service-curve measurement under normal stopping semantics.

The next comparison includes more than memory:

GateRequired evidence
FitWeights, KV, Activations, and peak allocation
ExecuteKernels/fallbacks, TTFT, TPOT, failures
QualityResults from the same evaluation suite
CapacityService curve / goodput satisfying every constraint

Suppose configuration Q reduces a Replica from two GPUs to one, but its SLO-constrained goodput falls. It may still be worthwhile because of better fleet placement or cost, or it may require enough extra Replicas to erase the gain. The answer depends on the full fleet design, not only on “one fewer GPU per Replica.”

An auditable quantization decision

quantization_decision:
  candidate:
    artifact_digest: sha256:...
    quantization_config_digest: sha256:...
    scales_digest: sha256:...
    kv_cache_dtype: fp16
  baseline:
    artifact_digest: sha256:...
  workload_fingerprint: wl_7fd2
  evidence:
    memory_ledger: artifact://memory-comparison
    kernel_trace: artifact://kernel-resolution
    quality_report: artifact://quality-gate
    service_curve: artifact://benchmark-curve
  result:
    quality_gate: pass
    capacity_change: measured
    cost_change: modeled-from-measured-capacity
  invalidate_on:
    - model_revision_changed
    - quantized_artifact_or_scales_changed
    - quantization_config_changed
    - kv_cache_dtype_changed
    - runtime_or_kernel_changed
    - hardware_changed
    - workload_distribution_changed

This record does not assume that lower bit width is always better. It requires every decision to remain traceable to complete evidence.

Back to the problem

The 4-bit weight-only configuration did shrink the weights. It did not also compress the KV Cache, guarantee a faster Kernel on the target hardware, or automatically satisfy the original quality contract.

Memory saved is therefore only one input to a quantization decision. A candidate becomes a deliverable-capacity improvement only after it passes the quality gate, produces a new service curve under the target workload, and yields higher fleet goodput or lower cost per qualified delivery.
