Agent Memory 4: Use Version Chains for Correction and Revocation

07/14/2026 Views
AgentMemoryData Governance

The problem

A user originally asked for meetings in the morning whenever possible, then explicitly changed the preference to “afternoons only from now on.” The system updates the same row’s value from “morning” to “afternoon.”

The current value looks correct, but two problems remain. The system can no longer explain why it scheduled morning meetings last week. Another writer that already read “morning” may submit later and overwrite the new preference. An in-place update retains only the final string. It preserves neither the meaning of the change nor evidence that a writer is stale.

Memory must permit facts to change, but mutability does not require overwriting the only version in place.

Version history, current view, and audit solve different problems

A governable Memory record can have three layers:

  • version history retains versions of a claim, their sources, and their relationships;
  • the current view exposes only versions that are valid and readable now;
  • audit events record who requested each mutation and how policy decided it.
memory_id: schedule_preference_17
version: 3
value: meetings_only_in_afternoon
status: current
supersedes: version_2
source_ref: message_88
expected_version: 2

Retrieval normally queries the current view, so the model does not need the complete history in Context. When explanation or recovery is required, the system can follow version relationships and audit events back to the source of a change.

Supersede, revoke, delete, and undo are different operations

All four can remove an old value from the current view, but they express different facts:

OperationMeaningResult
SupersedeA new current value replaces the old oneCreate a version that points to the replaced version
RevokeThe old record is no longer accepted, with no replacement valueRemove it from the current view and record why
DeleteContent must become unavailable under a user request or retention policyErase protected content; keep only a minimal tombstone when policy permits
UndoRestore a previous business valueCreate a restoring version instead of moving history backward

“Withdraw an incorrect inference” and “the user changed their preference” should not both be generic updates. The first does not assert that an opposite fact is true; the second has a source for a new value. Nor may an append-only design permanently retain sensitive content after deletion. Physical retention remains subject to privacy and retention requirements.

Walk the morning-to-afternoon change through the model

The old current record is version_2 = mornings_preferred. After the correction, the writer submits version_3 with the original message source and expected_version: 2. The Memory service switches the current view conditionally:

version_2: superseded by version_3
version_3: current, afternoons_only
current view: version_3

The system can still explain last week’s decisions based on version 2, while the next Retrieval sees only version 3. If the user says, “Undo that change; mornings are better,” the service does not delete version 3 and revive version 2. It creates version_4 with the morning value and records that the operation was an undo. The current view advances to version 4 while history remains ordered.

Conditional writes stop stale writers from replacing new facts

Suppose the in-loop Agent and a consolidation job both read version 2. The Agent first writes version 3 from the user’s explicit statement. The consolidation job later submits its candidate with expected_version: 2.

The service should reject the second switch because the current version is no longer 2. This follows the same idea as HTTP If-Match preventing a lost update: a writer must prove that it is modifying the version it read. After rejection, it can only reread version 3 and decide whether its observation still conflicts, can be merged, or should be abandoned.

Do not hide the conflict with last-writer-wins. Two authorized writers may have made compatible changes to different fields. Whether to merge depends on record type and claim scope, not submission time.

The current view must change when a source becomes invalid

Business corrections are not the only reason for status changes. If a source loses authorization, passes its retention limit, or fails an integrity check, any current record that depends on it needs revalidation. The default is to mark the record unavailable, request confirmation, or trigger rebuilding—not to reactivate a superseded claim automatically. The system may select a replacement current record only when the record type defines an explicit recovery rule and independent, currently valid evidence supports that value. It must never keep returning an unreadable version from a search index.

This is why the current view is separate. Version history explains what happened; the current view answers what may be used now. If both are reduced to a table sorted by update time, authorization changes and supersession become ordinary ranking problems when they are not.

What to test

Tests should cover more than a normal v2 → v3 path: two writers modifying v2 concurrently, revocation without a replacement, content becoming unrecoverable after deletion, undo creating a new version, and source revocation removing a value from the current view.

Key invariants include an acyclic version chain, at most one current version per claim scope, valid supersedes targets, rejection of stale revisions, and current-view validation that a lagging search index cannot bypass.

Back to the problem

Changing “morning” to “afternoon” in place produces only a latest string. It neither explains the change nor prevents a concurrent writer from overwriting it with an old value.

Give supersede, revoke, delete, and undo distinct meanings. Preserve the history that policy allows through append-style version relationships, expose usable facts through a current view, and protect each switch with expected_version. Memory can then accept user corrections without sacrificing explanation or concurrency safety.
