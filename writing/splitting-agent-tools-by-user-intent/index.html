Agent Tools 2: One Tool or Several?

Split Tools by user-distinguishable intent, permission, and side effects—not by backend endpoints.

07/14/2026 Views
AgentToolsAPI Design

The problem

A file service exposes one backend endpoint. Its conceptual request shape accepts these fields:

{
  "command": "read | write | delete",
  "path": "...",
  "content": "...",
  "recursive": false,
  "force": false
}

A real schema could use oneOf or conditional branches so each command accepts only its relevant fields; this block is not complete JSON Schema. Even after field validity is solved, exposing the endpoint directly as manage_file creates a semantic problem. When the user says “take a look at the configuration file,” read, overwrite, and delete remain branches of one model-visible entry point. The Runtime can derive and version a restricted schema that removes unauthorized branches, or authorize precisely after normalizing command and resource. The cost is that surface filtering, policy mapping, caching, and contract tests must all understand the branch layer.

The resulting call may conform to the schema and still select the wrong action.

The opposite extreme—turning every endpoint and every flag combination into a separate Tool—is not automatically better. A long list of similarly named Tools makes the model guess among more candidates, while duplicated fields and vague descriptions create different selection errors. The important question is not the number of Tools. It is where the model should make each decision.

Splitting changes two decision dimensions

Agent Tools 1 treats Tool Schema as a model-facing API. Tool boundaries affect two parts of a Tool-call error model:

  1. Tool selection: which action matches the user’s intent?
  2. Argument generation: after identifying an action, which parameters describe it?

These are analytical dimensions, not a claim that a provider observes the model selecting a name and then generating arguments in a sequential process. Protocols usually expose only the final name and arguments, and one response may contain no call or multiple calls. Combining very different actions hides name selection inside a command parameter. Splitting too far makes the name candidate set represent differences that belong in ordinary parameters. A useful boundary makes Tool selection correspond to a user-understandable action, while arguments describe variation within that action.

Five questions help decide whether two actions should remain together:

SignalGreater differences favor splitting
User intentWould users describe the actions with different verbs, objectives, or success criteria?
Required argumentsAre many fields for one action meaningless to the other?
Permission and confirmationDo they require different capabilities, approvals, or confirmation?
Side effects and retryIs one read-only while the other writes, deletes, or creates an external effect?
Result and repairDo their result shapes and recovery paths differ?

These are design signals, not a formula in which three checked boxes force a split. Real Task distributions and model Evals still decide the boundary.

Different side effects should become different Tools

The model-facing API for the opening endpoint could be:

read_file(path, line_range?)
write_file(path, content, overwrite=false)
delete_file(path, expected_file_version)
delete_directory(path, expected_tree_version)

read_file is read-only, requires read permission, and often recovers from failure by correcting a path. write_file changes content and needs write authority; overwriting an existing file may require a version precondition or additional confirmation. Both deletion actions bind a target version and may require confirmation based on risk. Recursive deletion additionally binds the tree scope and version and usually needs stricter capability and confirmation. Their resource scope and recovery cost justify separate Tools.

Now, for “take a look at config.yaml,” the model selects read_file and produces path. content, force, and deletion confirmation no longer participate in the decision. After validating and normalizing the Tool name and arguments, the Runtime checks the actor’s existing capability against the canonical file.read action and target resource; model selection does not grant authority.

For “change the timeout to 30 seconds,” the model selects write_file or a narrower edit Tool. Whether edit_file deserves its own boundary depends on the actual contract. If editing accepts a patch, requires an original-content version, and has conflict-specific recovery, while writing accepts full content and may create a file, a split helps. If both accept complete replacement content and share permissions and failure semantics, two near-synonyms may only add ambiguity.

Do not turn ordinary arguments into Tools

Suppose the read endpoint also supports encoding=utf-8|base64. This is usually a representation choice within one read intent. It adds no new permission, side effect, or success criterion. Splitting it into read_utf8_file and read_base64_file forces the model to guess the encoding before it sees the file.

Likewise, list_files(path, recursive=false) may remain one Tool when ordinary and recursive listing share the same permission boundary, bounded cost, and result contract. If recursion crosses resource boundaries, creates materially greater cost, or requires separate confirmation, that is evidence for another restricted action.

A backend endpoint is therefore neither a merge rule nor a split rule. One endpoint can support several model-facing Tools. Several endpoints can implement one stable user intent when the Runtime hides internal topology instead of asking the model to infer it.

Permission boundaries tend to be stronger signals than naming preference

Splitting is especially valuable when two actions differ in security properties. Consider get_invoice and refund_invoice. They share invoice_id, but one is read-only while the other creates a financial side effect, needs greater authority, and requires explicit confirmation. With invoice(command=get|refund), the Runtime can still normalize the schema-validated command into a canonical action before authorization, logging, and confirmation. Hiding refund before model invocation requires deriving and versioning a restricted schema. Splitting simply makes that filtering and policy mapping more direct.

After splitting, the Runtime can hide refund_invoice before model invocation when the actor lacks the capability. If it remains visible, execution validates and normalizes the Tool name and arguments, then reauthorizes the canonical action and resource from trusted Context and current backend state, with confirmation bound to the invoice and amount. A Tool name is also model-generated and is not a security boundary. Splitting makes surface filtering, policy mapping, and audit more direct.

Let Evals decide instead of schema aesthetics

Prepare at least four Task classes: read-only requests, writes, high-risk deletion, and incomplete intent that should trigger clarification. Label the allowed result set for every case first:

case_id: inspect_config
expected: call(read_file) | clarify
forbidden_effects: [write, delete, network_egress]

Compare merged and split designs under the same model snapshot, prompt, Tool visibility policy, and Task set. Repeat a fixed number of trials per case and use a sandbox, dry run, or spy backend to record:

  • whether the result belongs to the labeled call / clarify / refuse set, including zero and multiple calls;
  • whether arguments are valid and limited to the selected action;
  • whether the model proposes a side effect beyond user intent;
  • how many repair calls follow a failure;
  • how many tokens the schemas and Tool definitions consume.

Whether policy and confirmation bind precisely to an action is better checked with deterministic contract tests than model sampling. A later Tool Eval article can define the full metric system; this minimal experiment only asks whether the proposed merge or split reduces semantic mistakes.

OpenAI function tools and Anthropic client tool definitions both describe callable actions with a name, description, and JSON Schema. OpenAI also supports custom tools whose input is not a JSON Schema object, so this statement does not cover every Tool type. Strict schema adherence constrains argument shape; it does not decide semantic Tool boundaries. command=delete can satisfy an enum perfectly and still violate a request to inspect a file. Evals must check intent and side effects, not only JSON validation.

Back to the problem

The universal Tool hides the differences among read, write, and delete inside one parameter, making side effects harder for the model to distinguish. Narrowing the surface by action then requires a derived restricted schema, while policy must normalize the discriminator first. Mechanical splitting turns encoding, flags, and backend topology into unnecessary Tool-selection choices.

A better boundary follows user-distinguishable intent, required parameters, permission, external effects, and repair paths, then tests whether the model actually makes fewer mistakes. In the file example, read, write, file deletion, and recursive directory deletion deserve separate actions. Encoding usually remains an argument. The Tool surface should support model decisions rather than mirror a backend directory.
