Agent Evaluation 1: Pass Rate Is Not Enough for Nondeterministic Systems

Two identical aggregate pass rates reveal why Agent evaluation must preserve case, configuration, trial, and failure distribution.

07/12/2026 Views
AgentEvaluationReliability

The problem

Consider a simplified constructed example. Two Agent versions each pass 20 of 25 tests, so the dashboard gives both an 80% pass rate.

Expanded by case, the results describe very different systems:

                      case 1  case 2  case 3  case 4  case 5
system A (5 each)       4/5     4/5     4/5     4/5     4/5
system B (5 each)       5/5     5/5     5/5     5/5     0/5

System A has one varying result in every case. In these five observations, system B passes every trial for four cases and fails every trial for one case. Aggregating all 25 results turns both failure structures into 80%.

If the product permits automatic retry, A may sometimes recover. If B’s failed case represents a high-risk action, that blind spot may block release. The first step in evaluating a nondeterministic Agent is therefore not choosing a more elaborate overall score. It is preserving the three dimensions case × configuration × trial.

Aggregate Pass Rate erases the case distribution

One pass or failure is the outcome of one trial. Mixing cases, model configurations, and random samples in one denominator discards two questions at once:

  • Which cases contain the failures?
  • Does a case fail repeatedly across observations, or only occasionally?

System B’s overall average is not low, but case 5 has 0/5 success in this observation set. A release gate based only on overall Pass Rate can make that blind spot appear smaller simply by adding more easy cases.

The dashboard should therefore support drill-down from the aggregate into a per-case trial matrix. The aggregate is useful for trends, but it cannot replace the worst-case and failure-distribution views.

The minimum record is one Trial, not the final state of a Case

Each trial should preserve its own outcome and complete configuration identity:

{
  "case_id": "case_5",
  "dataset_version": "regression@18",
  "configuration": {
    "model": "model_alias_a",
    "prompt_version": "prompt@7",
    "tool_surface_version": "tools@12",
    "grader_version": "grader@4"
  },
  "trial_id": "trial_5_3",
  "seed": 103,
  "outcome": "task_failed",
  "failure_class": "task_failure",
  "failure_reason": "wrong_tool_selection"
}

case_id identifies the input and goal under evaluation. configuration fixes the system version being compared. trial_id identifies one execution under those conditions. Random seed, provider metadata, timeout, and concurrency should also be recorded, but they do not replace these three core grains.

If the case row is overwritten with a final state, fail → pass looks as though the problem disappeared; the data no longer shows that the system failed four times before one success. If every execution becomes a new case, the data no longer shows that they repeatedly tested the same capability.

Single-trial, Pass@k, and All-trials-pass answer different questions

The same set of trials can derive several metrics, but they are not different names for one metric.

Single-trial success

micro-averaged valid-trial success
= successful valid trials / all valid trials

This is the success frequency when selecting one execution from all valid trials. A and B are both 20/25 in the opening example. This micro average gives more weight to cases with more valid trials. When infrastructure-invalid trials leave different valid support across cases, report valid and invalid support per case and also report the macro average of per-case success, or first restore equal valid support before comparison.

Pass@k

Pass@k asks for the probability that at least one of k candidates succeeds when they are independently generated for the same case under a fixed configuration. In the HumanEval paper, each problem has n sampled candidates, c of them correct, and n ≥ k; the unbiased estimator is:

pass@k = 1 - C(n - c, k) / C(n, k)

When n - c < k, the estimate is 1. Compute it per case and then average over cases. Do not merge n and c from different cases into one calculation.

This metric measures the ability to generate multiple candidates and identify a successful one under a fixed configuration. The candidates are typically sampled from the system-under-test model under that configuration; the verifier or selector may be a deterministic test program, another model grader, or a human. The Eval manifest must record its implementation type and version rather than hiding the actual decision-maker behind “a selector.” Pass@k approximates product experience only when the samples meet the evaluation assumptions, the product can safely generate k candidates, and the real verifier or selector is aligned with the grader. If production uses only heuristic ranking, separately evaluate Task success after that real selector. An adaptive repair or retry that changes the prompt, state, or Tool result should be evaluated as a complete retry policy at the Task-outcome grain. A high Pass@3 does not authorize blind repetition of file writes, payments, or messages.

All-trials-pass

cases whose every trial passed / evaluated cases

This metric emphasizes consistency within a finite observation set. No case in A reaches 5/5, while four cases in B do. It is highly sensitive to small amounts of variation, so reports must include the number of trials per case. Results from two trials and fifty trials are not directly comparable.

Single-trial success, Pass@k, and all-trials-pass answer, respectively, single-execution reliability, coverage across candidate samples, and whether every observed trial passed. Which metric belongs in a gate depends on how the product actually executes.

Infrastructure-invalid trials need a separate denominator

Before labeling a trial infrastructure_invalid, define the system-under-test (SUT) boundary and the failure owner. A trial is infrastructure invalid only when an evaluation-owned fixture fails to start, test data is corrupt, or the grader or harness crashes before producing a valid observation of the declared SUT. If the provider, Runtime, or network belongs to the product execution path, an undelivered request or network interruption is a valid timeout or system failure and must remain in the valid denominator. Recording evaluation-side failure as model failure conflates the SUT with evaluation infrastructure; silently removing product-path failure inflates the success rate.

A complete report retains both:

scheduled trials        100
valid trials             92
infrastructure invalid    8
task successes           74 / 92 valid trials

This yields valid-trial success and infrastructure-invalid rate separately. The first describes task behavior among valid executions. The second says whether the experiment can support a conclusion.

If one configuration’s invalid rate rises materially, the remaining valid samples are not enough to declare a quality improvement. First determine whether invalidity is causally related to the configuration—for example, a new Tool Surface may be incompatible with the harness. While the failure owner remains unresolved, report those trials separately and mark the comparison inconclusive instead of first removing them from the denominator or automatically blaming the model.

Failure Distribution separates blind spots from variation

Pass or fail says whether the result met the criterion. Failure taxonomy says where to investigate. Keep a stable, low-cardinality failure_class separate from a more specific failure_reason. An entry-level taxonomy can begin with coarse classes:

Failure classExamplePrimary investigation
task_failureIncorrect final answer, missing Artifactmodel, prompt, Tool behavior
policy_violationInvoked a prohibited Toolsurface, authorization, grader
timeoutDid not complete before the deadlinelatency, retry, budget, downstream dependency
infrastructure_invalidFixture failed to start, harness crashedEval infrastructure

Then return to the per-case matrix:

  • A case that fails under every configuration may expose a dataset or grader-definition problem.
  • If only one configuration fails every observed trial for the same case, it looks more like a fixed capability regression.
  • Different timeouts appearing randomly across cases look more like global flakiness or a provider or Runtime issue.
  • If one case moves from failure_class = task_failure to failure_class = timeout, or its failure_reason moves from wrong_answer to deadline_exceeded, the overall pass rate may still decline while the repair direction has changed.

An entry article does not need a taxonomy for every domain error. It needs the raw trial, a stable failure class, and an evolvable reason so later analysis can drill into Tool, grader, provider, or Runtime ownership instead of retaining only a boolean.

A Release Gate should follow product retry and error cost

No single metric fits every Agent product.

If the product produces one answer, single-trial reliability and the worst cases matter more. If it may safely sample three side-effect-free code candidates, Pass@3 may map directly to the experience. If the action is high risk and cannot be retried automatically, one policy violation may be a hard failure even when the aggregate Pass Rate is high.

A gate should therefore specify at least:

  • How many trials run per case and why that support is sufficient for the decision.
  • How many retries or candidate samples the real product permits.
  • Which failures are recoverable and which must never occur.
  • Whether the metric aggregates by trial, case, or Task outcome.
  • At which infrastructure-invalid threshold the experiment becomes incomparable.

More trials reduce the influence of an accidental sample. They do not fix dataset coverage. Running five cases one hundred times each still describes only those five cases.

Back to the problem

Systems A and B both report 80% only because the aggregate collapses case and trial into one denominator.

After preserving case × configuration × trial, A shows broad coverage with variation in every case. In these five observations, B shows four all-pass cases and one all-fail case. Combined with whether the product permits retry, whether failure has side effects, and the infrastructure-invalid rate, the team can decide whether to address flakiness, repair a fixed blind spot, or reject the experiment’s conclusion.

Nondeterministic evaluation is not about collecting more metrics. It is about ensuring that every metric still answers one explicit product question.
