Agent 45: Automatable Does Not Mean Worth Automating

Evaluate end-to-end benefit, human review, failure handling, Tool Coverage, verifiability, and risk cost together to estimate the real Automation Ceiling.

07/29/2026 Views
Agent DiscoveryAgentEvaluationCost

The problem

In an offline Eval, a refund Agent gives a policy-compliant text answer for 80% of cases. The Eval ends at the answer; it neither executes a refund nor verifies external results. The team nevertheless estimates that if support handles one hundred refund requests per day, the Agent can replace eighty manual tasks.

The Pilot tells a different story. Support agents recheck every policy judgment. Some logistics data is unavailable to the Agent. A small set of failures is concentrated in high-value orders. After a Tool timeout, a person must determine whether the refund was already created. The model returns an answer quickly, but end-to-end resolution does not improve materially.

“Eighty percent of cases produced a correct answer” describes model behavior under test conditions. It does not say how many business tasks completed, and it excludes review, failure, and risk-handling cost.

Determining whether an Agent Use Case is worth building requires putting automatable capability back into the full task system.

Value is measured at the Task, not the model call

A model call may summarize, select a Tool, apply policy, or propose a next step. Business value usually appears at the end of a longer chain:

request enters
→ evidence is collected
→ judgment is made
→ action is executed
→ external result is awaited
→ completion is verified

Improving one short step does not automatically improve the end-to-end outcome.

In a hypothetical example, drafting a disposition takes two minutes while approval takes two hours. Reducing the first to ten seconds leaves the customer-visible cycle controlled by approval. If support agents instead spend substantial time collecting data across systems and the Agent can perform that step reliably, the Agent may create real value even if a human still approves the result.

The numerator and denominator of ROI must therefore use the same Task boundary. A team cannot claim the labor cost of the whole task as potential benefit while using one model call’s success rate as proof of capability.

Benefit and new cost belong in the same ledger

An Agent may:

  • reduce manual operation time;
  • shorten waits and handoffs;
  • reduce omission and inconsistency;
  • expand service coverage;
  • reserve scarce experts for exceptions;
  • enable a capability that could not previously scale.

It also adds:

  • model, Runtime, and Tool cost;
  • human confirmation and sampled review;
  • Clarification and exception takeover;
  • data integration, authorization, and audit work;
  • error recovery and customer remediation;
  • Eval, monitoring, and ongoing maintenance.

A directional net-value model is:

net value
= labor and cycle-time savings
+ quality improvement and new capability
- review and takeover cost
- system build and operating cost
- expected failure loss

Discovery does not need to invent precise numbers. It needs to establish whether each term exists, which evidence can estimate it, and which assumption would most likely reverse the conclusion.

If every draft requires line-by-line review, review time may consume the generation benefit. If an incorrect refund is detected quickly and can be reversed, expected risk may be lower than for an irreversible action. Cost must follow task facts rather than a generic “Agent risk” score.

Tool Coverage limits actual task coverage

The model knowing what to do does not mean the system can do it.

Tool Coverage should examine the Agent’s capability across the task loop:

Capability layerQuestion to verify
ObserveCan it obtain the data required for completion?
InterpretDoes the data have clear semantics, provenance, and freshness?
ActDoes a bounded Tool exist?
AuthorizeDoes the current identity have the required permission?
VerifyCan the external state be observed again after action?
RecoverCan a timeout or partial failure be reconciled?

Without logistics state, the Agent may cover only unshipped goods. If it can create a draft but cannot confirm submission, Task completion must stop at draft state. If a write cannot be queried afterward, unknown outcome limits autonomous execution.

Tool Coverage is not the number of connected APIs. It is the share of real cases covered by the observe–act–verify chain required for the target Task.

Several constraints jointly define the Automation Ceiling

The practical Automation Ceiling can be understood as a conceptual product:

Automation Ceiling
≈ observable cases
× verifiable cases
× Tool-executable cases
× authorization-permitted cases
× exception-handled cases

This is not an instruction to multiply percentages mechanically. It is a reminder that any gap can remove a case from the automatable set.

Among otherwise routine refunds:

  • some lack required material;
  • some have no reliably available logistics state;
  • some exceed Agent authority;
  • some are policy exceptions without deterministic rules;
  • some Tool failures leave the result unknown.

A strong reasoning model still should not complete those cases automatically. A better target may be:

Complete cases automatically only when evidence is complete, policy is explicit, amount is low-risk, and the result is verifiable. For every other case, gather evidence and escalate.

Escalation is not necessarily failure. If a human receives complete context, verified evidence, and a clear conflict, the Agent has still reduced human work. “Automatically completed” and “usefully prepared for escalation” must be measured separately.

Risk depends on discoverability and recovery, not only error probability

Two Agent Use Cases with the same success rate may have different risk.

An omission in an internal meeting summary is usually discoverable and editable. An incorrect refund may lose money. Incorrectly closing a security incident may let risk continue to grow.

Failure cost should consider:

  • whether the error creates an external side effect;
  • whether the effect is reversible;
  • whether the next step can detect it automatically;
  • how long the error remains undiscovered;
  • whether an explicit owner can take over;
  • whether one failure and a batch failure have different impact.

A high-risk task may still use an Agent, but its autonomy should narrow. The Agent may collect evidence and create a draft for an authorized reviewer, or execute only low-value, reversible actions whose result can be verified immediately.

Risk control should change the Task Contract rather than appear as a vague “compliance risk” score at the end of an ROI table.

A Pilot should test the most fragile assumption

A Pilot should not demonstrate only selected successful cases. It should test the assumptions that determine ROI:

  • What share of real input satisfies automation conditions?
  • How much time does human review actually consume?
  • Where do Tool and data failures appear?
  • Does escalation give humans enough context?
  • Can completion be verified automatically?
  • Do users actually delegate the task to the Agent?
  • Does local savings change the end-to-end cycle?

A useful Pilot therefore narrows itself to:

  • one role and one Task;
  • a representative distribution of real cases;
  • a limited, auditable Tool surface;
  • low-risk or recoverable actions;
  • explicit human boundaries;
  • predefined continuation and exit conditions.

If the primary cost comes from approval wait that the Agent cannot change, stop or redefine the scope. Adding more model capability does not fix the value mechanism.

Back to the problem

The refund Agent’s offline policy-answer correctness is 80%, but the metric excludes execution and result verification. Review, data gaps, and high-risk exceptions then remove much of the end-to-end value during the Pilot.

At the Task grain, the team must measure automatic completion, useful escalation, human review, and failure recovery separately. Tool Coverage, verifiability, authorization, and exception distribution define the Automation Ceiling.

An Agent need not complete every case to create value, but every value class must occur in real work and must subtract the cost of trustworthy execution.

Automatable describes what the system may be able to do. Worth automating requires evidence that the business result improves after risk and human boundaries are included.
