Agent 43: A Task Map Must Include State, Decisions, and Exceptions

Move beyond sequential flowcharts to a map of tasks, state, decisions, evidence, and exceptions so an Agent knows when to continue, clarify, or escalate.

07/29/2026 Views
Agent DiscoveryAgentTask Modeling

The problem

The team reconstructs the refund workflow from real work:

query order
→ query payment
→ query logistics
→ check refund policy
→ create refund draft

The Agent receives three results: the order system says shipped, the logistics system says not collected, and the payment system says captured. The sequential workflow points next to “check refund policy,” but it does not say which state to trust or whether the conflict has removed the Agent’s authority to continue.

A flowchart expresses a stable path. An Agent operates in task state that changes after every observation. Requirements modeling must move from “what should be called next?” to “what is known now, and what does that evidence permit?”

A step cannot represent both an action and a state

“Query logistics” is an action, not a task state. It may return collected, not collected, order not found, service unavailable, or timeout. Every result can change the next step.

A traditional flow often collapses these differences into one box:

[query logistics] → [evaluate refund]

For an Agent, the fuller representation is:

action: query logistics
observation: not collected
evidence: shipment state returned by logistics system
conflict: order system says shipped
decision: current facts are insufficient to create a refund draft
next step: request confirmation from logistics or its human owner

This does not require a complete state machine in the requirements document. It requires separating the action, observation, and authorization consequence. Otherwise the model may treat “Tool call succeeded” as “business condition satisfied.”

Task State is the set of facts currently supported by evidence

Task state should not be only a coarse label such as processing or pending. To choose the next step, the Agent needs the facts currently supported by evidence, together with their sources and freshness.

A refund task may project state like:

order:
  status: shipped
  source: order-system
payment:
  status: captured
  source: payment-system
shipment:
  status: not_collected
  source: logistics-system
policy:
  revision: refund-policy@18
authority:
  max_refund_amount: 1000

This is a conceptual example, not a recommendation that every system use the same YAML. The point is that state must preserve enough provenance to support a decision rather than retaining only the model’s summary that “the order may have shipped.”

When two sources conflict, the task must not average away the difference in natural language. Requirements must state:

  • which system is the Source of Truth for the field;
  • whether normal propagation delay can explain the conflict;
  • whether another query may recover it;
  • which time or condition requires escalation;
  • which actions remain prohibited during conflict.

Source and freshness determine whether a fact can authorize the next action.

A decision point must bind evidence and an owner

A decision point contains at least:

Decision: what must be decided now
Evidence: which evidence may support it
Outcome: which next steps each result permits
Owner: who decides when the evidence is insufficient

“Is this refund eligible?” can then be decomposed:

DecisionEvidenceOutcomeOwner
Is the request within the refund window?Purchase time and policy revisionContinue or rejectPolicy/Workflow
Has the item actually shipped?Shipment state and trusted sourceContinue, wait, or escalateLogistics owner
Is the amount within authority?Refund amount and execution identityCreate draft or request approvalAuthorization system/supervisor
Is this a policy exception?Customer material and exception clausesPropose or escalateBusiness owner

Not every Decision belongs to the model. Deadline and amount thresholds fit deterministic rules. The model may propose a classification for open-text material. A policy exception still belongs to the business owner.

Requirements modeling is valuable because it separates these owners instead of assigning every judgment to “the Agent.”

Exceptions determine when the Agent loses authority to continue

The Happy Path shows how the Agent completes a task under ideal input. Exceptions define the autonomy boundary.

Start with four classes:

Information exceptions

A required field is missing, malformed, or ambiguous. The Agent may obtain new information through Clarification.

State exceptions

Systems return conflicting facts, or data exceeds its freshness limit. The Agent may query again or may need to wait for the true state owner.

Execution exceptions

A Tool times out, authorization is denied, or a dependency is unavailable. The next step depends on whether the action may already have produced an effect; retry is not universally safe.

Business exceptions

The current policy has no matching path, risk is too high, or an action is irreversible. The Agent should not treat further model reasoning as authority that did not already exist.

Each exception needs:

detect: how it becomes observable
recover: which recovery action is permitted
limit: how many attempts or how much time is allowed
prohibit: what must not happen meanwhile
escalate: who receives the task
handoff: which state and evidence accompany it

“Send to a human when uncertain” defines neither detection nor ownership. It lets the Agent choose arbitrarily between continuing and stopping.

Completion must be an observable state transition

The other end of the task map is completion. Completion cannot mean only that the model stopped generating or a Tool returned success.

If the refund Agent only creates a draft, completion may require:

refund_draft = created
draft_reference = queryable
evidence_bundle = complete
required_approval = identified

If it also confirms submission, completion requires a business record in the payment system. If it owns customer notification, the message must agree with the observed external state.

The minimal Task loop is therefore:

initial state
→ evidence-backed Decision
→ authorized Action
→ new external observation
→ Completion or Escalation

The path may change dynamically, but no step may lose evidence or ownership.

Walk the opening example through the same map

Return to the refund request with conflicting shipment state. The task map no longer says merely “continue to policy”:

  1. The Agent observes order, payment, and logistics sources.
  2. shipped in the order system conflicts with not_collected in logistics.
  3. The conflict state prohibits refund-draft creation.
  4. The Agent may query logistics once more after a bounded interval.
  5. If conflict remains, it escalates to the logistics owner with the order ID, shipment ID, both query results, and the policy revision.
  6. After human confirmation, the task continues from explicitly recorded task state and a handoff point. Whether the Runtime persists that state as a recoverable Checkpoint belongs to its recovery contract.

The model does not decide which system “looks more correct.” The task map gives recovery and decision authority to the boundary that owns the fact.

Back to the problem

The refund flow originally connected “query logistics” directly to “check policy.” When order and shipment state conflict, that edge cannot tell the Agent whether it still has authority to continue.

After the flow becomes a task, state, evidence, decision, and exception map, conflict is explicit: one bounded re-query is allowed, draft creation is prohibited, and unresolved conflict goes to the logistics owner.

A sequential flow answers what usually happens first and next. An Agent Task must also answer which facts are established, who owns the judgment, which action is authorized, and what ends autonomous execution.

Only the latter can become the shared input for Tools, authorization, Human-in-the-Loop, and Eval.
