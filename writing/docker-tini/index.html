Why Use Tini as a Docker Container Entrypoint?

01/16/2020 Views
DockerProcessLinuxTechNotes

The question

I often saw the following lines in Dockerfiles for Jupyter Notebook images:

ENTRYPOINT ["tini", "-g", "--"]
CMD ["start.sh"]

Curious about their purpose, I read the Tini documentation. It describes three benefits:

  1. It protects you from software that accidentally creates zombie processes, which can (over time!) starve your entire system for PIDs (and make it unusable).
  2. It ensures that the default signal handlers work for the software you run in your Docker image. For example, with Tini, SIGTERM properly terminates your process even if you didn’t explicitly install a signal handler for it.
  3. It does so completely transparently! Docker images that work without Tini will work with Tini without any changes.

The first two points are the essential ones: reaping zombie processes and forwarding signals. To understand them, it helps to review Linux processes and signals first.

Processes in Linux

A process is a running program and the basic unit to which resources are allocated. A process consists of its program and data together with a Process Control Block, represented in Linux by the task_struct structure.

The PCB includes:

  • Process identity
    • PID
    • UID
  • Control and management information
    • CPU, disk, and network usage
    • Current process state
  • Allocated resources
    • Open files
    • Memory regions
    • I/O devices
  • Register values

Process state is particularly important when discussing zombie processes.

Process states 1

/*
 * The task state array is a strange "bitmap" of
 * reasons to sleep. Thus "running" is zero, and
 * you can test for combinations of others with
 * simple bit tests.
 */
static const char * const task_state_array[] = {

	/* states in TASK_REPORT: */
	"R (running)",		/* 0x00 */
	"S (sleeping)",		/* 0x01 */
	"D (disk sleep)",	/* 0x02 */
	"T (stopped)",		/* 0x04 */
	"t (tracing stop)",	/* 0x08 */
	"X (dead)",		/* 0x10 */
	"Z (zombie)",		/* 0x20 */
	"P (parked)",		/* 0x40 */

	/* states beyond TASK_REPORT: */
	"I (idle)",		/* 0x80 */
};

1. R — running or runnable (on a run queue)

The process has all the resources it needs and is either running on a CPU or waiting for CPU time. Its task_struct is placed on the run queue of one CPU; a process can appear on at most one CPU’s run queue at a time.

Some systems distinguish Running from Ready, but Linux represents both as TASK_RUNNING.

2. S — interruptible sleep (waiting for an event)

The process is suspended while waiting for an event, such as a socket connection or a semaphore. Its task_struct is placed on the event’s wait queue. When the event occurs, an external interrupt or another process wakes one or more processes from that queue.

Most processes in a typical process list are in this state.

3. D — uninterruptible sleep (usually I/O)

While a process is performing certain operations in kernel mode, particularly I/O, Linux may protect it with TASK_UNINTERRUPTIBLE. Interrupting an interaction with a device at the wrong moment could leave that device in an inconsistent state. This state is normally brief and can be difficult to catch with ps.

4. T/t — stopped or traced

  • T: Sending SIGSTOP moves a process into TASK_STOPPED, unless it is currently in TASK_UNINTERRUPTIBLE. Like SIGKILL, SIGSTOP cannot be intercepted or replaced by a user-space signal handler. SIGCONT (kill -18) returns the process to TASK_RUNNING; kill -9 attempts to terminate it immediately.
  • t: A traced process is in the special TASK_TRACED state while paused for its tracer. A process stopped at a breakpoint in GDB is one example. At other times, the traced process remains in one of the regular states described above.

5. X — dead and about to be destroyed

Some processes do not retain a task_struct after exiting and therefore never become zombies. Examples include a detached thread or a child whose parent explicitly ignores SIGCHLD. Such a process enters EXIT_DEAD, after which the kernel immediately releases it. The state is so brief that ps will rarely observe it.

6. Z — zombie: terminated but not reaped by its parent

The process has exited, but its task_struct remains so that its exit code and accounting information are available to its parent. The parent can call one of the wait system calls, such as wait4 or waitid, to retrieve that information. The same call then releases the remaining process descriptor.

Two related situations arise when parents and children exit at different times:

  1. Zombie process. A process creates a child with fork. If the child exits and the parent never calls wait or waitpid, the child’s descriptor remains in the process table. The kernel sends the parent a signal when the child exits so that it can reap the child. A short-lived zombie is normal when the parent has not yet handled the notification. A persistent zombie indicates that the parent failed to reap it; terminating the parent or restarting the service will resolve it.
  2. Orphan process. If a parent exits while one or more children are still running, those children become orphans and are adopted by another process—often the next eligible subreaper or PID 1. Every process therefore has a parent at all times, except PID 1 itself, also known as the init process.

The first user-space process created when Linux boots is the init process. It has two main responsibilities:

  • Run system initialization and start other processes.
  • Wait for child processes to exit and call waitid to reap them.

The kernel protects the init process from normal suspension and termination. It waits for children in TASK_INTERRUPTIBLE and becomes TASK_RUNNING while reaping them.

Signals

A signal is one form of inter-process communication.2 One process asks the kernel to deliver a signal to another, and the recipient handles it at an appropriate point.

Processes can register handlers for signals they care about. Applications commonly handle SIGTERM so they can release resources and shut down gracefully. SIGKILL, by contrast, terminates a process immediately and cannot be handled. A well-behaved application should catch and process SIGTERM; SIGKILL should be the last resort. Other signals, such as SIGUSR1, are available for application-defined behavior.

Signals inside a container 3

Docker’s stop and kill commands can both send signals to a container.

The behavior of PID 1 is critical because Docker sends the container’s signal to that process.

docker stop first sends SIGTERM and waits for the application to shut down gracefully. If the application is still running after the timeout, Docker sends SIGKILL. docker kill sends SIGKILL by default, although its -s option can select another signal.

If PID 1 does not handle and forward signals correctly, the application is much more likely to be killed forcibly than to shut down gracefully. Which process becomes PID 1 depends largely on how ENTRYPOINT, CMD, and related instructions are written, so the distinction between their forms matters.4

Back to the question

With:

ENTRYPOINT ["tini", "-g", "--"]
CMD ["start.sh"]

the container starts tini as PID 1. Acting as init, it waits for exited children and reaps orphaned descendants that are reparented to it. We should avoid creating zombies in the first place, but we do not always control every program that runs inside a container.

With -g, Tini also forwards signals sent to the container to the child process group. This is one reason to prefer it over using a shell as init, even though a shell may be capable of reaping children in some situations.

If a container runs multiple processes, or runs a process that creates many children, using Tini is a simple and reliable safeguard against lingering zombie processes.

NOTE: If you are using Docker 1.13 or greater, Tini is included in Docker itself. This includes all versions of Docker CE. To enable Tini, just pass the —init flag to docker run.5
