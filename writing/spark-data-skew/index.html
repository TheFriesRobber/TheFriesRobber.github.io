Spark Data Skew — How to Identify, Diagnose, and Fix It

Data skew is not simply a slow job. It is an imbalance in how data is distributed across partitions. This article uses the Spark UI, key distributions, and execution plans to diagnose and address skew in joins and aggregations.

04/16/2020 Views
SparkBigdataPerformanceShuffle

The problem

Most tasks in a Spark job finish quickly, but the final few keep running. One executor continues to spill, spend time in GC, or even run out of memory. Adding executors, increasing memory, or raising the number of shuffle partitions does not solve the problem.

This is often data skew rather than a simple lack of cluster resources: the work is not distributed evenly across partitions, so a few tasks process far more data than the rest.

Data skew commonly appears when:

  • Operations such as join, groupBy, and reduceByKey repartition data by key.
  • Many null values, empty strings, placeholders, or abnormal keys land in the same partition.
  • A small number of popular users, products, or tenants account for most records.
  • A join that should be one-to-one becomes locally many-to-many and expands the data.

Distinguish skew from similar problems

Not every task straggler is caused by data skew.

Too few partitions

If all tasks are large and take a similar amount of time, the job may simply lack parallelism. Increasing the partition count to a reasonable level can help.

Uneven input files

If the imbalance appears during the input stage, a few files may be unusually large, unsplittable, or unevenly distributed in the source. This differs from skew created after a shuffle by key-based joins or aggregations.

A slow executor or node

If tasks with similar input sizes become slow only on a particular node, inspect the node, disk, network, and executor first. Data skew normally shows up as a large difference in input records or shuffle read volume, not merely as a difference in task placement.

Data skew

Suspect skew when most tasks in a stage finish quickly while a few tasks have an order of magnitude more input, shuffle read, spill, or records.

How to diagnose it

1. Find the skewed stage in the Spark UI

Look at the distribution of task metrics, not only their averages. Useful signals include:

  • Median and maximum task duration, together with the long tail.
  • Input Size / Records.
  • Shuffle Read Size / Records.
  • Shuffle Write Size / Records.
  • Memory Bytes Spilled and Disk Bytes Spilled.
  • GC Time, Peak Execution Memory, and retry counts.

If the maximum is far above the median, inspect the partition ID, executor, and input size of the slowest tasks. The important evidence is uneven work, not task duration alone.

2. Find the operator that creates the shuffle

For SQL and DataFrame jobs, inspect the execution plan:

df.explain("formatted")

Look for joins, aggregations, distinct operations, and windows around Exchange nodes. For RDD jobs, use toDebugString to inspect dependencies and focus on transformations such as join, groupByKey, reduceByKey, and repartition that may produce a shuffle.

3. Inspect the key distribution

Count suspicious keys and examine how much of the total volume belongs to the most frequent values:

import org.apache.spark.sql.functions._

df.groupBy($"key")
  .count()
  .orderBy(desc("count"))
  .limit(20)
  .show(false)

This diagnostic query also causes a shuffle. On a large dataset, begin with a sample or a limited time range. In addition to the top keys, inspect:

  • null, empty strings, and placeholder values.
  • Keys that violate business constraints.
  • The number of rows for the same key on both sides of a join.
  • Whether hot keys change with date, tenant, or traffic events.

If one key has m rows on one side of a join and n rows on the other, the result may contain m × n rows. Many cases described as join skew begin with an incorrect join grain or a violated uniqueness constraint.

A practical order for fixing skew

1. Correct the data semantics first

Do not begin with salting. First ask whether the hot key should exist at all.

  • Filter null or placeholder values if they should not participate in the join.
  • Restore the correct data model when different meanings have been collapsed into one default key.
  • Deduplicate or repair the upstream constraint when a dimension key should be unique.
  • Keep only the required rows and columns before the join to reduce shuffle volume.

These changes improve correctness as well as performance and are usually more fundamental than configuration tuning.

2. Broadcast a small join side

If one side of the join is small enough, broadcast it to the executors and avoid shuffling the large side by join key:

import org.apache.spark.sql.functions.broadcast

val result = facts.join(broadcast(dim), Seq("key"), "left")

The broadcast side must fit safely in executor memory. Do not force a broadcast of a dataset that is large in reality merely because its statistics are wrong.

3. Aggregate or prune before the join

If downstream logic only needs a summary by key, push eligible filters and aggregations before the join. Joining a billion detail rows and then reducing them to one million rows is often worse than aggregating first.

Confirm that the rewrite preserves semantics, especially for deduplication, non-equi joins, and many-to-many relationships.

4. Handle hot keys separately

When only a few known keys are skewed, split them into a separate branch:

val hotKeys = Seq("unknown", "anonymous")

val isHot = coalesce($"key".isin(hotKeys: _*), lit(false))
val hot = df.filter(isHot)
val normal = df.filter(not(isHot))

The normal data can keep the original plan. The hot-key branch can be filtered, aggregated separately, broadcast, or processed with a specialized join strategy according to its meaning. Compared with salting the entire dataset, this limits the scope of the change and makes validation easier.

5. Salt a skewed join

If hot keys on the large side must participate in the join and the other side is too large to broadcast in full, split each hot key into several salt buckets. Assign the large-side records to buckets using a stable field, and copy the corresponding small-side rows to every bucket. In the following example, hotFacts and hotDim are the hot-key branches already isolated from the fact and dimension tables:

import org.apache.spark.sql.functions._

val buckets = 16

val saltedFacts = hotFacts.withColumn(
  "salt",
  pmod(xxhash64($"event_id"), lit(buckets)).cast("int")
)

val expandedDim = hotDim.withColumn(
  "salt",
  explode(sequence(lit(0), lit(buckets - 1)))
)

val result = saltedFacts.join(expandedDim, Seq("key", "salt"))

More buckets are not always better. Salting duplicates the other join side and increases record count and scheduling overhead. Choose a bucket count based on the hot-key volume, target partition size, and executor parallelism, and apply it only to keys that are actually skewed.

6. Use two-stage aggregation

For aggregations that are associative and commutative, first aggregate by (key, salt), then remove the salt and aggregate again:

val partial = input
  .withColumn("salt", pmod(xxhash64($"event_id"), lit(16)))
  .groupBy($"key", $"salt")
  .agg(sum($"amount").as("partial_amount"))

val result = partial
  .groupBy($"key")
  .agg(sum($"partial_amount").as("amount"))

Operations such as sum, count, min, and max are straightforward to split. An avg requires carrying both sum and count. Exact distinct counts, quantiles, and order-dependent calculations cannot use the same rewrite without additional work.

7. Let AQE handle runtime skewed joins

For Spark SQL and DataFrame workloads that support Adaptive Query Execution, Spark can use runtime shuffle statistics to identify and split skewed partitions:

spark.sql.adaptive.enabled=true
spark.sql.adaptive.skewJoin.enabled=true
spark.sql.adaptive.skewJoin.skewedPartitionFactor
spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes

Defaults and applicable join strategies can change by version, so verify them against the deployed Spark version. AQE can mitigate runtime partition skew, but it cannot correct a bad join grain, abnormal keys, or data expansion. See Notes on Spark Adaptive Query Execution for more detail.

Why adding partitions is often insufficient

In a typical key-based hash shuffle, records with the same key enter the same partition. Even if the partition count grows from 200 to 2,000, a hot key that represents 30% of the data still lands in one partition.

Additional partitions make ordinary partitions smaller, but they do not split a single hot key. The median task may become faster while the slowest task barely changes, and the job may gain extra scheduling and small-file overhead.

How to validate the fix

Do not compare total job duration alone. At minimum, check whether:

  1. The gap between the maximum and median task duration, shuffle read, and spill has narrowed within the stage.
  2. The slowest task no longer holds the stage open for a long time.
  3. Salting or branch splitting has introduced unexpected data expansion.
  4. Row counts, aggregate values, and join semantics match the baseline.
  5. The approach remains stable across dates, tenants, and traffic peaks.

Performance work must not compromise correctness. Salting, pre-aggregation, and hot-key branches should all be reconciled against a repeatable dataset.

Back to the problem

The first step in fixing Spark data skew is not tuning a setting. It is identifying which stage, which shuffle boundary, and which keys create the imbalance.

A reliable sequence is:

  1. Use the Spark UI to establish that task workload is uneven at the partition level.
  2. Use the execution plan to find the join or aggregation that creates the skew.
  3. Inspect key distribution and business grain, correcting data problems first.
  4. Then choose among broadcast, pre-aggregation, hot-key branching, salting, and AQE.
  5. Validate both performance and result correctness.

Data skew is produced by the interaction between data distribution and computation boundaries. Once you understand why the data concentrates in a few partitions, you can choose a fix that does not merely move the complexity elsewhere.
