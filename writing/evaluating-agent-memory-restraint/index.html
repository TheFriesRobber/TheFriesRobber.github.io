Agent Memory 8: Memory Evaluation Needs More Than Recall

Evaluate whether Memory should be written, remains current, can be revoked, and stays within scope—not only whether it can be recalled.

07/14/2026 Views
AgentMemoryData Governance

The problem

In a synthetic test, Memory system A answers 92 of 100 historical questions correctly, while B answers 86. This is end-to-end question-answering accuracy, not Retrieval Recall. If the comparison stops at correct answers, A appears better.

The trace reveals three additional behaviors. A saves “use the short format this time” as a durable preference, keeps citing the old version after the user switches to a detailed format, and mentions a sensitive health record in an unrelated travel-planning response. B misses a few more questions because it writes more cautiously and filters by authorization, but it avoids these failures.

Retrieval Recall asks whether required Memory entered the top-k result. End-to-end accuracy also includes reading and reasoning. A durable Memory evaluation must ask more: should this content have been written, is it current now, may this Task use it, and does it stop influencing the system after a correction or deletion? Ignoring these stages rewards systems that store and retrieve everything.

Decompose one score across the lifecycle

A correct answer may depend on a Writer saving the right content, a Store maintaining versions correctly, Retrieval finding the current record, and Assembly using it under the current permissions and budget. A failure may originate at any of those layers. Collapsing them into end-to-end QA accuracy hides overcollection and provides no repair owner.

A more useful evaluation unit is scenario × system configuration × assertion checkpoint × trial. System configuration distinguishes A and B together with their model, prompt, and policy revisions. An assertion checkpoint binds the initial Memory snapshot, committed event sequence, and an explicit observation boundary. Lifecycle phase remains useful as a checkpoint classification, but cannot identify an observation by itself.

The same scenario should observe both the write and a future read:

PhaseCore questionExample metrics
WriteDoes the system write what it should and refrain when it should not?write precision, write recall, false-write rate
VersionDo corrections, expiry, and revocation update the canonical current view?stale-current-view rate, update latency
RetrieveDoes it recall current, authorized records?read recall, read precision, unauthorized-hit rate
AssembleDo retrieved records enter an appropriate Task?stale-exposure rate, unauthorized-exposure rate, irrelevant-exposure rate
OutcomeDoes Memory improve the Task without causing out-of-scope behavior?task success, harmful-memory influence rate

Metric names can vary, but denominators must be explicit. false_write_rate, for example, is the fraction of no-write trials that produce a durable record, not a fraction of all inputs. Old versions need three separate observations: stale_current_view_rate checks the canonical view, stale_exposure_rate checks the prompt, and stale_influence_rate checks whether the old version changed the output. Neither exposure nor influence proves that the canonical view failed because a stale index or cache might bypass a correct view.

“Do not remember” needs first-class cases

Many benchmarks provide a question and a history containing the answer, which naturally rewards maximum retention. Restraint requires explicit no-write and no-use cases:

  • “Use a table this time,” which applies only to the current Task;
  • a third-party email that claims to contain a durable user preference;
  • sensitive information mentioned casually but irrelevant to future Tasks;
  • an explicit correction to an old preference;
  • revocation or deletion of a stored record;
  • a similar fact that belongs to another user, workspace, or resource scope.

These cases test over-persistence of temporary instructions, source promotion, data minimization, freshness, editability, and isolation. LongMemEval includes knowledge updates and abstention among long-term conversational Memory abilities. A full lifecycle evaluation should extend this with write restraint, permission, and deletion propagation.

Layered metrics can change the conclusion drawn from one aggregate score

The opening test can be decomposed into one stateful scenario and two independent exposure cases:

S1.1 explicit durable preference: “Use a short format for every weekly report”
S1.2 current-only instruction:     “Use a short format this time”
S1.3 correction after S1.1:        “Use a detailed format from now on”
C4 authorized-but-irrelevant:      travel planning should not read this user's health record
C5 cross-scope unauthorized:       this user must not read a similar record from another workspace

A writes both S1.1 and S1.2, so a dataset that rewards only historical QA has more opportunities to find “short format.” In a lifecycle score, S1.2 is a false write. After S1.3 commits, the test separately checks whether the old record remains in the canonical view, enters the prompt, or affects the output. Permission may pass in C4, where relevance should reject the record. Permission or scope must reject C5 first. Even when neither changes the answer, prompt entry counts as irrelevant or unauthorized exposure. Waiting for output leakage is too late.

B may write only S1.1 and keep S1.2 in the current Run. S1.3 creates a new version and removes the old one from the current view. Relevance rejects C4, while permission rejects C5. Lower raw QA accuracy does not automatically make B better overall, but in this scenario B is more reliable under the fuller objective: write when appropriate, use when appropriate, and otherwise refrain.

This is not a new composite score. It expands the same synthetic observations against their denominators. Cross-scope cases such as C5 still need a separate safety gate and cannot be offset by higher QA accuracy.

Do not force every dimension into one opaque weighted score. First define the observation boundary and eligible denominator for the core metrics:

MetricNumerator / eligible denominatorBoundary and aggregation
write recallrequired records successfully written / all required recordsInspect the store after commit for each write trial
false-write rateno-write trials producing a durable record / all no-write trialsCount once per trial, not once per generated record
read Recall@krequired current records in top-k / required record set for that read trialFix k and macro-average across trials
stale-current-view rateupdate/delete trials whose canonical view still contains the old version / all committed update/delete trialsObserve after the canonical commit
stale-exposure rateeligible post-update read trials whose prompt contains the old version / all eligible post-update read trialsObserve at the Model Turn input boundary
unauthorized-exposure ratecross-scope trials whose prompt contains an unauthorized record / all cross-scope trialsObserve at Model Turn input; keep as a separate hard gate
irrelevant-exposure rateno-use trials whose prompt contains an authorized but irrelevant record / all no-use trialsReport separately from unauthorized exposure
propagation latencyelapsed time from correction/deletion commit until all affected instances of a named derived view are invalidatedReport current view, index, cache, and summary separately
task outcome deltasuccess with Memory minus success without Memory on the same caseFix snapshots and report the mean and distribution across trials

If a release needs a gate, require observed unauthorized exposure = 0 on the current suite while reporting the trial count and a confidence upper bound, and separately bound stale exposure. Compare read Recall@k and Task outcome only among configurations that pass those gates. Zero observed violations in a finite suite is not a claim of zero underlying risk, and it does not replace production monitoring or continued regression expansion.

Make each failure point to a repair layer

Evaluation is useful only when a result identifies an owner:

  • Missing a required write points to the extraction prompt, Writer Gate, or confirmation path.
  • Writing a no-write case points to capture policy, content origin, request actor, or retention.
  • Missing an existing current record points to candidate generation or reranking.
  • Using an old version points to current-view resolution, index lag, or cache invalidation.
  • Retrieving a record but omitting it from Context points to the Memory Budget or Assembly decision.
  • Exposing an irrelevant or unauthorized record points to permission, scope, or minimum-disclosure policy.

Repeat every checkpoint in a scenario under each fixed configuration. Model output and Tool selection can vary, so a single pass does not establish stability. Report trial count, model version, prompt version, Memory snapshot, committed event sequence, and policy revision to distinguish model variance from a system change.

Back to the problem

A’s 92 correct answers came from more aggressive storage and retrieval, while hiding persistence of temporary information, stale-version use, and sensitive-data exposure. B’s 86 is not automatically better. The synthetic comparison shows that neither end-to-end QA accuracy nor Retrieval Recall can represent durable Memory quality by itself.

Evaluate writing, versioning, retrieval, Assembly, and outcome across the lifecycle. Memory becomes more than an ever-growing history search box only when it recalls correct, current, authorized records when needed and remains restrained at every other time.
