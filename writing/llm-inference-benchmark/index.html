LLM Infra 03: How an Inference Benchmark Produces a Comparable Service Curve

Fix the workload distribution, arrival control, warm state, deployment manifest, and quality constraints to measure a service curve that capacity planning can consume.

07/29/2026 Views
LLM InfraInferenceBenchmarkReproducibility

The problem

Configuration B reports higher tokens/s than Configuration A. A closer look reveals that B uses shorter outputs and an already warm Prefix Cache, and counts only successful requests. Timed-out requests disappear from its latency distribution.

Both results are called a “100 QPS Benchmark,” but they are not measuring the same thing. QPS does not specify the arrival pattern, concurrency limit, input/output lengths, warm state, or quality requirements. Averaging only successful requests also removes the slowest group entirely.

The purpose of a Benchmark is not to produce a larger number. It is to answer a specific decision: under fixed constraints, how much workload can each deployment configuration deliver?

Write the decision before starting the load test

Different questions require different experiments:

  • To compare Runtimes, fix the model, quantization, parallelism, and workload.
  • To compare parallel strategies, fix total hardware, model, Runtime, and SLO.
  • To validate capacity, vary arrival rate and observe where SLO attainment declines.
  • To validate cold start, state whether every trial reloads the model and Cache.

If the experiment asks only “which one is faster,” a researcher can easily change the interpretation after seeing the result. A more robust approach records this before the run:

decision: choose_serving_configuration
hypothesis:
  candidate_b_increases_goodput_without_changing_quality
fixed:
  workload_fingerprint: wl_7fd2
  model_release: model-manifest-sha256:...
  hardware_pool: gpu-topology-a
  quality_gate: chat-contract-v3
changed:
  serving_engine_config: [candidate_a, candidate_b]
primary_metric:
  name: application_goodput_rps
feasibility_gate:
  good_request_fraction_gte: 0.95

This is a conceptual experiment contract. Before execution, it forces the experiment to state what is fixed, what changes, and what result would falsify the hypothesis.

Workload identity cannot be only QPS

The workload envelope from the previous article should enter the Benchmark directly rather than being replaced by a convenient set of generated requests. At minimum, fix:

  • input and output Token distributions and their correlation;
  • model, adapter, template, and feature distributions;
  • arrival process, burstiness, and concurrency limit;
  • streaming, deadlines, priority, and cancellation behavior;
  • warm/cold Cache state;
  • request count, duration, and random seeds.

The vLLM Benchmark CLI exposes request-rate, burstiness, and max-concurrency as separate parameters. NVIDIA AIPerf can likewise combine a Poisson request rate with a maximum concurrency. Request rate and concurrency are not the same control.

Two common load patterns answer different questions:

  • Open-loop load sends requests according to an external arrival process. New requests continue to arrive when service slows, exposing queues and overload.
  • Closed-loop load keeps concurrency fixed and sends another request only after one completes. Its sending rate falls as service slows, making it more suitable for observing response under a given concurrency.

Using closed-loop results to promise open-loop capacity lets the load generator perform backpressure on behalf of the service. Maximum throughput measured with an unlimited request rate also does not directly represent tail latency under production arrivals.

The deployment manifest determines what the result belongs to

Inference performance is not a property of bare model weights. A reproducible trial needs to record at least:

deployment_manifest:
  model:
    repository: example/model
    revision: immutable-commit
    tokenizer_revision: immutable-commit
    chat_template_digest: sha256:...
  runtime:
    engine: example-engine
    version: x.y.z
    quantization: bf16
    scheduler_config_digest: sha256:...
  placement:
    replicas: 1
    tensor_parallel: 2
    pipeline_parallel: 1
  hardware:
    gpu_model: example-gpu
    gpu_count: 2
    interconnect: local-high-bandwidth
  state:
    model_warm: true
    prefix_cache: cold

The same model name may resolve to different revisions. The Tokenizer, chat template, and generation defaults can also change the actual Token sequence. Runtime version, Kernel, driver, parallel topology, and scheduler configuration change the execution path.

Without a complete manifest, a result can be labeled only as one observation. It cannot be a stable input to the next capacity-planning cycle.

A Service Curve is not one peak value

Capacity planning does not need “maximum tokens/s.” It needs a service curve: under a fixed workload and deployment manifest, what latency, goodput, and failure outcomes does the system deliver as offered load or concurrency changes?

The following is a synthetic result structure, not measured data:

1.5 req/s1.43 req/s95.3%1,420 ms76 ms4.7%

Each request is jointly checked for TTFT ≤ 1,500 ms, TPOT ≤ 80 ms, completion, and quality before application goodput and good-request fraction are calculated. If the contract requires a good-request fraction of at least 95%, this synthetic curve supports only the conclusion that the feasible region extends to roughly 1.5 req/s. P95 values in the table help diagnose distributions; they cannot independently prove joint attainment. The example also does not establish that any real hardware has this capacity.

A Service Curve must retain full distributions and every attempted outcome. If it preserves only averages for successful requests, the overload region may look faster because its slowest requests already timed out, were rejected, or were cancelled.

Warm state, output length, and quality cannot become hidden variables

Three common biases create false improvements.

First, Cache state differs. Prefix Cache warmup can reduce repeated Prefill, but only for matching prefixes. Testing A warm and B cold, or the reverse, is not a fair comparison. Report cold, steady-state warm, and Cache-hit distributions separately.

Second, output lengths differ. If one candidate generates shorter text because of EOS, truncation, or changed generation defaults, both E2E latency and tokens/s change. The experiment must record requested and actual output lengths and explain why the output still satisfies the same quality constraint.

Third, failed samples are filtered out. Every request should retain arrival, first Token, completion or cancellation, Token count, and reason code. Aggregate tables must be derived from complete raw results rather than serving as the only evidence.

Stochastic decoding also requires fixed or recorded sampling configuration, random seeds, and trial repetition. The quality gate comes before the performance conclusion: if the output protocol or capability changed, the faster result cannot be called an equivalent optimization.

Deliver evidence that capacity planning can consume

A Benchmark suitable for capacity planning delivers at least four kinds of artifact:

  1. experiment-contract.yaml: the question, hypothesis, fixed factors, and changed factors.
  2. workload-envelope.yaml: lengths, arrivals, deadlines, and random seeds.
  3. deployment-manifest.yaml: model, Runtime, configuration, hardware, and warm state.
  4. raw-results.* plus derivation scripts: per-request timestamps, Tokens, outcomes, and trial identity.

Record warmup, number of trials, and environmental noise as well. Without repeated experiments and uncertainty estimates, one observation may be reported, but a small difference should not be interpreted as a stable improvement.

Back to the problem

Configuration B’s higher tokens/s still does not support the claim that “B is better.” It changed output length and Cache state and removed timed-out requests, changing the workload, state, and result denominator at the same time.

A valid rerun fixes the experiment contract, workload envelope, deployment manifest, and quality gate; uses the same arrival control; and preserves every raw outcome. Its final deliverable is not one peak value but a service curve showing how goodput, TTFT, TPOT, and failures change with offered load.

The next article can consume this curve for capacity planning. If the workload or manifest changes, the curve must be invalidated and measured again.
