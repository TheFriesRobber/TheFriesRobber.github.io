Agent Sandbox 2: Why a Runtime Provider Is Not Enough

Use a lost Runtime-creation response to separate the responsibilities of the Agent Control Plane and the underlying Runtime Provider.

07/14/2026 Views
AgentSandboxDistributed Systems

The problem

The Agent system asks a Runtime Provider—an underlying platform such as Kubernetes or a cloud service that creates and stops workloads—to create a Runtime. The Provider creates the workload, but its response is lost and the caller sees only a timeout.

Immediately retrying createRuntime() may create a duplicate. Treating the timeout as failure may leave an orphan that keeps running, costing money, and holding network access. Even a Provider that deduplicates by request token can answer only whether physical creation was repeated. It does not know:

  • which Agent Session owns the Runtime and which Workspace it should mount;
  • whether this Runtime generation still has execution authority and whether its environment can execute Tools;
  • whether ending the Session should reclaim it.

Creating infrastructure does not make the Provider the owner of Agent business state. The Agent system still needs its own Sandbox Scheduler, treated in this article as the business Control Plane.

The Provider owns physical resources; the Control Plane owns business intent

In the table below, a generation is one Runtime incarnation of a logical Sandbox. A Lease grants time-bounded execution authority to the current generation. The Ready Contract is the combined set of Runtime, Workspace, Lease, and environment conditions that must hold before the Sandbox becomes usable.

QuestionRuntime ProviderSandbox Control Plane
create, query, and stop workloadownerissues intent and records result
Provider resource ID, region, templateownerstores reference
Session, user, and tenant identitymust not inferowner

The Provider API supplies mechanism. The Control Plane owns policy and intent: it records the Sandbox a Session wants and normalizes different Provider semantics into one business contract.

This does not mean rebuilding Kubernetes or cloud scheduling. Node placement, image pulls, and container restarts remain Provider mechanisms. The Control Plane retains only the state that a Provider cannot decide for the Agent application.

Session identity is independent of Provider resources

One Session may use several Runtimes:

session_12
  desired sandbox profile: code-agent.v4
  workspace: workspace_7
  current generation: 42

generation 41 → provider resource workload_a → expired
generation 42 → provider resource workload_b → ready

If workload_a is the Sandbox identity, replacement appears to create an unrelated Sandbox and loses Session continuity. If the Session ID is the only physical resource ID, a replacement, blue-green upgrade, or orphan recovery cannot observe multiple candidate workloads.

The Control Plane stores logical identity and physical bindings while declaring which generation is current. A Provider resource is observed state, not the business owner.

Desired State and Observed State are not one Status

The central record distinguishes intent from observation:

{
  "sandbox_id": "sandbox_session_12",
  "spec": {
    "desired_state": "active",
    "runtime_profile": "code-agent.v4",
    "workspace_id": "workspace_7"
  },
  "status": {
    "phase": "provisioning",
    "generation": 42,
    "provider_ref": "workload_b",
    "conditions": {
      "runtime_reachable": true,
      "filesystem_writable": false,
      "lease_fresh": true
    }
  }
}

desired_state=active expresses business intent; phase=provisioning expresses observation. Temporary disagreement is normal and drives reconciliation. A stop request may commit desired_state=stopped before Provider deletion finishes.

A single status=running loses direction: the system cannot tell whether to repair, wait for, or terminate the resource.

After a create timeout, enter Unknown and reconcile

Before calling the Provider, persist the logical Sandbox identity and a stable operation identity. The operation_key below represents this logical create action: it remains stable across physical retries of the same action, while one Provider call is an Attempt.

sandbox=sandbox_session_12
generation=42
provider_operation=create
operation_key=sandbox_session_12:42
state=dispatched

A timeout does not prove absence. Mark the physical operation unknown, then recover through Provider capabilities:

  1. Query by operation_key or labels.
  2. Claim one matching workload and persist its provider_ref.
  3. If several match, retain one allowed by policy, then isolate and clean up the rest.
  4. Retry with the same operation identity only after confirming absence and while the deduplication boundary remains valid.
  5. If no safe conclusion is possible, remain in reconciliation or manual repair rather than inventing a new identity.

Idempotent create, lookup by external key, and conditional delete make this safer. The Control Plane still decides whether a resource should be claimed and whether it matches current Session intent.

Ready is a Control Plane commit condition

Provider Running or created does not imply Agent Ready. The Control Plane combines:

  • a Provider resource bound to the current generation;
  • the correct Workspace mount identity;
  • completed Runtime Contract initialization;
  • sufficient Lease headroom;
  • no unacceptable build, policy, or network drift.

Acquire returns an endpoint only while these conditions hold together. Ready also expires: Leases lapse, builds drift, and probes fail. The Control Plane refreshes the Ready Contract or removes the Sandbox from the allocatable set.

Acquire, Refresh, Release, and Expire are business operations

OperationControl Plane meaning
Acquirefind or create a Runtime satisfying the Session Contract and return its current generation
Refreshrenew Lease and revalidate Ready Contract without changing logical Session
Releasesurrender execution authority, then keep warm, return to pool, or stop under policy
Expirereject allocation after Lease or Ready Contract expiry and trigger convergence

Release need not immediately delete the workload. A warm Runtime may reduce future latency, but it should not retain expired execution authority. Business Lease, Workspace access, and physical-resource lifecycle remain separate.

Reconciliation needs stable lookup and conditional writes

load desired + last observed state
        ↓
query provider / storage / lease facts
        ↓
compute one safe next action
        ↓
commit with expected generation/version

The last step must be conditional. If desired state became stopped after a query, an old reconciliation result cannot publish Ready. Generation, resource version, or compare-and-swap rejects that late result.

Kubernetes controllers use the same desired-state, current-state, and control-loop model. An Agent Control Plane adopts the convergence pattern; it does not require every system to implement a Kubernetes CRD.

A Provider adapter normalizes capabilities without hiding differences

An interface limited to:

create()
get()
delete()

hides recovery-critical differences: idempotency keys, label lookup, eventual consistency, asynchronous stop, Volume availability, and readiness probes.

A safer adapter explicitly declares those capabilities and translates raw Provider state into Control Plane observations. When a capability is missing, the Control Plane chooses a conservative path instead of pretending all Providers offer the same guarantees.

Back to the problem

After a Runtime-create timeout, the platform owns the workload’s physical facts. It cannot decide whether that resource still matches current Agent Session intent.

The Sandbox Control Plane persists Session identity, desired state, generation, and operation identity before the call. It queries, claims, or cleans up uncertain resources, publishes Ready only after the Session Contract holds, and later drives Release when users stop or Leases expire.

The Provider creates resources. The Control Plane proves that this resource may represent this Session now. Both are necessary, but they cannot co-own the same semantic decision.
