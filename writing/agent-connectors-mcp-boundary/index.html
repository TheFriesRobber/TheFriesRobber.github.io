How Connectors, MCP, and the Host Control Plane Divide Responsibility

Separate the Connector credential boundary, the MCP protocol, and the host control plane to identify who owns capability discovery, versioning, health, and authorization.

07/24/2026 Views
Agent StateAgentMCPSecurity

The problem

An MCP server upgrades its search Tool from v1 to v2, adding a required workspace_id field to the Schema. Some Runtimes reconnect and discover v2, while others continue using a cached v1 definition. At the same time, the user revokes authorization for the external account, but an old worker still holds a token that has not yet been cleared.

A static endpoint list can say only where a connection might go. A token can serve only as a credential for a particular access. Neither answers whether the current protocol version is compatible, which Tool definition may be exposed to which tenant, whether the token remains valid, or where traffic should be routed during a failure.

Three boundaries must cooperate: the MCP protocol owns version and capability exchange within a connection; the Connector owns external-account and credential lifecycles; and a host-built control plane owns fleet-wide desired versions, observed health, tenant visibility, and routing.

What the MCP protocol provides—and what it does not

Using the MCP 2025-11-25 specification as the version boundary, the client and server negotiate the protocol version and capabilities during initialization. A server can expose Tools, and the client obtains the currently visible definitions through tools/list. The relevant capability can also declare support for Tool-list change notifications.

For HTTP transports, the MCP authorization specification defines OAuth-based protected-resource discovery and requires tokens to be bound to the target resource. Authorization is optional, and the stdio transport has a different credential-acquisition boundary.

These are protocol contracts. They do not automatically provide:

  • the desired rollout version for a multi-instance server fleet;
  • long-term health evaluation across connections;
  • tenant-to-server-instance routing policy;
  • Schema compatibility gates and quarantine;
  • the full lifecycle of an external SaaS refresh token;
  • the final set of Tools exposed to the Runtime in this Turn.

Calling all of this an “MCP control plane” conflates a protocol with the host architecture.

A Connector is the credential and external-subject boundary

A Connector maintains a controlled mapping between an internal user or tenant and an external account:

internal subject + tenant
→ connection record
→ external account reference
→ credential reference
→ allowed audience/scope

The model may propose business arguments. It cannot read the access token, select a trusted tenant, or forward the credential to another server. At call time, the Connector or credential broker resolves the credential reference, checks expiry, revocation, audience, and scope, and uses short-lived credentials where possible.

A token received by an MCP server should be intended only for that MCP resource. The current MCP authorization specification explicitly prohibits an MCP server from passing through the token supplied by the client to a downstream API. If the server calls a third-party service, it should use a separate token intended for that service. This avoids turning token passthrough into a confused-deputy path.

A Connector is not a Tool, either. A Connector manages connections and credentials; a Tool definition is a model-visible API. One Connector can provide several Tools, and the same Tool may be implemented by different routes.

Capability discovery is only an observed fact

tools/list returns the Tool set declared by the server for this connection under the current authorization. That set cannot automatically become the model’s Tool surface:

observed tools
→ protocol/schema validation
→ compatibility check
→ tenant and capability authorization
→ host policy selection
→ per-turn Tool surface

The host needs to retain the definition fingerprint, server identity, negotiated protocol version, and discovery time. If the v2 Schema is incompatible with the current Runtime adapter, the correct result is an unavailable route or continued use of an explicitly compatible v1—not random exposure of the new definition to a subset of Model Turns.

Even when a server sends a Tool-list-changed notification, the host should treat it as a rediscovery signal rather than immediately mutate an in-progress Turn. The active Turn continues to use its own configuration snapshot; the next Turn can consume the newly validated surface.

The control plane owns desired/observed state and routing

The following is a proposed host control plane, not a requirement of the MCP specification:

register desired server/version
→ establish connection and negotiate protocol
→ discover capabilities
→ validate schema/compatibility
→ observe health and authorization state
→ promote route or quarantine
→ publish resolved capability revision

A route record might contain:

server: search-service
desired_release: v2
observed_protocol: "2025-11-25"
toolset_fingerprint: sha256:...
compatibility: incompatible_with_runtime_v7
health: reachable
route_state: quarantined

reachable does not mean compatible or authorized. A health probe proves only that some class of request receives a response. Routing also requires the Tool definition, tenant visibility, credential state, and Runtime contract to hold.

After a timeout, the control plane also cannot assert that the call did not execute. The Tool Execution still records unknown, query, and retry state according to its own effect contract. Route health consumes only this observation; it cannot overwrite the business outcome.

A Schema upgrade and token revocation are separate state chains

Handle the two parts of the opening example independently:

Schema breaking change

v2 discovered
→ fingerprint differs
→ required workspace_id unsupported by Runtime v7
→ v2 quarantined for v7
→ compatible clients may canary; others retain v1 route

Whether v1 fallback is allowed depends on semantic compatibility and security policy. If v1 has been revoked or omits a required authorization field, the host should disable the capability rather than fall back for availability.

Token revocation

connection revoked
→ credential record becomes inactive
→ new lookup denied
→ affected routes no longer authorized
→ in-flight result handled by Tool effect contract

Clearing the local token cache is not the only action. Routes and capability surfaces also need to consume the connection revision. An external request already in flight may still complete; revocation does not prove that its effect never occurred.

Walk one external Tool Call end to end

A call can pass through:

Model proposes Tool arguments
→ Runtime validates against snapshotted Tool definition
→ trusted identity resolves tenant + connection_ref
→ control plane resolves compatible authorized route
→ credential broker returns audience-bound credential
→ MCP client invokes server
→ server validates token and arguments
→ Runtime normalizes result/effect evidence
→ audit links subject, actor, route, tool revision, Attempt

Each failure preserves its own owner. Model arguments cannot override the connection identity. An MCP response cannot decide external business authorization on behalf of the backend. Control-plane route health cannot declare business success on behalf of the Tool contract.

Back to the problem

The v2 server in the opening example is reachable, but the current Runtime does not support its new required field. The control plane should therefore quarantine that route until a compatible adapter and Tool contract are ready. After the user revokes the connection, the Connector invalidates the credential reference, and subsequent Turns stop exposing capabilities that depend on it.

MCP initialization, capability discovery, and HTTP authorization provide connection-level protocol facts. The Connector provides external-account and credential facts. Only the host control plane converges the desired version, observed compatibility, tenant policy, and health into a consumable route.
