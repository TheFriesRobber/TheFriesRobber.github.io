Agent 14: How to Revise a Plan Safely When Its Assumptions Change

Model a Plan as a revisable Artifact with revisions, dependencies, assumptions, and evidence lineage—not as an execution state machine.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentPlanningArtifacts

The problem

An Agent’s plan assumes that the target API supports batch writes, so it creates three steps: prepare a batch payload, invoke the batch endpoint, and verify the result. During execution, the Agent reads new documentation stating that the API supports only individual writes, but all three steps still show ready.

If the model is simply asked to “make another plan,” the old plan items, evidence already collected, and work in progress lose their relationships. Continuing with the old plan causes repeated failure under an invalid assumption. The Plan needs revision, but it must not impersonate Runtime execution state.

A Plan describes commitments; it does not own execution facts

A Plan item states what the system intends to complete in service of a goal. It may refer to a Child Run, Job, or Tool operation, but each execution primitive owns its own started state, Attempts, outcomes, and cancellation.

Marking a Plan item directly as running/succeeded easily mixes two kinds of fact:

  • the Plan revision says whether the current commitment remains valid;
  • the execution owner says what work actually occurred.

An execution result may become Plan evidence. A Plan must not overwrite Tool or Job history. That separation keeps replanning from deleting side effects that have already occurred.

A minimal Plan Artifact needs a revision

A revisable Plan contains at least:

plan_id
revision
goal
items
dependencies
assumptions
evidence references
supersedes

Each item should also express commitment states such as ready, blocked, stale, or done. Here, done means that the evidence required by the goal is satisfied, not that a particular handler promise returned.

A revision tells every reader exactly which version it sees. Editing item text in place leaves an executing Child Run unable to determine which proposal it implements and prevents audit from explaining why the plan changed.

The model can propose only a new revision. A trusted Plan owner validates evidence, policy, and expected_revision, then atomically switches the active revision with compare-and-swap (CAS). If a user edit and a background replan both start from revision 1, only one proposal may commit. The other must read the new active revision and recompute. Execution objects and result consumers remain bound to plan_id + revision + item_id.

Invalid assumptions propagate through dependencies

The opening plan can be represented as:

assumption A: bulk API is supported
item 1: build bulk payload      depends on A
item 2: call bulk API           depends on item 1
item 3: verify all writes       depends on item 2

When the new documentation invalidates A, not all existing evidence must be discarded. The collected record list remains valid. The organization of the batch payload may not. The verification goal remains valid, but its input dependencies must be rebuilt.

After validating expected_revision=1, the Plan owner commits revision 2:

  • mark A invalid and reference the new documentation;
  • mark items 1 and 2 stale;
  • add “write each record with an operation key”;
  • make item 3 depend on terminal evidence from all individual writes;
  • retain references to reusable input evidence.

This is safer than generating an unrelated new plan because the reason for the change and all still-valid evidence remain traceable.

A replan must say what changed

An inspectable replan answers at least:

  1. Which new evidence invalidated which assumption?
  2. Which dependencies made items stale or blocked?
  3. Which evidence remains valid?
  4. Which started executions should be cancelled, awaited, or allowed to continue?
  5. When does the new revision become the active Plan?

A Plan revision cannot cancel external work automatically. If an old item already created a Child Run, the real execution owner still handles cancellation and effect reconciliation. The Plan changes only whether that work still serves the current commitment.

A Plan may produce a Delegation proposal

A ready item may become a delegation proposal, but it does not decide whether execution should use a SubAgent, background Job, or durable Workflow. The execution primitive depends on who owns completion, lifecycle, isolation, and recovery.

This also means that a simple task with no explicit Plan can still delegate, while a task with a Plan does not need to make every item a Child Run. The Plan owns dependencies and commitments. Delegation chooses the execution owner.

Back to the problem

After discovering that the batch API is unsupported, a safe revision neither erases the old plan nor keeps retrying its old steps. The Plan owner should:

  1. invalidate the old assumption with the new evidence;
  2. propagate stale or blocked state through dependencies;
  3. preserve input and verification evidence that remains valid;
  4. create a new Plan revision;
  5. let each execution owner independently cancel or converge work already started.

A Plan is therefore a versioned, revisable Artifact. It tells readers and the system why the current commitment has this form without falsifying execution facts that already occurred.
