Capability Integration 5: A File Is More Than a Message Attachment

Follow one PDF through upload, derivation, editing, and download to separate Blob, Artifact, Workspace Path, and Message Reference.

07/15/2026 Views
AgentFilesInfrastructure

The problem

A user uploads requirements.pdf on a phone and asks an Agent to turn it into a project plan. The Agent extracts text, edits plan.md several times in a Workspace, and generates plan.pdf. The next day, the user continues on a computer. A week later, the original upload message is deleted.

If the system stores only a Message Attachment record and download URL, message deletion raises questions that the Attachment cannot answer:

  • Who retains the original PDF, extracted text, working draft, and final report?
  • Should the computer open the latest Workspace draft or a version once shown in a Message?
  • When a download link expires or the user deletes the source, which content is actually deleted?

Longer URL expiry does not solve this. A Message Attachment can say how the current Message points to a file. If it also carries content, business identity, working path, and access entry, the other objects lose their owners when the Message lifecycle ends.

One file lineage contains five objects

Upload upload_17
  └─ Blob sha256:ab...                 original PDF bytes
       └─ Artifact artifact_source_17  requirements.pdf v1
            ├─ Artifact artifact_text_18  extracted.txt v1
            └─ Workspace Path /project/plan.md
                 └─ Artifact artifact_report_25  plan.pdf v3

Message message_8 ──references──> artifact_source_17
Message message_21 ─references──> artifact_report_25

Several may share one table, but not one meaning. Deleting message_8 directly removes only its reference to artifact_source_17. Artifact, Blob, and derived-output deletion still follow their own owners and retention.

A Blob stores bytes; an Artifact stores business identity

A Blob is a good immutable-content object. A content digest supports deduplication and integrity checks:

{
  "blob_id": "sha256:ab12...",
  "size": 284193,
  "media_type": "application/pdf"
}

Equal bytes are not necessarily the same business object. Alice and Bob may upload the same template for different purposes. Their Artifacts may share physical bytes but require separate identity, authorization, and retention.

{
  "artifact_id": "artifact_source_17",
  "owner": {"type": "user", "id": "user_7"},
  "kind": "source_document",
  "version": 1,
  "blob_ref": "sha256:ab12...",
  "created_from": {"upload_id": "upload_17"}
}

Content-addressed identity proves whether bytes match. It cannot prove who owns them, why they exist, or who may read them. Policy and business lifecycle bind to the Artifact.

A Workspace Path is a mutable working name, not a version identity

/project/plan.md gives Tools a stable path for repeated reads and writes. It means “what this name points to now,” not an immutable history.

/project/plan.md → workspace_file_9 revision 1 → blob sha256:c1...

After editing:

/project/plan.md → workspace_file_9 revision 2 → blob sha256:d8...

If the user asks to export yesterday’s version, a path alone cannot identify those bytes. The Workspace owner needs revisions, content references, and concurrency conditions. When a revision becomes an input, checkpoint, approval object, or deliverable, it should be promoted to a stable Artifact.

Not every keystroke needs an Artifact. Workspace revisions support frequent internal saves; important boundaries receive Artifact identity. This avoids both an uncontrolled version archive and a deliverable that exists only at a mutable path.

Derivation records input versions and the generator

extracted.txt and plan.pdf did not appear spontaneously:

{
  "artifact_id": "artifact_report_25",
  "kind": "report",
  "version": 3,
  "blob_ref": "sha256:f4...",
  "derived_from": [
    {"artifact_id": "artifact_source_17", "version": 1},
    {"workspace_file_id": "workspace_file_9", "revision": 7}
  ],
  "generated_by": {
    "type": "program",
    "name": "pdf_renderer",
    "execution_id": "job_pdf_25"
  }
}

generated_by must identify the producer. A model may generate the prose, while a deterministic renderer produces the PDF bytes. Labeling both merely “AI-generated” leaves readers and the system unable to tell whether to rerun the model, rerun the renderer, or reuse a Blob.

Provenance need not copy the entire execution log, but must at least identify input identity and version, transformation type, producer, and execution. W3C PROV similarly models derivation through activities between entities rather than inferring it from filenames.

A download link is an access capability, not Artifact identity

Cross-device download often uses a short-lived URL:

download capability
  subject=user_7
  artifact=artifact_report_25@v3
  expires_at=2026-07-22T10:00:00Z
  disposition=attachment

Link expiry invalidates access, not the Artifact or Blob. Conversely, revocation or authorization loss should deny access even before URL expiry. Amazon S3 presigned URLs likewise constrain access through expiration and signing credentials; they are not long-term business identities.

A Message should store an Artifact reference and ask the authorization service for a fresh URL when read, instead of treating one signed URL as a permanent attachment field. Device changes, expiry, and permission changes can then be evaluated against the same Artifact.

Retention and deletion converge along references

Deletion has at least three decisions:

  1. The Conversation owner deletes the Message Reference.
  2. The Artifact owner checks whether Tasks, Workspaces, delivery records, or retention policy still preserve the Artifact.
  3. The Blob owner reclaims physical content only after valid references and retention end.

Derivation does not imply cascading deletion. A delivered report may remain after source deletion while its provenance records that the source was deleted or is unavailable. A policy requiring deletion of a source and reversible derivatives should let the Artifact service produce an auditable deletion plan, not let object storage guess from path prefixes.

Versioned object storage adds another boundary: deleting a current key may create only a delete marker while older versions remain. artifact.deleted, download revocation, and completed physical erasure are distinct states.

Artifact marked deleted
  → revoke capabilities
  → detach references
  → evaluate descendants and retention
  → delete eligible blob versions
  → record erasure outcome

Only the final successful step proves erasure of the physical version. An intermediate failure should remain retryable rather than letting deleted=true claim complete deletion.

The minimum Artifact Contract

A file that crosses Messages, Sessions, or devices needs:

  • stable artifact_id, owner, and kind;
  • immutable blob_ref, media type, size, and integrity digest;
  • Artifact version or referenced Workspace revision;
  • provenance: input versions, transformation, generator, and execution;
  • authorization and revocable access;
  • retention, deletion state, and physical-erasure result;
  • references from Messages, Tasks, Workspaces, or delivery records.

This does not require preserving every file forever. It requires a clear owner for retention and deletion, while URL, path, and Message stop impersonating the file itself.

Back to the problem

Deleting the original upload message first removes only message_8 → artifact_source_17. The Artifact owner decides whether to retain the PDF based on the Task, retention requirements, and the user’s deletion intent. The Workspace owns plan.md. The delivered plan.pdf@v3 can remain an Artifact and receive a new authorized download on the computer.

Once a file enters a long-running Agent task, it is more than a Message Attachment. The Blob stores bytes, the Artifact stores business identity and provenance, the Workspace Path supplies a mutable name, the Message Reference handles presentation, and the download URL grants time-limited access. Separating them gives versioning, cross-device access, deletion, and audit consistent owners.
