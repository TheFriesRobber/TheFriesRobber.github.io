Agent Memory 6: Tier Memory into Pinned, Hot, and Cold Views

Memory should not enter every prompt in full; classify its visibility before assembling it within the current budget.

07/14/2026 Views
AgentMemoryData Governance

The problem

A user asks an Agent to revise an in-progress European market weekly report. Memory contains three kinds of records: an explicit preference that every weekly report must list risks, a recently confirmed and still-current reporting convention for the European market, and complete notes from a meeting six months ago.

The easiest implementation is to put all three into the prompt. This makes facts less likely to be missed, but irrelevant old records consume tokens continuously and expand the exposure surface for sensitive content. The opposite extreme is to run similarity search only. The old meeting notes may be more similar to “weekly report” than the short durable preference, so returning many items still does not guarantee that the non-negotiable rule reaches the model.

The problem is not that Memory stores too much. It is that “available to read” and “should enter this Context” have been treated as the same decision.

A Memory Budget is not an even slice of the total budget

The global Context Budget is first allocated across history, Memory, files, and Tool Results. Within Memory’s allocation, the Runtime still has to decide which records must remain visible, which belong to the recent working set, and which should be read only when the current Task retrieves them. Context Engineering 2 covers the first, cross-source decision; this article covers the second, Memory-internal decision.

Pinned, Hot, and Cold describe these three visibility policies. They do not require three isolated storage systems:

TierCondition for entering ContextWhen the budget is tightTypical content
PinnedThe current, authorized version is required for a class of TasksCompress its representation first; if it still does not fit, narrow or fail the Task rather than silently dropping itExplicit durable preferences, identity, and hard constraints
HotIt is relevant to the current Task and belongs to the recent working setSummarize it, reduce its allocation, or return it to ColdRecently confirmed project conventions and recently corrected durable preferences
ColdRetrieval selects it and validity and permission filters accept itKeep only a reference or omit itLong-tail facts, historical material, and infrequent evidence

Pinned does not mean “always put this into every prompt.” A preference that is revoked, expired, or unauthorized in the current resource scope must not remain visible even if it was once pinned. Pinned means that, after validity checks pass, ordinary relevance scores cannot crowd it out of the budget.

Hot does not simply mean “recently written,” either. A recent but irrelevant record has no reason to enter this Context, while an older record that still belongs to the active Task may remain Hot. Cold does not mean deleted; Retrieval can still read it when needed.

These tiers consume current Memory records that have already passed a Writer Gate. They do not persist current Task state or live Tool data. Those inputs remain under their own owners and enter Context through Context Assembly when the current turn needs them.

Pinned, Hot, and Cold decide visibility before competing for budget

Suppose a global Assembly planner allocates 900 tokens to Memory. A Memory view builder then classifies authorized current records against Task scope and policy revision and records why each record was selected or omitted. The final assembler rechecks authorization before injection. Pinned, Hot, and Cold are therefore derived per-Model-Turn views, not permanent record attributes.

The candidates for this turn are:

mem_pref_v3   pinned  weekly reports must list risks       45 tokens
mem_eu_v8     hot     current European reporting convention 520 tokens
mem_notes_v2  cold    meeting notes from six months ago  3,400 tokens

The Runtime places mem_pref_v3 first. It is selected not because it is most similar to “revise the weekly report,” but because it is a current hard constraint for this class of Task. mem_eu_v8 then consumes the Hot allocation, leaving room for only a small amount of retrieved evidence. Even if mem_notes_v2 contains the phrase “weekly report,” it does not remain in Context in full. Retrieval selects relevant spans only when the Task actually asks about that meeting.

Assembly receives an auditable Memory view rather than unexplained text:

memory_view:
  pinned: [mem_pref_v3]
  hot: [mem_eu_v8]
  cold_refs: []
  omitted:
    - memory_id: mem_notes_v2
      reason: not_relevant_within_budget
  watermark: memory_revision_41

This view represents a choice for the current Model Turn. Records do not disappear from the Memory Store merely because this turn omitted them. Another Task may assemble a different Hot set and different Cold results.

A preference update must invalidate the old Pinned view

The user now changes the requirement to “list risks only in management reports.” The Memory Writer should create mem_pref_v4 and remove the old version from the current view instead of overwriting mem_pref_v3 in place.

If Context Assembly caches pinned text by memory_id alone, it may inject the old requirement into the next turn. Principal and tenant identity must be carried either by physical partitioning or by the cache key. Under either design, the view identity must still bind resource and Task scope, the current version set, and every revision that changes visibility, for example:

partition: (subject_id, tenant_id)
key: (resource_scope, task_scope,
      current_version_set_digest, memory_revision,
      authorization_input_fingerprint, budget_policy_revision)

A change to any input invalidates the cached view. Authorization must also be checked against current state immediately before injection; a cache hit is not proof of permission. A normal team report now sees that mem_pref_v4 does not apply to its scope, while a management report includes the new version as Pinned. Current visibility changes without deleting the historical version.

Waiting for this cache to expire naturally is unsafe. Pinned records are usually constraints that change model behavior. Even brief use of the old version can contradict a correction the user has already completed.

Tiers need explicit failure semantics

Tiering is valuable not only because it saves tokens, but because it makes budget failure predictable:

  • Resolve version and scope when Pinned records conflict; do not hand contradictory text to the model.
  • Compression may shorten an over-budget Pinned representation, but it must not change the constraint. If it still does not fit, narrow the Task or return context_budget_exceeded.
  • Hot records may be summarized or returned to Cold, but summaries need source references so they do not become untraceable facts.
  • Do not add unrelated Cold content merely to fill unused tokens.

Evaluation therefore cannot stop at prompt length. It should also measure coverage of required constraints, exposure of irrelevant records, the rate at which old versions enter a view or prompt after an update, and Task completion under the same budget. A delayed index may legitimately return an old version as a candidate; treat that as a freshness diagnostic, not a tiering failure, as long as current-version resolution blocks it before model exposure. Back to the problem

Full injection confuses “stored” with “needed now.” Similarity-only retrieval makes required constraints compete with ordinary candidates. Pinned, Hot, and Cold separate those decisions: first establish whether a record is currently valid, then decide its visibility and degradation policy for this turn.

The reporting rule remains visible as Pinned, the recently confirmed reporting convention uses the Hot allocation, and old meeting material stays Cold until a specific query needs it. When the user updates the preference, the version and revision invalidate the old view immediately. Memory remains complete while the prompt receives only the current, authorized portion that the Task needs.
