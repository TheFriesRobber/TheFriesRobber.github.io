Agent Runtime 9: Make Plans Safely Revisable

A research plan that keeps running after its premise fails shows how Plan revisions, execution facts, evidence, and delegation proposals should remain separate.

07/15/2026 Views
AgentRuntimePlanning

The problem

A user asks an Agent to compare public data from 2024 and 2025. The Agent first produces a plan:

plan v1
P1 find the 2025 dataset and validate comparability
P2 compute the 2024 / 2025 difference, depends_on P1
P3 write the comparison, depends_on P2

Search results then reveal that the publisher changed its methodology in 2025, so no directly comparable dataset exists. The Plan is only an earlier checklist, however. The Runtime marks P1 complete as soon as it finds the dataset, without validating comparability, continues with P2, and eventually produces a polished report whose premise is invalid.

Asking the model for another list does not solve the problem by itself. The system still needs to relate the old and new Plans, determine which items actually ran, preserve valid evidence, and converge work already started under the old revision.

A Plan describes work; it does not own execution facts

A Plan item answers what remains necessary for the current goal. A Run, Tool Execution, or Child Job answers what actually ran. They may reference each other, but they do not share a state owner.

Plan item P1: validate whether the 2025 data is comparable
Tool Execution search_7: queried publisher material, succeeded
Evidence source_12: the 2025 methodology changed
Plan decision: P1's original premise is invalid

The success of search_7 proves that the query ran, not that P1’s premise was true. Marking P1 invalid also cannot rewrite the Tool Execution that already occurred. If a Plan item is delegated to a SubAgent or Job, that execution owner still converges its state; the Plan keeps only a stable reference and a condition for consuming the result.

This boundary also means that a Plan is not persisted chain-of-thought. It stores user-observable goals, dependencies, state, and evidence without recording private internal reasoning.

The minimum artifact needs revisions and dependencies

Implementations can use different schemas, but a revisable Plan needs to express at least:

plan_id: plan_report_4
revision: 1
goal: compare 2024 and 2025 public data
items:
  - id: P1
    state: in_progress
    objective: validate whether the 2025 dataset is comparable
    depends_on: []
    evidence_refs: []
  - id: P2
    state: blocked
    objective: compute the comparison
    depends_on: [P1]
  - id: P3
    state: blocked
    objective: write the conclusion
    depends_on: [P2]

Dependencies are not there to turn every Plan into an elaborate DAG. They give a revision a bounded impact. When P1’s premise fails, the Runtime can supersede or replace P2 and P3 without disturbing confirmed work that does not depend on that premise.

Plan mutations should also carry expected_revision. The Plan owner must validate the current revision and write the new revision within one atomic boundary: v1 may advance to v2 only when expected_revision=1 still matches the current revision. If two writers edit v1 concurrently, one succeeds and the other’s conditional / CAS update fails. The loser must read v2 and decide again. The field alone cannot stop a background replan from silently overwriting a human edit.

Revise v1 into v2

Walk the opening example through the model:

T1  search_7 returns source_12: the 2025 methodology changed
T2  the Runtime appends the evidence and marks P1's premise invalid
T3  it creates plan v2, which replaces plan v1
T4  P2 and P3 become superseded in v1
T5  v2 adds P4: establish a comparable definition or explain why the datasets cannot be compared directly
T6  only after P4 has verifiable evidence may new compute and writing items be created

v2 does not delete v1. The revision relationship explains why the work panel changed and lets the system classify a late result by the Plan version that requested it.

Suppose v1 already started job_compare_9 for P2. Activating v2 can issue a cancellation request, but the Plan owner cannot rewrite Job history to cancelled. Before a claim, retry, or irreversible effect, the Job owner must verify that plan_revision=1 and item_id=P2 are still accepted by the current Plan and that the cancellation fence has not advanced. Once P2 is superseded, an unsubmitted effect must stop. If an effect intent was already committed but its result remains unknown, the owner reconciles it instead of executing it again. CAS on the Plan revision protects only Plan mutation; it cannot converge Job execution state. If a result arrives later, the consumer still checks its revision and item. The result may remain as audit evidence or an artifact, but it cannot advance v2 automatically.

A replan should say what changed

Creating a revision whenever a model phrases a list differently turns the Plan into noise. A revision is useful when it changes execution choice, for example:

  • new evidence invalidates a premise;
  • the user changes the goal, constraint, or priority;
  • an execution owner reaches an unrecoverable terminal state and needs an alternative;
  • a human explicitly inserts, skips, or reorders work.

The revision decision should record the reason, affected items, retained evidence, and replacement relationship. Editorial rewrites or equivalent item orderings do not need another version.

Planning loops also need a limit. If repeated revisions add no evidence and alternate between equivalent approaches, the Runtime should spend a replan budget and eventually request confirmation instead of treating revision count as progress.

From a Plan item to delegation

When P4 needs independent research, the Plan can create an execution-neutral delegation proposal:

proposal_id: delegation_17
source:
  plan_id: plan_report_4
  revision: 2
  item_id: P4
goal: establish a comparable data definition
required_evidence: [official methodology, year mapping]
result_consumer: parent_run_8

This proposal is not yet a SubAgent. The Runtime next chooses a Child Run owned by the parent Run, an independent Child Job, or a durable Workflow node according to ownership, durability, cancellation, and delivery requirements. The Plan says what should be completed; it should not also decide who owns the execution lifecycle.

A work panel exposes commitments, not private reasoning

A structured Plan can produce a user-visible work panel: current goal, active item, waiting condition, confirmed evidence, and revision reason. This is more verifiable than “the Agent is thinking” and does not require exposing chain-of-thought.

Plan progress still does not replace Task outcome. After every item completes, the Task owner must verify that the user artifact exists and satisfies its constraints. Conversely, if the user cancels the Task, the Plan cannot continue authorizing new execution.

Back to the problem

The failure in the opening example is not that the model cannot make a list. The Plan is text without revision, dependency, or evidence boundaries. When the premise changes, the Runtime cannot identify invalid work or reject late results from the old Plan.

As a revisable Runtime Artifact, a Plan lets new evidence create a new revision, uses dependencies to bound invalidation, leaves execution facts with their owners, and classifies late results by their bound revision. The Plan becomes an observable and correctable work commitment rather than reasoning that the next generation silently overwrites.
