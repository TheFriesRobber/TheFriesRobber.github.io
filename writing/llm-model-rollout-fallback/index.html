LLM Infra 15: How Model Upgrades, Rollouts, and Fallbacks Preserve the Deployment Contract

Bind the Model, Tokenizer, Template, Adapter, Engine image, Runtime configuration, and capability claims into a release manifest, then use the same workload to drive canary evaluation and rollback decisions.

07/29/2026 Views
LLM InfraInferenceRelease EngineeringFallback

The problem

A “minor model upgrade” changes only the model name while retaining the old tokenizer, template, and generation defaults. The API still returns 200, but the actual Token sequence, structured output, latency distribution, and memory behavior all change. Rolling back only the weights does not restore the old behavior.

The publishable unit of inference is not a bare set of model weights. It is the collection of artifacts and configuration that jointly determine the input, execution, and output contract.

A model name is not a Release identity

Hugging Face Hub can pin a snapshot by commit revision. Transformers tokenizer revisions and chat templates determine how messages become the Tokens the model actually sees. vLLM separately exposes model revision, code revision, tokenizer revision, quantization, and generation configuration.

A release manifest can look like:

inference_release:
  release_id: chat-v3-20260729.1
  base_model:
    repository: example/chat-model
    commit: 8f3...
    digest: sha256:...
  tokenizer:
    repository: example/chat-model
    commit: 8f3...
    digest: sha256:...
  chat_template_digest: sha256:...
  adapter:
    repository: example/tool-adapter
    commit: 91a...
    digest: sha256:...
  generation_config_digest: sha256:...
  weight_dtype: bf16
  quantization_method: null
  engine_image_digest: sha256:...
  engine_args_digest: sha256:...
  parallelism: {tp: 2, pp: 1}
  hardware_class: gpu-pool-a
  protocol_schema_version: response-v4
  capability_claims: [streaming, structured-output-v2]
  benchmark_evidence_refs: [curve_aa12, quality_87c]

This schema is a design recommendation. The important point is to resolve every mutable input to an immutable reference instead of depending on main, a latest image, or implicit defaults.

Compatibility has at least four dimensions

DimensionQuestion
ProtocolAre request/response schema, streaming, and finish reasons compatible?
CapabilityAre Context, structured output, Adapter, reasoning, and other required features supported?
QualityDoes the release pass the same evaluation suite?
ResourceDo memory, TTFT/TPOT, and the service curve remain inside the envelope?

Fallback may enter only a pre-reviewed allowlist and must satisfy the full compatibility contract: protocol, the current request’s required capabilities, quality and safety gates, data policy, and the SLO envelope required by the workload. Routing must also verify current resource availability, but spare capacity cannot bypass quality, semantic, or data constraints.

Infra does not reshape an incompatible provider response into the semantics the application wanted; that belongs at the Agent/provider boundary. Infra either selects a deployment that satisfies the full contract or returns an explicit unsupported or rejected outcome.

“Semantically equivalent” cannot exist only as a configuration claim. It requires evaluation, contract tests, and workload-specific Benchmark evidence.

Shadow, Canary, and Staged rollout prove different things

Shadow can copy production inputs to a candidate release and observe offline output, latency, and resources. It cannot prove real Client delivery, and the extra traffic may itself affect capacity. Prompt data must also remain within data policy.

Canary sends a small portion of real requests to the candidate and can observe end-to-end outcomes. Traffic must be stratified by workload segment; canarying only short requests hides long-Context risk.

Staged rollout expands compatible traffic progressively while defining promote, hold, and rollback conditions.

Each stage records:

requested model/capability
resolved release digest
workload fingerprint
quality result
TTFT/TPOT/goodput
failure and fallback outcome

Comparing only 5xx responses is insufficient. Protocol drift, shorter output, or quality regression behind a 200 response can still violate the contract.

The rollback unit is the complete Manifest

If a new release changes:

  • model weights;
  • tokenizer or template;
  • Runtime image;
  • scheduler defaults;
  • quantization or parallelism;

rolling back only one object creates an untested combination. Rollback should redirect routing to a complete manifest that has already been validated and remains loadable.

This still does not guarantee Token-for-Token reproduction. Sampling, driver and hardware, external policy, and Cache state can all change behavior. A reasonable rollback promise restores a validated deployment contract within its evidence boundary; it does not promise bitwise determinism.

The platform must also retain:

  • availability of the old artifacts and image;
  • the corresponding hardware class;
  • Cache namespaces before and after migration;
  • a draining policy for in-flight requests;
  • the conditions that prohibit fallback from a new release to an older capability.

Walk the opening upgrade through the process

The original upgrade combined new weights with the old tokenizer and template. Under a release-manifest process:

  1. Build a candidate manifest that pins every artifact and default.
  2. Run protocol and quality contract tests.
  3. Measure a new service curve with the same workload used in Article 03.
  4. Let Shadow collect only permitted data and differences.
  5. Send real Canary traffic stratified by workload segment.
  6. If any hard constraint fails, route new requests back to the old complete manifest and drain the candidate.

Rollback now restores a known combination instead of improvising “old weights plus new Runtime.”

Back to the problem

The opening upgrade still returned 200 but changed Tokens, protocol, latency, and memory because the model name did not fix a complete deployment identity. Rolling back weights alone could not restore a validated combination.

Treat the complete release manifest as the atomic publishable unit. Move it through Shadow, Canary, and staged rollout with the same workload and full compatibility contract. Fallback may select only an allowlisted release that passes protocol, capability, quality and safety, data policy, and SLO-envelope gates. Rollback returns to a complete manifest without overstating that result as deterministic Token-for-Token replay.
