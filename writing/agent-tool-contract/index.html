A Tool Is an Execution Contract for the Model

Build a complete Tool contract from model-facing Schema through trusted execution, external side effects, normalized results, and repairable errors.

07/24/2026 Views
Agent CoreAgentToolsAPI Design

The problem

The model invokes create_note, and its arguments pass JSON Schema validation. The handler sends a write request to a remote system and then times out. The Runtime puts only the exception text "request timed out" back into Context.

On the next Turn, the model sees an error string. It does not know whether the arguments need to change, whether the action may be retried, or whether the note was already created. The Schema is valid and the handler did run, but this is still not a complete Tool contract.

Schema supports model decisions

Backend APIs are often designed around database fields, historical compatibility, and transport efficiency. A Tool schema participates in two different model decisions:

  1. Which Tool should be selected now?
  2. Which arguments should be supplied after selection?

Exposing a backend DTO directly therefore creates two common problems: the model must infer intent from many irrelevant fields, or a high-privilege endpoint is wrapped as an ordinary-looking multipurpose Tool.

A Tool definition should provide the minimum sufficient information:

  • its name and description distinguish the user’s intent;
  • its schema represents the inputs the model must decide;
  • tenant, actor, credential, and operation ID values that the model must not decide are injected by the trusted Runtime;
  • actions with different side effects or authorization boundaries should preferably be separate Tools.

Schema constrains the shape of model-visible input. It is not the complete execution security boundary.

A Tool Call is an untrusted proposal

Even when arguments conform to the schema, they still come from model output. A complete invocation path includes at least:

definition
→ model proposal
→ provider binding transform
→ canonical validation
→ authorization
→ handler invocation
→ external effect
→ normalized result

Validation in a provider SDK proves only that the SDK accepted a particular request shape. The Runtime must still validate against the canonical schema. The handler must also check that the resource exists, the version matches, and business invariants hold. Authorization must never obtain trusted identity from model arguments.

These layers are not redundant. Each owns different facts: the schema knows structure, the Runtime knows the current execution identity, and the backend knows the latest resource state.

A handler return value is not the entire external fact

For a pure-function Tool, a function return value can approximate the execution result. That is not true for a Tool with side effects. A network timeout, process exit, or cancellation can occur after an external commit.

The first article used operation, Tool Execution, and Attempt to explain the recovery state machine for an unknown effect. This article does not repeat that control flow. It treats unknown as one category in the result contract and focuses on how the envelope constrains the model’s next action.

A model-visible result therefore needs at least these distinctions:

FieldMeaning
outcomesucceeded, failed, or unknown
retryableWhether current evidence permits a new Attempt
errorClassvalidation, authorization, dependency, timeout, and similar classes
effectRefAn external reference that can be queried or reconciled
repairWhich inputs the model may safely modify

This is a target envelope, not a set of fields already present in Pi’s AgentToolResult. Pi currently places the Tool Result back into Context and uses a separate isError value for errors, but it does not standardize unknown outcomes, retryability, or effect references. See the current types in types.ts.

A repairable error must constrain the next action

The model can usually repair Tool selection or arguments: a required field may be missing, an enum value may be invalid, or a resource name may have several candidates. An error can return a bounded candidate set or an explicit hint.

The model cannot repair:

  • a lack of permission for the current identity;
  • an unknown outcome of an external action;
  • a backend invariant that requires a human or another state owner to decide;
  • an action explicitly forbidden by policy.

Describing all these cases as “please retry” lets the model cross the actual owner’s boundary. For an unknown effect in particular, the next action is query or reconciliation, not generation of a more convincing argument set.

The same Envelope must distinguish three next actions

One error string encourages the model to retry every case. A structured envelope returns authority to the correct owner:

EnvelopePermitted next action
errorClass: validation, with a bounded candidate set or field hintThe model may repair arguments and propose a new call
errorClass: authorization, retryable: falseStop invoking; the user or authorization owner must change permission
outcome: unknown, with an effectRefThe Runtime or a query capability reconciles; the model must not regenerate the write

Return to create_note. After Runtime validation, the trusted layer injects the subject and operation key. The backend accepts the request but the response is lost, so the handler returns outcome: unknown and effectRef: op-17. This article does not need to replay the complete retry flow. It needs only to show that the model sees one safe next action: query or request reconciliation.

Contract tests must therefore do more than test the schema parser. At a minimum, they should verify that provider binding preserves constraints, the canonical validator and handler interpret examples consistently, and the three envelope classes do not turn into one another—especially that an unknown effect never becomes an ordinary repairable failure.

Pi’s current validation, Tool execution events, and result-writeback path are implemented in agent-loop.ts. The richer effect/error envelope described here is a proposed direction for host evolution.

Back to the problem

A JSON Schema and a handler cover only two segments of the Tool contract. A complete contract must also answer:

  • Why can the model select the right Tool?
  • At which trusted boundary are the arguments validated again?
  • Who authorizes the action under the current identity?
  • Who owns the external effect?
  • After a timeout, is the outcome failed or unknown?
  • Which errors may the model repair, and which must return to the Runtime or backend?

When create_note times out, the model should receive a constrained next action rather than an exception string with no semantics. Only then is the Tool genuinely an API for the model that also preserves execution facts.
