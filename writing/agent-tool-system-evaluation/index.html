Which Failure Layer Should a Tool System Eval Diagnose?

Evaluate Tool selection, arguments, repair, mutation precision, and Task success separately so a final answer cannot hide execution errors.

07/24/2026 Views
Agent VerificationAgentEvaluationTools

The problem

A constructed case asks an Agent to update the address of customer_42. The final answer says “The address has been updated,” but the Trace shows:

model selection: bulk_update_customers
arguments: filter = "status:active"
first call: schema validation failed
repaired call: execution succeeded
external result: customer_42 and two other records changed

An Eval that checks only for the new address in the answer passes. Handler tests may also pass because the handler performed the requested bulk update. The failures are Tool selection, mutation scope, and evidence for the success claim.

A Tool System Eval must retain results at every lifecycle layer instead of collapsing model, schema, Runtime, and effect failures into one Task score.

Fix the Tool lifecycle under evaluation

eligible case
  → candidate Tool surface
  → model proposal
  → trusted argument validation
  → optional repair episode
  → authorized Tool Execution
  → provider Attempt
  → normalized Tool Result
  → external effect evidence
  → Task outcome

The surface controls visible capabilities; the model proposes a Tool and arguments; the Runtime owns trusted validation, authorization, and repair policy; the handler/provider performs physical Attempts; the external owner determines effects; the Task owner judges completion from evidence.

Eval records preserve case, operation, Tool Execution, and Attempt identities. Argument repair before authorization is a repair episode or round, not an Attempt. An authorized proposal creates the Tool Execution; physical retries create new Attempts.

Selection metrics need an eligible population

Selection recall asks whether cases that require a Tool selected it:

eligible cases selecting the correct target Tool
/ eligible cases whose contract requires that Tool

Selection precision asks whether proposals were necessary and correct:

necessary proposals selecting a correct Tool
/ all model Tool proposals

A Tool-free question is excluded from target-Tool recall, but an unnecessary write proposal belongs in precision or restraint. When several Tools can complete a goal, the case defines an allowed set or behavior constraints rather than treating one reference trace as the only valid path. Both update_customer and a precisely filtered bulk_update_customers may be valid; authorization and mutation scope remain mandatory.

Argument validity and repair are separate outcomes

LayerExampleEvidence
Schema validitytypes, required fields, enumstrusted validator
Semantic validitydate range, revision, resource relationdomain rule
Authorization validitypermission to modify the targetpolicy decision
Execution validityprovider accepted and executednormalized result

Parameter validity uses all model proposals as its denominator, not only calls reaching the handler. Otherwise validation failures disappear.

Repair success applies only where an error was repairable and the Runtime offered a repair opportunity:

repair episodes passing target validation after repair
/ all eligible repair episodes

Retain episode count, error class, and whether intent changed. Schema-valid arguments may still broaden the filter or target the wrong resource.

Execution outcome cannot replace effect evidence

Handler ok describes the handler result. A side-effecting Task also needs owner evidence such as a committed revision, immutable event, queried provider operation ID, mutation diff, or Artifact identity and checksum.

A timeout is not confirmed external failure. If commit may have occurred, record outcome=unknown and query by operation key before retrying.

These layers may disagree within one case.

Mutation precision verifies that only intended state changed

before:
  customer_42.address_revision: 7
allowed_mutations:
  - customer_42 # one structured address + revision update, record-level grain
forbidden_mutations:
  - other_customer.*

At record-level grain, report:

expected mutations observed / expected mutations
allowed actual mutations / all actual mutations
forbidden mutations count

If three records changed and only customer_42 was allowed, precision is 1/3 and forbidden mutations count=2 can trigger a hard failure. Read-only cases do not enter this denominator; they instead test read scope, source correctness, and absence of forbidden effects.

Cover different effect semantics

Case typePrimary verification
Read-onlysource, argument scope, returned evidence
Idempotent writeoperation key, repeated Attempts, final revision
Non-idempotent writeno blind retry after timeout; unknown preserved
Repairable argumentserror envelope drives safe repair
Concurrent mutationexpected revision, conflict, no overwrite
Unauthorized actionselection restraint and authorization hard failure

Different Tools need not share every metric. Each effect and recovery contract needs corresponding evidence.

The handler and schema repair succeeded, but selection failed, repair broadened scope, and two forbidden mutations make the Task fail.

These rates cannot be added into one “Tool accuracy.”

Contract tests, Model Evals, and production evidence own different layers

Schema tests catch field and adapter drift; handler tests cover success, error, cancellation, and effect contracts; surface integration tests cover discovery, binding, and hooks; model Evals expose selection and repair; production observation exposes real distributions and unknown effects.

These are not duplicate suites. A rename can change model routing without breaking a handler test; an adapter can corrupt arguments after correct selection; production providers can time out after all offline tests pass.

Back to the problem

The opening Agent fails despite correct-looking text and a successful handler: it chose the wrong Tool, expanded scope during repair, and modified two forbidden resources.

Separate selection, arguments, repair, execution, effect, and Task outcome, with denominators at the case, logical-operation, Tool Execution, Attempt, or mutation grain. Real side-effect claims require effect evidence or a backend assertion.

The goal is diagnosis, not one attractive score: model-selection errors, invalid parameters, unsafe repair, unknown execution, and out-of-scope mutations must not disappear behind “Task complete.”
