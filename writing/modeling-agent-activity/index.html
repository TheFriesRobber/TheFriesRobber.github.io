Define the Grain Before Modeling Agent Activity

07/12/2026
AgentData ModelingObservabilityLineage

The problem

An Agent Run executes a file-reading Tool. The first request times out, the retry succeeds, and the Agent eventually replies “the report has been generated.”

The system records two Tool logs: one timeout with an unknown outcome and one confirmed success. Asking “did this Tool execution succeed?” now produces at least two apparently contradictory answers:

By physical request: 1 success / 2 attempts = 50%
By logical Tool Execution: eventual success / 1 execution = 100%

If the Run returns final output normally, it is also successful at the Run grain. If the report Artifact has not been delivered, the user’s Task may still be incomplete. All of these numbers can be correct because they answer different questions.

The first problem in Agent Activity modeling is not whether enough fields exist. It is grain: does one row represent a user goal, an Agent Loop, a model cycle, a logical execution, or a physical attempt?

Separate the objects along one execution

Continue with the report example:

User Message: “Generate a report from this file”
  └─ Task: generate and deliver the report
       └─ Run: Agent Loop handling this user input
            ├─ Model Turn 1: the model proposes reading the file
            │    └─ Tool Call: read_file(file_17)
            │         └─ Tool Execution tool_exec_42
            │              ├─ Attempt 1: timeout
            │              └─ Attempt 2: succeeded
            ├─ Model Turn 2: the model generates the report from the content
            └─ Artifact: report.md

These are not several names for the same thing:

  • A Message is one user- or Agent-visible expression.
  • A Task is an application-owned user goal that may span multiple Runs.
  • A Run is an Agent Loop started by one new input or resume action.
  • A Model Turn is one model response and its Tool-call processing inside the Loop.
  • A Tool Call is the model’s proposal; a Tool Execution is the logical identity created after Runtime validation and authorization.
  • An Attempt is one physical try of the same Tool Execution.
  • An Artifact is a durable result read or produced by execution.

This article focuses on analytical grain rather than the complete Runtime state machines. The first fact to recognize is that these objects are usually not one-to-one.

Retry exposes grain mistakes most clearly

Suppose an analytical table treats every HTTP request as one Tool Execution. The initial timeout and successful retry are counted as two different actions, making the system appear to have read the file twice.

If retry overwrites one row instead, the final state becomes succeeded, but the latency, cost, and error from the first timeout disappear.

The correct relationship preserves both logical-execution identity and attempt identity:

tool_execution_id = tool_exec_42
  ├─ attempt_id = attempt_1  → timeout
  └─ attempt_id = attempt_2  → succeeded

tool_call_id can preserve the model’s original proposal. tool_execution_id answers “which logical action did the Runtime execute?” attempt_id answers “how many physical tries occurred?” Separating them lets the system analyze model behavior, Tool outcome, and downstream reliability independently.

When a user clicks “regenerate,” the system normally starts a new Run rather than adding an Attempt to the previous Run. Whether it remains in the same Task is a product decision: continuing the original goal may reuse the Task, while retaining a second independent result may require a new Task or goal version. Log timestamps alone cannot decide identity.

Do not infer causality from temporal proximity

Agent execution may cross queues, SubAgents, and external callbacks. The order in which two events reach the logging system is not necessarily the order in which they happened.

For example, the timeout for the first Tool Attempt may arrive before an external service later reports “read completed.” Sorting only by ingested_at can make the callback look like a new action after the retry.

Persist explicit relationships instead of reconstructing them later:

Task task_report_7
  └─ Run run_12
       └─ Model Turn model_turn_3
            └─ Tool Execution tool_exec_42
                 ├─ Attempt attempt_1
                 └─ Attempt attempt_2

Artifact report_7
  ← derived from file_17@v3
  ← produced for task_report_7

Timestamps still support wait-time and latency calculations. Stable IDs, causality edges, and Artifact lineage express what triggered what and which inputs a result depends on.

One Event Stream should not be every metric directly

The execution system can continuously emit events such as Attempt started, timeout, retry scheduled, Model Turn completed, and Run completed. The analytical layer should derive facts at the grain required by each question:

Analytical questionAppropriate grain
Is one downstream request reliable?One Tool Attempt per row
Did an authorized Tool action eventually complete?One Tool Execution per row
What were model tokens and latency?One Model Turn per row
How did one Agent Loop end?One terminal Run per row
Was the user’s goal eventually completed?One Task outcome per row
Which inputs does final content depend on?One Artifact lineage edge per row

Putting all of these grains into a wide “one Run per row” table creates deeply nested arrays and cannot represent a Task spanning Runs. Querying raw events directly for dashboards forces every query to reimplement retry, lateness, and deduplication.

A more stable design preserves process detail in source events, then derives analytical facts idempotently at stable grains. One underlying event may contribute to several derived models, but each model retains its own grain.

A metric must state its denominator

“Tool success rate” is not a complete metric. It could mean any of the following:

successful attempts / all terminal attempts
successful tool executions / all terminal tool executions
successful runs using this tool / all terminal runs using this tool
successful tasks using this tool / all terminal tasks using this tool

When the first Attempt times out and only the second is confirmed successful, Attempt success rate is 50% while the Tool Execution still succeeds. That distinction is useful: the logical action is eventually confirmed complete, but the underlying request did not return a confirmed outcome within its deadline.

Latency and cost have the same issue. Run latency covers Model Turns, Tool Executions, retry backoff, and waits inside one Agent Loop. End-to-end Task latency may also span several Runs and background Jobs. Keeping only a final total hides where time and cost accumulated; keeping only Attempts cannot answer what the user goal cost overall.

Aggregation must therefore follow explicit relationships upward rather than sum whichever table is most convenient.

Artifacts connect “success” to an actual result

A Run in succeeded state says only that one Agent Loop ended normally. It does not prove that the user received the correct result. A report may still be undergoing background conversion, may use an old file version, or may fail during upload.

Model Artifact as an independent object and record which Task it serves, which Run or Job produced it, and which source versions it read. The model can then answer:

  • Does the final report exist and was it delivered?
  • Which version of file_17 did it use?
  • Did regeneration create a new Artifact or overwrite the old one?
  • Which downstream results depend on one incorrect source?

The Task owner evaluates that evidence instead of copying succeeded from a Run or Job. This lineage requires only observable input-output relationships, not hidden model reasoning.

Back to the problem

When abundant logs still cannot explain a failure, different grains of fact have usually been mixed together.

Separating Task, Run, Model Turn, Tool Execution, Attempt, and Artifact lets one retry express two facts at once: an underlying request timed out and its outcome was temporarily unknown, but the logical Tool Execution was eventually confirmed successful. Whether the Run ended normally and whether the user’s Task was truly delivered remain separate evidence questions.

The starting point for Agent Activity modeling is not one wide table for every use case. It is deciding what each record represents.
