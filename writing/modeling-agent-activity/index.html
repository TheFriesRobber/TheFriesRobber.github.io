Define the Grain Before Modeling Agent Activity

07/12/2026
AgentData ModelingObservabilityLineage

The problem

An Agent Run calls a file-reading Tool. The first request times out, the retry succeeds, and the agent eventually produces a report.

The system records two Tool logs: one failed and one successful. Ask “Did this Tool call succeed?” and at least two apparently contradictory answers are possible:

by physical request: 1 successful attempt / 2 attempts = 50%
by logical Tool Call: 1 eventually successful call / 1 call = 100%

If the final report is correct, this Run’s outcome is successful. Across this one-Run sample, the Run-level success ratio would be 100%. These numbers can all be correct because they answer different questions.

The first Agent Activity modeling decision is not how many fields to add. It is the grain: does one row represent a user goal, a logical action, or one physical attempt?

Separate the objects along one execution

Continue with the report example:

User Message: “Generate a report from this file”
  └─ Run: completes the user goal
       ├─ Turn 1: model decides to read the file
       │    └─ Tool Call: read file_17
       │         ├─ Attempt 1: timeout
       │         └─ Attempt 2: succeeded
       ├─ Turn 2: model generates the report from the content
       └─ Artifact: report.md

These are not several names for one object:

  • A Message is one user- or agent-visible expression.
  • A Run is one logical execution started to complete a user goal.
  • A Turn is one complete model request and response.
  • A Tool Call is one logical action proposed by the model.
  • An Attempt is one physical Runtime execution of that action.
  • An Artifact is a persistent input read or output produced by the execution.

This article focuses on analytical grain, not the full Runtime state machine for these objects. The important observation is that their relationships are usually not one-to-one.

Retry exposes grain mistakes quickly

Suppose an analytics table treats every HTTP request as a Tool Call. The timeout and successful retry become two separate actions, making it appear that the model requested the file twice.

If retry instead overwrites one row, the final state becomes succeeded, but the initial timeout—and its latency, cost, and error—disappears.

The logical and physical identities must coexist:

tool_call_id = call_42
  ├─ attempt_id = attempt_1  → timeout
  └─ attempt_id = attempt_2  → succeeded

tool_call_id answers “which action did the model intend?” attempt_id answers “how many times did the Runtime actually try?” Together they distinguish the logical Tool Call’s outcome from attempt-level reliability. Determining whether the user goal completed also requires linking the Tool Call to its Run and evaluating terminal Run evidence.

Similarly, a user clicking “regenerate” should usually create a new Run, not an Attempt on the previous Run. The distinction comes from product semantics, not from timestamps: do the events represent the same user intent, and may they produce independent results?

Do not infer causality from nearby timestamps

Agent execution can cross queues, SubAgents, and external callbacks. The order in which events reach the logging system may differ from the order in which they occurred.

For example, the first Tool Attempt’s timeout may be ingested before an external service later reports that the read completed. Sorting by ingested_at alone can make the callback look like a new action after the retry.

Relationships should be stored explicitly instead of reconstructed from timing:

Run run_12
  └─ Tool Call call_42
       ├─ Attempt attempt_1
       └─ Attempt attempt_2

Artifact report_7
  ← derived from file_17@v3
  ← produced by run_12

Timestamps still measure waiting and latency. parent_id, a logical action ID, and Artifact lineage express who triggered whom and which inputs produced a result.

One Event Stream should not directly serve every metric

An execution system can append events such as attempt started, timeout, retry scheduled, and run completed. The analytical layer should derive facts at the grain required by each question:

Analytical questionAppropriate grain
Is one downstream request reliable?One Tool Attempt per row
Did a model-proposed Tool Call eventually finish?One logical Tool Call per row
Did the user’s goal complete?One terminal Run per row
Which inputs contributed to final content?One Artifact lineage edge per row

Putting every grain into one wide “one row per Run” table creates nested arrays. Querying raw events directly makes every dashboard reimplement retry handling, late-arrival logic, and deduplication.

A more stable pattern preserves process history in source events and derives analytical facts idempotently at explicit grains. One underlying event may contribute to several derived models, but each model must preserve its own grain instead of treating the event as the same kind of record everywhere.

A metric must name its denominator

“Tool success rate” is incomplete. It may mean:

successful attempts / all terminal attempts
successful logical Tool Calls / all terminal logical Tool Calls
successful Runs using this Tool / all terminal Runs using this Tool

When the first attempt fails and the second succeeds, Attempt success rate falls while the logical Tool Call still counts as successful. That difference is useful: the user’s goal recovered, but underlying reliability deteriorated.

Latency and cost have the same issue. End-to-end Run latency includes model time, queue wait, Tool Attempts, retry backoff, and Artifact writes. Keeping only the final total hides where time and cost went. Keeping only Attempts cannot answer how much one user goal consumed.

Aggregation should therefore follow explicit relationships upward, rather than adding whichever numbers happen to share a table.

Artifacts connect “success” to an actual result

A Run with status succeeded does not necessarily mean the user received the correct output. A report may reference an old file version, or generation may complete while upload fails.

Making Artifact a separate object—and recording which Run produced it and which source versions it read—lets the system answer:

  • Does the final report actually exist?
  • Which version of file_17 did it use?
  • Did a rerun create a new Artifact or overwrite an old one?
  • Which downstream results were affected by one bad source?

This lineage needs only observable input-output relationships. It does not require storing hidden model reasoning.

Back to the problem

When many logs still cannot explain an execution, the system has often mixed facts at different grains rather than omitted one more field.

Separating Run, logical Tool Call, Attempt, and Artifact lets one retry express both truths: a low-level request failed, but the user goal eventually recovered. Success rate, latency, cost, and lineage can then use the appropriate denominator and causal relationship.

Agent Activity modeling should not start with one wide table for every use case. It should start by defining what each record represents.
