Agent Runtime 5: A Checkpoint Is Not an Object Snapshot

07/15/2026 Views
AgentRuntimeRecovery

The problem

An Agent is generating a report. It has called create_document, the external service has returned doc_42, and the model is about to write the summary. At that point, the background process executing this Run—the worker—crashes.

If the system serializes its Runtime objects once per minute, the latest snapshot may still describe the moment before the Tool call:

in-memory snapshot: ready to call create_document
external fact: doc_42 has already been created

Resuming directly from the snapshot creates the document again. Marking the entire function as complete omits the summary. The problem is not the serialization format. An in-memory object never owned the complete state of the outside world.

Four persistent objects that are easy to conflate

A Checkpoint becomes useful only after its responsibility is separated from the other persistent objects:

ObjectQuestion it answersTypical contents
Event LogWhich execution facts have been committed?Tool intent, result, Model Turn completed
SnapshotWhat is the current derived state?Run state, current Model Turn, remaining budget
CheckpointWhere and under which conditions should recovery resume?snapshot reference, event cursor, waiting condition, version
ArtifactWhat deliverable did execution produce?files, reports, code, citations

The Event Log emphasizes history, the Snapshot supports fast reads, and the Artifact is a user-visible result. A Checkpoint is a recovery protocol: it points to a position and states which external conditions recovery code must verify.

Serializing an ORM connection, async task, socket, or framework-internal object may look more complete, but those objects generally cannot survive a process, version, or machine boundary. Recovery should recreate them.

For external side effects, the Runtime must also persist an effect intent before making the call: a stable effect_key, a parameter digest, the target system, and an initial state. The call can begin only after that intent commits. If the worker then crashes after the call, recovery at least knows that this logical action may have happened instead of assigning a new identity and executing it again.

The minimum a Checkpoint should contain

For the Run in the opening example, a conceptual Checkpoint could look like this:

{
  "checkpoint_version": 4,
  "run_id": "run_8",
  "run_spec_fingerprint": "sha256:...",
  "resume_contract_revision": "report-agent.v3",
  "snapshot_ref": "snapshot_73",
  "event_cursor": {"stream_ref": "session:session_17", "seq": 73},
  "resume_at": "reconcile_create_document",
  "waiting": null,
  "pending_effects": [
    {
      "effect_key": "run_8:create_document:v1",
      "provider": "document-service",
      "idempotency_scope": "tenant:tenant_9",
      "idempotency_expires_at": "2026-07-18T09:00:00Z",
      "status": "in_progress",
      "external_ref": null
    }
  ],
  "artifact_refs": [],
  "budget": {"model_turns_used": 6},
  "created_at": "2026-07-17T09:00:00Z"
}

Here, snapshot_ref points to the complete recoverable derived state through seq=73 in Session stream session:session_17. Recovery verifies the binding among the Snapshot, stream, and sequence before reading later events. The bare number 73 has no meaning in another Session stream. To restore this Run, recovery still reads that Session stream in order and applies only events causally related to the current Run. A system that does not persist a Snapshot may instead replay the Event Log from the beginning, but it cannot start from a cursor in the middle without any base state.

The RunSpec identifies the execution contract, while resume_contract_revision identifies the version of recovery semantics on which resume_at depends. An effect contract also records the downstream provider, idempotency scope, and key expiry. The effect_key alone does not prove that a retry days later will still deduplicate.

resume_at should not be an arbitrary source-code line. It should name a logical boundary that future code can continue to understand, such as a committed Tool Execution, a pending approval, or an effect that requires reconciliation.

Recovery is reconciliation, not deserialization

Recovery for run_8 can proceed in this order:

1. Load Checkpoint version 4, its RunSpec, and snapshot_73; verify that the Snapshot covers exactly through cursor 73 in the specified Session stream.
2. Read events with seq > 73 from that stream and incorporate later facts related to this Run.
3. For every effect with an intent but no terminal result, first query by a stable business reference. Retry with the original key only while it remains inside the provider's deduplication window; this includes in_progress, dispatched, and explicit unknown states.
4. Revalidate authorization, Artifacts, and waiting conditions.
5. Construct new Runtime state and continue from the next legal boundary.

Suppose the worker appended seq 74 effect.succeeded(effect_key, doc_42) after the external service returned doc_42, but crashed before creating a new Checkpoint. The old Checkpoint still says in_progress, but step 2 incorporates seq 74 and adds doc_42 to the new state. Recovery does not create the document again.

If the external call succeeds but even the success event is missing, durable state may still say intent or in_progress; it does not automatically become unknown. Recovery should treat every effect with a committed intent and no terminal result as uncertain. While the key remains inside the downstream deduplication window, recovery may retry with the original key. After expiry, it may continue only if it can query the original result through a stable business reference. If it can neither query the result nor confirm that the provider will still deduplicate, the Run enters reconciliation or manual_recovery; reusing the same key is not enough.

Conversely, if no effect intent exists, the Runtime should not have made the external call. That is the boundary established by “persist the intent before the call.” If an implementation calls first and records the intent later, no amount of Checkpoint detail can reliably identify the orphaned side effect.

A Checkpoint therefore does not replace idempotency or reconciliation. It tells recovery what must be reconciled.

Pause and crash use the same recovery contract

Human approval, user input, and a scheduled pause can all be represented as explicit waiting conditions:

{
  "kind": "approval",
  "request_id": "approval_9",
  "resource_version": 17,
  "expires_at": "2026-07-18T09:00:00Z"
}

Before pausing, the Runtime commits the waiting event and Checkpoint, then releases the worker. Resume cannot check only whether someone clicked Approve. It must confirm that the approval is bound to the same action, parameters, and resource version; that it has not expired; and that the current authorization still holds.

A crash and an intentional pause differ in how they begin, not in the recovery protocol. Both rebuild from the last committed boundary instead of depending on a call stack that still exists in the original process.

Why replay is usually not fully deterministic

Some durable workflow systems replay deterministic workflow code from an event history and store external call results as history events. That is a strongly constrained execution model.

An ordinary Agent Runtime is often looser:

  • Calling the model again with the same prompt may produce a different result.
  • The data behind a Tool can change.
  • Current authorization, time, and file versions may have changed.
  • A Provider may update model behavior.

“Replay from a Checkpoint” should therefore mean replay recorded facts to rebuild state, not call every external dependency again and expect the same result.

A reproducible Eval needs a fixed RunSpec, prompt, Tool fixtures, model version, and grader, with external calls replaced by recorded results. That is a separate reproducibility contract; a production Checkpoint cannot provide it by itself.

Handling schema and code upgrades

A long-running Run may span a deployment. checkpoint_version versions the storage schema, while resume_contract_revision versions the semantics of resume_at, state transitions, and recovery actions. Both participate in the worker compatibility matrix: a change in recovery logic needs a new resume contract revision even when the schema is unchanged. The system then needs one compatibility strategy:

  • New code remains backward-compatible with older supported Checkpoint schemas.
  • Old Checkpoints are migrated before the deployment.
  • Old Runs are routed to compatible workers until they finish.
  • A Run that cannot be recovered safely enters an explicit manual_recovery state instead of silently restarting from the beginning.

Compatibility tests should use retained fixtures from older Checkpoint versions, including their resume contract revisions, and verify that new code can load, replay, and continue from them. A round-trip test for only the latest schema cannot expose a real upgrade failure.

How often to create a Checkpoint

Writing a Checkpoint for every token is too expensive, while writing one only when the Run ends removes most recovery value. Natural boundaries include:

  • after a Tool Execution with side effects converges;
  • after a Model Turn completes;
  • before entering human approval or a long timer;
  • after producing an important Artifact;
  • when the Event Log has grown enough that recovery should shorten its rebuild path.

The right frequency depends on how much pure computation the system can redo, write cost, and recovery objectives. A Checkpoint may lag behind the Event Log as long as recovery reads the facts after its cursor.

Back to the problem

A Runtime object snapshot records only what one process once observed. It cannot prove what happened in the outside world.

A useful Checkpoint preserves a logical resume position, a Snapshot reference bound to an event cursor, a RunSpec identity, waiting conditions, and the stable identities of pending, unknown, or confirmed effects. Recovery then loads the base state, replays later events, reconciles uncertain side effects, and recreates transient objects. The contract does not promise fully deterministic replay of the outside world. It gives every resumed execution an explainable, verifiable starting point.
