Agent 40: Platform Boundaries Follow State Ownership and Reversal Conditions

Decide whether an Agent capability should become a platform service using Sources of Truth, failure domains, resource curves, adoption cost, and reversal conditions.

07/24/2026 Updated 07/27/2026 Views
Agent ArchitectureAgentPlatform EngineeringArchitecture

The problem

A system splits Loop, Context, and Tool into three services by noun. A Tool write succeeds and Tool Service emits a result, but Loop Service crashes before updating Run state. Context Service recovers from an old projection and gives the same Tool Call to the model again.

Loop Service: Run still executing
Tool Service: Tool Execution succeeded
Context Service: latest Context lacks Tool Result

More services did not clarify responsibility. Platform boundaries should follow fact ownership and invariants, then independent deployment should be justified by failure, resource, or evolution benefits.

Source of Truth means semantic authority

Several copies may coexist. What must be unique is the authority to commit one business decision. Ask who may transition state, which contemporaneous facts and policy support it, which copies are projections, and what can rebuild them.

The opening permits two designs.

A: Core atomically commits observed effect evidence and next state.

external backend:
  owns actual effect

core transaction:
  commit(effect reference/evidence,
         Tool Execution state,
         next Run state,
         Context revision)

The backend still owns the real effect. If the process crashes between external commit and the local transaction, recovery queries by stable operation ID and must not repeat the Tool Call before reconciliation.

B: an Event Log owns Core’s observed facts.

atomic append:
  tool_effect_observed {
    operation_id,
    tool_execution_id,
    source_attempt_id,
    effect_ref,
    observed_outcome
  }
derived:
  Run state projection
  Context projection

Projections rebuild by cursor, version, and idempotent processing. tool_execution_id identifies the execution to converge; source_attempt_id preserves the physical observation when applicable. Unknown remains unknown. Reconciliation appends another event instead of overwriting history or treating a local append as the external effect.

Repair a derived view at the right location

If an authoritative effect event exists but Context missed it, replay the projection and repair its cursor. If the event normalized unknown as succeeded, fix the Tool-result boundary rather than teaching Context a second timeout rule.

Every independent boundary declares authoritative state, accepted commands, emitted facts, derived views, idempotency/version, and recovery/rebuild/reconciliation. Network topology without these contracts is not a platform boundary.

Rebuildable views also need versioned semantic facts

An Event Log alone does not make a projection rebuildable. Its events must preserve semantics already decided by the owner instead of exposing raw statuses for every consumer to reinterpret. The opening effect observation can be represented as:

{
  "event_id": "event_51",
  "schema_version": 2,
  "operation_id": "op_17",
  "tool_execution_id": "tool_exec_42",
  "effect.outcome": "unknown",
  "normalization_policy_version": 4,
  "effect_ref": "provider_op_9",
  "supersedes_event_id": null
}

If v2 adds unknown, an old consumer cannot continue with a catch-all rule that treats every non-success as failure. Its compatibility contract must preserve unknown, reject the event, or degrade explicitly while exposing the unsupported schema/version. Otherwise the Source of Truth preserves uncertainty while a Derived View invents confirmed failure.

Historical repair must also distinguish three operations:

  • authoritative fact correct, projection rule wrong: fix the source range and rule version, then rebuild idempotently;
  • original observation correct, later reconciliation obtains new evidence: append a new fact referencing the earlier event instead of overwriting the observation;
  • owner contract gains a new meaning: publish a versioned schema and consumer compatibility policy first, and backfill only when historical evidence can support the value.

Deterministic rebuild therefore needs authoritative history for the target range, stable identity/sequence, consumed schema versions, projection-rule versions, and a cursor. Reconciliation uses them to repair local drift; rebuild regenerates a larger range from a trusted point. Neither operation bypasses the semantic owner.

Separate code boundaries from deployment boundaries

BoundaryPrimary benefitAdded cost
Module/packagesemantic encapsulation and dependency testsshared process failure and release
Library/shared processimplementation reuse and local callscompatibility and host upgrades
Independent serviceindependent capacity, failure, release, ownershipnetwork failure, latency, schemas, operations, recovery

Start with the smallest useful boundary while contracts stabilize. A rapidly changing Context policy should not become a remote API prematurely. A stable owner with an independent resource curve may eventually deserve centralized governance.

An independent service needs a real separation signal

Failure needs isolation

Sandbox execution of untrusted code may need a different security and failure domain from Agent Core. “This module can fail” is insufficient; name the blast radius and handle the new partial failures introduced by the network.

Resource curves diverge

Sandbox scheduling may follow CPU, memory, and startup queues; Evaluation may consume batch model capacity; Core may hold low-latency Run state. Without measured profiles, this remains a hypothesis.

Change cadence and compatibility diverge

A service supporting several host versions needs schema evolution, compatibility windows, and deprecation. Separate teams do not automatically imply separate runtime topology.

Multiple adopters share a stable contract

Repeated stable semantics across products may justify a shared Runtime. A second caller alone does not: a module or library may suffice, and migration, support, compatibility, and exit cost still matter.

Platform benefits need observable denominators

DimensionRequired grain and denominator
Adoptioneligible workloads using the contract / all eligible workloads in a window
Reliabilitysuccess and failure by logical operation or request
Latencydistribution for the same workload class
Costobserved/allocated cost per Task, operation, or resource unit
Migration burdenmigrated callers, remaining callers, actual work

Use a baseline, window, and configuration identity. Include retries and timeouts introduced by remote calls. A central API also needs support and incident ownership; centralizing an endpoint while leaving recovery to every caller does not centralize semantics.

Choose the smallest necessary boundary for the opening system

Agent Core deployment
  owns:
    Run transition
    per-turn Context projection
    Tool Execution logical state
    observed effect evidence
  modules:
    loop
    context
    tool contract
    memory read/write policy

Sandbox control plane (candidate independent service)
  owns:
    sandbox admission
    lease
    runtime provider reconciliation

Keeping tightly related Run, Context, Tool state, and observed evidence under one owner reduces cross-service recovery. The external backend still owns effects. Sandbox is a candidate remote boundary because of untrusted execution, independent capacity, and reconciliation.

This is conditional. A stable authoritative Event Log may permit Context to rebuild independently. An external Tool provider does not remove Core’s responsibility for Tool Execution and unknown outcomes. Evaluation may deploy separately for batch capacity while still reusing the production Spec compiler and execution contract.

An ADR records the decision and reversal conditions

decision: keep Context projection in Agent Core
status: accepted
reversibility_class: staged_commitment
context:
  invariant: observed effect evidence, Run transition and visible Tool Result must share one revision
assumptions:
  - Context workload does not require independent capacity
  - all current consumers release with Agent Core
alternatives:
  - independent Context Service
evidence_needed:
  - latency profile
  - failure ownership
  - eligible adopters
consequences:
  - shared deployment
  - simpler local atomicity
irreversible_commitments:
  - after the first external adopter, support the published API through its declared compatibility window
validation:
  metrics:
    - projection latency by workload class
    - rebuild parity from the same event cursor
  observation_window: ...
reversal_conditions:
  - measured workload requires independent capacity
  - stable event contract permits deterministic rebuild
  - multiple consumers require an independently versioned API
migration_or_rollback:
  - build the candidate projection from the same versioned facts
  - compare current state at an explicit cursor
  - move one eligible consumer while retaining the Core path
  - route that consumer back if parity or recovery invariants fail
deprecation:
  old_path_sunset_when:
    - every declared consumer uses the versioned API
    - the rollback window has ended
review_owner: ...
review_date: ...

This is a decision structure, not evidence from a real system. Michael Nygard’s original ADR description emphasizes the forces behind a decision and preserving a superseded record when it is reversed.

reversibility_class says whether the decision is a low-cost experiment, a staged commitment, or a high-cost choice. irreversible_commitments identifies API, data, or support obligations that cannot disappear immediately after external adoption. Migration first proves that the same versioned facts and cursor produce an equivalent projection, then moves consumers. Deprecation begins only after adopters, the rollback window, and support ownership satisfy explicit exit conditions. Reversibility is therefore an execution contract, not merely a reminder date in an ADR.

“Scale grows” is not a reversal condition. Tie it to evidence and an action:

if Context computation becomes a sustained independent capacity bottleneck
for the same workload class,
and the event contract can rebuild the projection deterministically,
then reevaluate independent deployment.

A triggered condition reopens the decision; it does not automate the split. The new decision must still recalculate migration, partial-failure, and compatibility costs.

A simple design still has a scope

One deployment unit can remain modular when contracts, owners, event identity, and recovery are explicit. With one host, similar workload curves, synchronized changes, and invariants needing local atomicity or low latency, local boundaries may be enough. Separate only when durable failure, resource, evolution, or adoption benefits exceed remote-call and governance costs.

Back to the problem

Splitting Loop, Context, and Tool by noun made the Run harder to keep consistent because deployment preceded state ownership and invariants.

Keep the external backend as effect owner. Let Core use either an atomic current state for effect evidence, logical state, and Context, or an append-only event model; recover by operation/effect reference. Separate Sources of Truth from rebuildable projections, and promote modules to services only when failure isolation, resource curves, change cadence, or adoption provide evidence.

Record assumptions, denominators, migration cost, and reversal conditions in an ADR so boundaries can contract or split when evidence changes.
