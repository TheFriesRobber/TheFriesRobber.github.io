Agent 39: Closing the Loop Between Evaluation and Production

Share the production execution path with Eval, then use Shadow, Canary, and evidence-backed bad-case ingestion to build a reversible release loop.

07/24/2026 Updated 07/27/2026 Views
Agent VerificationAgentEvaluationRelease Engineering

The problem

An Agent version passes every offline regression case but cannot call update_customer in production. Model and prompt are the same; the execution systems are not:

ObjectEvalProduction
Tool surfacehandwritten mock exposing only update_customergenerated from user authorization
Argument validationmock accepts any stringRuntime requires expected revision
Timeoutfixture returns immediatelyprovider has a deadline
Contexttest script concatenates inputproduction assembly policy
Resultmock returns oknormalized effect evidence

The offline pass proves only that the test-script Agent works. A closed evaluation loop must establish semantic parity before release, validate online with controls proportional to effect risk, and convert new failures into reproducible evidence.

Eval should not reimplement the Agent

Context assembly, Tool binding, defaults, error interpretation, retry, and termination belong to the Runtime under test. Copying them into the harness creates a second implementation.

Agent configuration
  → production Spec compiler
  → per-turn configuration snapshot
  → production executeRun / executeTurn
  → production Tool contract
  → normalized events

Eval injects only:
  case input, fixture, isolated effect boundary, clock, grader

“Production” means the implementation that owns semantics, not connection to every production resource. Dependencies may be replaced; Context decisions, Tool validation, result normalization, retry, and event schema should not be rewritten.

A shared path does not require a shared external environment

Replaceable boundaryReasonRequired record
Model providerfixed response or cost isolationstub/recording version and limitations
Tool provideravoid real effectsfixture, effect contract, failure injection
Clockreplay timeout and expiryclock policy and starting time
External datafix case inputsnapshot or content fingerprint
Graderevaluate resultsgrader, rubric, Judge configuration

Replace implementations without changing contracts. A mock returning only ok is not equivalent to a production envelope containing outcome, retryability, and effect reference. A fixture provider can simulate succeeded, failed, unknown, and revision conflict under the same contract.

Check parity with snapshots and manifests

Shared code is insufficient because production resolves configuration from identity, flags, resources, and time. Eval must save its actual snapshot:

spec_compiler_version: ...
runtime_version: ...
turn_snapshot:
  model_configuration: ...
  prompt_sha256: ...
  context_policy_sha256: ...
  tool_surface_sha256: ...
  authorization_fixture: ...
  timeout_policy: ...
  resource_budget: ...
external_environment:
  fixture_sha256: ...
  provider_mode: isolated
grader_sha256: ...

A parity diff distinguishes equal, intentional, and unknown differences:

same: runtime, prompt, context policy, Tool contract
intentional: production provider → isolated fixture
unknown: historical feature-flag revision

Record intended substitutions and the conclusions they limit. An unknown critical configuration supports investigation, not a claim of strict reproduction.

Offline gates preserve deterministic contracts first

Before release, run schema, authorization, and effect contract tests; smoke and regression suites; repeated per-case trials; Tool, Context, and grader metrics; and parity checks. They catch known deterministic failures but cannot cover real distributions, shared-resource contention, or changing dependencies.

The next step need not always be Shadow, Canary, then A/B. Choose validation by the question and effect risk.

Shadow is safe only after effects are isolated

Shadow sends real or mirrored inputs to a candidate without exposing its result to users. It can observe Tool selection, arguments, Context assembly, latency, usage, taxonomy, and response differences.

Invisible output is not effect isolation. A candidate that can send messages, mutate databases, or publish Artifacts already affects the world. Mutation-capable Shadow needs a contract-compatible recorder, isolated tenant/Sandbox, enforced dry-run, or no write authorization. A prompt saying “do not execute” is not enforcement. Production-data permission and retention still apply.

Canary exercises the real path but needs exit criteria

A Canary sends some real work units through the candidate Runtime, dependencies, and effect path. The Google SRE Workbook describes canarying as a partial, time-bounded deployment evaluated before rollout continues.

The unit may be request, Task, tenant, or low-risk capability. Do not let Turns from one Task drift across incompatible configurations. Define eligible population, configuration identities, safety/success/latency/cost/invalid metrics, observation window and support, stop and rollback conditions, and handling for committed mutations.

There is no universal traffic percentage. Insufficient support means insufficient evidence. Canary manages release risk; A/B testing usually studies product outcomes and adds causal-design requirements.

Every stage must explain why it may continue

Offline
  gate: regression + parity pass
  evidence: manifest M18

Shadow (read-only and recorder Tools)
  gate: no forbidden proposal; trace schema complete
  exit: enough eligible cases or evidence remains insufficient

Canary (low-risk eligible population)
  gate: safety hard failures = 0 in observed valid cases
  monitor: success, latency, cost, invalid support
  rollback: any declared hard invariant violation

Staged rollout
  gate: repeat the same checks at each population boundary

This is process structure, not measured rollout data. Low-risk reads may skip Shadow; high-risk writes may still require human confirmation or be unsuitable for online experiments.

Bad cases need evidence before entering the loop

production signal
  → locate Task / Run / configuration
  → identify failure owner and evidence horizon
  → sanitize and minimize
  → freeze fixture or simulate dependency
  → design grader
  → confirm by replay
  → add to versioned dataset

An unreplayable Trace can remain investigation evidence but not masquerade as regression. Deduplicate repeated failures into one canonical case; only a new boundary condition should expand the fixture. Record the case’s source class, owner, tier, manifest, grader, and retirement condition. After a fix, run multiple trials on the candidate configuration while retaining the baseline results, so the regression verifies the mechanism rather than one output string.

Rollback does not delete failure evidence

After a Canary stop, return traffic to a known configuration while preserving affected work units, committed effects, reconciliation needs, Tasks requiring recovery or compensation, and the Trace and manifest. Binary rollback cannot unsend email or undo database mutations; effect-level recovery must be planned before release.

Back to the problem

The opening Eval covered neither the production Tool surface, validation, Context, nor timeout, so it tested another Agent.

Reuse the production Spec compiler, per-turn snapshot, execution entry point, and Tool contract. Record intentional provider and fixture substitutions in the manifest. Then choose Shadow, Canary, or staged rollout by risk, and isolate every Shadow mutation at a trusted boundary.

A production failure becomes regression evidence only after identity linkage, minimization, fixture control, grader design, and confirmed replay. The loop carries one execution semantics across offline evidence, reversible release, and production feedback.
