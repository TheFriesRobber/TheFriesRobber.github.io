Notes on Spark Adaptive Query Execution

02/17/2022
SparkBigdataSQLPerformance

The problem

Before execution, Spark SQL uses the Catalyst optimizer to produce logical and physical plans. Many optimizations depend on data volume and distribution, but that information may be inaccurate when a query is submitted.

For example:

  • The data left after filtering may be far smaller than the statistics predict.
  • A few join keys may be heavily skewed, making a small number of partitions much larger than the rest.
  • spark.sql.shuffle.partitions may be set too high, producing many tiny tasks.
  • The initial plan may choose a sort-merge join, only to discover at runtime that one side is small enough to broadcast.

Adaptive Query Execution (AQE) addresses this uncertainty: while a query is running, Spark uses real statistics produced by shuffle stages to re-optimize the remaining physical plan.

What AQE solves

AQE focuses on the physical execution plans of Spark SQL and DataFrame workloads. It is not a general optimizer for the RDD API, nor is it a switch that automatically solves every performance problem.

Its common capabilities include the following.

1. Coalescing shuffle partitions

Many jobs use a relatively high value for spark.sql.shuffle.partitions to avoid partitions that are too large under heavy workloads. When the actual data volume is small, however, excessive partitioning creates many tiny tasks and makes scheduling overhead significant.

AQE can use shuffle output sizes to combine adjacent small partitions and reduce the number of downstream tasks.

Relevant settings include:

spark.sql.adaptive.enabled
spark.sql.adaptive.coalescePartitions.enabled
spark.sql.adaptive.advisoryPartitionSizeInBytes

This is usually a relatively safe optimization because it reduces the number of tasks after the shuffle has already completed.

2. Changing the join strategy at runtime

When Spark creates a physical plan, it uses statistics to choose among strategies such as sort-merge join, broadcast hash join, and shuffle hash join.

If AQE discovers that one side is small after the shuffle, it can replace a sort-merge join with a broadcast join, avoiding some subsequent shuffle and sort work.

Relevant settings include:

spark.sql.adaptive.enabled
spark.sql.autoBroadcastJoinThreshold
spark.sql.adaptive.localShuffleReader.enabled

A broadcast join still consumes executor memory. If the broadcast side is not actually small, or its statistics are misleading, this optimization can introduce new memory pressure.

3. Handling skewed joins

With skewed data, some shuffle partitions become much larger than others. AQE can identify partitions that are substantially larger than the rest and split them into smaller pieces.

Relevant settings include:

spark.sql.adaptive.skewJoin.enabled
spark.sql.adaptive.skewJoin.skewedPartitionFactor
spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes

This is useful for skew that only becomes visible at runtime. It still depends on SQL or DataFrame execution plans, however, and does not replace fixing abnormal keys, dirty data, or an inappropriate business-level join grain.

Enabling AQE

For a Spark SQL workload, start by enabling AQE:

spark.conf.set("spark.sql.adaptive.enabled", "true")

Then adjust individual behaviors according to the problem at hand. AQE is enabled by default in many Spark versions, but production environments should still verify the setting explicitly so that behavior does not depend on version- or platform-specific defaults.

With spark-submit, the settings might look like this:

spark-submit \
  --conf spark.sql.adaptive.enabled=true \
  --conf spark.sql.adaptive.coalescePartitions.enabled=true \
  --conf spark.sql.adaptive.skewJoin.enabled=true \
  ...

Confirming that AQE is working

The most direct approach is to inspect the Spark UI and the execution plan.

The SQL tab displays the adaptive plan. While the query runs, the initial plan may be replaced by a final plan. Look for:

  • An AdaptiveSparkPlan node.
  • A change in join type.
  • Fewer shuffle partitions.
  • Split skewed partitions.
  • Stage and task counts that match your expectations.

You can also inspect a plan in code:

df.explain("formatted")

Keep in mind that AQE’s final plan depends on runtime statistics. An explain captured before execution may not reveal the final changes.

AQE is not a cure-all

AQE is well suited to cases where runtime data volume or distribution differs from the optimizer’s estimate. It should not become an excuse to ignore data modeling and data quality.

Some important boundaries:

  • If the join-key design is wrong, AQE can mitigate the symptoms but cannot correct the business logic.
  • If the data contains many null values, placeholders, or dirty keys, clean the data first.
  • If UDFs hide filters and expressions from the optimizer, AQE has fewer opportunities to help.
  • If input files are severely fragmented, AQE mostly operates after shuffle and does not solve the small-file problem.
  • If resource allocation is too small, AQE cannot create executor memory out of thin air.

A practical sequence

I usually approach AQE this way:

  1. Enable spark.sql.adaptive.enabled.
  2. Keep spark.sql.shuffle.partitions reasonably conservative so AQE has room to coalesce partitions.
  3. For SQL and DataFrame jobs, inspect the adaptive plan in the Spark UI.
  4. If tiny tasks are the main issue, focus on partition coalescing.
  5. If joins are slow, check whether the join strategy changes.
  6. If task stragglers dominate, examine key distribution together with the skew-join settings.

Back to the problem

AQE lets Spark SQL revise the remaining plan with runtime shuffle statistics instead of relying entirely on estimates made before execution. That matters in production because data volume, filter selectivity, and key distribution are rarely static.

It is best understood as a runtime optimization layer, not a master performance switch. After enabling it, you still need to inspect the Spark UI, understand the query plan, and examine the data distribution. Do not leave to configuration what can be fixed through data modeling, and do not hide optimizer-friendly logic inside a UDF too early.
