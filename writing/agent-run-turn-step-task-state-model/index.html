Run, Turn, Step, and Task Are Different State Machines

07/15/2026
AgentRuntimeState Machine

The problem

A user asks an Agent: “Read this file, generate a report, and export it as a PDF.”

Suppose reading and saving can finish within the current request, but PDF conversion may take several minutes and requires a separate conversion environment. Rather than hold the HTTP connection open, the Runtime saves the Markdown, submits the conversion to a queue, and lets another worker execute it. The request can return, and the original process may even restart, but the Run cannot finish until the PDF actually exists.

Under those conditions, one execution might proceed like this:

Turn 1: the model decides to read the file
Step 1: read_file succeeds
Turn 2: the model generates the report body
Step 2: saving report.md succeeds
Task 1: convert report.md to report.pdf in the background

Task is not a mandatory layer in every Agent. Here it represents work that has left the current call and must be queued, executed, and recovered independently. If PDF conversion is merely a synchronous call inside the current function, such as await convert_to_pdf(report), it remains a Step in the Run and does not need a separate Task.

If the system stores only one execution record:

{
  "id": "run_18",
  "status": "running"
}

this running status answers almost nothing. Is the model still generating content? Has the file been saved? Is the PDF conversion waiting in a queue? What should stop when the user cancels? After a process restart, should the system regenerate the entire report or resume only the conversion?

All of these activities belong to one user request, but they do not share one completion condition. The problem is not a shortage of status values. The system has compressed execution objects with different grains into one state.

Start with the question each state answers

Run, Turn, Step, and Task are not standardized terms across frameworks. One implementation may call an Agent Loop iteration a step; another may call background work a job. The names can differ, but four distinct questions still need answers:

ObjectQuestion it answersWho decides it is complete
RunHas this user goal been completed?Agent Runtime or orchestrator
TurnHas this model request and response finished?model adapter
StepDoes this logical action have a definite result?the Runtime executing the action
TaskHas this independently scheduled work converged after leaving the current call?queue, worker, or workflow engine

The goal is not a perfectly shaped object tree. It is to let each state describe only the facts its owner can actually establish.

Objects inside one Run can occupy different states at the same time. A parent status must not overwrite facts already established by its children.

A Run tracks the user goal

In this example, the Run’s goal is not “the model returned once.” It is “a usable PDF report exists.” When Turn 2 returns the report body, the Run therefore cannot enter succeeded; it is still waiting for the PDF Task.

A more accurate state is:

run_18: waiting
reason: task_9 has not finished
completed evidence: report.md version 3
missing evidence: report.pdf artifact

The distinction between waiting and running matters to both the product interface and recovery logic. waiting says no model or Tool currently owns execution and the system is waiting for an external condition. running means an owner is actively advancing the work only while a valid lease or heartbeat supports that claim. A stale running value left after a process crash is not a live fact; an expired lease must enter reconciliation or recovery.

A Run’s terminal state must also return to the goal. If the PDF Task ultimately fails, the Run may be failed. If the user explicitly accepts the Markdown report as a degraded result, the same Run may end as succeeded, but it should record which Artifact was delivered. The absence of an exception from the last function call is not enough to prove that the user goal was completed.

A Turn describes one model round trip

Turn 1 receives the user’s request and the file Tool, then returns a proposed read_file call. Turn 2 adds the file content to its input and returns the report body.

Each Turn can record independently:

  • which model and provider actually received the request;
  • which context revision and Tool surface were used;
  • whether the response completed, was cancelled, or failed to parse;
  • token usage, latency, and finish reason.

A succeeded Turn proves only that the model adapter obtained a usable response. It does not prove that a Tool proposed by the response executed, or that the Run completed.

If the transport fails before the provider accepts the request and retry is known to be safe, the Runtime may still treat the second transport attempt as part of the same Turn. A new Turn begins only after the model receives new visible input, such as the result of reading the file. Otherwise infrastructure retries are miscounted as additional rounds of Agent reasoning.

A Step tracks one logical action

A Step is a logical action the Runtime needs to observe and advance. Reading the source file and saving the Markdown are two Steps in this example.

Suppose save_report writes report.md, but its response is lost. After seeing a timeout, the Runtime should not move the Step directly to failed. Its status is unknown: the external effect may have happened even though no result was confirmed.

step_save_report
  logical identity: save this report
  status: unknown
  attempt 1: timeout

If a later retry is still confirming or completing the same save, it keeps step_save_report and adds an Attempt. If the user asks to save a second copy, that is a new Step.

This is why a Step and a physical request cannot share one identity. A Step answers “did this action eventually complete?” An Attempt answers “how many times did the Runtime physically try?” Attempt is execution evidence, not a fifth business state machine introduced by this article.

A Task appears only after the lifecycle leaves the current call

Once PDF conversion enters a queue, the HTTP request can return and a worker may restart. The conversion no longer belongs to the current call stack. A scheduler owns it, so it needs identity and state that can survive across requests and processes. That is the Task in this article.

task_9: convert report.md@v3 to PDF
  attempt 1: worker lost
  attempt 2: running

The Task’s retry unit is the same scheduled work—not a new Run and not a request for the model to regenerate the report. As long as the input remains report.md@v3 and the conversion can be replayed safely or deduplicated downstream by task_9, another worker Attempt can remain part of the same Task. If the report body advances to version 4, the Runtime should explicitly cancel the old Task or create a new one rather than let two versions compete for the same output path.

When the Task succeeds, it produces report.pdf, which may give the Runtime the evidence needed for run_18 to reach a terminal state. The Task status is not copied automatically into the Run. The Run evaluates its own goal condition again: an Artifact derived from the correct input version was published atomically and passed a minimum integrity or format check. Merely seeing an output path does not rule out a partial file left by a worker crash or cancellation.

If conversion is fast and the parent waits for it before returning, the design can stay simpler: execute convert_to_pdf as another Step. The boundary between Step and Task is neither the operation name nor duration alone. It is whether lifecycle and ownership have separated. Work that the current Runtime call remains responsible for awaiting and converging is a Step; work transferred to a queue, worker, or workflow engine is a Task.

Retry must stay at the correct layer

Now suppose the first PDF worker crashes and the second succeeds. The recovery path should be:

run_18 remains waiting
turn_1 and turn_2 remain succeeded
step_read and step_save_report remain succeeded
task_9 adds attempt 2

If the system can retry only the whole Run, the model reads the file again, regenerates the body, and saves it again. Even if the final PDF is correct, the system can no longer explain the additional tokens, file versions, and external writes.

Conversely, a model-output parse failure should not retry the PDF Task. First determine whether a failure is recoverable within the object where it occurred. End the Run or create a new one only when the original goal can no longer continue.

This rule does not mean every layer must retry automatically. It means a retry must not silently change logical identity:

  • a transport retry remains in the same Turn;
  • a Tool retry remains in the same Step;
  • a worker retry remains in the same Task;
  • a user-requested rerun usually creates a new Run.

Cancellation does not rewrite every state to cancelled

If the user cancels while the PDF conversion is running, the Runtime first moves the Run to cancelling and sends task_9 a cancellation request. It must not rewrite completed Turns and Steps to cancelled; the report body was generated and saved, and those are historical facts.

The Task should not claim cancelled merely because it received the request. A worker may be writing a file, and a remote conversion service may already have produced a result. The Task reaches its appropriate terminal state only after its owner confirms that work stopped and handles any remaining Artifact. Until then, it can remain in cancelling or another explicit transitional state.

The Run waits for its unfinished owned work to complete reconciliation, then enters a terminal state according to product policy. If the PDF finishes after the cancellation request, policy may retain it as an undelivered Artifact, deliver it and mark the Run succeeded, or clean it up and mark the Run cancelled. None of these choices rewrites the history of children that already completed.

Cancellation therefore propagates intent, not a status overwrite across every child. Each owner must still resolve its state from the facts it can observe.

Separate states produce definite answers

At one instant, the system can store:

Run run_18       → waiting for task_9
Turn turn_1      → succeeded
Step step_read   → succeeded
Turn turn_2      → succeeded
Step step_save   → succeeded, artifact report.md@v3
Task task_9      → running, attempt 2

The product UI queries the Run and knows the user goal is still in progress. Model-cost analysis queries Turns. Tool reliability uses Steps and Attempts. Queue operations inspect Tasks. Parent, causality, and Artifact version connect these objects, but they no longer compete for one status field.

What a Checkpoint persists, and how an event log produces a current snapshot, are separate persistence questions. How an analytics store calculates metrics at the correct grain is covered in Model Agent Activity by Grain First. This article establishes the Runtime semantics first: who owns each state, who decides completion, and which layer should recover from a failure.

When one state is enough

If a request makes one model call, executes no Tool, starts no background work, and can restart from the beginning without additional side effects, then Run and Turn may be one-to-one. The implementation can store one record rather than create four tables for conceptual completeness.

The trigger for separation is an actual lifecycle split: one user goal now includes multiple model round trips, a logical action can retry, or work must continue outside the current request. At that point, sharing one state makes recovery and metrics ambiguous.

Back to the problem

Run, Turn, Step, and Task differ not because of their names or hierarchy, but because they have different completion evidence and retry units.

A model response does not prove a Tool executed. A completed Tool does not prove background work converged. Even a succeeded Task helps complete the user goal only when it delivers the correct Artifact required by the Run.

Once state belongs to the object that owns it, the Runtime can recover only the necessary layer after a failure. It can also explain whether the system is calling a model, resolving an action, waiting for a worker, or has actually completed the user goal.
