Agent Runtime 2: The State Layers of an Agent Execution

A PDF-report Task shows how completion ownership and retry boundaries separate Task, Run, Model Turn, Tool Execution, and Job, then maps those layers to OpenAI, Anthropic, and pi terminology.

07/15/2026 Views
AgentRuntimeState Machine

The problem

A user asks an Agent: “Read this file, generate a report, and export it as a PDF.”

Reading the file, generating Markdown, and submitting a conversion request can finish in the current Agent Loop. PDF conversion may take several minutes, however, and run in a separate worker. After the current request returns “conversion in progress,” the user may ask for status and the process may restart. Those later activities still serve the same goal, but they do not necessarily belong to the same Agent Loop.

Under the object relationships used in this article, the goal can first be written as:

Session session_3: shared conversation and Context
  Task task_report_7: generate and deliver a PDF report
    Run run_18: handle the user's initial request
      Model Turn 1 → Tool Execution: read_file
      Model Turn 2 → Tool Execution: save_report
      Model Turn 3 → Tool Execution: enqueue_pdf_conversion
      Model Turn 4: reply “the report is being converted”
    Job job_pdf_9: a worker converts report.md to report.pdf
    Run run_19: the user asks for status later

If the system stores only one record:

{
  "id": "run_18",
  "status": "running"
}

this running status answers almost nothing. Is the model generating? Has the file been saved? Is background conversion in the queue? Has the current Agent Loop ended, or was it explicitly paused for later resumption? Is the user cancelling this interaction or the entire report goal?

The problem is not merely a shortage of status values. The system has compressed a user goal, one Agent Loop, model turns, Tool side effects, and background scheduling into one object.

Run, Turn, and Step have no shared definitions across frameworks

OpenAI, Anthropic, and pi all implement a loop that calls a model, executes Tools, and returns results to the model. They do not use run, turn, and step in exactly the same way:

EcosystemPrimary terminology in public documentationBoundary to keep in mind
OpenAI Agents SDKOne SDK run is one application-level turn; the Runner may call the model and execute Tools repeatedly inside itOpenAI calls the whole application interaction a turn, so bare Turn is ambiguous for an internal model cycle
Anthropic Agent SDK / Messages APIquery() starts Agent work; the documentation also uses assistant turn for one Claude response and continues the loop with tool_use / tool_resultA Session can span multiple interactions; max_turns counts model-loop turns, not durable user goals
piagent_start / agent_end delimit one low-level agent run; agent_settled means pi will not continue through an automatic retry, post-compaction retry, or queued follow-up; each turn_start / turn_end represents one LLM response and its Tool callsA low-level run and the final settled boundary differ; turn explicitly names an internal Loop grain

This article therefore does not claim that the industry has one standard object tree. The series instead uses a vocabulary that maps the three semantics explicitly:

Term in this seriesQuestion it answersCommon owner
SessionWhich interactions share durable conversation, Context, and resources?application / session service
TaskHas the user’s durable goal been completed?application / orchestrator
RunHas an Agent Loop started by one new input or resume action stopped, paused, or failed?Agent Runtime
Model TurnHas one model response and its Tool-call processing reached the boundary before either the next model request or the current Run pauses or stops?Agent runner
Tool ExecutionDid one authorized Tool action reach a definite outcome?Tool Runtime
JobHas work transferred to a scheduler converged?queue, worker, or workflow engine

Model Turn deliberately includes Model to avoid collision with OpenAI’s application-level turn. Step is no longer a fixed Runtime object in this series: one framework may use step for a loop iteration while a product may use it for any progress item. Use Model Turn for model decisions, Tool Call or Tool Execution for Tool activity, and Attempt for physical retries.

Session, Task, Run, and Job are connected by identity and causality, but each decides completion independently.

A Session defines context scope; a Task tracks goal completion

First separate two questions:

  • A Session answers, “Which interactions share conversation history, Context, and resources?”
  • A Task answers, “Has one specific user goal been completed?”

They can be associated without sharing a lifecycle. session_3 can remain active while it first carries task_report_7, “generate and deliver the PDF,” and later carries a new Task, “send me the report.” Conversely, task_report_7 can remain waiting after the first interaction ends because the PDF has not been delivered.

The Task in this example is “generate and deliver a PDF report.” The application creates task_report_7 from the user’s initial request. After the system replies “conversion in progress,” the goal remains incomplete, so the Task stays waiting.

task_report_7: waiting
completed evidence: report.md@v3 has been saved
waiting for: job_pdf_9 to produce an artifact_ready report.pdf, then for the Task owner to commit delivery

When the user later asks “is the conversion done?”, the new input arrives in the same Session and starts a new Run. That Run can read the state of task_report_7 and job_pdf_9, then answer without pretending that the original Agent Loop has retained execution ownership the whole time.

Therefore, Session active does not mean that one Task is still executing, and Task succeeded does not mean that the Session should end. Whether a Task is reused depends on whether the application still considers the user goal identical, not merely whether messages share a Session.

Task is an application-level term here. It is neither Python’s asyncio.Task nor a queue Job. A framework does not automatically define when an application’s user goal is complete; that judgment belongs to the product or orchestrator.

One Task can span multiple Runs; a Run owns only one Agent Loop

In this example, Task and Run have a one-to-many relationship: task_report_7 is the stable goal identity, run_18 handles the initial request, and run_19 handles the later status query. Both Runs serve the same Task, but each owns its own start, stop, and recovery state. This is the application model used by the article, not a claim that every framework uses the same database schema.

run_18 starts with the user’s initial input. Its Runner calls the model and executes Tools repeatedly until the model returns “the report is being converted.” That application-level turn has now ended. The Run can become succeeded while task_report_7 continues waiting for the background Job.

run_18: succeeded
final output: the report is being converted
task_report_7: waiting for job_pdf_9

This separation corrects a common misuse: the Run should not remain running indefinitely after the HTTP request returns merely because the user goal is incomplete. running should be supported by a real owner, lease, or heartbeat. Otherwise it is an unverifiable stale value.

One case can preserve the same Run identity: the Runtime explicitly pauses it as a resumable execution, such as waiting for approval or durably storing everything required to continue the Agent Loop. A resume then continues the same unfinished application-level turn; it is not justified merely because the same Task has more work. If the original Run already returned final output to the user, later input normally starts a new Run.

A Run’s terminal state therefore describes only how that Agent Loop stopped. It may successfully return “conversion accepted” without proving that the PDF Task has completed.

A Model Turn is one model cycle inside the Loop

In run_18, the first Model Turn lets the model see the user request and file Tool, then returns a read_file call. The Tool Runtime executes it and adds the result to the next model-visible input. The second Model Turn uses the file content to generate the report and propose save_report. The third sees the saved result and proposes enqueue_pdf_conversion. The fourth sees that the conversion Job was accepted and replies “the report is being converted.” This expansion also shows that a Model Turn and a Tool Execution are distinct objects that alternate inside the Loop.

Each Model Turn can record independently:

  • the model and provider that actually received the request;
  • its Context revision and Tool surface;
  • model response, tokens, latency, and finish reason;
  • proposed Tool Calls and the Tool Execution identities created from them.

The Model Turn reaches its boundary after the model response and its Tool-call processing are complete, when the Runner is either ready to make the next model request or ready to pause or stop the current Run. Model Turn 4 has no Tool Call; it reaches the boundary when its final output completes and stops run_18. This maps to pi’s turn events and explains the assistant turns in Anthropic documentation. For OpenAI, it is one internal model/Tool iteration inside an SDK Run; do not mistake it for another application-level turn.

If transport fails before the provider accepts the request and retry is known to be safe, the second physical request can remain a transport Attempt of the same Model Turn. A new Model Turn begins only when the model receives new visible input, such as the read_file result. Otherwise infrastructure retries are miscounted as extra rounds of Agent reasoning.

A Tool Call is a proposal; a Tool Execution owns execution state

When the model returns save_report(path, content), it creates a Tool Call: a structured action proposal. The Runtime validates arguments, checks authorization and policy, and only then creates a Tool Execution that may produce external effects.

Suppose save_report writes report.md, but its response is lost. After seeing a timeout, the Runtime cannot move the Tool Execution directly to failed; the external effect may have happened without a confirmed result.

tool_execution_save_4
  logical identity: save report.md@v3
  status: unknown
  attempt 1: timeout

If a later retry still confirms or completes the same save, it should keep tool_execution_save_4 and add only an Attempt. If the user asks to save another copy, that is a new Tool Execution.

This is why the series no longer uses a generic Step object. A Tool Call answers “what did the model propose?” A Tool Execution answers “what did the Runtime authorize and execute?” An Attempt answers “how many physical tries occurred?” Calling all three a Step loses retry and external-effect identity again.

A Job is background work owned by an independent scheduler

Once PDF conversion enters a queue, the current Agent Loop can end and workers may restart. A scheduler independently queues, leases, retries, and converges the work, so this article calls it a Job.

The name does not change merely because PDF conversion takes longer. The deciding question is who owns the work identity, retries, and terminal state after the Run ends. If an independent scheduler can continue and recover the work without running the model again, it is a Job in the vocabulary used here.

For example:

job_pdf_9: convert report.md@v3 to PDF
  attempt 1: worker lost
  attempt 2: running

The Job’s retry unit is the same background work—not a new Run and not a request for the model to regenerate the report. As long as the input remains report.md@v3 and conversion can be replayed safely or deduplicated by job_pdf_9, another worker Attempt can remain in the same Job. If the report advances to version 4, its conversion must receive a new Job identity. The system should also cancel the old Job or use fencing, isolated outputs, or versioned output paths so v3 and v4 cannot compete for one result.

Success for job_pdf_9 means only that it used the correct input version to produce an integrity-checked, artifact_ready PDF that has not yet been delivered to the user. In this example, “delivery” is limited to publishing a download reference or access grant in the same transactional boundary as Task state. The Task owner conditions one write on Task state=waiting + state_version; that write makes the reference visible, records delivery_committed, and moves the Task to succeeded. If cancellation has already moved the Task to cancelling, the delivery commit must fail. This creates separate completion boundaries for “background result ready” and “user goal delivered” rather than copying Job state into Task state.

If delivery sends email, posts a message, or calls another external system, it cannot be claimed as atomic with local Task state. That path needs a separate Delivery identity and stable effect key: persist the delivery intent first, then use idempotent sending or reconciliation. While the result is unconfirmed, the Task should remain delivering, cancelling, or explicitly unknown; it must not claim succeeded or cancelled. This is a cross-system delivery protocol and does not change the Task–Job hierarchy used in this example.

If conversion is merely a synchronous call in the current Tool function, such as await convert_to_pdf(report), it does not need a Job; it remains part of the current Tool Execution. Entering a queue is not the sole criterion either. The boundary is still whether lifecycle and ownership have transferred to a scheduler that can recover the work independently.

Retry must remain on the correct identity

Suppose the first PDF worker crashes and the second succeeds. The recovery path should be:

task_report_7 remains waiting
run_18 and model_turn_1..4 remain succeeded
tool_execution_read, tool_execution_save, and tool_execution_enqueue remain succeeded
job_pdf_9 adds attempt 2

If the system can retry only the entire Run, the model reads the file again, regenerates the body, and saves it again. Even if the final PDF is correct, the system can no longer explain the extra tokens, file versions, and external writes.

Conversely, a model-output parse failure should not retry the PDF Job. First recover within the identity owned by the failing component:

  • transport retry remains in the same Model Turn;
  • Tool retry remains in the same Tool Execution;
  • worker retry remains in the same Job;
  • resuming an explicitly paused Agent Loop can preserve the same Run;
  • new user interaction normally creates a new Run;
  • the application creates a new Task when the work is no longer the same user-goal instance; a changed goal, an explicit request to run it again, or a new delivery after the old Task became terminal normally creates a new Task.

Cancellation enters an intermediate state before each owner converges

Before the user says “I no longer want this report” during PDF conversion, the objects have these states:

Task task_report_7              → waiting
Run run_18                      → succeeded
Tool Execution save / enqueue  → succeeded
Job job_pdf_9                   → running

This sentence is new user input, so it starts run_20. That Run interprets the user’s intent and submits a control command targeting task_report_7; it neither resumes run_18 nor treats run_18 as the cancellation target.

The application persists the cancellation request and uses a conditional write to move the Task from waiting to cancelling. If the Task is already terminal, that transition must fail rather than overwrite the terminal state. The orchestrator sends the request to job_pdf_9; only after the scheduler admits it does the Job move from running to cancelling. Once the request is accepted, run_20 can reply “cancellation in progress” and enter succeeded:

Task  waiting  → cancelling
Job   running  → cancelling
Run   run_18   → succeeded  (historical state unchanged)
Run   run_20   → succeeded  (cancellation request accepted)
Tool Execution succeeded  (unchanged)

cancelling means that the owner has accepted the cancellation intent but has not yet confirmed termination. It is not a terminal state. The completed run_18, Model Turns, and Tool Executions must not be rewritten as cancelled: the report body was generated and saved, and those are historical facts.

The scheduler then stops dispatching new Attempts and asks the active worker to stop. Worker exit or lease loss alone is not enough: a paused old worker may recover and perform a late write. The scheduler must also increment a cancellation generation or fencing token, or revoke the old Attempt’s publication capability. The Artifact store that accepts the final PDF must atomically check the current Job state, version, and token and reject an old Attempt.

Only after the current Attempt has stopped and old Attempts can no longer commit an artifact_ready result may the Job owner move the Job from cancelling to cancelled. The Task owner then confirms that no delivery_committed fact exists and handles Artifact access according to the cancellation contract before moving the Task from cancelling to cancelled:

Job   cancelling → cancelled
Task  cancelling → cancelled

These two transitions cannot be collapsed into a copied status. A cancelled Job proves only that the background conversion stopped. The Task owner must also confirm that no other Run or Job can complete the goal and that there is no delivery_committed fact or Artifact still accessible to the user.

Entering cancelling does not guarantee that the Job’s final state will be cancelled. After the scheduler admits the request, the active worker may still commit an artifact_ready PDF before the new fencing boundary takes effect. Generation then wins the race at the Job layer:

Job   cancelling → succeeded
Task  cancelling → cancelling  (the delivery commit fails its state precondition)

The Job must remain succeeded; it cannot be rewritten as cancelled, but that success proves only that the Artifact is ready. Because the Task is already cancelling, a conditional delivery_committed write fails. After the application handles the undelivered Artifact, the Task can still move from cancelling to cancelled.

The Task-level race is between two conditional writes:

waiting → cancelling  (the cancellation request wins)
waiting → succeeded   (delivery_committed wins)

Only one transition can match the same state_version. If delivery commits first, the Task is already succeeded and the later cancellation transition must fail. run_20 should report that cancellation arrived too late while recording the request separately. If delivery or remaining effects cannot be confirmed, the Task must not claim cancelled; it should remain cancelling or enter an explicitly defined exceptional terminal state.

A cancelled Task also does not mean that the system automatically deleted report.md@v3 or a generated PDF. It proves only that this goal will not be delivered to the user. Artifact deletion, retention, and access revocation have separate contracts. If the product defines deletion as a condition of successful cancellation, the Task owner must also wait for evidence that deletion completed.

If the user says only “stop the current answer,” the target identity is the Run currently generating the answer, not the whole Task. The application sends a cancellation request only to that Run; product policy decides whether task_report_7 and job_pdf_9 continue. A cancellation request must explicitly target a Run, Tool Execution, Job, or Task. A parent can propagate intent, but each owner still performs its own state transition from facts it can observe.

Separate states produce definite answers

At one instant, the system can store:

Session session_3               → active
Task task_report_7              → waiting for job_pdf_9
Run run_18                      → succeeded
Model Turn model_turn_1..4      → succeeded
Tool Execution tool_exec_save_4 → succeeded, report.md@v3
Job job_pdf_9                   → running, attempt 2

The product UI queries Task to learn whether the user goal remains in progress. Interaction history queries Run. Model-cost analysis queries Model Turn. Tool reliability uses Tool Execution and Attempt. Queue operations inspect Job. Parent, causality, and Artifact version connect these objects, but they no longer compete for one status field.

What a Checkpoint persists, and how an event log produces a current snapshot, are separate persistence questions. How an analytics store calculates metrics at the correct grain is covered in Agent Observability 1: Define the Grain before Modeling. This article first fixes the Runtime semantics used by the series: who owns state, who decides completion, and which identity should recover from failure.

Back to the problem

The common industry behavior is that an Agent Runtime repeatedly calls models and Tools. The inconsistent part is which layer each project calls run, turn, or step. Copying one ecosystem’s bare word lets the same Turn mean a whole application interaction in one article and one model response in another.

This series therefore uses explicit terms: Session defines the scope of shared conversation and Context; Task records one user goal and may be associated with multiple Runs and background Jobs; Run represents one Agent Loop and contains Model Turns and Tool Executions; Job represents background work owned by an independent scheduler. Step remains ordinary process language, not a fixed state-machine object.

Once the names align, the operational boundaries become clear too: a model response does not prove a Tool executed, a successful Run does not prove a Task completed, and a Job retry should not restart the Agent from the beginning.
