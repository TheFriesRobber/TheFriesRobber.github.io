Agent 29: A Verifiable Confirmation Protocol for High-Risk Actions

Bind user confirmation to a specific action, parameters, resource revision, identity, and expiry so stale approval cannot be reused.

07/24/2026 Updated 07/27/2026 Views
Agent ProductionAgentSecurityHuman-in-the-Loop

The problem

An Agent is preparing to delete /reports/draft.md. It shows the path to the user and asks whether to continue. The user replies, “Confirm.” While the Agent waits, however, two things happen: another process replaces the file, and after recovery the model generates a new Tool Call whose path is /reports/final.md.

If the Runtime merely searches the Session for the latest confirmation message, it may apply approval for the old file to the new action. Natural language expresses the user’s intent, but it does not bind that intent to a stable Tool, parameter set, resource revision, or expiration time.

High-risk confirmation needs to become a verifiable protocol: the user confirms a canonical action proposal, and the confirmation may be consumed only while the same identity, action, parameters, and resource preconditions still hold.

First fix exactly what the user saw

A model-generated Tool Call first passes schema validation, trusted parameter normalization, and risk classification. Do not sign raw JSON directly: object key order, default values, path aliases, and case differences can all create ambiguity.

A conceptual proposal might look like this:

{
  "proposal_id": "prop_41",
  "subject_ref": "user_7",
  "actor_ref": "agent_run_19",
  "tool": "delete_file",
  "arguments": {"artifact_id": "file_12"},
  "resource_revision": "etag_18",
  "policy_revision": 7,
  "risk": "destructive",
  "expires_at": "...",
  "nonce": "..."
}

The UI renders an understandable description from this canonical proposal: which file will be deleted, which project owns it, which revision is current, and whether recovery is possible. The object shown to the user and the object that will be executed must share the same source. The system must not display a model-written summary while executing raw parameters that were never compared with it.

A trusted policy should classify risk from the Tool, effect type, resource, tenant, and parameters. The model may explain the risk, but it cannot label a destructive action as harmless.

A confirmation token binds to the proposal

After the user confirms through an authenticated interaction, the confirmation service signs or stores an unforgeable record:

confirmation =
  subject + actor/delegation
  + proposal digest
  + resource revision
  + policy revision
  + issued_at + expiry
  + one-time nonce

This is a design recommendation, not a field set required by a universal standard. The core invariant is that a change to anything that could affect the user’s decision invalidates the old confirmation.

resource_revision is especially important. HTTP If-Match illustrates the same principle: a state-changing request can carry a strong validator for an existing representation, and the origin server does not perform the method when that validator does not match. A backend may instead use an ETag, database row version, Artifact revision, or another strong precondition.

Pause and resume cannot rely on conversation text

When execution pauses for confirmation, the Runtime should persist:

  • the proposal_id and canonical digest;
  • which authenticated subject it is waiting for;
  • expiration and revocation state;
  • the associated Run, Tool Execution, and resume point;
  • the current resource and policy revisions.

After Session recovery, the Runtime loads this waiting record and then processes the confirmation event. It should not ask the model to infer from messages whether the user agreed, nor should it regenerate a similar-looking Tool Call and consume the old confirmation.

If the model needs to change parameters, the system creates a new proposal and shows the difference to the user again. A presentation-only wording change may retain the same canonical proposal. A change to the resource, recipient, amount, destination, scope, or effect type requires a new confirmation.

Consuming a confirmation once does not make the effect exactly once

Through one durable CAS, the confirmation service should atomically move a token from issued to consumed(operation_id). The consumed state and the stable operation that owns it must be persisted together. This prevents two operations from claiming the same confirmation and avoids an orphan confirmation if the process crashes after marking it consumed but before recording its owner. It constrains consumption of the confirmation credential; it does not guarantee that an external side effect happens exactly once.

Suppose the backend deletes the file, but the Runtime crashes before recording the Tool Result. Recovery cannot declare failure merely because the confirmation was consumed, and it cannot issue another confirmation and delete the file again. The system needs a stable operation_id and a backend effect reference:

proposal prop_41
→ confirmation conf_9 consumed by operation delete_42
→ backend outcome unknown
→ query delete_42 / resource revision
→ confirmed or manual reconciliation

For a backend with neither idempotency nor a query interface, the result may remain unknown indefinitely. The confirmation protocol cannot remove that uncertainty.

During recovery, only the same operation_id may continue using this confirmation. If evidence proves that dispatch never started, the operation may create a new Attempt. If execution crossed the effect boundary, it must query or reconcile first; recovery must not reinterpret it as a new operation.

The backend still reauthorizes and checks preconditions

Even when a confirmation matches exactly, execution still needs to:

  1. Revalidate subject, actor, delegation, and tenant.
  2. Confirm that current policy still permits the action.
  3. Check the resource revision and state.
  4. Execute or query the side effect with the operation identity.
  5. Audit the authorization decision, confirmation, and effect outcome separately.

Confirmation means the user saw and agreed to a particular proposal. It does not mean the user has permission forever, nor does it prove that the backend is currently in a valid state for execution. Revoked access, a resource placed on legal hold, or a policy upgrade can all cause a confirmed action to be rejected.

Not every Tool needs confirmation. Reading public material and performing side-effect-free format conversion can usually proceed under policy. Deletion, sending sensitive data externally, irreversible submission, and high-value actions are more likely to require confirmation. The product’s risk model should set the threshold instead of asking the user to confirm every step.

Back to the problem

The old confirmation in the opening example must be rejected. The revision of /reports/draft.md has changed, and the recovered Tool Call points to /reports/final.md, so the canonical proposal digest no longer matches.

The Runtime creates a new proposal that clearly shows the target file and its current revision. The backend may accept the deletion only after the user confirms again and identity, policy, and resource preconditions still hold at execution time.

Confirmation is therefore neither generalized trust in the Agent nor reusable conversation text. It is time-bounded authorization evidence for one specific action proposal, and it cannot replace backend authorization, idempotent effect handling, or auditing.
