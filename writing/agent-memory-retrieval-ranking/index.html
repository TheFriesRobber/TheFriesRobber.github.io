Agent Memory 5: Retrieval Cannot Rank by Similarity Alone

Start from currently valid facts and combine keyword, vector, hybrid search, and reranking instead of optimizing similarity alone.

07/17/2026 Views
AgentMemoryRetrieval

The problem

A user asks, “Schedule next week’s project review.” Memory contains two records. An old version says “available in the morning, suitable for project reviews,” while the new version says “only weekday afternoons remain available.” Because the query mentions a review, the more detailed old version with the exact term receives a higher similarity score.

Vector search did not malfunction. It answered “which text is semantically close?” The system needs “which still-valid facts may this Task use?” Similarity-only Retrieval allows expired, superseded, or unreadable content to win the first position.

Candidate generation is not final Memory

Memory Retrieval can be separated into a bounded pipeline:

Task query
  → permission / subject filter
  → keyword + vector candidate generation
  → current-version resolution
  → task-aware reranking
  → Context Assembly

Keyword, vector, and hybrid search only increase candidate recall. Before a candidate enters Context, it must resolve to the current version in the source of truth and pass permission, expiry, and Task-relevance checks. Similarity is a signal, not authorization or fact status.

What keyword, vector, and hybrid search each solve

MethodGood at retrievingCommon gaps or mistakes
KeywordNames, product identifiers, error codes, exact wording, and rare tokensParaphrases and natural-language variation
VectorSemantically similar records with different wordingExact identifiers; it may also rank a similar old version highly
HybridA union of lexical and semantic candidatesIt still does not understand version, permission, or business validity

Hybrid search can combine the two result sets with weighted scores or reciprocal rank fusion. It is often more robust than relying on a single path, but fusion only changes candidate order. It does not remove a revoked record. Subject, tenant, and read permission must be enforced before candidate payloads are read or ranked. Version and expiry may be validated during source-of-truth resolution, but they must be resolved before Context Assembly, with authorization checked again before model injection.

Walk the review-scheduling example through the pipeline

Candidate generation might return:

1. v1  available mornings; suitable for project reviews   keyword/vector: high
2. v2  only weekday afternoons remain available          vector: medium
3. v5  prefers 30-minute project reviews                  keyword: medium

The version resolver looks up the stable memory_id in the current view, discovers that v1 was superseded by v2, and prevents v1 from reaching reranking. The reranker then considers the Task of scheduling a review: v2 determines availability, while v5 determines duration. Both are relevant. Context Assembly receives a set of valid facts with different roles, not the top-1 text:

availability: weekday afternoons only (current v2)
meeting preference: 30-minute reviews (current v5)

If index synchronization lags and v1 still ranks first, source-of-truth resolution removes it anyway. “The index will be rebuilt later” is not a correctness guarantee. An index may supply candidates; it cannot define current truth.

Signals for reranking

After hard filtering, reranking can combine softer signals:

  • relevance to the current Task and its stage;
  • Memory type, such as availability, preference, or completed fact;
  • freshness and explicit expiry;
  • source authority and evidence strength;
  • whether the record is useful together with another current record.

The implementation may be a learned model, rules, or a two-stage combination. An opaque total score must not override permission, revocation, or current-version status. Hard constraints filter first and soft signals rank second, preserving an explanation for why a record did not enter Context.

The query need not merely copy the user’s last sentence. Runtime can construct a structured retrieval request with the subject, desired Memory types, time window, and Task stage. A scheduling Task can then request availability and meeting preferences explicitly instead of hoping that both records happen to use similar wording.

Similarity alone is not an evaluation

An offline dataset should label the current records that should be recalled, stale or unauthorized records that must be rejected, and the record set the Task ultimately requires. That supports several measures:

  • recall: whether required current facts reach the candidates and final result;
  • precision: whether returned records actually help the Task;
  • stale-hit rate: whether superseded, expired, or revoked content is used;
  • unsupported-use rate: whether content without valid source or permission enters Context.

Tests should deliberately lag the search index behind the version store and verify that current-view resolution still blocks old versions. Top-k similarity on a clean index misses the most dangerous Retrieval failure path.

Back to the problem

The old record is more similar because it contains “project review,” but it is no longer a usable fact. Ranking it first is a reasonable candidate-generation result. Passing it to the model is the Retrieval pipeline’s mistake.

Use keyword and vector search to increase recall, resolve current versions against the source of truth, enforce permission and validity as hard filters, and only then rerank by Task relevance, type, freshness, and authority. The Retrieval output becomes a trustworthy set of facts for the current Task rather than merely similar text.
