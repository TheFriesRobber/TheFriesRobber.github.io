Agent Memory 3: Isolate Write Authority by Writer

A background consolidation job that overrules an explicit preference shows why Memory mutation authority must follow writer identity, evidence, and action.

07/14/2026 Views
AgentMemoryData Governance

The problem

A user explicitly said, “Schedule meetings in the afternoon whenever possible.” Weeks later, a background consolidation job notices that the last three meetings occurred in the morning and changes the long-term preference to “morning meetings.”

The job did not invent the events. It treated observed behavior as authority to replace a user-approved preference. If the in-loop Agent, background consolidation, bulk import, and user editing all call the same write_memory operation with access to every record, write quality depends on a prompt that says “be careful.” One mistaken writer can then pollute every later Session.

The question is not merely who authenticated. It is whom this mutation represents, what evidence supports it, and which kind of Memory it may change.

A model cannot declare its own writer identity

The Memory service should obtain actor identity from the trusted execution environment rather than a model argument such as writer: user. A mutation should bind at least:

actor: background_consolidation
subject: user_42
namespace: preferences.schedule
action: propose_observation
evidence_class: behavioral_observation
source_refs: [calendar_event_7, calendar_event_9, calendar_event_12]

Together these fields form a constrained capability: an actor may perform specific actions for a specific subject and namespace with an allowed evidence class. A model may generate candidate content, but it cannot expand that capability.

Four writers should not share a write-all surface

WriterEvidence it may useReasonable actionsAuthority it should not have
In-loop AgentUser statements and Tool Results in the currently authorized ContextSubmit candidates; write explicit facts when policy allowsModify unrelated subjects or arbitrary history
Background consolidationRepeated observations in authorized historyAppend a lower-authority observation; propose a merge or supersessionOverride an explicit user statement
Import jobA mapped dataset and mapped fieldsWrite to a designated namespace with dataset provenanceWrite outside that mapping
User editInput confirmed in the user’s Memory UICorrect, revoke, or delete records the user may manageBypass privacy, retention, or third-party data rules

This is not a global writer priority. Authority must be scoped to subject, namespace, action, and evidence. Otherwise even “user edit has highest priority” could be misused to alter someone else’s records.

An Observation cannot overwrite an explicit preference

The consolidation job may submit “the last three meetings occurred in the morning,” because its sources support that observation. When it attempts to supersede “the user prefers afternoons,” however, the Memory service compares the mutation with its capability:

requested_action: supersede_explicit_preference
actor: background_consolidation
allowed_actions: [append_observation, propose_change]
decision: reject
reason: writer_cannot_override_explicit_user_statement

The system may retain the morning observation for schedule-conflict analysis or create a change proposal that requires confirmation. The current preference remains “afternoon.” If the user later changes it to “use mornings for now” in the Memory UI, the trusted user-edit actor can submit a new explicit version. The old preference is superseded rather than silently overwritten by a background job.

Conflict handling therefore considers claim scope and provenance together. Three morning meetings and a long-term afternoon preference may both be true: one describes events; the other describes intent. The system should not first reduce them to the same string and then choose by writer rank.

Least privilege must reach each mutation

Giving each writer a different API key is not enough. A “background key” that can write the entire store is still write-all authority under a new name. The service needs to validate for every mutation:

  • whether the actor may represent this subject;
  • whether the namespace belongs to its responsibility;
  • whether the action is append, propose, supersede, revoke, or delete;
  • whether the evidence class can support the target record type;
  • whether source references remain authorized and retained.

The Memory service, not the prompt, should enforce these checks and return stable rejection reason codes. Auditing can then answer who tried to change what from which sources, while Evals can verify that unauthorized mutations always fail.

Delegation must not bypass the boundary. When a parent Agent delegates consolidation to a child Agent, it passes a narrower capability. The child should not inherit every Memory permission of its parent or claim through natural language that it represents the user.

Use unauthorized mutations to test the isolation boundary

Tests need negative cases as well as successful writes: consolidation overriding an explicit preference, an import targeting the wrong namespace, an in-loop Agent modifying another subject, a user edit containing unauthorized third-party data, and a model forging an actor field.

Useful measures include unauthorized mutation acceptance rate, provenance completeness, and correct conflict escalation—not simply writer success rate. A safe writer may propose many candidates, but writes outside its capability must fail reliably.

Back to the problem

Observing morning meetings does not mean the user withdrew an afternoon preference. The failure occurred because consolidation and user editing shared mutation authority, so the system could not distinguish “observed” from “authorized by the user.”

Keep actor identity inside the trusted boundary and grant capabilities by subject, namespace, action, and evidence class. A background job can still detect change, but it can only append an observation or propose an update. Changing current Memory is reserved for a writer with the required evidence and authority.
