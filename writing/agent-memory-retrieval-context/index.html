How Retrieved Memory Enters Context

Connect candidate generation, current-view filtering, reranking, authorization, and the Context budget into one read decision.

07/24/2026 Views
Agent StateAgentMemoryRetrieval

The problem

A user asks, “Can you contact me this afternoon?” Vector search returns two highly similar Memory records:

0.94  v1: preferred_contact_time = morning
0.91  v2: preferred_contact_time = afternoon

The user has corrected v1; only v2 is current. If the system takes the top result directly, the more similar stale version becomes active again. If it simply raises top_k, the model sees a more complete contradiction.

A retrieval score expresses some form of match. It does not prove that a record is current, true, or authorized for use. Memory needs a layered decision chain before entering Context: first constrain the query with trusted identity and scope, then generate candidates inside that isolation boundary; filter them by the current view, record-level permission, source, and expiry; rerank them for the current Task; and finally let Context Assembly allocate budget across all sources.

Candidate generation only broadens the candidate set

Keyword, vector, and hybrid retrieval suit different kinds of matches:

  • keyword retrieval preserves exact names, IDs, and enumerated values;
  • vector retrieval finds semantically similar content with different wording;
  • hybrid retrieval combines the two signals.

They produce candidates, not verdicts. But the query must not begin against an unisolated global collection. A trusted Runtime should first bind the tenant, subject, namespace, or authorized resource partitions, and the Memory service should perform coarse query admission. Otherwise, unauthorized records can fill top_k, create side channels, or damage availability even if they are filtered later.

Within that constrained set, the embedding model, index revision, and query expansion can all change the score. Scores that have not been versioned and evaluated cannot be compared across configurations, much less used for record-level authorization. A candidate record should carry at least a stable memory_id, version, source reference, and index revision so that downstream code can validate it against the Memory service rather than consume only a text copy from the search engine.

Hard filters come before reranking

After coarse isolation, the candidate list still needs record-level checks that relevance cannot override:

FilterRejection condition
Current viewSuperseded, revoked, or deleted
PermissionThe current subject/actor may not read it
Tenant/scopeOutside the current isolation domain or resource scope
ExpiryPast its permitted use time
Source policyIts source type is not allowed for this Memory category

A trusted service should perform these checks against current state. The model cannot request “include old versions too” through an argument, and metadata in the search index cannot replace the Source of Truth.

After filtering, the opening candidates become:

v1 morning    → drop: superseded
v2 afternoon  → keep: current + authorized

This happens before reranking, so a highly similar unauthorized or stale record never gets another chance to compete.

Reranking answers what the current Task needs

Even after hard filtering, too many candidates may remain. Reranking can use:

  • relevance to the current Task;
  • freshness and remaining validity;
  • source/evidence class;
  • record specificity;
  • conflicts with the current instruction or another source;
  • retrieval configuration.

Reranking output should preserve the reason and score provenance. A high score does not promote an observation into an explicit user preference, and it does not turn Memory into an instruction. It only helps Context Assembly allocate attention among valid candidates.

If two current records genuinely conflict in scope, the right result may be to preserve the conflict and ask for clarification rather than let the higher score silently win.

Pinned, hot, and cold are policies inside Memory

The Memory service may assign records visibility tiers:

  • pinned: explicitly prioritized for matching tasks;
  • hot: recent or frequently relevant, but still query-dependent;
  • cold: considered only when explicitly recalled.

Pinned does not mean permanently included in every prompt, and it cannot override permission, expiry, or supersession. It is only a priority policy within Memory’s candidate set.

The final Model Turn must also contain the current user input, system constraints, unresolved Tool Results, files, and other data sources. Cross-source Context budget belongs to Context Assembly. The Memory service should return candidates with provenance and budget suggestions, not fill the entire window by itself.

Budget degradation should preserve semantics, not truncate the tail

Suppose the valid candidates are:

v2 contact_time=afternoon     required for task
timezone=Asia/Shanghai        required for interpretation
old meeting summaries        optional

When the budget is tight, the system should first preserve the current Task constraint and the timezone needed to interpret v2, then compress or drop unrelated summaries. Truncating by score or cutting from the tail can preserve “afternoon” while losing its timezone, or protect a long old summary while dropping the current correction.

Every include, drop, or compress decision should be tied to an assembly revision. When the result is wrong, this makes it possible to distinguish a missed candidate from a bad hard filter, incorrect reranking, or a mistaken global-budget decision.

Walk the opening query through the pipeline

A conceptual decision record could be:

query: contact availability this afternoon
query_scope:
  tenant: tenant_7
  subject: user_42
candidate_generation:
  returned: [contact_time@v1, contact_time@v2, timezone@v3]
hard_filter:
  dropped:
    - id: contact_time@v1
      reason: superseded
rerank:
  - contact_time@v2
  - timezone@v3
context_projection:
  included: [contact_time@v2, timezone@v3]
  provenance_preserved: true

This is a design example, not the current schema of a particular product. Its value is giving every layer one clear question and one owner.

Back to the problem

The opening v1 has the higher similarity score, but it should never enter Context because the current view has already established that v2 superseded it. V2 and the timezone pass permission, scope, and expiry checks, receive budget based on the current question, and enter the projection with their source and version intact.

Memory retrieval is therefore not “find the most similar text.” It first constrains the query to a trusted isolation domain, then ensures that every candidate is current and authorized, and only then decides which content is most useful to this Turn. Context Assembly still makes the final tradeoff across all sources.
