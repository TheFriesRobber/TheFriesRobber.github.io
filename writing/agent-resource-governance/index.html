How Budgets, Quotas, and Backpressure Work Together

Separate per-Run budgets, subject quotas, burst limits, and hotspot backpressure, then propagate admission decisions through the execution chain.

07/24/2026 Views
Agent ProductionAgentReliabilityCost

The problem

An Agent Run stays within its model-token limit but creates ten Child Runs in succession. Every child requests a Sandbox, calls an external Tool, and writes an Artifact. Average global CPU and Queue lag still look healthy, but this tenant has exhausted one Sandbox class and other requests are beginning to wait.

Setting max_tokens on the parent Run did not prevent the failure. Tokens are only one kind of cumulative consumption. They are not Sandbox concurrency, a tenant’s total allowance within a time window, or evidence of a hotspot on one queue partition.

Resource governance needs four kinds of limits to work together: a Budget constrains one execution, a Quota constrains a subject’s total use within a window, Rate Limits and concurrency limits protect burst capacity, and Backpressure carries downstream saturation back to the admission boundary that can act on it.

Give each limit the correct owner

MechanismTypical questionOwnerExample unit
Run budgetHow much may this execution consume?Runtime / delegation ownermodel tokens, Tool Calls, wall time
Subject/Tenant quotaHow much may a subject use within a window?Policy/admission serviceSandbox-seconds/hour, requests/min
Rate limitAre requests arriving too quickly?API/Tool admissionrequests/second
Concurrency limitHow many scarce slots are occupied at once?Resource scheduleractive Sandboxes, in-flight Tools
BackpressureCan the downstream system still accept work safely?Produced downstream, consumed by admissionqueue lag, oldest age, saturation

These units are not interchangeable. A Context token budget controls how much input one model turn can see. A financial budget may use currency or billing units. Sandbox capacity is measured in concurrency and duration. Calling all of them budget makes policy impossible to explain.

Delegation cannot create new allowance from nothing

The most dangerous default when a parent Run creates a Child Run is to give the child a fresh set of global limits. The parent can then evade its own constraints by spawning indefinitely.

A conceptual resource envelope could look like this:

{
  "run_id": "run_19",
  "remaining": {
    "model_tokens": 40000,
    "tool_calls": 30,
    "sandbox_seconds": 600
  },
  "concurrency": {
    "child_runs": 3,
    "sandboxes": 2
  },
  "deadline": "..."
}

When creating a child, the Runtime can:

  • reserve a portion of the parent’s remaining allowance and return the unused portion later;
  • share the same counter between parent and child, with atomic consumption;
  • reject delegation when it cannot construct a safe envelope.

Different resources need different strategies. Tokens and Sandbox-seconds are cumulative. A concurrency slot is a lease held at one point in time. A deadline normally takes the earlier of the parent’s deadline and the child’s requested deadline. One generic add-and-subtract rule cannot cover all of them.

Admission must happen before resource consumption

Checking quota after creating a Sandbox is already too late. An admission decision should be consumed before the system occupies scarce resources:

request
→ validate identity and tenant
→ check Run budget
→ check subject/tenant quota
→ check rate and concurrency
→ consume downstream backpressure
→ reserve capacity
→ admit / delay / reject / degrade

The decision should return a machine-readable reason such as run_budget_exhausted, tenant_concurrency_limit, or sandbox_pool_saturated. The parent Run can then stop, wait, reduce the task, or explain the limitation instead of inferring it from a timeout.

Reservations also need a lifecycle. If resource creation fails, the request is cancelled, or the worker crashes, an expiring lease or reconciler must release the reservation. Otherwise, capacity that was reserved but never used will gradually consume the system.

Averages hide hotspots

Suppose nine of ten queue partitions have no backlog while one partition accumulates long-running work from a single tenant. Average global lag may still be low even as that partition’s oldest message age and worker utilization deteriorate.

Backpressure therefore needs to be observed at the real contention key, such as:

  • tenant;
  • queue partition or message group;
  • Tool or provider;
  • Sandbox profile;
  • destination service.

The signal must reach an admission point that can change traffic. An alert on a dashboard is not backpressure. Allowing an already saturated worker to extend the Queue without bound merely turns overload into a longer durable backlog.

Admission may delay or reject work, reduce fan-out, choose a cheaper execution mode, or reserve a fair share. The fairness policy is a product decision. The requirement here is narrower: downstream pressure must reach upstream admission and act on hotspot dimensions, not only global averages.

A runtime limit can stop growth, not reverse an effect

When a Budget is exhausted during execution, the Runtime can stop admitting new Model Turns, Tools, or Child Runs, request cancellation of existing work, and wait for the agreed convergence boundary.

That does not reverse an external effect that has already been dispatched. After a Tool timeout or forced Sandbox termination, the effect outcome may still be unknown and require a query or reconciliation against its backend. Resource governance prevents further consumption; it does not fabricate a business rollback.

Separate cost facts from policy decisions

Observability can record the model, Tool, Sandbox, storage, and retry usage of every Attempt, then aggregate those facts by logical operation. It answers “what was consumed,” not “how much should the next execution be allowed to consume.”

A policy owner can consume these facts offline or nearline to adjust quotas, reservations, or degradation thresholds. Making the current bill itself the runtime authorization source would pull observation delay, recomputation, and price changes into the admission Source of Truth.

This article gives no fixed threshold or price because those values must come from concrete capacity, SLO, and cost data.

Back to the problem

Before creating children, the parent Run in the opening example should face a resource envelope: at most three concurrent Child Runs and two Sandbox slots, with Sandbox-seconds for each child reserved from the parent’s remaining allowance.

When that tenant has exhausted concurrency for the relevant Sandbox profile and the corresponding queue partition’s oldest age keeps rising, the backpressure signal reaches admission. Later spawn requests are delayed or rejected with tenant_sandbox_saturated. Existing children converge within the remaining budget and cannot continue producing unbounded fan-out.

max_tokens therefore solves only one local problem. Complete governance models Budget, Quota, Rate Limit, Concurrency, and Backpressure separately by resource type and responsible subject, then combines them before the resource is consumed.
