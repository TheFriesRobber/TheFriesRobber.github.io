Context Engineering 2: How Context Should Degrade under Budget Pressure

Replace tail truncation with source quotas, priorities, and layered degradation when Context exceeds its budget.

07/15/2026 Views
AgentContext EngineeringRuntime

The problem

Suppose an Agent is updating a design document from project files. Before the next Model Turn, Context Assembly has collected:

ContentEstimated tokensPurpose
System instructions and safety constraints2,500Define behavioral boundaries
Current Task and latest user requirements1,500State what this request must accomplish
Tool definitions3,000Tell the model which Tools are available
Recent conversation5,000Preserve active reasoning and corrections
File excerpts and Tool Results12,000Provide evidence required to edit the document
Earlier history and Memory7,000Supply background and prior decisions

This synthetic example totals 31,000 tokens. Suppose the model has a 32,000-token context window, but the system must reserve 4,000 tokens for output and another 2,000 for estimation error and protocol overhead. Only 26,000 tokens remain for input.

The simplest response is to delete the oldest messages first or tail-truncate the final string. That deletion order reflects position in an array, not value to the current Task. The system may remove a compatibility requirement that the user confirmed earlier while retaining two copies of the same build log.

Exceeding the context window is therefore not a string-length problem. It is an information-selection problem: which content must remain verbatim, which can be compressed, which can be retrieved on demand, and which can safely be dropped?

Calculate the usable budget before assigning the whole window to input

A model’s published context window usually accommodates both input and output. If the Runtime treats the full window as its input limit, generation may hit the boundary before it finishes. If local token estimates differ from the provider’s actual count, the request may not fail until after submission.

Start with a simple relationship:

input budget
= context window
- reserved output
- protocol and estimation margin

reserved output is not a universal constant. A request that returns one classification label does not need the same reserve as one that generates a complete report. Tool definitions, images, and provider-injected control information may also consume input. The margin should therefore come from measurements of real requests, not from one permanent percentage.

This calculation answers only “how much can fit?” It does not yet answer “what should fit?”

Budget candidates need semantics

Once Assembly has flattened every source into one large string, the Budget layer can see token counts but cannot tell whether it is removing a safety constraint or a duplicate log.

A better input preserves each candidate’s source and purpose:

{
  "id": "file_chunk_27",
  "source": "file",
  "role": "evidence",
  "tokens": 1800,
  "priority": 70,
  "degradation": ["full", "excerpt", "reference"],
  "provenance": {"file_id": "design_4", "revision": 8}
}

Here, priority is only one policy input; it must not determine the result by itself. A safety constraint with low task relevance still cannot be removed. Highly relevant file content may be ineligible because the current user lacks permission to read it. Context Assembly should resolve permissions, source roles, and conflicts first. Budgeting chooses only among eligible candidates.

Candidates can be grouped by their degradation behavior:

ClassMeaningCommon examples
pinnedRequired for the current request to remain valid; cannot be removed silentlySystem instructions, current user requirements, output Schema
compressibleCan preserve its main meaning in a shorter formConversation from completed phases, repeated Tool logs
retrievableKeep only a summary or reference now, then load the full content if neededLarge files, complete search results, Artifacts
droppableRemoving it does not change current Task constraints or primary evidenceDuplicate excerpts, low-relevance candidates, stale intermediate output

These are not permanent labels attached to each source type. A user-mandated passage in one file may be pinned while the remaining sections are retrievable. A Tool error under active repair should retain its original arguments, while an old log from a successful operation can be compressed.

Source quotas are caps, not reserved seats

Quotas for history, Memory, files, and Tool Results can prevent one source from filling the entire window. A quota should not mean “reserve this share even when the source has nothing useful to contribute.”

If the current Task does not use Memory, there is no reason to include irrelevant preferences merely to fill memory=10%. Conversely, if editing the document requires two critical chapters, files may consume available shared capacity as long as they do not displace hard constraints or the output reserve.

A more useful policy is:

  1. Satisfy every pinned candidate first.
  2. Apply hard caps to sources that can grow without bound.
  3. Let eligible candidates compete for the remaining space according to Task phase and evidence value.
  4. Return unused quota to a shared pool instead of filling it artificially.

If pinned content alone exceeds the input budget, the system still must not truncate it silently. It should narrow the Tool Surface, ask the user to reduce the Task, or return an explicit error that Context cannot be assembled safely. pinned means “do not drop without saying so,” not “may grow without limit.”

Degradation should follow a predefined ladder

Return to the 31,000-token example. The system must remove at least 5,000 tokens. It could proceed as follows:

31,000  original candidates
 -2,000 remove duplicate Tool logs and duplicate file excerpts
 -4,000 replace 5,000 tokens of history from a completed phase
        with a 1,000-token checkpoint summary
=25,000 sent as model input

This path does not truncate an arbitrary string or remove a user requirement. The complete earlier history remains in the raw record; the next Model Turn uses only the summary with its source range. If file content later grows further, it can degrade from full to excerpt, then to a reference that can be resolved on demand.

One general degradation ladder is:

deduplicate
→ narrow the Tool Surface or remove unused Schemas
→ compress stable history
→ replace large content with excerpts or references
→ drop low-value candidates
→ reject or reduce the Task

The exact order still depends on the Task. An Agent in the middle of a Tool invocation cannot save tokens by removing an unfinished Tool Call and Tool Result pair. A Task that requires source quotations cannot replace every file with a summary. Degradation policy must understand the current Task phase, not merely the source name.

Record every degradation decision

When the model misses a constraint, the final prompt alone does not explain why. The constraint may never have been retrieved, may have passed permission checks but lost its budget allocation, or may have been distorted by a summary.

The Budget layer can record a compact decision for each candidate:

{
  "candidate_id": "tool_result_18",
  "decision": "summarized",
  "from_tokens": 3200,
  "to_tokens": 480,
  "reason": "completed_phase",
  "summary_id": "summary_9"
}

These records allow the system to evaluate three separate questions: did important information become a candidate, did the Budget policy retain it, and did the model use it correctly after seeing it? Overall Task success alone makes it difficult to locate which layer failed.

How to evaluate a degradation policy

Lower token usage does not imply a better policy. A system that deletes every input uses the fewest tokens and cannot complete the Task.

At minimum, evaluate together:

  • whether required constraints and critical evidence enter the final input;
  • whether facts, instructions, and provenance in compressed content remain recoverable;
  • whether the model repeatedly reloads content that was just removed;
  • how success rate, latency, and token usage change on the same Task set;
  • which requests end in “reduce or reject the Task,” and whether those outcomes are justified.

This evaluation covers a Budget policy across sources. How Memory classifies pinned, hot, and cold content, and how long history produces a reliable summary, still require their own policies.

Back to the problem

When Context exceeds its budget, the Runtime is not handling one oversized string. It is handling information with different purposes and different degradation options.

Reserve output and estimation capacity first. Then let semantic candidates enter a degradation ladder according to whether they are pinned, compressible, retrievable, or droppable. Only then can the system explain what it retained and why it removed something else.

Simple truncation only guarantees a shorter request. Structured degradation attempts to preserve a valid Task.

Follow-up questions

  • How should stable long history produce an incrementally maintainable summary with source ranges?
  • How should Memory divide its own content into pinned, hot, and cold tiers?
  • How should Context recall, contamination, conflict handling, and budget efficiency be evaluated separately?
