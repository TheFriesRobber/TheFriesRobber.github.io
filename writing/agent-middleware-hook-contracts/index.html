Agent Runtime 12: Define an Execution Contract for Middleware Hooks

07/15/2026 Views
AgentRuntimeMiddleware

The problem

An Agent Runtime registers three Hooks before calling a model:

  • a capability policy removes Tools unavailable under the current permissions;
  • a request transformer renders the internal request as a provider payload;
  • tracing records structured information about the instructions and Tools the model actually received rather than capturing complete sensitive content by default.

The initial Tool candidates are:

read_file, write_file, delete_file

The current user has read and write permissions, so delete_file must not enter the model input. If Hooks merely execute in registration order, several different outcomes are possible:

transform → policy
the provider payload already contains delete_file; changing the internal list is too late

trace → policy → transform
the trace records a Tool surface that the model never received

policy → transform → trace
policy narrows the capabilities first, and the trace records the final request

Each Hook looks reasonable in isolation, yet changing their order changes both security and the observable facts. The name beforeModel says only that a callback runs before the model. It does not say who may change which fields, who may block the call, or whether tracing observes the request before or after mutation.

A Hook becomes a stable Runtime extension point only when it has a composition contract—not when the Runtime exposes a large set of callback names.

Registration order cannot define execution semantics

The easiest implementation stores Hooks in an array and calls them in order:

for hook in before_model_hooks:
    request = await hook(request)

This code lets “who registered first” decide policy precedence, mutation authority, and the observation boundary at the same time. Adding a plugin—or merely changing initialization order—can change the final Tool surface.

A safer design defines phases first, then allows explicit priority or dependency within a phase:

trusted context
  → policy decision
  → request transformation
  → observation scope opens on the final request
  → model call
  → result normalization
  → output policy
  → observation scope closes with the final result

Every Runtime does not need these exact phase names. The sequence expresses a more basic constraint: capabilities should be narrowed according to trusted permissions before the request is rendered or sent; transformation must not re-expand capabilities already removed by policy; and an observer must not open its span until the final request exists and must close it after result normalization so the observed version is unambiguous.

Hook phases express authority and fact boundaries. Position in a registration array should not silently change those boundaries.

First distinguish what a Hook is allowed to do

Hook systems tend to lose control not because they have too many callbacks, but because every callback receives the same authority by default. Start by separating a few kinds of behavior:

KindWhat it may doWhat it should not do
Policyallow, deny, require approval, or narrow capabilitysilently add a Tool or fabricate trusted context
Transformationproduce a new typed value from approved inputchange identity, permissions, or the audit subject
Controlshort-circuit, fall back, or choose an explicit branchreturn an arbitrary string indistinguishable from a normal result
Observationrecord events, metrics, and tracesrewrite a business result or secretly initiate another business action

This is not an attempt to create a callback taxonomy. It limits mutation authority. Tracing that needs only to read the final request should not receive a mutable request. A request transformer responsible only for provider shaping should not be able to replace the subject or credential injected by the Runtime.

One simple approach is for transformations to return new values rather than share a mutable object:

import asyncio


decision = policy.evaluate(context, request)
if decision.denied:
    return denied_result(decision.reason)

provider_request = transform(decision.allowed_request)
with trace.model_span(provider_request) as span:
    try:
        response = await model.generate(provider_request)
    except asyncio.CancelledError:
        span.record_cancelled()
        raise
    except BaseException as error:
        span.record_error(error)
        raise
    else:
        span.record_result(response)

model_span is a conceptual interface, not the API of a particular SDK. The example assumes that record_* methods and scope cleanup are no-throw or write to a local buffer first: observation failures are recorded and retried separately, and must not replace a model result, original exception, or cancellation. The example expresses that observation begins after the final provider request exists, and that the same observation scope closes correctly whether the model succeeds, raises an exception, or is cancelled.

Return to the opening example. Policy receives the three Tool candidates plus trusted permissions and produces an allowed request containing only read_file and write_file. The transformer can render only that set. The trace records Tool names or a stable hash from the final provider request. The transformer cannot reintroduce delete_file by rereading the original registry.

A short-circuit must be a visible result

A policy that rejects a high-risk Tool, a cache hit that skips a model call, and an exhausted budget may all need to short-circuit execution.

If a Hook returns only None to mean “do not continue,” the caller has no reliable way to distinguish denial, cache hit, and a Hook bug. A clearer contract returns a typed outcome:

continue(transformed_request)
deny(reason, policy_id)
require_approval(action_id)
use_cached(response_id)
fail(error_class, retryable)

An observer can then record why the model was never called, and the Run can decide whether to wait for user approval, use a cached result, or enter a failed state. Each outcome must also define the phase where execution resumes: deny, require_approval, and fail do not call the model or Tool handler; use_cached skips the model call, but the cached response still passes through the same normalization and output policy as a live response; every branch emits an observable execution event. Otherwise the cache becomes a hidden path around result policy.

A short-circuit changes control flow, so it must become an execution fact rather than remain an early return hidden inside one callback.

Before and After are not usually symmetric lists

Some Hooks manage resources in pairs. A tracing span opens before a call and closes afterward. A temporary credential may be injected before a Tool and revoked when the Tool exits.

These Hooks behave more like nested scopes:

before A
  before B
    execute
  after B
after A

If after callbacks also run in registration order, A may close a resource that B is still using. Whether cleanup runs in reverse order should be part of the Runtime contract, not something every Hook author has to guess.

Cancellation must follow the same unwind contract: scopes already entered clean up in reverse order, so resources such as temporary credentials are not left behind. A cleanup error should be recorded separately rather than replace the original cancellation. Whether an after Hook with an external side effect may be replayed follows the delivery contract defined later.

Not every after Hook belongs to the same nesting model. A metrics observer may consume a completed event, while an output policy must run before content reaches the user or enters the next Model Turn’s Context. Putting both into one afterModel array once again delegates different semantics to registration order.

A Hook failure must not rewrite a Tool result that already happened

Ordering problems appear on the happy path; retries make the failure contract even more important.

Suppose write_file successfully saves a report. An afterTool Hook then sends a trace event to a remote collector, but the collector times out. If middleware marks the whole chain as failed, an outer retry may execute write_file again:

attempt 1: write_file succeeds → trace delivery times out
attempt 2: write_file succeeds again

The second write is not a tracing retry. It repeats the business side effect. The Runtime must preserve two separate facts:

Tool Execution: succeeded, artifact = report.md@v3
Trace delivery: failed, pending an independent retry or degradation

Each Hook kind therefore needs a predefined failure policy:

  • If Policy cannot decide, a high-risk action generally should not continue; fail closed or require approval.
  • If Transformation fails, the model or Tool call has not happened yet, so the current phase can stop. Retrying is easy to reason about only when the transformation itself is pure.
  • If Observation fails, the Runtime generally should not repeat a completed business action. It can buffer locally, retry the observation separately, or mark observability as degraded.
  • Strict compliance may require a failed observation channel to block later actions, but that constraint must execute before the action. It cannot retroactively pretend an existing side effect did not occur.

“Generally” matters. Different products can choose different policies. The contract does not prescribe one universal answer; it prevents accidental exception propagation from deciding whether a failure blocks, degrades, or recovers independently.

Retry and replay need stable identity

When a Runtime retries a model call, it can rerun pure validation and transformation. A metric observer can be replayed safely only when the metric intentionally counts physical Attempts, tolerates duplicates, or deduplicates by stable event identity. Once a Hook has an external side effect, replay can produce duplicates.

Suppose a Hook sends a notification after a Tool finishes. The process crashes after the notification succeeds but before a checkpoint records that fact. Recovery enters afterTool again. If the Hook generates a new message ID, the user receives two notifications.

This kind of action should not hide inside a callback as incidental work. There are two safer choices:

  1. Promote the notification to an explicit Tool Execution whose logical identity, Attempts, and result are stored by the Runtime.
  2. If it genuinely belongs to an infrastructure Hook, use a stable event_id, let the downstream system deduplicate it, and retain delivery state.

Replay then means another delivery of the same Hook event, not a new business intent. Observers for metrics, tracing, billing, and audit must likewise state whether they accept at-least-once delivery, require an idempotent upsert, or need a durable outbox. A stable event_id alone cannot prevent duplicate side effects; repeated deliveries converge on one result only when the downstream system deduplicates them or performs an idempotent upsert.

Contract tests should verify composition, not only individual Hooks

Testing each callback’s return value is not enough. Composition semantics are the part that is easy to get wrong. A minimal contract-test suite can verify that:

  • capability policy runs before provider payload generation;
  • a transformer cannot add a Tool removed by policy;
  • the model or Tool handler is not called after deny or require_approval;
  • a cached response still passes through normalization and output policy;
  • paired scopes unwind their after behavior in reverse order;
  • cancellation unwinds entered scopes in reverse order, and cleanup errors do not replace the original cancellation;
  • observer failure does not turn a successful Tool Execution into failed;
  • replay follows its declared delivery contract: at-least-once delivery reuses one event_id and may deliver duplicates, while only idempotent or deduplicated delivery is tested for a single side effect;
  • the trace distinguishes original candidates, policy decision, and final request.

These tests do not need a real model. A fake handler that records call order can verify whether the Runtime’s extension contract is stable. Model evals test whether a Hook’s policy is effective; contract tests first establish that the policy executes in the intended place.

Trace content also needs a boundary. Structural metadata, stable IDs, phases, states, and redacted summaries are generally enough by default. Complete instructions or provider payloads should be captured only when explicitly needed and must be governed by redaction, access control, and a retention policy. Credentials, secrets, and unnecessary user content should not enter a trace.

Back to the problem

beforeModel, afterModel, beforeTool, and afterTool provide temporal positions, not execution semantics.

A stable Hook system must also answer: in what order do policy, transformation, control, and observation run; which fields may each kind change; how does a short-circuit become observable; does an exception block, degrade, or recover independently; and can retry or replay duplicate a side effect?

Once those contracts are explicit, Hooks can extend a Runtime safely. Otherwise every new callback adds a hidden control-flow branch, and the true execution order can be discovered only by reading initialization code.
