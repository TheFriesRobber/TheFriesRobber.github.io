Agent Sandbox 4: How a Workspace Survives Runtime Replacement

Separate Session, Runtime, Volume, and Lease, then define a path contract that lets an Agent continue after Runtime replacement.

07/14/2026 Views
AgentSandboxDistributed Systems

The problem

An Agent has spent half an hour writing /workspace/project/report.md. Runtime A crashes, and the file is gone after the Control Plane starts Runtime B.

/workspace was supposed to be the Workspace: the editable file area that survives Runtime replacement. The system restores the same Session Context, which preserves conversation and execution context but not file bytes. The model knows what to do next and B can execute commands, yet /workspace was merely A’s local container filesystem. The Session persisted; the working files still died with the Runtime.

Persisting the entire container disk appears to solve the problem, but creates others: caches and temporary credentials survive indefinitely, old and new Runtimes may write concurrently, final deliverables have no independent version, and the system cannot explain whether a path belongs to a Session, a Task, or one machine.

A persistent Workspace is not a longer-lived container disk. It separates the logical work area, replaceable compute, physical storage, and current write authority.

Four identities cannot share one Sandbox ID

ObjectWhat it representsLifecycle
SessionA resumable interaction and resource scopeMay span Runs and Runtimes
RuntimeThe process currently executing commandsMay fail, upgrade, and be replaced
VolumeStorage that preserves Workspace bytesMay outlive a Runtime
LeaseWhether one Runtime generation currently owns the WorkspaceTime-bounded and replaceable

Their relationship is:

Session session_12
  └─ Workspace workspace_7
       └─ Volume volume_31

Runtime A ── lease generation 41 ──> workspace_7  (expired)
Runtime B ── lease generation 42 ──> workspace_7  (current)

The Session preserves logical continuity, the Volume preserves bytes, the Runtime supplies compute, and the Lease identifies the current owner. Kubernetes PersistentVolumes similarly have lifecycles independent of individual Pods. A replacement Pod receives a new UID; the old Pod does not move to a new machine and continue existing.

Workspace identity comes before Volume identity

The application cares about workspace_7, not a cloud disk or PVC name. A Workspace record might contain:

{
  "workspace_id": "workspace_7",
  "session_id": "session_12",
  "storage_binding": {
    "provider": "pvc",
    "volume_id": "volume_31",
    "binding_version": 9
  },
  "path_contract_version": 2,
  "status": "bound"
}

The Volume is the current physical implementation. A storage migration, snapshot restore, or cross-region copy may change volume_id while preserving the Workspace identity and its internal paths.

Conversely, the presence of /workspace inside a Runtime does not prove a binding. Both the Control Plane and an initialization probe should verify the workspace_id, Session, and binding version so that an empty directory or wrong Volume cannot impersonate the Workspace.

The path contract separates persistent, temporary, and deliverable data

Agent Tools need stable paths, but those paths should not share one retention policy:

/workspace/                 persistent across Runtimes
  project/                  user- and Agent-editable files
  .agent/                   recoverable working metadata

/tmp/agent/                 local to the current Runtime
  downloads/
  caches/

/artifacts/                 read-only or controlled Artifact views
  input/
  output/

This is a virtual-filesystem (VFS) path contract, not a requirement that one filesystem implement every path. /workspace may be a persistent Volume, /tmp/agent may use local ephemeral disk, and an Artifact gateway may expose object-storage content under /artifacts.

Here, fencing means enforcing rejection of writes from an expired generation at the storage or write boundary. A Lease field does not provide that enforcement by itself.

Path classAfter Runtime replacementDirectly writableTypical use
persistentpreservedyes, under Lease and fencing rulesdrafts, code, intermediate work
temporarydiscardedyesextraction directories, caches, reproducible downloads
artifactfollows Artifact lifecyclenormally read-only; edits export a new versioninputs and final deliverables

Persisting everything turns temporary secrets and unbounded caches into retention risks. Leaving every output in the Workspace deprives final deliverables of stable identity, version, and download authorization.

First binding establishes the logical relationship first

When a new Session first needs a Workspace:

1. Create or load workspace_7
2. Allocate volume_31 for workspace_7
3. Conditionally commit storage binding version 9
4. Obtain a Lease for Runtime generation 41
5. Mount volume_31 and verify its Workspace marker inside the Runtime
6. Initialize the path contract
7. Publish Ready

A Workspace marker may contain the Workspace identity and path-contract version, but it is not the sole Source of Truth. A disk restored from an old snapshot may contain a stale marker. The Runtime observation must agree with the current Control Plane binding and Lease.

If Volume allocation succeeds but the binding commit fails, a Controller should query by allocation identity and either claim or reclaim the Volume. Silently allocating another Volume creates two content branches that both appear to belong to one Workspace.

Runtime replacement remounts; it does not copy the Session

After A crashes:

1. Lease generation 41 expires or is revoked
2. Generation 42 obtains a new Lease
3. Runtime B mounts volume_31, the current binding for workspace_7
4. B verifies the filesystem and path contract
5. B publishes Sandbox Ready
6. The Run owner restores execution from a Checkpoint or Event Log, then reads report.md

Workspace recovery and Agent execution recovery are separate. The Volume restores files. The Sandbox owner publishes Sandbox Ready after mount, path, Lease, and fencing checks succeed. The Run owner uses a Checkpoint or Event Log to determine how far execution progressed and which external effects still need reconciliation. That process may end in resumed, remain waiting, or require manual_recovery; it is not a prerequisite that should be folded into Sandbox Ready.

Messages stored in the Workspace do not replace execution state. A Checkpoint stored in a database cannot recover bytes that were never persisted.

Safe takeover must fence the lost Runtime

Lease expiry says that the Control Plane no longer authorizes A. It does not prove that A stopped. If storage permits A and B to remain attached, A may resume writing after its network recovers.

Safe takeover needs at least one enforceable fence:

  • storage validates a generation-scoped write token;
  • infrastructure forcibly detaches the old mount before switching;
  • storage guarantees a single writer, and the old attachment is confirmed released;
  • every write first lands in an isolated overlay or immutable Blob, then the Workspace owner atomically checks the current Lease generation and expected base revision—the logical Workspace commit on which those changes were based—and advances the visible revision only if that base still equals the currently visible revision.

Kubernetes PersistentVolume access modes describe scheduling and mounting, but the official documentation warns that they do not necessarily enforce write protection after mount. The name ReadWriteOnce alone does not prove that an old business writer has been fenced.

If the system cannot prove that A lost write access, B can recover read-only or enter takeover_pending rather than permit unbounded dual writes. The availability tradeoff depends on the acceptable risk of data loss, but it must be explicit.

Workspace revisions make important writes explainable

A regular filesystem provides paths and bytes, not logical Agent commits. A Workspace owner may establish revisions for important changes:

{
  "workspace_id": "workspace_7",
  "revision": 18,
  "base_revision": 17,
  "lease_generation": 42,
  "changes": [
    {"path": "project/report.md", "blob_ref": "sha256:..."}
  ]
}

When a Runtime directly modifies a shared Volume, this revision can track and detect conflicts but cannot fence writes. The old Runtime may overwrite bytes before submitting a revision. Storage-level fencing, reliable detach, or an enforced single-writer attachment must therefore complete before B receives a writable mount.

If Runtimes instead write only to isolated overlays or immutable Blobs, Tool completion, a Checkpoint, or Artifact export can establish a revision boundary. In one conditional commit, the Workspace owner verifies the current Lease generation and expected base_revision, then advances the visible revision. lease_generation is an input to that owner-side check; the field alone does not prove that the caller remains current.

For a code repository, a Git commit can provide part of the revision identity. General files still need a minimal snapshot or manifest mechanism defined by the Workspace service.

Workspace, Memory, and control state are not substitutes

These three persistent state classes are often called “Agent memory,” but have different owners and recovery paths:

StateContentsRecovery use
Workspacefiles, code, editable intermediate resultsremount and verify revision
Memoryuser preferences, long-term facts, retrieved contentreload under scope and policy
Control stateRun, Tool Execution, Lease, Checkpointrecover through state machines and Event Logs

Writing run_status.json into a Workspace does not create atomic state transitions. A database row containing the path to report.md does not prove that the file still exists. Each class retains its own Source of Truth and connects through identities.

Deletion and reclamation are layered too

Stopping a Runtime releases compute; it need not delete the Workspace. Ending a Session need not immediately erase a Volume:

Runtime stopped
  → revoke Lease
  → detach Volume
  → Workspace enters retained
  → retention expires
  → check snapshots and Artifact references
  → delete Volume

A final report exported as an Artifact may follow its delivery retention while Workspace drafts are later removed. Conversely, deleting an Artifact download entry should not erase the entire Workspace.

Cleanup failures need durable state and a retry owner. Deleting the Workspace row while leaving an unclaimed Volume is not successful deletion; it has only removed the identity needed to track the leak.

Back to the problem

Runtime B cannot find report.md because the file never left A’s ephemeral filesystem, not because Session restoration failed.

The corrected model gives the Session a stable Workspace, binds that Workspace to replaceable storage, and leaves compute to the Runtime. Lease and fencing determine which generation may write. B obtains a new generation, remounts the same Volume, validates the path contract, and then combines it with Run recovery. A cannot publish changes from its stale generation even if it reconnects.

Persisting a Workspace is not persisting a machine. It separates file identity that should survive Runtime replacement from compute, caches, and execution authority that should not.
