Agent 16: Who Should Own the Execution State of Delegated Work?

Choose a parent Run, Child Run, Job, or Workflow according to completion ownership, lifecycle, durability, cancellation, and result consumption.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentDelegationWorkflows

The problem

An Agent encounters two subproblems:

  1. Read two public documents in parallel and compare their differences.
  2. Wait for a batch of external approvals that may take hours and cross process lifetimes, then continue execution.

If both become spawn subagent, the second gives durability responsibility to an in-process object. If both are promoted to a Workflow, the first bears unnecessary persistence and operational cost. The source of a subproblem does not determine its execution primitive. The owner of completion state does.

Find the completion owner first

A delegation proposal describes only what should be solved and what result is expected. Choosing an execution primitive requires answering:

  • Who can decide that the work is complete?
  • Must the work continue after the parent exits?
  • Does it need independent permission, Context, or Workspace?
  • How does cancellation propagate?
  • Who validates and consumes the result?
  • Who recovers after a process failure?

If the parent Run must remain online, await all results, and own them, an in-process child task or Child Run may be sufficient. If the work must continue across restarts, completion ownership should move to a Job or Workflow system.

Four choices serve different lifecycles

Execution formCompletion ownerAppropriate cases
Continue in the parent RunParent RunShort, sequential work that needs no isolation
Child Run / SubAgentParent Run or an explicit child ownerIndependent Context, Tool surface, or parallel reasoning
Background JobQueue/worker + business stateAsynchronous work with one explicit task result
Durable WorkflowWorkflow state ownerMultiple steps, long waits, compensation, and cross-process recovery

These are not capability levels. A Workflow is not “more intelligent” than a Child Run. It takes responsibility for different durability and state guarantees.

A Child Run is not a copy of its parent Agent

Copying every parent Context item, Tool, and credential into a Child Run by default is expensive and dangerous. A model-generated Spawn Request is still an untrusted proposal and may express only:

subproblem
input references
requested capabilities
expected result schema

The trusted Runtime resolves an Agent definition from the registry, assigns child identity, derives and narrows a delegation grant from the parent’s authorization, chooses the actual Tool surface, budget, and Workspace owner, and finally creates an unforgeable execution envelope. The model cannot choose the identity chain, credentials, or final authorization set.

Creation must cross explicit states:

dedup by parent_run_id + spawn_request_id
→ admission
→ reserve child_run_id in preparing
→ compile delegation envelope
→ atomically persist ready + dispatch intent
→ idempotent dispatch by child_run_id
→ collect and validate result

Spawn retries reuse a stable request identity so that a timeout does not create multiple Child Runs from one proposal. If the process exits after reserve, a reconciler can continue compilation or converge the record to an explicit failure. If it exits after ready but before dispatch, a durable dispatch intent—or a scheduler that claims ready records—makes the work discoverable again. Persisting ready and then sending one in-memory Queue notification can strand a child forever.

The parent still needs the child handle, cancellation relationship, and result-validation method. A natural-language response that says “done” does not prove an external effect. The parent must consume a structured result or queryable evidence.

Pi Core provides Agent/Harness, follow-up, and host-control boundaries, but it does not contain a complete durable delegation protocol. A host may implement Child Runs on those boundaries, but it must not describe the workflow capability as something Pi currently provides automatically.

Jobs and Workflows take over durable responsibility

A background Job fits one independently identifiable asynchronous task whose result can be retried or queried. A Queue may deliver more than once, so the Job still needs a logical operation ID, idempotency, and a business fact owner.

A Durable Workflow fits multiple steps, Timers, external Signals, and compensation relationships. The Workflow owns control progress; the business database still owns business facts. Putting all long-lived state into Workflow history creates one kind of double ownership, while inferring all control progress from business tables creates another.

The key question in choosing a Job or Workflow is not whether expected duration exceeds a particular number of minutes. It is who continues to own completion, waiting, and recovery after the parent process exits.

Choose for the two subproblems

For the public-document comparison:

  • the two reads affect only the current answer;
  • the parent Run remains online and waits for the results;
  • the children may share read-only inputs but use a narrowed Tool surface;
  • cancelling the parent should request convergence from both children.

A Child Run or parent-level structured concurrency is sufficient.

For the long-running approvals:

  • the parent process may exit;
  • approval events arrive from an external system;
  • durable timers, signals, and recovery are required;
  • business actions may require compensation.

The durable Workflow should therefore own completion. The parent receives only a workflow handle and may end the current interaction or resume later. It should not keep an in-memory SubAgent waiting.

Several children may also finish only partially. The parent declares its result policy before delegation:

PolicyParent behavior
all_requiredany child failure prevents completion of the goal
partial_allowedretain successful results and expose the missing coverage
fallbacklet the parent Run or another capability take over after failure

The policy belongs to the owner of the final goal, not to a child. A child reports its own completed, partial, failed, or cancelled state while keeping effect outcome, Artifacts, and evidence separate. Only after validation does the parent decide whether the whole Run may continue.

A Plan is not a prerequisite for Delegation

A Plan item may produce a delegation proposal, but a simple task may also discover a subproblem directly. Conversely, some items in a complex Plan should still run sequentially in the parent.

Keeping the two abstractions separate has two benefits:

  • a Plan revision does not rewrite the history of Jobs or Workflows already created;
  • Delegation chooses an owner according to the actual lifecycle instead of mechanically spawning from planner output.

Back to the problem

The two subproblems should not use the same primitive merely because both are called “subtasks”:

  • the short document comparison is owned by the parent Run or Child Runs, with the parent online to wait, validate, and converge;
  • the long-running approval is owned by a durable Workflow that receives Signals, advances state, and handles compensation across restarts.

When selecting a Delegation primitive, first ask who owns completion state and recovery responsibility. Only then ask whether the work needs separate Context, permission, Workspace, and budget. After choosing a Child Run, creation still passes through deduplication, admission, identity reserve, envelope compilation, durable dispatch intent, and result validation; the parent continues to own any partial-result policy. Multi-Agent is not the default answer. A new execution boundary is valuable only when ownership and isolation genuinely change.
