LLM Infra 02: Why Latency, Throughput, and Cost Cannot Be Optimized Separately

Separate TTFT, TPOT, end-to-end latency, throughput, goodput, and cost per Token, then turn performance goals into a service decision constrained by workload and quality.

07/29/2026 Views
LLM InfraInferenceSLOPerformance

The problem

A batching change increases aggregate tokens/s. The dashboard reports better throughput, yet interactive users wait longer for the first Token and some long requests are cancelled by clients before completion.

“Throughput improved” and “the experience got worse” can both be true because they observe different outcomes. The former counts how many Tokens the Runtime completes. The latter asks whether requests delivered useful output within a specified deadline.

This article asks how TTFT, TPOT, end-to-end latency, throughput, and cost should form an executable inference SLO instead of five objectives pulling in different directions.

Decompose one streaming request

At minimum, the path from a client sending a request to receiving the full response contains:

arrival
  → gateway / scheduler queue
  → prefill
  → first output token
  → repeated decode + streaming delivery
  → completion or cancellation

Common metrics cover different intervals:

MetricQuestion answered
TTFTHow long before the user sees the first useful output
TPOT / ITLWhether output progresses smoothly after the first Token
E2E latencyHow long the request takes from submission to completion
aggregate throughputHow many requests or Tokens the whole system processes in a window
per-user token rateThe generation speed experienced by one request

Metric definitions must also fix their measurement boundary. AIPerf measures TTFT from the client sending a request until it receives the first non-empty response chunk, so the value includes network time, queueing, and Prompt processing; one chunk may contain multiple Tokens. vLLM’s current per-request time_to_first_token_ms starts when the scheduler accepts the request and excludes scheduler queueing. Both are useful for diagnosis, but they are not directly comparable unless the boundary is stated.

This is also why “TTFT must be below one second” is not a complete SLO. Where does the clock start? Does the first reasoning chunk count as useful output? Does the boundary include the gateway and network? The contract must answer these questions.

Batching trades waiting time for throughput

Batching lets one model execution advance more Tokens at once and generally benefits aggregate throughput. Requests may have to wait for enough peers or for a scheduling opportunity, however, and sequences at different phases and lengths can interfere within the Batch.

Consider a synthetic scheduling result:

A1,00098%1%
B1,25082%9%

These numbers are conceptual inputs, not measurements. They show only that if Configuration B obtains a larger Batch by waiting longer, raw throughput can rise while TTFT attainment falls. Prefill or Decode work already performed for cancelled requests still appears in throughput, but it did not produce a completion that the user accepted.

Throughput should therefore not be maximized independently of deadlines, cancellation outcomes, and workload class.

Goodput adds delivery constraints to throughput

Mainstream serving Benchmarks usually define request goodput as the number of successful requests that satisfy every per-request latency SLO divided by test duration. This article also needs to include quality and output-protocol requirements in the product decision, so it explicitly calls the extended measure application goodput rather than presenting it as a built-in tool metric.

Conceptually:

application goodput =
  requests that jointly satisfy input/output, quality, TTFT, TPOT,
  and completion requirements
  / observation window

DistServe likewise uses request goodput based on TTFT and TPOT SLO attainment to compare deployment strategies. The important point is not to reuse that paper’s thresholds, but to apply the same idea: first evaluate a joint pass predicate for every request, then aggregate qualifying requests into effective capacity.

This changes how the earlier configurations should be evaluated. Configuration B has higher raw throughput, but for an interactive workload it may simply count unproductive work caused by waiting and cancellation as a benefit. For an offline Batch workload without a strict TTFT requirement, the same configuration may be appropriate.

Goodput must always include its qualifiers:

  • the workload envelope;
  • the TTFT, TPOT, or completion deadlines;
  • the required SLO attainment;
  • the model-quality and output-protocol requirements;
  • how failures, cancellations, and retries are counted.

Without these conditions, “higher goodput” becomes just as empty as raw throughput.

Cost needs the same effective-delivery denominator

GPU-hours alone combine idling, queueing, execution after cancellation, and failed retries. Cost per output Token alone may reward shorter or even truncated output.

A more useful cost view separates resource facts from delivery outcomes:

resource facts:
  input_tokens
  output_tokens_computed
  output_tokens_delivered
  execution_time
  cancelled_work
  retry_attempts

delivery outcomes:
  met_ttft
  met_tpot
  completed
  quality_gate_passed

The decision can then choose the appropriate denominator:

  • For fleet cost planning, use requests that meet the SLO per GPU-hour.
  • For Decode optimization, use qualifying output Tokens per GPU-hour.
  • For waste analysis, use cancelled or failed work as a share of total compute.

Reducing cost then means reducing the resources consumed by each qualifying delivery, not simply making the GPU busier.

Different workloads need different constraints

The workload envelope from the previous article now becomes useful.

Workload classPrimary constraintsSecondary constraintsMetric that should not be misused
Interactive chatTTFT, TPOT, cancellation rateCost per qualifying requestAggregate tokens/s alone
Asynchronous long generationCompletion deadline, success rateCost per qualifying outputExcessive emphasis on the first Token
Offline BatchCompletion within the window, failed rerunsGPU-hour, qualityOne per-request P95 as the only objective

These are not three unrelated monitoring systems. They share Token, execution, and outcome facts, but apply different constraints to decide whether work becomes goodput.

An executable SLO decision record might look like:

workload_class: interactive
workload_fingerprint: wl_7fd2
latency:
  per_request_lte_ms:
    ttft: 1500
    tpot: 80
outcome:
  completion_rate_gte: 0.99
  cancelled_after_start_lte: 0.01
quality:
  evaluation_suite: chat-contract-v3
capacity_metric:
  name: application_goodput_rps
  good_request_fraction_gte: 0.95
diagnostics:
  report_percentiles: [p50, p95, p99]

The fields are conceptual examples. The thresholds must come from specific product requirements and measurements. Every attempted request must be evaluated jointly for TTFT, TPOT, completion, and quality; application_goodput_rps = good_request_count / duration, while good_request_fraction = good_request_count / attempted_request_count. P95 and P99 remain useful diagnostic distributions, but they cannot replace the joint attainment rate.

Back to the problem

The increase in tokens/s after the batching change does not by itself prove that service improved. For an interactive workload, additional Tokens do not become goodput if they come from longer queues, continued execution after a timeout, or work that misses quality and delivery deadlines.

The right evaluation places the configuration under the same workload-specific contract. Do TTFT, TPOT, completion, and quality requirements still hold? Did the rate of qualifying requests improve? Did the cost of each qualifying delivery fall?

The next article’s Benchmark must reproduce all these constraints. Otherwise, even if it produces more tokens/s, it will not measure the service curve that capacity planning actually needs.
