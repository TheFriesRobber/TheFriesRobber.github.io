Agent Reliability 1: How Sources of Truth and Derived Views Divide Responsibility

A downstream reporting bug separates Sources of Truth from Derived Views through semantic ownership, lineage, and rebuild boundaries.

07/12/2026 Views
ArchitectureData ModelingContractsSource of Truth

The problem

Suppose a task system defines terminal outcome as a cross-system contract. The classification drives failure alerts, automatic retry, billing, and reporting. The Task owner adds cancelled_by_user and specifies that a user cancellation is not a system failure. The old event schema, however, sends downstream consumers only the raw task.status, without the authoritative outcome_class. The warehouse keeps its old rule and classifies every status other than succeeded as failed.

The dashboard exposes the problem first: user-cancelled tasks suddenly count as system failures. The most direct fix adds one condition to the query:

CASE
  WHEN status = 'cancelled_by_user' THEN 'cancelled'
  WHEN status != 'succeeded' THEN 'failed'
  ELSE 'succeeded'
END

The report looks correct again, but the alerting and retry consumers still use the old rule. When expired appears next month, several downstream systems interpret the new state independently again. The visible symptom has been patched, but the authoritative classification is still absent from the propagation contract and the consumer’s unsafe catch-all is unchanged.

This class of failure requires one question first: which layer owns the decision about what a state means, and which layers only read and reshape that decision?

The layer that finds the error may not own the meaning

The dashboard owns presentation, not necessarily the business definition of task state. The warehouse owns an analytical model, not necessarily the decision about whether cancellation is a failure. An event stream records upstream changes, but that alone does not make it the owner of every meaning.

To locate the repair boundary, ask four questions:

  1. Which component owns the legal transition that changes the state?
  2. Which contemporaneous facts and policy determine that decision?
  3. Which downstream systems only copy, filter, aggregate, or reindex it?
  4. If all downstream views disappeared, which records would be sufficient to rebuild them deterministically?

In the opening example, failure classification affects alerts, retry, billing, and reports; it is not a warehouse-only analytical bucket. The Task owner decides that cancelled_by_user is a legal terminal state and owns the cross-system outcome contract. The dashboard sees only the state that was produced and cannot reconstruct the original actor, reason, or transition rule.

The repair location should therefore follow semantic ownership, not whichever component raised the first alert.

A Source of Truth is decision authority, not the only copy

Source of Truth is often misunderstood as “the whole system may store only one copy of the data.” A distributed system naturally contains database rows, events, caches, search indexes, warehouse facts, and dashboard aggregates.

What needs one clear owner is the semantic decision itself.

If downstream systems need only current state, the Task owner may persist a transition as current state. If billing, audit, or the warehouse must reconstruct history, the owner must also retain version history, correction records, or immutable events covering the target time range. Storage forms may differ, but a record is sufficient as the Source of Truth for a view only when it preserves the facts that view needs:

  • Only the authoritative owner can commit legal state changes.
  • Each decision has a stable identity, version, or sequence.
  • The record keeps the minimum provenance needed to explain the decision.
  • Concurrent updates and retries cannot create contradictory current results.
  • Downstream consumers can identify the schema or version they consumed.

This does not imply one global Source of Truth for an entire system. Task lifecycle, user authorization, Artifact content, and deployment intent usually have different owners. Putting every fact in one database does not create shared semantics automatically.

A Derived View may reshape facts but not reinvent them

A Derived View serves a read pattern, so it can perform transformations that do not belong in the Source of Truth:

  • Denormalize normalized records into a wide table.
  • Aggregate by date, tenant, or state.
  • Build an inverted index for full-text search.
  • Project event history into a current snapshot.
  • Produce a low-latency UI cache.

The boundary is that every transformation must remain explainable and must not silently invent a business meaning that belongs upstream.

A dashboard may aggregate an upstream outcome_class = cancelled by week. It should not infer outcome_class = failed merely from status != succeeded. The latter is not a presentation choice; it creates a new business classification.

If a downstream system needs a concept that upstream does not provide, first decide whether it exists only for analysis. If “first response exceeded 30 seconds” is a reporting-only SLA bucket, the warehouse can own the derived rule and record its version. If “user cancellation counts as task failure” affects alerts, retry, and billing, it belongs in a contract closer to the Task owner.

Lineage tells each view where it came from

A Derived View should at least answer which inputs it read, which rule version it used, how far it processed, and whether it can be rebuilt.

Task owner
  task_17 outcome_class=cancelled version=8
        ↓ event schema v3
Event stream
        ↓ warehouse transform outcome_rule v5
Task outcome fact
        ↓ dashboard query v2
Failure-rate panel

This lineage does not require every system to share one transaction. It requires enough identity and version information at each hop to locate the divergence:

  • Did upstream commit an incorrect outcome?
  • Did the event producer use an old schema?
  • Did the warehouse transform omit a new enum?
  • Did the dashboard read a stale projection?

Without lineage, downstream shows only an incorrect number and the nearest layer tends to overwrite it. With lineage, the repair location can follow dependencies back to the boundary where the divergence actually occurred.

Complete the owner contract before rebuilding the view

In the opening example, the Task owner has already defined cancelled_by_user as outcome_class = cancelled; the old event schema simply omitted it. A safe repair has six steps:

  1. Define the outcome meaning and schema version in the Task owner’s contract.
  2. Make new transitions or events carry the authoritative outcome_class instead of forcing each consumer to infer it from raw status.
  3. Require consumers to place unknown enum values in unknown, reject them, or degrade explicitly instead of using a catch-all failure bucket.
  4. Run a repeatable historical backfill with a recorded input range and rule version.
  5. Rebuild warehouse facts from corrected events or an owner snapshot that retains the required historical versions.
  6. Remove the temporary semantic patch from the dashboard so it returns to presentation and aggregation.

A backfill is not arbitrary history rewriting. It must distinguish two cases:

  • The original fact was correct and only the derived rule was wrong: recompute from the same source version.
  • The upstream fact itself was corrected: create a new version or correction record and preserve the provenance of the prior value.

A Derived View should support idempotent rebuild. If a team can only edit the final number manually and cannot reproduce the same output from the same input, the view still lacks a recovery contract.

Reconciliation repairs a view that fell behind correct facts

Not every inconsistency requires a semantic change. The Source of Truth may already be correct while a projector falls behind after a timeout or missed message.

The repair location is then the derived layer: compare source version or sequence with the projection cursor, reprocess missing input, and converge through an idempotent upsert. The repair catches the view up; it does not decide the task outcome again.

This is the distinction between rebuild and reconciliation. A rebuild regenerates a larger range from a trusted starting point. Reconciliation continuously compares desired or authoritative state with the observed view and repairs local drift. Both require a clear Source of Truth and deterministic derivation rules.

Contract evolution cannot change only the producer

The opening failure is not merely one missing warehouse WHEN. It contains two independent gaps: the propagation contract exposes only raw status and does not version the outcome semantics already defined by the owner; the consumer interprets unknown values through a status != succeeded catch-all. Fix only one gap and the next enum change can still produce another incorrect classification.

Contract evolution should specify at least:

  • The business meaning of the new field or enum.
  • The producer version that begins to provide it.
  • Whether consumers preserve, reject, or explicitly degrade an unknown value.
  • Whether historical data is backfilled, and how original fact is distinguished from later correction.
  • When the old rule can be removed.

This is slower than adding a compatibility branch to every downstream query, but it places change cost back at the boundary that owns the meaning. When expired appears later, producer and consumers can evolve through the versioned contract instead of scattering five new interpretations.

Back to the problem

The dashboard finding “user cancellation is counted as failure” does not make the dashboard the owner of cancellation semantics.

Following lineage back, the Task owner in this example owns the legal transition and the outcome semantics shared by alerts, retry, billing, and reporting. The correct repair defines cancelled_by_user → cancelled in the owner contract, propagates the decision in a versioned record, requires safe handling of unknown values, and then backfills and rebuilds downstream views. The dashboard only aggregates the outcome that has already been defined.

The boundary between a Source of Truth and a Derived View is not a prohibition on data copies. It gives each semantic decision one explicit owner so the other copies remain explainable, rebuildable, and able to converge after drift.
