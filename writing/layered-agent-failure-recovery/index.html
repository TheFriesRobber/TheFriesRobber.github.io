Agent Runtime 6: Choose Recovery at the Failure Boundary

A report-generation failure shows how a Runtime should choose retry, fallback, repair, replan, or reconciliation from the failure owner, result certainty, and side-effect boundary.

07/15/2026 Views
AgentRuntimeReliability

The problem

An Agent is generating a market report. It asks a model to organize data, calls create_document, and then asks the model to add a summary.

After the primary model request times out, the HTTP client makes at most three requests including the first. The Provider Adapter selects from at most three route attempts including the primary route, and the outer Run executes the whole flow at most three times. Three Attempts at each nested layer can expand one logical Model Turn into 27 physical requests.

create_document is more dangerous. If the external service created the document but its response was lost, repeating the outer Run creates multiple documents. A uniform “retry on failure” rule is not a recovery system. It is an Attempt multiplier.

The problem is not the number three. It is that three layers all treat the error they observe as authority to recover independently.

Identify the failure owner first

A recovery action should stay within the object that owns the state. A transport timeout, Model Turn, Tool Execution, Plan, and Task are not the same retry unit:

Failure locationStable identityFirst question
Transport / providerModel TurnWas the request accepted, and is any response item complete?
Tool validationTool Call / Tool ExecutionCan the model repair the input, and has any side effect occurred?
External Tool effectTool ExecutionIs the result failed, or still unknown?
Plan premisePlan revision / itemWhich later items depend on the invalid premise?
Task outcomeTaskCan the user goal still complete, or must it stop or escalate?

One exception string is not enough to classify the failure. timeout says only that the caller received no confirmation before its deadline. It does not prove that a provider generated nothing or that a Tool produced no external effect. The Runtime also needs the current owner, logical identity, committed facts, and side-effect contract.

Transport retries and route fallbacks within one inference boundary are different Attempts of the same Model Turn here. The Runtime starts a new Model Turn only when the model input or intended inference boundary changes; changing providers alone must not silently change the measurement grain.

Errors should therefore be normalized into stable failure classes such as transport_timeout, provider_rate_limited, tool_invalid_argument, effect_result_unknown, and plan_premise_invalid. The raw exception can remain in controlled logs, but recovery policy should not depend on strings that change with an SDK or provider.

Recovery is not another word for retry

Only after classification can the Runtime choose an action:

ActionApplicable conditionWhat it must not do
RetryThe same logical operation is safe to attempt again and budget remainsGenerate a new identity that hides duplicate execution
FallbackThe original route failed and another route still satisfies the contractJoin partial output from two Attempts
RepairThe model can correct Tool input from a structured errorRepeat the same invalid arguments
ReplanA premise or dependency is invalid, so the old plan cannot reach the goalMerely mark the failed item pending again
ReconcileAn external effect may have occurred but its result is unknownRepeat an irreversible action before checking
Escalate / stopPolicy, authorization, or safety forbids automatic recoveryUse more retries to bypass a hard boundary

Backoff and jitter control when retries happen; they do not prove that a retry is safe. A side-effecting call still needs a stable idempotency key, a queryable business reference, or explicit reconciliation. If none exists, the result should remain unknown and automatic replay should stop.

Walk the report through the policy

Now let one Runtime policy coordinate recovery:

1. The primary model request times out
   → the Routing Decision already guarantees provider_side_effects=none for this route
   → no complete response item was accepted, so discard incomplete output
   → create another Attempt in the same Model Turn and spend one fallback unit

2. The secondary model returns a complete create_document Tool Call
   → the Runtime validates it and creates a stable Tool Execution

3. The create_document response times out
   → an effect intent exists, but no terminal result does
   → mark effect_result_unknown and query by idempotency key / document reference

4. Reconciliation finds doc_42
   → converge the Tool Execution to succeeded without creating another document

5. Later evidence invalidates the report's data premise
   → send plan_premise_invalid to the Plan owner and create a new revision
   → cancel or replace only affected items; do not replay the confirmed doc_42 fact

If step 3 produced an explicit validation error, the action would be repair. If authorization had been revoked, the action would be stop. The recovery action follows the failure class and effect state, not the hope that another attempt might work.

Retry budget must be shared across layers

Each local retry can look reasonable while their composition exhausts the deadline, token budget, and downstream capacity. A RunSpec or Runtime policy should allocate a shared budget to the logical goal and record what each action spends:

recovery_budget
  transport_attempts: 2
  model_fallbacks: 1
  tool_repairs: 2
  replans: 1
  deadline: 45s

These are not universal defaults. They show that budgets need action-specific dimensions. A cheap transport retry and a replan have different costs and risks. Each may have a local limit, while all remain bounded by the total deadline, cost, and side-effect policy.

The Runtime should also detect loops that make no progress. If two Plan revisions still cite the same invalid premise, or Tool repair repeats the same argument digest and error code, more budget adds no information. The system should stop, request confirmation, or enter manual recovery instead of presenting the loop as ongoing work.

How to evaluate the policy

Final success rate alone rewards unlimited retries. A recovery trace should retain the logical operation, every Attempt, failure class, chosen action, budget use, final side effects, and artifact references.

That evidence reveals whether the system replayed a whole Run at the wrong layer, violated a capability constraint during fallback, duplicated a Tool effect, or replanned without changing an invalid dependency. Production failures can then become fixed fixtures that verify whether the same classification still produces an action within the same boundary.

Back to the problem

Uniform retry collapses failures owned by different objects. It amplifies requests and can repeat external actions whose outcomes remain unknown.

Layered recovery first locates the failure identity, then combines result certainty with the side-effect contract to choose retry, fallback, repair, replan, reconcile, or stop. A shared budget limits the complete recovery chain, while Attempt lineage proves what actually ran. Recovery then moves state toward convergence at the correct boundary instead of restarting from the outside.
