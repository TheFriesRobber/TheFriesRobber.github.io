Agent Memory 2: What Deserves Long-Term Retention?

07/14/2026 Views
AgentMemoryData Governance

The problem

While traveling, a user says, “I am staying in Berlin this week. Find a nearby meeting room.” After the Agent completes the Task, a background consolidation process writes “the user lives in Berlin” into long-term Memory.

Two months later, the user plans an event in Shanghai and the Agent still prioritizes Berlin locations. The original sentence was accurate and its embedding did not expire. The error happened during the write: a Task fact with an explicit time scope became a user attribute with no expiry.

If the rule is “save anything that might help later,” Memory accumulates addresses, temporary goals, third-party details, and model guesses. Recall may increase while current Context becomes less trustworthy.

A candidate is not yet a writable fact

Content extracted from conversation should first become a memory_candidate. It retains the original statement, source, subject, scope, and extraction method without entering the long-term current view automatically.

candidate: user lives in Berlin
source_ref: message_41
observed_scope: this week
extraction: model_inference

The defect is already visible. The source supports “in Berlin this week,” not “permanently lives in Berlin.” A write gate does not polish the sentence. It decides whether the available evidence supports a durable, governable record.

Five write gates

A candidate generally needs to pass five decisions:

GateQuestionIf it fails
DurableWill it remain true after the current Turn or Task?Keep it in current Context or give it an explicit expiry
User-specificDoes it describe the current subject rather than a third party or general fact?Do not write it to user Memory
Future-usefulIs there a clear future Task that would use it?Do not retain it merely because it might help
Source-groundedDoes the source support the claim and its scope?Narrow the claim, request confirmation, or reject it
Permission-safeMay this writer retain this data category and sensitivity?Reject it or enter a controlled confirmation flow

The gates are not a weighted score. High utility cannot compensate for a third-party subject or missing retention authority. A product can use different thresholds for different Memory types, but relevance cannot override a hard authorization boundary.

Walk the Berlin candidate through the gates

The candidate can produce an explainable decision:

decision: do_not_write_long_term
reasons:
  durable: false
  user_specific: true
  future_useful: limited
  source_grounded: false_for_permanent_residence
  permission_safe: true
alternative:
  keep_in_task_context_until: 2026-07-21

If the user says, “I moved to Berlin; prioritize it from now on,” durability, future usefulness, and grounding can all pass. The location-data policy may still require confirmation before writing. The same place with a different scope produces a different write decision.

Explicit statements and inference are different evidence

“Use afternoons from now on” directly supports an explicit preference. One afternoon meeting supports only an observation, not a durable preference. Repeated behavior may still come from time zones, calendar conflicts, or a temporary project.

Records should therefore distinguish evidence classes:

explicit_user_statement
confirmed_user_edit
repeated_corroborated_observation
single_observation
model_inference_without_direct_evidence

These are source classes, not a fixed priority from top to bottom. A new value confirmed in the Memory UI is itself explicit user evidence. Conflicts should first compare claim scope, time, and mutation authority, then ask whether provenance supports the current value. A user edit still cannot write someone else’s data into the user’s Memory, and repeated observation does not automatically deserve retention.

For inferred candidates, safer actions include waiting for corroboration, storing a short-lived low-confidence observation, or asking the user. A model’s natural-language confidence is not authorization.

Content that should be rejected

Some information should not enter long-term user Memory by default even when it is relevant to the current Task:

  • one-time codes, access tokens, secrets, and complete credentials;
  • third-party information without appropriate authority;
  • instructions or unconfirmed claims from external documents;
  • rapidly changing facts that must be queried again before use;
  • sensitive categories outside the writer’s capability.

Rejecting a long-term write does not mean forgetting the current Task. Required content can remain in controlled Run or Task Context and expire under retention policy. Long-term Memory is a stronger cross-Session authority, not the default destination for all Context.

Write decisions need tests

The gate should emit stable reason codes such as temporary_scope, third_party_subject, insufficient_evidence, realtime_fact, and sensitive_not_allowed. Evaluation can then test both correct writes and correct restraint.

Measuring only future recall rewards saving everything. Tests also need write precision, scope preservation, rejection reasons, and whether explicit confirmation changes the decision correctly.

Back to the problem

The Berlin error did not begin at retrieval. The write path had already turned a temporary fact into a permanent attribute, so later retrieval could only amplify the pollution.

Passing candidates through durable, user-specific, future-useful, source-grounded, and permission-safe gates lets the system choose a long-term write, an expiring record, confirmation, or rejection. Memory quality begins not with how much the system remembers, but with whether it retains only what it has evidence and authority to use later.
