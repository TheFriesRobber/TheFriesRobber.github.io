Agent Memory 1: Why RAG Cannot Replace Memory

A repeatedly retrieved stale preference reveals the difference between historical text retrieval and governed long-term user state.

07/12/2026 Views
AgentMemoryData Governance

The problem

On June 1, a user tells an Agent, “From now on, schedule reviews in the morning when possible.” The system embeds the message. On July 10, the user explicitly corrects it: “Use afternoons from now on.”

The next time the Agent schedules a review, vector search returns both highly relevant messages:

0.93  From now on, schedule reviews in the morning when possible
0.91  Use afternoons from now on

Increasing top_k returns the contradiction more reliably. Raising the similarity threshold may remove the newer, correct statement. Retrieval answers which historical text resembles the query, not which user preference is currently valid.

That is the boundary between RAG and long-term Memory. RAG retrieves evidence. Memory must also govern state that can be corrected, revoked, or expired.

Historical evidence is not current state

Both messages really occurred and belong in conversation history. The current Task still cannot apply “morning” and “afternoon” simultaneously. Treating historical text as a Memory record collapses three questions:

QuestionRequired object
What did the user say before?Source event / raw history
Is this worth preserving across Sessions?Memory write decision
Which version applies now?Current view over versioned records

The current view does not delete history. It is a derived result that identifies which records remain effective under the current authorization, time, and version rules. When the decision must be explained or re-evaluated, the system can follow source references back to the original statement.

A minimum Memory pipeline

A governed pipeline needs at least these stages:

source event
  → memory candidate
  → write gate
  → versioned memory record
  → current view
  → retrieval candidate
  → Context Assembly

A model or rule can propose a candidate from conversation, but a candidate is not yet a long-term fact. The write gate decides whether it is durable enough, relevant to this user, useful later, grounded in a source, and permitted to be retained. Only then does the system create a Memory record with an owner, source, and version.

Retrieval is not the final decision maker either. It finds candidates from the current view. Context Assembly then combines them with instructions, permissions, and other sources for the current Task. A Memory does not become a current instruction merely because search returned it.

Corrections must change the current view

The June 1 statement expresses an ongoing scheduling preference that may remain useful across Sessions. Only after it passes the write gate does the system turn that source event into a Memory record. At this point, v1 is current rather than merely another text fragment waiting for similarity search:

memory_id: meeting_time_preference
version: 1
value: morning
source_ref: message_61
status: current

On July 10, the user explicitly says to use afternoons from now on. This is not an additional piece of similar text; it corrects the same preference. The Memory writer creates v2 and moves the current view from v1 to v2. The version history can now be represented as:

- memory_id: meeting_time_preference
  version: 1
  value: morning
  source_ref: message_61
  status: superseded
  superseded_by: 2

- memory_id: meeting_time_preference
  version: 2
  value: afternoon
  source_ref: message_82
  status: current
  supersedes: 1

Raw history still contains both messages, while the current view exposes only v2. If the user asks whether they previously preferred mornings, the system can inspect history. If the current Task schedules next week’s review, retrieval should start from v2.

“Use afternoons for the next two weeks” may instead create a scoped exception with an expiry time rather than permanently superseding the default preference. When scope is unclear, the system should ask rather than let a Memory writer turn a temporary Context decision into long-term state.

Similarity search cannot define mutation rules for every state

This version switch applies to long-term user preferences. It does not follow that every state called “Memory” should use the same retrieval and mutation rules. “Memory” often names several objects: long-term user preferences, current Task state, working state for one Run, and a fixed Agent persona. They may use similar storage technologies, but they should not share mutation rules.

User preferences change through user statements and controlled writers. An application owner reconciles Task state. Runtime owns Run working state. Persona comes from versioned configuration. Putting all four into one vector index lets the ranking from one similarity query influence user facts, execution state, and system behavior at once.

This article establishes only the minimum boundary for long-term user Memory. Later decisions determine what to write, what each writer may change, how versions handle concurrent change, and how retrieval ranks the current records.

A vector index retrieves candidates; it does not define truth

Memory may live in files, a relational database, a document store, or a search index. Anthropic’s Memory Tool explicitly asks the application to execute client-side file operations, so the data remains in infrastructure controlled by the application. The interface lets a model request reads and writes; it does not define versioning, authorization, or the current view for the application.

Likewise, a vector database can be a candidate index without becoming the only source of truth. Candidates can be rebuilt after an embedding model or index changes. Source, version, and revocation relationships must not exist only as vector metadata.

Back to the problem

The stale preference in the opening example is not a retrieval failure. The system found relevant history. The error was treating relevant history as current state.

Agent Memory adds a write gate, versioned records, and a current view above source events before handing effective content to retrieval and Context Assembly. “Morning” remains traceable history, while “afternoon” becomes the current preference. The system preserves evidence without letting a more similar old sentence become active again.

Follow-up questions

  • What information deserves to enter long-term Memory across Sessions?
  • What mutation authority should each Memory writer receive?
  • How should corrections, revocations, and concurrent edits create new versions?
  • After the current view, how should keyword, vector, and hybrid retrieval work, and how should their candidates be reranked?
