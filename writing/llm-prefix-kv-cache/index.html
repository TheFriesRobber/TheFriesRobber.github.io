LLM Infra 07: Why Prefix Cache Reuse Cannot Rely on Matching Text Alone

Separate Prefix/KV Cache reuse into deployment namespace, Token block identity, and isolation policy so identical text is not mistaken for compatible state.

07/29/2026 Views
LLM InfraInferenceKV CacheCaching

The problem

A platform hashes Prompt text directly and uses that value as its Prefix Cache key. After a model upgrade or a LoRA change, the same text still hits an old entry. A different tenant sends the same system Prompt and enters the same sharing domain as well.

Matching text proves only that the input strings are identical. KV Cache is derived state produced by one particular model execution. Before reusing it, the platform still has to answer two questions:

  1. Is this state execution-compatible?
  2. Even if it is compatible, does policy allow the requests to share it?

KV is model-derived state, not text

While processing Tokens, a Transformer computes and stores Key/Value state for attention. Later Tokens can read the existing KV instead of recomputing the entire prefix.

The direct input to reuse is therefore not the original string, but the Token IDs and their positions in the prefix. Chat templates and tokenizers determine how a string becomes Tokens. Once two requests have produced exactly the same Token IDs, the template and tokenizer do not independently alter the KV after tokenization. Conversely, identical text that passes through different templates or tokenizers can produce different Token IDs and cannot match the same block identity.

More fundamental changes come from model execution:

  • model weights or revision;
  • LoRA / adapter;
  • attention and position semantics;
  • KV dtype, layout, and format version;
  • multimodal content that affects model input.

Within a single-model Runtime, some of these conditions can be fixed by process configuration and need not appear separately in every per-block hash. A cross-process or remote Cache service instead needs an outer namespace that prevents blocks from different deployments from meeting accidentally.

Divide Cache identity into three layers

An auditable design can separate identity into:

cache_namespace:
  model_artifact_digest: sha256:...
  model_config_digest: sha256:...
  adapter_artifact_digest: sha256:... # use a stable sentinel for the base deployment as well
  kv_format: fp16-layout-v3
  attention_mode: causal-rope-v2
  block_hash_algorithm: sha256
  serialization_format: canonical-cbor
  serialization_version: 1

block_identity:
  parent_block_hash: ...
  token_ids_hash: ...
  runtime_extra_hashes:
    multimodal_input: null
    lora_id: null

isolation_policy:
  trust_domain: tenant-group-a
  cache_salt: ...
  retention_class: short-lived

This is a design suggestion, not a copy of an existing vLLM object.

  • cache_namespace proves that the physical state format is compatible with the deployment. The Adapter field must derive from an immutable artifact digest; a Runtime-local LoRA ID is usable only within a fixed engine namespace. A cross-process or remote Cache must also pin the hash algorithm and canonical serialization version rather than assuming that different Python/Runtime versions produce reproducible bytes.
  • block_identity proves that this is the same block on the same Token-prefix chain.
  • isolation_policy proves that the request is permitted to enter the same sharing domain.

Collapsing all three layers into a prompt hash loses both execution compatibility and the authorization boundary.

A specific Runtime’s block hash covers only the boundary it owns

Current vLLM Automatic Prefix Caching builds each block hash from the parent block hash, the current block’s Token IDs, and extra hashes. Examples of extra hashes in the official design include LoRA ID, a multimodal input hash, and a cache salt for multi-tenant isolation.

It also caches only complete blocks. The parent chain prevents the same Token block at different prefix positions from being mistaken for the same state. LoRA and multimodal information supply execution differences that Token IDs alone cannot express.

Why does model revision not always appear in every block hash? Because the base model is usually fixed inside one engine. It is an engine/namespace precondition. If a platform moves blocks into a remote Cache shared across deployments, the namespace must make those compatibility dimensions explicit.

The rule should be: a Cache key needs to include fields that can vary at that layer and alter the derived state; conditions fixed by an upper layer must be isolated by its namespace.

Mathematical compatibility does not imply permission to share

Two tenants can use the same model revision, identical Token IDs, and the same adapter, producing mathematically compatible KV. The platform may still prohibit sharing because a Cache hit can reveal whether a prefix has appeared before, and entries can be governed by different retention or data-region policies.

vLLM’s cache_salt participates in the first block’s hash and, through the parent chain, affects all later blocks. This constrains the sharing domain of the Prefix Cache. The official documentation presents it as Cache isolation for shared environments.

This is not a complete tenant-security solution. Cache salt does not replace ingress authentication, log isolation, process/device isolation, or retention enforcement. It addresses only the Cache-reuse path.

The isolation decision must be injected by a trusted boundary and cannot be supplied arbitrarily by a client:

authenticated tenant
→ policy resolves trust_domain and salt
→ request enters Cache namespace
→ block lookup

Eviction must preserve identity and state

Prefix Cache still occupies KV blocks and therefore competes with active sequences for GPU memory. The Runtime must decide which entries can be evicted, which are referenced by a current request, and which are constrained by retention policy.

Common states can be conceptualized as:

candidate → resident → referenced → evictable → evicted

An eviction policy can consider recency, block cost, and memory pressure, but it cannot merge statistics across namespace and isolation boundaries. A high hit rate for one tenant does not automatically authorize another tenant to share its entries.

Cache hits must also enter the observability record:

cache_decision:
  namespace_digest: ...
  matched_tokens: 512
  block_count: 32
  isolation_domain: tenant-group-a
  outcome: hit
  reused_prefill_tokens: 512

This lets a Benchmark distinguish cold from warm state, and lets capacity analysis determine how much Prefill work was actually skipped.

Back to the problem

The opening prompt hash binds only the original text. It proves neither that the KV came from a compatible deployment nor that tenant-sharing policy permits reuse.

Safe reuse requires three decisions: whether the deployment namespace is compatible, whether the Token block and parent chain match, and whether isolation policy permits sharing. The tokenizer and template serve as provenance that determines Token IDs, but once the Token IDs are identical they should not be mechanically duplicated in the key.

Cache hit rate can be optimized only within those three boundaries. A “hit” that crosses a correctness or isolation boundary is state corruption, not a performance gain.

Cache identity determines which KV state can be reused. The next article covers quantization, which changes the physical representation of that state and must therefore enter the namespace and trigger new validation of memory, quality, and the service curve.
