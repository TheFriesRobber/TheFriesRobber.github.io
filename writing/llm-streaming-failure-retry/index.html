LLM Infra 14: When Can a Failed Streaming Inference Request Be Retried?

Separate logical requests, attempts, executions, partial delivery, and cancellation to define the boundaries of retry, restart, and explicit failure for streaming inference.

07/29/2026 Views
LLM InfraInferenceStreamingReliability

The problem

A request has already streamed part of its text when the connection breaks. The Gateway automatically sends the same Prompt to another Replica. The new output starts over and diverges, so the Client receives duplicate or contradictory text while both Replicas produce usage.

Ordinary HTTP retry often treats “no complete response” as “send it again.” That model does not hold for autoregressive streaming: the request may already have executed, and some Tokens may already have become visible to the user.

A timeout describes only the observer

The gRPC deadline documentation makes the boundary explicit: after a client deadline expires, the client stops waiting, but the server application is still responsible for stopping work it has already started. The client and server may also reach different local conclusions for the same call: the server completes while the client observes deadline exceeded.

Therefore:

gateway timeout
≠ placement did not arrive
≠ execution did not start
≠ cancellation took effect
≠ no usage was produced

Likewise, a client disconnect proves only that the transport broke. Propagating cancellation from the Gateway through the scheduler, Replica, and parallel ranks takes time and can fail.

Four objects determine the recovery boundary

attempt_state:
  logical_request_id: req_123
  attempt_id: att_2
  release_digest: release_91a
  execution:
    started: true
    stopped: unknown
  cancel:
    requested_at: ...
    engine_observed_at: null
  delivery:
    chunks_emitted: 6
    emitted_token_cursor: 47
    ack_protocol: none
    acknowledged_cursor: null
    terminal_transport_status: unavailable
  usage:
    generated_tokens: 91
  • A Logical request is one unit of work the caller wants completed.
  • An Attempt is one physical send; every retry receives a new attempt_id.
  • An Execution records whether the Runtime admitted and computed the request.
  • A Gateway emitted cursor records how much output the Gateway attempted to send.
  • An acknowledged cursor records caller confirmation only when the API defines explicit application acknowledgement.

Ordinary SSE and HTTP streams generally have neither a universal application-consumption acknowledgement nor a portable Token resume protocol. A successful write creates, at most, local Gateway evidence that output was emitted. It does not prove that the Client received, parsed, or committed the output. Without acknowledgement, the Client-visible outcome remains unknown. Unless the API and Runtime explicitly support it, no cursor implies an ability to “continue from Token 48.”

Retrying before the first output is not free or fully safe

If the Client received no chunk, a new attempt will not create duplicate visible Tokens, but the old attempt may still have:

  • completed Prefill;
  • entered Decode;
  • produced billable or GPU usage;
  • continued during cancellation propagation;
  • completed at the same time as the new attempt.

The more accurate rule is: before the first chunk, a new attempt may start when the caller protocol allows it, but the platform must still accept duplicated computation and an unknown execution outcome.

The platform can first request cancellation and wait for execution_stopped evidence before deciding to retry. If it receives only cancel_observed_by_engine, whether the old execution stopped remains unknown, so it must treat concurrent execution as possible. If the deadline does not allow waiting, record that risk in outcome and usage rather than calling the behavior exactly-once.

After possible partial delivery, do not splice by default

Autoregressive output depends on the prefix, sampling, model and Runtime revision, and execution path. Even with the same seed, version, Batching, and numeric differences may change the result. Regenerating from the same Prompt on a new Replica does not guarantee a continuation compatible with the first 47 Tokens.

Make the choices explicit:

Known stateDefault actionReason
Gateway confirms no chunk was emitted; old execution confirmed stoppedStart a new attemptNo duplicate visible output, but it is still new computation
Gateway confirms no chunk was emitted; old execution unknownA new attempt may start by policyAccept duplicate execution and usage risk
Gateway emitted a chunk; Client ACK is absent or confirms only partFail explicitly, or restart from the beginning with caller consentTreat as possibly partially visible; do not splice by default
Runtime provides an explicit resume contractResume through that protocolBind state, release, and cursor
Completed while acknowledgement is unknownReturn unknown or query the result when supportedAutomatic retry may duplicate the full result

Fallback to another deployment must also pass the complete compatibility contract defined in Article 15, including protocol, capability, quality and safety, data policy, and SLO envelope. Resource shortage is not authorization to change models silently.

Cancellation requires three separate facts

Do not compress cancellation into cancelled=true. Record at least:

cancel_requested
→ cancel_observed_by_engine
→ execution_stopped

The first event records caller intent. The second proves the Runtime observed it. Only the third proves that the GPU is no longer advancing that execution. In multi-rank or P/D-disaggregated topologies, the evidence must also identify which stages stopped.

Usage should remain per attempt:

  • accepted input Tokens;
  • Tokens generated by the Runtime;
  • chunk or Token cursor emitted by the Gateway;
  • explicit Client acknowledgement, when the protocol has one;
  • Tokens computed after cancellation;
  • terminal outcome.

Every fact must retain its producer and provenance. The Runtime cannot sign a claim that Tokens were delivered to the Client. How billing or quota combines attempts for one logical request is an upper-layer policy; Infra provides usage evidence without dropping facts or crossing ownership boundaries.

Handle the opening disconnect

The original flow was:

gateway emitted through token cursor 47
→ disconnect
→ gateway retries from prompt
→ second output diverges

The corrected flow is:

  1. The Gateway records that attempt att_1 emitted through cursor 47. Without acknowledgement, it marks Client consumption unknown and conservatively treats the outcome as possible partial delivery.
  2. It asks the Runtime to cancel and records requested, observed, and stopped separately.
  3. By default, it returns an explicit failure and does not splice output.
  4. If the caller chooses “regenerate from the beginning,” it creates att_2 and identifies it as new output.
  5. Both attempts remain associated with the same logical request while retaining separate outcomes and usage.

Back to the problem

The opening Gateway already emitted part of the output. Even if it cannot prove how much the Client consumed, it cannot interpret “connection failed” as “model did not execute,” nor can it splice a second full generation onto the first output.

Streaming recovery must combine attempt and execution state, Gateway-emitted evidence, explicit Client acknowledgement when available, and cancellation facts. A new attempt before the first chunk may still duplicate computation. When partial delivery is possible, fail explicitly by default. Only an API and Runtime with a defined resume contract can continue from confirmed state.
