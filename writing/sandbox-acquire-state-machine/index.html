Agent Sandbox 3: A Created Runtime Is Not Yet Ready

Treat Volume binding, Runtime creation, mounting, initialization, and Ready publication as recoverable commit boundaries.

07/14/2026 Views
AgentSandboxDistributed Systems

The problem

createRuntime() returns successfully, yet the Agent’s first command sometimes fails:

ENOENT: /workspace/project

This happens when Acquire—the complete flow from accepting a request, through preparing the Runtime and Workspace, to returning an executable Sandbox—ends too early. The same command works a few seconds later. In another incident, the Runtime exists but the Scheduler restarts before receiving the Provider response, then creates a duplicate. In a third, the Volume mounts but initialization fails while the system still reports Ready.

These failures share one cause: Acquire was implemented as a synchronous function, and the return from createRuntime() was treated as an acquired Sandbox. Volume binding, Runtime creation, mount, filesystem initialization, and readiness belong to different systems and have different unknown-outcome boundaries.

In this article, the Provider creates, queries, mounts, and stops physical resources. The Sandbox Scheduler is the business Control Plane that owns Session intent, generation, Lease, and Ready publication. Every state transition below follows that split.

Acquire returns a committed contract, not a create response

Acquire does not merely return a Runtime ID. It publishes a Ready record only when the following conditions hold. Here, generation is the monotonically increasing Runtime incarnation within one logical Sandbox and increments on every Runtime replacement. A Lease grants time-bounded execution authority to the current generation. A Ready record is the durable record the Control Plane may return only after these facts hold together:

runtime bound to current generation
∧ intended workspace mounted
∧ filesystem initialized and writable
∧ runtime contract verified
∧ lease still fresh

Each condition has its own owner, so intermediate state must be durable. Otherwise a Scheduler restart can only repeat the whole function, without knowing which effects occurred or which actions are safe to retry.

Phases describe progress; Conditions describe facts

A recoverable Acquire can use these main Phases:

Requested
  → Binding
  → Starting
  → Mounting
  → Initializing
  → Ready

Errors and recovery should not overwrite the main Phase. Preserve the last committed business Phase, then use active_operation, a stable operation identity, and operation_status=unknown|reconciling to identify which external result is uncertain and what the Controller is querying. The operation identity remains stable across retries and recovery of the same external action, so a restarted Controller can still query the original result. One physical call sent to the Provider is an Attempt, and one operation may require several Attempts. Failed means this generation reached a terminal state that cannot be repaired automatically. Replacing its Runtime requires a new generation.

Conditions preserve composable observations:

{
  "phase": "Mounting",
  "active_operation": {
    "kind": "mount_workspace",
    "operation_id": "mount:sandbox_12:42",
    "status": "reconciling"
  },
  "conditions": {
    "volume_bound": true,
    "runtime_created": true,
    "workspace_mounted": false,
    "filesystem_initialized": false,
    "runtime_contract_ready": false
  }
}

The Phase tells callers what the attempt is mainly waiting for. Conditions tell the Controller which facts already hold. Encoding every combination as a linear status quickly produces a state explosion.

These committed facts are the starting points for crash recovery. A Provider reference held only in memory cannot be claimed or deleted after a Scheduler crash.

The Control Plane therefore persists an operation identity before calling the Provider. The Provider owns the physical resource and its state; after creation or discovery, the Control Plane saves the provider binding record as early as possible, before long readiness waits. Persistence order matters more than function-call order.

Desired State may change in any phase

A user may cancel during Mounting. The state machine should not reach Ready merely to Release. It commits:

desired_state: active → stopped

The Controller sees the new intent and takes the cleanup path:

Binding / Starting / Mounting / Initializing
        └─ desired=stopped → Releasing → Terminated

Phase describes observed progress; desired state describes the convergence target. Keeping them separate makes cancellation and timeout legal from every intermediate phase.

Three timeout locations require three responses

Binding timeout: a different Volume may be unsafe

If the Workspace owner confirms no binding was created, retry the same binding identity. If the result is unknown, first query whether the Session already received a Volume. Allocating another one may split a single Workspace into two content branches.

Starting timeout: query the Provider first

When the Provider creates a Runtime but its response is lost, the operation becomes Unknown. Query by operation key, label, or generation:

0 matches  → retry within the idempotency boundary
1 match    → claim and persist provider_ref
many       → choose one and isolate the rest
uncertain  → remain Reconciling or require manual repair

A timeout is not evidence that creation failed.

Ready timeout: the resource exists but the contract does not

A Runtime may remain Running while mount or initialization Conditions fail. Repeating createRuntime() is usually the wrong repair. Inspect Conditions, then repair initialization, create a new generation to replace the Runtime, or mark the current generation Failed.

Using one error string for all three timeouts causes automation to take the wrong action. An error should identify the phase, operation identity, whether the outcome is known, and its retry conditions.

Ready publication rejects late results

Suppose generation 41 has a slow initialization probe. A retry lets generation 42 obtain the Lease and become Ready before 41 finally reports success.

The Ready write must atomically compare every binding it claims to hold together. This SQL illustrates the conditions; they need not all live in one table:

UPDATE sandbox
SET phase = 'Ready', ready_contract = ...
WHERE sandbox_id = ?
  AND generation = 41
  AND desired_state = 'active'
  AND provider_ref = ?
  AND workspace_binding_version = ?
  AND lease_generation = ?
  AND lease_expires_at > now()
  AND contract_version = ?
  AND resource_version = ?;

If the generation is 42—or any Provider, Workspace, Lease, or Contract binding changed within the same generation—the update affects zero rows and the late result returns to reconciliation. Checking once in application code and then performing an unconditional write still leaves a race. Every Runtime replacement should increment the generation; an implementation with a separate attempt identity must compare it in every conditional write that commits that Attempt’s result.

The Ready record also binds runtime_id, workspace_binding_version, lease_generation, and contract_version. Otherwise successes observed at different times can be combined into a state that never existed simultaneously.

A restarted Scheduler continues from durable facts

Recovery does not rerun all of acquire(). Given:

phase=Starting
operation_key=sandbox_12:42
provider_ref=null

the Controller knows a Provider call may have happened and queries first. Given:

phase=Initializing
provider_ref=workload_b
workspace_binding=volume_31@v9

it probes the workload and mount, then continues initialization or cleanup. Every phase must answer:

  • Which effects may have happened?
  • Which identity can query them?
  • Which action is safe to retry?
  • Does current desired state still require progress?

An intermediate state that cannot answer these questions is progress text, not a recoverable state machine.

Observability should locate the waiting phase

Total acquire_latency cannot distinguish slow Provider startup, blocked Volume binding, or failed initialization. Record:

  • phase entry, residence time, and exit reason;
  • the oldest nonterminal Acquire;
  • counts and ages of unknown and reconciling;
  • failure reasons by Condition;
  • the phase where Ready timeout occurred;
  • cleanup outcomes for orphan Runtimes and duplicate bindings.

Separate cold create, warm reuse, and recovery latency. Combining them makes the average neither representative of user wait nor useful for locating an optimization.

A state machine need not be one giant table

State may live in a current Snapshot, an append-only log, or both. The required properties are:

  • stable identity and commit boundaries around external actions;
  • conditional transitions by the owner;
  • repeatable Controller actions from durable facts;
  • unknown results that are not relabeled as failures;
  • terminal states that late responses cannot reopen.

Workspace, Provider, and Control Plane may each store the facts they own, while the Control Plane projects the current Acquire state. A single state machine does not require every system to share one status field.

Back to the problem

createRuntime() success proves only that the Provider created compute. /workspace/project additionally requires the correct Volume binding, an observed mount, completed initialization, and a current Lease.

Requested, Binding, Starting, Mounting, Initializing, and Ready establish recoverable boundaries, while Unknown, Reconciling, and cleanup preserve failure semantics. Ready is a conditional commit after these facts hold together, not a successful response from one Provider API.
