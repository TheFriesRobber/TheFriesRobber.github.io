Agent Runtime 8: Receive Steering through a Durable Inbox

07/17/2026 Views
AgentRuntimeStreamingReliability

The problem

An Agent is calling a Tool that takes two minutes when the user sees an intermediate result and adds, “Keep only data from the last month.” The server immediately replies “received” and places the message in the in-memory queue of the background process executing the Run, referred to below as the worker.

A few seconds later, the Tool returns just as the worker restarts. A new worker resumes from the existing messages, but the additional instruction is gone. The user was explicitly told that the system had received it; to the Runtime, the input never became a recoverable fact.

Appending the message directly to the current messages array does not solve the problem. A model request may already be in flight, making it impossible to tell whether the current Model Turn saw the message. Mutating Context while it is being assembled or iterated also makes behavior depend on timing.

“Received” contains three promises

New input that arrives during execution is usually called steering, but that term can blur several distinct stages:

  1. accepted: the system has durably admitted the input, so it survives a restart.
  2. consumed: the input has been bound to the canonical input of a specific Model Turn; this does not prove that the Provider accepted the request or that the model “read” it.
  3. applied: the model or a Tool actually changed its behavior in response.

The Runtime can record the first two. The third usually has to be established from later execution facts or result validation. Returning accepted after only an in-memory enqueue makes a promise the system cannot keep.

Steering therefore needs a durable Inbox. It is not another copy of chat history. It owns the state “admitted by the system but not yet included in a Model Turn.” accepted also carries an important condition: both the input body and the Inbox record are durable. Persisting only a payload_ref that points to missing content still cannot satisfy the promise after recovery.

A minimal Inbox model

An input can retain these logical fields:

input_id
tenant_id
subject_ref
session_id
target_run_id
inbox_seq
payload_ref
payload_digest
payload_canonicalization
state              pending | consumed | rejected_terminal
accepted_at
consumed_by_model_turn_id
consumed_at

input_id prevents a client retry from creating a duplicate only when a database constraint enforces that identity—for example, with a unique key on (tenant_id, subject_ref, input_id). The ID names one operation within the submitting subject’s namespace, so different subjects may use the same ID independently. On conflict, the system must also compare target_run_id, payload_canonicalization, and payload_digest. It returns the original admission result only when the target and content match. Reusing the same ID for a different target or payload under the same subject must return an explicit conflict.

Before writing anything, a trusted ingress layer must derive tenant_id and subject_ref from the authenticated session and confirm that the subject may steer the target Run. It must not trust those values from the request body; otherwise an attacker who guesses a run_id could inject input into someone else’s execution.

inbox_seq is a monotonically increasing admission order within one Run. It is more stable than ordering only by accepted_at: two inputs can receive the same timestamp, and different service instances can write concurrently. consumed_by_model_turn_id identifies the Model Turn whose canonical input received the message instead of reducing the state to an ambiguous processed=true flag.

When the payload and Inbox share a database, immutable content and the Inbox row can commit in one transaction. When the content lives in object storage, a safer order is to write an immutable, content-addressed object before committing the Inbox row. The two kinds of unknown outcome require different reconciliation. If the object write is uncertain, look up the content address and verify its digest. If the Inbox commit is uncertain, query the admission record by the idempotency key above. Retention can clean up an orphaned payload that has no Inbox row; object existence alone must never be treated as proof that the input was accepted. The Runtime should verify the digest again before consumption so that damaged or replaced content does not enter the model request.

After receiving accepted, a client knows only that the input entered the Inbox. A more precise interface can display “assigned to Model Turn” after the input is bound. A model request being sent and a model response arriving belong in later Model Turn events.

Why consumption belongs at a Model Turn boundary

A Model Turn boundary is a point before the next model request has been assembled or after the previous round has ended. At that boundary, the Runtime can:

1. read pending inputs in inbox_seq order
2. generate input messages in a stable order
3. create the next Model Turn
4. mark those inputs as consumed_by_model_turn

“Creating the Model Turn” means more than allocating a model_turn_id. It also persists the immutable canonical input used for that model request, or a stable content reference, plus the Inbox input_id values included in it. That work and the consumed_by_model_turn_id updates need one atomic boundary. Otherwise, a worker may create only the Model Turn identity and crash, leaving a consumed record whose input cannot be reconstructed; recovery may also inject the same steering input into another Model Turn.

If a model request is already in flight, new input goes to the next Model Turn by default. A system may explicitly interrupt the current model call and open a new round, but that is an interruption policy—not a reason to mutate an array already in use.

Return to the opening example. The additional instruction first becomes pending. The old worker crashes after the Tool returns, but the new worker can still see the input and bind it while creating the next Model Turn. The message no longer disappears with the process that received it.

Completion creates the hardest race

A subtler problem appears when the Run is about to complete. Assume first that the Run owner has verified final output for this Agent Loop, all child work owned by the Run has converged, and the current state permits a terminal transition. An empty Inbox does not prove that the parent Task is complete. The following protocol only linearizes an already-valid Run terminal decision against steering that arrives at the last moment.

T1 Runtime checks the Inbox: empty
T2 user sends new input
T3 Runtime marks the Run completed
T4 the new input is accepted, but no executor remains to consume it

Checking the Inbox “one more time” before completion is not enough because the check and admission can still interleave. The system needs a terminal admission boundary, and the admission transaction and finalization transaction must contend on the same serialization point.

A rebuildable Run snapshot for a product page should not act as that coordinator. A small command-side run_control record is a better fit:

run_id
admission_epoch
admission_state       open | closing | closed
owner_fencing_token
next_inbox_seq

This record owns only the admission window and current execution owner; it does not store the complete user-facing Run state. Decisions such as steering.accepted, steering.consumed, run.continued, and run.completed still enter the Event Log, and query-facing Run snapshots are built from those facts.

For example, the admission path first authorizes the subject and queries for an existing record by the complete idempotency key. If one exists, it compares the subject, target, canonicalization, and digest, then returns the original admission result—even if the window has since closed. That first lookup is only a fast path: two identical retries may both miss the other’s uncommitted row. After locking run_control, the path must query the idempotency key again. Only when that second lookup still proves the key is new may it check the current epoch, allocate inbox_seq, persist the payload and Inbox row, and append the admission event:

BEGIN;
-- After authorization, look up the idempotency record first. If it exists
-- with matching content, return the original accepted result.
SELECT admission_epoch, admission_state
FROM run_control
WHERE run_id = :run_id
FOR UPDATE;

-- Recheck the idempotency key under the lock. If it exists, validate its
-- content and return the original result. INSERT ... ON CONFLICT DO NOTHING
-- followed by a read and comparison is another valid implementation.
-- Validate tenant, subject, and steering permission.
-- Allocate inbox_seq and insert a pending input only while the current epoch is open.
INSERT INTO steering_inbox(...);
-- Append steering.accepted.
COMMIT;

The finalization path takes the same lock. It first moves the current epoch to closing, preventing new input from silently entering the round that is about to end, and then reads pending input:

BEGIN;
SELECT admission_epoch, admission_state, owner_fencing_token
FROM run_control
WHERE run_id = :run_id
FOR UPDATE;

UPDATE run_control
SET admission_state = 'closing'
WHERE run_id = :run_id
  AND admission_state = 'open'
  AND owner_fencing_token = :owner_token;

SELECT input_id
FROM steering_inbox
WHERE target_run_id = :run_id
  AND state = 'pending'
FOR UPDATE;

-- Pending input: create and bind the next Model Turn, mark the inputs consumed,
--                advance admission_epoch, and reopen the window.
-- No pending input: append run.completed and set the window to closed.
COMMIT;

This SQL is a conceptual model. Creating the Model Turn, marking Inbox rows consumed, and appending the decision event must also participate in one commit protocol, and the application must inspect the actual result of every statement. A serializable transaction retried as a whole or an equivalent versioned CAS protocol can provide the same boundary. The particular database syntax is not the point. The two paths must not each read admission_state once from an ordinary snapshot and then commit independently.

The race now has only two deterministic outcomes:

  • The input commits first: the finalizer sees the pending input, atomically creates the next Model Turn, advances the epoch, and reopens admission for later input.
  • The finalizer commits the terminal state first: the window becomes closed, so later input is not incorrectly marked as belonging to the current Run. The product can reject it explicitly or create a follow-up Run.

There is no third outcome in which the current Run accepts an input that nobody owns.

If Run control, the Inbox, and the Event Log live in different stores, the system cannot claim that these steps commit atomically. The admission decision must converge on one Source of Truth, with an outbox or reconciliation driving the other stores.

This protocol also assumes that only one Run owner with a valid lease may consume the Inbox and submit a terminal state at a time. owner_fencing_token rejects late writes from a stale worker. Lease renewal and takeover belong to the broader execution-ownership problem, but the assumption must be explicit here; otherwise two workers can still create competing next Model Turns.

Wake-up signals still help

A durable Inbox does not require every worker to poll at high frequency. After a successful write, an in-process queue, Redis Pub/Sub, or another notification mechanism can wake the current owner.

A signal means only “new input may exist.” A woken worker still queries the Inbox as the authority. Guaranteeing eventual processing after a lost signal requires an explicit re-drive mechanism. For example, the Inbox transaction can write an outbox record whose relay publishes to a durable queue, which retries delivery; alternatively, a heartbeat or scheduled scan can rediscover pending input within a defined maximum interval. A duplicate signal does not bind the same input twice because consumption is recorded in Inbox state and ordered by inbox_seq.

This is similar to the boundary for output streaming: notifications reduce latency, while durable records provide correctness. The owners differ, however. Output events prove what the Runtime has done; the Inbox proves whether user input was admitted and consumed.

Stop, steer, and follow-up are different actions

All three can enter through the same input box, but they have different semantics:

Input typeTargetCommon handling
steerThe next inference in an active RunEnter the Inbox and consume at a Model Turn boundary
stopCurrent execution control statePersist a cancellation request and wake the executor
follow-upNew intent against a completed targetCreate a new Run that references prior Session facts

Treating stop as a natural-language message can delay it until the model’s next round. Forcing a follow-up into an already terminal Run breaks terminality. A shared ingress layer can reuse identity and idempotency infrastructure, but each action needs its own state transition.

Back to the problem

Input that arrives during execution cannot live only in the current worker, and it cannot safely mutate messages while a model request is in progress.

A clearer protocol authorizes the request at a trusted ingress layer, writes the content and input idempotently to a durable Inbox, and creates a consumption record at an explicit Model Turn boundary. Signals only reduce wake-up latency; durable re-drive provides eventual discovery. Before a Run completes, the Runtime closes the current admission epoch and forces the race to resolve as either “atomically create the next Model Turn and reopen admission” or “commit the terminal state and route the input explicitly.”

The distinction keeps accepted, consumed, and “actually executed” from disappearing behind one ambiguous “received” status.
