Agent 08: Which Capabilities Should an Agent Expose on Each Turn?

Separate instruction resources, the Tool surface, Connectors, and MCP to decide which capabilities the model actually sees on one Turn.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentToolsSkills

The problem

A host integrates search, files, databases, ticketing, email, and dozens of business Tools. It also loads several Skills and MCP servers. The simplest approach is to place every description in every model request and let the model “choose for itself.”

The result is often the opposite of what was intended: similar Tools interfere with one another, high-privilege actions appear in unrelated tasks, schemas consume large amounts of Context, and newly discovered capabilities bypass the original policy. Integrating a capability is not the same as exposing it.

Separate four meanings of “capability”

Tool, Skill, Connector, and MCP are often grouped under the word capability, but they answer different questions:

AbstractionPrimary responsibility
ToolWhich structured actions the model may propose
SkillReusable working methods and instruction resources
ConnectorExternal identity, credential, and system-access boundary
MCPProtocol interface for capability discovery and invocation

One invocation path can use all four. A Skill tells the Agent how to handle a ticket, MCP exposes a discoverable Tool, a Connector resolves the user’s credential, and the final Tool definition enters the model request. Collapsing them into one registry mixes instruction, execution authority, and credential ownership.

A Surface is the resolved view for one Turn

A registry represents what the host knows exists. The surface for the current Model Turn is the result of resolving that registry against the task, identity, and policy.

normalized capability inputs
          ↓ discovery
task + identity + policy
          ↓ resolve
turn-scoped capability surface

Before a Tool definition enters this pipeline, it should already have been divided according to user intent, permission, and side effect. This article does not decide again how many Tools should wrap one endpoint. It consumes normalized definitions.

The final surface must answer:

  • Which Tools does the current model see?
  • Which Skill content has entered the prompt, and which Skills require explicit invocation?
  • Does a discovery result still require authorization?
  • From which version and source did the capability come?
  • Which changes take effect when the next Turn resolves its surface?

Eager, deferred, and disabled are different states

A small number of frequent, low-risk, and easily distinguished Tools may be exposed eagerly. Large collections of similar, infrequent, or expensive capabilities are better suited to deferred discovery. A capability prohibited by policy is disabled and must not become available merely because search found it.

“Frequent means eager, infrequent means deferred” is only a starting point. A Turn should consider at least five dimensions:

QuestionFavors eagerFavors deferred
Can the task predict the need?probably requiredonly potentially useful
What is the cost of missed recall?the task goes wrong or cannot recoverthe system can report a missing capability
What is the definition cost?small, distinguishable schemalarge schema or many similar definitions
Can discovery express the need?user language maps poorly to capability namesa namespace or summary is easy to search
Is an extra round trip acceptable?latency is unacceptablea long task can afford discovery

High risk does not imply deferred. An unauthorized capability must be disabled. A low-frequency control Tool such as request_confirmation or report_blocker may need to be eager because missing it sends the task down an unsafe path. Classification is not a permanent Tool-class property either: write_file may be eager in an explicit editing task and disabled in a read-only research task.

Tool Search returns candidates, not execution authority. A complete deferred path should be:

search query
→ candidate definitions
→ identity/policy filter
→ schema/version check
→ next-turn surface

If a search result is inserted directly into a model request that is already being generated, the model input loses its stable snapshot. If search bypasses policy, discovery becomes a privilege-escalation path.

Discovery can fail because an index is stale, a query returns nothing, a provider cannot load Tools dynamically, or the model never performs the search. Failure must not expand every deferred Tool. Doing so would turn an availability problem into a sudden change in token use, selection space, and security surface.

Safer fallback keeps a budgeted set of core eager Tools, provides a small static surface for selected high-value namespaces, or returns a repairable “capability not found” result. Every fallback still consumes the same allowed set. Discovery failure can never make a disabled capability visible.

Pi’s Skill and resource boundaries

Pi currently represents a Skill as an instruction resource with fields such as name, description, content, and filePath. Three responsibilities remain distinct:

  • a package utility discovers, loads, and formats Skills;
  • the host decides which concrete resources and prompt content enter Harness;
  • Harness provides runtime boundaries such as explicit skill() invocation.

This does not mean Harness automatically owns a complete Skill registry or package governance. Versioning, pins, dependencies, rollback, and the Tools, files, or environment required by a Skill are provenance contracts that a host may add. Pi’s current fields do not already guarantee them.

See Pi’s skills.ts and agent-harness.ts.

Test the final Surface with two tasks

The first task is “search and summarize public documentation.” It needs search and read Tools and perhaps a related Skill. It does not need to send email, modify tickets, or use a user’s private credential.

The second task is “update a ticket with approved content.” It may need a ticketing Connector, the current user’s authorization, and a write Tool, but it still should not automatically gain email or database-administration capabilities.

Both resolutions can use the same registry and produce different surfaces:

read task  → search, read
write task → search, read, update_ticket

If dynamic discovery finds delete_ticket, policy can still leave it in the disabled set. Whether a capability exists, has been discovered, is visible on this Turn, and is authorized for execution must remain four separate decisions.

Back to the problem

After integrating many Tools, Skills, Connectors, and MCP servers, the right response is not to put all of them in front of the model. Instead:

  1. Keep the responsibility boundary of each capability.
  2. Consume normalized capability inputs with provenance.
  3. Choose eager or deferred from task predictability, missed-recall cost, definition cost, discoverability, and latency.
  4. Filter discovery and fallback results by identity and policy.
  5. Freeze the resulting set into the next Turn snapshot.
  6. Revalidate authorization in the Tool and backend at execution time.

The capability surface is a turn-scoped view, not a copy of the global registry. The smaller and more explainable it is, the easier it is for the model to choose the right action—and the less security depends on the model voluntarily ignoring irrelevant capabilities.
