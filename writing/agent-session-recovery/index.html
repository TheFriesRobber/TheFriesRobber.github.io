Agent 11: How a Session Tree Supports Recovery

Separate branched Session history, Context projection, and the execution Journal, then show how the host restores configuration and settled results from a Checkpoint.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentSessionRecovery

The problem

An Agent invokes write_note. The remote system completes the write, but the process exits before saving the Tool Result. After restart, the Session contains only the earlier messages. Should the system continue, query, or invoke the Tool again?

The same branch also underwent Context compaction earlier. From the visible messages, the restarted host can infer neither the write fact nor whether the model, active Tools, and runtime dependencies selected before compaction can still be reconstructed completely from the current path.

If recovery means sending messages back to the model, the model may propose the write again. Assuming success directly would have no supporting evidence. Session history can recover a conversation, but it does not automatically recover execution facts or runtime configuration. This article brings both concerns into one recovery path: the Session preserves traceable history, while independent evidence supports effect reconciliation and host configuration rehydration.

A Session Tree stores traceable history

Pi Harness Sessions form a branching tree from append-only entries with parentId. Selecting different leaves produces different branches, and a compaction entry can compress earlier messages into a new Context starting point.

This structure is better than modifying a message array in place for:

  • preserving history before a user edit or retry;
  • creating a new branch from an older node;
  • recording entries for changes to the model, thinking, active Tools, and other configuration;
  • projecting Context from the current leaf.

But “an entry was recorded” does not mean full configuration will always be visible during recovery. Pi’s buildContext() uses getPathToRootOrCompaction(). When it encounters a compaction with a retained tail, the path stops at that boundary, and the compaction entry does not itself store every configuration value. The last model, thinking, or active-Tools change before compaction may therefore no longer participate in derivation of the current SessionContext.

The current Session can derive configuration along the context-visible path. It is not a complete branch-scoped restore source.

Context projection is not an execution journal

A Session Tree primarily answers, “What is the model Context for the current branch?” An external side effect asks, “What happened in which Attempt of which operation?” These facts have different grains.

The opening write needs at least this durable evidence:

operation id
attempt id
tool proposal
authorization/config revision
started marker
effect reference
terminal outcome or unknown

Putting all this into a natural-language message erases state boundaries. Saving only the final Tool Result leaves uncovered the window where the effect occurred but the result was not persisted. The previous article defines the execution Journal and Checkpoint contracts for authoritative records, commits, and replay. This article consumes only their settled or unknown evidence and limits Session messages to settled results.

The current Harness does not automatically restore complete runtime configuration

Pi’s current createTurnState() consumes context.messages derived from the Session, while the model, thinking mode, active Tools, and runtime function dependencies still come from host configuration. Even when the Session can derive those values, Harness does not automatically reconstruct them into executable configuration.

Recovery also involves objects that cannot or should not be deserialized blindly:

  • a provider client and in-progress stream;
  • Tool handlers, credential providers, and network connections;
  • current policy, secrets, and runtime resources;
  • upgraded schemas or code versions.

Restore is therefore not deserialization of an entire object graph. It is host rehydration: read durable state, resolve dependencies again in the current environment, and validate compatibility.

See Pi’s current Session and Harness boundaries in session.ts and agent-harness.ts.

Compaction and restored configuration need separate contracts

Context compaction may discard details that the model no longer needs. It must not thereby lose the current execution revision on which recovery depends.

The host has two safe options:

  1. Traverse the complete parent ancestry separately for configuration recovery instead of reusing the path truncated by Context compaction.
  2. Store a verifiable configuration checkpoint with compaction and make later entries reference it explicitly.

Either approach must keep a Context summary separate from a restore checkpoint. The former saves model budget; the latter restores Runtime dependencies.

Let evidence decide the recovery action

For write_note, the minimal recovery table is:

Durable evidenceRecovery action
A terminal effect record existsReconstruct the Tool Result without repeating execution
Only intent/start and an effect reference existQuery or reconcile the external system
An operation key exists and the external system confirms non-executionCreate a new Attempt
No durable intent exists or lookup is impossibleRemain unknown and stop automatic retry

The table deliberately does not interpret “the Session has no Tool Result” as “the Tool did not execute.” Missing records prove only that the local system lacks evidence.

After recovery, the host creates a new turn snapshot and projects confirmed results back into Context. A provider stream does not resume in the middle. Client reconnection, if required, should consume independent durable events and a cursor.

Back to the problem

Restoring only messages cannot determine whether write_note took effect externally, nor can it guarantee reconstruction of runtime configuration selected before compaction. A Session Tree provides branched, traceable Context history, but it has three explicit boundaries:

  • configuration is derived only from the context-visible path, which compaction may truncate;
  • the current Harness automatically consumes only derived messages, while the host reconstructs runtime dependencies;
  • external Tool effects require an independent operation/Attempt journal.

One recovery should therefore proceed in this order:

  1. Use the operation journal to find terminal evidence, an effect reference, or unknown evidence for write_note, and reconcile with the external system when necessary.
  2. Independently read the complete ancestry or a configuration checkpoint, then combine it with current host policy to reconstruct the model, Tools, credential provider, and other dependencies.
  3. Validate compatibility between old state and current code, schemas, and permissions; stop or migrate when they are incompatible.
  4. Only then create a new turn snapshot that projects confirmed Tool results and current configuration into Context.

The Session Tree is the historical foundation for recovery, but neither effect evidence nor restore configuration can be guessed from visible messages. The tree itself is not a complete recovery protocol.
