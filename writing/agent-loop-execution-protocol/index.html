Agent 01: The Agent's Minimal Core: Loop, Turn, and Execution State

Starting from a Tool write with an unknown outcome, this article uses a minimal state model to separate the Agent Loop, Model Turn, Tool Execution, and Attempt.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentRuntimeState Machine

The problem

Consider a minimal Agent:

while (true) {
  const response = await model(messages);
  if (!response.toolCalls.length) return response;

  for (const call of response.toolCalls) {
    messages.push(await tools[call.name](call.arguments));
  }
}

It can already invoke Tools and return their results to the model. But suppose write_note has written content to an external system and the response times out before returning. The loop sees only a rejected promise. It cannot answer the most important question: did the write fail, or is its outcome unknown?

Treat both cases as failure and retry immediately, and the second call may create a duplicate. Treat the timeout as success, and the Agent may report an action that never happened. The minimal core of an Agent Runtime is therefore not a while loop, but a protocol that separates model proposals, execution attempts, and external facts.

A Tool Call is only an action proposed by the model

A Tool Call says, “I propose invoking write_note with these arguments.” It is neither authorization nor evidence that an external action has occurred.

Moving from proposal to fact crosses at least three owners:

BoundaryWhat it ownsWhat it can prove
ModelTool Call proposalThe model wants to perform an action
Runtimevalidation, authorization, and execution AttemptAn attempt was admitted, started, or returned
External systemBusiness state such as a note, payment, or fileWhether the side effect actually occurred

Pi’s current Loop already separates model turns, Tool Calls, Tool Results, and turn-boundary control flow; agent-loop.ts also emits Tool execution events. It does not, however, expose independent state objects for logical operations, Tool Executions, or Attempts. The state model below is a design recommendation built on Pi’s control flow, not a description of its current API.

This article uses the following hierarchy:

Task
└─ Run: one execution instance of the Agent Loop
   ├─ Model Turn: one model request and its response
   └─ Tool Execution: the logical execution of one authorized proposal
      └─ Attempt: one physical dispatch that has started

logical operation: a stable identity that links one business intent
                   across Turns or Tool Executions

A Task represents the user’s goal. A Run begins with one input and spans Model Turns and Tool Executions until that Loop invocation converges. Each retry creates a new Attempt under the same Tool Execution. A logical operation is a cross-layer correlation key and should not be drawn as the direct parent of an Attempt. These objects do not all need to become public classes, but logs, evaluations, and recovery logic must know which grain they are measuring.

One Tool execution needs three identities

Timeout and retry handling most often confuses three identities:

  • logical operation: the stable user or business intent, such as “write this content to note-42”;
  • Tool Execution: the Runtime’s logical execution of one authorized Tool proposal;
  • Attempt: one physical dispatch actually started to complete that Tool Execution.

After the first write_note times out, the logical operation and Tool Execution remain the same, but the Attempt has ended. If the idempotency contract and current evidence permit another call, the Runtime should create a new Attempt ID instead of overwriting the previous history.

operation op-17
└── tool execution tool_exec-1
    ├── attempt a1 → timeout → observed outcome unknown
    └── attempt a2 → may be created only after safety is established

This distinction allows two apparently contradictory metrics to be true at once: the Attempt timeout/unknown rate may increase while the Tool Execution and logical operation eventually succeed. Later observability, evaluation, and cost attribution must preserve the same grain.

After crossing an external Effect boundary, a timeout proves only an unknown outcome by default

A function return value describes what the Runtime observed, not necessarily what happened in the external world. If the timeout occurred before dispatch, during validation, or at another point where the handler provably had not started, the Runtime can confirm that no side effect occurred. Only after execution crosses an external effect boundary whose outcome cannot be confirmed does timeout mean unknown by default.

For a pure read, issuing another query after a timeout usually does not change business state. For an idempotent write, the Runtime may retry with a stable operation key. For a write that offers neither idempotency nor a lookup API, the only safe state is unknown.

During preflight, a proposal first moves through proposed → rejected | authorized. An authorized proposal creates a Tool Execution; the Runtime creates an Attempt only when it actually starts physical dispatch. The conceptual state of one Attempt begins there:

dispatching
  → observed_succeeded
  → observed_failed
  → observed_unknown

observed_failed requires evidence that the action did not take effect, or that the failure occurred before any side effect. observed_unknown explicitly means that the Attempt did not produce a usable conclusion; it must not be converted automatically into failed. The original observation on an Attempt is immutable. A Tool Execution updates its current verdict only after aggregating Attempts and later effect evidence and completing any required query or reconciliation.

Return to write_note. If the external system can query by operation key, the Runtime first looks up op-17. If the note exists, Attempt a1 still records that its observed outcome was unknown at the time, while the effect evidence and the verdict of tool_exec-1 converge to succeeded. Only a lookup that confirms no execution permits a new Attempt. If no lookup is possible, the state remains unknown and the uncertainty is exposed to the upper layer.

Cancellation does not rewrite facts that already occurred

For an Attempt that has started and crossed the external effect boundary, cancellation has the same limitation as timeout. An abort signal can ask a handler to stop promptly, but it cannot roll back an HTTP request, database transaction, or remote job that has already been committed. A Tool Execution that has not started dispatch can stop definitively, in which case it never creates an Attempt.

Cancellation is therefore a separate control state, not an effect outcome alongside succeeded, failed, and unknown. It contains at least two facts:

  1. The Runtime will not start new work.
  2. Attempts that already started must converge cooperatively, while their external effects are still recorded as succeeded, failed, or unknown.

Only before dispatch can a Tool Execution settle as cancelled_before_dispatch, with no Attempt. Once an Attempt has been created and crossed the effect boundary, the Runtime can record only cancellation_requested while preserving the Attempt’s independent observed outcome and the Tool Execution’s current verdict. If dispatch has started but the Runtime can prove that no effect occurred, the Attempt may be observed failed. Treating cancelled as the final business result of every child action discards the actual history.

When may the Loop stop?

“The model did not request another Tool” is only a candidate stopping condition. The Runtime must also confirm:

  • there is no steering or follow-up that must still be processed;
  • there are no child tasks still owned by the current Run;
  • there is no unknown effect that must be exposed before returning;
  • the current result satisfies the host’s termination policy.

Pi’s current Loop checks steering at turn boundaries and checks follow-up when it would otherwise stop. That behavior makes termination part of the protocol, not a simple break. Durable recovery, distributed Jobs, and client reconnection belong to later articles, but all of them should consume the logical operation, Tool Execution, Attempt, and outcome defined here instead of inventing a second set of identities.

For implementation evidence, see Pi’s agent-loop.ts and types.ts.

Back to the problem

A while loop that can invoke Tools describes control flow, not execution facts. When write_note times out, the right questions are not merely whether to call the function again, but:

  1. Which logical operation, Tool Execution, and Attempt is this?
  2. Did the timeout occur before the side effect, after it, or at a point where that cannot be determined?
  3. Which owner can query or repair the external fact?
  4. Does the current evidence permit retry, require reconciliation, or force the state to remain unknown?

Once the Runtime can answer these four questions, retry, cancellation, termination, and later recovery share a common meaning. The Loop can remain small without mistaking a function return value for the state of the world.
