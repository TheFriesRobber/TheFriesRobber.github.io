Context Engineering 3: Manage Long Conversations with Incremental Compression

Use checkpoint summaries, incremental compression, and source backlinks to manage long conversations.

07/15/2026 Views
AgentContext EngineeringMemory

The problem

Suppose a user and an Agent complete a report over 100 user interactions: the first 30 establish scope, the next 40 search for evidence, and the final 30 revise the conclusions.

By the seventieth user interaction, the complete history no longer fits in Context. Two direct responses are:

  1. Resummarize all earlier messages after every interaction.
  2. Maintain one summary and overwrite it with a new version whenever space runs out.

The first approach repeatedly reads and summarizes the same content, so its cost grows with the conversation. The second is cheaper, but repeated rewrites can gradually move the summary away from the source. Worse, at interaction 82 the user may say, “The report should not cover every region. Keep Europe only.” The system must know which conclusions in the old summary depended on the corrected scope.

If a summary is only an unsourced paragraph, the system cannot tell which messages it covers or whether it should apply a local correction, rebuild the whole summary, or let the latest statement override it temporarily.

The central problem in long-conversation compression is therefore not “write a shorter summary.” It is: treat the summary as a rebuildable derived view and record which raw interval it covers.

Separate raw history from model input

Compression itself should not rewrite or delete the conversation’s factual record. Independent retention and authorization policies may still delete a source or make it unreadable. Start by separating two concepts:

  • Raw history: User messages, model responses, Tool Calls, and Tool Results that remain readable under the current retention period and authorization policy.
  • Context view: The history view actually sent to the model for the current Model Turn. It may combine a summary with recent raw content.

Raw history is the source of a summary. The summary is derived to satisfy a Context Budget. This article splits generation responsibility in two: a programmatic Compression Controller selects still-authorized source spans, stable boundaries, and metadata, while a summarizer model produces only the structured body. The program then validates coverage, references, and version predicates before committing the active summary with CAS. An implementation may substitute a deterministic summarizer, but that changes only the body generator; source selection, authorization, and commit authority do not move to the generator. Keeping only the summary would replace source data with a cache: once compression is wrong, no reliable basis remains for repair. Conversely, when a source is deleted or its permission is revoked, a summary derived from that source must not bypass the original policy and continue exposing the content.

The compression checkpoint in this article is a watermark that says “history has been compressed through this point.” It is not the Checkpoint used to recover Runtime execution. It does not restore a Tool Attempt, external side effect, or process state.

One incremental compression spans three intervals

Divide the current history into three parts:

checkpoint summary | stable raw prefix | recent raw window
   compressed          ready to compress       kept verbatim for now
  • The checkpoint summary covers older messages that have become stable.
  • The stable raw prefix contains topics or execution phases that ended after the previous checkpoint.
  • The recent raw window keeps active discussion, incomplete Tool Calls, and the user’s latest corrections verbatim.

“Stable” does not mean merely old. It means the content no longer participates in an unresolved action. If the model has issued a Tool Call and the result has not returned, replacing the pair with “query in progress” may leave the next Model Turn without the call/result relationship.

A checkpoint must record its coverage

A useful summary record contains more than the summary body:

summary_id: summary_3
covers: event_seq 1..checkpoint_seq
dependencies:
  previous_summary_backlinks: [summary_2]
  source_spans:
    - event_seq 1..previous_checkpoint_seq
    - event_seq previous_checkpoint_seq+1..checkpoint_seq
  decision_refs: []
policy_revision: 4
authorization_revision: authz_19
retention_revision: retention_6
created_at: 2026-07-15T10:00:00Z

Here, event_seq is the order in the Session Event Log across user messages, model responses, Tool Calls, and Tool Results. It is different from a stable content identity such as message_id=msg_evidence_42. covers says only which event interval the summary represents, so Assembly can detect overlaps or gaps against the recent window. dependencies records the complete set of inputs that affect summary content: raw sources, Assembly Decisions, and any previous-summary backlinks actually reused during generation. Dependency checks recursively follow those backlinks, so a coverage interval cannot stand in for the dependency closure. policy_revision identifies the compression rules, while the authorization and retention revisions record the data-visibility boundary used during generation.

The body should preserve structure instead of flattening everything into prose:

current goal: complete the European market report
confirmed constraints: use only public sources; every citation must be traceable
completed: evidence search, data cleaning
unresolved: whether the 2025 definition matches the 2024 definition
critical evidence: message_id msg_evidence_42, tool_result_id result_17, file_id file_8@revision_8

Structure cannot guarantee that a summary is correct. It does let later compression and conflict resolution distinguish goals, constraints, completed work, and evidence instead of reducing all of them to generic background.

Incremental updates must not summarize summaries forever

At the stable event boundary corresponding to the seventieth user interaction, the system can create summary_3 from summary_2 + the stable raw prefix after the previous checkpoint. It avoids reprocessing the complete earlier history on every pass, then advances from the new stable boundary next time.

If the system always summarizes only the previous summary, however, early omissions become permanent and repeated rewrites accumulate semantic drift. The incremental path also needs a rebase path. While raw sources remain readable, the following changes should trigger regeneration from affected raw history instead of another incremental rewrite:

  • The user explicitly corrects a fact or constraint stored in the summary.
  • The compression policy, model, or structure changes incompatibly.
  • Evaluation finds that repeated compression frequently loses a particular class of facts.

Source deletion or permission revocation is not an ordinary rebase. First follow the complete dependency closure and mark every summary that directly or transitively depends on the source as unusable; a coverage-interval lookup is not sufficient. Then rebuild using only remaining records that are readable, still authorized, and independent of the invalid source. Later messages, Assembly Decisions, or Tool Results that repeat the source also belong to the dependency chain. If their independence cannot be established, conservatively exclude the related suffix. If a safe rebuild still cannot be produced, mark that Context as needs_rebuild and exclude the old summary. The existence of a cached summary must not continue exposing content from an invalid source.

This resembles an incrementally maintained materialized view: consume new changes normally, then rebuild the affected range when a dependency becomes invalid. It is only a mental model; the implementation does not need to use a database view.

How should a summary change after a user correction?

Suppose the active summary still says “Europe and North America,” and the user explicitly says “keep Europe only”:

summary_3: report covers Europe and North America; covers event_seq 1..checkpoint_seq
correction_seq: user says “keep Europe only” (message_id=msg_scope_correction)

The system appends the correction to Raw history instead of rewriting summary_3. Context Assembly’s programmatic policy then decides two things: the current Task uses “keep Europe only,” and the correction should affect later conversation. An implementation may use a model to help classify semantic scope, but the Assembly Controller owns the policy record and the decision to trigger a rebuild. Because the old summary conflicts with that decision, Assembly pauses request rendering while the compression layer follows dependencies to still-authorized sources and asks the summarizer to rebuild the stable interval identified by covers:

summary_4: covers event_seq 1..checkpoint_seq
replaces: summary_3
dependencies:
  decision_refs: [correction_seq / msg_scope_correction]
current goal: complete only the European market report

summary_4 rebuilds only the old stable interval; correction_seq remains verbatim in the recent window. After validation, the system switches the active summary with CAS. The predicate checks the active version, event watermark, and authorization/retention revisions; a change to any of them discards this result and triggers another rebuild. On failure, Raw history and the old summary version remain available, while the current Run ends with failure_reason=context_needs_rebuild instead of sending conflicting content to the model.

If the user says “hide North America for this presentation,” Assembly creates a Context view for the current Run and does not rebuild the summary. Rebuilding depends on the correction’s scope, not on whether its wording contains “hide” or “delete.”

The recent window cannot use a fixed message count

Keeping “the last 20 messages” is simple, but the cutoff can split one execution unit: retain a Tool Result while removing its Tool Call, or retain the model’s “complete” response while removing the user’s subsequent correction.

The left boundary of the recent window should at least preserve complete interaction units:

  • Do not split a Tool Call and Tool Result pair.
  • Do not split an unresolved confirmation or user correction.
  • Do not move the boundary past evidence still referenced by the current planning or execution phase.
  • Keep the latest explicit instruction verbatim instead of relying only on a summary.

The system usually starts from a target token size and searches backward for a safe boundary rather than preserving exactly N messages.

How to evaluate compression reliability

Compression ratio only describes how much shorter the content became. It does not say whether important information survived. A test case for a long conversation can label:

  • user constraints that must remain;
  • facts that require a source reference;
  • completion states that must not be rewritten;
  • old information corrected by newer messages;
  • Tool Call and Tool Result pairs that must stay together.

Then evaluate factual retention, instruction retention, provenance completeness, conflict updates, and rebuild cost separately. Test repeated incremental compression rather than only the first summary; semantic drift often appears after several passes.

Back to the problem

A long conversation cannot rely only on repeated full-history summaries or one summary that is overwritten indefinitely.

A more stable model uses raw history within retention and authorization boundaries, compresses stable intervals into a checkpoint summary with coverage and source backlinks, and keeps the recent window verbatim. It advances incrementally under normal conditions. After a correction or compression drift, it rebases from affected sources that remain readable. After source deletion or permission revocation, it first invalidates related summaries, then rebuilds from the remaining sources.

The summary is then an inspectable and rebuildable Context view, not long-term Memory that gradually replaces the factual record.
