Apache Spark Resource Management on YARN

An overview of Apache Spark resource management and the application model used when Spark runs on YARN.

04/12/2020 Views
SparkBigdata

The questions

What does the architecture of an Apache Spark application look like? How does it differ from MapReduce? How does a Spark application use YARN for resource management?

Comparing Spark with MapReduce

Applications

The highest-level unit in MapReduce is a job. A job loads data, runs a map function, shuffles the data, runs a reduce function, and writes the result back to storage.

In Spark, the highest-level unit is an application. One application can contain multiple jobs; a job can be divided into stages, and each stage contains multiple tasks.

A Spark application corresponds to a SparkContext instance. In general, one JVM should have only one SparkContext. An application may execute a single batch job or run multiple jobs interactively. Unlike MapReduce, a Spark application owns a set of processes requested from the resource manager, known as executors. Those processes can remain alive in the cluster even when no job is currently running. This allows data to remain in memory for fast access and avoids repeatedly paying process startup costs.

Executors

Each executor can use multiple threads, represented as cores, to run tasks concurrently. Holding resources throughout an application’s lifetime can be unfriendly to a shared cluster. Dynamic allocation1 lets an application acquire and return executors according to demand, using the resource-management mechanisms provided by the cluster manager.

Driver

The driver manages job flow and task scheduling for a Spark application. It commonly runs in the client process, but under YARN it can also run inside a YARN container, depending on --deploy-mode client or --deploy-mode cluster. The driver contains essential components for DAG construction, task orchestration, and execution-plan generation, which are beyond the scope of this article.

Multiple cluster managers

Spark supports several cluster managers, including YARN, Mesos, standalone mode, and Kubernetes. Each provides two broad components:

  1. A central service that decides which applications may start executors, and where and when those executors run—for example, the YARN ResourceManager, Mesos master, Spark standalone master, or Kubernetes control plane.
  2. A per-node service that starts executor processes and monitors their health and resource consumption—for example, the YARN NodeManager, Mesos agent, Spark standalone worker, or Kubernetes node components.

Running on YARN

Cluster mode

  • The client submits a request to the ResourceManager to start an ApplicationMaster, then can exit once the application has been accepted.
  • A NodeManager launches the ApplicationMaster. In cluster mode, the driver runs with the ApplicationMaster in a YARN container.
  • The ApplicationMaster requests resources from the ResourceManager and starts Spark executors.
  • The driver schedules work and communicates directly with executors to run tasks.

Client mode

  • The client requests an ApplicationMaster from the ResourceManager while the driver remains in the client process.
  • A NodeManager starts the ApplicationMaster, whose primary role in this mode is to request cluster resources.
  • The ApplicationMaster requests resources from the ResourceManager and starts Spark executors.
  • The driver schedules work and communicates directly with executors to run tasks.

Advantages of Spark on YARN

  • A YARN cluster can run Spark alongside other frameworks and workloads, including MapReduce, Impala queries, Tez, and Pig, without maintaining a separate cluster.
  • YARN schedulers2 support workload classification, isolation, and prioritization.
  • Kerberos credentials can support secure authentication for executors and access to cluster services.
