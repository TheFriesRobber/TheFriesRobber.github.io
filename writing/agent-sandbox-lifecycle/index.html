Agent 24: Sandbox Lifecycle and the Control Plane

Use Session, lease, policy, acquire, readiness, and reconciliation to explain why successful Sandbox creation does not make it ready for execution.

07/24/2026 Updated 07/27/2026 Views
Agent ProductionAgentSandboxControl Plane

The problem

An Agent Session has been running for a while. The Control Plane asks a provider to create a Runtime. The provider returns created, the health check passes, and the system mounts the old Workspace and resumes execution.

But another chain of facts also exists: the old lease has expired, a new Session has taken over the same Workspace, and the new Runtime is still using the previous policy revision. The container is alive, but it is neither the current owner nor running under the current policy.

A successful create workload proves only that the provider’s own creation contract holds. It may mean that the request was accepted, a resource record was created, or the workload exists. Readiness answers only whether the process is prepared to respond to a probe. Neither proves the Agent-level ownership and policy contract. The Agent needs a stronger conclusion:

The current Session holds an unexpired lease for the specified Workspace, and a Runtime that conforms to the target policy has completed its mount and initialization and can accept execution.

That is the lifecycle contract a Sandbox Control Plane must own.

Four objects cannot be collapsed into one sandbox ID

A stateful Sandbox contains at least four objects with different lifecycles:

ObjectStable identityWho decides whether it is valid
Sessionsession_idAgent Control Plane
Workspaceworkspace_id, revisionWorkspace store
Runtime workloadProvider resource IDProvider and Control Plane observations
LeaseOwner, generation, expiryTrusted lease store

A Runtime can be deleted and recreated while the Workspace remains. A Session can end while a provider workload survives temporarily because deletion timed out. A lease can expire while the container remains healthy. One sandbox_id cannot express these forks.

A client-visible Sandbox handle should therefore combine several verified facts rather than alias a provider ID. The following is a conceptual record, not a provider API:

{
  "session_id": "session_42",
  "workspace": {"id": "ws_7", "revision": 18},
  "runtime": {"provider_id": "vm_91", "profile": "python-3.13@sha256:..."},
  "lease": {"owner": "session_42", "generation": 6, "expires_at": "..."},
  "policy_revision": 12,
  "state": "ready"
}

Here, ready is not a Boolean that any component may set independently. It is client-visible state computed by the Control Plane from durable facts at each acquire stage.

The Control Plane owns convergence, not resource creation

Providers are good at creating workloads, networks, or volumes and reporting their current state. They usually do not know Agent-domain concepts such as Sessions, Workspace ownership, delegation, or policy revisions.

The Control Plane therefore needs to retain separately:

  • desired state: which Workspace this Session should bind, and which Runtime profile and policy revision it should use;
  • observed state: which workloads, mounts, and networks the provider currently reports, plus probe results;
  • ownership evidence: who holds which lease generation, and the Workspace’s current revision;
  • client-visible state: whether the caller may acquire, wait, retry, or must stop.

Kubernetes controllers provide a useful implementation pattern by using a control loop to move current state toward desired state. They do not automatically add Agent Session ownership semantics. The application’s Control Plane still has to define that Session contract.

Acquire is a recoverable, multi-stage protocol

A safe acquire can advance through:

requested
  → lease_acquired
  → runtime_allocated
  → workspace_attached
  → initialized
  → policy_verified
  → ready

Every step can complete its side effect and then lose the response. The state machine therefore needs a stable acquire identity and must let each stage resume by querying facts instead of interpreting a timeout as “nothing happened.”

After an allocate timeout, for example, the reconciler should first query for an existing workload by request tag or provider reference. If it finds a matching resource, it records observed state and continues. If it cannot determine the outcome, it enters unknown or reconciling instead of creating another workload immediately.

Likewise, a readiness probe proves only that the process meets the probe condition at that moment. It does not prove that:

  • the Workspace is mounted at the expected revision;
  • the lease still belongs to the current Session;
  • egress, secret, and resource limits follow the target policy;
  • another Runtime cannot continue writing the same Workspace.

ready must combine all of this evidence. When a stage fails, the system should return an explicit wait or stop state. It must not hand a handle to the Agent and let the first Tool Call discover that the mount is incomplete.

Ready is a conditional commit that must be refreshed

Reading every Condition and then unconditionally writing state=ready still creates a race. Suppose generation 5 has a slow initialization probe. The user stops the Session, or generation 6 takes over, before that probe succeeds. Its late result must not reopen the old Runtime.

A local CAS lets the Control Plane stop a late result from overwriting newer desired state, but it cannot prove that a lease, Workspace, and policy owned by different systems remain valid at the same instant. A stronger Ready Contract requires those owners to participate. The Control Plane assigns a readiness_epoch, and each owner returns a time-bounded proof bound to that epoch, the Runtime generation, and its own revision.

desired_state = active
desired_revision = 27
runtime_generation = 6
provider_ref = vm_91
readiness_epoch = ready_6_27
workspace_proof = ws_7@18, generation=6, valid_until=t1
lease_proof = lease_4@generation_6, valid_until=t1
policy_proof = policy_12, runtime=vm_91, valid_until=t1
control_plane_version = 44

When any owner performs a takeover, detaches a binding, or changes policy, it must advance its generation or revision, or otherwise invalidate the old proof. The Control Plane may publish a Ready record through CAS only while every proof remains unexpired and bound to the current epoch. The record stores the proof references and their earliest valid_until. This does not require a distributed transaction across owners, but asynchronous reads must not be presented as proof that every fact held simultaneously. If an owner supplies only asynchronous observations, Ready is explicitly a time-bounded projection.

Ready is not a permanent terminal state either. Every Tool admission revalidates the lease generation, proof freshness, and valid_until. The owner of an actual Workspace or effect write must also check the generation or fencing token at its write boundary. Even if takeover occurs immediately after Ready was published, the old Runtime then cannot exploit the TOCTOU window to keep producing effects.

A refresh obtains fresh owner proofs, conditionally updates the projection for the current readiness_epoch, and revalidates at least that the lease has sufficient headroom, Runtime and Workspace bindings have not drifted, and the target policy remains enforced. A refresh timeout does not authorize the Runtime to assume that renewal succeeded. As a lease or Ready Contract approaches expiry, the Control Plane stops new Tool admission before renewing, replacing, or quarantining the Runtime. An expired generation cannot be revived by refresh; it must acquire new execution authority.

A lease needs a generation, not only an expiry

Comparing only expires_at still permits an old owner to revive. Runtime A becomes unreachable and its lease expires. Runtime B acquires the lease and takes over the Workspace. A later regains connectivity and continues writing.

A common design assigns a monotonically increasing lease generation to every takeover and passes it to the Workspace write boundary. The Workspace backend accepts only the current generation:

Runtime A: generation 5 → rejected
Runtime B: generation 6 → accepted

This fencing check must occur at a trusted boundary that can enforce rejection. Asking the old Runtime to reread the lease cannot stop a disconnected process from continuing with cached state.

The Kubernetes Lease API demonstrates leases for heartbeats and leader election, but the generation, Workspace fencing, and acquire states in this article are design recommendations for an Agent Sandbox. Kubernetes Leases do not provide them automatically.

Release must also converge through reconciliation

A normal-path release() is not the end of the lifecycle. Deleting the Runtime can succeed before writing the Control Plane database fails. Conversely, the database can mark the resource released before provider deletion times out.

A more reliable design first changes desired state so that the Sandbox can no longer be acquired, then lets a reconciler repeatedly compare observed state:

  1. Stop new lease refresh and Tool admission.
  2. Revoke or advance the lease generation so the old owner becomes invalid.
  3. Query and delete workloads, network attachments, and temporary resources that have lost ownership.
  4. Retain, quarantine, or release the Workspace or volume according to retention policy.
  5. Mark a terminal state only after provider facts and local state have converged.

Deletion must be repeatable, and not found should be treated as possible convergence evidence rather than a new error. Resources with an unknown owner, an exhausted retry window, or an unresolved mount conflict should enter quarantine or manual review instead of being retried forever or returned directly to the pool.

Back to the problem

Although the opening workload has been created and passes its health check, the Control Plane should reject acquire: its policy revision is stale, and the Workspace’s current lease generation belongs to another Session.

The system should mark the old workload as having lost ownership, stop admission, and let reconciliation clean it up. It should return an executable handle only when the new Runtime simultaneously satisfies the Workspace binding, a valid lease, the target policy, and readiness.

A Sandbox is therefore not “a container that has started.” It is a continuously verifiable Session contract. The provider creates resources; the Control Plane owns the contract’s desired state, ownership, and eventual convergence.
