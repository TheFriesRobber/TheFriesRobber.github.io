Context Engineering 5: Isolate Provider Differences behind Adapters

07/15/2026 Views
AgentContext EngineeringModel Routing

The problem

Suppose the Runtime has already selected a model and is about to perform a document search. Internally, it records the same logical interaction:

user request
→ assistant tool call: search_documents(call_17)
→ tool result: call_17
→ assistant final answer

Providers may represent this interaction differently. Some expose Tool Calls and Tool Results as separate items; others place them in content blocks inside assistant and user messages. Tool names, supported Schema subsets, streaming events, and finish reasons may also follow different constraints.

If business code exposes only one generate() method but scatters branches around each call:

if provider == "a":
    # change roles and attach the tool result
elif provider == "b":
    # change content blocks and transform the schema

then the provider difference has not been abstracted. It has merely leaked out of the HTTP client and into Context Assembly, the Agent Loop, and the Tool Runtime.

The system needs to standardize semantics, not merely a method name: which instructions, messages, and Tools a request contains; which complete items came back; and how a Tool Call is associated with its Tool Result.

A canonical contract is not the smallest common Provider subset

The Runtime can first define its own canonical contract:

{
  "operation_id": "model_op_17",
  "continuation_ref": "conversation_9@item_24",
  "instructions": [{"kind": "runtime_policy", "content_ref": "policy_8"}],
  "input_items": [
    {"type": "user_message", "content": "Find the retry policy in the design documents"},
    {
      "type": "assistant_tool_call",
      "call_id": "call_16",
      "name": "search_documents",
      "arguments_ref": "args_16"
    },
    {
      "type": "tool_result",
      "call_id": "call_16",
      "status": "succeeded",
      "content_ref": "artifact_42"
    }
  ],
  "tools": [{"definition_ref": "search_documents@revision_5"}],
  "required_features": ["tool_call_identity", "streaming"],
  "required_provider_guarantees": ["preserve_required_fields"]
}

The canonical contract should not copy one provider’s API, nor should it collapse into the smallest set of fields every provider can express. It should represent the capabilities the Runtime actually requires. When a route cannot express one of them, its Adapter returns an explicit incompatibility instead of silently dropping fields.

Upstream code then handles only canonical user_message, assistant_tool_call, tool_result, and a stable call_id. Whether a provider places them in a particular role or content block belongs to the Adapter.

An Adapter declares capability before transforming a request

An Adapter should not receive a request and guess about compatibility while it converts fields. It can first run a preflight against the route’s capability profile:

canonical request
→ capability check
→ schema and message transform
→ provider request
→ provider response / stream
→ canonical items and events

Preflight needs at least three outcomes:

ResultMeaningUpstream action
supportedThe required semantics are representableContinue rendering the request
lossyThe request can be sent, but some semantics weakenContinue only when policy explicitly permits the loss
unsupportedRequired semantics cannot be representedReturn control to the Router to select another route

The Adapter does not infer business risk from a field name. The canonical request or an upstream policy should state which provider-side generation guarantees are required, such as preserve_required_fields; the Adapter only reports whether the corresponding constraint can be represented. An unavailable required guarantee produces unsupported, while loss of a nonessential constraint produces lossy. An Adapter must not weaken a contract merely to make an HTTP request succeed, nor should it decide whether a particular Schema keyword is important to the business.

Tool Call identity must survive conversion

Continue with search_documents. The Runtime needs a stable way to know which Tool Call produced a Tool Result:

canonical call_id: call_17
provider call identity: provider_call_xyz

The Adapter may persist a mapping, but it must restore the canonical call_id before returning data to the Runtime. Matching only on the Tool name becomes ambiguous as soon as two search_documents calls execute in parallel with different arguments.

This mapping cannot be an in-process pair of values. A provider continuation may resume in another process, and the same logical model operation may create another Attempt after fallback. At minimum, the mapping needs:

canonical call_id
route and provider
model attempt_id
provider response / conversation identity
provider-native call identity

It should be persisted with the canonical event or provider continuation state. A Tool round trip that continues the same provider conversation is usually route-sticky and sends back the native call identity. After fallback to another provider, the target Adapter may render a new pair from the canonical Tool Call and Tool Result only when it can completely express every required, portable piece of continuation state. A native ID from the first provider must never be copied into the second.

A canonical call_id solves business association; it does not make the whole continuation portable. Provider-native reasoning items, opaque compaction items, and mandatory message ordering may remain bound to the original route. If the target protocol cannot express them, the Adapter should return incompatible_continuation. The Runtime then starts a new model operation from confirmed facts at a stable boundary instead of pretending to preserve one conversation without loss.

A request-side transformation might be:

canonical tool_result(call_17)
→ provider-specific message role / content block
→ provider_call_xyz

The response side normalizes in the other direction:

provider tool-use item(provider_call_xyz)
→ canonical tool_call(call_17, name, arguments)

This mapping belongs to the execution protocol; it is not merely a diagnostic field. Losing it breaks Tool Calls, retries, and result consumption.

Prompt shaping must not change authority or fact boundaries

Providers may require different placements for system instructions, different message roles, or different Tool description formats. An Adapter may change representation, but it must not reinterpret authority or content roles.

Suppose Context Assembly has already classified a file fragment as untrusted data. The Adapter may render it as a text block, but it cannot promote the file into a system instruction merely because a provider has a convenient message role. The Tool Surface should likewise be determined by policy before it reaches the Adapter. The Adapter transforms only the definitions that have already been allowed.

The division of responsibility can be explicit:

LayerResponsible forNot responsible for
Context AssemblySelecting content, enforcing permissions, resolving conflictsProvider role formats
RouterSelecting a route that satisfies the constraintsMessage and Schema transformation
AdapterExpressing the canonical contract and reporting lossRewriting business policy
RuntimeConsuming canonical items and eventsParsing every provider’s raw response

Streaming can unify event semantics, not chunk shapes

Providers may stream tokens, content blocks, Tool argument deltas, or complete items. Mapping every raw chunk one-to-one into the same shape would make the Runtime depend on one provider’s segmentation.

A safer design standardizes the events the Runtime actually uses:

response.started
text.delta
tool_call.delta
item.assembled
tool_call.validated / tool_call.invalid_arguments
response.completed
response.failed

A delta is useful for live display but may not be independently replayable. item.assembled means only that the provider ended transmission of the item and the Adapter assembled its chunks. It does not guarantee that Tool arguments can be parsed, much less that they satisfy the Schema. Only after the Runtime parses the arguments and applies canonical validation does it emit tool_call.validated or tool_call.invalid_arguments; only the former may enter the handler.

Standardizing events also does not imply identical token boundaries, timing, or finish reasons across providers. The Adapter should preserve the native reason for diagnostics while mapping it into a finite Runtime classification. When no accurate mapping exists, it should emit unknown, not invent a plausible-looking category.

Walk one request through the Adapter

The document search request might pass through the Adapter as follows:

1. The Router selects route_b and fixes Adapter profile revision 9.
2. The Adapter checks Tool Call identity, streaming, and Schema capabilities.
3. It renders the canonical messages and Tool definition as a provider request.
4. When a Tool Call identity first appears in the stream, the Adapter allocates or
   restores a canonical `call_id` and persists the mapping by route, Attempt, and
   provider response.
5. It converts the remaining raw stream into text.delta and tool_call.delta events.
6. When Tool argument transmission ends, it emits
   item.assembled(tool_call call_17).
7. The Runtime parses the arguments and validates them against the canonical Schema;
   only after emitting tool_call.validated does it execute the Tool.
8. On the next Model Turn, the same Adapter renders tool_result(call_17) back into
   the provider protocol.

The Agent Loop never needs to know which role route_b uses, and the Tool Runtime never needs to parse that provider’s content blocks. If step 2 finds that a required Schema constraint cannot be represented, the flow returns unsupported before sending the request and leaves the Router to decide whether another eligible route exists.

Contract tests should verify semantic round trips

Testing only whether a request returns 200 cannot detect a lost Tool Call identity, a dropped Schema constraint, or a false finish-reason mapping. Adapter contract tests should cover at least:

  • Whether a provider-accepted structure can be rendered from the canonical request.
  • Whether Tool Calls, Tool Results, and parallel calls maintain stable associations across restart, continuation, and model Attempt boundaries.
  • Whether a request containing provider-native reasoning or opaque continuation items resumes correctly on the same route and explicitly returns incompatible_continuation when another provider cannot express them.
  • Whether required Schema constraints are preserved, explicitly degraded, or explicitly rejected.
  • Whether streaming chunks converge into complete canonical items.
  • Whether provider errors map into a finite but faithful failure classification.
  • Whether a canonical → provider → canonical round trip preserves the semantics on which the Runtime depends.

These tests should bind the provider API version, Adapter revision, and capability profile revision. When provider behavior changes, the system can update its conversion rules instead of adding another temporary branch to business code.

Back to the problem

A unified generate() method hides only the call site. It does not automatically hide protocol differences.

The Runtime should first define the canonical contract it depends on, then let each Provider Adapter perform capability preflight, message and Schema shaping, Tool Call identity mapping, and response and streaming-event normalization. Any part that cannot be represented without loss should be reported explicitly.

This keeps responsibilities separate: the Router decides which route to use, Context Assembly decides what the model may see, and the Adapter decides how to express it. Only then do provider differences remain behind the boundary.
