How a RunSpec Moves Product Policy Out of the Agent Loop

07/17/2026
AgentRuntimeArchitecture

The problem

Suppose one Agent Runtime supports two entry points:

  • Interactive chat uses a fast, inexpensive model, exposes only search and read Tools, and allows at most 8 Model Turns.
  • Background research may run longer, exposes file writes and SubAgents, and receives a larger budget.

The most direct implementation branches on the entry point inside the Agent Loop:

if request.mode == "chat":
    model = "fast-model"
    tools = read_only_tools
    max_model_turns = 8
elif request.mode == "research":
    model = "reasoning-model"
    tools = read_write_tools + subagent_tools
    max_model_turns = 40

Paid tiers, regional restrictions, experiment cohorts, user authorization, and model fallback soon add more conditions. Each one appears to require only another if, but eventually the Loop decides both “what this execution may do” and “how a Tool Call should execute.”

The most dangerous consequence is not the length of the code. It is that one request can change meaning in the middle of execution: recovery rereads newer configuration, Eval uses a different set of defaults, or one branch fails to apply the same Tool permissions.

Why policy and mechanism should be separate

Here, policy means “what this execution selects,” such as the model, Tool Surface, budget, and authority boundary. Mechanism means “how to execute after those choices are made,” such as calling a model, validating a Tool Call, propagating cancellation, and recording events.

An Agent Loop should be able to execute different policies, but it should not need to know why a particular user received a particular set of Tools. Otherwise every new product rule changes the core execution control flow.

The boundary can be reduced to three objects:

ObjectQuestion it answersLifecycle
ProfileWhat policy does this kind of scenario usually use?May change continuously
RunSpecWhat execution contract did this Run ultimately receive?Fixed when the Run is created
Runtime stateHow far has this Run executed?Changes during execution

A Profile may instead be called a scenario, preset, or agent definition. The name is not important. It remains mutable policy; the Runtime should receive a RunSpec in which defaults, authorization, and experiment conditions have already been resolved.

What a RunSpec fixes

Continue with the background research entry point. Its compiled RunSpec might have this conceptual structure:

{
  "spec_version": 3,
  "profile": {"id": "research", "revision": 12},
  "model_route": {
    "primary": "reasoning-model",
    "fallback_policy": "same-capability-only"
  },
  "tool_surface": {
    "revision": 27,
    "allowed": ["search", "read_file", "write_file", "spawn_agent"]
  },
  "limits": {
    "max_model_turns": 40,
    "deadline_seconds": 1800,
    "max_subagents": 3
  },
  "authority": {
    "subject_ref": "subject_8",
    "grant_ref": "grant_31",
    "grant_revision": 5,
    "max_audience": ["search-service", "workspace-service"],
    "max_scopes": ["web:search", "workspace:read", "workspace:write"]
  }
}

It fixes the selection result; it does not place the entire live execution into configuration.

  • Model responses, the current Model Turn, remaining budget, and Tool Results belong to Runtime state.
  • A newly uploaded file and steering input received during execution are new runtime facts.
  • Secrets such as OAuth tokens and API keys should not be copied into the RunSpec. grant_ref + revision points to an immutable maximum-authority envelope, while the RunSpec also fixes audience, scope, and resource boundaries. Revocation or current conditions may narrow authority during execution, but authority must not expand while the fingerprint remains unchanged.
  • The Context actually sent to the model on each Model Turn still combines current history, Memory, files, and Tool Results. It should not be frozen into one long string when the Run is created.

This distinction keeps the RunSpec serializable and explainable without turning it into “a JSON object containing everything.”

Walk the opening example through the design

When the background research request arrives, the Loop no longer branches on mode:

1. The compiler reads research Profile revision 12.
2. It narrows the Tool Surface to four Tools under the current authorization.
3. It resolves the model and budget and produces RunSpec version 3.
4. It persists the immutable RunSpec and fingerprint, then appends a
   `run.created(run_id, runspec_ref, fingerprint)` fact that references them.
5. The Runtime starts the Loop from the RunSpec and records the model and Tool events
   that actually occur.

If the user lacks file-write permission, step 2 excludes write_file. The Runtime does not need to reinterpret “may a research user write files?” on every Tool Call. A trusted Tool handler still performs backend authorization and may reject an action after authorization is revoked, but it cannot give this RunSpec capabilities beyond its compiled ceiling.

When the RunSpec and Event Log share a database, persisting the RunSpec and appending run.created can share a transaction. Across stores, the system should persist the immutable RunSpec first and then append its reference; retention or reconciliation cleans up an orphaned RunSpec if the append ultimately fails. The RunSpec is a contract referenced by execution facts, not a projection of the Run snapshot.

If the Profile advances to revision 13 halfway through execution, the current Run continues to use revision 12. The new policy affects only Runs created afterward. Recovery therefore cannot unexpectedly switch models or add a Tool merely because it rereads the Profile.

Why versions and fingerprints matter

Storing only profile_id=research is not enough because that Profile changes. A RunSpec should retain at least its own schema version, the revisions of its dependencies, and a fingerprint calculated from its canonical content.

They answer different questions:

  • spec_version tells recovery code how to read the structure.
  • Revisions for the Profile, Tool Surface, prompt, and other dependencies identify the inputs that were used.
  • The fingerprint tells whether two executions actually used the same contract rather than merely sharing a name.

A fingerprint is a short identifier for the RunSpec’s content. SHA-256 accepts bytes; it does not understand how JSON object keys, whitespace, or numbers should be represented. The system must therefore define canonicalization: how the same logical content always becomes the same byte sequence.

For example, the system can first exclude runtime fields such as created_at according to its domain rules, sort Tool collections that have no ordering semantics, and then use the RFC 8785 JSON Canonicalization Scheme to produce UTF-8 bytes. The following are complete test vectors. In each case, the hash input is the UTF-8 bytes of the single JSON line in the code block, without a trailing newline:

{"canonicalization":"jcs-v1","model":"reasoning-model","profile":{"id":"research","revision":12},"tool_surface":{"allowed":["read_file","search"],"revision":27}}
sha256 = 374c31f96298b5fe5522161fb193f902efb1cee09fcf76dd2a45c11ac97de0b1
{"canonicalization":"jcs-v1","model":"reasoning-model","profile":{"id":"research","revision":12},"tool_surface":{"allowed":["read_file","search","write_file"],"revision":28}}
sha256 = eb98321387bd356c133bbb08dfe58262608b8e304a2a5604a7e22f795a23fb44

Both Runs are named research, but the second includes write_file, so their fingerprints differ. A Trace or Eval can then tell that the Runs should not be compared merely by Profile name. Conversely, identical canonical content produces an identical fingerprint, so consumers do not need to compare the full RunSpec field by field.

The canonicalization identifier is itself part of the contract. An implementation must fix which fields are included, how domain-level sets are sorted, and which JCS version is used, and preserve the corresponding test vectors. “Sort the JSON first” is not sufficient to make different languages produce the same bytes.

A fingerprint is not a security signature. Anyone who can modify the RunSpec can calculate a matching new hash. It is useful for detecting configuration drift and comparing content quickly, but it cannot by itself prove who generated the RunSpec.

Even an identical fingerprint cannot prove that an external provider will behave identically. It answers only: “Did these executions use the same local contract?”

The Runtime still makes execution-time decisions

Compiling policy into a RunSpec does not remove every branch from the Runtime. Decisions based on execution facts still belong to mechanism:

  • Does the Tool Call satisfy its schema?
  • Has the deadline passed?
  • Has cancellation been requested?
  • Does this failure satisfy the retry conditions permitted by the RunSpec?
  • Has the current authorization reference been revoked, and does the backend still permit the side effect?

The difference is that the Runtime evaluates an explicit contract against current facts. It no longer derives product identity, plan tier, or entry-point type. The policy compiler chooses the retry budget; the Runtime consumes it correctly.

Back to the problem

An Agent Loop should not grow with every entry point, user tier, and experiment policy. A more stable division is: the Profile expresses mutable policy, the compiler fixes the selection result in a RunSpec before execution, and the Runtime interprets that contract while recording execution facts.

Adding a scenario then usually means adding or changing a Profile and compiler rule, not adding another product branch to the model-and-Tool loop. More importantly, one Run can refer to the same execution contract from creation through recovery and Eval.

Follow-up questions

  • After a RunSpec is created, what should be the source of truth for messages, state, and events produced by the Runtime?
  • How should each Model Turn assemble current Context from history, Memory, files, and Tool Results?
  • Should Profile, compiler, and Runtime live in different services, and which failure and ownership boundaries should decide that split?
  • When a RunSpec crosses a trust boundary, how should an HMAC or digital signature prove its provenance and integrity?
