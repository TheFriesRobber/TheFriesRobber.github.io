LLM Infra 16: How Tenant Identity Traverses the Inference Resource Chain

Carry trusted Tenant identity through the Queue, Model and Adapter, Prefix Cache, execution, logs, and usage evidence while separating logical isolation from hardware isolation.

07/29/2026 Views
LLM InfraInferenceMulti-TenancySecurityCost

The problem

Tenant A’s long requests occupy many KV blocks while Tenant B’s latency-sensitive requests remain queued. Both use the same text prefix, and the Cache layer reuses state based only on a Token hash. Usage is eventually attributed only by gateway request count.

Fairness, Cache isolation, and resource attribution look like three separate problems. What is actually missing is one trusted Tenant identity. After entry authentication, it stopped propagating through the Queue, Adapter, Cache, execution, and usage paths.

Tenant identity cannot come from a client assertion

The platform derives an isolation context from an authenticated subject and server-side policy:

isolation_context:
  subject_id: subject_123
  tenant_id: tenant_a
  trust_domain: tenant_a-prod
  cache_salt_id: salt_91
  quota_class: interactive-standard
  adapter_scope: tenant_a
  log_scope: tenant_a
  issued_by: trusted-gateway
  immutable: true

A request header may carry a reference to this context, but the Client cannot override tenant_id, the salt, or the quota class. Every retry attempt must carry a trusted, unexpired, tamper-resistant principal context and pass admission again. When an attempt crosses an authentication boundary, or its authorization grant has expired or been revoked, authentication or authorization must run again. The platform cannot trust client-supplied fields or reuse an obsolete quota deduction.

Tenant identity and user subject are not interchangeable. The subject identifies the caller; the tenant identifies resource and isolation ownership. One tenant may have many subjects.

Identity must enter every shared boundary

trusted gateway
→ admission / queue
→ model and adapter resolution
→ Prefix Cache namespace
→ Replica execution
→ logs / traces / artifacts
→ usage facts

Each boundary consumes identity for a different decision:

BoundaryHow identity participates
QueueQuota, priority, and weighted fairness
Model/AdapterVisibility and permitted revision
Prefix CacheTrust domain and cache salt
ExecutionAttribution, cancellation, and isolation placement
Logs/TraceQuery and content-access scope
UsageOwnership of attempts and resource facts

Article 07 explains how cache_salt can separate Prefix Cache sharing domains. It reduces cross-domain Cache reuse and timing exposure, but it is not complete authorization and cannot replace process, network, log, or hardware isolation.

Fairness and Quota need the same Work unit

Rate limiting by request count assigns the same cost to a very long Context and a short request. A more useful admission model can consider:

  • requested prompt and maximum output Tokens;
  • active sequences and KV reservation;
  • deadline and priority;
  • tenant burst allowance;
  • admitted but unfinished work.

These remain estimates; actual usage becomes available only after Runtime execution. Keep fairness policy separate from usage facts:

  • Policy decides how much work may enter now.
  • Runtime facts record the Tokens actually produced, execution time, and outcome.

If the two use different tenant identities, the entry point charges A, the Runtime records B, and billing later averages away the broken link.

Isolation strength is a spectrum

Kubernetes multi-tenancy documentation describes namespaces, RBAC, NetworkPolicy, and quotas as logical and control-plane isolation mechanisms. They do not automatically provide physical GPU isolation.

NVIDIA MIG partitions part of GPU compute, cache, and memory paths into separate instances, providing stronger resource and fault isolation. MPS or time-slicing continues to share more underlying resources. Even with MIG, the platform cannot claim that every side channel, Runtime bug, or application-layer data leak is gone.

Placement policy must therefore select a boundary based on the data and risk:

Isolation requirementCandidate approachWhat remains shared or unresolved
Efficient sharing inside one trust domainSame process and same-GPU Cache sharingQuota, logs, and Cache salt
Separate application and Runtime stateIndependent process or logically dedicated ReplicaIf the GPU remains shared, no SM, L2, or memory-bandwidth QoS guarantee
Partition resources and QoS within one GPUMIG on supported hardware and profilesHost, network, control plane, and application defects
Strong hardware or organizational isolationDedicated GPU, node, or clusterIdentity propagation, logs, and supply chain still remain

“Shared GPU” is not one security level, and a namespace is not proof of hardware isolation.

A Usage fact is not a Billing decision

usage_evidence:
  usage_id: usage_771
  logical_request_id: req_123
  attempt_id: att_2
  tenant_id: tenant_a
  release_digest: release_91a
  execution_fact:
    producer: runtime-signed-event
    input_tokens: 2400
    output_tokens_generated: 91
    cache_read_tokens: 512
    execution_started_at: ...
    execution_ended_at: ...
    replica_uid: replica_a
    outcome: cancelled_after_start
  delivery_fact:
    producer: gateway-signed-event
    chunks_emitted: 6
    emitted_token_cursor: 47
    client_ack_protocol: none
    acknowledged_cursor: null

The bundle separates Runtime execution from Gateway delivery evidence by producer. Without explicit application acknowledgement, it does not claim that the Client received or consumed Tokens. It also does not set a price. How GPU time is divided inside a Batch, whether Cache hits are charged, and whether failed work is refunded belong to Billing policy. Policy may evolve, but it cannot rewrite the original usage evidence.

A Gateway Token count is not GPU consumption either. Prefix Cache, quantization, Batching, preemption, and parallel topology all change resource cost. An attribution model may consume these facts, but it must disclose its assumptions.

Use negative tests to prove identity did not disappear

At minimum, verify:

  1. A forged tenant_id header cannot override trusted context.
  2. The same prefix with different Cache salts does not cross-hit.
  3. Tenant A’s Adapter cannot be routed for B.
  4. Queue policy applies quota to long Token work instead of counting only requests.
  5. Log and Trace queries enforce tenant scope.
  6. Retry creates a new attempt, runs admission again, and records usage.
  7. Billing adjustments do not modify any original usage evidence; they append a separate ledger or event.

These tests are stronger than “every component has a tenant field” because they exercise enforcement across the actual boundaries.

Back to the problem

Tenant A crowding out B, cross-tenant Prefix Cache hits, and incorrect usage attribution do not require one component that owns security, scheduling, and pricing. They require the same unforgeable Tenant identity to reach every owner.

The Queue uses it for fairness, the Cache for trust-domain separation, Adapters and logs for visibility, and the Runtime for usage facts. Placement expresses isolation strength through a shared process, MIG, dedicated device, or cluster; a namespace name cannot imply that boundary.

The series now closes the loop: it begins with workload and SLO, passes through Runtime and Cluster execution constraints, and ends with production delivery explained by observability, recovery, release, and isolation contracts.
