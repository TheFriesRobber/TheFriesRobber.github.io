Which Runtime Threats a Sandbox Must Constrain

Define the Sandbox Runtime threat boundary across command, filesystem, network egress, secret, and resource controls.

07/24/2026 Views
Agent ProductionAgentSandboxSecurity

The problem

A user authorizes an Agent to run a build in a trusted repository. The repository script contains no prompt injection, and the Agent selects the correct command. But the script reads a cloud credential from an environment variable, sends diagnostic data to an external address, and recursively forks child processes because of a bug.

The user did authorize the business action: run the build. The risk comes from an overpowered Runtime. The process can see an unnecessary secret, has unrestricted egress, and has no process or CPU limit.

“It runs in a container” is therefore not a complete Sandbox security conclusion. A Sandbox must bind workload identity to a least-privilege policy and separately constrain command, filesystem, network/DNS, secret, and resource capabilities. Readiness is meaningful for execution only after those constraints have been observed or proven to be active.

Define what must be protected first

The opening execution crosses at least three protection domains:

Protection domainPrimary assetsPaths to block
Host / control planeKernel, metadata service, provider credentialPrivilege escalation, host mounts, control-plane access
Current tenantWorkspace, Artifact, short-lived credentialOut-of-scope reads and writes, secret disclosure
Other tenants / external systemsOther workloads, internal services, Internet destinationsLateral access, resource exhaustion, arbitrary egress

The attacker is not necessarily a malicious user. Model-generated code, a dependency in a trusted repository, a build script, or a compiler can all be defective or compromised. Sandbox policy should assume that executed content does not deserve host privileges.

Five capability classes need different enforcement

Command and process privileges

A string-based command denylist is easy to bypass through a shell, interpreter, or child process. More trustworthy controls live at the Runtime layer:

  • run as a non-root identity;
  • drop unnecessary Linux capabilities;
  • prevent privilege escalation;
  • apply a seccomp, AppArmor, or SELinux profile;
  • prohibit host PID/network namespaces and high-risk devices.

Kubernetes securityContext provides configuration points for these mechanisms, but whether they take effect depends on the Runtime, node, and cluster policy. Using a container does not mean these restrictions are enabled.

Filesystem

Mount the Workspace according to purpose:

/inputs       read-only
/workspace    writable, current tenant only
/outputs      writable, publish through Artifact service
/runtime      ephemeral
host paths    not mounted

A read-only root filesystem reduces persistent modification, but it does not prevent reading an exposed secret or protect a host path that was mounted by mistake. File access still needs minimal mounts, UID/GID or label isolation, and Workspace lease/fencing.

Network and DNS

When a Sandbox allows unrestricted egress by default, filesystem isolation prevents host writes but not data exfiltration. Network policy should identify allowed destinations, ports, and protocols and handle DNS and cloud metadata endpoints explicitly.

There are two different layers:

  • Runtime egress policy enforces where the process can actually connect.
  • A Tool/backend allowlist enforces who may receive a particular business effect.

An allowlist on one HTTP Tool cannot block curl. A network allowlist alone cannot determine whether the target account or resource belongs to the current user.

Kubernetes NetworkPolicy is an interface for packet filtering, and actual support and behavior depend on the network implementation. DNS policy also needs explicit design; permitting cluster DNS does not make every resolved destination safe.

Secret

The safest secret never enters the Sandbox. When one is truly needed, prefer:

  • a short-lived credential constrained by audience and scope;
  • on-demand exchange through workload identity;
  • visibility only to the process or proxy boundary that performs the operation;
  • exclusion from prompts, command lines, Workspaces, images, and logs.

Mounting a secret as an environment variable is convenient but exposes it more easily to child processes, error reports, or /proc. A stronger design delegates constrained requests to a separate broker or sidecar, at the cost of additional system complexity.

Resource

CPU, memory, disk, process count, open files, network bandwidth, wall-clock time, and concurrency can all become denial-of-service paths. Limits need reservation before admission and enforcement inside the Runtime.

A timeout usually triggers cancellation or stops computation. It does not prove that an external side effect did not happen. After forcibly reclaiming a Sandbox, the Control Plane must still hand any unknown effect to the owning backend for query or reconciliation.

Policy must be part of acquire evidence

The Control Plane can compile target policy into provider-specific configuration, but a client should not see only healthy: true. An executable handle should be associated with at least:

{
  "workload_identity": "sandbox_91",
  "policy_revision": 12,
  "observed_enforcement": {
    "filesystem": "verified",
    "network": "verified",
    "secret": "none",
    "resources": "verified"
  }
}

This is still a design example. Platforms provide different observed evidence. Some can prove only that configuration was accepted, not that every rule is effective at Runtime. The system should distinguish requested, configured, and verified honestly rather than hide evidence strength behind one ready flag.

Whether an old Runtime can continue after a policy update depends on the risk of the change. Tightening egress or revoking a secret usually cannot wait for natural rebuild. The Control Plane needs to stop admission, rotate credentials, and rebuild or quarantine Runtimes that no longer conform.

Back to the problem

The opening build should not receive the cloud credential. If it truly needs to fetch a dependency, it should receive a short-lived credential valid only for the target registry. Host paths outside the Workspace are not mounted, the root filesystem is read-only, egress is limited to the necessary registry, and process, CPU, memory, disk, and wall-clock limits are enforced.

The process/resource limit terminates the fork bomb, the network layer rejects connections to unknown destinations, and no secret is available to read. The Control Plane then reclaims the workload and separately reconciles any external effect whose outcome remains uncertain.

These controls do not replace backend authorization, and they do not cover the image or toolchain supply chain. They establish only the Runtime threat boundary: even when the trust judgment about executed content is wrong, the process does not naturally inherit every capability of the host and shared environment.
