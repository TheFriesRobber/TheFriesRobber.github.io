Agent Discovery

Define the Business Outcome Before Deciding Whether You Need an Agent

Move from “we want an Agent” back to task outcomes, current loss, responsibility boundaries, and completion evidence so a preferred solution becomes a verifiable business problem.

07/29/2026 Updated 07/30/2026 Views
Agent DiscoveryAgentProduct Discovery

The problem

A customer-support team asks for a refund Agent. The first feature list comes together quickly: read customer messages, query orders, evaluate refund eligibility, generate a reply, and ideally create the refund as well.

The request sounds concrete, but it does not answer a more basic question: which outcome is the team trying to improve?

If the real bottleneck is delayed payment-status synchronization, generating a reply will not shorten resolution time. If most time is spent waiting for supervisor approval, producing a recommendation faster will not reduce that wait. If refund errors come from inconsistent policy versions, a stronger model will only apply the wrong rule faster.

“We want an Agent” has already chosen a solution without defining the problem. Requirements discovery should first remove the Agent from the sentence and restate the task outcome, current loss, and responsibility boundary.

A feature request hides three different problems

What users call a requirement usually mixes three layers:

solution preference: we want a refund Agent
capability request: it should query orders, apply policy, and reply
business problem: refunds are slow, and equivalent cases receive inconsistent outcomes

The first two layers help explain the product users imagine. Only the third supports an investment decision. It describes what is wrong today without assuming that an Agent must fix it.

The same capability request may also serve different business problems. “Query orders automatically” may reduce manual work, or it may prevent agents from missing cancelled orders. “Reply automatically” may shorten first-response time, or merely standardize phrasing. Those goals require different completion conditions and Evals.

Discovery therefore cannot stop at “what should the system do?” It must also ask:

  • Who consumes the result of this task?
  • Why is the current result inadequate?
  • Does the loss appear in time, cost, quality, risk, or capability coverage?
  • Which change would actually matter to the business?
  • Who can confirm that the change occurred?

These questions do not reject the proposed Agent. They look for a reason that can be falsified.

A business outcome must reach external state

In the refund scenario, the team may successively name three goals:

  1. generate customer-service replies faster;
  2. complete refund handling faster;
  3. reduce the time from refund request to money received.

The goals sound similar, but their boundaries differ.

Generating a reply requires only text. Completing refund handling requires the payment system to accept the action and return a refund identifier. Reducing time to receipt also depends on later payment-channel state. The outcome owned by the Agent determines which data and Tools it needs and when it may declare completion.

A minimal outcome chain can test the requirement:

model output
→ user or system takes an action
→ external state changes
→ the result is observed and confirmed again

The task responsibility should end where this chain ends. If the Agent only recommends, it cannot be evaluated on refund completion. If it is expected to complete the refund, “generated the correct wording” cannot count as success.

This is also why a business outcome needs evidence. A support agent saying “handled,” a Tool returning HTTP 200, and a refund record appearing in the payment system represent different strengths of fact. Requirements discovery does not need to design the full Runtime protocol, but it must identify which external state will prove completion.

Current loss determines whether the opportunity is real

After defining the outcome, the team still needs to establish whether the current state is worth changing. A task can feel tedious without producing net value when automated.

Recent real cases can answer:

  • How long did the task take from trigger to completion?
  • How much time was active work, and how much was waiting?
  • Which steps caused the most rework?
  • How long did errors remain undiscovered?
  • Which roles repaired them?
  • Where would the loss continue if nothing changed?

Discovery does not need a polished ROI estimate yet. It first needs the mechanism that creates loss.

Suppose drafting a refund takes two minutes while supervisor approval takes two hours. Reducing the draft to ten seconds will not materially change the end-to-end cycle. Conversely, if support agents spend substantial time gathering information across systems and the Agent can perform that work reliably, it may create real value even if final approval remains with a human.

The conclusion should come from real cases, tickets, or operation records rather than impressionistic numbers from interviews. Without measurement, record a hypothesis to validate; do not turn “users say it happens often” into a benefit claim.

Responsibility boundaries must be defined with the outcome

A business outcome also hides another question: who owns the task, and who bears the error?

A refund may involve the customer, support agent, supervisor, finance team, and payment system. The person asking for the feature, the person using it, the person approving risky actions, and the person absorbing loss are often different.

A business-problem statement should therefore separate at least:

RoleResponsibility in the requirement
Task initiatorProvides the request and required material
Frontline operatorHandles routine cases and maintains customer communication
Decision ownerDecides exceptions not directly covered by policy
Risk ownerApproves high-value or irreversible actions
Result verifierDetermines completion from external evidence

Without these distinctions, “help support” can expand into “replace supervisor authorization,” or “create a refund draft” can be rewritten as “complete the refund.”

The autonomy level can be decided later, but the responsibility owner must be identifiable during discovery. Otherwise the team cannot define authorization or explain who should receive a failure.

A business-problem statement is enough to screen the direction

After these clarifications, the refund requirement can be rewritten:

Frontline support agents handling refunds covered by standard policy must collect evidence across order, payment, and logistics systems. Routine cases take too long, and missed states create rework. The goal is to reduce evidence-collection and draft-preparation time without expanding refund authority. Amounts above the threshold, state conflicts, and cases outside policy remain with their corresponding owners. End-to-end handling time, human correction rate, incorrect refunds, and escalation quality verify the result.

This statement does not promise that the solution will be an Agent, but it already identifies four objects for further discovery:

  • evidence collection in real work;
  • the boundary between routine and exceptional cases;
  • actions that may be delegated;
  • metrics that verify business change.

If later discovery shows that every rule is fixed, the answer may be a Workflow. If the main value is decision support, it may be a Copilot. An Agent becomes a plausible candidate only when the task requires dynamic evidence collection, path selection, and progression of external state.

Back to the problem

The support team initially requested a refund Agent that could query orders, apply policy, and generate replies. That was a feature list, not a verifiable requirement.

After temporarily removing the Agent, the real problem becomes visible: evidence collection and draft preparation consume time in routine refunds, missed state causes rework, and high-risk exceptions still require explicit owners.

The team has not yet selected a product form, but it knows which outcome should improve, which responsibility boundaries must remain, and which external evidence will prove change. Those facts matter more than choosing a model or Tool first.

Requirements discovery does not prove that the requested Agent is worth building. It first proves that there is a business outcome worth changing.
