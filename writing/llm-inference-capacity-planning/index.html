LLM Infra 04: How to Derive Inference Capacity from Token Workload

Combine a workload envelope, per-Replica service curve, failure reserve, and provisioning lead time into a capacity range instead of guessing the Replica count from average GPU utilization.

07/29/2026 Views
LLM InfraInferenceCapacity PlanningReliability

The problem

An inference cluster has modest day-to-day GPU utilization, yet a burst of long Prompts quickly builds a backlog. Adding one Replica provides temporary relief. The next model upgrade keeps the same Replica count, and capacity falls short again.

This problem is often described as “not enough GPUs,” reducing capacity planning to adding cards based on average utilization. Utilization does not describe queued Token work or bind the model, Runtime, and SLO, so it cannot answer how much deliverable capacity is required.

Capacity planning must connect two bodies of evidence established earlier: the production workload envelope and the service curve produced by the Benchmark.

The numerator is the workload to be delivered

The workload envelope provides arrival patterns, input/output Token distributions, deadlines, and workload classes. A capacity calculation must not compress them back into one average QPS.

First divide the workload by execution compatibility and service contract:

SegmentModel requirementInput/output characteristicsSLO
interactive-shortchat-v3Short input, short outputStrict TTFT/TPOT
interactive-longchat-v3-longLong Context, medium outputRelaxed TTFT
async-generationgenerate-v2Medium input, long outputCompletion deadline

This does not require a dedicated cluster for every class. It prevents non-interchangeable work from being added together. A Replica that supports only short Contexts cannot count toward capacity for the long segment. A configuration that meets a Batch deadline does not necessarily meet interactive TTFT.

The forecast also needs to express a range rather than one exact point:

low / base / high arrival
× input-output distribution
× burst window
× deadline and priority

Forecast uncertainty should remain visible in the model. Pretending that “next quarter will be exactly 8.5 req/s” only hides error inside an arbitrary headroom percentage.

The denominator is a Service Curve that meets the SLO

Single-Replica capacity is neither theoretical FLOPs nor peak tokens/s from a product page. It comes from a measured service curve under a fixed deployment manifest.

Suppose a finer sweep between 1.0–1.5 req/s in Batch 1’s synthetic Benchmark produces:

workload fingerprint: wl_7fd2
deployment manifest: dep_a91c
maximum offered load meeting contract: 1.1 req/s per Replica

Here, 1.1 req/s is the maximum offered load that one Replica can sustain under a feasibility constraint of good-request fraction ≥ 95%. It is an input to the calculation, not a measurement from real hardware. It comes from an experiment that includes input/output distributions, Batching, TTFT/TPOT, and all failure outcomes, but it is not application goodput: if exactly 95% of requests qualify, the corresponding application goodput is approximately 1.045 req/s.

If Replicas are homogeneous, the Router balances this workload evenly, no shared gateway or network bottleneck exists, and Cache or Adapter affinity does not pin traffic to a few Replicas, the simplest initial steady-state estimate is:

N_steady = ceil(forecast_offered_rps / max_supported_offered_rps_per_replica_at_target_fraction)

For a base forecast of 8.5 req/s:

ceil(8.5 / 1.1) = 8 Replicas

Both numerator and denominator are offered load under the same good-request-fraction gate. The result is only a candidate fleet size, not proof of fleet capacity. The real deployment still requires a multi-Replica service curve to verify that routing, affinity, and shared components preserve the composition assumption. The result remains valid only while the workload fingerprint and deployment manifest remain unchanged. A change in model revision, quantization, parallelism, scheduler policy, driver, or hardware may invalidate the original service curve.

Headroom is not a fixed percentage

Mechanically adding 30% to the estimate appears safe but combines several distinct risks:

  • workload forecast error;
  • short bursts;
  • variation in single-Replica performance;
  • loss of one Replica or one failure domain;
  • provisioning lead time before new capacity becomes ready.

These risks operate on different timescales and have different recovery mechanisms, so they should be handled separately.

Steady-state headroom

Do not operate Replicas permanently at the boundary where the service curve first loses its SLO. Choose a stable region of the curve that can absorb observed noise and workload drift.

Burst buffer

If a burst is shorter than the startup time for a new Replica, Autoscaling cannot respond in time. The system must rely on existing idle capacity, a bounded queue permitted by deadlines, or explicit admission.

Failure capacity

If the base workload must still be served after losing one Replica, the earlier synthetic result requires at least:

N_failure = N_steady + 1 = 9 Replicas

This N+1 applies only under the synthetic assumption that one homogeneous Replica is the failure unit. If one Replica spans several GPUs, or several Replicas share a node, switch, or power domain, the failure unit cannot be reduced to one process. The actual requirement should state that after losing the target failure domain, the remaining fleet’s measured goodput still covers the target workload.

Provisioning reserve

Node creation, image pulls, model loading, parallel-group formation, and warmup all take time. Sending a scale-out request does not make capacity ready. Only a Replica that passes readiness and service-curve validation can count as deliverable capacity.

The final result is therefore better expressed as a conditional capacity range:

ScenarioSynthetic resultAssumptions
Low steady state6 ReplicasLow forecast, all healthy
Base + one Replica failure9 ReplicasBase forecast, N+1
High + one Replica failure12 ReplicasHigh envelope requires 11 at steady state, plus one homogeneous failure reserve

These numbers remain calculation examples. They demonstrate the structure rather than recommend a configuration.

GPU utilization explains only part of device activity

High GPU utilization may indicate busy compute, or it may show a large Batch delivering an offline workload successfully. Low utilization may also mean:

  • requests are still in a gateway or scheduler queue;
  • the Replica cannot admit work because of KV or memory limits;
  • multi-GPU execution is waiting on communication or synchronization;
  • the target model or Adapter has not been loaded;
  • arrivals are simply low.

Utilization is therefore diagnostic evidence, not a capacity formula. The actual comparison is:

compatible workload to be delivered in a future window
vs.
service capacity of current ready Replicas under the same contract

Utilization, queue age, pending Tokens, KV pressure, and active sequences can explain the gap, but they cannot replace the workload and service curve.

A capacity result must carry invalidation conditions

An executable capacity record might look like:

capacity_plan:
  workload_fingerprint: wl_7fd2
  forecast_window: 2026-Q3
  scenarios:
    low_rps: 6.0
    base_rps: 8.5
    high_rps: 12.1
  service_curve:
    deployment_manifest: dep_a91c
    max_supported_offered_rps_per_replica: 1.1
    good_request_fraction_gte: 0.95
  failure_requirement:
    unavailable_replicas: 1
  provisioning:
    ready_lead_time_p95: measured-separately
  invalidate_on:
    - workload_distribution_changed
    - model_or_tokenizer_revision_changed
    - runtime_or_scheduler_changed
    - hardware_or_parallelism_changed

Lead time must be measured from the real deployment process rather than filled in from experience. The plan should also be compared periodically with production observations: does the actual workload remain inside the envelope, and do ready Replicas still deliver the original service curve?

Back to the problem

The original cluster’s low GPU utilization does not prove that capacity is sufficient. A burst of long Prompts may form a queue before the GPU receives the requests. A model upgrade invalidates the old service curve, so the same Replica count no longer represents the same goodput.

A valid capacity conclusion must take this form:

specified workload envelope
× specified SLO and quality constraints
÷ service curve for a specified deployment manifest
+ independent burst / failure / provisioning constraints

Batch 1 now forms a closed loop: Article 01 defines the work, Article 02 defines effective delivery, Article 03 measures the service curve, and Article 04 converts them into a capacity range.
