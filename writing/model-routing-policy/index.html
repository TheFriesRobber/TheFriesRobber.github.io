Context Engineering 4: How Model Routing Falls Back Safely

07/17/2026 Views
AgentModel RoutingReliability

The problem

Suppose an Agent needs to read a screenshot, organize the problems it contains, and then call create_ticket. Here, create_ticket is a client Tool executed by the local Runtime: the provider request only generates a Tool proposal and cannot itself execute a provider-side Tool or create a ticket. This execution requires a model with all of the following:

  • Image input support.
  • Structured output support for the current Tool Schema.
  • A Context window large enough for the screenshot description, recent conversation, and Tool definitions.
  • Compliance with the current data-region policy and cost budget.

The Runtime calls the primary model, but the request times out. The most direct fallback is to replace the model name with a backup and resend the request unchanged.

That path may fail again. The backup model may not accept images, may support a different Schema subset, may have a smaller Context window, or may violate the Task’s data policy. Even if the request succeeds, the Runtime may not know whether the primary model produced a complete Tool Call before the timeout or whether any partial output it received can be reused.

Model Routing is therefore more than switching from one string to another. It must answer two questions: which model satisfies this execution contract, and whether the current failure permits execution to continue on another model.

Filter ineligible models before comparing cost and latency

If the Router ranks every model by price or average latency first, it may select an inexpensive candidate that cannot complete the Task. A safer order begins by extracting hard constraints from the RunSpec or current Task:

required modalities
required tool / structured-output features
estimated input and reserved output budget
required context capacity and maximum output
data policy and region
allowed provider set
provider-side effect policy

The model catalog maintains a capability profile for each candidate. The profile describes known capabilities, limits, and current health, but it is not a permanently correct static table. Model versions, provider behavior, and organizational configuration all change, so the profile also needs a revision.

The Router first excludes candidates that violate hard constraints, then ranks the remaining set by latency target, cost budget, quality tier, and current availability:

all candidates
→ capability and policy eligibility
→ latency / cost / quality ranking
→ selected route with fallback set

This keeps “ineligible” separate from “lower priority.” A model without image input is not merely a lower-scoring candidate; it is ineligible for this request.

A Routing Decision should explain the selection

Return to the screenshot Task. The Router might produce this conceptual decision record:

{
  "operation_id": "model_op_17",
  "requirements": {
    "modalities": ["text", "image"],
    "tool_contract": "ticket_tools@revision_8",
    "estimated_input_tokens": 18000,
    "reserved_output_tokens": 4000,
    "required_context_capacity_tokens": 22000,
    "minimum_max_output_tokens": 4000,
    "provider_side_effects": "none",
    "data_policy": "region_a"
  },
  "selected": "model_route_primary",
  "eligible_fallbacks": ["model_route_secondary"],
  "excluded": [
    {"route": "model_route_fast", "reason": "image_input_unsupported"},
    {"route": "model_route_large", "reason": "cost_budget_exceeded"}
  ],
  "policy_revision": 6
}

estimated_input_tokens estimates the current Assembly result; it is not a model capacity. The Router adds it to reserved_output_tokens to derive the required Context capacity, then separately checks that the candidate’s maximum output is at least minimum_max_output_tokens. Collapsing these values into one min_input_tokens field would mix “how large is this request?” with “how much can this model hold?” again.

The record identifies a route, not necessarily a bare model name. A route can also fix the provider, model version, Adapter profile, region, and parameter ceilings. A Trace can then distinguish “the Router selected incorrectly” from “the selected model call failed,” while an Eval can compare results under the same routing policy.

Fallback depends on where the failure occurred

Not every model failure should trigger a model switch:

Observed failureWhat the Router can doWhat it cannot infer
Capability mismatch detected before the requestSelect another eligible candidateThe original candidate was merely “lower quality”
Provider explicitly returns rate limit or unavailableSwitch to an eligible route within budgetThe first call produced a usable result
Timeout without a complete responseCreate a new Attempt when there are no provider-side effects; otherwise query or reconcile firstThe provider definitely did not finish generation or an external action
Partial text or a partial Tool Call receivedDiscard the incomplete item and retry from a stable boundaryPartial JSON can be continued safely
Complete output fails a quality checkRepair, add Context, or replanTrying more models will necessarily help
Data policy or authorization disallows the requestStop or narrow the TaskA cheaper model may bypass policy

A timeout is only a Runtime observation: no confirmable result arrived before the deadline. It does not prove that the provider never completed its work. For the route in this article, which only generates client Tool proposals, the model request itself has no external side effects. The Runtime must still determine which items were completely recorded in the Event Log before it decides where fallback can resume.

Only when the route capability explicitly guarantees provider_side_effects=none is the safe default to create a new Attempt under the same logical model operation on a new route. That Attempt reuses only confirmed input facts and never concatenates incomplete output from two Attempts. If a route permits provider-executed server Tools or remote MCP Tools, a request timeout may leave an external action in an unknown state. The Runtime must query or reconcile through a provider response identity or Tool Execution identity, or rely on an explicit idempotent recovery contract. This classification follows the execution owner and side-effect contract, not whether a Tool uses the MCP protocol. When the Runtime cannot determine the outcome, the state remains unknown; it must not fall back and execute the action again. The Runtime’s layered recovery policy still owns the overall retry budget and failure recovery across Tool Executions.

Switching models also requires revalidating the input

Two models both marked as supporting images and Tools do not necessarily accept the same final request unchanged. Before fallback, the Runtime must revalidate at least the following:

  • Whether the new route’s Context limit can hold the current Assembly result.
  • Whether the Tool Surface retains every required constraint after conversion by the corresponding Adapter.
  • Whether system instructions, message roles, and structured output can be represented without semantic loss.
  • Whether completed Tool Results preserve call identity and content boundaries in the new protocol.
  • Whether output budgets, sampling parameters, and stop conditions remain valid.

If the Context is too large, the system can return to structured degradation. If a required Tool Schema cannot be represented, it should return incompatible_route instead of silently removing constraints and continuing.

This is why the Router and Provider Adapter need separate responsibilities. The Router decides which candidate to use; the Adapter answers how to express the canonical request in that provider’s protocol. When an Adapter reports incompatibility, the Router may choose another candidate. The Adapter should not switch models on its own merely because conversion failed.

Walk the opening example through fallback

The complete selection and fallback path for the screenshot Task might be:

1. Read image, Tool contract, Context, data-policy, and provider-side effect
   requirements from the RunSpec.
2. Exclude routes that do not support images, violate regional policy, or execute
   Tools inside the provider.
3. Select a primary route with `provider_side_effects=none` from the eligible set
   and persist the Routing Decision.
4. The primary Attempt times out and no complete response item was accepted; this
   route cannot execute external actions itself.
5. Classify the failure as transport_timeout and consume one unit of fallback budget.
6. Select a secondary route that still satisfies every hard constraint.
7. Render the same canonical request through the secondary Adapter.
8. The new Attempt returns a complete Tool Call; only then does the Runtime enter
   the Tool Lifecycle.

If step 4 had already received a complete, validated create_ticket Tool Call, an interrupted final text stream alone would not justify asking another model to generate a second ticket proposal. The Runtime should decide whether to execute the original Tool Call from the persisted item and current Task state; the Router should not guess. If the route instead permits provider-side Tools, this example path no longer applies: the Runtime must first query or reconcile prior execution after the timeout.

How to verify that the Router is not hiding failures

A Model Routing Eval should measure more than whether the system eventually answered. At minimum, it should observe each failure class separately:

  • Whether hard-constraint filtering missed an incompatible route.
  • Whether each selection and exclusion can be explained by the decision record.
  • Whether fallback still satisfies the original capabilities and policy.
  • Whether timeout, rate limit, unsupported features, and quality failures trigger different actions.
  • Whether the number of fallbacks, added latency, and added cost remain within budget.
  • Whether partial output from two Attempts is incorrectly concatenated or consumed more than once.

Otherwise a higher final success rate may come only from unbounded fallback while hiding uncontrolled cost and occasional duplicate Tool Calls.

Back to the problem

Safe Model Routing compiles Task requirements into hard constraints, filters out ineligible candidates, and only then ranks the remainder by cost, latency, and quality. After a failure, it uses the failure class to decide whether fallback is allowed and revalidates the new route against the original execution contract.

Changing a model name only changes the request target. The Routing Decision, compatibility checks, and Attempt boundary are what keep that switch inside the same explainable Agent Run.
