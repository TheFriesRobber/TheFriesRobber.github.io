LLM Infra 11: Preventing Cold-Start Amplification in Multi-Model and Adapter Routing

When the number of models and Adapters exceeds resident capacity, separate artifact identity from residency observation, then manage cold starts through load reservations, popularity, and routing stability.

07/29/2026 Views
LLM InfraInferenceModel RoutingLoRA

The problem

A burst of requests for the same Adapter reaches several gateways at once. Each gateway finds that the target Adapter is not ready, chooses a Replica, and triggers a load. Duplicate downloads and GPU-memory reservations evict hotter Adapters, causing more misses. A cold start for one object spreads across the entire pool.

The problem is not that the Router does not know where the model is. The system has failed to separate artifact identity, physical residency, and an in-progress load operation.

A logical name cannot identify an immutable Artifact

A routable Adapter must bind at least:

artifact_identity:
  base_model_commit: 8f3...
  adapter_repository: example/sql-adapter
  adapter_commit: 91a...
  adapter_config_digest: sha256:...

A name such as sql-lora is suitable for a request, but not as a deployment identity. A path with the same name can be replaced, and an incompatible base model can also prevent the Adapter from loading correctly.

The vLLM LoRA documentation allows an Adapter to specify its name, path, and base-model lineage, and it supports dynamic loading and unloading. Its security documentation gives an explicit warning: Runtime LoRA updating should not be exposed to untrusted clients.

A request must therefore refer only to an artifact resolved by the control plane. End users must not be allowed to inject arbitrary download paths, revisions, or permissions.

An Artifact existing does not mean an Endpoint is Ready

Physical residency also requires an observation:

residency_observation:
  endpoint_uid: replica_a
  artifact_id: adapter_91a
  state: ready
  active_slot: true
  cpu_cached: false
  observed_at: 2026-07-29T12:00:00Z
  generation: 18

This article uses the following conceptual states to describe the lifecycle:

absent
→ reserved
→ loading
→ ready
→ draining
→ evicted

This is a design suggestion for a control plane spanning multiple Endpoints, not a standard vLLM state machine. vLLM’s model manager can maintain registered and active Adapters and use LRU under capacity limits. The cluster layer must still coordinate simultaneous loads across Endpoints, late completions, and the consistency of routing observations.

Single-flight needs one Load owner

When several gateways observe a miss at the same time, the minimum fix is not to choose a random Replica. The load operation needs a unique owner:

load_operation:
  load_id: load_442
  artifact_id: adapter_91a
  reconciliation_key: adapter_91a/pool_chat/generation_19
  owner: residency-controller
  pool: pool_chat
  desired_residency_count: 1
  selected_endpoints: [replica_a]
  reservation_expires_at: 2026-07-29T12:00:30Z
  publish_generation: 19

The operation can proceed as follows:

  1. The Controller first creates a global reconciliation operation keyed by artifact identity + pool/deployment generation.
  2. The first creator obtains ownership. All other gateways may only join the same operation; they cannot select their own Endpoints first.
  3. The owner explicitly sets desired_residency_count before selecting target Endpoints. Warming multiple replicas must be an explicit objective, not an accidental result of concurrent misses.
  4. Each target Endpoint’s load lease is a child operation. The Loader validates the digest, base-model compatibility, and available capacity before loading.
  5. The result is published as ready only while the operation generation remains valid. A loader that finishes after a timeout or cancellation cannot overwrite newer residency state.

Single-flight, reservations, and publish generations are suggestions in this article. They should not be presented as a cluster protocol already built into vLLM. They address repeated execution of the same physical action by multiple controllers.

LoRA affinity and Prefix affinity are different

If a Replica has loaded an Adapter, it can avoid an Adapter cold load. If it holds relevant Prefix KV, it may reduce Prefill work. The two kinds of affinity have different owners, hit conditions, and benefits.

A routing score may consume all of the following:

  • base-model and Adapter compatibility;
  • an active Adapter slot;
  • a Prefix KV observation;
  • free KV or Token budget;
  • Adapter load time and the deadline;
  • tenant isolation.

The order remains compatibility first, capacity second, and affinity last. A Prefix hit cannot justify sending a request to an Endpoint without the Adapter, and an Adapter being ready cannot override tenant Cache isolation.

Eviction must consider reload cost, not only recency

When the number of Adapters exceeds the available active slots, LRU is a reasonable starting point, but not a complete policy. The control plane must also consider:

InputEffect
Recent and predicted popularityLikelihood of another request
Artifact size and load timeRecovery cost after a miss
Sharing relationship with the base modelSet of eligible Endpoints
Current in-flight requestsWhether draining is safe
Tenant reservationWhether minimum residency is guaranteed
Deadline classWhether a cold load can finish in time

Suppose A is hot, B is cooler, and C receives its first burst. Stateless gateways may load C on several Endpoints at once and evict A. A residency-aware control plane instead creates one global operation for C with desired_residency_count: 1. A unique owner chooses one Endpoint, while other requests wait on the same operation or are explicitly rejected.

No specific improvement in hit rate can be claimed in advance. The benefit must be measured with the same workload, Adapter heat distribution, and cold state.

Routing may consume only trusted Residency

The dynamic loading API is a management-plane interface, not a data-plane fallback. The official vLLM security guide requires LoRA load and unload Endpoints to be restricted to trusted administrators and warns that dynamic loading is not a safe operation for untrusted clients.

The complete boundary is therefore:

request model name
→ resolve immutable artifact identity
→ query trusted residency observation
→ choose compatible Endpoint
→ local admission

The artifact registry, residency controller, Router, and Runtime each own different state. Putting all of it in gateway memory makes restarts, concurrent loads, and stale observations difficult to explain.

Back to the problem

The gateways in the opening scenario load the same Adapter repeatedly because “the Adapter is not local” is translated directly into several physical actions. The correct model first resolves an immutable artifact identity. A control plane then manages the global reconciliation operation, desired replica count, and per-Endpoint child leases by artifact and pool generation. Finally, the Router consumes only published ready state.

A cold miss no longer expands automatically into duplicate reservations, eviction of hot Adapters, and cascading misses. The cost is that the system must explicitly maintain load ownership, generations, and an eviction policy.
