A Tool Lifecycle Is More Than a Function Call

07/15/2026
AgentToolsRuntime

The problem

An Agent Tool is often described as “a function with a JSON Schema”: the model generates arguments, the Runtime invokes the function, and the return value goes back to the model.

Tool definition → Model arguments → Handler → Tool Result

That model works well for demonstrating function calling. Suppose the user says, “Save the report in the project directory,” and the model calls:

{
  "name": "write_file",
  "arguments": {
    "path": "/project/report.md",
    "content": "..."
  }
}

Even if the handler has no bug, the call can fail elsewhere. The user may not be allowed to write to the directory. The model may have seen an outdated Tool definition. The file may have been written while the Runtime received only a timeout. Or the handler may return a complete file object that still does not tell the next model turn whether the write succeeded.

The function body alone cannot solve these problems because they occur before the model sees the Tool, before the action executes, while an external side effect occurs, and after the result returns.

The purpose of a Tool Lifecycle is not to invent more stages. It is to preserve identity, authority, and outcome as one logical action crosses those boundaries.

A registered Tool should not always be visible

A registry answers “which capabilities exist in the system?” The current Tool surface answers “which capabilities may this model turn use?” Those sets are not the same.

write_file may be registered but absent from the model input because the user has read-only access, the project workspace is not mounted, or the current phase permits analysis but not modification.

registered tools
      ↓ identity, permission, environment
allowed tools
      ↓ eager, deferred, on-demand
current model surface

The allowed set must be computed before choosing which Tools are eager, deferred, or discoverable on demand. Otherwise an unauthorized Tool may reveal its name, description, or resource types to the model even if execution later rejects it.

Agent Tool Surfaces: Eager, Deferred, and On-Demand Discovery discusses surface selection separately. For the lifecycle, the important fact is which definition a call used and why that definition appeared in the current surface.

Model arguments are an execution proposal

The model-generated path and content describe how it proposes to complete the task. They cannot also decide which user the action represents, which tenant owns it, or whether write permission exists.

A trusted execution combines information from three sources:

InformationSourceExample
Model argumentsGenerated from the taskpath, content
Runtime contextInjected by authentication and policy layerssubject, actor, tenant, deadline
Backend stateMaintained by the resource ownerfile version, directory permission, current lease

Only the first category belongs in model output. Putting tenant_id or authorization scope in a Tool Schema lets untrusted input claim its own authority.

The conceptual handler interface is therefore closer to:

type ToolHandler<Args, Result> = (
  args: Args,
  context: TrustedToolContext,
  signal: AbortSignal,
) => Promise<Result>

args carries the model’s proposal, context supplies trusted identity and execution boundaries, and signal carries deadline or cancellation. They meet at the function boundary but must retain their different provenance.

Schema-valid does not mean executable

A JSON Schema can verify that path is a string and that content stays within a length limit. It cannot prove that the user may modify /project/report.md, or know whether the file changed after the model read it.

Two trusted boundaries still need to make different decisions before execution:

  • The Runtime uses the authenticated subject, actor, and tenant for authorization.
  • The backend uses current resource state to check ownership, version, business constraints, and the transaction boundary.

This is not duplicate validation. Schema rejects structurally invalid arguments. Authorization rejects an action the caller may not perform. The backend rejects a change that cannot be applied to the resource’s current state.

Tool Schemas Are Model-Facing APIs explains the schema boundary in more detail.

A handler exception does not prove that the action failed

Suppose the file service saves report.md, but the response is lost on its way back. The Runtime sees a timeout. Calling the Tool again may overwrite the file, create a new version, or trigger downstream work twice.

A write therefore needs a stable logical identity. Several attempts may belong to one write, but a retry must not silently become a new user action:

write operation_7
  ├─ attempt 1: timeout, outcome unknown
  └─ attempt 2: confirms that file_version_12 exists

The Runtime must retain the operation identity, and the downstream service should provide idempotency or result lookup where possible. At this point the lifecycle records succeeded, definitely failed, or unknown; it does not translate every exception into “nothing happened.”

A successful backend response still should not enter Context unchanged

An external file API may return permission lists, internal storage fields, version history, and several megabytes of content. A successful handler call does not make all of that suitable for the next model turn.

The Runtime should normalize the backend response into a bounded, interpretable Tool Result:

{
  "status": "succeeded",
  "file": {
    "path": "/project/report.md",
    "version": 12
  },
  "content_included": false
}

The result should say whether it is complete or truncated, where its facts came from, and where large content can be read as an Artifact. Without those boundaries, the model may treat a partial result as complete or mistake instructions embedded in external data for trusted instructions.

The lifecycle connects one action

The write_file call has now crossed several owners. The Registry supplied the definition. Policy decided visibility. The model generated arguments. The Runtime injected trusted context. The backend confirmed the side effect. A result normalizer decided what the model would see.

The lifecycle does not require all of this code to live in one service. It requires the decisions to remain linked to the same logical call: which definition the model saw, who authorized which action, which attempts occurred, and which result was finally confirmed.

If those relationships break, the system knows only that “a function was called” and “something failed somewhere.” It cannot distinguish a Tool-selection problem from argument generation, authorization, execution, or result consumption.

Back to the problem

A successful handler invocation proves only that execution reached the function boundary once.

An interpretable Tool Runtime must also ensure that the model saw the currently allowed definition; model arguments could not forge trusted identity; Schema, authorization, and backend state each checked the facts they own; an unknown result did not blindly become a new action; and a successful response was normalized before entering the next model turn.

Once those boundaries remain connected, a Tool is no longer just a function. It becomes an agent capability whose execution can be authorized and whose result can be confirmed.
