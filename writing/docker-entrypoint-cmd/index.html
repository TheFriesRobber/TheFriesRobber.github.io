CMD or ENTRYPOINT in a Dockerfile?

CMD and ENTRYPOINT serve similar purposes in a Dockerfile, but their behavior—especially when combined—requires careful attention.

01/17/2020 Views
DockerTechNotes

The question

How should CMD and ENTRYPOINT be used in a Dockerfile, and how do they differ?

Exec form and shell form

These two forms determine which process becomes PID 1 inside the container.

Exec form

With the exec form, the application itself becomes PID 1 in the container.

FROM alpine:3.9
CMD ["top"]

The command is not executed through a shell, so shell expansion is unavailable. Environment variables such as $HOME, for example, will not be expanded. You can still invoke a shell explicitly when that behavior is required:

FROM alpine:3.9
CMD ["sh", "-c", "echo $HOME"]

Shell form

The shell form runs the supplied command through a shell, which means the shell becomes PID 1.

FROM alpine:3.9
CMD top

This is effectively equivalent to:

FROM alpine:3.9
CMD ["sh", "-c", "top"]

CMD 1

The CMD instruction has three forms:

CMD ["executable","param1","param2"] (exec form, this is the preferred form)

CMD ["param1","param2"] (as default parameters to ENTRYPOINT)

CMD command param1 param2 (shell form)

There can only be one CMD instruction in a Dockerfile. If you list more than one CMD then only the last CMD will take effect.

The main purpose of a CMD is to provide defaults for an executing container. These defaults can include an executable, or they can omit the executable, in which case you must specify an ENTRYPOINT instruction as well.

If CMD is used to provide default arguments for the ENTRYPOINT instruction, both the CMD and ENTRYPOINT instructions should be specified with the JSON array format.

The official documentation describes three forms of CMD:

  • Exec form
  • Default arguments for ENTRYPOINT
  • Shell form

A Dockerfile can contain only one effective CMD. If multiple CMD instructions are present, only the last one takes effect.

In short, CMD provides the default command for a container. If it does not specify an executable, the Dockerfile must also declare an ENTRYPOINT; in that case, CMD supplies the default arguments to that entrypoint.

If the user specifies arguments to docker run then they will override the default specified in CMD.

Images normally provide a default command, but users do not always want to run it. Arguments supplied to docker run replace the default from CMD. Unlike ENTRYPOINT, this also applies when CMD uses the shell form.

ENTRYPOINT 2

ENTRYPOINT has two forms:

The exec form, which is the preferred form:

ENTRYPOINT ["executable", "param1", "param2"]

The shell form:

ENTRYPOINT command param1 param2

An ENTRYPOINT allows you to configure a container that will run as an executable.

Like CMD, ENTRYPOINT defines the default task for a container and supports both exec and shell forms.

Here are a few examples:

  • With an exec-form ENTRYPOINT, arguments supplied on the command line are appended to the entrypoint’s argument list. The following container runs top -b -c:
FROM alpine:3.9
ENTRYPOINT ["top", "-b"]
docker run --rm test1 -c
  • CMD can supply optional default arguments. The following container also runs top -b -c:
FROM alpine:3.9
ENTRYPOINT ["top", "-b"]
CMD ["-c"]
docker run --rm test1
  • Arguments to docker run can replace the defaults from CMD. The final command here is top -b -n 1:
FROM alpine:3.9
ENTRYPOINT ["top", "-b"]
CMD ["-c"]
docker run --rm test1 -n 1
  • When ENTRYPOINT uses the shell form, command-line arguments are ignored. In the following example, ls is ignored (and the CMD is overridden):
FROM alpine:3.9
ENTRYPOINT echo $HOME
docker run --rm test1 ls
  • To replace the default ENTRYPOINT, use --entrypoint:
docker run --rm --entrypoint ls test1

Back to the question

Both CMD and ENTRYPOINT can define a container’s default executable. If an image defines neither, starting the container results in an error. Most images today include at least one of them.

In many cases, using one instruction on its own is sufficient. Their interaction becomes more involved when they are combined. Docker’s reference table3 summarizes the resulting command for each combination:

No ENTRYPOINTENTRYPOINT exec_entry p1_entryENTRYPOINT [“exec_entry”, “p1_entry”]
No CMDerror, not allowed/bin/sh -c exec_entry p1_entryexec_entry p1_entry
CMD [“exec_cmd”, “p1_cmd”]exec_cmd p1_cmd/bin/sh -c exec_entry p1_entryexec_entry p1_entry exec_cmd p1_cmd
CMD [“p1_cmd”, “p2_cmd”]p1_cmd p2_cmd/bin/sh -c exec_entry p1_entryexec_entry p1_entry p1_cmd p2_cmd
CMD exec_cmd p1_cmd/bin/sh -c exec_cmd p1_cmd/bin/sh -c exec_entry p1_entryexec_entry p1_entry /bin/sh -c exec_cmd p1_cmd
