Agent 25: How a Workspace Recovers Across Runtimes

Use Workspace identity, Runtime profile compatibility, and leases to decide whether a stateful execution environment should be reused, migrated, or quarantined.

07/24/2026 Updated 07/27/2026 Views
Agent ProductionAgentSandboxRecovery

The problem

A Python Agent’s Runtime crashes. The system starts a new Runtime, remounts the old Workspace at the same path, and resumes the previous Session.

The first Tool Call corrupts the Workspace. A native extension from the old environment was built for another Python version, its cache is incompatible with the new toolchain, and the previous write still has an unconfirmed outcome. The files are still there, but that does not make the Workspace safe for the new Runtime to take over.

Recovery must answer two different questions:

  1. May the current Session take ownership of this Workspace?
  2. Is the new Runtime compatible with the state that must be preserved in the Workspace?

Leases and fencing answer the first. Explicit Runtime profile compatibility answers the second. Reuse is allowed only when both hold; otherwise the system must migrate, rebuild derived state, or quarantine the Workspace.

Workspace identity must be independent of the Runtime

Equating a Workspace with a directory inside a container makes the Runtime lifecycle determine the file lifecycle. A more robust model is:

ObjectPurposeTypical lifecycle
Workspace identityRepresents a file space in which work can continueAcross Runtimes
RuntimeProvides processes, toolchains, and isolationReplaceable
Workspace leaseDetermines the current write ownerExpiring and transferable
Artifact referencePoints to a stable publishable or downloadable resultAcross Workspaces
Temporary pathHolds disposable intermediate files inside a RuntimeEnds with the Runtime

The same /workspace/report.md means only that the in-process path is the same. It does not prove that the underlying Workspace identity, file revision, or lineage is the same. A recovery record should retain stable references and let the new Runtime materialize them to local paths.

Classify Workspace content by compatibility responsibility

State inside a Workspace does not carry one uniform compatibility promise:

  • User and Task outputs: source code, documents, and data files that generally need to be preserved.
  • Rebuildable derived state: package caches, indexes, and build outputs that can be deleted and rebuilt after a profile change.
  • Runtime-owned metadata: virtual environments, sockets, PIDs, locks, and absolute-path indexes that usually cannot be inherited directly by another Runtime.
  • External Artifact references: references and revisions whose identity must survive a mount-path change.

This classification determines the migration strategy. Treating every directory as a persistent file makes the new Runtime reuse stale binaries and locks. Treating the entire Workspace as cache loses results that the user actually needs.

A minimum manifest can record:

{
  "workspace_id": "ws_7",
  "revision": 18,
  "created_by_profile": "python-3.12@sha256:old",
  "layout_revision": 3,
  "data_schema_revision": 5,
  "mount_policy_revision": 8,
  "zones": {
    "/project": "durable",
    "/cache": "rebuildable",
    "/runtime": "runtime_owned"
  }
}

This is a design example, not a universal provider schema. The important property is that the recovery decision has comparable inputs.

A Runtime profile is a compatibility promise, not an image tag

latest or another mutable image name is insufficient for compatibility decisions. A Runtime profile should pin at least the parts that change how the Workspace is interpreted:

  • image digest and OS/architecture;
  • language Runtime and important toolchain revisions;
  • Workspace layout and mount policy;
  • Runtime-owned metadata schema;
  • the parts of Sandbox security policy that change visible paths or permissions.

Not every difference requires a full migration. Comparison results can be divided into four classes:

ResultConditionAction
compatibleDurable areas retain the same interpretation, and derived state remains compatibleMount directly and validate
rebuildableDurable areas are compatible; cache or Runtime-owned areas are notQuarantine old derived state and rebuild it
migration_requiredLayout or data Schema requires conversionRun a versioned migration under an exclusive lease
incompatibleNo safe migration path exists, or policy forbids itQuarantine and stop automatic recovery

“The same major version is probably compatible” is not a reliable rule. Explicit rules and fixture tests should support profile compatibility. When compatibility cannot be established, quarantine is safer than allowing the new Runtime to write.

Takeover must verify both the lease and the revision

Suppose Runtime A becomes unreachable at Workspace revision 18. The Control Plane gives Runtime B a generation 6 lease. A successful mount is not enough for B to write. It should also establish:

workspace_id = ws_7
expected_revision = 18
lease_generation = 6
profile_decision = rebuildable

The Workspace backend or a trusted write boundary checks generation and revision at commit. If A returns and commits with generation 5, it should be rejected. If the Workspace is already revision 19, B cannot continue using a migration plan derived from revision 18.

The migration itself needs states such as planned → running → verified → committed. On failure, preserve the old revision or quarantine intermediate results so that “the script started” is not mistaken for a completed migration. Creating a new revision or snapshot before an irreversible conversion often makes recovery easier, but the exact atomicity depends on the underlying storage and cannot be promised by the Workspace abstraction alone.

Fencing must reach the actual file-write path

A lease record or Workspace revision field does not stop an old Runtime from modifying an ordinary shared volume that remains mounted. If A can still issue direct POSIX writes, it may overwrite bytes before any revision commit. Detecting its stale generation afterward exposes a conflict but cannot undo the write.

The takeover protocol must therefore choose a boundary that can enforce rejection:

  • the storage service accepts a write token carrying the generation and rejects stale tokens;
  • infrastructure force-detaches the old mount before proving a new single-writer attach;
  • the new Runtime mounts read-only until evidence shows that the old writer has lost access;
  • the Runtime writes only to an isolated overlay or immutable Blob, and the Workspace owner publishes a new visible revision by atomically comparing lease generation and expected base revision.

Storage systems provide different capabilities. If the system cannot prove that A has lost write access, B remains takeover_pending or read-only instead of opening concurrent writes for availability. A scheduling or mount label such as ReadWriteOnce cannot replace the product’s actual enforcement guarantee for an already mounted writer.

The opening also says that the previous write remained unconfirmed. Workspace recovery can observe visible revisions, but it cannot declare the logical operation succeeded or failed on behalf of the Run or Tool effect owner. Recovery queries or reconciles through the original operation/effect reference first. If the unknown effect might still modify the same files, the new Runtime quarantines those paths or waits for the owner to converge. A new lease does not prove that the old operation never happened.

Walk the opening Workspace through recovery

The new Runtime in the opening example uses Python 3.13, while the manifest records Python 3.12:

  1. The Control Plane first confirms that the old lease is invalid and obtains generation 6 for the new Session.
  2. A compatibility rule decides that source files in /project can be preserved while /cache and /runtime/venv must be rebuilt.
  3. The system quarantines the old derived directories as read-only diagnostic data so the new toolchain cannot load them directly.
  4. The Run owner queries the previous unconfirmed write. Only after confirming that no old effect can still mutate /project does the Workspace owner open generation 6’s write boundary.
  5. The new Runtime rebuilds the environment from the lockfile, runs the minimum validation, and advances the Workspace to revision 19.
  6. The Sandbox becomes ready only when revision 19, generation 6, and the target profile all match.

If the lockfile or data Schema has no supported migration path, the result should be incompatible. The user can select the old profile, export an Artifact, or perform a manual migration; the system should not attempt one silently.

A volume pool cannot change recovery semantics

Precreated volumes can move provisioning latency out of the user-facing critical path, but a pooled volume should not have the logical identity of a Workspace before binding. Allocation must still atomically bind workspace_id and perform the same cleanup, initialization, profile, and lease checks.

A volume pool is therefore a latency and cost optimization. It cannot skip compatibility checks or promote “this disk is available” to “this Workspace is recoverable.” Without real latency and idle-cost data, on-demand creation is usually simpler.

Back to the problem

The opening Workspace should not be handed directly to the Python 3.13 Runtime. The correct recovery path first gives the new Session a new lease generation, proves that the old Runtime can no longer write, lets the original effect owner converge the unconfirmed operation, then uses the manifest to separate durable files from rebuildable state, removes incompatible environment state, rebuilds the toolchain, and validates the new Workspace revision.

If the profile rules cannot establish compatibility, the system should quarantine the Workspace rather than treat a successful mount as successful recovery.

The persistent Workspace identity lets files survive across Runtimes. The lease prevents simultaneous ownership. Profile compatibility determines how the new Runtime may interpret the Workspace. Together, they turn recovery from “remount the disk” into a verifiable takeover protocol.
