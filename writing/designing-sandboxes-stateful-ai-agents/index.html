Agent Sandbox 1: A Healthy Container Is Not a Usable Sandbox

Start from a healthy old Runtime that has lost Workspace ownership and derive the minimum stateful Sandbox contract.

07/12/2026 Views
AgentSandboxDistributed Systems

The problem

At 10:00, a network partition prevents runtime_a, a replaceable process executing the Agent, from renewing its Lease. A Lease is time-bounded execution authority issued by the Control Plane. The process remains alive and passes health checks, but it no longer has current execution authority after the Lease expires.

At 10:02, the user sends another message. The system starts runtime_b, mounts the same persistent Workspace—the working directory that must survive process replacement—and issues a new Lease.

At 10:05, the network recovers. A asks to resume with its old Session and Workspace path:

runtime_a: process healthy, lease epoch 41
runtime_b: process healthy, lease epoch 42
workspace: bound to epoch 42

If the Sandbox acquisition flow checks only container health, both A and B appear usable. They may overwrite the same file, repeat Tool effects, or report contradictory results. The rest of this article calls that flow Acquire.

Health answers whether a process responds. A stateful Agent needs to know whether this Runtime may currently represent this Session and continue using this Workspace.

A Sandbox is a verifiable binding, not a container

In this article, a usable Sandbox means:

Sandbox usable
  = Runtime ready
  ∧ Workspace bound to the intended Session
  ∧ Lease held by this Runtime generation

The three facts have different owners:

FactWhat it provesTypical owner
Runtime readinessprocess and environment satisfy current Runtime ContractProvider + readiness checker
Workspace bindingVolume or Workspace belongs to the intended Sessionworkspace/storage control plane
Lease ownershipwhich Runtime generation may perform side effectsSandbox Control Plane

Container ID, Session ID, Workspace ID, and Lease generation cannot substitute for one another. A Runtime may be healthy with an expired Lease; a Volume may mount to the wrong Session; a Lease may be valid before initialization finishes. Any missing condition must prevent Ready.

Runtime Ready verifies an execution contract

running often means only that the main process started. Agent Tools may also depend on:

  • a writable mounted work directory;
  • correct commands and Runtime version;
  • initialized environment variables, credential proxy, or egress policy;
  • readable Skills, Tool bridge, and bootstrap files;
  • a Runtime build compatible with the Session.

Readiness should verify this Runtime Contract, not merely probe an HTTP port. Kubernetes also distinguishes Running from Ready: readiness probes determine traffic eligibility, while startup probes protect slow initialization from premature failure.

For an Agent, traffic eligibility is still insufficient. A Runtime that returns 200 OK with the wrong Workspace cannot execute the user’s task.

Workspace Binding prevents cross-Session mounts

The Workspace is persistent Session state; the Runtime is replaceable compute. Acquire cannot check only that /workspace exists, because an empty directory, stale cache, or wrong Volume can satisfy that condition.

A verifiable binding contains at least:

{
  "workspace_id": "workspace_7",
  "session_id": "session_12",
  "volume_id": "volume_31",
  "mount_path": "/workspace",
  "binding_version": 9
}

An initialization probe should observe the same Workspace identity inside the Runtime. The Control Plane verifies that the current binding still targets the Session. First binding, remount, and Runtime replacement all require new observations; a past successful mount does not prove the current one.

Kubernetes PersistentVolumes outlive individual Pods, enabling a Workspace to span Runtimes. But Volume existence does not prove current business ownership. The upper-layer binding and Lease still do that.

A Lease carries current execution authority

A Lease is time-bounded authority, not a permanent owner field:

{
  "lease_id": "lease_session_12",
  "holder_runtime_id": "runtime_b",
  "generation": 42,
  "expires_at": "2026-07-23T10:07:00Z"
}

When a Runtime performs a side-effecting Tool call, commits a Workspace revision, or publishes a result, it should carry the generation and the resource owner should verify that it is current. This is fencing: even when the old Runtime reconnects, generation 41 is rejected.

Renewal and owner replacement alone do not stop a stale writer if downstream effects never check the generation. The Lease decides current intent; fencing enforces that decision at effect boundaries.

Acquire publishes only after all three facts converge

The minimum flow is:

1. Resolve or create the Session's Workspace binding
2. Obtain a Lease for this Runtime generation
3. Create or reuse a Runtime
4. Mount and initialize the Workspace
5. Verify Runtime Contract and Workspace identity
6. Atomically publish this generation as Ready for the Session

“Atomically publish” does not require a distributed transaction across Provider, database, and storage. It means the Control Plane conditionally commits a returnable Ready record only while the observed Runtime, Workspace, and Lease still match:

{
  "session_id": "session_12",
  "runtime_id": "runtime_b",
  "workspace_id": "workspace_7",
  "lease_generation": 42,
  "ready_contract_version": 3
}

If the Lease or Workspace binding changes before publication, the attempt must revalidate. Observations from different moments cannot be assembled into a state that never held simultaneously.

Reconnect is another Acquire

After a process crash, client disconnect, or Scheduler restart, reconnecting by old runtime_id is tempting. Reconnect cannot restore past authority; it must prove the current binding again.

At 10:05, A may still have the old Session ID, read local /workspace, and pass its health and Runtime Contract checks. Its generation remains 41 while the current binding is 42. The Control Plane must reject it and schedule isolation or termination.

Likewise, a valid Lease for A cannot compensate for a failed Workspace mount. The three conditions must hold in the same Acquire result.

Reconciliation converges partial failures

Acquire spans storage, Provider, and database, so partial failure is expected:

  • Lease issued but Runtime creation failed;
  • Provider created the Runtime but lost its response;
  • Volume mounted but initialization never passed;
  • new Runtime became Ready while old Runtime failed to stop;
  • Scheduler restarted before Ready publication.

A request handler can report only current knowledge; it cannot synchronously roll back every system. The Control Plane compares desired and observed state:

desired: session_12 owned by generation 42, one ready runtime
observed: runtime_b ready, runtime_a still reachable
action: keep b, fence and terminate a

Kubernetes controllers follow the same general pattern: observe current state and repeatedly drive it toward desired state. For a Sandbox, the goal is not just one container. It is exposing only a Runtime that still owns the correct Workspace and Lease.

The minimum return contract

Acquire should return more than an endpoint. It needs enough identity to bind:

  • Session and Sandbox;
  • Runtime and generation;
  • Workspace and binding version;
  • Lease expiry or renewal boundary;
  • Ready Contract version and validation time.

The Tool Runtime can verify later requests against the current generation. Callers need not understand every Provider detail, but must distinguish a replacement Runtime in the same Session from a late response from the old one.

Back to the problem

At 10:05, runtime_a is healthy but unauthorized. It satisfies Runtime readiness, while Workspace and Lease now belong to generation 42 on runtime_b.

Stateful Sandbox usability is a relationship among Runtime readiness, Workspace binding, and Lease ownership. Acquire verifies and publishes it, fencing rejects stale effects, and Reconciliation cleans up orphaned resources left by partial failures.

Once a Sandbox is treated as this verifiable Session Contract, the container returns to its proper role: a replaceable Runtime carrier, not the identity of user state or ownership.
