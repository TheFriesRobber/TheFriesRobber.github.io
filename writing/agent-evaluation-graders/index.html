Which Layer of the Result Should a Grader Verify?

Place deterministic assertions, rule-based Graders, LLM Judges, and domain results for Tools and Context in one evidence hierarchy.

07/24/2026 Views
Agent VerificationAgentEvaluationLLM Judge

The problem

A constructed Eval case asks an Agent to:

  1. update a customer’s address to a specified revision;
  2. write an email explaining the effect of that change.

The final prose reads naturally, so an LLM Judge awards a high score. The backend is still on the old revision, however, and the email applies the wrong delivery rule for the customer’s region.

Asking one Judge to determine whether the database changed, whether domain rules hold, and whether the writing is clear collapses three questions with different evidence strengths into one score. The Judge may trust the Agent’s self-report and cannot inspect the true backend state.

Grader design should begin with: how close is this proposition to a deterministic fact, and what is the strongest available evidence?

Decompose success into observable propositions

PropositionStrongest evidenceCharacter
Address revision changed from 7 to 8backend read or committed eventdeterministic execution fact
Only the target customer address changedmutation diffdeterministic execution fact
New address belongs to Northversioned regional rulesencodable domain decision
Email uses North’s delivery guidanceemail structure + rule mappingmostly encodable
Email is clear and appropriatetext + rubricopen semantic judgment

Each grader then proves only what it can observe. Task success combines these conditions under the product contract; it cannot replace the evidence below it.

Prefer deterministic assertions for existing facts

When a proposition can be observed directly from a Trace, Artifact, database, or explicit contract, use code assertions:

must:
  customer_42.address_revision == 8
  mutation_diff.changed_records == ["customer_42"]

forbid:
  unauthorized_tool_call
  mutation_to_other_customer

must-before:
  committed_revision_event < agent_success_claim

must, forbid, and ordering constraints test presence, prohibition, and sequence. Their failures point to concrete facts without asking another model to reinterpret them.

Deterministic does not mean string equality. JSON Schema, set differences, Artifact hashes, database revisions, Tool effect references, and state transitions are valid assertion inputs when they come from a trusted owner. The Agent’s own “updated” text cannot prove that an update happened.

Code assertions still require versioning, tests, and review. Being implemented in code does not make a contract correct.

Rule-based Graders own encodable domain constraints

Some conclusions are derived rather than raw, yet follow a stable rule:

input: normalized_address + region_rule@12
output: region = North

The evaluator can then verify that the email includes North’s required guidance and does not cite South’s. If the domain owner supplies a stable contract, an LLM Judge does not need to infer it on every run.

A rule-based grader records:

  • input fields and source revision;
  • rule or policy version;
  • the rule that matched;
  • verdict and reason;
  • handling of unknown values.

An uncovered address should produce unknown or manual review, not a silent pass through a default branch.

Use an LLM Judge only for semantics that resist stable encoding

Clarity, completeness of explanation, and tone may be difficult to encode. An LLM Judge is useful there, but it provides a conditional semantic judgment, not a deterministic fact.

task: explain_address_change
candidate_email: ...
grounding_facts:
  region: North
  delivery_rule: ...
rubric_version: email_clarity@4

Separate dimensions such as factual consistency, completeness, clarity, and tone. If the regional rule can be checked deterministically, pass that verdict as grounding or make it a hard gate rather than asking the Judge to vote again.

Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena compares model judges with human preferences and discusses position, verbosity, and self-enhancement biases. For engineering systems, a reasoned Judge output still requires calibration and version governance.

The Judge is itself a system under evaluation

A maintainable Judge contract includes:

  • a resolvable Judge model version or response metadata;
  • rubric, system prompt, and input-normalization versions;
  • a human-labeled calibration set;
  • verdict distributions across repeated trials;
  • handling for pass, fail, uncertain, and invocation failure;
  • cache key, usage, latency, and cost facts;
  • an identity distinct from the configuration under test.

Do not store only the average:

case_id × judge_configuration × judge_trial → verdict

Report agreement with human labels, false positives, false negatives, uncertain results, and denominators. No universal threshold fits every rubric, risk level, or human-review cost.

When Judge model or rubric changes, old and new scores are not directly interchangeable. Run an overlap experiment on the same calibration set, inspect disagreements, and then decide whether historical results need regrading.

Cache and cost must not hide Judge changes

A Judge cache key should contain:

normalized input fingerprint
+ judge model/configuration identity
+ rubric version
+ grading prompt version

Omitting one element can reuse a verdict from an old rubric. Count cache hits separately from real calls. Attribute token, latency, and billed cost only to actual calls; allocate shared infrastructure cost under an explicit method.

“Average Judge cost” must say whether its denominator is scheduled items, actual Judge calls, or Judge Attempts including retries. Provider prices are intentionally absent because they change and do not determine the grader-selection principle.

Preserve hard failure, soft score, and unknown separately

deterministic:
  address_revision_updated: fail
  mutation_scope_exact: pass
rule_based:
  region_mapping: North
  delivery_rule_consistent: fail
llm_judge:
  clarity: pass
  tone: pass
  judge_configuration: judge_config_sha256:...
task_outcome: fail

The missing address commit is a hard failure despite strong semantic scores. If facts and rules pass while the Judge returns uncertain, the system can request human review rather than silently converting uncertainty into pass or fail.

Weighted scores can support ranking and trend analysis but must not dilute a hard invariant. Release gates handle prohibitions and deterministic failures first, then explain how soft scores and denominators are aggregated.

More complex domain metrics keep their own owners

Tool Eval further tests selection, arguments, repair, execution, and mutation precision. Context Eval tests required information, provenance, pollution, conflict, and permission. Those definitions belong to their domains instead of one universal Judge.

The shared selection rule is:

trusted fact directly observable
  → deterministic assertion

explicit domain rule stably encodable
  → rule-based grader

open semantics not stably encodable
  → calibrated LLM Judge or human review

When an open judgment becomes a stable contract, move it down into a rule or deterministic assertion. The evidence hierarchy should become more verifiable as the system matures.

Back to the problem

Backend revision and mutation diff prove whether the address changed. A versioned domain rule proves the region. Only the clarity and tone of the email warrant a calibrated LLM Judge.

One Judge score would let persuasive prose overwrite a real side effect. Use the strongest available evidence, preserve hard failures, soft scores, and unknowns, then combine them under the product contract into a Task outcome.

An LLM Judge is not the final truth layer. It is a versioned, calibrated, repeatedly evaluated, and metered component for questions that deterministic facts and encodable rules cannot answer fully.
