LLM Infra 13: Which Execution Grains Must Inference Observability Align With

Align identity, timestamps, and outcomes across logical requests, attempts, executions, sequences, Replicas, and deployments so that aggregate metrics remain explainable.

07/29/2026 Views
LLM InfraInferenceObservabilityTracing

The problem

Request P95 rises while GPU utilization and aggregate tokens/s remain normal. Without gateway queue timestamps, resolved deployment identity, engine arrival, first scheduling, and cancellation outcome, the platform cannot distinguish three explanations:

  • the workload became longer;
  • placement or queueing became slower;
  • model execution itself became slower.

More averages do not remove the ambiguity. The observability model must first fix the execution grain, then return latency, Token, memory, and outcome facts to their respective owners.

One request expands into several execution objects

At minimum, distinguish:

GrainStable identityFacts it owns
Logical requestlogical_request_idCaller intent and final caller-visible result
Attemptattempt_idOne physical send, timeout, and retry
Model executionexecution_idEngine admission, Prefill/Decode, and Tokens
Sequencesequence_idSampling branch, KV state, and finish reason
Replicareplica_uidRunning/waiting work, KV fraction, and health
DeploymentManifest digestResolved model, Runtime, configuration, and topology

One logical request may produce several attempts through gateway retry, while one attempt may produce several sequences. Attaching every Token to a logical-request counter hides repeated computation. Recording a client timeout as a model failure collapses two observation boundaries.

OpenTelemetry GenAI semantic conventions cover client and server operation duration, Token usage, and requested/response model. They separately define client time_to_first_chunk and server time_to_first_token; the two observe different boundaries and must not be treated as interchangeable TTFT values. These conventions are still marked Development. Placement, batch iteration, KV block, Replica, and TP group also lack a single standard, so the platform needs a versioned local convention rather than a claim that the industry has converged.

TTFT can be decomposed only when the timestamps exist

To explain a slower first output, record:

request_received_at
→ admission_decided_at
→ placement_decided_at
→ engine_arrival_at
→ first_scheduled_at
→ first_token_generated_at
→ first_chunk_sent_at
→ client_first_chunk_at

These timestamps support the following intervals:

IntervalPossible meaning
receive → admissionGateway policy and queue
admission → placementCluster scheduling
placement → engine arrivalNetwork and handoff
engine arrival → first scheduledRuntime queue
first scheduled → token generatedPrefill and first Decode step
generated → sent → receivedServer serialization and transport

If the system records only request start and client first chunk, it can establish that end-to-end TTFT increased, but it cannot infer that Prefill caused the increase. Each latency segment needs timestamps in the same clock domain or explicit clock-skew handling.

Metrics, traces, and events do different jobs

Replica-level metrics are suitable for low-cardinality aggregation:

running requests
waiting requests
KV cache usage
prompt / generation tokens
TTFT / ITL / E2E histograms
preemption and finish-reason counts

vLLM production metrics cover these Runtime dimensions, including running/waiting requests, KV, Tokens, TTFT/ITL/E2E, preemption, and finish reason. They do not provide one counter spanning every engine and transport failure. Gateway or Router failures and scheduling outcomes still need llm-d metrics or a versioned local convention.

High-cardinality identities should not become Prometheus labels. request_id, attempt_id, execution_id, and each batch iteration fit better in traces, structured events, or sampled profiles:

  • Metrics show whether an anomaly exists.
  • Traces connect one request across boundaries.
  • Events record admission, placement, cancellation, and finish transitions.
  • Profiles explain Kernel, communication, and memory details.

Persisting every iteration as metric labels creates cardinality and storage problems. Keeping no iteration evidence makes scheduler interference impossible to explain. A practical boundary is to retain it for errors, slow requests, or sampled traces.

Outcomes must separate failure from unknown

An outcome taxonomy can look like:

attempt_outcome:
  logical_request_id: req_123
  attempt_id: att_2
  execution_id: exec_91
  state: cancelled_after_start
  transport_status: deadline_exceeded
  cancel:
    requested_at: ...
    engine_observed_at: ...
    execution_stopped_at: ...
  usage:
    input_tokens: 2400
    generated_tokens: 91
  gateway_delivery:
    chunks_emitted: 6
    emitted_token_cursor: 47
    transport_status: disconnected
  client_ack:
    protocol: none
    acknowledged_cursor: null

The taxonomy must distinguish:

  • rejected before execution;
  • cancelled before or after execution starts;
  • engine error or CUDA OOM;
  • transport failure after possible partial delivery;
  • completed while client acknowledgement remains unknown.

The Runtime can prove that Tokens were generated. The Gateway can prove which chunks it attempted to emit. Only a protocol with explicit application acknowledgement can record a cursor confirmed by the Client. Without that acknowledgement, whether the Client received, parsed, and committed the output remains unknown.

A timeout likewise establishes only that the observer did not receive the required result before its deadline; it does not prove the server did not execute. unknown is not an observability defect. It is the honest distributed-call result when stronger evidence is absent.

Use evidence to eliminate the three opening explanations

Suppose the completed evidence shows:

workload input-token distribution: unchanged
placement latency: unchanged
engine queue time: increased
prefill execution: unchanged
KV usage and preemption: increased

This supports a bounded inference: the slower first Token coincides primarily with Runtime queueing and KV pressure, rather than slower model compute. Correlation alone still does not prove root cause; the next evidence should inspect scheduler decisions and preemption events.

If instead P95 input Tokens increase while queue and execution time rise with length, workload drift becomes the more direct explanation. The objective is not to find the answer in one step, but to make every explanation falsifiable by the next piece of evidence.

Back to the problem

Whether request P95, GPU utilization, and tokens/s look normal or abnormal, they still do not explain TTFT by themselves. Only aligned identities for logical request, attempt, execution, Replica, and deployment—plus real timestamps at each boundary—can separate queueing, placement, Prefill, Decode, and transport.

The output of observability is not a larger dashboard. It is an evidence model that keeps every failure at the correct grain and makes every explanation falsifiable.
