LLM Infra 09: How the Bottleneck Determines the Inference Deployment Topology

Separate model fit, single-request latency, aggregate goodput, and Prefill/Decode resource asymmetry before choosing Replicas, Tensor/Pipeline Parallelism, Context Parallelism, or P/D disaggregation.

07/29/2026 Views
LLM InfraInferenceParallelismDistributed Systems

The problem

The same instruction—“assign multiple GPUs to one model”—can produce very different results:

  • Tensor Parallelism makes the model fit, but aggregate throughput does not grow with the GPU count.
  • More Replicas increase aggregate throughput, but still cannot handle a single request with an extremely long Context.
  • Prefill/Decode disaggregation reduces interference between phases, but adds KV transfer and cross-pool scheduling.

These results do not contradict one another. Replication, model partitioning, and phase separation solve different constraints. A deployment topology must be derived backward from the bottleneck, not assembled forward from the number of available GPUs.

First separate the constraints into four categories

Model fit

Weights, KV, Activations, and Runtime headroom do not fit on one GPU. The problem is that one executable copy does not fit; creating more copies does not help.

Single-request latency

The model fits, but a single request misses its TTFT or TPOT target. Increasing the parallel degree may shorten some computation, but it also introduces collectives and smaller Kernels. The outcome must be measured.

Aggregate goodput

One Replica already meets the per-request SLO, but the total arrival rate exceeds its service curve. Replicating independent Replicas is usually the most direct candidate in this case.

Phase asymmetry

Prefill and Decode have materially different resource preferences, SLOs, or arrival patterns. Keeping them on one Replica may prevent independent sizing, but separating them introduces KV transfer and two scheduling stages.

Only after identifying the active constraint do we know which deployment topologies deserve comparison.

Replica replication solves fleet throughput

In common Data Parallel serving for a dense model, the system replicates the complete model weights. Each Replica handles independent requests and owns its own KV Cache. vLLM’s Data Parallel deployment supports this structure and can combine DP with TP. MoE is an important exception: combining DP with Expert or Tensor Parallelism may require ranks to align their forwards and synchronize at expert layers, so a failure group and an execution boundary can span multiple ranks.

Replication gives relatively direct failure and scheduling boundaries:

request
→ choose one compatible Replica
→ that Replica owns the sequence execution

It still has prerequisites:

  • A single Replica must already fit the model and the target Context.
  • Each copy needs enough independent batching opportunity.
  • The Router, gateway, and shared storage must not become new bottlenecks.
  • The workload must distribute reasonably across Replicas instead of being pinned by adapter or KV affinity.

Fleet capacity therefore cannot default to Replica count × single-Replica peak. It needs another fleet service-curve measurement with the real routing policy and workload.

TP, PP, and Context-direction partitioning solve different fit constraints

Tensor Parallelism (TP) partitions matrices or Tensors within a layer. A typical Transformer partition performs collective communication inside a block; the exact count and location depend on the implementation. TP can reduce per-GPU weight memory and may shorten some operators, but communication and smaller Kernels create diminishing returns.

Pipeline Parallelism (PP) partitions the model by layer or stage. A single autoregressive sequence still advances according to stage dependencies. Only enough concurrency or enough microbatches can amortize the pipeline bubble. PP is therefore primarily a model-placement mechanism, not a default solution for single-request latency.

Context- or sequence-direction partitioning distributes the state or attention computation of a long sequence across ranks. Whether it is available and how KV is sharded depend on the model architecture and Runtime. “Long Context” alone does not imply one fixed design.

A regular dense deployment is often conceptualized as:

fleet GPUs ≈ DP × TP × PP

This relationship applies only to regular topologies. Context Parallelism, Expert Parallelism, heterogeneous devices, and shared workers all change it.

Prefill/Decode disaggregation solves phase sizing

DistServe and Splitwise place Prefill and Decode in different resource pools so that each phase can choose its own parallelism and scaling policy. vLLM also provides experimental disaggregated prefill. Its current official documentation limits the purpose to tuning TTFT and ITL independently and controlling tail ITL, and explicitly states that this implementation does not improve throughput. Other systems must also be measured against their own versions and workloads; paper results must not be turned into Runtime guarantees.

P/D disaggregation is not merely another Router. It adds:

request
→ Prefill placement and execution
→ KV state transfer
→ Decode placement and streaming

The decision must therefore include:

  • The format, bandwidth, and failure semantics of KV transfer.
  • Whether the Prefill and Decode deployment revisions are compatible.
  • How the two queues jointly meet TTFT and TPOT.
  • Who owns the outcome when one phase succeeds and the other fails.
  • Whether cross-node placement makes transfer costs erase the benefit of independent scaling.

P/D disaggregation is a reasonable candidate only when the value of phase asymmetry exceeds the transfer and control-plane costs. Performance numbers from a paper apply only to the models, hardware, and network it tested; they are not universal thresholds.

Back to the problem

TP did not make total throughput grow with the GPU count because its first job was to make one copy fit, and it added communication to the critical path. Replicas could not handle the extremely long Context because replication did not change the per-Replica state limit. P/D disaggregation added KV transfer because that is the cost of scaling the two phases independently.

The right sequence for deployment topology is to determine whether model fit, single-request latency, aggregate goodput, or phase asymmetry is the active constraint; build candidates for that constraint; and finally measure their service curves with the same workload and SLO.
