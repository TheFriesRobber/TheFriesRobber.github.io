LLM Infra 01: Start by Describing the Inference Workload

Build a workload envelope from input and output Tokens, Prefill/Decode, arrival shape, concurrency, and deadlines so that SLOs, Benchmarks, capacity planning, and scheduling consume the same model.

07/29/2026 Views
LLM InfraInferenceWorkloadCapacity Planning

The problem

Two model endpoints both sustain 100 requests/s. Endpoint A mostly receives short Prompts and produces short outputs. Endpoint B has the same average request rate but includes long Contexts and long generations. A QPS-only dashboard makes the two endpoints look equally loaded, yet B starts queueing earlier and its Time to First Token (TTFT) keeps rising.

The QPS calculation is not wrong. It simply counts requests without describing how much work each request asks the model to perform, how long it holds state, or when completion is still useful.

This article does not build a larger list of metrics. It builds a workload envelope that SLO design, Benchmarking, capacity planning, and scheduling can all consume.

Request count hides Token work

Start with two synthetic workloads. They illustrate the description method; they are not measurements from any model or GPU.

EndpointRequest rateInput Token distributionOutput Token distributionTraffic shape
A100 req/sP50 120, P95 240P50 32, P95 64Uniform arrivals
B100 req/sP50 120, P95 8,000P50 32, P95 1,000One burst per minute

The same request count does not imply the same number of input Tokens, output Tokens, or concurrently resident sequences. More importantly, input and output Tokens cannot simply be combined into one total because they enter different execution phases.

Mainstream inference tools preserve these distinctions as well. vLLM’s per-request metrics separately record prompt_tokens, completion_tokens, queue time, generation time, and inter-token latency. NVIDIA AIPerf separately defines Input Sequence Length, Output Sequence Length, TTFT, and Inter Token Latency. These fields are not a matter of statistical preference. They follow from differences in the execution model.

requests/s is therefore only one projection of arrival rate. It cannot serve as a capacity unit on its own.

Prefill and Decode exert different pressure

Generative inference can usually be divided into two phases:

  • Prefill processes the existing Prompt, computes representations at each layer, and establishes the KV state required for generation.
  • Decode produces new Tokens autoregressively. Each step reads the existing state and appends the state for the new Token.

A long Prompt directly increases Prefill work. A long output keeps a sequence resident in the Decode scheduler and KV Cache for longer. Even two requests with similar total Token counts can produce very different TTFT, inter-token intervals, and memory residency because their input/output ratios differ.

The DistServe paper models TTFT with Prefill and Time Per Output Token (TPOT) with Decode, and it notes that the two phases have different compute and resource characteristics. This conclusion does not depend on adopting any particular deployment architecture: a workload model must preserve execution phases rather than only total Token count.

Endpoint B is no longer mysterious. Long Contexts extend Prefill for some requests, while long generations increase active-sequence residency. Together they change queue and memory pressure, and QPS is blind to both changes.

Average length still hides tail risk

Replacing QPS with “an average input of 400 Tokens and an average output of 100 Tokens” is still insufficient.

Suppose 99 requests contain 100 input Tokens and one contains 30,000. The average reflects total volume, but it does not tell the scheduler whether the long request will block short ones or tell capacity planning whether it will reach a Context or KV limit.

A usable workload description must preserve at least the following distributions instead of only their means:

DimensionWhy preserve it
Input Token distributionDetermines Prefill work and the initial KV footprint
Output Token distribution or limitDetermines Decode residency and the final KV footprint
Input/output correlationShows whether long inputs usually accompany long outputs
Arrival shapeUniform, Poisson, periodic bursts, and concentrated submissions produce different queues
Observed concurrency and connection lifecycleUnder open-loop load, concurrency emerges jointly from arrivals and service time; clients may also cancel streaming requests early
Deadline / priorityThe same amount of work with a different completion deadline is a different service
Model / adapter / featureDetermines which compatible deployment can execute the request

These fields do not require the platform to retain raw Prompts indefinitely. Token counts, buckets, time windows, and approved workload labels support most capacity analysis while reducing unnecessary content retention.

The workload envelope separates observation from forecast

The following is a conceptual schema, not a Runtime API. Its purpose is to separate observed facts from assumptions about the future:

workload_envelope:
  identity:
    model_requirement: chat-compatible-v3
    workload_class: interactive
  observed_window:
    start: 2026-07-28T10:00:00Z
    duration: 15m
    request_count: 90000
    input_tokens: {p50: 180, p95: 2200, p99: 7800}
    output_tokens: {p50: 64, p95: 420, p99: 900}
    requested_max_output_tokens: {p50: 256, p95: 1024}
    input_output_joint_buckets_ref: artifact://wl_7fd2/joint-token-buckets
    replayable_arrival_trace_ref: artifact://wl_7fd2/arrival-trace
    arrival:
      mean_rps: 100
      peak_10s_rps: 175
    observed:
      active_requests: {p50: 38, p95: 92}
      streaming_connections: {p50: 35, p95: 86}
    cancellations:
      before_first_token: 0.012
      after_first_token: 0.006
  forecast:
    horizon: 30m
    arrival_multiplier: [0.8, 1.0, 1.4]
  contract:
    ttft_deadline_ms: 1500
    tpot_deadline_ms: 80
    priority: normal

Token distributions, correlations, arrival windows, observed concurrency, and cancellation outcomes are observations. arrival_multiplier is a forecast. Deadlines belong to the service contract. If all three are mixed together, downstream analysis cannot distinguish “traffic changed,” “the forecast was wrong,” and “the SLO changed.” The marginal percentiles above make the envelope readable; reconstructing the actual workload still requires the joint buckets or arrival trace.

In the synthetic example, Endpoint B should not be reduced to “100 req/s.” It should describe the input and output length distributions in a specific window, the burst pattern, the concurrency, and the deadlines by which requests must receive their first and subsequent Tokens.

The same envelope must flow through downstream decisions

A workload model is valuable only if downstream decisions actually consume it:

  • SLO design uses it to separate interactive, asynchronous, and Batch requests instead of assigning them one shared P95.
  • Benchmarks use it to generate length, arrival, concurrency, and deadline distributions instead of testing only fixed lengths.
  • Capacity planning uses it to choose a service curve measured against the same production workload.
  • A single-Replica scheduler uses it to estimate Prefill, Decode, and KV demand.
  • Autoscaling and admission use it to compare pending work with deadline slack.

If every layer redefines “one request,” metric semantics drift. A Benchmark may prove throughput for short Prompts while capacity planning uses it to promise long-Context service. The gateway may count logical requests while the Runtime counts retry attempts as new demand.

The workload envelope is not the only Source of Truth, but it needs a stable version and fingerprint so every performance claim can answer: which workload does this claim describe?

Back to the problem

Endpoints A and B both receive 100 requests/s, but they do not carry the same workload. B’s long Contexts increase Prefill pressure, long outputs extend Decode and KV residency, and bursty arrivals create queues within short windows.

The right fix is not to add one average Token count to QPS. It is to build a workload envelope that preserves distributions, execution phases, arrival shape, concurrency, and deadlines. The next article can then define what successful delivery means for the same body of work when discussing TTFT, TPOT, throughput, and cost.
