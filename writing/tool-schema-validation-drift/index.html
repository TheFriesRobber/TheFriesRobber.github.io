Agent Tools 8: Why Tool Validation Drifts

Why the same Tool Schema may accept different arguments after provider adapters and executors, and how contract tests keep its semantics stable.

07/14/2026 Views
AgentToolsAPI Design

The problem

Suppose an Agent has a Tool for archiving notes in bulk:

{
  "name": "archive_notes",
  "parameters": {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "properties": {
      "note_ids": {
        "type": "array",
        "items": {"type": "string"},
        "minItems": 1,
        "uniqueItems": true
      }
    },
    "required": ["note_ids"],
    "additionalProperties": false
  }
}

Its intent is straightforward: archive at least one note, reject unknown properties, and reject duplicate IDs within the note_ids array of one Tool Call.

Runtime A passes the Schema unchanged to a binding that supports these constraints. Runtime B’s Adapter preserves type, properties, required, and additionalProperties, but removes unsupported array constraints. The model returns this under Runtime B:

{"note_ids": []}

The same canonical Tool definition is rejected on one path but may reach the handler on another. If the handler happens to interpret an empty list as “archive everything,” an ordinary compatibility difference can become a high-risk side effect.

This is validation drift: Tool arguments no longer follow the same effective constraints across transformation and execution paths.

“Schema-compliant” can mean three different things

A Tool Call is often described simply as “Schema-validated,” but that phrase can collapse three distinct stages:

  1. Whether the provider accepts the Tool definition.
  2. Whether model-generated arguments satisfy the constraints the provider actually enforces.
  3. Whether the Runtime validates those arguments against the canonical contract before invoking the handler.

A provider accepting a Schema does not necessarily mean it supports every keyword in that Schema. In non-strict mode, model output looking like JSON does not mean it satisfies required, range, or array constraints. Some providers’ strict tool modes guarantee conformance within a supported Schema subset, but that guarantee still depends on the mode, model, and supported subset. Passing local Runtime validation also does not prove that the caller is authorized to modify the current resource.

Schema validity, authorization, and business-state validation therefore need separate boundaries. This article covers structural validation across the three stages above; it does not attempt to define a complete Tool security model.

Drift emerges along a transformation chain

A Tool definition commonly passes through this chain:

canonical schema
→ provider adapter
→ provider tool binding
→ model arguments
→ parser / coercion
→ runtime validator
→ handler

Every segment can change semantics:

  • The provider supports only a subset of JSON Schema.
  • The Adapter removes, expands, or rewrites keywords for provider compatibility.
  • The parser automatically converts the string "3" to the number 3.
  • The validator uses a different draft or treats format only as an annotation.
  • A bridge injects default values while another path preserves missing properties.
  • The handler uses a separately maintained DTO that has drifted from the Tool definition.

Some transformations may be acceptable, but they must be explicit contracts. A Runtime may decide that every entry path permits a safe string-to-enum normalization. It must not let that coercion occur accidentally on only one provider path.

A canonical Schema must pin down its dialect first

Keeping one Schema without a dialect is not enough to create a cross-Runtime contract. JSON Schema drafts and vocabularies can interpret keywords differently. The contract must also decide whether format is only an annotation or is evaluated as an assertion.

A canonical binding contract should therefore specify at least:

schema dialect: https://json-schema.org/draft/2020-12/schema
required vocabularies: as declared by the dialect
format policy: annotation only
coercion policy: disabled
default application: runtime-defined, disabled by default

The root Schema’s $schema tells an implementation which dialect to use. The contract must still specify parser, format, coercion, and default policies that $schema cannot define by itself. This example depends on at least the Core, Applicator, and Validation vocabularies: properties, items, and additionalProperties belong to Applicator, while type, required, minItems, and uniqueItems belong to Validation. A Runtime that does not support a required vocabulary declared by the dialect should fail while loading the Tool definition instead of continuing under its own default draft.

The canonical validator is the shared structural-validation boundary

A provider-facing Schema constrains how the model generates a Tool Call. Strict mode can provide stronger Schema conformance within the subset a provider supports. Non-strict mode and lossy transformations are closer to generation guidance. Neither should be the sole trusted execution boundary across providers, because the Runtime must still unify dialect, transformation, and handler-entry semantics.

The Runtime should retain the original canonical Schema and apply the same validation rules after arguments are complete but before the handler executes:

provider says complete tool call
→ parse without hidden coercion
→ canonical validation
→ repairable error or structurally validated handler input

Return to the empty-array example. Even if Runtime B’s Provider Adapter removes minItems, the local canonical validator still rejects the arguments:

{
  "status": "invalid_arguments",
  "tool": "archive_notes",
  "path": "/note_ids",
  "constraint": "minItems",
  "message": "At least one note_id is required."
}

This error can become repair input for the next Model Turn, but the handler is not invoked. Removing a provider-side constraint may reduce the probability that model-generated arguments pass canonical validation on the first try, but it does not silently expand the structural-validation boundary.

An Adapter must report what it changed

If the system saves only the final Provider Schema, it is difficult to tell whether a failure came from the model or from a constraint the Adapter removed. Each Tool Surface compilation can produce a transform report:

{
  "tool": "archive_notes",
  "canonical_revision": 7,
  "canonical_dialect": "https://json-schema.org/draft/2020-12/schema",
  "adapter_revision": 12,
  "provider_profile_revision": 4,
  "preserved": ["type", "properties", "required", "additionalProperties"],
  "dropped": ["minItems", "uniqueItems"],
  "classification": "lossy"
}

Not every dropped keyword requires rejecting the route. The important questions are whether the change alters the accepted argument set and whether the Runtime still enforces the constraint reliably before execution. For differences that affect side-effect scope, data types, or required properties, policy may require the Adapter to return unsupported. For descriptive information that affects only generation quality, policy may allow a lossy transformation, but the loss must remain observable.

Contract tests should start with a case set

Comparing two Schema documents as text cannot prove that they behave the same way. A more direct approach is to maintain provider-neutral cases for every Tool contract:

[
  {"name": "one id", "args": {"note_ids": ["n1"]}, "valid": true},
  {"name": "empty", "args": {"note_ids": []}, "valid": false},
  {"name": "duplicate", "args": {"note_ids": ["n1", "n1"]}, "valid": false},
  {"name": "unknown field", "args": {"note_ids": ["n1"], "all": true}, "valid": false},
  {"name": "wrong type", "args": {"note_ids": "n1"}, "valid": false}
]

The tests have two layers:

  1. Canonical validator test: every Runtime must load the same dialect and validator policy and produce the same result for these cases. An implementation that does not support the dialect fails immediately.
  2. Binding contract test: every Adapter states what its current mode and provider subset guarantee, which constraints are preserved, rejected, or degraded, and verifies that transformation does not accidentally rename properties or omit a required field.

If a test invokes a real model, it should be treated as a generation-behavior Eval rather than a deterministic validator test. A model can produce different arguments under the same Schema. The test should measure results by case × configuration × trial; one success cannot prove that a constraint is always enforced.

Do not hide defaults and coercion in an Adapter

JSON Schema defines default as an annotation. It does not require a validator to fill in a missing property. Some SDKs or DTO layers inject defaults while others do not. Likewise, automatically converting strings to numbers expands the accepted input set. The canonical validator policy must standardize these behaviors.

If the product needs them, the canonical binding contract should say so explicitly:

missing optional field → runtime applies declared default
string "3" for integer → rejected
unknown property → rejected

Every provider path then returns to the same rules before entering the handler. Otherwise, changing an SDK, validator, or language implementation can change the Tool’s effective input boundary.

The handler still needs defensive validation

A canonical Schema can validate only the structure of the current arguments. It cannot know the latest resource state. Even when note_ids is a non-empty array of unique strings, the handler and backend must still check:

  • whether the notes exist and belong to the current tenant;
  • whether the current subject may archive them;
  • whether any note revision has changed;
  • how many notes one operation may archive;
  • whether the current retry Attempt still belongs to the Tool Execution with the same stable identity, and whether an idempotency key, result lookup, or reconciliation prevents repeated side effects.

These checks do not reimplement JSON Schema. They protect facts owned by different layers. The provider binding helps the model generate arguments. The Runtime validator enforces the structural contract. The handler and backend protect authorization, business state, and side effects.

Versions belong in traces and Evals

When validation drift appears on only one route, a trace should link at least:

tool definition revision
tool surface revision
adapter revision
provider capability profile revision
canonical schema dialect and validator policy revision
canonical validator version
handler version

There is no need to copy every complete Schema into every log entry, but stable references must make the original transformation chain reconstructable. Otherwise, a provider update, Adapter change, or handler release mixes old failures with new ones and makes regression tests impossible to reproduce.

Back to the problem

When one Tool Schema behaves differently across Runtimes, the Schema document usually did not change on its own. The provider subset, Adapter transformation, parser, validator, and DTO along each path changed the set of accepted inputs.

The solution is neither to deny the guarantee of provider strict mode nor to trust that one layer has already “validated strictly.” It is to standardize the dialect, vocabularies, and validator policy as one canonical contract: the Adapter explicitly reports what the current mode guarantees, degrades, or does not support; every complete set of Tool arguments passes through the same validator before entering the handler; and contract tests verify behavior with positive and negative cases rather than comparing Schema text alone.

The provider binding can then offer strict generation guarantees within its supported range without becoming the only boundary that decides whether a Tool may execute safely.
