Agent 02: How Run Configuration Stabilizes for Each Turn

Separate long-lived policy from per-turn snapshots, and constrain how control Hooks and read-only Observers may affect those snapshots.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentRuntimeHooks

The problem

An Agent is waiting for a model response, and its current Tool surface includes write_file. An administrator disables that Tool before the response arrives. When the model still proposes write_file, should the Runtime execute or reject it?

If the Runtime reads the “latest configuration” throughout one Model Turn, the model sees an old Tool schema while the executor uses a new allowed set. If configuration is frozen for the entire Run, an emergency disable may take too long to become effective. The question is not whether configuration may change, but at which explicit boundary a change becomes visible.

Policy must first converge into a Run-level execution ceiling

Long-lived policy expresses what the host wants the system to obey, such as which models and Tools are allowed and which resource limits apply. It can change during a Run and may depend on the current user, tenant, and environment.

The Runtime must not let every Turn obtain a fresh unrestricted capability set from this mutable policy. At Run creation, a trusted compiler first resolves entry point, identity, authorization, and policy into an immutable Run envelope:

run_contract_ref: run-17/spec-1
profile_revision: research@12
model_routes: [model-a, model-b]
tool_surface_max: [search, read_file, write_file]
authority:
  grant_revision: grant-31@5
  max_audience: [search-service, workspace-service]
  max_scopes: [web:search, workspace:read, workspace:write]
limits:
  max_model_turns: 40
  deadline_seconds: 1800

The envelope fixes this Run’s selected contract and capability ceiling. It does not contain secrets, provider clients, or current messages. The host persists it with a fingerprint of its canonical content. The fingerprint lets recovery, Traces, and Evaluation determine whether they consumed the same local contract; it is not a security signature that proves provenance.

If later policy adds a Tool or scope, the current Run does not expand its envelope. A capability expansion requires a newly authorized Run. Emergency revocation, expiry, and current backend facts may always narrow the envelope further.

A Turn Snapshot fixes concrete values for this moment

A Model Turn needs concrete values resolved within the Run envelope:

immutable Run envelope
  + current policy narrowing
  + session state
  + runtime resources
           ↓ resolve
      turn snapshot

At a minimum, the snapshot fixes messages, model, thinking parameters, Tool definitions, resource references, configuration revision, and run_contract_ref. The model input, Tool binding, and later validation can then explain both which revision each decision used and why it remained within the Run-creation ceiling.

“Fixed” does not require copying an entire object graph. It requires the observable semantics of this Turn not to be modified in place. Immutable data, versioned references, or controlled reads can implement that rule. The important property is that one Turn must not silently consume two revisions.

Pi currently creates a per-turn object

Pi Harness’s createTurnState() constructs an object that is then reused for the Turn. That is a clearer boundary than reading every field ad hoc. The current construction process, however, contains several asynchronous steps: Session context, resources, metadata, Tool context, and the system prompt may be resolved in sequence while Harness setters can still change the model, Tools, and other configuration.

The resulting object can therefore combine old resources with a new model. A top-level spread is also only a shallow copy and does not guarantee that nested references remain unchanged. Calling this object an “atomic snapshot” would overstate what the current implementation provides.

A host that needs a same-revision guarantee can use either of two common approaches:

  1. Capture configurationRevision before construction, then validate it again after asynchronous resolution; discard and rebuild the snapshot if the revision changed.
  2. Serialize configuration writes while a snapshot is being built, giving readers and writers the same critical boundary.

Both are target contracts for the host layer, not behavior that Pi currently supplies automatically. Pi’s current boundary is visible in agent-harness.ts.

Configuration changes need declared visibility

With revisions in place, disabling write_file has a precise interpretation:

MomentVisible configurationHandling
Model request already sentrevision 12Preserve the semantics of this Turn’s input
Before Tool executionrevision 12 + current security authorizationReauthorize the Tool
Next Model Turnrevision 13Do not expose write_file to the model
After process recoveryoriginal Run envelope plus current narrowing conditionsValidate the fingerprint, revisions, and dependencies before continuing

A snapshot is not a pass that bypasses current security checks. A Tool being visible to the model proves only that it was available at proposal time. Backend authorization still evaluates current facts before execution. If an emergency disable must block every new side effect, the host may reject the old proposal at the execution boundary and return an explainable rejection result.

Hooks may affect a revision only at a declared boundary

Hooks can destabilize the same boundary. If a beforeModel Hook can change the Tool surface, it must say whether the result belongs to the current revision or the next one. An Observer that is nominally read-only must not mutate the snapshot through a shared reference.

Pi currently has several distinct mechanisms:

  • low-level before/after Tool callbacks;
  • typed Harness on() events and their current result-composition semantics;
  • subscription interfaces such as subscribe().

These should not be described collectively as a complete Hook framework. This article considers only their intersection with snapshots: when control-return values take effect and what read-only observers may see. Hook containers, cleanup, a generic reducer, and replay form a separate API-design question.

A simple rule is:

  • A Hook result that changes a later model, Tool surface, resource, or other snapshot configuration must enter a named configuration revision. If it cannot belong to the current revision, it takes effect on the next Turn.
  • A result that only allows or denies the current Tool Call, patches its result, or short-circuits execution is an execution decision or outcome bound to the current snapshot revision; it does not create a new configuration revision.

Back to the problem

Disabling write_file during a Run does not require choosing between “always use the old configuration” and “mix in the new configuration immediately”:

  • The model request already sent remains interpreted under revision 12.
  • The Tool Call is still only a proposal, so the execution boundary may reject it under current security policy.
  • The next Turn uses revision 13 and no longer exposes the Tool.
  • A configuration update may select or narrow only within the original Run envelope. It cannot expand Tools, audiences, scopes, or budget ceilings.
  • Only a Hook or configuration update recorded in an explicit revision may change a later snapshot; a call-local execution decision remains bound to the current snapshot revision and does not create a configuration revision.

Pi provides a reusable per-turn object and several callback and event boundaries, but it does not automatically provide an immutable Run envelope or one atomic snapshot revision across asynchronously resolved fields. Making both layers explicit lets the host preserve the original execution ceiling across recovery and dynamic configuration changes instead of depending on a reassuring name.
