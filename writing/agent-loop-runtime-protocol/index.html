Agent Runtime 1: Why a while Loop Is Not Enough

One Tool write with an unknown outcome shows why a simple Agent Loop can lose track of the task's actual state.

07/15/2026 Views
AgentRuntimeSystems Design

The problem

A minimal Agent Loop often looks like this:

while True:
    response = model.generate(messages, tools)
    if response.tool_calls:
        messages.extend(execute(response.tool_calls))
    else:
        return response.text

The model proposes a Tool Call, the Runtime executes it, and the result goes back to the model. The loop ends when the model stops calling Tools.

For a demo, this is enough. Suppose a user says, “Check tomorrow’s weather in Beijing and save it to my notes.” The model calls get_weather, then write_note, and finally reports completion. When every step succeeds, the execution really does behave like a while loop.

The problem is not that the loop cannot run. It is that the loop describes only the happy path. As soon as one Tool call no longer has a definite outcome, the loop no longer knows how far the task actually progressed.

One timeout breaks the model

Continue with the note-writing example.

write_note saves the content successfully, but the network fails while the response is returning. The Runtime sees only a timeout:

try:
    result = await write_note(content)
except TimeoutError:
    # What should happen next?
    ...

From the Runtime’s perspective, at least three things may have happened:

  1. The request never reached the note service.
  2. The request arrived, but the write failed.
  3. The write succeeded, but the response was lost.

The same timeout observation is compatible with three different underlying outcomes. A simple loop now has several unreliable choices.

Treat the timeout as failure and ask the model to retry, and the user may get two identical notes. Pretend it succeeded, and the system may claim that a nonexistent result exists. Stop immediately, and the current execution path leaves completion unresolved; without a status lookup or reconciliation mechanism, neither the user nor the Runtime learns the outcome.

The missing piece is not another try/except. The loop has conflated two different questions:

  • Did the current function receive a return value?
  • Did the outside world observe a side effect?

A failed return path does not imply a failed external operation. For a read, the distinction may cost only another request. For writing a file, sending an email, or creating an order, it changes the user-visible outcome.

Why one Tool error is not enough

To see why the loop cannot handle this timeout, separate three layers of fact:

model: proposes write_note
Runtime: sends the call but receives no definite response
note service: may already have created note_42

The model can propose the next step. The Runtime can say whether it received a response. Only the note service owns the actual write result. During normal execution, these facts can collapse into one Tool Result; after a timeout, they diverge.

If the Runtime appends only this message:

Tool error: request timed out

the model sees a failed call and will naturally try write_note again. But the message omits the most important fact: the first write did not definitely fail; its result is unknown.

An unknown result is an execution state that requires resolution, not merely a natural-language error. The Runtime must at least remember which write this was, whether it ever received a note_id, and whether the next action should confirm the original outcome or execute again. If a restart restores only messages, that information disappears.

This is where a timeout becomes a retry problem: when the first outcome is unknown, what does “call it again” actually mean?

Before retrying, distinguish “try again” from “do again”

The user asked for one note. Retrying after a timeout sounds natural, but the Runtime first has to decide whether the retry continues the original write or starts a second write.

Suppose the first request created note_42, but its response was lost. If the Runtime treats the retry as a new create request, the result is:

user intent: create one note

first call  → creates note_42, but the Runtime sees only a timeout
second call → creates note_43 and returns successfully

The second request succeeds, yet the user receives two notes. The problem is not a failed retry. The same user intent was executed twice.

The note service needs a way to recognize that both requests are attempts to complete the same write. A common mechanism is a stable idempotency key: an identifier that remains the same across attempts for one logical operation.

first attempt  (operation_7) → creates note_42, response is lost
second attempt (operation_7) → recognizes the same operation and returns note_42

This requires downstream idempotency support, and it requires the Runtime to retain operation_7 after the timeout. If a restarted process restores only the conversation and generates a new identifier, the retry becomes a new write again.

Retry therefore does not mean “call again after failure.” The system must identify which attempts belong to one logical operation and preserve that identity across unknown outcomes and process restarts. Otherwise retry amplifies one uncertain execution into several possible duplicates.

The minimum a Runtime must add

There is no need to design a large schema yet. This example requires only that the Runtime stop treating a logical operation, one call attempt, and the confirmed result as the same thing.

For the goal “create one note,” it needs to preserve three levels:

logical operation: create one note (operation_7)
execution attempts: attempt 1 times out; attempt 2 returns successfully
confirmed result: note_42 exists

One logical operation may have several attempts, but they must converge on exactly one confirmed result. A retry after timeout then continues operation_7 instead of silently creating a new operation.

These facts may live in a state table, event log, or workflow engine depending on the system’s needs. The important decision is not which infrastructure to choose first. It is that an unknown result can survive the current function call—and, when necessary, a process restart.

The while loop may still control execution. The Runtime adds the execution facts that exist outside the loop.

Back to the problem

There is nothing wrong with the while loop. It accurately describes the control flow: the model chooses a next step, the Runtime executes it, and control returns to the model.

What it lacks is a boundary between facts after failure.

When a Tool timeout can mean “not executed,” “failed,” or “succeeded but the response was lost,” the Runtime cannot replace actual state with one error message or ask the model to guess what happened outside it.

At that point, an Agent Loop is no longer just a while loop. The Runtime must distinguish logical operations, execution attempts, confirmed facts, and unresolved outcomes.
