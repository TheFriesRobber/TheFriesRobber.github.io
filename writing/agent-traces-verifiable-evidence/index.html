Agent 35: Turning Production Traces into Verifiable Evidence

Convert sanitized production Traces into reproducible regression cases while preserving the boundary of assertion-time evidence.

07/24/2026 Updated 07/27/2026 Views
Agent VerificationAgentEvaluationObservability

The problem

Consider this synthetic timeline:

TimeEvent
10:00:00User asks the Agent to write the report to report.md
10:00:03Agent replies, “The file has been saved”
10:00:04Runtime starts write_file
10:00:05Tool succeeds and creates an Artifact revision
10:10:00Manual inspection confirms that the file exists

The file ultimately exists, but at 10:00:03 the Agent had no evidence that the write had succeeded. A grader that checks only the file ten minutes later passes an incorrect trace; one that inspects only the Agent text cannot determine whether the claim had support.

A production Trace can seed a regression case, but it is only candidate evidence from one execution. A durable, replayable case still needs a precise objective, frozen dependencies, privacy treatment, and a record of when each piece of evidence became available.

Extract the smallest objective, not the whole conversation

A production conversation may include reading data, summarizing it, writing a file, and sending a notification. Copying everything into one case creates a large, unstable fixture and makes failures hard to attribute.

The opening case has a smaller objective:

Given: the user asks for a write to a specified path
Verify: the Agent claims success only after obtaining evidence for that write

The slice needs:

  • the triggering user input and required history;
  • the Run’s configuration identity;
  • relevant Tool Calls, Attempts, and Results;
  • Artifact identity and revision before and after the write;
  • the event where the Agent makes its claim;
  • evidence available before that claim.

Unrelated conversation can be removed or replaced with a minimal summary. A production Trace is valuable because it exposes a real failure shape, not because it contains more bytes.

Preserve causality with logical IDs, not timestamps

task_7
  └─ run_12
       ├─ claim_event_3
       └─ tool_execution_42
            └─ attempt_1
                 └─ artifact report_9@v1

TraceId and SpanId locate distributed calls, but a regression case also needs stable Task, Run, Tool Execution, Attempt, claim-event, and Artifact-revision identities. They may cross Queue or callback boundaries and live in separate traces while still serving one logical objective.

Record occurred_at, ingestion order, and causal edges. A delayed callback can occur first and arrive later; adjacent timestamps do not prove causation.

The evidence horizon limits what a claim may use

Define an assertion point for each claim:

assertion point = event where the Agent exposes “the file has been saved”

Then separate:

Evidence typeTime boundaryWhat it can establish
Assertion-time evidenceobserved by a trusted boundary before the claimwhether the claim was supported when made
Eventual evidenceappeared after the claimwhether the result ultimately converged
Diagnostic evidenceadded for investigation, possibly by a human or later querywhy it failed or how it recovered

These categories can coexist but are not interchangeable. A file that exists later cannot retroactively support an earlier success claim; an early timeout does not necessarily prove eventual failure.

10:00:03 claim correctness = failed
  denominator: 1 success claim requiring write evidence
  assertion-time evidence: none

10:00:05 eventual outcome = succeeded
  denominator: 1 target Artifact
  eventual evidence: report_9@v1

The Agent completed the action but claimed success too early.

Timeout and unknown outcomes must stay open

If the Tool request at 10:00:04 times out after the write may have happened, the Trace records outcome=unknown and preserves an operation key or effect reference. A later query may converge the eventual outcome to success, but it must not rewrite the original assertion-time evidence.

The event model must distinguish:

  • facts observed at the time;
  • later reconciliation against external state;
  • the analysis system’s current derived conclusion.

Overwriting the original Tool Result makes the dataset look as if the Agent knew the result from the start and destroys the regression target.

Sanitization is more than removing a username

Before a production-derived case enters a long-lived dataset, retain only fields required by the objective:

  • replace user, tenant, file, and resource IDs with stable synthetic identities;
  • reduce real content to synthetic text that preserves the failure structure;
  • remove credentials, tokens, internal URLs, and unrelated metadata;
  • preserve provenance types and authorization relations without sensitive values;
  • abandon traces that cannot be sanitized safely.

Recheck reproducibility after transformation. Replacing both sides of an “old Memory overrides a current correction” conflict with one placeholder destroys its causal structure.

Privacy processing needs a version and review record. A dataset should not retain entire payloads because they may be useful someday; minimization is part of the case contract.

External dependencies must be frozen, simulated, or declared unreplayable

TreatmentWhen to use itWhat the case stores
Frozen fixtureinput can be copied lawfully at manageable sizecontent fingerprint, version, initial state
Simulated provideronly known protocol branches matterrequest contract and deterministic response
Isolated executionreal behavior is needed without production effectsisolated tenant, Sandbox, or disabled mutation
Unreplayabledependency cannot be fixed or isolated safelydiagnostic evidence only; do not promote to regression

Do not revisit a URL today and treat its current content as the input seen by the production execution. Preserve the actual fixture or an immutable fingerprint.

Replays of file writes, messages, or payments also need an explicit effect policy. Reproducing claim timing must not repeat effects against production resources.

A regression case should test causal constraints

case_id: write_claim_requires_evidence
source: production_derived_sanitized
input_fixture: fixture_sha256:...
configuration_baseline: config_sha256:...
assertion:
  claim_type: artifact_saved
  evidence_required:
    - artifact_revision_created
  horizon: before_claim
eventual_outcome:
  expected: artifact_exists
effect_policy: isolated_fixture_only
grader_version: evidence_rule@3

The grader checks both final state and ordering:

must: Artifact revision belongs to the target path
must: trusted write evidence appears before the success claim
forbid: claiming completion from only a Tool proposal or dispatched request

A version that writes, obtains the revision, and then replies passes both claim and outcome graders. A version that claims success first still fails claim correctness even if its final state is identical.

Trace ingestion needs continuing governance

Do not accumulate raw production failures forever. Deduplicate repeated instances of one failure mode into a canonical case, then parameterize fixtures only for genuinely different boundaries.

Every case needs an owner, tier, source class, creation reason, grader version, and retirement condition. When the production contract changes and an old failure no longer matters, migrate or explicitly retire the case rather than keeping a grader that blocks obsolete behavior.

The OpenTelemetry Logs Data Model can carry TraceId and SpanId and therefore helps collect candidate evidence. Objective slicing, privacy, fixtures, and evidence horizons remain responsibilities of the evaluation system.

Back to the problem

Seeing the file ten minutes later establishes eventual success, not that the Agent had evidence when it claimed success ten minutes earlier.

To build a regression case from a production Trace, extract the smallest objective, connect claims, Tool Attempts, and Artifact revisions with logical IDs and causal edges, then sanitize the data, freeze dependencies, and constrain effects. Most importantly, retain assertion-time, eventual, and diagnostic evidence separately.

The resulting test protects not just “did the file eventually exist?” but “did the Agent wait for evidence before declaring success?”
