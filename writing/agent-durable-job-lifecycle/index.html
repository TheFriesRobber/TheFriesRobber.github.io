Agent 31: How Durable Job Cancellation, Results, and Delivery Converge

Use claim leases, generation fencing, an intermediate cancelling state, and conditional delivery to handle duplicate workers, late results, and user cancellation.

07/27/2026 Updated 07/27/2026 Views
Agent ProductionAgentDistributed SystemsJobs

The problem

An Agent submits a Job that converts report.md@v3 to PDF. Worker A receives the message and starts rendering, then stops renewing its claim during a network partition. The Job service lets Worker B take over. Meanwhile, the user says, “Cancel the report.”

After the system marks the Job cancelled, A reconnects and uploads the PDF. The download page then exposes this late result: the scheduler believes the work is cancelled, while the Artifact store sees only a valid upload.

A Queue can redeliver a message, and a cancellation signal can ask a worker to stop. Neither alone decides who may still commit a result. A durable Job needs a more complete lifecycle: a stable Job identity accepts several delivery Attempts; the Job owner uses a claim lease with a generation to assign current execution authority; the result owner fences stale Attempts; cancellation and completion compete through conditional state transitions; and Artifact readiness remains separate from user-visible delivery.

A delivery, a claim, and a Job are different objects

One background operation carries several identities:

ObjectOpening exampleWhen it changes
Jobjob_pdf_9when the user goal or input revision changes
Queue deliverydelivery_18, delivery_19potentially on every redelivery
Execution Attemptattempt_a, attempt_bwhen a worker actually begins execution
Claim generation41, 42when the Job owner transfers execution authority
Result/Artifactartifact_pdf_31@1when output commits successfully
Delivery commitmentdelivery_commit_7when output becomes visible to the user

A Queue visibility timeout or acknowledgment deadline governs only the delivery mechanism. Amazon SQS Standard queues, for example, use at-least-once delivery, and duplicate delivery may still occur during a visibility timeout. Receiving a message does not grant unique write authority over the business Job.

The worker therefore asks the Job owner to claim job_id before it executes:

job_id: job_pdf_9
input: report.md@v3
state: running
claim:
  owner: worker_b
  generation: 42
  expires_at: ...
state_version: 11

This conditional write succeeds only while the Job remains executable, the previous claim has expired, and the input revision is unchanged. Duplicate deliveries may resolve to the same Job, but they do not create a new business intent.

Acquiring a new claim does not prove that the previous Attempt stayed before the external effect boundary. Before rendering again or invoking a provider, B reads the intent, effect reference, and committed result of the same result operation. If A’s result may still be in flight, B queries or enters reconciliation. A claim transfers execution authority; it does not turn an unknown outcome into not started.

A lease assigns current authority; fencing rejects stale results

A claim lease lets the Job owner reassign work after a worker disappears, but lease expiry does not prove that the old process has stopped. Worker A may continue computing, invoking an external service, or uploading a result.

The generation must therefore reach a boundary that can reject the result. A safe commit checks at least:

job_id = job_pdf_9
expected_job_state = running
expected_state_version = 11
claim_generation = 42
input_revision = report.md@v3
result_operation = render:report.md@v3

If the Artifact store and Job store share a trusted conditional-commit boundary, the owner can atomically validate these fields and publish the result. Across stores, a more common design lets the worker upload only an isolated, invisible staging Blob. The Job owner then validates current generation and state before binding a stable Artifact reference as the Job result.

A’s generation=41 upload may leave unclaimed staging data, but it cannot advance job_pdf_9. Background cleanup can remove it according to retention policy. The existence of a Blob must not be promoted into Job success.

Lease refresh also compares generation and state version. A stale worker cannot revive a Job already in cancelling, succeeded, or cancelled. A refresh timeout does not authorize the worker to assume that renewal succeeded.

Cancellation enters an intermediate state first

When the user requests cancellation, the Job owner should not immediately write terminal cancelled. It first conditionally persists the cancellation intent:

running@v11
  → cancelling@v12
  → cancelled@v13

After entering cancelling, the owner:

  1. stops dispatching new Attempts;
  2. rejects refresh from the old generation;
  3. advances the fencing generation or revokes the result-publish capability;
  4. sends a cancellation request to the current worker;
  5. queries external actions that may have crossed an effect boundary.

A cancellation request proves only that the request was sent. Process exit proves only that computation stopped. If a worker already invoked an external service that cannot be queried, the effect outcome may remain unknown.

The Job owner can enter cancelled only after stale Attempts can no longer commit, the current Attempt has stopped or converged, and no effect remains unresolved. With an unknown effect, state remains cancelling or reconciling, or moves to manual review. A simpler UI does not justify fabricating a terminal outcome.

Conditional commits decide whether completion or cancellation wins

Cancellation and completion may reach the Job owner concurrently. Both paths compare the same state and version:

result commit: running@v11 → succeeded@v12
cancel commit: running@v11 → cancelling@v12

Only one conditional write can succeed:

  • Result commits first: the Job remains succeeded; a late cancellation cannot rewrite a completion that occurred.
  • Cancellation commits first: the Job enters cancelling; a result carrying the old version or generation is rejected.

A rejected late commit is not a retryable conflict. The worker queries current Job state. If the Job is cancelled, it abandons or quarantines the staging result. Creating a new Job identity for the late result would bypass the user’s persisted cancellation intent.

For Jobs with independent external effects, the result race also uses a stable operation identity. If the provider executed but the response was lost, the owner queries or reconciles first. It creates a new Attempt under the current valid claim only when evidence proves that dispatch did not begin.

Artifact ready does not mean the user’s goal was delivered

A successful PDF Job proves only that report.md@v3 produced an Artifact satisfying the agreed checks. It does not prove that the user still wants the report or that download authorization has been published.

The two boundaries can remain separate:

Job owner:
  job_pdf_9 → succeeded
  result = artifact_pdf_31@1

Task / product owner:
  goal_state = waiting
  expected_input = report.md@v3
  → publish download reference
  → delivery_committed
  → goal_state = succeeded

The owner of the user-goal state conditionally commits final delivery. It rechecks that the goal is still waiting, the subject remains authorized, Artifact and input revisions match, and any confirmation or policy remains valid.

If the user cancels the whole report goal, the Task owner can first move the goal to cancelling. Even if the Job wins its race and becomes succeeded before fencing takes effect, delivery fails because the goal state no longer matches. Job success remains a true historical fact. The undelivered Artifact follows retention cleanup; the system does not rewrite completed work as cancelled merely to make two statuses look consistent.

For delivery through email, payment, or another external API, local goal state and the remote effect usually cannot commit atomically. That path needs a separate delivery operation, effect key, and reconciliation. delivery_committed is written only when its own evidence supports it.

Fencing keeps late results behind the staging boundary

In the opening, Worker A holds generation 41 and B holds generation 42 after takeover:

  1. On user cancellation, the Job owner conditionally advances running@v11 to cancelling@v12 and invalidates generation 42’s result-publish capability.
  2. B receives the cancellation request and stops. After confirming that no effect is unknown, the Job owner advances to cancelled@v13.
  3. A reconnects and uploads a PDF, but it can write only a staging Blob. Both generation=41 and state=cancelled fail the Job-result binding check.
  4. Artifact cleanup records and removes the unclaimed staging data. The product layer never publishes a download reference.

If A’s valid result had committed before the cancellation condition, the Job would remain succeeded, while the product owner could still withhold delivery according to the cancelled user-goal state. Each owner preserves what actually happened.

Back to the problem

The opening failure was not caused by Queue redelivery alone. It came from collapsing “message received,” “still authorized to execute,” “result ready,” and “delivered to the user” into one Job status.

The corrected protocol resolves every delivery to a stable Job and then acquires a claim lease for the current generation. Fencing carries that authority into result commit. Cancellation enters cancelling and races completion on the same state and version. Finally, the product owner commits user-visible delivery separately.

An old Worker that reconnects can now produce only quarantined late data; it cannot reopen a cancelled Job. Job success also cannot overwrite cancellation of the user’s goal. Durability does not mean work must eventually finish. It means takeover, cancellation, results, and delivery each have a verifiable owner and convergence boundary.
