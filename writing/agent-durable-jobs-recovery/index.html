Recovering Durable Jobs Across Queues and Workflows

Separate Queue redelivery, event publication, and partial success across state owners, then choose the right recovery mechanism for each failure boundary.

07/24/2026 Views
Agent ProductionAgentDistributed SystemsWorkflow

The problem

An Agent writes a file-conversion job to a Queue. A worker finishes the conversion and commits Artifact revision 4 to storage, then crashes before deleting or acknowledging the message. When the visibility timeout expires, another worker receives the same message.

If the second worker treats this delivery as a new job, it may call the external service again and even publish revision 5. If it drops the message because it was “already processed,” it may lose a downstream event that the first worker never published.

The Queue, business database, and Workflow history own different facts. A recovery protocol must first distinguish the logical operation from a delivery Attempt, then choose a mechanism for each commit boundary:

  • Handle duplicate delivery with stable operation identity, idempotency, and fact lookup.
  • Bridge a local business transaction and event publication with a transactional outbox.
  • Converge partial success between Workflow state and external business state with retry, reconciliation, or domain compensation.

One “enable retry” switch cannot replace these mechanisms.

One message may produce multiple Attempts

Start by fixing the identities:

ConceptExampleChanges on redelivery?
Logical operationconvert:file_12:source_rev_3No
Jobjob_42Usually no
Delivery Attemptattempt_1, attempt_2Yes
Business resultartifact_19@rev4Must not be recreated merely because of redelivery

Amazon SQS Standard queues explicitly use at-least-once delivery and tell applications to design for duplicate processing. A visibility timeout also does not guarantee that a message cannot be delivered more than once during that interval. Other Queues have different contracts, so the system must use the official guarantees of the product it actually selected instead of claiming exactly-once in general.

A visibility timeout only hides a message temporarily. Extending it can reduce redelivery for long-running work, but it does not prove that a worker is alive and cannot replace a business lease, idempotency key, or result lookup.

Query business facts before repeating work

The opening timeline is:

t0 attempt_1 receives job_42
t1 artifact rev4 committed for operation convert:file_12:source_rev_3
t2 worker crashes before ack
t3 visibility timeout expires
t4 attempt_2 receives job_42

attempt_2 first queries the business store by operation key:

operation record exists, outcome = committed
artifact_ref = artifact_19@rev4
source_revision = 3

If the record and result are complete, it reuses revision 4, completes any control-plane steps that are safe to repeat, and then acknowledges the message. It does not run the conversion again.

For the query to be reliable, the operation record and business result should be associated within the same business commit boundary. An in-memory “already done” flag or the Queue message ID alone cannot cover process crashes, producer resubmission, or identity changes between Queues.

The lookup may instead return:

  • not started: the current Attempt may execute after acquiring the required lease;
  • committed: reuse the result and continue convergence;
  • in progress with live owner: delay or wait rather than repeat concurrently;
  • unknown/partial: query the external effect or enter reconciliation or manual review.

A timeout must not be classified automatically as not started.

Idempotency is more than a deduplication table

A processed_message_ids table only says that an ID was recorded. It does not say whether the business effect succeeded, what result it produced, or whether the input revision matched.

A more useful operation record binds:

{
  "operation_id": "convert:file_12:source_rev_3",
  "input_revision": 3,
  "status": "committed",
  "result_ref": "artifact_19@rev4",
  "effect_ref": "provider_request_81"
}

If the same key arrives with different parameters, the system should return a conflict rather than the old result. An idempotency key represents a retry of the same intent; it must not merge two distinct business actions merely because their content looks similar.

For an external system that supports neither idempotency keys nor state lookup, automatic retry must be restricted and the result kept unknown. An application cannot prove in its own database that the remote system never executed.

An outbox bridges only a local transaction and event publication

Suppose Artifact revision 4 and the operation record have committed to the database, and the system now needs to publish artifact.ready. If it commits the database first and then publishes directly, the process may crash between those steps. If it publishes first, a consumer may observe business state that does not yet exist.

A transactional outbox writes the business update and pending event in the same local transaction:

DB transaction:
  commit artifact rev4
  commit operation outcome
  insert outbox event artifact.ready

dispatcher:
  read unpublished outbox rows
  publish event
  mark published

The dispatcher can still crash after publishing and before marking the row published, so the event may be duplicated and the consumer still needs idempotency. The outbox prevents loss of the intent to publish an associated local commit. It does not provide end-to-end exactly-once and cannot turn two independent databases into one atomic transaction.

Workflow state is not business state

A durable Workflow can preserve control-flow history, timers, retries, and activity completion. Artifacts, payments, tickets, and files still belong to their respective backends. Either of these states can occur:

Workflow activity recorded timeout
Business backend actually committed

or:

Workflow step completed
Outbox dispatcher has not published downstream event

Recovery chooses an action according to the failure owner:

  • Retry when the operation is safe to repeat or the remote system preserves semantics under the same operation key.
  • Reconciliation when the system can query the Source of Truth and align control state with business state.
  • Compensation when a confirmed business action requires another domain action to offset it, such as issuing a refund or restoring a previous revision.

Compensation is not a database rollback. It may itself fail, be retried, or require authorization, and it exists only when the business domain can define how to offset an action. If an external effect is unknown, reconcile first rather than compensating blindly for something that may never have happened.

A DLQ is an isolation area, not a business terminal state

A message entering a DLQ after exhausting its retry policy means only that the Queue will no longer deliver it automatically under that policy. It does not prove business failure or reverse an effect that already completed.

DLQ handling needs the operation identity, last error, Attempt history, and a way to query the business state. Query facts before redriving. A permanent schema error, revoked authorization, and unknown outcome need different responses, not one “replay all” command.

Backpressure, worker scaling, and Queue selection are resource-governance concerns rather than part of this recovery protocol.

Back to the problem

When attempt_2 receives the duplicate message in the opening example, it queries convert:file_12:source_rev_3 and finds that Artifact revision 4 is already committed. It therefore does not call the conversion service again. It confirms that the outbox contains the publication intent for artifact.ready, lets the dispatcher continue delivery, and finally acknowledges the current message safely.

If revision 4 exists only in the remote system while the local operation outcome remains unknown, the worker reconciles by effect reference. If lookup is impossible, it preserves unknown instead of repeating the work or pretending that it failed.

A Queue retry creates a new Attempt, not a new business intent. The outbox preserves publication intent after a local commit, the Workflow preserves control flow, and the business backend preserves domain facts. Once these owners are explicit, durable work can recover across duplication, crashes, and partial success without relying on nonexistent end-to-end exactly-once execution.
