Agent 04: Context Is a Constrained Projection

Resolve provenance, authorization, conflicts, and budget decisions before provider shaping so that every model input remains explainable and can degrade safely.

07/24/2026 Updated 07/27/2026 Views
Agent CoreAgentContext EngineeringPolicy

The problem

A user has just said, “Contact me in the afternoon from now on.” Long-term Memory still contains an older preference for morning contact, while a query Tool reports that it is currently nighttime in the customer’s time zone. If history, Memory, and the Tool Result are simply appended to a prompt, the model sees three fragments that all look factual but conflict with one another.

Now suppose the input is already close to the model’s context limit. A simple tail truncation may delete the user’s latest correction. Context Assembly is therefore not a message-concatenation problem. It is a constrained projection decision.

Context is not a copy of any state source

History, Memory, files, and Tool Results each have their own fact owner. Context is only a read view generated for one Model Turn. It must not become a source of long-term facts itself.

At least four layers should remain distinct:

LayerResponsibility
Source of TruthStores original facts, versions, and permissions
CandidateContent that may be relevant to the current task
AgentMessage projectionSemantic input after Runtime selection, conflict resolution, and compression
Provider payloadThe final request converted by an Adapter into a model-specific protocol

At the model-call boundary, Pi exposes transformContext and convertToLlm, reflecting the distinction between AgentMessage and provider payload. Pi does not decide every host policy for source conflicts and budgets. Those remain responsibilities of Context Assembly.

Exclude content that cannot enter before ranking

Ranking is not the first step. A candidate that is unauthorized, revoked, outside the current tenant, or missing explainable provenance must not enter the Turn, no matter how high its vector similarity is.

Each candidate should be able to answer at least:

Which source and revision did it come from?
For which time and subject scope is it valid?
May the current subject / tenant read it?
What semantic type is it, and how much budget is it expected to consume?

This information is not intended to turn Context into a database schema. It answers three execution questions: where did this content come from, is it still valid, and may this model see it?

Return to the contact-time example. The user’s new input supersedes the old Memory. The old value may remain in audit history, but candidate filtering should exclude it. The nighttime observation from the Tool affects only whether to send something now; it cannot overwrite the user’s long-term preference.

Resolve conflicts explicitly by authority and time

When two candidates are both valid, the Runtime must still decide whether they complement or conflict with each other. Common signals include:

  • A user’s explicit current instruction normally outranks an older inferred preference.
  • A newer revision from the same fact source outranks a superseded revision.
  • A Tool observation is valid only for its declared time and subject scope.
  • System policy can constrain an action, but it should not fabricate a user fact.

The decision should preferably be enumerable instead of leaving only a final string:

include
exclude_stale
exclude_unauthorized
shadowed_by_newer_revision
compress
truncate_payload

When the model returns an unexpected answer, engineers can then inspect the assembly decision before guessing why the model “ignored” a sentence.

Apply budgets to semantic units

Budget allocation begins only after legality and conflict decisions are complete. Truncating the tail by character or token count can break Tool Result payloads, JSON, references, and conversational causality.

A safer degradation sequence is:

  1. Preserve the current user intent, required system constraints, and unresolved Tool Call/Result pairs.
  2. Produce bounded summaries of older history.
  3. Truncate Tool payloads that can be fetched again while preserving their effect references and critical fields.
  4. Remove optional candidates with low relevance and low authority.
  5. If the input is still over budget, fail explicitly or use a larger context rather than silently deleting a critical constraint.

There is no universal rule that allocates a fixed number of tokens to each source. A source quota is a limit and a protection boundary, not a reserved seat that must always be filled.

The projection result must be explainable

For the opening example, a minimal decision record could be:

user correction: include
old memory: exclude_stale
timezone observation: include, valid for current scheduling decision
older history: compress

The resulting Context can tell the model clearly: the user prefers afternoons; the current local time is unsuitable for immediate contact; if another action must be scheduled, choose the next suitable afternoon. It neither concatenates the three raw fragments nor lets a Tool observation rewrite long-term Memory.

For Pi’s current conversion boundary, see agent-loop.ts. The provenance, conflict, and budget decisions in this article are host-layer design recommendations.

Back to the problem

When History, Memory, and Tool Results conflict, Context Assembly should proceed in this order:

  1. Generate candidates with provenance from their fact sources.
  2. Exclude unauthorized, revoked, and out-of-scope content.
  3. Resolve conflicts by authority, revision, time, and the current task.
  4. Apply structured budget degradation to the remaining semantic units.
  5. Record each include, exclude, and compress decision.
  6. Only then let the Adapter produce the provider payload.

Context is therefore not the set of “everything the system knows.” It is an explainable projection for one Model Turn under the current permissions, evidence, and budget. That distinction gives later Memory, Provider Adapter, and Context Eval work a shared evidence chain.
